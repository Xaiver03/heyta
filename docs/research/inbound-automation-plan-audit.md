## 3. P1：执行前必须补齐

### P1-1：领取租约没有定义跨设备提交的唯一事实，ACK 丢失仍可重复写

**计划位置：38、48、58、60 行。** 租约、持久去重和“重试不产生重复 op”只是目标，尚未定义提交的线性化点、fencing、重领恢复与本地落盘之间的协议。

**代码依据：** `packages/op-log/src/engine.ts:389` 的 `dispatchLocked` 先构造 op 再 `appendLocal`；`:422` 的 `buildOp` 默认生成设备、时间、计数器组成的新 ID。`packages/app-host/src/actions.ts:459` 每次 `create` 分配新实体 ID。当前工作树 `packages/app-host/src/ai-tool-run.ts:126` 的 `autoExecutionRecords` 只是 WeakMap，`:143` 的 `executeAiToolProposal` 明确只在宿主生命周期内去重，并在条目超过上限时淘汰，不能当作持久协议。

**反例：** A 领取事件 E，生成并落盘任务 T1，但在同步上传或 ACK 前断网；租约到期后 B 领取 E，B 尚未同步到 T1，再生成 T2。稍后 A、B 的 op 均上传，账号得到两条任务。仅在 ACK 上检查旧租约编号，最多拒绝 A 的回执，不能撤销已写的 T1。A 挂起至租约过期，B 接手后 A 恢复并本地提交，是同一个问题的另一窗口。稳定实体 ID 可以减少重复实体，却仍可能产生两枚不同 op、两个不同 AI 解析结果及覆盖用户修改，不能独自兑现计划的“无重复 op”。

**最小补充：** 在计划增加事件状态机与崩溃窗口表，定下 `accountId + ruleId + eventId` 的唯一约束、载荷摘要、冻结的规则版本/解析结果版本、执行设备认证身份、单调 lease generation、到期时间，以及每次续租、结果发布、提交声明和 ACK 的 CAS 条件。相同键不同载荷须显式冲突，不能返回旧成功；暂停/删除/权益失效与在途提交须有确定先后顺序。

还必须选择一种能解释“本地已写、中心未知”的完整协议：例如把不可重复的提交身份、准备结果和恢复证据持久化后，再授权唯一提交；无法证明原 worker 未落盘时进入 `commit-uncertain` 并对账，不盲目转派新建。若要求任意设备立即接手，则必须另行证明跨设备确定性提交/同步去重的完整机制。租约 fencing 必须约束实际业务提交，不能只约束队列表。普通本地任务仍应离线可写；这里需要联网确认的是自动化事件处理权。

**receipt 的落点不能含糊：** `packages/domain/src/entities.ts:206` 当前 Task 没有自动化来源 receipt；`packages/op-log/src/state.ts:553` 可以合并新增 payload 字段，因此未来可用可选来源标记随同任务 op 原子落地，再从日志/物化状态重建索引。可是 `packages/storage/src/op-log-store.ts:99` 没有“事件 receipt + op”的联合提交接口；若另建本地表，必须提供等价原子事务或可恢复派生索引。任务被用户删除、归档、日志 checkpoint/归档后，去重记录仍需按约定存活。B 在同步到来源标记前看不到它，所以把 receipt 放进 Task 也**不能单独解决跨设备争用**。

### P1-2：现有原子入口不支持“内容各异的一批新任务”，AC-5 会被误读为接线任务

**计划位置：38、60 行。** “复用 app-host 原子写入口”未区分已有单 op 能力和需要新增的批创建语义。

**代码依据：** `packages/app-host/src/actions.ts:491` 的批完成发一枚 `OpType.Batch`，但 payload 只有共享的完成字段。`packages/op-log/src/state.ts:582` 的 `applyOperation` 遍历 `entityId/entityIds`，对每个 ID 调用同一个 op/payload，不能表示每个任务各自的标题、时间、备注。`packages/app-host/src/ticktick-import-actions.ts:390` 的批导入则循环 `dispatch(entry.intent)`，不是单 op 原子批。`packages/local-api/src/tools/task.ts:128` 与 `packages/app-host/src/local-api-host.ts:648` 的创建契约是单条。

**反例：** 一场会议提取两项行动，执行者循环调用 `create_task`，第一项落盘后进程终止，留下半批；若只把两个 ID 填进现有 `entityIds`，两项会获得同一 payload。已有 Batch 枚举或底层 append 数组都不能自动解决这个差异。

**最小补充：** 把 AC-5 拆出“批创建意图及 reducer 语义”前置项，明确批大小、零项/一项/多项、每项稳定身份、共享来源 receipt、整批校验失败是否全拒，以及不同 payload 的线形状。实现必须覆盖本地原子落盘、远端回放、重复与乱序、checkpoint 恢复、三套存储实现，不允许先 create 后补备注/排期/来源形成多个 op。新增字段可选并有运行时默认；若采用 payload marker，写明版本与能力门槛。不要直接搬用全库快照或导入路径来掩盖新增语义。

### P1-3：付费方向已定，但自托管可验证授权、离线有效期和身份绑定未定

**计划位置：24、26、46、52、56 行。** “单独核验授权”尚不足以实现同样的收费语义。

**代码依据：** `server/src/entitlement.ts:52` 的能力只有 `hosting`、`ai`；`:349` 在 `gate.enabled === false` 时直接返回。能力词表还受该文件头列出的订阅事实源、价格门禁和数据库 CHECK 约束。现有服务端裁决基于本实例订阅行，不等同于官方签发的离线授权。

**反例：** 在自托管配置打开自动收集后直接套现有 guard，可不查权益就放行；反过来要求自托管每次调用官方在线核验却未披露，官方不可达时所有已付费规则停止。若许可证只写账号数字 ID，两个实例的 `userId=1` 可被错误地视为同一主体。

**最小补充：** AC-1 先产出明确授权契约：新 capability 名、套餐包含关系、官方签发者/验证公钥及轮换、签名载荷版本、官方购买主体与实例/本地账号的绑定、有效期、续费与吊销、可信时钟/回拨处理、离线核验与宽限策略。若首版只支持在线验证，就明确写出；不要暗示已有离线授权。管理接口、凭据签发、接收、领取/解析、提交各自的校验点及错误码要列出，定义“已接收后到期”和“解析中到期”如何终止或等待。新增 ADR 与新增迁移承接新能力，不修改既有历史迁移，也不让新开关改变免费同步。

### P1-4：现有托管 AI 计量按请求扣费，无法直接满足事件重试不重复计量

**计划位置：18、46、48、56 行。** 没有定义自动收集费用和模型调用费用是一个账还是两个账，也没有定义失败与重试的消耗点。

**代码依据：** `server/src/ai/metering.ts:282` 的 `consumeManagedAiRequest` 只接收账号、时钟、额度和存储参数；`:345` 附近按 `(user_id, period_anchor)` 累加 requests，无事件 ID。`server/src/ai/managed-proxy.routes.ts:392` 先消费额度，再发上游；`:435` 明确某些发出前失败已消费且不退。`server/prisma/schema.prisma:1306` 的 AiUsageCounter 是周期计数器，不是事件账本。

**反例：** E 的模型请求已计量且供应商已完成，客户端丢失响应；重试 E 再调用托管代理会再次扣数。只让 webhook 接收幂等，不能让模型代理幂等；只在客户端记“已扣费”，崩溃与换设备后仍失效。

**最小补充：** 明确功能权益、事件额度、托管模型额度、BYO 模型费用之间的关系。新增按事件/解析版本/尝试标识归属的持久结算或预留账本，定义 reserve/consume/release/unknown 的状态及周期跨越口径，原子绑定额度裁决与事件状态。冻结已取得的解析结果，提交失败不得再次解析。供应商响应丢失时若无法证明没有执行，规定有限重试和成本承担；区分“用户不被重复扣功能额度”与“供应商物理调用绝不重复”，不能承诺后者已有保证。具体价格、限额和保留期可由负责人给出，契约和测试边界必须先定。

### P1-5：独立密钥“或”HMAC 仍是两种协议，防重放、隔离和查询权限没有落点

**计划位置：24、48、57 行。** 独立凭据与消息完整性不是等价选项。若采用 HMAC，需要明确以该独立凭据为签名材料；若保留 bearer 模式，应单独定义其安全边界。

**代码依据：** `packages/local-api/src/tools.ts:221` 的本机 token 契约只服务回环接口，不能直接放到公网；`server/src/billing/webhook.routes.ts:329` 以后在插件作用域处理原始请求体，再交支付 adapter 验签，该路由不能当成新通用接口。当前计划没有独立的自动收集线协议。

**反例：** 签名只覆盖 JSON 序列化后的 body，时间戳或规则 ID 不在签名内，攻击者可改时间戳重放或挪到另一规则；签名正确但以同一幂等键换正文会被旧结果掩盖；只按 IP 限流无法约束拥有凭据的账号制造大量不同事件。轮换后旧凭据若仍能查结果，撤销语义也不成立。

**最小补充：** 规定版本化请求契约与正反例：method、规范化路径/规则标识、keyId、时间戳格式与允许偏差、来源事件 ID/幂等键、Content-Type、原始字节摘要的签名串；固定算法、编码、常量时间比较、重复 header 处理、压缩请求策略及 UTF-8/JSON 解析边界。签名验证应绑定最终账号/规则映射，账号身份不得由正文自报。凭据权限至少分接收、用户管理、设备领取、结果查询；轮换、撤销、暂停的版本与在途处理行为须明确。

请求总字节、解压后大小（或拒绝压缩）、JSON 深度、字段长度、解析输出数、每账号/规则速率、队列条数/字节与并发预算均需配置边界及拒绝码；永久错误和临时错误要能指导发送方重试。ACK 只在队列持久化后返回成功，避免接受后掉电丢事件。结果查询须验证账号/规则权限，不能用可猜事件 ID 直接查询。

### P1-6：公钥加密暂存还没有接入既有密钥生命周期，结果回执也有新的明文面

**计划位置：38、40、42、48、57、58 行。** 已正确披露接收端看到当次明文；但“用户/设备公钥”尚未选择，不能被当成一个现成字段。

**代码依据：** `packages/shared-schema/src/vault-key-contract.ts:36` 的 Vault 包是口令与恢复码包装的根密钥，没有入站公钥字段；`packages/app-host/src/vault-session.ts:272` 持有对称 rootKey，`:361` 锁定会清理它，`:464` 以后涉及根密钥轮换。不是把现有 package 上传接口多传一个公钥就闭合了。撤销认证设备与撤销已取得的解密能力也不是同一件事。

**反例：** 只用设备 A 公钥封装载荷，A 永久丢失后 B 领取成功但永远不能解密；共用账号私钥却未随 Vault 恢复/轮换保存，改口令或撤销设备后队列不可读或旧设备继续读。接收密文存储合规，但设备 ACK 回传解析后的任务标题、备注，再被状态接口明文保存/回显，就重新暴露了客户端数据。

**最小补充：** 选择账号收件密钥或多接收设备 envelope，写明生成端、算法及 AEAD 封装版本、keyId、账号/规则/事件作为 AAD 的绑定；私钥如何由 Vault 包装、跨设备同步、恢复与存储，公钥如何经认证发布及 CAS 换代。列出新增设备、最后一台设备丢失、Vault 锁定、改口令、root rotation、设备撤销时，已排队密文和在途 worker 的状态及重新封装责任；没有可用解密设备时不得仍显示可处理。

“立即失效”只可承诺停止新的服务端访问/授予，无法抹除离线旧设备已取得的私钥或明文。需界定新事件使用新 key epoch、旧队列迁移/等待/过期策略。密文暂存保护静态存储，不证明接收服务器从未看到或未暂存明文；代理、异常日志、错误详情和备份也必须纳入边界。向发送方的回执/重复结果默认只含不透明事件 ID、状态、错误码和允许披露的计数；任务内容只在客户端解密后展示，不能为了“返回原任务结果”破坏 E2EE。任务 ID 是否向发送方暴露也应明示。

### P1-7：解析字段与真实创建/日历契约不一致，日期的不确定路径互相重叠

**计划位置：24、30、34、59、60 行。** “日历项”尚不清楚是带排期的 Task，还是另建实体；“日期不明确进收集箱”和“时区缺失进待确认”也没有优先顺序。

**代码依据：** `packages/local-api/src/tools/task.ts:128` 的 create_task schema 只列 title/dueDate/priority/projectId，`:234` 映射也不含 note/startDate/durationMinutes/source。`packages/app-host/src/local-api-host.ts:262` 实际接受日期或不带时区的 `YYYY-MM-DDTHH:MM`，用执行设备本地 `new Date(...)` 转 epoch；因此不能简单说它只收日期，也不能当成支持规则时区。`packages/domain/src/entities.ts:206` 已有 note、dueDate、startDate、durationMinutes，其中起点与截止独立。`packages/ui/src/calendar/model.ts:122` 已按 start/due/duration 投影任务，`:490` 的日内桶另有 dueDate 语义；`packages/app-host/src/actions.ts:643` 的排期写入有时长范围。`packages/app-host/src/calendar-anchor.ts:63` 使用当前宿主时区偏移，没有任意规则时区参数。

**反例：** 上海规则的“明天九点”在纽约设备领取，直接复用宿主转换会写错绝对时刻；周日接收、周二处理的“下周”会随队列延迟变化。一场 09:00、90 分钟的会议通过 create_task 被映射后开始时间/时长/备注丢失；后补 setSchedule 又违反原子批。日期已知但没有钟点的课程，是全天还是待确认，现文无法判定。

**最小补充：** 增加输入→中间解析结果→领域字段的逐字段映射表，明确单项/数组、必填、长度、未知字段、批上限、合法清单以及来源标记。首版优先明确“日历显示是 Task 的排期投影”，避免误用 EVENT 倒数日实体。截止、开始、时长不能互相擅自补算；定义 date-only、全天、IANA zone/显式 offset、DST 重叠/缺失时刻、相对日期锚点（来源发生时刻/接收时刻及可信要求）与规则时区优先级。冻结解析上下文，重试不得按今天重新解释。

另列判定表：无日期的正常任务、格式无效、明确日期但缺时间、规则可补时区、时区冲突、过去日期分别进入哪个状态；“待确认”是排队草稿还是已建无日期任务，批里一项不确定是否整批等待。扩展共享工具契约与 app-host 字段验证，不能仅在新 UI 或 worker 私下拼字段。

### P1-8：规则授权尚未定义版本、范围与出境面，不能直接复用助手全量工具授权

**计划位置：24、32、34、42、59、60 行。** “复用工具授权”应复用判定函数和语义，不等于照搬用户对交互助手的所有权限。

**代码依据：** `packages/local-api/src/tools.ts:449` 的 `isToolGranted` 仅判断具体工具是否为 true，不限制清单、操作次数或规则版本。`packages/app-host/src/ai-assistant.ts:123` 按助手档位生成工具 grants；当前工作树 `packages/app-host/src/ai-tool-run.ts:92` 的低风险分类不止 create-task。`packages/ai/src/egress.ts:45` 的 AiFeature 联合与 `EgressConsent` 没有自动收集输入类别，授权绑定 feature/destination；`packages/app-host/src/ai-capture.ts:152` 的 invocation 当前面向短句捕获，`:98` 的输入上限及返回候选语义不能直接代表邮件长文批解析。

**反例：** 用户允许对话助手修改标题，不表示任意回调正文可以调用 update_task；来源文本声称目标清单改为另一个清单，也不能覆盖已授权规则。用户曾同意短句 capture，后台就把整封邮件、额外字段或已有任务上下文发给远端模型，授权披露会失真。规则暂停后，已运行的模型调用返回，worker 使用旧 grants 继续写入。

**最小补充：** 规则授权记录必须版本化并限定目标清单、create-only、输入字段、输出数、解析方式及处理设备范围；领取/解析前/提交前重新核对有效版本，与 P1-1 的失效线性化点对齐。模型只产出受限结构化提取结果，不给来源内容开放工具选择循环、读任务、任意 URL/端点或修改授权；白名单和服务端/宿主校验是边界，prompt 指令只是辅助。

为自动收集新增明确的出境披露及授权标识，或证明现有标识的范围完全匹配并获得相应重新同意；复用 authorizeEgress/invokeRouted，不绕过账号联网同意、提供商选择和字段裁剪。明确定义目标切换、撤回同意、仅本地模型不可用时的暂停/待确认，不能静默转远端。负向判据必须观察实际请求字段和实际提交次数，覆盖正文中的工具指令、模型额外字段和规则配置篡改。

## 4. P2：上线前补齐责任与用户闭环

### P2-1：在线不代表可执行，等待与恢复状态不足以让用户自行排障

**计划位置：24、34、42、58、61、63 行。** 页面列“最近结果”和“等待设备”，还不能区分打开应用、解锁 Vault、续费、授权模型、修正规则分别能解决什么。

**代码依据：** `apps/mobile/src/sync/auto-sync.ts:99` 的 ready 要求前台，`:169` 只在回前台触发同步；`packages/app-host/src/vault-session.ts:361` 会锁定会话。现有同步调度不能被当成新增队列的后台 worker 保证。

**反例：** 用户手机有网络但应用在后台且 Vault 已锁，回调一直“等待设备”，用户不知道必须打开并解锁；本地 op 已提交但尚未同步，另一端查不到，页面却显示无范围的“已完成”。待确认项目在任意设备确认后，旧设备又把旧草稿执行一次。

**最小补充：** 首版明确可处理端与生命周期支持矩阵、自动发现/注册处理设备流程；UI 区分接收、等待可执行设备、待解锁/授权/续费、处理中、待确认、提交结果待核实、本地已创建、同步待完成、完成、永久失败、过期/取消。可以合并展示，但底层原因码不能丢。最近结果必须能定位原因、手动重试、打开创建结果；试运行是否发模型请求/计费、是否保证零业务写入要说清。跨设备确认与重试沿用同一事件身份；对已建任务的撤销是新用户意图，不是重新接收事件。

### P2-2：保留期不只是数值，删除、撤销来源记录和去重寿命必须分开

**计划位置：40、46、48、60、61、63 行。** 只说“上线前明确保留期”没有定义清理对象；“可撤销来源记录”也可能被误读为删除全部由规则生成的任务。

**代码依据：** `server/src/ai/metering.ts:440` 现有清理只针对 AI 计数器；`server/prisma/schema.prisma:1306` 对应的也是该表，不覆盖新队列。`packages/domain/src/entities.ts:45` 以后明确软删/彻底移出回收站不等于抹除 op 历史。AGENTS §8.18 要求新增账号关联数据同步隐私类别、用途、留存和注销范围。

**反例：** 按载荷保留期一起删去重行，上游迟到重试又创建同一事件；删除规则顺带删所有生成任务，会覆盖用户后续编辑；密文队列已清但明文错误详情、结果或备份仍长期保留。

**最小补充：** 分别定义载荷密文、解析结果、最小幂等 tombstone、计量凭据、状态日志和备份的寿命；约定最大重放窗口与过期事件响应，不能让清理重启业务效果。明确规则暂停、凭据轮换、规则删除、事件取消、撤销一次创建、账号注销的不同影响；来源记录的撤销不得自动等于删除用户任务。列出所有新表的账号归属、级联/清理任务、备份期限及中英隐私文档更新。价格/天数未拍板时保持占位并阻止上线，不用现有 AI 的保留数字填空。

## 5. 给下一位执行者的交接门槛

原 AC-1～8 适合作为能力目录，尚不足以作为互不沟通的实现者各自开发的接口边界。以下是交接前需要补入唯一计划或其明确链接的协议文档的内容，不是要求先完成生产功能：

| AC | 交接前必须有的可审阅输入 | 实现后最低验收证据 |
|---|---|---|
| AC-1 | 新能力/套餐决策、官方与自托管授权签发校验、离线策略、事件与模型两类计量契约、迁移清单 | 关闭旧权益 gate 仍挡住未授权自动收集；免费同步仍通过；免费/过期/错主体/错实例/坏签名/额度耗尽均拒绝且不产生业务效果；重试账目可对账 |
| AC-2 | 版本化请求/响应、签名测试向量、权限分离、大小/速率/队列边界、密文 envelope 与查询披露 | 真 HTTP 验证字节签名、窗口、大小、并发限额、跨账号隔离；同键同体重放返回同事件，同键异体冲突；持久化失败不返回 accepted；查询无任务明文 |
| AC-3 | 事件状态机、lease generation/fencing、提交唯一身份、崩溃恢复图、设备/密钥可用判定、ACK 语义 | 两个独立真实宿主和独立数据库执行下述故障窗口；观察任务数、op 数、回执和计量，不只断言 HTTP 成功 |
| AC-4 | 字段映射、冻结的规则/时间/解析版本、不确定状态表、出境授权范围 | 同一事件在不同时区/不同处理日得到相同归一化结果；DST/非法日期/长输入/多输出受限；注入与额外工具字段不能触发越权调用；实际出境请求符合披露 |
| AC-5 | 新批创建 payload/intent、来源 receipt、reducer/存储契约、清单存在与授权校验 | 多项不同字段只产生一枚逻辑 op；中断重启无半批；三个存储适配器及远端回放收敛；删除任务后重试不复活；旧数据无来源字段仍能 hydration |
| AC-6 | 规则版本、预览计费/零写语义、待确认和故障恢复动作、端能力表 | 用户独立完成启用→测试发送→等待→打开/解锁→自动处理→查看结果；暂停/撤销/改规则与在途处理竞态可解释；亮暗、窄屏、中英及各壳入口可用 |
| AC-7 | 与真实部署契约一致的示例、错误/重试指引、隐私及价格说明更新清单 | 官方与自托管样例分别可运行，端点和权限真实；明确后台/锁定限制；仍未上线的能力继续标规划，旧承诺只按新增 ADR 限定范围修订 |
| AC-8 | 平台×权益×设备状态×失败阶段的具体用例表、证据归属、当前产物核验步骤 | 当前源码产物完成仓库要求的跨端安装/实机闭环；Linux 的当前交付定位也应在矩阵中说明，不能被“跨端”两个字隐去 |

AC-3 至少在以下切断点逐项注入中断，每项分别核对中心事件、两个本地库、同步日志和计量结果：

1. 队列已落盘、接收 HTTP 响应丢失；发送方原键重试。
2. 已领取、解析前终止；租约到期后恢复/转派。
3. 模型已计量且可能完成、结果响应丢失；进入已规定的重试/unknown 策略。
4. 解析结果已冻结、提交前终止；接手方不得按新的“今天”或新模型重新解释。
5. 本地 op 已落盘、来源索引/回执尚未完成；同设备重启不再派发。
6. 本地 op 已落盘但尚未上传、ACK 丢失，A 租约过期后 B 领取；最终不得两次创建或偷偷降级成两个 op。
7. A 持过期 lease 恢复，B 已获得新 generation；A 的续租、提交和 ACK 都按明确边界处理。
8. 暂停/删除规则、撤销凭据/设备、权益到期、撤回模型同意、Vault 锁定分别发生在解析中与提交前。
9. 任务被用户编辑/删除、队列正文过期后上游重试；既不覆盖编辑，也不重建删除任务。
10. 第一台设备永久丢失、新设备加入及根密钥轮换；每个保留事件要么可解密恢复，要么有确定终态与可见原因。

所有数值边界均需测试“恰好上限/上限加一”，所有防线至少有能使其失败的负向用例。密钥、正文、恢复码、账号凭据不得写入证据文件；用合成秘密和布尔对账证明未泄漏。

## 6. 最终结论

**不能把当前 65 行计划原样交给执行者直接实施。** 它已经确定产品范围和正确的隐私边界，但 P1-1 至 P1-8 涉及多个包、服务器和设备必须共同遵守的契约；让各执行者在 AC 内自行选择，会产生互不兼容的授权、加密、计量和去重实现。

建议先完成一轮有负责人裁决的协议补充，依次固定权益/授权与密钥身份、事件及提交状态机、批创建与字段/时区语义，再将 AC 拆给执行者。P2 项可以与实现并行，但不得遗漏上线验收。此文不新增第二份实施计划；所有裁决与进度仍应回到 [inbound-automation.md](../plans/inbound-automation.md)。此次审计完成只表示交接缺口已被列明，**不表示自动收集功能已开发、可购买或已上线**。
