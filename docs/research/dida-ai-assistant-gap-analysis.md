## 0. 一句话结论

**三句话，按重要性排序：**

1. 🔴 **今天挡住用户用 AI 的不是工具列表，是一条全仓零记录的 CORS。**
   heyta 只有两个内置端点预设，都是回环地址；Web 应用挂在 `https://heyta.waytofuture.cn/app/`，
   浏览器带 `Origin: https://heyta.waytofuture.cn` 请求本机 Ollama 时**被回 403**。
   全仓 `OLLAMA_ORIGINS` 出现 **0 次**。用户看到的是"AI 不可用，去设置查端点"，而设置里没有答案。
   证据与探针为什么看不见：§6。
2. **形态差距是真的，但它是**一个有理由、且挂着豁免条件的主动决策**，不是漏看。**
   `docs/adr/0005-ai-data-path.md` §3.1 末尾明文"**本 ADR 维持那条禁令 —— 不做聊天助手**"，
   而它维持的那条反需求（`docs/research/feature-matrix.md` §11）写的是
   "内嵌 AI 聊天助手（**除非明确有差异化价值**）"。所以今天要做的不是补漏，是**重新裁决一个条件句**。
   证据：§7。
3. **能力面差距可以量化：滴答对外 51 个工具 / heyta 6 个；且 heyta 的 6 个里有 3 个在 AI 路径上结构性不可达。**
   不可达的原因不是没写，是**单步架构下模型永远拿不到 `entityId`**。证据：§3.4。

**反向结论（不写进报告就是失真）**：在"AI 能不能绕过用户确认直接改数据"这一条上，
heyta 比滴答**强一个量级** —— 我们是类型层 + 静态门禁的硬保证，滴答是文档里教用户"等我确认后再执行"。
详见 §5。

### 2.1 🔴 截图 B 那句拒绝，对用户是一句**产品谎言**

滴答产品本身**完全支持**这件事：倒数纪念日的日期**可选公历或农历**、可加多个提醒、可设重复。
官方帮助中心甚至给了两条手工路径（直接输入"农历x月x日"让智能识别；或先选阳历再"设置重复-农历每年"）。
出处：[《添加倒数纪念日》](https://help.dida365.com/articles/7321447466803396608)、
[《设置重复任务》](https://help.dida365.com/articles/6950660365923385344)（两篇均已过 §10 的逐篇归属核对）。

所以它说的"在我们的产品里，纪念日只能查看不能新建"，**对模型是实话（工具表里确实只有 `list_countdowns`），
对用户是错的**。

> **这条区分是本文最重要的产品结论之一**：诚实拒绝必须把「**我没有这个工具**」和「**产品做不到**」
> 分成两件事说。heyta 要抄的是"先看能力清单再答"这个**动作**，**不要抄它的主语**。
> 正确的话术形状是："我没有建纪念日的工具，但产品支持它，路径是 Y。"

而这句话在 heyta 恰好有一个时间窗：见 §7.3。

## 3. heyta 现状（逐条回到代码）

### 3.1 形态：严格单轮，第二轮在**类型上表达不出来**

```
packages/ai/src/routing.ts:873-878
  // 数据面**恰好**是 system + user（+ 可选 tools）。没有别的字段。
  messages: [
    { role: 'system', content: invocation.system },
    { role: 'user', content: invocation.user },
  ],
```

`AiInvocation`（`packages/ai/src/provider.ts:86-103`）只有 `system` / `user` / `fields` / `tools?`
—— **没有 messages 数组，也没有 history 字段**。

- 全仓唯一的 `for` 循环是**跨端点故障转移**（`routing.ts:706-708`，`maxAttempts: 2`），不是 turn 上限。
- 零 `response_format`、零 SSE、零 token streaming。
- 会话历史无处存放。

⚠️ 这不是"忘了做"。`messages` 那行的注释和 `AiInvocation.fields` 的注释说明它是一个**刻意的数据面契约**：
每次出境必须逐字段声明（`fields` 就是披露依据，工具名本身也算出境数据）。
不过 [`../adr/0035-ai-tool-calling-reuses-local-api.md`](../adr/0035-ai-tool-calling-reuses-local-api.md) §表格
已经为这个矛盾给出过解法（"循环**开始前**按可达工具集算出字段并集**一次性披露**；步骤要发集合外字段 → **停**"），
所以**扩到多轮并不需要推翻出境模型** —— 这一点必须写清，否则会被误读成"架构冲突，做不了"。

### 3.2 工具目录：**6 个**，只碰 TASK / PROJECT

`packages/local-api/src/tools.ts:75-114`（全仓唯一一份；ADR-0035 声称内置 AI 与 MCP 共用，
`isToolGranted` / `runReadTool` / `toWriteIntent` / `listAuthorizedTools` 四处共用**逐条核实成立**，
并由 `check:ai-tools` 静态钉住 —— 这部分没有漂移，是好消息）：

| 工具 | 读/写 | 作用实体 | `defaultEnabled` |
|---|---|---|---|
| `list_tasks` | 读 | TASK | `false` |
| `get_task` | 读 | TASK | `false` |
| `list_projects` | 读 | PROJECT | `false` |
| `create_task` | 写 | TASK | `false` |
| `update_task` | 写 | TASK | `false` |
| `complete_task` | 写 | TASK | `false` |

目录文件头写着它的设计立场（`tools.ts:70-74`）：

> "够用就停 —— **工具每多一个，'默认关'的清单就长一条，而用户不可能逐个理解它们的风险**。
> 所以只留 6 个：3 读 + 3 写。宁可将来加，不要现在删。"

🔴 **覆盖度要分两个口径说，否则会造出一个测不准的门禁**（这直接决定 W10 那条门禁长什么样）：

`packages/domain/src/entities.ts` 的 `EntityModelMap` 有 **10 个成员**：
`TASK` `PROJECT` `TAG` `NOTE` `HABIT` `HABIT_LOG` `FOCUS_SESSION` `REMINDER`
`AI_FEEDBACK` `PREFERENCE_CORRECTION`。

| 口径 | 分母 | 工具覆盖 | 比 |
|---|---|---|---|
| 全部已物化实体 | 10 | 除 `AI_FEEDBACK` / `PREFERENCE_CORRECTION` 外的全部 8 格 | **8/10 = 80%** ⚠️ 2026-10-03 现量（同一天里本行先后记过 2/10 与 3/10）|
| **用户可操作**的已物化实体（剔掉 `AI_FEEDBACK` / `PREFERENCE_CORRECTION` —— 那两个是 AI 反馈与偏好纠正的**落库载体**，用户不直接创建） | **8** | **全部 8 格**（`TASK` `PROJECT` `TAG` `NOTE` `HABIT` `HABIT_LOG` `FOCUS_SESSION` `REMINDER`） | **8/8 = 100%** ⚠️ 2026-10-03 现量（命令：`node scripts/gen-ai-capability-manifest.mjs --check`）。
**这一行的历史比它的数更值得留**：同一天记过 **2/8**（口径错 —— `covered` 判"有任一工具"，把只有一个只读 `list_projects` 的 `PROJECT` 算成已覆盖）与 **3/8**（口径对、但只是当天早几小时的读数）。口径现已收成"**读和写都有**"（`countsAsCovered()`，见 §3.2 与 `ai-event-tool-contract.md` §2.1）。
🔴 **两个"100%"都不是"AI 能做界面上所有事"**：门禁只判到"每格有一读一写"，**每格内的动作缺口**逐条记在 `ai-event-tool-contract.md` §5.4（清单里 `HABIT` 的改目标、`TAG` 的删除这类是"还没做"，改颜色/图标这类是"要产品先回答谁给 AI 赋义"）。|

三个容易踩混的地方，写门禁前必须先分清：

1. **四象限与搜索不是实体**。`packages/shared-schema/src/entity-types.ts` 的设计原则第 2 条明写
   "**视图不建实体** —— 四象限、今日视图、日历都由 TASK 的字段派生"。
   ⇒ 它们该有工具（"帮我排四象限""搜便签"），但**不该出现在实体覆盖表里**，否则门禁的分母会随视图增删漂移。
2. **`TASK_REPEAT_CFG`（重复规则）在 `ENTITY_TYPES` 里，但**不在** `EntityModelMap` 里**
   ⇒ 它是同步协议认识的实体，却没有领域模型。所以"重复规则零工具"这句话**不能**写成
   "有一个已物化实体没配工具"，只能写成"重复的**动作**没有工具入口"
   （零件确实有：`packages/app-host/src/repeat-presets.ts` 的 `RepeatPresetId`）。
3. `HABIT_LOG` 与 `HABIT` 是**两个**实体（打卡记录独立），滴答的对应面是
   `upsert_habit_checkins` 一个工具管两件事，且**回填范围限最近 90 天** ——
   那个"用范围上限代替自由写"的形状与 §3.5 的 W3 是同一条设计思路。

⇒ 结论不变但措辞要准：**用户可操作的 8 个已物化实体里，工具只覆盖 2 个**；
另外"标签 / 便签 / 提醒 / 专注 / 习惯打卡"各自独立成实体，也各自零工具。
而它们的**动作层零件全都已存在**（`packages/app-host/src/actions.ts`、`repeat-presets.ts`、
清单与标签共用的 `OrganizerSection` 那条线）—— 属于"**零件都在、没配工具**"，不是"零件没有"。

### 3.3 工具选择：4 条正则，且**一条都不指向写入**

`packages/app-host/src/ai-tool-selection.ts:94-119`，`DEFAULT_TOOL_SELECTION_RULES` 共 4 条：

| 规则 id | 命中工具 | 传出的 args |
|---|---|---|
| `list.projects` | `list_projects` | `{}` |
| `list.today` | `list_tasks` | `{}` ← 🔴 见 §3.5 |
| `list.completed` | `list_tasks` | `{ completed: true }` |
| `list.tasks` | `list_tasks` | `{}` |

**全部指向只读工具。** 这是 ADR-0035 §"拒绝的选项"里的第 6 条明文决定的：
"**默认只读。默认规则集不含任何写工具；写工具要显式注入规则才会被选中。**"
所以"没有写入规则"是纪律，不是遗漏 —— 但它同时意味着 §3.4 那个结构性锁**叠了两层**。

### 3.4 🔴 单步 ⇒ 所有需要 `entityId` 的工具在 AI 路径上**结构性不可达**

```
packages/app-host/src/ai-tool-call.ts:267-274
  if (calls.length > 1) {
    return { ok: false, reason: 'multiple-tool-calls',
      message: `模型一次要求调用 N 个工具，而当前只支持单步。请说得更具体一点。`, ... };
  }
```

推理链（每一步都有代码位置）：

1. `update_task` / `complete_task` / `get_task` 要求 `taskId`（`packages/local-api/src/server.ts:300-302` 显式校验：`get_task 需要 taskId。`）。
2. 模型要拿到一个**真实** `taskId`，必须先读一次（`list_tasks`）再引用它 —— 这是**两次**工具调用。
3. 单步架构在第 2 次调用前就返回 `multiple-tool-calls` 失败。
4. ⇒ **这 3 个工具在生产 AI 路径上永远拿不到合法入参**。它们不是"没做完"，是"做完了也到不了"。

另一条配套事实：第 5 个功能面板（`AiToolRun`）**没有任何浏览器级行为用例** ——
`e2e/tests/` 下 AI 相关只有
`ai-breakdown` / `ai-capture` / `ai-duration` / `ai-prioritize` / `ai-row-layout` / `ai-unavailable` 六个。

⚠️ **这条推论要单独记**：它说明**"把 P3 做完"不等于"能复现截图 A"**。
ADR-0035 与计划里 P3 的定义是"**多步只读循环**"，写永不进循环（那是 §5 的强项，不该改）；
而截图 A 是 **3 读 + 1 写**。所以补齐它需要的是**"读循环 + 末尾一次写提案"**这个
**当前计划里没有名字**的形态。这是 §7.2 那条内部分歧的实质。

### 3.4.1 执行链的真实形状（本轮逐个数过消费点，并纠正初稿的一处误报）

初稿曾把 `runAiTool` / `grantedToolNames` 零生产调用点写成"**零件没接线**"。
**那个推断是错的** —— 真实形状是"**一个执行核 + 两个前门，其中一个前门多余**"：

| 入口 | 定义处 | `apps/` 消费点（排除测试与 `dist/`） | 性质 |
|---|---|---|---|
| `resolveToolSelection`（规则前门） | `ai-tool-selection.ts` | **4** | ✅ 已接线 |
| `requestToolCall`（模型前门） | `ai-tool-call.ts:178` | **4** | ✅ 已接线，**且是界面实际走的那条** |
| `runSelectedTool`（执行核：目录 / 授权 / 参数 / 读执行 / 写提案） | `ai-tool-run.ts:129` | 直接 0，但被 `requestToolCall` 在 `ai-tool-call.ts:210` 与 `:303` 调用 | ✅ **唯一执行核，活着** |
| `confirmAiToolProposal`（全仓唯一 `submit`） | `ai-tool-run.ts:183` | **3** | ✅ 已接线 |
| `runAiTool` | `ai-tool-run.ts:106` | **0** | 🔴 **冗余外壳**：`ai-tool-run.ts:112` 只是转调 `runSelectedTool`。删它不丢任何能力 |
| `grantedToolNames` | `ai-tool-run.ts:191` | **0** | 未用（给模型看的目录投影走 `toToolDescriptors` / `listAuthorizedTools`） |

⇒ **修正后的结论**：写入能力**今天是可达的**
（`requestToolCall → runSelectedTool → 提案 → confirmAiToolProposal`）。
唯一挡住"改某一条具体任务"的，是 §3.4 那条**单步锁**，不是缺接线。
这个区别决定性质：**AI-G4 不是"补功能"，是"放开一个架构约束"** —— 工作量与风险完全不同。

⚠️ 顺带一条文档债：`ai-tool-call.ts:31-34` 那张"谁负责什么"的对照表**通篇写 `runSelectedTool()`**，
而该模块的真实入口叫 `requestToolCall` ⇒ 读那张表会以为存在一个叫 `runSelectedTool` 的前门。

### 3.5 🔴 当下就在给用户错数据的一条缺陷

- `list_tasks` 的执行器**只认三个参数**：`projectId` / `completed` / `limit`
  （`packages/local-api/src/server.ts:290-297`）—— **没有任何日期参数**。
- 而规则 `list.today`（`packages/app-host/src/ai-tool-selection.ts:102-106`）命中"今天要做什么"之后
  传的是 `args: () => ({})`，**空参数**。

⇒ 用户问"今天有什么任务"，AI 拿到的是**全量任务的前 N 条**，与问"列出任务"逐字相同，
而界面按"今天"回答。对照 `list.completed` 至少传了 `{ completed: true }`，
说明写规则时想到过要带参数，只是 `list.today` **无可传的参数**。
**现有测试只断言 args、不断言结果**，所以它一直绿。

### 3.6 时间锚点：四条链路里只有一条有，且不传时区

"今天是几号"只进了 `ai-capture.ts:182` 一条 prompt；拆解 / 估时 / 排序 / **整条工具链**都没有日历锚点，
**也从不传时区**。相对日期"14号"**没有任何一层负责解析** —— 规则内核只有 `X月Y日`
（`packages/app-host/src/capture.ts:353`），没有裸日规则。

这个立场有实测依据（`packages/ai/src/index.ts:23-27` 记录：模型曾把"明天"算错**四个半月**），
所以"不信任模型算日期"是对的；**缺的是替代它的那件工具**（滴答的 `CalendarInfoTool`）。

## 5. 三处我们比它强，报告里不能抹掉

1. **越权防线不靠提示词。** 全仓 `host.submit` 只出现在 `confirmAiToolProposal()` 一处
   （`packages/app-host/src/ai-tool-run.ts:183-188`），由 `check:ai-tools` 静态钉住"**恰好一处**"
   —— ADR-0035 明确否决过"只检查写有没有在确认函数里"这个 weaker 判据，理由是
   "同时留着另一处直接 `submit` 仍会绿"。滴答的对应机制是**文档里的一句示例 prompt**。
2. **出境是逐字段披露的**，用户点发送前就看到会送出什么；`AiInvocation.fields` 是**必填**的，
   连工具名都算出境数据（`provider.ts:96-102` 的注释）。
3. **本机优先 + 回退不跨越隐私边界**：本机端点挂了**不许**悄悄发给云端
   （`routing.ts:806` 返回独立的 `fallback-needs-consent`，从不自动重试到另一目的地）。

这三条是 heyta 在 E2EE 前提下**唯一不可让渡**的资产。任何"向滴答看齐"的补齐动作，
如果以它们为代价，就不是补齐而是换产品。

## 6. 🔴 真正的拦路虎：一条全仓零记录的 CORS

**这是本轮唯一"今天就在挡住真实用户"的一条，且文档零记录。**

- 内置端点预设只有两个，都是回环：`packages/ai/src/presets.ts:60-80`
  （Ollama `http://localhost:11434/v1`、LM Studio `http://127.0.0.1:1234/v1`）。
- Web 应用挂在 `https://heyta.waytofuture.cn/app/`（域名迁移见
  [`../runbooks/deployment.md`](../runbooks/deployment.md) §3.7.2）。浏览器发请求带
  `Origin: https://heyta.waytofuture.cn`。
- 实测（2026-10-02，Ollama 0.23.2）：**对非 `localhost` 的 Origin 回 403，预检也 403**；
  `https://heyta.local`（Windows 壳）与 `heyta-local://app`（macOS 壳）同样 403。
- 解法是把来源加进 Ollama 的 `OLLAMA_ORIGINS` 白名单 —— **全仓该串出现 0 次**，
  没有任何 runbook、界面提示或错误分类提到它。
- 该 403 被 `routing.ts:897` 归成通用 `http-error` ⇒ 界面说"AI 不可用，去设置里查端点"，
  而设置页里**没有对应的答案**。

**为什么我们的探针看不见（§7 元规则第 1 条的形状）**：

1. e2e 的假端点**不是不知道跨源这件事** —— 恰恰相反，`e2e/stub-provider.mjs` 的 `CORS_HEADERS`
   文件头把这一类症状写得极准（原文）：

   > "缺了它的症状**极具误导性**：请求在 DevTools 里是 CORS 拒绝，而应用层拿到的是
   > `TypeError: Failed to fetch` —— 界面把它渲染成「无法连接端点：Failed to fetch」，
   > 看起来像'端点没起来'或'地址填错了'，而假端点其实活得很好。"

   但它无条件回 `'access-control-allow-origin': '*'`、**从不读 `Origin`、从不拒绝**
   （`e2e/stub-provider.mjs:108-112`，预检分支只回头不带 body）。
   ⇒ 🔴 **这条知识已经在本仓库被写下来了，只是那个假端点永远站在放行的一侧**，
   所以它从未被用来诊断一个**会拒绝**的真端点。这不是认知缺口，是**判据只测了一半**。
2. ✅ **本条已在 2026-10-02 实测闭合，原判断被推翻**（初稿写的是"到底是哪一条，标为未证实"）：
   四探针实测 —— 无 `Origin` → **200**；`Origin: http://127.0.0.1:4321` → **200 且回显该来源 + `Vary: Origin`**；
   `Origin: https://heyta.waytofuture.cn` → **403、`Content-Length: 0`、完全没有 `ACAO`**；
   坏来源的 `OPTIONS` 预检 → **403、无 `ACAO`**。
   ⇒ **浏览器侧恒为 CORS 拦截 → `TypeError` → `'network'` 分支**，
   而**不是**初稿与工单原计划假设的 `http-error`。
   🔴 更关键的推论：**JS 永远看不到那个 403**，所以"加一个新失败原因来分类"这条路
   **技术上不可能成立** —— 处置只能是**上下文推导**（端点是否 loopback 预设 + 页面自身 Origin）。
   详见 [ADR-0045](../adr/0045-conversational-assistant-split-authorization-from-catalog.md) §4 与
   [`../plans/ai-assistant-closure.md`](../plans/ai-assistant-closure.md) W1。
   ⚠️ 附带查出真正的 bug 位置：`apps/web/src/features/ai/ai-failure-copy.ts` 里
   `'network'` 的注释是"网络与空响应是**暂时性**的，设置里改什么都修不好"、跳转目标 `undefined` ——
   **这句注释对本机端点是错的**，而它正是"用户看到'去设置查端点'而设置里没有答案"的成因。
   ⚠️ 还有一条结构性事实：Ollama 默认放行的就是 **loopback 来源** ⇒
   **只有开发机上的 localhost 页面能用本机端点**，生产 Web 壳与两个原生壳必然撞上它。
   这也解释了为什么它至今没被发现：**所有人都在 localhost 上测。**
3. **四个**真端点验收脚本今天全部"**跳过并退出 0**"：
   `scripts/verify-ai-live.mjs` / `-breakdown-live.mjs` / `-output-language.mjs` /
   `-preferences-live.mjs` 各自抄了一遍"读不到配置 ⇒ `process.exit(0)`"，
   而配置被 i18n 那轮搬到 `/tmp/heyta-ai-live-provider.json.stashed-by-i18n-round` 后未归位
   （该文件实测存在，100 B，mtime 2026-10-01 18:19；键为 `mode/endpoint/apiKey/model`，
   值是**本机 Ollama** `127.0.0.1:11434` + `qwen2.5:0.5b`）。
   ⇒ 这是"一条永远通过的判据比没有判据更糟"（§7 元规则第 2 条）的**现行实例**。

   🔴 **严重性要按实测说，我初稿把它说高了**（下面两条是核对 `package.json` 与
   `.github/workflows/ci.yml` 之后的更正）：

   - 这四个脚本**都不在 `pnpm check`、也不在 CI 里**（`ci.yml` 只跑 `pnpm check` 与
     `pnpm test`，另在第 141 行明确写"想让它真跑，用 `pnpm verify:ai-live` 系列脚本在本地执行"）。
     所以它们**没有把 CI 变成假绿**，骗到的是**手动运行它的人**。
   - `verify-ai-output-language.mjs` **连 `verify:` 别名都没有**（`package.json` 里查不到），
     只能 `node scripts/…` 直接跑 ⇒ 它比另外三个更不可发现。
   - 另有两处同源的小缺陷：三个脚本**用了 `config.model` 却只校验 `endpoint`/`apiKey`**
     （⇒ 模型缺失时是 `model: undefined` 发出去，不是"没配"），
     以及把"JSON 解析失败"和"文件不存在"**都**当成"还没配"。

   ⚠️ **真正在门禁里的那个空转不在 `scripts/`**：
   `apps/web/tests/journey-ai-memory.integration.spec.tsx:256` 用
   `describe.skipIf(CONFIG === undefined)` 挂在**同一个** `/tmp/heyta-ai-live/provider.json` 上，
   而它属于 `pnpm -r test` ⇒ **是 `pnpm check` 的一部分**。
   它是 web 侧唯一碰真模型的用例，配置文件缺失时整块静默跳过
   （该文件自己的注释 line 197 已经写下"一个永远不执行的判据，比没有判据更糟"——
   即前一轮已经看见了这条，但没有改它）。
4. 拿那份被搬走的配置喂 `verify-ai-live`，第一条断言即炸（它硬要求**远端**端点）；

## 7. 已知 vs 新情报：这件事的性质

### 7.1 对话式助手是**被主动否决**的，且禁令挂着条件

- [`../adr/0005-ai-data-path.md`](../adr/0005-ai-data-path.md) §3.1 末尾（约 L93-95）原文：
  > "与 `docs/research/feature-matrix.md` §11 的关系：该节把'内嵌 AI 聊天助手'列为反需求。
  > **本 ADR 维持那条禁令** —— 不做聊天助手。本 ADR 允许的是**AI 作为输入方式**…
  > 这两件事的**隐私面、工程面和失败模式都不同**，不应混为一谈。"
- 被它维持的那条原始反需求（[`feature-matrix.md`](feature-matrix.md) §11，L155）原文：
  > "内嵌 AI 聊天助手（**除非明确有差异化价值**）"
- 而 [`ai-competitive-and-architecture.md`](ai-competitive-and-architecture.md) §1.2 早在 2026-09
  就把滴答 AI Assistant 记成"对话式管理任务与时间；可读存量数据；需用户确认"，带帮助中心出处。

⇒ **结论：形态是已知且被主动否决的，不是漏看。** 今天要做的不是补一个遗漏，
是**重新裁决那个"除非"**。这个决定属于产品负责人，本文不代拍（§9 D-1）。

### 7.2 三条内部分歧（不处理就会互相打脸）

1. **P3 的定义复现不了截图 A。** ADR-0035 与计划里 P3 = "多步**只读**循环"，写永不进循环；
   截图 A 是 3 读 + 1 写。**做完 P3 也到不了那个形态** —— 缺的是一个当前计划里没有名字的目标形态
   （"读循环 + 末尾一次写提案"）。
2. **"4 个 AI 功能"已过期。** `ai-competitive-and-architecture.md:200` 那句是 2026-09 的口径，
   现在 `AiFeature` 有 **5 个**（多了工具调用）。既有审计 [`ai-feature-completeness-audit.md`](ai-feature-completeness-audit.md)
   §0 表格也写"4 个 AI 功能 + 工具调用"，读起来像 4 件 —— 见 §10 勘误。
3. **"调用审计故意不做"与"轨迹可见化"从未被区分。** `../reference/ai-architecture.md` 那条
   （技术债表："调用审计/日志**故意**不做"）说的是**服务端留痕**；截图 A 的"已调用 N 个工具"是
   **本机当次会话的过程呈现**。两者不冲突，但文档里从没分开写过，导致"轨迹可见化"看起来像已被否决。

### 7.3 倒数日有一个时间窗

### 8.1 🔴 关于 AI-G13 这条撤回（留给后来者的取证教训）

子审计给出的"有定义、有测试、生产无写入口"这条**是错的**：
`retainValidConsents` 在 `apps/web/src/features/settings/AiSettings.tsx:364` **有真实生产调用点**，
而 `AiSettings.tsx:341` 的注释还专门写着"唯一的过滤事实源是 `retainValidConsents()`"。
它甚至有自己的回归测试（`apps/web/tests/ai-settings.spec.tsx:911`、
`apps/web/tests/ai-endpoint-disabled.spec.tsx:148`）。

**成因**：那一路的搜索范围落在了 `packages/`，而这条逻辑的**消费者在 `apps/web`**。
这正是本仓库已经记过的同一种错 ——
[`ai-strategy.md`](../plans/ai-strategy.md) 附近的历史条目写过：
"**只在 `apps/web` 里搜，就会把服务端渲染的流程误判成'没做'**"；
这次是**镜像的那一半**：只在 `packages/` 里搜，就会把界面接线的东西误判成"没接线"。

⇒ 本文其余 13 条缺口里，凡是"**零生产调用点 / 无消费者 / 没接线**"式的否定结论，
**复核范围都必须是全仓**（`packages` + `apps` + `server`），不能只查被调方所在的那一层。
本轮已按这个标准重查过的有：`AiSupplyMode`（确实只在 `packages/ai` 内）、
`runAiTool` / `grantedToolNames`（确实零生产调用点）、
`describeFocusGaps`（确实零调用点，但那是**刻意**的分层纪律，见 `ai-strategy.md` §8 的边界说明）。

## 9. 三条待产品负责人拍板的决策（本文不代拍）

**D-1｜是否用"除非明确有差异化价值"这条豁免，取代 ADR-0005 的"不做聊天助手"禁令？**

- 支持取代的证据：滴答 2026-09-29 已上线该形态且三区同批；用户会拿它当基线；
  出境模型的多轮矛盾 ADR-0035 已给出解法（字段并集前置披露），**不需要推翻 E2EE 前提**。
- 支持维持的理由（ADR-0005 自己给的三条，至今未被推翻）：隐私面、工程面、**失败模式**都不同 ——
  单点面板错了只错一个字段，agent 错了会连续做错五件事。
- ⚠️ 无论哪个方向，**都要新写一份 ADR 建立取代关系**（`docs/README.md` §一：ADR 不可改，只能新增取代）。
- **本文的立场**：真正未论证的不是"要不要对话"，而是"**要不要多步**"。
  对话只是外壳；截图 A 的价值 90% 来自"3 读 + 1 写"的那条链，而那条链今天被 AI-G4 锁死。
  **先解 AI-G4，再谈要不要给它套 chat 壳**，顺序反过来会做出一个能聊天但什么都做不了的助手。

**D-2｜工具目录扩到几十个之后，授权粒度按"工具"还是按"能力/会话"？**

这是 AI-G6 的真冲突：目录是内置助手与入站 MCP **共用一份**（ADR-0035 明令不许另建），
而 MCP 侧的立场是"每个工具单独默认关，用户不可能逐个理解风险"（`tools.ts:70-74`）。
为助手把目录从 6 扩到 40，**同时也把外部 AI 的攻击面扩到 40**。
不先定这个，扩目录就是拿隐私换功能。可选形状（**均未实现，只是形状**）：
按实体分组授权 / 按"读-写"两档授权 / 会话级临时授权（本次对话允许改任务）。

**D-3｜倒数日 `EVENT` 实体是否与它的 AI 工具同批设计？**

挂在 §7.3 那个时间窗上。若不同批，需在 `countdown-anniversary.md` 显式登记"AI 覆盖延后"并给编号，
不要让它静默消失。

## 12. 方法论（后人别再踩）

1. 🔴 **滴答帮助中心任一篇文档页面都把全部 96 篇正文内嵌在同一份 HTML 里**（SSR，无需登录）。
   ⇒ **"在某 URL 上 grep 到某句话"不能证明那句话属于那篇文章** —— 任何 URL 都能 grep 到任何句子。
   正确做法：按 `"title":"…","content":"…"` 成对解析出 title→content 映射，再断言 needle 落在**被引那篇**里。
   本文 6 条承重引文全部过了这道核对。
2. **中文搜索命中率最高的两条"滴答 AI 横评"（`post.smzdm.com/p/arzg560q/`、`…/p/apq558k2/`）
   正文自标"内容由 AI 生成"**，实读是微博摘要拼盘，几乎没有滴答事实 ⇒ **不可作为任何事实出处**，只作反面样本。
3. 真正承重的三类来源：帮助中心正文（SSR 全文 JSON 可 curl，不用登录）、
   **Apple iTunes lookup API**（版本与 release notes 的权威时间戳）、官网首页逐字引文。
4. 数字自己数，且**中英各数一次**；别人的快照与自己的计数冲突时**两个都登记、不合并**（见 §1.4）。
5. 🔴 **判"一份中文文档提没提某个 ASCII 主题词"时，子串匹配会大面积假阳**：
   本轮判 `countdown-anniversary.md` 有没有 AI 工作项，`grep ai` 命中 5 行，
   逐行读后发现全是 `daily` / `reminders` 里的子串。⇒ 要用词边界，并**把命中行读一遍**。
6. **既有审计文档可能答的根本不是同一个问题。** 本文最初的问题（"用户能使唤 AI 干活吗"）
   与仓库里那篇（"已声明的 AI 功能做完了吗"）在标题上几乎无法区分，而结论完全不通用。
   ⇒ 读旧审计前先读它的"本文回答的问题只有一个"那一句。
