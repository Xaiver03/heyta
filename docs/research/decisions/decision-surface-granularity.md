# 决策记录：heyta 的「屏」按窗口数补，还是按视图 key 补

> 状态：**待产品拍板**（本文件给出建议，不替产品下结论）。
> 日期：2026-11-06。
> 起因：[逆向取证总目录 §5 待裁决第 1 条](../ticktick-teardown-index.md)（`ticktick-teardown-index.md:140`）
> 与 [界面地图 §3.3 / §5](../ticktick-surface-matrix.md)（`ticktick-surface-matrix.md:364-370`、`:477-478`）。
> 一句话问题：滴答把可命名界面都做成**独立窗口**，heyta 把它们做成**视图 + 槽**；
> 对标时差集按哪个口径记，直接决定 P2 里一半的格子是「该做」还是「不该做」。

---

## 1. 两种口径的定义与现状读数

### 1.1 口径 A：按窗口数（滴答的产品 IA）

**定义**：一个「屏」= 一个可独立打开、可被系统窗口管理（平铺、置顶、多开）的窗或对话框。
滴答两端都是「一屏一文件」的组织方式（[P2 §3.3 第 1 点](../ticktick-surface-matrix.md)，`:364`）。

现状读数（口径均为「按文件名后缀数窗口/对话框级界面」，来源 [P2 §3.2 现量表](../ticktick-surface-matrix.md)，`:343-349`）：

| 端 | 读数 | 来源 |
|---|---|---|
| 滴答 Windows 8.2.5.0 | **153** = 108 个 `*window` + 45 个 `*dialog` | `ticktick-surface-matrix.md:346` |
| 滴答 macOS 8.2.03 | **35** 个 `*WindowController`（另有 210 个 `*ViewController`、163 个 cell 级） | `ticktick-surface-matrix.md:346-348` |
| 两端之比 | Windows 是 macOS 的 **4.4 倍** —— 同一产品，两个端对「独立窗口」的理解差 4 倍 | `ticktick-surface-matrix.md:356` |

⚠️ 口径提醒：**153 是滴答 Windows 的窗口总数，不是「heyta 该补的窗数」**。
两者之间的换算没有现成读数 —— heyta 若按窗口口径对齐，真实新增窗数
「未核实」；总目录给的量级说法是「约 150 个窗」（`ticktick-teardown-index.md:140`），
P2 结论层的说法是「会补出 150 个我们并不需要的窗」（`ticktick-surface-matrix.md:478`），
两处都是**规模感估计而非实测**，引用时必须带上这个性质。

### 1.2 口径 B：按视图 key（heyta 的现行 IA）

**定义**：一个「屏」= 顶层导航能到达的一个 `ViewKey`；其余界面以**槽**的形式嵌在视图里
（详情面、捕获条、各 popover —— [P2 §3.3 第 2 点](../ticktick-surface-matrix.md)，`:373`：
heyta 是「12 个视图 + 一个 `TaskDetailCard` + 5 个 popover」）。

现状读数：

| 项 | 读数 | 来源 |
|---|---|---|
| heyta 顶层视图 | **12 个 `ViewKey`**：tasks / search / calendar / quadrant / habits / focus / timeline / growth / notes / countdown / trash / settings | `apps/web/src/features/shell/view-tabs.ts:127-139`（本次逐行核实） |
| 不引入 router 是**显式决定** | 「P1 只有四个平级视图、没有深链接需求……到 P2 需要深链接时再引入」 | `view-tabs.ts:122-125` 注释 |
| 矩阵里 heyta 的三方差集 | 79 行：有 47 / **半有 11** / 无 21 | `ticktick-teardown-index.md:51`；`ticktick-surface-matrix.md` §1 |
| 11 格半有的成因 | 「不是漏做，是两边的『屏』粒度不同」 | `ticktick-surface-matrix.md:367-368`、`:475-476` |

## 2. 按窗口数补的代价

1. **数量级**：差集里 21 格「无」+ 11 格「半有」若全部按「独立窗」补齐，
   量级即上文的「约 150 个窗」（`ticktick-teardown-index.md:140`）。
   其中相当一部分在 heyta 的平台上根本不该存在窗：Web 壳没有原生多窗，
   「窗」会退化成 route 或 modal 的爆炸；移动端（`apps/mobile`）没有窗口概念。
2. **每一面都过本仓库的全套门禁**：这不是抽象的「维护成本」，而是每加一面要跑的固定程序 ——
   i18n 词条只能进唯一事实源（AGENTS.md §4 规则地图 · `packages/i18n`）、
   浮层必须登记关闭策略与危险档位（`docs/agents/overlay-feedback.md`）、
   界面验收要求 Playwright 真跑真看截图（`docs/agents/ui-acceptance.md`）、
   交付前要四端重装（`docs/agents/multi-end-build.md`）。
   150 面 × 每面一套 = 债务账本按面计息，而 `feature-matrix` 的差集本身也会从 79 行涨到几百行。
3. **对标对象自己就不自洽**：滴答两端窗口数差 4.4 倍（§1.1），
   「按窗口补」没有唯一答案 —— 按 macOS 补 35 还是按 Windows 补 153？
   且 BAML 文件名是编译产物路径残留，「拿它当 IA 用会同时把零件当屏、把屏当零件」
   （[P2 §4.1](../ticktick-surface-matrix.md)，`:404-406`）。
4. **与 heyta 自己的 IA 决定相抵**：12 个视图是刻意收敛的结果
   （`view-tabs.ts:122-125` 的无 router 决定、[dida-view-unification.md](../dida-view-unification.md) 的视图统一方向），
   按窗口补等于推翻它再用 150 个窗换回滴答的文件组织习惯。

## 3. 按视图 key 补的代价

1. **三类界面会被系统性压掉**（在两口径下判断相反，见 §4 表）：
   「独立总结屏」「习惯按打卡记录窗」「专注按日/周/月图表屏」——
   视图口径下它们都记为「某屏已有半段、够了」，于是**永远挂着半有**，
   谁也不再负责把它们做完。这正是总目录 §5 说「不裁决就只能挂着」的内容。
2. **迁移者的点名找不到**：矩阵的行定义是「用户能用一句话点名的界面」
   （[P2 §0.1](../ticktick-surface-matrix.md)，`:23`）。滴答用户迁过来点名「标签管理」「总结」，
   在 heyta 里没有同名可点之物 —— 槽不是入口（P2 §0.5 已区分「这一屏存在」与「它有一个入口」，`:120`）。
3. **深链接/外部唤起没有落点**：URL 只能指到 12 个视图级；
   「打开这条任务的附件区」「跳到快捷键一览」这类可寻址单元在视图口径下不存在，
   P5/P2 里命令面板、Siri 快捷指令等格的缺失会连锁变贵。
4. **设置细分被整段吞并**：滴答把「设置里的日历段」「主题编辑器」做成了独立窗，
   heyta 是一个 sheet + 八节（[P2 §3.1](../ticktick-surface-matrix.md)，`:337`）；
   视图口径会把「缺一段」记成低成本，但**滴答的产品重量恰恰在编辑器与设置细分**
   （[P2 §3.3 第 2 点](../ticktick-surface-matrix.md)，`:372-373`），低成本感会误导投入方向。

## 5. 用户能感知到什么差异

1. **点名可达性**：窗口口径下「习惯打卡记录」「总结」是搜得到、标题写得出的一屏；
   视图口径下用户只能靠侧栏逐层翻到一段热力图。矩阵行定义就是按「一句话点名」切的（`:23`）。
2. **多任务并排**：窗口口径支持「左边列表右边详情窗」这类 OS 级用法（滴答有
   `TTSideBySideListContainerViewController`，`:135`）；heyta 的槽方案在一台设备上同时只能开一个详情面。
3. **入口数量感**：滴答 macOS 菜单 13 项但 rail 只有 5 视图 + 3 动作（`§0.5:117-119`）——
   窗口多不等于入口多。heyta 若按窗口补而不加入口，用户只会觉得「弹窗变多了」而不会觉得「功能变全了」。
4. **回执与打扰**：窗有系统级关闭/焦点语义；槽要靠 `overlay-feedback.md` 的关闭策略表逐面自定义。
   补 150 面 = 用户面对的模态打断形状不一致的概率同步上升。
5. **跨端一致性**：桌面「窗」在 Web/移动只能降级为 route/sheet；按窗口补会把差集债务
   复制到四端（`multi-end-build.md`），用户在不同端看到的「屏数」反而更不一致。

## 6. 建议与待拍板的一句话

**建议：以口径 B（视图 + 槽）为准记差集，但必须显式裁决 §4 的四格分歧项，并把裁决写成「不做」进 ADR，不许挂着。**
理由：(a) 视图口径是本仓已成立的 IA 决定（`view-tabs.ts:122-125`），推翻它的前提是证明窗口形态带来用户可感收益，而 §5 里唯一站得住的是「点名可达」与「多开」两项，均可用「给槽加一级入口 + P2 引入 router 深链接」低成本拿到；
(b) 16/46/48/50 四格若裁决为「不做独立屏」，则成长/习惯/专注三面的**现有槽加深**（图表、按日记录、补录）反而升级为该做的主项 —— 这与 P2 「投入方向是编辑器深度与设置细分、不是再加视图」（`:373-374`）互洽；
(c) 无论哪种裁决，P0（标签管理）与 P1（任务附件）不动 —— 它们本来就不该按窗口口径记成本。

**需要产品负责人拍板的一句话**：
「差集是否一律按『视图 + 槽』口径记账——若是，总结屏、习惯打卡记录窗、专注按日月图表窗这三类界面正式裁决为『不做独立屏、改为加深现有槽』并写入 ADR；若否，请同时指定对齐滴答 macOS 35 窗还是 Windows 153 窗。」
