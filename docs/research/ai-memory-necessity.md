# heyta 需不需要向量数据库？—— 一次用实验回答的调研

- **日期**：2026-09-26
- **问题**：「我们的日程清单应该有记忆，应该有个数据库」→ 要不要引入向量库 / AI 记忆库？
- **方法**：🔴 **先做实验，再下结论**。不是调研完就断言。
- **产出的实验**：`packages/domain/tests/recall-experiment.spec.ts`（`pnpm --filter @heyta/domain test` 可复现）
- **产出的代码**：`packages/domain/src/memory.ts`（特征层）、`packages/domain/src/recall.ts`（词法检索基线）
- **相关**：[ADR-0005](../adr/0005-ai-data-path.md)、[ai-strategy.md](../plans/ai-strategy.md) §4

---

## 0. 🔴 一句话结论

**不需要向量数据库。** 但理由**不是**"词法检索够用" —— 实验证明它**不够**。
真正的理由是：**需要语义判断的地方，用已经配置好的那个模型直接判，
比为它建一套检索基础设施更便宜、更安全。**

我原本的预判是"不需要"，实验**部分推翻了**它（难档召回 0%），
但**推翻的是我的理由，不是我的结论** —— 详见 §3⑥，我在那里记下了自己搞错的地方。

后台调研独立跑了一遍（[原料](../../research/ai-memory-db-2026-09.md)），
**得出了同一结论，但论据更强**，并纠正了我一处技术错误。两条独立路径收敛。

---

## 1. 为什么先做实验而不是先调研

我（AI）对这个问题的**预判**是不需要向量库。如果我只写一段话断言"不需要"，
那是**自证** —— 没有价值，而且很可能错。

所以把它翻译成一个**可证伪**的问题。落在产品上最具体的一步是**重复检测**：
用户敲进一条任务时，能不能认出"这个你已经有了"。它有清晰的 ground truth。

对每条新任务，基线算相似度，`>= 0.35` 判定重复。于是可测**召回**与**误报**。

### 🔴 实验的关键设计：把"重复"分成两档

| 档位 | 例子 | 词法基线**应该**的表现 |
|---|---|---|
| **易**：字面重叠 | 「写周报」↔「写周报初稿」 | 应该命中 —— **这是"基线不是稻草人"的守门测试** |
| **难**：语义相同、字面零重叠 | 「准备季度汇报」↔「做 Q3 review 的 PPT」 | 这正是词法基线该失败的地方 |

两档**分开报数**，不允许用总体召回率把难档的失败平均掉。

---

## 2. 实测结果

语料 26 条（含 18 条无关干扰项），阈值 0.35。

| 档位 | 实测 | 判读 |
|---|---|---|
| 易档召回（n=8） | **100%** | 词法基线在"用户复用了词"时完全够用 → **基线有效，不是稻草人** |
| 🔴 难档召回（n=8） | **0%** | 词法基线**彻底失效**（唯一非零的一条也只有 0.125） |
| 误报率（n=8） | **25%** | 还会把**相反**的动作判成同一件事 |

### 检索模式指标（precision@k / recall@k / MRR）

上面那组测的是「**词法自己能不能做决定**」。但还有一种架构值得测：

> **词法负责召回候选 → 模型负责判断**

这种架构下判定阈值不重要，重要的是**真正那条有没有被捞进候选集** ——
因为模型**只会看到候选**。所以另外测了一组 @k（k=5）：

| 指标 | 易档 | 🔴 难档 |
|---|---|---|
| precision@1 | **100%** | 13% |
| recall@5 | **100%** | **13%**（8 条里仅 1 条） |
| MRR | 1.000 | 0.125 |

🔴 **这张表比上面那张更要命。** 难档 recall@5 = 13% 意味着：

> **87.5% 的"换说法"任务，词法连候选都捞不出来 —— 模型根本没机会看到它。**

所以"让模型来判"这条路**不能**建立在"词法先缩小候选"之上。
（唯一那条擦边命中是「把旧手机数据清掉」↔「手机要出二手，先处理干净」，
相似度 0.125，纯属运气。）

### 最恶劣的一条误报

```
给团队订周五的会议室  ↔  取消周五的会议室预订
相似度 0.556  → 判定为重复
```

**动作相反却被判成同一件事。** 这个如果上了生产，会真的误导用户。

### 难档为什么是 0%

逐条看：`准备季度汇报` ↔ `做 Q3 review 要用的 PPT` 相似度 **0.000**。
两条**没有一个共享的实词**。词法方法在这里数学上就不可能命中 ——
这不是调参能解决的，是靠阈值永远换不回来的。

## 3. 🔴 但"词法不行"**不等于**"要上向量库"

这是本次调研最关键的一步推理。实验只证明了"纯词法不够"，
它**没有**证明"向量库是解法"。把这两件事分开看，会发现三条更便宜的路：

### ① 需要语义判断的地方，**直接用模型判**，不需要索引

重复检测的本质是"**这两个是不是一回事**"，这是一个**判断**问题，不是**检索**问题。
既然 heyta 已经有配置好的模型端点（`own` 或 `managed`），
把标题放进 prompt 问一句就行 —— **不需要为它建 embedding 管道 + ANN 索引**。

⚠️ **但这里有个前提条件，是上面的 @k 数据逼出来的**：
既然难档 recall@5 只有 13%，那就**不能**采用"词法先缩小候选、再让模型判"的做法 ——
模型会漏掉 87.5% 的换说法任务，而且**它不知道自己漏了**。

所以这条路要成立，必须**把整份任务列表给模型**。这在 heyta 的量级下是可行的
（见下一条），但它同时意味着：**成本随任务数线性增长**。
这也是本结论最脆弱的假设 —— 已列入 §5 的推翻条件。

### ② heyta 的任务量级是**数百条**，候选集可以整份给模型

向量数据库存在的理由是**海量语料下做近似最近邻**。
一个用户的待办列表是 10²–10³ 量级 —— 全部标题塞进 prompt 是可行的，
**根本不需要索引**。为数百条数据引入 ANN 是杀鸡用牛刀。

### ③ 🔴 真正的瓶颈是**嵌入模型**，不是索引 —— 而它正好撞在 E2EE 与 Hermes 上

这是最容易被忽略、也最致命的一条：**要拿到向量，先得有 embedder。**

| 嵌入来源 | 代价 |
|---|---|
| **远程 API** | 任务明文出境 → 要过 `authorizeEgress` 的精确授权，并产生**服务端明文派生物** |
| **本地 WASM**（transformers.js / ONNX） | 实测 `@huggingface/transformers@4.3.0` 依赖 `onnxruntime-web`（**WASM**）→ **Hermes 上直接死** |
| **本地原生**（Core ML / ORT Mobile） | 要为 iOS / Android / 鸿蒙**各写一套原生推理** —— 正是 `AGENTS.md` §7 明确规避的事 |

**而且 embedding 本身就是明文派生物。** 嵌入反演攻击能从向量恢复出相当部分的原文语义
（[arXiv 2503.12896](https://arxiv.org/html/2503.12896)）。
这与 ADR-0005 反复警告的是同一类风险 ——
**在本地多存一份 embedding，等于多存一份可被反演的语义摘要。**

> **向量库是这条链上最便宜、最可替换的一环。** 把瓶颈（embedder）换掉毫无收益，
> 却要为最便宜的那一环引入新依赖、并在三端各写一遍。

### ④ 🔴 向量库解决的是 heyta **不存在**的规模问题（有实测数字）

本机单线程纯 JS 暴力余弦扫描实测：

| 向量数 × 维度 | 耗时 |
|---|---|
| 1,000 × 384 | **0.3 ms** |
| 10,000 × 384 | **2.6 ms** |
| 100,000 × 384 | 28.2 ms |
| 10,000 × 1536 | 10.6 ms |

个人任务管理器的量级是 10³–10⁴ → **暴力扫描 0.3–3 ms**，而那段代码只是一个
`Float32Array` + 一层 `for` 循环：**三端一致、零依赖、零原生构建**。
ANN 索引优化的是 10⁶ 以上的场景。**引入向量库等于为不存在的问题付费。**

### ⑤ 不可重建性 —— 撞上 heyta 自己的核心不变量

`packages/storage/src/stores.ts` 明写 `STATE`「**可从 OPS 完整重建**」。

若向量索引由**非确定性**的 embedder 生成，它**无法从 op-log 确定性重建** →
变成**第二个、会漂移的事实源**。heyta 为「两端各自裁剪向量时钟」这种小得多的漂移
写过一整份 [ADR-0008](../adr/0008-vector-clock-limit.md)。
引入不可重建的派生索引是**同一类故障形状的放大版**。

### ⑥ ⚠️ 一处**我原先搞错**的地方（必须记下来）

我在上一版结论文档里写过「主流向量库要么依赖 WebAssembly（Hermes 直接出局）」。
**这句话对移动端是错的**，调研逐字读了 heyta 已安装的
`@op-engineering/op-sqlite@18.2.5`：

> 它**原生预编译**了 sqlite-vec —— iOS 侧 `sqlitevec.xcframework`，
> Android 侧 `libsqlite_vec.so`，**不依赖 WASM**。`README` 特性列表原文含
> `sqlite-vec plugin`，**license: MIT**。

**所以"WASM 出局"不能作为否决理由。** 真正成立的是上面 ③④⑤ 三条 ——
它们比"跑不了"更本质：**即使跑得了，也不该跑。**

> 教训：**"环境不支持"是最容易被推翻的一类论据**（本仓库已经吃过一次：
> 「端侧模型」被否的理由之一也是 WASM，而真正的理由是准确率与明文派生物）。
> 结论应当建立在**产品立场**上，而不是借来的技术限制上。

### ⑦ 顺带发现：FTS5 目前是**关的**

heyta 当前 iOS/Android **既没有 FTS5 也没有 sqlite-vec**：
`op-sqlite` 的构建开关 `fts5 = false`、`use_sqlite_vec = false` **默认都是关的**，
且全仓库 `grep op_sqlite_config / sqliteVec / fts5` **零命中**。

要用 FTS5，需要在 monorepo 根 `package.json` 加 `"op-sqlite": { "fts5": true }`
并**重新原生构建出包** —— 改动是一行，性质是原生构建配置，且要过
`pnpm check` 里的 iOS 原生依赖门禁。

⚠️ 浏览器端用不了：web 是 IndexedDB，**没有 SQL**。

### ⑧ 一个被推翻的常见前提：heyta 的「三端」是**三种不同的存储引擎**

| 端 | 存储 | 有 SQL 吗 |
|---|---|---|
| 浏览器（`apps/web`） | **IndexedDB**（`apps/web/src/lib/oplog.ts:61` → `IndexedDbAdapter`） | ❌ **完全没有** |
| React Native | `@op-engineering/op-sqlite@18.2.5`（JSI 原生） | ✅ |
| Node（桌面 / CLI） | `node:sqlite` | ✅ |

**后果**：任何「基于 SQL 的检索 / 向量」方案天然只有 **2/3 端可复用**，
浏览器端**必须另写**。

这条比"哪个库更好"重要得多 —— 它决定了**任何依赖 SQL 的检索都不是跨端方案**。
如果记忆层要三端一致，它就只能建立在**纯函数 + op-log**之上
（本仓库的 `packages/domain` 正是这个位置）。

### ⑨ 一条会浪费半天的工程陷阱：许可证门禁按**字符串**判定

调研实测发现，`pnpm check:licenses` 会拦下两个**底层许可其实没问题**的包：

| 包 | 它声明的 | 为什么被拦 |
|---|---|---|
| `usearch` | `"Apache 2.0"`（**无连字符**） | 脚本用 `up.includes('APACHE-2.0')` → 匹配失败 → 落入 `other` → 未登记 → 退出 1 |
| `pgvector` | `PostgreSQL` | 不在 `PERMISSIVE` 枚举里 |
| `sqlite-vec` | `"MIT OR Apache"` | 含 `MIT` 子串 → **反而通过** |

⚠️ 修法是走 `REVIEWED_OTHER` 登记，**不要**为了让门禁变绿去改 `PERMISSIVE` 白名单 ——
那会同时放行所有同类许可的包，把门禁变成摆设。

### ⑩ 另一个容易混的名字

`packages/storage/src/stores.ts` 的 `OP_FIELDS` 里有 **`VECTOR_CLOCK`** ——
那是**因果向量时钟**（同步用），**不是向量检索**。两者毫无关系，别被名字带偏。

## 4. 那"记忆"到底怎么建

**不需要新建数据库。heyta 已经有最好的记忆载体。**

| 已有的 | 为什么它**就是**记忆 |
|---|---|
| op-log | append-only 全量事件历史 —— 每次创建/推迟/完成/专注都在里面 |
| `MaterializedState` | 当前状态的物化视图 |
| SQLite（`packages/storage`） | 已经能带索引查询 |

缺的不是**存储**，是**在它之上的派生层**。

### 🔴 而且这一点已经被代码证明了，不是理论

`packages/domain/src/memory.ts` 里，「**这个任务被推迟过几次**」
**只能从事件流算出来** —— 物化状态里**根本不存在**这个信息。

状态里只有"当前截止 = 10 天后"。「被推过 2 次」只在历史里。

> 这条是**「op-log 就是记忆」的直接证据**：
> 换掉 op-log 去用一个只存当前值的库，**这个能力就不复存在**。
> 已在 `memory.spec.ts` 里用测试钉住。

### 已经落地的东西（`packages/domain/src/memory.ts`，纯函数、零依赖）

- `computeTaskMemory()` —— 推迟次数 / 累计推后天数 / 逾期天数 / 多久没碰 / 专注分钟 / 是否从未开始
- `computeFocusGaps()` —— **「说的 vs 做的」落差**（AI 护城河的事实基础）
- `describeFocusGaps()` —— 把事实写成一句人话，**不调用模型**

最后一条是刻意的：**没有配置任何 AI 端点时，这个功能依然有输出。**
少了它，"AI 未配置"就退化成"整个功能是灰的"。

## 5. ⚠️ 这份结论的边界（不许被当成定论）

| 项 | 诚实说明 |
|---|---|
| **样本量** | 每组 **n=8**。只能**定性**，不能定量。这是"第一刀"，不是最终结论 |
| **难档是我构造的** | 我刻意构造了"零字面重叠"的对抗样本。真实用户**经常复用词**，所以线上难档比例会**低于** 100% |
| **阈值是拍的** | 0.35 不是调出来的。调低会同时提高召回**和**误报 —— 报告同时给出两者，就是让这个取舍可见 |
| **只有两个人做标注** | ground truth 由我一个人定，可能有偏 |
| **未测** | 没测多语言、没测超长备注、没测几百条真实数据下的表现 |

### 什么会推翻本结论

1. 线上数据显示**跨措辞检索是高频刚需**（而不只是重复检测）
2. 🔴 「把全部标题给模型」的成本被证明**不可接受**
   —— 而 @k 数据说明**没有中间路线**：词法缩小候选会让模型漏掉 87.5%，
   所以"省 token"的唯一办法就是另找语义检索（即向量库）。
   这一条是本结论最脆弱的假设
3. 出现一个**纯 JS / 无 WASM / 三端可用 / 无明文派生物**的语义方案
4. 任务量级增长到 **10⁴+**（那就真的需要索引了）
