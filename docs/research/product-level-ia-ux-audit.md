## 2. 产品定位（乙为主，甲补充核实）

**问题**：能力都在增长，但"heyta 最擅长解决什么问题"没有一句能被界面本身说出来的答案。
建议主叙事方向（乙提案，待产品负责人定稿）：

> heyta 是一个本地优先、重视隐私的任务执行工作台。

在这个叙事下，一级导航应优先服务"**收集、安排、执行、复盘**"，而不是平等展示所有能力。

**真正的差异化资产**（乙列、甲核实均真实存在）：本地优先 / E2EE / 可自建 / 多端同步 /
四象限与任务执行 / AI 不直接替用户写入数据（提案-确认制）。
问题不在有没有，在于**它们停留在说明文案里，没有转化成可感知的交互**——
例如"AI 只提案不写入"是全仓硬约束，但界面上它表现为一块与新建任务同视觉层级的技术面板（§4.3）。

## 3. 信息架构（合并）

### 3.1 骨架执行层（甲，8/10）

三层壳 `rail（去哪看）→ sidebar（范围）→ main + 详情列` 成立，且：
- 功能模块开关 + 关掉**不进 DOM**（`apps/web/src/features/shell/modules.ts`），
  次级表面统一浮层 + 统一出口（`closeSecondarySurface`）；
- 首启隐私分层（同意 / 只用本机）有产品立场；
- 移动端把四象限/时间线吸收为任务页视图档不给 tab（ADR-0015）裁决正确。

### 3.2 决策收敛层（乙为主，甲逐条核实）

1. 🔴 **"更多"设计与实现脱节**（乙发现，甲核实成立）：
   `apps/web/src/features/shell/view-tabs.ts:170-178`（旧裁决："**而不是**把低频的藏进「更多」"）
   与 `:190-205`（新裁决："收进 **4 + 1（更多）**"）**两代裁决同文件并存**；
   而 `apps/web/src/App.tsx:1359-1366` 的 `visibleMainTabs` 只是 `filter`——
   **无截断、无更多按钮，全文件 grep「更多」只命中注释**。
   当下用户看到的 rail = 所有启用模块平铺。这是 IA 决策未完成的物证：
   要么实现、要么删注释收敛成一代裁决。
2. 🔴 **视图与筛选未分离**（乙断言，甲核实成立）：domain 的 filter kinds 实测含
   `quadrant`（另有 `date/overdue/undated/withinDays/tag/project`，`packages/domain/src/filters.ts`）
   ——四象限既是完整看板（rail 视图）又是任务列表筛选（侧栏入口），两类"目的地"混在一级导航。
3. 🟡 **"任务"按钮二次点击承担"回收集箱"手势**（`App.tsx` rail onClick 注释 +
   `tests/app-mount.spec.tsx` 钉住；乙误写为"回收箱"，见 §9 第 2 条）：
   手势可成立，但缺可见反馈，用户只能试错学习。
4. 🟡 **可开启能力面广度**（产品负责人确认方向，证据表述按 §9 第 1 条修正）：
   默认开 4 模块 + 任务/搜索常驻（`modules.ts:81-127`），但设置摆着 8 个开关、
   搜索与帮助也在宣传全部能力、全开后 rail 平铺（同第 1 条）——
   "功能集合感"来自呈现方式，不是默认值。
5. 🟡 **智能清单偏少**（对照滴答侧栏：今天/明天/最近7天/全部/已完成/分配给我/过滤器）：
   heyta 有 今天/最近7天/已完成（"全部"合并进 rail 任务键，有注释裁决）；
   无"明天"、无过滤器实体（前次审计已登记为 IA 差异；无协作功能故无"分配给我"，属合理取舍）。
6. 🟡 **跨端投影漂移且无对照契约**：分类 = 移动端一级 tab vs web 藏在成长页（默认关）；
   便签 = web 有视图（默认关）vs 移动端无一级入口；搜索 = web rail 常驻 vs 移动端任务页浮层。
   单看各有理由，但没有一份"两端投影对照表"让差异成为受控决策。

### 3.3 IA 终局建议（乙方案 + 两条待拍板项）

乙建议收敛为：一级目的地 = 任务 / 日历 / 专注 / 习惯 / 搜索；
四象限 / 时间线 / 便签 / 倒数日 / 成长 / 回收站降为次级工具。
**甲注**：这本质是把移动端已落地的 ADR-0015 模型推广到 web，方向自洽；
且落地缝已存在——`quadrant` 已是 filter kind，"保筛选、降视图"迁移成本低于重做。
但有两条是**产品拍板项不是对错**：
① 把"专注"提一级要先翻"默认克制"旧裁决（专注现默认关）；
② 把"搜索"提一级与现裁决"一个应用只有一个搜索入口（浮层）"相左。

## 4. 交互方式（**乙为准**，裁决 1；甲的证据核实随附）

1. 🔴 **窄屏底部导航**：把 rail+sidebar 压缩进底栏，中文标签**逐字竖排**。
   证据：`screenshots/web-mobile/MW01-移动端任务.png`（甲目验：底部 7+ 项 =
   收集箱/今天/已完成 + 四象限四色点 + 新清单/新标签，"重要且紧急"五字竖列）。
   乙的整改方向：底部固定 4-5 个目的地；范围筛选改页面内 segmented control / sheet；
   底部标签必须单行，中文禁依赖自然换行。原生 RN 五 tab 方向本身合理。
2. 🔴 **设置浮层与任务详情列同屏争夺注意力**。
   证据：`apps/web/evidence/detail-pane-overlay/settings-sheet.png`（甲目验：
   设置面板约 60-65% 宽 + 右侧任务编辑表单约 30% 并列，无遮罩无主次）。
   整改：进设置/帮助/搜索/账户流程时关闭或遮蔽详情列。
3. 🔴 **AI 工具调用过于显眼且技术化**：与新建任务同视觉层级，
   文案（"用一句话让 AI 调一个工具"）是开发者视角。整改：默认收起为"助手"入口，
   任务输入框是页面唯一主动作；本地/远程/规则三条路径用简短状态说明表达。
   （甲注：这不与"提案-确认制是强项"矛盾——强的是流程安全，错的是视觉位置。）
4. 🔴 **空态主次不清**：`0/0`、AI 面板、输入框、中央空态同屏无主次。
   整改：空态只突出一个首要动作（"先记下一件事"）+ 少量示例。
5. 🟡 **四象限空态占屏**：证据 `apps/web/evidence/selection-projections/02-quadrant.png`
   （甲目验：四卡占约 95% 宽 / 70% 高、仅 2 条任务、"拖任务到这里"出现 3 次、
   底部裸排长段规则说明；**另发现两条乙未提**：象限标题无计数徽标、
   未选中任务时右侧详情列仍渲染完整表单）。整改：缩空区高度、标题+颜色+数量为主层级、
   轻占位、说明文案收进可折叠帮助。
6. 🟡 **详情列功能太全、层级不够**：备注/子任务/清单/重复/RRULE/截止/提醒同一条纵向流程。
   整改固定四组：**基本信息（标题/备注/完成）→ 时间（截止/开始/提醒）→
   组织（清单/标签/子任务）→ 自动化（重复/AI/规则）**；
   重复规则先展示自然语言选项，原始 RRULE 收进"高级"。
   （甲注：web 的 `TaskRepeat.tsx` 已是"预设 + 自定义 RRULE"，与乙描述一致。）

> 甲登记的**能力密度清单**（无批量/右键/undo toast/移动端零滑动·长按·拖拽/无下拉刷新）
> 未纳入本轮裁决范围，登记在 §8 附录待产品排期，不丢弃。

## 5. 跨端一致性（**乙为准**，裁决 1；甲补移动端源码证据）

- 核心判断（乙）：当前响应式策略是**把桌面信息压缩到手机**，不是为手机重新设计信息层级。
- 甲补充的移动端源码证据（支持同一结论）：
  - tab 切换即卸载，屏内状态（视图档/筛选/搜索词）全丢（`apps/mobile/src/App.tsx:221-225`）；
  - 二级页面 20+ 张，混用"整屏替换"（`ProfileScreen.tsx:734-799` 一串 early-return）
    与 `Modal` 两种无统一返回栈的形态；代码注释自认"等出现真实的栈/深链需求再评估"——
    该需求事实上已到；
  - 触屏惯例交互（滑动/长按/拖拽）整体缺位，连"点行编辑"都要进 Modal。
- 甲保留的一条事实修正：乙的跨端结论全部来自一张 **web 窄屏**截图，无移动端源码证据
  （§9 第 4 条）——结论方向经甲补充后成立，但记分依据在此说明。

## 6. 设计系统（合并：甲的分层 + 乙的"值→行为"）

token 层与治理（甲评 9/10）不在此重复，见
[ui-aesthetic-and-design-system-coverage-audit.md](ui-aesthetic-and-design-system-coverage-audit.md)
与 `design-system/heyta/MASTER.md`。要点：210 token 三层架构、8 端代码生成 + 字节级门禁、
对比度测试实算、动效/材质/z-index token 化——**这套治理不是问题的来源**。

缺口（两份同向，合并表述）：

1. **原语层缺失**（甲）：组件库按"每个业务视图一份"组织（约 50 个板级组件），
   但 Button/Input/Select/Dialog/Toast/Skeleton/Sheet 无共享版，散在 web 壳约 4570 行 CSS。
   后果已现形：goal-layout-audit §8.2 登记的 UX 债 #6（对话框无 Esc）与 #9（AiPanel 伪 dialog）
   同根——没有共享 `useModalDismiss()`，每处浮层各自实现就各自漂。
2. **从"值系统"升级到"行为系统"**（乙的框架，甲认同为同一缺口的另一半）：
   缺"列表/卡片/看板/详情列分别何时使用"的规范、空/加载/错误态统一结构、
   密度模式规范、详情列分组规范、导航 active/selected/focused/pressed 状态矩阵、
   移动端与桌面的导航降级规则、动效在切换/开详情/保存/同步中的统一节奏。
   现在这些决策大多写在巨大注释里，组件 API 没有表达语义。
3. 排版豁免债 9 条在册（`PAIRED_TYPOGRAPHY_ALLOW`，只许删不许加）——治理方式对，债是真的。
4. 断点未 token 化（CSS 能力限制，已诚实登记）；MASTER.md 个别表格滞后于代码（9 档 vs 12 档）。

**补原语层（5-6 件）+ 行为规范文档**是设计系统的下一刀，不是加更多 token。

## 7. 系统与代码对产品体验的影响（甲为主）

这些不是纯工程问题，直接影响"用起来是否舒服"：

- **编排过度集中**：`apps/web/src/App.tsx` 近 3000 行，同时负责导航、搜索、详情列、
  设置、AI、任务列表与布局状态——产品规则过度集中是导航策略漂移（§3.2 第 1 条）的温床。
  乙的拆分建议：导航状态 / 内容路由 / 详情列 / 全局浮层四个编排域。
- 🔴 **功能完整性洞（甲发现，非交互维度）**：**Web 端任务标题不可改**——
  共享层 `packages/app-host/src/actions.ts:137` 的 `rename()` 存在且移动端已接线，
  但 web 的 `TaskDetailCard.tsx:109` 标题只读、`features/tasks/store.ts` 0 处调用；
  手动优先级同理（仅显示 + AI 批量写入）。纯接线遗漏，性价比最高的修复。
- 🔴 **手动排序未接通**：`packages/domain/src/entities.ts:296` `order?: number` 字段已在，
  `task-order.ts:50` 明写"**没有「手动拖拽」**。它需要一个持久化的 order 字段（每次拖动 = 一条 op）"
  ——缺的是 op-log/LWW 下的排序语义裁决（谁改序、怎么合并），先拍板再动 UI。
- 🔴 **子任务语义未决**：`subtasks.ts:31`"两件刻意不决定的事"、`:386`"不决定删除怎么级联、
  移动是否带子树"。UI 只给了"挂父级"选择器，不是可勾选子任务列表。
- **性能**：`performance-hotpaths-audit.md` 已在库（11 P0 / 18 P1，§8 有落地顺序与台账自检）。
  乙的补充判据值得采纳：**为 500 / 1000 / 5000 条任务建立体验性能基线**——
  任务应用在大数据量变慢，"平静专注"的产品气质会直接消失。
- **URL/深链策略**（乙）：当前视图/筛选无 URL 表示，无法分享、回退、恢复现场。
