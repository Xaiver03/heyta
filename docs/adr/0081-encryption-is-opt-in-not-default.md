# ADR-0081：默认**不加密**，端到端加密改成用户显式开启

- **状态**：已接受（2026-11-01，产品负责人拍板）
- **日期**：2026-11-01
- **取代**：[ADR-0080](0080-e2ee-is-optional-with-device-held-key.md) **§一 第 1 条**（"端到端加密仍是默认，也是卖点"）。
  0080 的其余结论**全部保留**：两个轴分开、关闭=整库迁移、钥匙可由设备持有、
  两个方向都拒错配。ADR-0079（基础资料明文）不动。
- **相关**：[ADR-0040](0040-email-password-auth-decoupled-from-e2ee.md)、[ADR-0050](0050-e2ee-key-lifecycle-and-recovery.md)、
  [ADR-0013](0013-cloud-ai-and-maas.md)（托管 AI 不是 E2EE）

---

## 一、决策

**新账号默认 `readable`（服务端可读的明文）；端到端加密是设置里的一项显式开启。**

产品负责人 2026-11-01 原话：

> 「默认是明文；加密变成用户显式开启，没问题，就应该这样。因为绝大多数用户在用记账软件，
>  即使是个人记账软件，也不会选择这个方向。我们没有必要强制自己做出任何差异之类的。」

## 二、为什么改（上一版错在哪）

ADR-0080 把"加密"当成**默认**、把"不加密"当成需要确认的例外。这个默认值本身是有代价的：

| 代价 | 谁在付 |
|---|---|
| 每个新用户都要理解并保管一个**丢了就找不回**的口令/恢复码 | 全部用户 |
| 忘记口令 = 历史数据永久不可读（服务端帮不了） | 忘记口令的人 |
| 托管 AI 与"服务端读不到"两句话长期互相打脸 | 用 AI 的人 |
| 支持成本：客服无法判断"是口令错还是数据坏了" | 我们 |

而它换来的保护，**只对真正需要它的人有价值**。让 100% 的人为 5% 的威胁模型付成本，
就是 ADR-0079 已经否掉过的同一种错误（"谁会把头像当成隐私？"）。

## 三、取舍的边界（这次没有放宽的东西）

1. **加密仍然完整可用**：开启走整库重加密（ADR-0080 §5.3 的机制原样保留），
   关闭走整库解密重传（§5.2）。两个方向的"半密半明"照样在服务端被拒。
2. **开启之后的所有承诺不变**：服务端读不到、我们也无法解密、忘记口令仍等于丢数据。
3. **默认明文 ≠ 不设防**：`payload_mode` 仍按账号存在且有 CHECK；读取失败时
   **fail-closed 到 `e2ee`**（不能因为一次数据库抖动就把明文收进来）。
4. **对外文案必须说"默认不加密"**，不许再写"服务端从设计上就看不到明文"这种绝对句。

## 四、落地形状

- 契约：`DEFAULT_SYNC_PAYLOAD_MODE = 'readable'`（`packages/shared-schema/src/sync-mode-contract.ts`，单一来源）
- 数据库：`user_sync_state.payload_mode` 默认改 `readable`，存量行回填
  （迁移 `20261101160000_default_payload_mode_is_readable`）
- 服务端 `readPayloadMode`：**行不存在 ⇒ 默认值**；**读失败/值不认识 ⇒ `e2ee`**。
  这两条退路刻意不同，理由见上。
- 客户端/宿主：无需改动 —— 模式一直是从服务端读的，翻默认值对它们透明。
- 对外口径：`site.integrations.e2ee.*`、服务条款第四条、隐私政策、数据权利、README 同步反转。

## 五、判据

| 层 | 判据 |
|---|---|
| 契约 | `DEFAULT_SYNC_PAYLOAD_MODE === 'readable'`；`SYNC_PAYLOAD_MODES` 仍只有两个值 |
| 服务端 | 无 `user_sync_state` 行 ⇒ `readable`；`findUnique` 抛错 ⇒ `e2ee`（两条要分开断言） |
| 闸门 | `readable` 账号收明文、拒密文；`e2ee` 账号反之（ADR-0080 S1 的四格表原样保留） |
| 迁移 | 真实 PostgreSQL：默认值已改、存量 `e2ee` 行被回填 |
| 开启路径 | 明文账号可走两步开启，之后 `payloadMode` 读回 `e2ee`、上传为密文 |
| 口径 | 全仓 grep"默认"与"看不到明文"的绝对句 ⇒ 0 命中 |

## 六、后果

1. **"服务端看不到明文"从默认承诺降为可选承诺**。这是本次**明确接受**的代价，
   换来的是不用口令、可找回、AI 与存储口径一致。
2. 想讲隐私卖点时，正确说法是"**你可以让它看不到**"，而不是"我们看不到"。
3. 若将来要给"默认加密"的用户做档位，那是另一次决策（可复用同一套开关与迁移）。
