# ADR-0094：平台独占能力（系统快捷指令 / 打印 / 应用锁 / 浮动便签）的对标边界

> 状态：**提议（Proposed）**（是否采纳由产品负责人决定；本文件只给结论与理由）
> 日期：2026-11-26
> 相关：[ADR-0024](0024-desktop-shell-and-ui-convergence.md)（桌面壳与 UI 收敛）、
> [ADR-0036](0036-main-battlefield-and-rn-single-source-ui.md)（主战场与 RN 单一源 UI）
> 证据：[`ticktick-coverage-graph.md`](../research/ticktick-coverage-graph.md) §3 的第 #36/#61/#70/#73 行与 §3c「D 档归属」；
> [`ticktick-desktop-teardown-2026-11.md`](../research/ticktick-desktop-teardown-2026-11.md)

## 1. 背景

覆盖图谱把四格标成「D 双缺」（没做、也无一手靶子），且都属「平台独占 / 桌面专属」类：
`#36 浮动便签/置顶窗`、`#61 应用锁`、`#70 打印/打印预览`、`#73 系统快捷指令`。
问题是：**这些格子要不要在 heyta 的 Web + Electron 桌面壳里对标实现？** 不写清楚，它们会永远挂在「待办」里当噪音。

## 2. 结论（逐格）

| # | 屏 | 结论 | 理由 |
|---|---|---|---|
| **#36** 浮动便签/置顶窗 | **做**（Electron `alwaysOnTop` 小窗） | 桌面壳能力，用户价值高、成本低；属桌面差异，不违反宿主边界 |
| **#61** 应用锁 | **做**（本地 PIN / 生物识别门禁） | 本地优先产品的基础隐私开关；纯客户端 gate，不涉服务端 |
| **#70** 打印/打印预览 | **做**（浏览器原生 `window.print` 打印当前视图） | 一个接口调用；无需自研排版引擎 |
| **#73** 系统快捷指令 | **不做**（Web/桌面无对应平台；iOS AppIntents 另立） | 系统级快捷指令是移动 OS 独占能力。Web 与 Electron 没有"快捷指令市场"这一平台；桌面的"快捷操作"由 #7 全局快捷键 + #6 命令面板承载。iOS 的 AppIntents/Siri 属 iOS 端后续工作，不纳入本轮 Web 对标。 |

## 3. 后果

- #36/#61/#70 落地后，这三格从 D 升到「有功能」（是否 A 取决于一手靶子，见各自实现）。
- **#73 从「D 双缺」改为「范围外（not applicable）」**，覆盖图谱档位记 `N/A` 而非 D；不再计入「没学到」。
- 判据：Web/桌面不再追补 Siri/快捷指令截图；若日后做 iOS 端，另写 iOS 能力 ADR。

## 4. 不做的事

- 不为 #73 自造一个"伪系统快捷指令"界面（那是把平台惯性当最佳实践抄回来）。
- 不为 #70 自研 PDF 排版引擎（浏览器原生打印够用，超出即违反可维护性门槛）。
