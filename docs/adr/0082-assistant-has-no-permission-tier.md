# 0082 · 内置助手**不设权限档**：删掉 `assistantTier`（只读 / 执行）

> 状态：**已接受**（2026-11-01）
> 授权依据：产品负责人 2026-11-01 指着设置页的「助手权限」控件（截图里那枚
> `只读 / 执行` 分段选择器）说：
> ①"这个地方设计很不合理"；②"我觉得都不需要有权限的设计，没必要区分只读和执行，
> 我没看到别的产品这么做过"；③"保持一致就行"（与 DSH 那种"没有权限模式、只有
> 危险动作确认"的形态对齐）。
> 取代：[ADR-0045](0045-conversational-assistant-split-authorization-from-catalog.md) 的
> **§5 D-5 那条两档落地方向**（以及 §2.2 表里"授权前端 = 能力档位"那一格）。
> ADR-0045 的其余结论**一条不动**（一次一个写提案、一次性并集披露、三个硬上界、
> 入站侧判据、"一份目录一个执行核"）。
> 证据基础：`packages/app-host/src/assistant-tier-settings.ts`（已删）、
> `assistantGrants()` / `planAssistantEgress()` 的调用面、`apps/web` 与 `apps/mobile`
> 的两处界面、`docs/research/ai-competitive-and-architecture.md`（同类产品的助手入口形态）。

---

## 1. 背景与约束

### 1.1 那个旋钮回答的是一个用户不会问的问题

`assistantTier` 只有两档：`read-only`（模型看不见写工具）与 `read-and-propose`
（看得见，低风险自动提交、高风险出提案）。它来自 ADR-0045 §2.2 那次"拆授权层"的
收尾 —— 当时要解决的问题是真的：**内置助手不该沿用入站 MCP 那套逐工具默认关**。

但落到界面上，它变成了一件用户没在问的事：

- 用户已经在对话框里说了"帮我把这条任务改到明天"；此时再要他去另一个界面把
  一个开关从"只读"拨到"执行"，是把**一次安全决策伪装成一项配置**。
- 更糟的是默认值：出厂就是"执行"，也就是说这个开关在**绝大多数用户那里从来没被
  碰过**。它实际承担的不是"选择"，而是"一次误触就把助手变哑"的机会。
- 而它承诺的保护（"只读档不会写"）在产品语义上并不成立 —— 助手**本来就不是**
  可以"只读地"用来查东西的地方（那是列表与搜索的活）。一个只会读的助手是
  一个没有存在理由的形态。

### 1.2 硬约束

| 约束 | 来源 | 意味着什么 |
|---|---|---|
| 写入必须仍然**一次一个、高风险确认** | ADR-0045 §2.1 / §2.4、ADR-0005 §2、ADR-0035 §2 | 删档**不许**顺带把确认链也删掉 |
| 出境必须在**任何一次请求之前**一次性说清 | ADR-0045 §2.3、ADR-0035 | 披露那块 UI 要留下，只是不再"随档位变" |
| 判断只能有一份 | AGENTS §3.5、ADR-0035 §2 | 外壳不许自己写"能不能写"，`isToolGranted()` 仍只有 `@heyta/local-api` 一处 |
| 入站本机 API 的授权一条不动 | ADR-0011、ADR-0045 §2.2 | 那张逐工具表（默认全关）与助手无关，不许被这次改动波及 |

## 2. 选项

| 选项 | 优点 | 缺点 | 判定 |
|---|---|---|---|
| **A. 删掉档位，助手 = 整份目录 + 风险闸门** | 用户只回答一个问题（"要不要让它做"），而不是两个；与同类产品一致；少一个持久化字段、少一个跨端漂移面 | 失去"完全禁止写入"这一档；只想要查询的用户没有开关可拨 | ✅ **采纳** |
| B. 保留两档，只把 UI 从设置页挪进对话框 | 改动小 | 问题不在**位置**，在**存在**。搬进对话框只是让一个用户不会问的问题更碍事 | ❌ 否决 |
| C. 只保留"只读"，删掉"执行" | 最保守 | 把助手降级成搜索框，ADR-0045 的全部价值（"界面里能做的事都能让 AI 做"）归零 | ❌ 否决 |
| D. 保留两档，但默认"只读"并加一次引导 | 看似更安全 | 默认只读 + 引导 = 每个新用户的第一句话都被拒一次。这是把 ADR-0045 §2.2 想解决的那个"先去设置页开六个开关"换个位置重演 | ❌ 否决 |

**为什么"没有只读档"不等于"没有安全边界"**：安全性由两件**已经存在**的东西提供，
档位从来没有真正参与其中 ——

1. `aiToolProposalRequiresConfirmation()`：破坏性动作（批量完成、改备注、更新事件、
   改清单项、清空标签……）仍然逐条出提案，模型看不到"它被批准了"；
2. 一次性并集披露：字段并集 + 工具名 + 三个硬上界，在**第一次发送之前**说完。

也就是说，档位只决定"低风险自动提交"那半边的**有无**，而那半边正是产品的卖点。

---

## 3. 结论

1. **删除 `assistantTier`**：类型、持久化字段、归一函数、`createAssistantTierStore`、
   两处界面控件（`apps/web` 设置页的 `assistant-tier-group` 与对话面板头部的
   `ai-assistant-tier-select`、`apps/mobile` 的设置 Chip 与助手页 Chip）全部删除。
   `packages/app-host/src/assistant-tier-settings.ts` 整份删除。
2. **`assistantGrants()` 不再收参数**，返回**整份工具目录**（`LOCAL_API_TOOLS` 每条 `true`）。
   `assistantEgressFields()` / `planAssistantEgress()` 同样不再按档位算。
3. **写入语义固定为原"执行"档**：低风险自动提交（仍要求 `executionId` 防重放），
   高风险出提案。`aiToolProposalRequiresConfirmation()` 一条不改。
4. **披露那块 UI 保留**（设置页 `ai-assistant-section` 的字段 / 工具 / 上界三行，
   对话面板的一次性披露卡），但不再"随档位变"—— 它现在只有一个答案。
5. **入站 MCP 的 `localApi.grants` 一条不动**：助手与它仍是两张表。
6. **`check:layering` 的 `no-assistant-tier-literal-in-apps` 规则随之删除** ——
   它保护的字面量已经不存在，而一条描述已删字段的规则会继续指着已删函数。

---

## 4. 后果

- **更好做**：助手的行为只有一种形态，两端不可能再出现"这台设备只读、那台能写"；
  设置页少一个用户不会用的控件，AI 那一屏的层次更清楚（披露是**信息**，不是**开关**）。
- **更难做**：真有人想要"只让它查、不许它写"，现在没有产品内的开关。
  正确的替代是**别让它做那件事**（说清楚要什么），或关掉 AI 总开关。
  若将来确实需要，那应该是一个**会话级**的临时约束（"这一条只问不改"），
  而不是一个跨设备的持久档位 —— 那要另写 ADR，不要把这个字段加回来。
- **要守住的东西**：`aiToolProposalRequiresConfirmation()` 现在**独自**承担
  "哪些写不自动落地"。给它加白名单时，等于在给自动写入开口子 —— 那是本 ADR 之后
  最危险的一处改动，必须配一条会失败的测试。
- **披露的诚实性**：字段并集现在包含 17 个写工具的 `egressFields`（它们通常为空，
  因为写结果不回送模型）。这不会让披露变假，但**目录扩写工具时要重新看一遍**。

---

## 5. 未核实项

- **同类产品是否真的都没有这个档位**：产品负责人的判断（"我没看到别的产品这么做过"）
  与 `docs/research/ai-competitive-and-architecture.md` 的观察一致（Todoist 的
  `--read-only` 是**入站 MCP** 客户端开关，不是应用内助手的用户设置），但本次
  **没有**逐一复核每一家。若将来发现某家用"应用内助手权限档"作为卖点，本 ADR 的
  §2 那张表要重读。
- **删除档位是否会减少实际写入量**：没有埋点，无法现量。可观察的替代指标是
  "AI 提案的确认率"，但那一层目前没有上报。
- **移动端 `heyta.ai.tier` 这个设备偏好键**：删档之后它不再被读写。**没有**做清理
  （写一次"删除该键"的迁移属于数据迁移，与本 ADR 无关），它只是一条永远读不到的
  旧值。若将来有人做偏好库清理，它可以一起删。
