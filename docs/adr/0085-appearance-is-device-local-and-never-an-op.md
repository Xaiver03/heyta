# ADR-0085：外观是"这台机器长什么样"，永不产生 op

- **状态**：已接受（2026-11-06，R13 开工前置）
- **日期**：2026-11-06
- **相关**：[ADR-0003](0003-multi-platform-strategy.md)（多端与宿主边界）、
  [ADR-0084](0084-local-library-ownership-and-signout-erasure.md)（本机库归属 —— 本条是它在"表达"这一维的同形）
- **上游需求**：[产品需求对齐清单](../plans/ticktick-parity-prd-2026-11.md) R13（R13a 入口 / R13b 主题与行着色）
- **取证**：[设置与个性化全量取证](../research/ticktick-settings-and-personalization.md)（八维、两类混排的三条证据、`本机 vs 账号` 那一层）

---

## 一、问题

R13 要落八个个性化维度（主题 / 界面风格 / 字体族与字号 / 密度 / 应用图标 / 自动深浅 / 便签与倒数日样式 / 快捷键），
外加一条最便宜也最"我的"的：**行着色**（按清单色或标签色）。

而 heyta 的写入口只有一条：**op-log**（事件溯源，向量时钟 + LWW + `clientId` 打破平局）。
如果外观也走 op，会出现三个具体后果：

1. **换一次主题 = 一条同步 op**，而它描述的不是"这份数据变了"，是"我这台机器长什么样"；
2. **两端会互相覆盖**：手机上选了深色、桌面上选了浅色，LWW 必有一端被改掉 ——
   而用户从来没要求"所有设备看起来一样"；
3. **行着色依赖清单色/标签色**（那是数据），一旦把"着色开关"也当数据写，
   就会出现"我关掉行着色"被同步成"你也关掉"这类**跨设备的行为改动**。

滴答把两类混在同一个设置树里：**个性化**（「让它看起来像我」）与**行为默认值**（「让我少填几次」）。
它唯一分开的是「本机 vs 账号」—— 外观进本地 `CommonSettings`，行为默认值进带 `SyncPoint` 的 `SettingsModel`。
**这一层分法是对的，我们采纳；混排那条不采纳。**

## 二、选项

| 方案 | 形状 | 代价 | 致命问题 |
|---|---|---|---|
| **A. 外观纯本机** | 外观只写设备配置（`localStorage` / 各壳偏好），op-log 里**零条** | 小 | 换设备看到的是默认外观（对"我的机器"这个语义而言**不是缺陷**） |
| B. 外观走 op | 与数据同一条通道，多端一致 | 中 | 上面三条后果全中；且与「一个用户意图 = 一条 op」冲突 —— 换主题不是数据意图 |
| C. 混合：默认本机 + 「推送到其他设备」 | A 为底，额外给一次显式推送 | 大 | 需要一个"外观包"的同步语义与冲突规则，而收益只覆盖"我想所有设备一样"这一种诉求 |

## 三、决策

**采用 A。C 明确列为"将来可做"，现在不做。**

1. **分层的判据是一句话**：这次改动**改的是同一份数据的表达，还是新建/触发时的初值**？
   - 表达（主题、深浅、字号、字体、密度、行着色开关与依据、应用图标、便签/倒数日样式）⇒ **本机，不产生 op**；
   - 初值（周起始、默认提醒、默认清单、默认时长、智能识别）⇒ **账号，走 op**。
2. **行着色是表达层**：它**读**清单色与标签色（数据），但"按什么着色 / 开不开"**不写数据**。
   ⇒ 判据是"读得多、写得零"，不是"它看起来像设置所以随便放"。
3. **自动深浅**（跟随系统）也是本机：它描述的是这台设备的显示环境。
4. **持久化键要登记**：外观类键与行为类键**分列两份清单**，新增一个外观键必须进外观那份。
   ⚠️ **口径声明**：正文里"24 个键 / 外观类只有 2 个"是 P9 那册取证的读数
   （[`ticktick-settings-and-personalization.md`](../research/ticktick-settings-and-personalization.md)），
   **不是我在本条里重新点过的**。我自己现量过一次字面量（`grep -rhoE "'heyta\.[A-Za-z0-9._]+'" apps/web/src apps/mobile/src packages/*/src`）
   得 **21** 个 —— 这是**字面量下界**，不是键总数（有些键是拼出来的），所以两个数不能互相顶替。
   🔴 **而且今天仓里没有这份清单**（`docs/reference/` 下没有任何键登记表）。所以这条规矩现在是**悬空的**：
   谁先加第一个外观键，谁负责建 `docs/reference/client-persistence-keys.md` 并把两类分开列 —— 别只加到代码里。
5. **`data-theme` 这类 DOM 钩子不算持久化**：它是渲染结果的形状，不是用户偏好。

## 四、后果

**接受的代价**

- 换设备**不会**带来同一套外观。这是故意的：我们把"外观"定义成**设备属性**，不是账号属性。
- 用户若真的想让两台机器一致，现在只能手动各选一次。方案 C 能解，但它要一整套"外观包"同步语义，**不在这一轮**。
- 服务端渲染/邮件/导出的外观不归本条管（那些是内容，不是"我的机器"）。

**换来的东西**

- 换主题**不产生同步流量**，也不与另一台设备打架。
- op-log 里不会出现"表达"类事件 ⇒ 事件溯源的语义更干净（每条 op 都是"数据变了"）。
- 跨端判断变简单：**同一份 tokens，两端各自的选择**，不需要同步冲突规则。

## 五、判据（每条都要能红）

| # | 判据 | 怎么才会红 |
|---|---|---|
| 1 | 改主题 ⇒ op-log 条数**不变** | 把外观写入改成 `dispatch(op)` ⇒ 条数涨 1，判据红 |
| 2 | 行着色切三态（按清单 / 按标签 / 关）⇒ 列表颜色变，**op-log 条数不变** | 注掉读取点 ⇒ 颜色不变而判据要求变，红；把开关写成 op ⇒ 第 1 类红 |
| 3 | 外观键只出现在外观模块 | 把外观键塞进行为默认值那份清单 ⇒ 键清单对账红（`docs/agents/` 的键清单是唯一真源） |
| 4 | 换端**不**同步外观（反向判据） | 若某天有人给外观加了 op，判据 1 立刻红；这一条钉的是"别悄悄加" |

## 六、残余

1. **方案 C（推送到其他设备）没做**，也没有设计。真要做，需要的不是"多发一条 op"，而是一套可解耦的"外观包"语义 + 一次显式用户动作。
2. **应用图标**在移动端是安装器级别的资源，不在本 ADR 的运行时范围；它同样不产生 op，但落地方式按端各自定。
3. **旧键迁移**：现在 24 个持久化键里外观类只有 2 个，没有历史包袱；但 R13b 之后要防止"同一个偏好两处存"，
   登记清单是唯一手段（判据 3）。
4. 本条**不覆盖**"界面风格（`interfacestylewindow` / `AppStylePickerViewController`）"这种**结构性皮肤**：
   它若真的改变布局而不只是颜色，代价与主题不同类，需要单独评估 —— 本轮不做。
