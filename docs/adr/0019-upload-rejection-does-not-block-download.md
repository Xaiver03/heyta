# ADR-0019：上传被拒不得阻断下载 —— 永久拒绝的 op 移出队列而不是无限重传

- **状态**：已接受
- **日期**：2026-09-27
- **相关**：[ADR-0016](0016-undecryptable-ops-do-not-block-sync.md)（同一类问题的上一例）、
  [ADR-0003](0003-multi-platform-strategy.md)（宿主薄壳）

---

## 1. 背景

### 1.1 现象

一台设备会进入一种**自愈不了**的状态：

- 界面上同步一直失败，待上传数永远不归零；
- 而真正发生的事是 —— **这台设备再也拉不到任何远端数据**。

它是**单向**聋的：别的设备写的东西永远到不了它这里，它自己的改动却可能照常上去。

### 1.2 复现（零 mock，真服务端 + 真 SQLite）

往一台设备的真队列里放一条 `clientId` 不属于本机的 op（真实故障的形状：
别的设备的残留数据混进了本机队列），然后连续同步两次：

| 第几次 | 结果 | 待上传 |
|---|---|---|
| 1 | `accepts 1, rejects 1` → **抛错** | 1 |
| 2 | `rejects 1/1` → **又抛错** | 1（永远） |

### 1.3 根因

`SyncClient.upload()` 在服务端拒绝**任何**一条 op 时直接 `throw`，
而那个 `throw` 发生在 `sync()` 的**下载阶段之前**：

```
sync() → upload() → ❌ throw
                ↘ download()   ← 永远走不到
```

于是"上传里有一条永远过不去的 op"这个**局部问题**，
升级成了"这台设备永久失去下载能力"这个**全局故障**。

同时那条被拒的 op 一直留在待上传队列里：每次同步重传它、每次都被拒。

### 1.4 已有的两处同类修正是**不同**的

- `markUploaded` 被移到 throw **之前**（同批里已被接受的 op 仍会落盘）——
  这解决了"整批重传"，但**没有**解决"throw 挡住 download"，
  也**没有**解决被拒那条自己永远留在队列里。
- ADR-0016 处理的是**下载侧**解不开的 op（跳过、不推进游标、如实上报）。

真正的缺口是：**上传侧的失败会影响下载侧的执行**。

---

## 2. 决策

### 2.1 上传的失败**永不**阻断下载

`sync()` 的下载阶段必须在上传阶段发生**任何**拒绝之后照常执行。
上传的问题只该影响"能不能上传"，不该影响"能不能拉取"。

### 2.2 拒绝分两类，处置相反

| 类别 | 含义 | 处置 | `retryable` |
|---|---|---|---|
| **永久拒绝** | 重传同一份内容永远不会被接受 | **移出待上传队列**（`markRejected`），如实上报 | `false` |
| **暂时被挡** | 限流、配额、服务端内部错 | **留在队列里**，下次重传 | `true` |

永久拒绝的名单是**显式白名单**（`PERMANENT_REJECTION_CODES`）：校验类、
`INVALID_CLIENT_ID`、`INVALID_OP_ID`、`DUPLICATE_OPERATION`、加密配置不匹配。

🔴 **拿不准的一律算"暂时"。** 判成永久会**丢掉一条本来能上去的改动**，
比"多试几次"严重得多 —— 而"多试几次"已经不会再卡死设备了（2.1 保证了这一点）。

### 2.3 新增第三种上传状态 `rejected`，**不并进** `uploaded`

`UploadStatus` 从 `pending | uploaded` 变成 `pending | uploaded | rejected`。

把被拒的 op 标成 `uploaded` 会让"待上传数归零"和"已同步"**同时说假话**：
那条数据哪都没去，而用户从此再没有机会知道。
`rejected` 既不在队列里，也不声称成功。

### 2.4 上报是结构化的新原因 `upload-rejected`

不塞进 `'unexpected'`：网络问题该重试，永久拒绝重试一万次也一样。
混在一起用户只会看到一句"同步出错"，既不知道**有改动没上去**，也无处可查。
报错里必须**点名是哪几条 op**（`opId` + 错误码 + 服务端原文）。

### 2.5 报错优先级：一次性信息排在持久状态之前

`upload-rejected` 在 `undecryptable-ops` **之前**上报。

理由：永久拒绝的 op 已经移出队列，**下一次同步不会再提它**
（错过就再也看不到）；而解不开的 op 是持久状态，下次照样会报。
**判据优先级 = "错过就再也看不到的"优先。**

## 3. 后果

### 3.1 好的

- 一条坏 op 不再能让一台设备失去下载能力；
- 队列**收敛**：`pending` 能归零，不再无限重传；
- 拒绝态**可观测**（`rejected` 是独立状态）—— 这同时是验收脚本的判据基础；
- 数据**不丢**：只移出队列，op 仍留在日志里（op-log 是事实来源）。

### 3.2 代价与已知限制

- **被拒的改动不会自动重试。** 这是有意的：它重试也不会成功。
  但界面目前只显示一句词条 + 诊断细节，**没有"我该怎么处理它"的引导**
  （比如"这条 op 属于别的设备，可以从本机移除"）。这是一个已知的产品缺口。
- **永久/暂时的划分靠白名单**，服务端将来新增一个真正永久的错误码时，
  它会被当成"暂时"而被无限重试。这**不会再卡死设备**（2.1 兜住了），
  但会让待上传数长期不归零。兜底方案（同一 op 连续被拒 N 次后自动隔离）
  **本轮未实现**，需要额外的持久化计数。
- 新增了一个 `UploadStatus` 取值。它是**既有字段的新取值**，不是新字段，
  所以不需要 bump `CURRENT_SCHEMA_VERSION`；但**读旧数据的代码要知道第三个取值存在** ——
  所有 `switch` 都已按穷尽写法处理（漏一个会编译不过）。

## 4. 验证

| 层次 | 手段 | 判据 |
|---|---|---|
| 存储契约 | `packages/storage/tests/contract/op-log-store.contract.ts` | `markRejected` 移出队列、**不标成 uploaded**、op 仍在日志里；三个适配器（IndexedDB / SQLite / 内存）**同一套** |
| 客户端单元 | `packages/sync-client/tests/sync.spec.ts` | 永久拒绝 → 移出队列 + `retryable:false` + **下载仍执行**；暂时被挡 → 留在队列 + `retryable:true`；未知码按暂时 |
| 零 mock 端到端 | `pnpm verify:sync-recovery` | 真服务端 + 真 SQLite：被拒的**同一次**同步里仍拉到另一台设备刚写的数据；`pending=0`、`rejected=1`、数据仍在；下次同步 `synced` |

**变异测试**（证明判据有鉴别力，而不是"读起来很对"）：

1. 把 `upload()` 改回"硬拒绝直接抛错" → `verify:sync-recovery` 在
   **「没拉到对端那条 —— 这台设备变聋了」** 上变红（4 项红，rc=1）；
2. 把 `RATE_LIMITED` 塞进永久名单 → 单元测试在
   **「暂时被挡时 op 留在队列里」** 上变红。

## 5. 被否决的方案

**「一律重试到底，不区分永久/暂时」**（= 保持原状，只是把 throw 挪到下载之后）。
否决理由：队列永远不收敛，待上传数永远不减，用户看到的仍是"同步一直失败"；
而且每次同步都要把那条注定失败的 op 重传一遍，白白消耗配额。

**「被拒就删掉那条 op」**。否决理由：op-log 是事实来源，删了就无法解释
本机曾经是什么值，重放也会与其它设备不一致。移出队列与删除是两件事。
