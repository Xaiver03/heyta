# ADR-0075：运营公告是一条**内容通道**，不走通知通道

> 状态：**已接受**
> 日期：2026-10-24
> 相关：[ADR-0038](0038-admin-console-scope.md)（后台范围，§2 第四条正是本份要划清的那条线）、
> [ADR-0052](0052-public-facts-are-deployer-supplied.md)（公共事实由部署方下发 —— 本份是它的**第二条**同型通道）、
> [ADR-0071](0071-share-notification-content-boundary.md)（通知的内容边界）
> 落地：`server/src/announcements/`、`apps/web/src/features/announcements/`、后台「公告」分区

---

## 1. 背景

产品负责人要求后台补上 SSOS 那一档里的**运营公告**：运营者写一条话，所有用户看得见。

而 ADR-0038 §2 第四条**明确否决过**一个看起来正是它的东西：

> **不做**：改订阅、退款、发券、**群发通知**。…… 群发自由文本会**同时**破坏两条既有立场：
> 通知的 `kind` 是封闭词表，且服务端只存**语义 + 参数**、不存渲染好的文案。
> 真要做营销触达，那是另一条线（需要新的 kind + 词条），不是后台的一个文本框。

所以第一件事不是"怎么实现"，而是**这句话到底拦的是哪件事**。

## 2. 关键区分：活动事件 ≠ 内容

`account_notifications` 里的一行是**一次发生过的事**：某人的共享邀请被接受、某台设备登录了。
它的形状因此必然是「语义（`kind`）+ 参数」，文案由 `packages/i18n` 在客户端渲染 ——
用户切语言，历史通知跟着换语言。**这是那条立场存在的理由，不是一条格式洁癖。**

一条运营公告不是事件。它是**一段现在挂着的内容**：没有"发生"过，不进入任何人的历史，
它的内容本身就是运营者写的那句话，**换语言也不该变**（因为它不是应用的文案，是那条公告）。

⇒ 把它塞进 `NOTIFICATION_KINDS` 是**用错了通道**：
要么服务端开始存文案（破坏 i18n 单源），要么给一段自由文本编一个 `kind` + 词条键
（词表被一个不存在的事件类型撑开）。两条都是把内容伪装成事件。

## 3. 决策

**一、公告是一条独立的内容通道，与通知无关。** 新表 `announcements`，
读面 `GET /api/announcements`，写面挂在后台 `/api/admin/announcements`。
**不新增任何 `NOTIFICATION_KINDS` 成员，不新增任何词条键承载公告正文。**

**二、形状与 ADR-0052 同型：服务端 → 客户端的下发内容，不进 op-log。**
它不是用户的数据，因此不参与端到端加密与同步；它是**部署方的公开陈述**，
与调休/补班同一类。这一条是本份决策最值钱的地方：**已经有过一次同样的取舍**，
不必重新论证"为什么这不是同步数据"。

**三、`level` 是封闭词表，正文是自由文本。**
`level ∈ {info, warning}` 决定界面怎么画（这一格是**语义**，不是外观 —— 见设计系统那条
"用语义名不用外观名"）；`title` / `body` 是运营者写的原文，界面**原样呈现**。
原样呈现不等于"界面里不许有文案"：应用自己的文案仍然全部住在 `packages/i18n`，
公告正文是**数据**，与"用户自己写的任务标题"同一类。

**四、有效期由服务端算，界面不判。** `publishedAt` / `expiresAt` ⇒
"现在这条算不算挂着"是一个会改变用户所见的事实，裁决权在服务端那一条查询里。
界面自己比时间戳 = 第二套标准（与后台那三个支持动作同一条纪律）。

**五、忽略是**设备本地**的，不是服务端的。** 用户关掉一条公告 ⇒ 记在本机，
换一台设备还会看到。理由：服务端记"谁读过哪条公告"是一次**新增的个人信息处理**
（要账号维度的阅读史），而它换来的便利只是少点一次关闭。
本仓库的前提是本地优先 + 服务端看不到用户明文 —— 阅读史与这个前提方向相反。

**六、写面权限最高的一组，且只有"发布"和"下架"两个动作。**
沿用 ADR-0052 §2.2 的取舍：**不提供逐条编辑历史、不提供定向投放**。
下架是删除那一行（内容本身没有"部分状态"可言），不是"下发一条空公告"。

## 4. 为什么不选另外三条路

| 选项 | 为什么不做 |
|---|---|
| 新增 `kind='announcement'` + 参数携带正文 | 就是 ADR-0038 §2 第四条拦的那个。服务端存文案 ⇒ i18n 单源破了；而且公告会混进"我的通知历史"，一条挂着三个月的公告在历史列表里是一个**谎**（它不是一次发生的事） |
| 走 op-log（当成一种实体同步） | 公告不是用户的数据。进 op-log 意味着端到端加密、向量时钟、冲突合并 —— 全都不需要，而代价是**每个部署方的公告都要在每个客户端的 op-log 里回放一遍** |
| 静态写死在 `packages/i18n` 里 | 那样"发一条公告"要发一次版。运营触达的定义就是**不发版也能改** |

## 5. 后果

**好的**：运营第一次能不发版告诉所有用户"今晚要维护"；
ADR-0038 §2 第四条**一字未改**仍然成立（它拦的是"群发通知"，本份没做群发通知）；
`NOTIFICATION_KINDS` 仍是封闭词表；服务端仍不存任何应用文案。

**要认下来的**：

1. **公告是明文。** 它走 HTTPS，不走端到端加密 —— 与调休/补班同一性质。
   所以**不许**在公告里放只有部分人该看到的东西（密码重置链接、个人数据）。
   这一条要写进后台那格的界面提示里，不能只写在本文档里。
2. **没有阅读回执。** 运营看不到"多少人看了"。这是 §3.5 那条取舍的直接后果，
   不是遗漏。将来若要，得单独论证一次个人信息处理。
3. **多语言靠运营者自己。** 一条公告一种语言。给同一件事发两条（中英各一）
   是当前的用法；做成"一条公告 N 个语言版本"要新增形状与界面，等真有人需要再做。
4. **忽略状态是本机的** ⇒ 换设备会重看一遍。可接受。

## 6. 与既有立场的对账（逐条核过，不是"应该没破"）

| 既有立场 | 本份动了吗 |
|---|---|
| ADR-0038 §2 第四条「不做群发通知」 | **没动** —— 本份做的不是通知。判据：`NOTIFICATION_KINDS` 成员数不变（`packages/domain/src/activity.ts`） |
| 「服务端只存语义 + 参数，不存渲染好的文案」（`activity/notifications.ts` 文件头） | **没动** —— 公告不住在那张表里 |
| 「文案的唯一事实源是 `packages/i18n`」 | **没动** —— 公告正文是**数据**不是文案；界面文案仍然全部走词条 |
| ADR-0052「公共事实由部署方下发、不进 op-log」 | **沿用**，并新增第二个实例 |
| 「管理端点一律不返回密文/密钥类字段」 | **沿用** —— 公告里本来就没有这类字段；投影仍是显式列出的白名单 |
| 「服务端是唯一裁决者」 | **沿用** —— 有效期、下架、权限全在服务端 |
