# ADR-0030：未认证的通行密钥验证端点**暴露"某个已知凭据是否还注册着"** —— 明确接受这个存在性预言机

> 状态：**已接受**
> 日期：2026-09-28
> 取代：无

## 1. 背景与约束

登录失败时，服务端此前**只有一种** 401：笼统的 `Authentication failed`。这带来一个
**用户无法自行诊断**的处境，而两种成因需要**完全相反**的动作：

| 真实成因 | 用户该做什么 |
|---|---|
| 这条凭据**服务端已经不认了**（在别的设备上删过、或账号被重置过） | **别重试**了 —— 重新注册一条，或换邮箱登录链接 |
| 凭据还在，但这次断言**没验过**（用户取消、指纹没识别、挑战过期） | **再试一次**是对的 |

两者的界面表现完全一样，于是"陈旧凭据"的用户会**反复重试一个永远不会成功的动作**，
而真正需要的动作（重新注册）他永远得不到提示。

硬约束：

1. **这个端点未认证**：它在用户登录**之前**被调用，无法用"当前用户"限定查询范围，
   所以任何"这条 id 存不存在"的差异都可能被外部探测。
2. **credential ID 不是秘密，但也不是公开的。** 它每次登录都明文出现在
   `navigator.credentials.get()` 的断言响应里，也躺在浏览器/系统的凭据库里；
   WebAuthn 规范**从不把它列为需要保密的数据**（需要保密的是签名私钥，以及
   足以伪造签名的材料）。但服务端此前**没有任何接口**返回它。
3. **它是 32 字节随机值**，不可枚举：攻击者必须**先知道某一个 credential ID**
   才能问出关于它的**一个比特**。

## 2. 选项

| 选项 | 优点 | 缺点 | 关键证据 |
|---|---|---|---|
| A. 保持单一笼统 401 | 零信息泄露；实现最简 | 用户**无法自行诊断**两种成因；"陈旧凭据"那条路会变成无限重试 | 本次改动前的行为 |
| **B. 用两个 `code` 区分**：`passkey_not_found` / `passkey_verification_failed`，而 `message` 保持同样笼统 | 客户端能说两句**不同且可行动**的话；判别只靠 `code`，文案不泄密 | **接受一个以"已知 credential ID"为键的存在性预言机** | 本 ADR 的结论 |
| C. 在响应里带上更多细节（如"该凭据属于哪个账号"） | 诊断更充分 | 直接把凭据与账号关联起来 —— 泄露远超"存在性" | 否决 |
| D. 改成"已认证才能查" | 无预言机 | 登录**失败**的用户正是未认证的 —— 与需求正交，等于不做 | 否决 |

## 3. 结论

**选了 B。** 服务端抛两个不同的 code（`message` **刻意保持同样笼统的**
`Invalid credentials`，判别**只靠 `code`**）：

- 服务端已不认得这条 credential ID → `code: 'passkey_not_found'`
- 认得凭据但断言没验过 → `code: 'passkey_verification_failed'`

`packages/app-host` 把两者映射成两个不同的 reason，Web 与移动端各用**两句不同的话**渲染。
测试断言两个 code **不同**，且两者都**不是**笼统的 `'Authentication failed'`。

**为什么接受这个预言机**（这是本 ADR 真正要记下来的部分）：

1. **它泄露的是一个非秘密数据的、非可枚举的一位。** credential ID 本身每次登录都明文
   出现在断言响应里；攻击者要先拿到它，才能问出"它还注册着没有"。
   这与"用邮箱查账号是否存在"（可枚举、且邮箱是身份标识）**不是一个量级**。
2. **收益落在最需要它的时刻**：用户正卡在登录失败页面，需要立刻知道"再试一次"还是
   "去重新注册"。把这句判别藏起来，代价由**已经进不来的用户**承担。
3. **后端仍然守住了真正重要的边界**：删除路径上"不是你的"与"不存在"**完全同形**
   （都是 `404` + 同一个码，测试断言两者响应体**逐字节相同**）——
   也就是说，**归属信息**没有被泄露，泄露的只是"这条 id 是否还在系统里"。

`SAFE_ERROR_MESSAGES` **没有**被放宽：这两个 code 是在路由里**显式**处理的，
不是靠给白名单加条目。白名单仍然只含原先那批通用文案。

## 4. 后果

- **不能把这个先例外推。** 本 ADR 为"**未认证**端点是否可以泄露**已知 credential ID** 的
  存在性"背书，**不**为"是否有账号"、"邮箱是否注册过"、"某个 id 属于谁"背书。
  后面这些仍然是必须防的（注册路径的 `excludeCredentials: []`、
  `REGISTRATION_SUCCESS_MESSAGE` 对已存在账号同样返回成功、恢复链接的中性响应，
  都是同一个原则的其它落点）。
- 如果将来 credential ID 变成**可枚举**的（例如改成短 ID、自增、或从邮箱可推导），
  **本 ADR 的结论立即失效**，必须重新评估。这是一个**隐含前提**，不是永久许可。
- 客户端侧的收益必须**真的用上**：两个 code 映射到两个不同的用户可见句子。
  如果哪天有壳把它们合并成同一句话，这个 ADR 的收益就等于零，而预言机的代价照付。

## 5. 未核实项

- **没有做过实际的枚举/探测实验**来量化攻击者能拿到多少。这依赖"credential ID 是
  32 字节随机值且不可枚举"这一**假设**，本 ADR 没有独立验证该假设，只是引用了
  WebAuthn 数据模型与生成代码。
- **没有评估过日志侧的泄露**：这两个 code 会进服务端日志，而日志的访问面没有审计过。
- 真硬件/真系统认证器**没有测过**，全部验证基于虚拟认证器。
