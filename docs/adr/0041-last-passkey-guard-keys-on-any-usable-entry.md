# ADR-0041：最后一条通行密钥的守卫改判"**有没有别的能用的入口**"，不再判"是不是最后一条"

> 状态：**已接受**
> 日期：2026-10-01
> 修订：[ADR-0029](0029-refuse-to-delete-last-passkey.md)（**保留其取舍，换掉它的判据**）
> 前置：[ADR-0039](0039-email-first-auth-and-desktop-reverse-authorization.md)，
> 以及**尚未成文**的 ADR-0040（登录口令与 E2EE 口令解耦；正文在
> [`docs/plans/email-password-auth.md`](../plans/email-password-auth.md) 的 D1，落地计划是 W8）

## 1. 为什么会漂

ADR-0029 选"删到只剩一条时拒绝"，靠的是一条当时的**事实**：

> 通行密钥**可能**是这个账号唯一的登录方式（`User.passwordHash` 可空，
> 魔法链接依赖邮件可达）。

那条事实曾经和"最后一条"等价，所以用"最后一条"当判据没有问题。邮箱 + 口令登录
落地之后两者**不再等价**：一个既可以有口令、又可以有凭据的账号，"最后一条通行密钥"
根本不是唯一入口。继续拒绝的结果是——

**用户在一个普通设置操作里被挡住，而挡他的理由不存在。** 这是判据落后于产品状态的
典型形状：代码里那句注释（"纯通行密钥账号没有别的登录方式"）从陈述事实
变成了只对一部分账号成立的条件。

## 2. 选项

| 选项 | 优点 | 缺点 |
|---|---|---|
| A. 保持"最后一条一律拒绝" | 判据简单、零新增依赖 | 有口令的账号被无谓挡住，用户会以为"删不掉"是 bug；而这条阻碍**没有任何安全收益**（口令就在库里） |
| **B. 改判"账号还有没有能用的入口"**：有可用口令时放行，否则照旧 409 | 挡住的是**真实的**自我锁定，不挡没有风险的删除 | 需要一个"可用口令"的定义，并且服务端与界面那句提示必须同时改（否则提示与判定错位） |
| C. 完全放开（删到零也允许，之后走恢复邮件） | 用户完全自主 | 就是 ADR-0029 否决的 A：恢复通道强度只等于邮箱访问权，且自托管实例未必配 SMTP |

**选了 B。** ADR-0029 的核心取舍（宁可拒绝，也不把"账号可进入性"寄托在用户读到一条
文案上）**一条都没动**；改变的只是它触发与否的条件。

## 3. "能用的口令"这个信号怎么算

这是本 ADR 唯一的实质内容，其余都是实现细节。

```
passwordHash IS NOT NULL  AND  is_verified = 1
```

- **`is_verified` 是承重的，不是装饰。** `loginWithEmailPassword` 在口令**校验通过之后**
  还会因为 `isVerified === 0` 抛 `email_not_verified`——那个顺序是为了不泄露邮箱有没有
  注册过（防枚举）。所以"有 hash 但邮箱没验证"的账号照样进不去。只看 `passwordHash`
  会放行的，正是一个**谁也进不去**的账号，而那恰好是这条规则唯一要防的东西。
- 🔴 **口令被限流（锁 15 分钟）算"能用"。** 限流自己会到期；而"因为一个会过去的计数器
  禁止一次删不掉的凭据"会让界面只能说出"过一会儿再来"，用户在那一刻反而更可能去试
  别的破坏性操作。**判据要建立在稳定事实上，不是建立在瞬时状态上。**
- **不看 E2EE 口令。** 登录凭据和解密数据是两件事（ADR-0040 明确解耦）：删掉一条通行
  密钥不影响任何密文的可解性，所以它不属于这条规则的管辖范围。把 E2EE 状态混进来会
  造出一条"删凭据前要检查加密配置"的伪规则。

## 4. 实现上的两条约束

1. **两条判据必须在同一条 `deleteMany` 的谓词里求值**（`OR: [还有另一条, 有能用的口令]`）。
   先查口令再删的写法在两次调用之间会漏——这正是 ADR-0029 §3 那条 TOCTOU 防护，
   它现在是**两个分支**共用一条语句，不是少了一个。回归钉在
   `server/tests/passkey-management.spec.ts`：那里**重复**断言了完整谓词形状，
   因为桩死的 `count: 0` 让"把守卫整行删掉"这条用例照样绿。
2. **服务端与界面同时改。** 409 只在"两条都不成立"时出现，所以那句提示可以**同时**给
   两条出路（先添加一条新的通行密钥 / 设一个登录口令），不必猜用户手上有什么。
   词条：`common.auth.error.lastPasskey`、`web.passkeys.error.lastPasskey`（中英各一，
   都写上了"邮箱得先验证过"——否则第二条出路对未验证的账号是一句会静默失败的建议，
   那正是 ADR-0029 §4 点名批评过的形状）。

## 5. 已知边界

- "设一个登录口令"这条出路要求**找回密码**那条链可用（`/password/forgot` → `/password/reset`），
  而它同样依赖邮件可达。邮件通道坏掉的自托管实例上，这条建议兑现不了 —— 本 ADR
  **没有**解决它，只是把它和 ADR-0029 §4 那条"有害文案"区分开：至少现在的两条出路里，
  "再添加一条通行密钥"是**当场可完成**的。
- 管理员强制登出 / `tokenVersion` 前进与这条判据无关：它们不影响账号能否被登录进来。
- 如果以后引入"账号被停用"这类状态，`能用的入口` 的定义必须**跟着登录闸门一起改**，
  而不是在这里独立发明一套"什么算可用"。
