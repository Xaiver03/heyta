# ADR-0015：习惯韧性的「冻结余额」保持**纯派生**且**不上界面** —— 冻结参数只能放宽

> 状态：**已接受**
> 日期：2026-09-26
> 取代：无

## 1. 背景与约束

激励体系引入了「冻结」：每连续 **7 个计划日**积攒 **1 个**冻结（上限 **2 个**），
用来吸收一次中断而**不清零**连续；另有「续接」（仅昨天、1 天窗口）与
「重新开始」（≥7 天没记录后保留最长与累计）。设计见
[`docs/plans/motivation-and-progression.md`](../plans/motivation-and-progression.md)。

于是有一个必须回答的问题：**「冻结余额」要不要成为一个持久化字段？**
上一版界面上是把它显示出来的（「还剩 N 个冻结」），所以这个问题当时是真的。

**硬约束**（结论由它们推导，不是偏好）：

| 来源 | 约束 |
|---|---|
| [AGENTS.md §3.3](../../AGENTS.md) | 默认**不** bump `CURRENT_SCHEMA_VERSION`；新增持久化字段必须可选并给 hydration 默认值 |
| [AGENTS.md §1](../../AGENTS.md) | 同步是 **op-log 事件溯源**，**不是 CRDT**；云不是事实源 |
| [AGENTS.md §7](../../AGENTS.md) 第 4、7 条 | **「两套并行定义」**是本仓库反复栽过的形状（词表、时钟语义、同步接线都栽过） |
| 计划 §6 反需求 | 不做金币 / 积分 / 商店；**不「卖后悔」**（Duolingo 的付费冻结与付费修复**明确否决**） |
| 计划 §4 | 显示给用户的连续类数字**只增不减** —— 屏幕上那个不缩水的数字是它的全部意义 |

产品侧还有两条来自产品负责人的约束（这次决策的直接动因）：
**界面要简洁**、**调性要统一**。

## 2. 选项

| 选项 | 优点 | 缺点 | 关键证据 |
|---|---|---|---|
| **A. 存字段 + 界面显示余额** | 数字绝对稳定；能支持"券"的跨会话承诺 | 引入第二份表示（与日志重放必然漂移）；是货币；暗示计划内缺勤 | Duolingo 截图（见 §3）——**库存与购买按钮是同一台机器**，那个价格在公开资料里是 **200 / 425 / 400** 三个数字 |
| **B. 存字段 + 不显示** | 数字稳定 | **为了一个看不见的东西付两份表示 + 一次 schema 风险**；收益为 0 | 无 —— 这是最不该选的一个：成本照付，用户侧毫无差别 |
| **C. 纯派生 + 只显示"它替你保住了什么"** ✅ | 跨设备一致性**免费**；零字段、零 schema；调性统一；用户不会把冻结当额度 | 参数放宽会让历史数字变大；规则变更需要纪律兜住 | 见 §3 的重放论证 |
| **D. 纯派生 + 界面显示余额**（上一版实际形态） | 无需新字段 | 保留了"库存"的全部缺点，却拿不到 A 的唯一好处（稳定性承诺） | 代码注释写着"不是『你还剩几个道具』"，而 JSX 渲染的正是「还剩 N 个冻结」——**注释是对的，代码没照做** |

## 3. 结论

**选 C，并且先做产品决定、再消解工程问题 —— 顺序不能反。**

### 3.1 为什么余额不上界面

1. **它是库存，不是事实。** 「还剩 2 个」等于在说"你还有 2 次可以不来的机会"，
   而冻结是给**意外**的宽容，不是**计划内**的额度。把额度摆上台面，
   等于把保险推销成通行证 —— 与"不制造内疚"直接冲突。
2. **它对用户不可操作。** 不能主动花、不能多挣、不能选时机、不能转让。
   一个做什么都用不上的数字就是纯噪声。
3. **它是整套体系里唯一的货币。** heyta 没有金币、没有宝石、没有商店、没有积分。
   冻结余额是**唯一**一处会让它读起来像资源管理游戏的地方 —— **调性不统一**。
4. **它需要"承诺稳定"**，而那正是它唯一真实的成本（见 §3.3）。

### 3.2 关键推论：产品决定把工程问题消解掉了

> **界面上不出现的东西，不需要稳定的持久化结构。**

余额一旦不可见，"这个数在不同设备 / 不同版本上是否严格一致"就**不再是产品问题**。
所以「派生还是存字段」这个二选一**被消解了**，而不是被绕过或推迟。

这条不是凭直觉。**竞品的一手证据**（[Duolingo 官方 blog，2022-01-31][dl]）里那张截图
同时包含三样东西：`You have 0 of 2 equipped`、两个空的火焰格子、
以及一个 `Refill streak freezes` for **400 gems** 的按钮 ——
**可见的库存和购买按钮是同一台机器**：库存要摆出来，是因为它能卖。
heyta 不卖它（每连续 7 个计划日自动发一个），所以那个计数器**没有任何职能**。

顺带一条佐证：该价格在公开资料中出现过 **200 / 425 / 400** 三个数字
（Wiki 两处 + 官方 blog 截图）—— 价格本身就是被频繁调参的运营变量，
这更说明它属于**卖的那一侧**，不属于"用户的进度"那一侧。

### 3.3 为什么派生是对的那个（不只是"更省事"）

1. **跨设备一致性是免费的。** 余额是日志的重放结果；日志同步了，
   两台设备**必然**算出同一个数。它不需要冲突解决策略，因为它没有**自己的**状态。
2. **存字段等于引入"第二份表示"。** 本项目是 op-log 事件溯源，余额的**权威在日志里**。
   再存一份数字 = 同一个事实有两个来源，它们一定会漂移
   （回放、撤销、跨设备重放都会）。见 §1 的「两套并行定义」约束。
3. **不加字段是有明确依据的默认值。** AGENTS.md §3.3：默认不 bump schema。
4. **这不是新发明，本仓库已有同形状的先例。** [ADR-0014](0014-memory-switch-and-corrections.md)
   已经定过：记忆推断结果**不持久化**（纯函数，每次从 op-log 重算），
   只有用户**纠正**才进 op-log。本 ADR 把这条规则从「推断结果」扩展到**奖励状态**。

### 3.4 配套纪律：**冻结参数只能放宽，不能收紧**

这是 C 的代价，必须用一条规则兜住，而不是靠"以后注意"。

派生式的真实风险是：`FREEZE_EARN_EVERY` / `FREEZE_MAX_HELD` 参与重放，
改参数会让历史被**重新判定**。

- **放宽**（7→5、上限 2→3）：过去的连续天数只会**变大**，
  与"只增不减"同向。用户看到的是"它连那次都替我算上了"，可以接受。
- **收紧**（7→14、上限 2→1）：过去的连续天数会**变小** —— 那正是红线禁止的形状。

**真要收紧时也不加字段**，而是加**代码常量切分点**
（例如 `FREEZE_RULE_V2_FROM = '2026-10-01'`，之前的日期按旧参数重放）：
零存储、可测、可解释。现在就加它是**投机性复杂度** —— 我们可能永远不改这两个数。

## 4. 后果

- **「不发行货币」从一条反需求升级为结构约束。** 以后任何"库存 / 余额 / 券 / 道具"型的
  UI 提案都要先过这一条：**它在替用户表达什么他不能自己决定的事？**
- **收紧冻结参数变成需要走 cutover 的例外流程**，而不是一次普通的调参。
  代码里那两个常量因此不是"随手可改的魔法数字"。
- **`freezesHeld` 仍然是领域层的内部量**（它决定某次中断能否被吸收），
  只是**不承诺跨版本稳定**、也**不上界面**。这不矛盾：它没有消失，只是没有外交职能。
- **已接受的不一致**：规则放宽后，用户可能在历史日期上看到"连续天数变大了"。
  方向只能是变大，且新数字反映的是**当前**规则 —— 这比"数字永不变化"更诚实。
- 因此余额**不能**用于任何"跨会话承诺"（例如"你还有 1 张券，下周再用"）。
  我们不需要这种承诺，因为不发行券。

## 5. 未核实项

- 🔴 **没做过用户测试。** "余额不可见"是否会让一部分用户**不知道冻结机制存在**，
  我们**没有实测**。目前的依赖是：首次真正用到的那一刻在界面上明说
  （「这段连续里有 1 天是冻结保住的」，见 `apps/web/tests/motivation-view.spec.tsx`
  那条带前提断言的守卫）。这是**设计意图，不是已验证的结论**。
- ⚠️ **cutover 常量方案只是设计，未落地代码，也未测过。**
  它是否真能覆盖所有读取路径，没有验证。
- ⚠️ Duolingo 的 **+0.38% DAU** 是**他们**的产品指标，**不能外推到 heyta** ——
  我们不按 DAU 设计（计划 §9.1 用"活跃周数"）。引用它是为了说明
  "库存为什么存在"，不是为了论证留存。
