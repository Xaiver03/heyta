# ADR-0010：AI 配置路由与回退策略

- **状态**：已接受（2026-09-26）
- **相关**：[ADR-0005](0005-ai-data-path.md)（AI 数据路径）、[ADR-0006](0006-supply-modes.md)（两种供给模式）、[`ai-capability-branches.md`](../plans/ai-capability-branches.md)
- **实现**：`packages/ai/src/routing.ts`（41 条测试）、`packages/ai/src/supply.ts`、`packages/ai/src/egress.ts`
- **调研依据**：[`ssos-ai-routing-design-analysis.md`](../research/ssos-ai-routing-design-analysis.md)（SSOS 既有实现分析）、[`e2ee-apps-ai.md`](../research/e2ee-apps-ai.md)（同类产品）

---

## 1. 背景

用户要求 heyta 提供**完整的 AI 配置路由**，并要求参考两个现成来源：

1. 本机 **CC Switch** —— 一个已在运行的 AI 网关，其 `proxy_config` 表里有一套成熟策略
   （自动故障转移、`max_retries=6`、三级超时、熔断阈值、成本上限）。
2. 上级目录的 **SSOS** 项目 —— 一个生产系统，已有 `ai-model-router` /
   `config-resolver` / `routes/admin/ai-config` 一整套实现。

两者都验证了一件事：**"配置路由"是一块真问题**，不是过度设计。
但两者都建立在同一个前提上 —— **服务端可信、且有明文**。
而 heyta 的前提正相反。所以本 ADR 的核心工作不是"把它们的路由抄过来"，
而是**判断哪些能移植、哪些会破坏 heyta 的承诺**。

## 2. 关键事实（从两个来源提炼）

### 2.1 ✅ 值得移植的（来自 SSOS，都有实现证据）

| # | 做法 | 为什么值得 |
|---|---|---|
| 1 | **能力词表 + `requiredCapabilities.every()` 单表达式过滤** | 调用方说"我需要什么能力"，不说"用哪个模型"。换模型不用改调用点 |
| 2 | **显式能力声明优先于推断** | SSOS 有 `config_options.capabilities` 字段；这是对的方向 |
| 3 | **有序回退链 + 语义化优先级**（`1` 主 / `2+` 备 / `NULL` 不在链上） | 顺序是产品语义，不是实现细节 |
| 4 | 🔴 **URL 校验在执行"写入"与"发送"两个点** | 它的原注释说得最好：**"Enforcement has to sit on the path that actually sends the request, not only on the path that stores it."** |
| 5 | **重试分级**：只有 408/429/5xx 可重试；非瞬态错误立刻转移 | 把"重试"和"换一个"分开，避免重放注定失败的请求 |
| 6 | **凭据轮换工程化**：默认 dry-run、具名 key id、确认串、**只报计数**、`WHERE old = old` 并发保护 | 轮换脚本最危险的失败模式是"打印了密钥"和"并发下换了两遍" |
| 7 | **密钥不出接口 + 日志不含凭据 + 诊断信息正则脱敏** | 密钥泄漏的路径比想象的多 |

### 2.2 🔴 不能移植的（同样有实现证据）

| # | 做法 | 为什么不能 |
|---|---|---|
| 1 | 🔴 **服务端代收发 + 服务端持解密后的 provider key** | SSOS 的 `ai-adapter` 要求服务端持有**明文消息**与**解密后的密钥**（其 `assertAIInputSafe` / 上下文窗口估算 / 响应缓存都建立在这之上）。heyta 是 E2EE，服务端**看不到明文也不能有密钥**。这不是"实现差异"，是**信任模型相反** |
| 2 | **按模型名子串重排路由**（`includes('GLM')` / `includes('opus')` / `includes('deepseek-r1')`） | **随模型改名即静默失效**，且失效时行为"看起来合理" |
| 3 | **按 provider 名猜能力**（`VISION_PROVIDERS` 集合） | 同上 —— 猜测的错误是静默的 |
| 4 | **明文凭据兼容直通**（`decryptApiKey` 遇到非加密值原样返回） | heyta **不应存在任何明文凭据路径**，哪怕"为了兼容" |
| 5 | **密文前缀当掩码**（`LEFT(api_key_encrypted, 8) \|\| '****'`） | 截的是密文头：既泄露了密文信息，又**没有任何安全意义**，还容易被误读成"密钥前 8 位" |
| 6 | **迁移文件里硬编码密文凭据** | 迁移会进版本库、进 pg_dump、进只读副本 |
| 7 | **流式与非流式回退策略不对称** | 同一件事两套语义，必然漂移 |
| 8 | **写死司法辖区的 host allowlist** | 对多地区产品是错的 |

### 2.3 🔴 与 SSOS **反向**的一条：localhost

SSOS 的 `isAllowedAIBaseUrl` **拒绝 localhost 与私有 IP 段**。
对它是正确的 —— 它是服务端产品，那条规则防的是 **SSRF**
（诱导服务器去访问内网）。

**但对 heyta 必须反过来：`http://localhost:11434/v1` 是我们最想支持的端点。**
（Ollama。明文**根本没出设备**。）
照抄 SSOS 会把最主要的使用场景拒掉。

→ 所以 heyta 的规则**按目的地分岔**，见 §3.5。

## 3. 决策

### 3.1 三道闸，缺一不可

| 顺序 | 闸 | 关掉时 | 粒度 |
|---|---|---|---|
| 1 | `enabled` 总开关 | 整个 AI 关闭 | 全局 |
| 2 | `allowRemote` 允许远程 | **远端端点不进入候选** | 粗粒度、一次设定 |
| 3 | 出境授权 `(功能, 目的地)` | 该功能该目的地不可发 | 细粒度、按功能、可撤销 |

**第 2 与第 3 道不是重复**，合并会丢掉语义：

- 第 2 道回答"**我根本不想用云**" —— 这类用户**不该被反复弹窗问"要不要授权云"**。
  所以远端端点在候选解析阶段就被**剔除**，不产生授权询问。
- 第 3 道回答"**这个功能可以发，那个不行**" —— 即使允许了远程，
  也要逐功能确认。

> 第 2 道照抄 Joplin 的 `Allow remote AI providers`（默认关）。
> 见 [ADR-0006](0006-supply-modes.md) §2.4 与 [`e2ee-apps-ai.md`](../research/e2ee-apps-ai.md)。

### 3.2 目的地由**端点**推导，不由模式声明

沿用 [ADR-0006](0006-supply-modes.md) 的 `classifyDestination`：
目的地是**算出来的**，不是配置里写的。

→ 于是"用户自备 + `localhost`"自动得到 `none`（明文没出设备、不需要授权），
而"用户自备 + 公网"得到 `user-endpoint`（需要授权）。
**把"自备"当成一个整体会丢掉这个最重要的区别。**

### 3.3 🔴🔴 回退不得跨越隐私边界（本 ADR 的核心）

**通用 AI 网关遇到失败就换下一个端点 —— 这没错，因为对它来说端点只是供应商。
但对 heyta，端点还带着隐私等级。**

所以：

> **候选链是 `[本机 Ollama, 云端]`，本机挂了 —— 不许悄悄发给云端。**

这不是"高可用"，这是**在用户没同意的情况下把数据送出去**。
通用网关做这件事是对的，因为它没有"本机"这个概念；**heyta 有**。

**实现**：每个候选**各自**过一次出境闸门（因为目的地可能不同）。
非首选候选未获授权时：

- **不发请求**（有测试数请求数，不是看返回值）
- 返回**独立的失败原因** `fallback-needs-consent`
- 且这个原因**不计入端点健康**（端点本身是好的，被拦的是回退）

**已用注入验证**：把闸门改成"仅首选检查"后，测试变红
（`expected true to be false` —— 云端那个请求真的发出去并成功了）。

### 3.4 能力必须显式声明，**不做任何推断**

- `AiCapability = 'structured_output' | 'vision' | 'long_context' | 'tool_calling'`
- 端点用 `capabilities?` 声明。🔴 **`undefined` = 只有基线（`structured_output`）**，
  不是"支持一切"。`vision` / `tool_calling` / `long_context` **必须写出来**。
- 过滤方式是 `required.every(cap => declared.includes(cap))`（单表达式，移植自 SSOS）。
- 各功能的必需能力写在 `DEFAULT_FEATURE_CAPABILITIES`。
  例：`breakdown` 需要 `long_context`（要读整条任务的备注）。

#### 3.4.1 🔴 这条决策有一个**配套义务**：界面必须能声明能力

本节结论**不变**（能力仍然必须显式声明、不做推断）。但要记下一个实测教训：

> 第一版设置面板**没有任何声明能力的地方**。于是通过界面加进来的每一个端点
> 都只有基线能力 `structured_output`，而 `breakdown` 需要 `long_context`
> —— **拆解功能永远没有路可走**，失败信息还只说「没有可用端点」。

这个洞在**给 `invokeRouted()` 接第一个真实调用点时**才暴露：
`packages/ai` 单测里手写的端点都带了能力声明，所以一直是绿的；
`packages/app-host/tests/ai-breakdown.spec.ts` 第一版夹具也照抄了带能力的端点，
直到把夹具改成"像用户那样只填地址和模型"，它立刻红了。

**规则：一个"必须由用户声明"的字段，如果界面上无处可填，等于这个功能不存在。**
现在设置面板每个端点都有四项能力勾选，并且有 6 条 UI 测试钉住
（其中"勾选后真的进了配置"这条防的是"界面能勾、实际没用"）。

→ **"没配" = 保守失败，而不是"没配" = 放开。**
且因为不按名字猜，**模型改名不会让路由静默失效**。

### 3.5 URL 校验：双点执行，规则按目的地分岔

**执行点**：`resolveRoute`（解析候选时）+ `attemptOnce`（**真正要发的那一刻**）。
第二次是**纵深防御**，不是重复代码 —— 配置可能来自导入 / 同步 / 迁移 / 手改文件，
任何一条都可能绕过保存时校验。删掉第二次，校验就退化成"只防君子"。
（这一条直接移植自 SSOS §2.1 #4。）

**规则**：

| 端点 | 明文 HTTP | HTTPS |
|---|---|---|
| 回环（本机） | ✅ **允许** | ✅ |
| 远端 | ❌ **拒绝** | ✅ |

拒绝远端明文 HTTP 不是洁癖：**同步通道是端到端加密的，
在 AI 这条路上退化成明文 HTTP 会让整个产品的隐私承诺自相矛盾。**

**另拒**：URL 里带 userinfo（`https://user:pass@host/`）——
它会把密钥写进配置、日志，以及任何打印这个 URL 的地方。

### 3.6 密钥只走 `SecretStore` 端口

配置里**只有 `keyRef`，没有密钥**。这是刻意的：
**配置文件会被同步、导出、贴进 issue，钥匙串里的不会。**
（对照 Obsidian Copilot："Keys are stored in this device's Obsidian Keychain,
not in the vault's `data.json`"。）

Web 端**没有钥匙串** → 只能实现成会话级内存，并在 UI 上**明说"关掉页面就没了"**。
这是 ADR-0005 §3.2.2 的结论（Web 上的 BYOK 架构上就不牢），
本 ADR 不替它遮掩。

### 3.7 熔断：**只有端点的锅才算**

| 结果 | 计入失败 | 理由 |
|---|---|---|
| `network` / `http-error` / `empty-response` | ✅ | 端点确实没给出可用结果 |
| `egress-not-authorized` | ❌ | 是**我们没获授权**，与端点无关 |
| `fallback-needs-consent` | ❌ | 同上 —— 而且它是"回退被隐私拦住"，端点本身是好的 |
| `not-configured` / `no-route` | ❌ | 配置问题 |

> 🔴 这张表必须写死。**把自己的错误记到端点头上**会造成最难查的一类 bug：
> 好好的端点被跳闸，而用户看到的是"AI 时好时坏"。

**"要不要记一笔"与"要不要换下一个"是两个问题**，对应两个函数
（`countsAsEndpointFailure` / `shouldTryNextEndpoint`），**不要合并**：

- `http-error 401`（凭据错）→ **要换**（别的端点凭据可能是对的），
  **也是端点的锅**（这个端点的凭据确实错了）。
- `http-error 400`（请求格式错）→ **不换**：我们发的东西就是错的，
  换谁都会 400，只会把同一个错误重放一遍、让排查更难。

**默认策略刻意保守**：`maxAttempts: 2`、`timeoutMs: 30_000`、熔断阈值 3、冷却 60s。

> 对照真实网关的取值（CC Switch 的 `proxy_config`：`max_retries=6`、
> `non_streaming_timeout=600s`、冷却 60–90s；SSOS：`MAX_ATTEMPTS=3`、超时 90s 默认/夹在 5–120s）：
> **那些是给无人值守的长任务用的。搬过来会让用户在一个输入框前站 10 分钟。**
> 这是任务管理，不是批处理。

### 3.6 密钥存储：端口在 `packages/ai`，实现在壳

`SecretStore` 端口只有一个 `get(keyRef)`。**写入不是端口的一部分** ——
因为"密钥存哪"是平台差异，而"取一个密钥来发请求"是每个平台都一样的事。

| 平台 | 实现 | 位置 |
|---|---|---|
| Web | **会话内存**（关掉标签页就没了） | `apps/web/src/features/settings/aiStore.ts` |
| macOS | **系统钥匙串**（`/usr/bin/security`） | `apps/node-host/src/keychain-secret-store.ts` |
| Windows / Linux | 🔴 **未实现** | —— |

#### 3.6.1 🔴 密钥绝不走 argv

`security add-generic-password -w <secret>` 会把密钥放进**进程命令行**，
一次 `ps` 就能看到。所以实现统一走 `security -i`（从 **stdin** 读命令）。

三个实测结论（在真实临时钥匙串上验证，不是推测）：

| 试过的写法 | 结果 |
|---|---|
| `-w` 不带值，密码走 stdin | ❌ **退出码 0 但什么都没写** —— 典型的静默失效 |
| 单引号 + `'\''`（shell 惯用转义） | ❌ `security -i` 的解析器不认，值被吞掉 |
| **双引号，`\` 与 `"` 各加一个反斜杠** | ✅ 空格 / 单引号 / 反斜杠 / 双引号 / `$;|&` 全部原样往返 |

`-X`（十六进制密码数据）看起来能免掉转义，但**读回来时 `-w` 对非文本数据返回的是十六进制**
—— 与"密钥本身就是十六进制串"无法区分。所以没采用。

⚠️ `-i` 逐行读命令，所以含换行的密钥**被明确拒绝**（而不是被悄悄截断）。
一个被截断的密钥会在很久以后表现为"认证失败"，那时没人会想到是写入时丢的。

#### 3.6.2 ⚠️ 一次真实事故：注入验证**写坏了开发者的登录钥匙串**

记下来，因为教训不是"代码写错了"。

关闭控制字符检查做注入验证时，含换行的密钥走进了 `security -i`。
`-i` 逐行读命令，那一行在换行处断了，**尾部的临时钥匙串参数被切到下一行**
—— 命令于是落到了**默认（登录）钥匙串**，留下一条垃圾记录（已删除）。

根因是：**测试的安全性依赖被测代码正确。** 那是错的 ——
测试必须在代码坏掉时也伤不到开发者的机器。

修法是测试里包一层护栏：任何一次 `security` 调用，如果在**将被执行的那一行**里
找不到临时钥匙串路径，就当场抛错、根本不执行。

⚠️ 护栏的第一版**自己也有 bug**：它检查整个 stdin 字符串，
而钥匙串路径确实在字符串里 —— 只是不在**第一行**。所以它没拦住。
改成只看首行之后，重放同一个注入：**测试照样红，钥匙串干净**。

> 这与之前"假注入"是同一类错误的第三次出现：
> **验证手段本身也要被验证。**

#### 3.6.3 降级的两只手都是张开的

- 钥匙串锁着 / 用户点了拒绝 → `get` 退化成 `undefined`（= 没有密钥），**不抛错**。
  一个锁着的钥匙串不该让整个应用崩掉；AI 功能灰着是可接受的状态。
- Windows / Linux → `isKeychainAvailable` 返回 false，`get` 返回 `undefined`、
  `set` **明确抛错**。不假装在没实现的平台上能用。

### 3.8 熔断状态落盘：为什么在 `packages/ai`，以及为什么必须**封顶**

`invokeRouted()` 每次都算出新的 `HealthMap`，但它只活在内存里 ——
进程一重启，"这个端点连着失败三次、已经跳闸"就忘了，下次启动**立刻再撞一次**。

落到哪个键、哪个文件是平台差异（留在壳里）；但"跳闸的端点重启后还算不算跳闸"
是业务判断 —— 所以序列化逻辑在 `packages/ai/src/health-store.ts`。

#### 3.8.1 🔴🔴 读回来的东西不可信，且必须封顶

落盘数据可能被手改、被旧版本写坏、被同步工具弄乱。而它的作用恰恰是
**阻止请求发出去** —— 所以一条坏记录可能让 AI **永久不可用**。

三道防线：
1. 形状不对的条目**丢掉**，不抛错
2. `circuitOpenUntil` **夹到 `now + 30 分钟`**
3. 已过期的跳闸**立刻清掉**

第 2 条最关键。假设 `circuitOpenUntil` 被写成 `now + 10 年`
（时钟跳变、手改、旧 bug），没有封顶的话用户会遇到一个**再也修不好**的状态：
改配置没用、重启没用，只能去删存储。**一个跳闸最多只能持续 30 分钟。**

#### 3.8.2 🔴 失败分支最需要 `health`，而它曾经没有

`BreakdownOutcome` 早先的形状是：成功分支的 `proposal` 里带 `health`，
**失败分支完全不带**。

这恰好把最该记的那次丢了 —— 端点失败才会让熔断计数器 +1。
而且位置不对称：`outcome.health` **不是一个合法访问**
（成功分支上它在 `proposal` 里，失败分支上根本没有）。

现在两个分支都在**顶层**带 `health`，形状一致。
它说的是"这次路由尝试"，不是"这份提议"。

> ⚠️ 这个 bug 是被 `tsc` 逼出来的：web 接线时 `outcome.health` 报
> `Property 'health' does not exist`。我一开始怀疑是构建缓存，
> 清了三轮缓存都没用 —— 最后用 `Extract<BreakdownOutcome, {ok:true}>['health']`
> 一行诊断才定位到是**类型形状本身**的问题。
> **怀疑缓存之前，先怀疑自己的类型。**

### 3.9 「不做推断」的配套义务：把差额说出来并给一键修复

§3.4 定了能力**必须用户显式声明**（不猜）—— 那是对的，推断会静默给错答案。
但它有一个代价，本轮才补上：

> 用户加了端点、配了路由，**只是忘了勾「长上下文」**，
> 「AI 拆解」就**永远不工作**，而界面一个字都不说。
> 用户只会觉得"AI 坏了"。

「不做推断」**不等于**「不告诉用户该怎么办」。

所以设置面板现在会：
1. 对每个功能算出**当前路由里缺哪些能力**（`capabilityGaps()`，纯函数）
2. 若**没有任何一个**候选端点能满足 → 明确写出缺什么 + 哪个端点缺 + 一个「补上」按钮
3. 「补上」是**并集**，不顶掉用户已经声明过的能力

⚠️ 第 2 条里的"没有任何一个"是关键。只要链路上有一个端点能满足，
就不该报缺口 —— 否则用户会被一个**跑得起来的功能**报错，那比不报还糟。

### 3.10 🔴 用户看到的失败原因，只能有一个来源

`packages/ai` 的 `explainNoCandidate()` 已经能**具体**说明"为什么没有候选端点"：
全部是远端但没允许远程 / 熔断冷却中 / 地址被拒 / **缺能力声明** / 端点不存在。

但 `packages/app-host` 早先把它**丢掉了**：

```ts
message: describeRoutedFailure(result.reason),   // ← result.message 里有具体原因，被扔了
```

于是最常见的那种情况 —— **用户忘了声明能力** —— 被显示成
「没有可用端点能处理这个功能。检查端点是否启用、地址是否合法。」

**而这两件事用户都没做错。** 那句话会把人引去查两个根本没问题的地方。

修法：优先用 `result.message`，`describeRoutedFailure()` 降级为**兜底**
（只在 `packages/ai` 没给句子时使用）。

#### 3.10.1 为什么这是一条**结构性**规则，而不是一次修 bug

同一句用户可见的文案有**两个来源**，就一定会漂移。而漂移的失败文案比没有文案更坏 ——
它会把人引向错误的方向。这与本仓库把 design tokens 收敛到唯一事实源是同一条道理。

所以 `describeRoutedFailure()` 现在带着一条明确约束：
**不要在那里重新概括已经由 `packages/ai` 说明的原因。**
将来新增失败原因时，先在那边的 `explainNoCandidate()` 加说明，
而不是在壳里补一行 `case`。

### 3.11 🔴🔴 「数据出不出设备」只能有一个判据 —— 附一次真实的隐私 bug

§3.10.1 记了"同一句文案有两个来源必然漂移"。**同一轮里就撞到了它的第二例**，
而且这次是隐私事故。

`apps/web` 里判断"这个端点是不是本机"用的是**自己写的一个正则**：

```ts
// 注释还写着"与 classifyDestination 同一条判据"
isLocal: /^https?:\/\/(localhost|127\.0\.0\.1|\[::1\])(:|\/|$)/.test(endpoint.endpoint)
```

而 `packages/ai` 的 `isLoopbackEndpoint()` 是**另一套**实现（用 `new URL().hostname`）。
实测两处分歧：

| 端点 | 手写正则 | 真判据 | 后果 |
|---|---|---|---|
| `http://127.0.0.1:80@evil.com/v1` | **本机** | 远端（host 是 `evil.com`，`127.0.0.1` 只是 userinfo） | 错误披露（详见下方更正） |
| `http://LOCALHOST:11434/v1` | 远端 | 本机（大小写不敏感） | 虚假警告 |
| `http://127.0.0.2:11434/v1` | 远端 | 本机（127/8 整段回环） | 虚假警告 |

#### 3.11.0 ⚠️ **更正：这里原先写的是"数据发给了 evil.com"，那句话是错的**

第一版我写成"🔴 不显示 E2EE 警告，数据发给了 evil.com"。
**下一轮实测推翻了这个说法**，特此更正：

```
http://127.0.0.1:80@evil.com/v1   → isLoopbackEndpoint = false（对）
                                  → validateEndpointUrl = **拒绝**（地址带了 userinfo）
https://127.0.0.1:80@evil.com/v1  → 同样被 validateEndpointUrl **拒绝**
```

`validateEndpointUrl()`（§3.5）本来就拒绝带用户名密码的地址。
所以这条 URL 在 `resolveRoute` 阶段就被排除了，`invokeRouted` 拿不到候选，
**一个字节都不会发出去**。

**真实性质是"披露不准"，不是"数据泄漏"** —— 二者严重程度差一个量级：

- 用户看到"数据不出设备"，按了发送
- 发送失败（地址被拒），界面上会报错
- 数据**没有**离开设备

这不改变结论（披露必须准确，而且错的方向必须偏保守），但它改变了**定级**。
把它写成"数据泄漏"会让人以为防线被击穿了，而实际上这里有两道独立防线，
第二道挡住了 —— 这恰恰说明 §3.5 的双点校验是有价值的。

> ⚠️ 我为什么第一版会写错：我看到"正则说本机、真判据说远端"就**直接推断**
> 数据会发出去，**没有去跑一遍发送路径**。推断和实测的差别就是这里。

#### 3.11.0b 同一轮里发现的**第二个**同形状实例（更严重，且是实测的）

修完回环判据之后，同一份文件里还有一处**平行实现**：
`resolvePreferredTarget()` 自己遍历路由链，只跳过 `undefined` / `disabled`，
而 `resolveRoute()` 还会按**能力、熔断、远端开关、URL 合法性**过滤。

实测（`路由 [A(缺 long_context), B(齐全)]`）：

```
披露说将发往： 供应商 A  https://a.example.com/v1
实际请求打到： https://b.example.com/v1/chat/completions
结果 ok = true
```

**用户同意了 A，数据发给了 B（另一家公司）。而因为最终成功了，
界面上没有任何提示。**

这一次是**真的发出去了**，而且是实测确认的（不是推断）。

两处修法：改用 `resolveRoute()`；并把**整条回退链**写进披露 ——
因为回退是真实行为，只披露首选必然不够。

#### 3.11.1 为什么这条线**本来就不该在 `apps/`**

按 ADR-0003 的判据："这一行在决定**业务上该怎么做**吗？"

「这个端点算不算本机」决定**要不要给用户看 E2EE 警告** —— 是产品语义。
所以它属于 `packages/`，`apps/*` 只该调它。

#### 3.11.2 于是加了一条门禁，而不是只修这一处

`check:layering` 新增第 8 条规则 `no-loopback-classification-in-apps`。

⚠️ 规则的难点是**只抓判断、不抓绑定**：
`server.listen(port, '127.0.0.1')` 是**我们自己**在监听，是反过来的事，
属于外壳职责。所以只匹配两种形状：正则字面量里出现回环主机名、
以及拿回环主机名做 `===` / `!==` 比较。

三个方向都实测过：
- 把真实 bug 写回去 → **门禁红，退出码 1**
- 换成 `hostname === 'localhost'` 的写法 → **门禁红，退出码 1**
- 保持 `listen(port, '127.0.0.1')` 不动 → **门禁绿，退出码 0**（不误伤）

> 只修这一处是治标的：修完 bug，下一个人照样会再写一个正则。
> 门禁才是把"这件事只有一个实现"变成**可执行的**约束。

### 3.12 只落盘不读回来 = 白做（熔断状态的闭环）

第 7 轮做了熔断状态落盘（`health-store.ts`），Web 侧也在 `onHealth` 里
写进了 `aiStore`。**但没有任何地方读回来。**

后果：`invokeRouted` 每次都从 `EMPTY_HEALTH` 开始 ——
"这个端点连着失败三次、已经跳闸"这件事**活不过一次页面刷新**，
用户每次打开都要再撞一次同一个坏端点。

> 这就是"能建不能用"：功能齐全、测试全绿、落盘逻辑有 35 条测试，
> 而**它是死代码**。落盘测试测的是"存进去能取出来"，
> 从来没有测"取出来的东西被用上了"。

修法：`AiBreakdown` 新增 `healthSnapshot` prop，在**发送那一刻**
调 `fromHealthSnapshot()` 解析后作为 `healthSeed` 传入。

⚠️ 解析放在发送时而不是渲染时 —— 冷却期要对**现在**算。
提前解析会让"跳闸 60 秒后自愈"在页面开着的过程中被冻结。

#### 3.12.1 顺带确认：回退链披露是**承重的**

披露（`resolvePreferredTarget`）用的是**不含熔断状态**的静态推导，
所以跳闸的 A **仍会出现在首选位置**，而实际请求会打到 B。

这在加了 §3.11.0b 的回退链披露之后是**安全**的 ——
因为用户按发送之前已经看到过 B 的名字。

**但这也说明那条披露不是"礼貌"，是必需的**：
没有它，熔断导致的回退就是一个**未披露的目的地变更**。
已用测试把这一点钉住（断言回退链里出现 B，且请求确实打到 B）。

### 3.13 「测试全绿」和「用户受益」是两件事（第二例）

§3.12 修的是"落盘没人读"。同一类问题还有一例：
`describeEndpointHealth()` 的文档写着「**给界面用**」，
而**没有任何界面调它** —— 设置面板里连 `health` 这个词都没有。

后果：一个已经跳闸、正在冷却的端点，在设置里和正常端点**长得一模一样**。
用户只看到"AI 暂时不可用"，不知道是**哪个**端点、也不知道**多久**恢复。

修法：设置面板的端点条目上显示 `describeEndpointHealth()` 的结果
（"暂时停止使用（连续失败 3 次，47 秒后重试）"）。

⚠️ 两个不能做错的细节：
- **过期的跳闸不该继续显示** —— 否则用户以为还坏着，而实际早已可重试
- **坏快照不该让面板崩掉** —— `fromHealthSnapshot()` 不抛错，这里也不该

> 这两轮的共同形状：**能力写好了、测试写好了、文档写好了，
> 但没有任何用户能碰到它。**
> 判断方法很简单：**去数一数这个函数被谁调用**。
> 「给界面用」这句注释本身不是证据 —— 调用点才是。

### 3.14 披露是**三维**，而界面只显示了二维

计划 §5 的验收判据 ④ 写的是「发送前显示"发给哪个端点 + 发哪几个字段"」——
**两条**。但 `buildDisclosure()` 的注释写着它产出的是
「展示给用户的完整披露」，字段有三块：`destinationText`（发给谁）、
`fields`（发什么）、`retentionText`（**留多久**）。

而 `buildDisclosure()` 自己的文档也写着：

> 纯函数，**测试与 UI 共用同一条路径**。

**UI 没有用它。** `AiBreakdown` 手写了一套披露 JSX，
于是「留多久」这一维**从头到尾没有出现在界面上** ——
`describeRetention()` 有现成的、写好的人话，一直没人渲染。

两句话都因此变得很值钱：

| 目的地 | 原本应当显示的文案 |
|---|---|
| 本机 | 未离开设备，不涉及服务端保留。 |
| 自备端点 | **保留策略由你自己的端点决定，heyta 无从知晓。** |

第二句尤其不能省 —— 它是 heyta 在**明确不背书**。
少了它，用户会默认"heyta 管着这些数据"，而事实上 heyta 根本不知道
那个端点会把内容留多久。

修法：UI 改调 `buildDisclosure()`，并在测试里**逐字比对**
界面文案与 `buildDisclosure()` 的输出 —— 这样界面不可能再自己漂移一份。

⚠️ `retentionText === undefined`（= 托管 AI，策略未定案）时界面显示
"未定案 —— 在 heyta 说明清楚之前，这个端点不允许启用"。
这条分支**目前不可达**（`managed` 被 `assertEnableable` 挡着），
是纯防御性的，我不假装它有测试覆盖。

## 4. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 直接调用厂商 SDK | 会把 provider 选择与凭据位置硬编码，而那两样**必须能由用户切换**。已由 `check-layering` 的 `no-vendor-ai-sdk-in-apps` 钉住 |
| 复用 CC Switch / LiteLLM 作为**唯一**路由 | 它们不在用户设备上（CC Switch 的代理虽然监听 `127.0.0.1`，但它是可选的外部依赖）。heyta 的主路径不能依赖用户先装另一个软件 —— **但 heyta 应该支持把端点指向它**（那时它算 `none` 目的地） |
| 按模型名猜能力/分层 | 静默失效（§2.2 #2/#3） |
| 用 `security -w <secret>` 传密钥 | 密钥进 argv，`ps` 可见（§3.6.1） |
| 用 `-X` 十六进制绕开转义 | 读回来也是十六进制，与"密钥本身是十六进制"无法区分 |
| 在没实现的平台上"尽力试试" | 会静默丢密钥；宁可明确不可用 |
| 失败就无脑换端点 | 🔴 会跨越隐私边界（§3.3） |
| 把 `allowRemote` 与出境授权合并成一道 | 会让"不想用云"的用户被反复弹窗（§3.1） |
| 在配置里存明文 API key | 配置会被同步/导出（§3.6） |
| 只在保存时校验端点 URL | 配置可能绕过保存路径（§3.5） |

## 5. 后果

### 正面

- **两种供给模式共用一条代码路径** —— 差别只在 `baseUrl` 与由此推导的目的地。
  这消除了"两套实现漂移"这个在本仓库已发生过两次的失效模式。
- **回退是安全的**：可以在链路里放本机端点做首选、云端做备用，
  而**数据不会在未授权时流出去**。
- **换模型不改调用点**：调用方说的是能力，不是模型名。
- 密钥**类型上**进不了配置文件（只有 `keyRef`）。

### 负面 / 需要接受的成本

- 🔴 **默认保守意味着"用户不配置就没有 AI"** —— 这是 ADR-0005 已记录的最大产品代价。
  缓解：AI-5（本地 API / MCP）让 AI 入口**零配置就有**。
- **配置面比其他产品复杂**（端点 / 能力 / 路由 / 两道开关 / 逐功能授权）。
  缓解：必须提供"一键本机 Ollama"之类的预设，而不是让用户从空表单开始。
- 熔断状态需要**持久化**才有意义（否则重启即忘），
  而它**不能进 op-log**（是本机偏好，不是业务数据）—— 见 §6。
- `maxAttempts: 2` 比通用网关激进，**长任务场景可能需要调高**。

### 需要靠测试/门禁兜住的

- ✅ 已有 41 条测试。其中**三条是承重的**，删除它们等于删掉本 ADR：
  1. 回退跨隐私边界 → 不发请求（**已注入验证能失败**）
  2. `allowRemote: false` 时远端不进候选、不被问授权
  3. 未声明能力 = 保守（`vision` 不会被误认为可用）
- ✅ `check-layering` 已拦 `apps/*` 直接写模型端点或引厂商 SDK（6 条规则）。
- ⏳ **尚未落地**：`packages/ai` 目前**零消费者**，
  所以测试证明的是"闸门自洽"，**还没证明"没人绕过它"** ——
  后者要等真的有调用点之后靠门禁兜。

## 6. 未决事项

1. 🔴 **熔断状态存哪**：本机偏好，**不进 op-log**。
   但要跨会话有效就得落盘。倾向：与"AI 设置"同一个本地存储，
   **绝不参与同步**。
2. **"AI 开关是否多端同步"** —— ADR-0006 §5.5 的同一问题，仍未定。
3. **预设从哪来**：一键 Ollama / 一键 DeepSeek 之类的预设需要维护一份端点清单，
   而清单会过期。倾向：只内置"本机 Ollama"（它不需要任何外部信息），
   其余让用户自填。
4. **成本上限**：CC Switch 有 `limit_daily_usd` / `cost_multiplier`，SSOS 有 `rate_limit_rpm`
   （但 SSOS 那一列**未见执行逻辑**）。heyta 目前**不做成本控制** ——
   端点由用户自付，heyta 中间不记账。若将来做托管 AI，必须补。
5. ⚠️ **能力声明的默认值可能需要调整**：现在 `undefined` = 只有 `structured_output`。
   若真实使用中"忘了声明 long_context"变成常见支持问题，需要改默认或加校验提示。
6. ⚠️ **SSOS 分析报告有几处未确认**（其末节已如实登记），
   本 ADR **未依赖**那些未确认项 —— §2 引用的都是它读到源码并有 `file:line` 的结论。
