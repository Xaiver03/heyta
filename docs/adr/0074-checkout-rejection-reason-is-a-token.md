# ADR-0074：收银台拒单的 `reason` 是**机器码**，散文只进日志；「这台实例能卖什么」要有只读自查

- **状态**：已接受（2026-10-24）
- **日期**：2026-10-24
- **相关**：[ADR-0017](0017-single-paid-tier-and-payment-channel.md)（单一付费档与统一支付中心）、
  [ADR-0054](0054-managed-ai-retention-and-selling-preconditions.md)（托管 AI 的可售前置；§10 的两道闸）、
  [`subscription-handoff.md`](../plans/subscription-handoff.md) §10.2（两枚开关的现状与现量命令）
- **触发**：产品负责人 2026-10-24 在「托管同步续费」按下 ¥12，屏上是「这一档现在还不能卖」，
  随后问："**现在不应该接了中央支付吗？**"

---

## 一、要解决的问题

收款**早就**统一走支付中心了（`server/src/billing/paycenter.adapter.ts`；微信直连已退场，
`registry.ts` 里那条注册被删掉，`config.ts` 对 `WECHAT_PAY_ENABLED=true` 直接启动期硬错误）。
挡住那一单的是**另一道闸**：`checkout.routes.ts` 的 ②′ —— 这一档授予 `ai`，
而这台实例没配托管 AI 上游（`MANAGED_AI_ENABLED` + 三项 `MANAGED_AI_UPSTREAM_*`）。

两个缺陷让这件事对用户完全不可见：

1. **一条 409 说两件事**。`PRICE_NOT_SELLABLE` 同时盖着「这一档要交付的能力本机没有」
   （换一档就能买）与「这一档全局还没开卖」（换也没用）。服务端本来给了 `reason`
   区分它们 —— 但那个字段里装的是**一句中文散文**，客户端只能二选一：
   原样印（英文界面漏中文，`CouponRejectionExplanation` 那一课）或不读（**今天的形状**：丢掉，
   于是屏幕上只剩一句含糊的"这一档现在还不能卖"）。
2. **没有任何一处能一眼看出"这台实例能卖什么"**。开关在 `config.ts`、注册在 `registry.ts`、
   闸门在 `checkout.routes.ts`、用户在屏幕上只看到一个 409。要买的人和要卖的人各自猜。

## 二、选项

| 选项 | 否决理由 |
|---|---|
| A. 客户端把 `reason` 原样显示 | 它就是中文散文。英文界面会漏中文，而且散文一改，界面跟着变 —— 等于让服务端决定文案 |
| B. 客户端按 `reason` 的**内容**猜（`includes('MANAGED_AI')`） | 字符串嗅探；文案一改就静默失配，而失配的症状是"界面不再解释原因" |
| C. 新增 `GET /api/billing/skus` 让客户端提前知道每档可售 | 方向对，但那是**新端点 + 新契约 + 新 ADR**，而且"可售"是**这一刻**的实例状态（两条独立开关都能在重启后变），提前读到的答案会在一次重启后过期。本轮不做，登记为后续（见 §五） |
| **D. `reason` 改成**稳定机器码**；散文只进日志；另加一条只读自查命令**（选定） | 代价：`reason` 的取值从"人话"变成"码"，读日志的人少了一句解释 —— 用日志的 `detail` 字段补上 |

## 三、结论

### 三.1 线协议：`reason` 只许是机器码

`server/src/billing/checkout.routes.ts` 导出 `CHECKOUT_REJECTION_REASON`：

| 码 | 谁拒的 | 用户该做什么 |
|---|---|---|
| `MANAGED_AI_NOT_CONFIGURED` | ②′：这一档授予 `ai`，本实例没配托管上游 | **换一档**（不含云端 AI 的那一档照卖 —— 服务端有对照判据） |
| `TIER_LOSES_GRANTS` | ④′：这一单会把已付费那一行的能力判小 | 别买这一档（等它到期或继续按原档续费） |

- 给运营者的散文进 `Logger.warn` 的 `detail`，**不进响应体**（`MANAGED_AI_NOT_DELIVERABLE_DETAIL`
  / `TIER_LOSSES_GRANTS_DETAIL`）。
- 客户端（`packages/app-host/src/checkout.ts`）**只认词表内的码**，词表外一律丢弃
  （包括"这枚字段上曾经放过一句中文散文"那种旧形状）—— 把陌生串当语义用就是替服务端编造意思。
- 界面按 `(code, reason)` 取自己的词条：web 多给一条**出口**（一键换成能买的那一档），
  移动端这一屏只给文案（档位选择器还没做 —— 不假装两端一样）。

### 三.2 运维侧：`pnpm doctor:billing`（只读）

`server/scripts/billing-doctor.ts`：不发请求、不碰数据库，只做三件客观的事 ——

1. 打印**解析之后**的配置事实（`config.paycenter` / `config.managedAi` 在不在），而不是猜 `process.env`；
2. 打印**真的注册成功**的收款通道（走生产同一个构造函数 `createBillingAdaptersFromConfig`）；
3. 逐 SKU 打印它授予什么、按闸门顺序会先撞上哪一道。

🔴 它**不**重新判断"能不能卖" —— 那是 `checkout.routes.ts` 的闸门，写第二份一定会漂
（AGENTS §3.5）。它只把运营看不见的那几格事实摊开，并指到"去设哪几枚变量"。
`--strict` 时有档卖不了就退 1（部署前自检用）。

## 四、后果

1. **两个 409 在屏幕上不再共用一句话**：②′ 说清缺什么并给出口，④′ 仍是"别买这一档"。
2. **界面不再替服务端猜**：没有 `reason` 时退回错误码那句（原有行为），不会凭空说"缺云端 AI"。
3. **"为什么买不了"有了可以一条命令回答的地方**，而且它的读数与生产启动走同一条装配路径。
4. ⚠️ **`reason` 的取值变了**：任何外部读这一字段的项目必须按码解析（本仓只有 `app-host` 读它，
   已在同一提交里改）。这是**线协议**的变更，故立此 ADR。
5. ⚠️ **它没有让这台实例变得能卖**：能不能卖取决于部署的 `.env`（两组开关，各自"全有或全无"）。
   本轮改的是"看不见"那一半。

## 五、本轮不做 / 已知边界

1. **不做 `GET /api/billing/skus`**（选项 C）：提前把"这台实例可售哪些档"交给客户端，需要新端点 +
   新契约，而答案会随一次重启失效。要做就先定"可用性快照多久内算有效"。
2. **移动端没有换档出口**：`RenewSection` 只有文案映射，没有档位选择器；两壳的差距如实留着。
3. **不把 ②′ 挪到 ④（收款通道）之后**：闸门顺序（① → ②′ → ④）有既有判据与变异臂钉着，
   挪动会改变"先报哪一句"的语义；而"这台实例连通道都没有"这件事由 `doctor:billing` 直接说。
4. **不把 ¥12 档从 `automation` 摘掉**：那是商业裁决（ADR-0060 第一句：既有购买能力不因
   该功能开发而关闭），不是闸门能顺手改的。

## 六、判据

| 层 | 判据 |
|---|---|
| 线协议（码而不是散文） | `server/tests/billing-checkout.routes.spec.ts`：②′ 与 ④′ 各断言自己的 `reason` 码，且两码不同 |
| 客户端只认词表内的码 | `packages/app-host/tests/checkout.spec.ts`：「词表外一律丢弃」（含旧的中文散文形状）；「没有 reason 时对象里不出现这个键」 |
| 界面（web） | `apps/web/tests/renew-panel.spec.tsx`：②′ 说清成因 + 一键换档后**真的**发 ¥5；没有原因码时**不**说"缺云端 AI" |
| 界面（移动） | `apps/mobile/tests/renew-entry.spec.ts`：查表顺序（原因码 → 错误码 → unknown）与原始码兜底 |
| 真浏览器 | `e2e/tests/renew-panel.spec.ts`：新增一条 ②′ 用例（文案 + 换档 + 重发 ¥5），与既有的 ①′/④′/503 四条并存 |
| 自查命令 | `server/tests/billing-doctor.spec.ts`：逐档读数（④/②′/无闸三条）+ 与环境变量名、闸门顺序的**源码对账**（帮助文本与顺序不许漂） |
