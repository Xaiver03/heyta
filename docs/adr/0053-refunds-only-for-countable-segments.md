# ADR-0053：退款只做「能精确数出那一段」的域 —— 收窄 ADR-0026 的适用范围，而不是推翻它

> 状态：**已接受**
> 日期：2026-10-05
> 取代：**不取代** [ADR-0026](0026-refund-side-entitlement-revocation-not-implemented.md) ——
> 它查证的那条建模缺口（`subscriptions` 记不下"哪一笔买了哪一段"）**没有被推翻**，
> 本 ADR 做的是**把"不做"的范围收窄到可数的那个域**：域内按笔回收，域外照旧**拒发**。
> 修订：[ADR-0038](0038-admin-console-scope.md) §2 的"不做：改订阅／**退款**／发券"里
> **退款**这一项（另两份文件各有一段指回这里的勘误）。
> 相关：[ADR-0017](0017-single-paid-tier-and-payment-channel.md)（通道）、
> [ADR-0018](0018-adjustable-pricing-and-coupons.md)（价目与券的 append 语义）。

## 1. 背景：ADR-0026 拦住的到底是哪一半

ADR-0026 §1 的查证留了两件事，而它们指向不同的方向：

1. **缺口是真的**：权益落在**一行** `Subscription` 上，字段只有
   `grants[] / status / currentPeriodEnd / lastEventAt`，
   没有任何字段记录"哪一笔支付买了哪一段"。⇒ 全量的"退第 2 笔、保留第 1 笔"
   在那套模型里**无法表达**，任何按笔回收都必然是**过度回收**。
2. **但经由收银台的单是另一回事**：每一单在 `checkout_orders` 里都有**自己的行**
   （带 `status='paid'`、`final_amount_minor`、`price_id`），而授予侧的规则是死的 ——
   一次支付 = `+SUBSCRIPTION_PERIOD_DAYS` 天（`webhook.routes.ts`），
   能力 = 这一单冻结的 `price_id` 的投影（`apply-event.ts`）。

第 2 条意味着：在一个**明确的子域**里，"这一单买下的那一段"是**可数的**，
不需要改权益模型也能算对。于是 ADR-0026 §3 的"本轮不做"可以从
"一行代码都不写"收窄成"**只在算得对的地方动手，其余一律拒发**"。

政策这一维也不再是阻塞：业主 2026-10-05 明确授权先定一个**临时口径**并落地
（"先做着，避免代码空置，我到时候完全可以改"）。所以本 ADR 的 §5 第 7 条把
"对外法务文案仍待确认"单独立成边界，而不是继续拿它当不做的理由。

## 2. 结论

### 2.1 可退的域（全部满足才发退款）

| 条件 | 不满足时的拒发原因 |
|---|---|
| `checkout_orders.status = 'paid'` 且有 `paid_at` | `ORDER_NOT_PAYABLE` |
| `out_trade_no` 非空（= 真的经收银台下的单） | 🔴 `NOT_CHECKOUT_ORDER` |
| 库里那一行的币种在 `Currency` 词表内 | **抛错**（数据已损坏），不按 `CNY` 猜 |
| 结算时收到的**实付**金额可比、为正整数 | `AMOUNT_UNVERIFIED` |
| 支付成功起 `7×24h` 内，**或**运营在后台带理由批了例外 | `WINDOW_PASSED` |
| 这一单没有别的**还开着**的退款行 | `REFUND_ALREADY_OPEN` |
| 这一单还没退过 | `ALREADY_REFUNDED` |

**不在这个域里的钱一律不发退款** —— 尤其是没有订单号的那条旧兼容到账路径
（`adapter` 自己声明 `oneTimeGrant` 的事件）。那种钱在库里没有可对账的一行，
回收量算不出来。这不是"实现得糙一点"，而是**只在能算对的地方动手**。

### 2.2 三条硬规则（这才是"绕开 ADR-0026 硬约束"的实际形状）

1. 🔴 **回收量 = 冻在 `refunds.period_days` 上的那一段，不是对当前状态的猜测。**
   申请那一步就把「实付金额」与「天数」写进退款行，之后的审批、通道答复、
   回收**只读这一行**。中途任何一次改价、改券、改授予常量都不许改变"该退多少、该扣几天"。
2. 🔴 **全链路只有一个落点能动权益**：`applyRefundResultInTransaction` 里
   `refunded_at` 由 `NULL` 翻成非空的那**一次**（靠条件更新的**影响行数**判定，
   所以它同时是幂等闸门）。通道回"受理"（`processing`）**不许**动 ——
   那与 ADR-0026 禁止的半真状态是同一类，只是方向更坏（钱还没出去，权益先掉了）。
   这件事不靠约定：迁移里的
   `refunds_success_needs_refunded_at` 把 `status='success' ⟺ refunded_at IS NOT NULL`
   钉成了**双向**的结构约束。
3. 🔴 **先翻订单状态，再数"还剩几笔已付"**。反过来会把这一单自己算进剩余里，
   于是回收量少算一整段（用户白拿 30 天），而两侧都不报错。

判定顺序本身也是一条规则：时间窗排在**最后**，所以 `operatorApproved`
只打开时间窗，不会连带把"这单根本没付过钱""这一单已经在退款路上"放行。

## 3. 被否决的选项

| 选项 | 否决理由 |
|---|---|
| **A. 只接订单侧反转、权益不动** | ADR-0026 已否决，本 ADR **继续否决**：那是字面意义上的"订单已退款而权益还在"。 |
| **B. 政策级"任一退款即整行失效"** | 会撤销用户**更早那笔合法购买**买下的时间。它简单，但它把一次退款变成一次惩罚。 |
| **C. 逐笔支付权益账本**（新表 + `Subscription` 退化为派生视图） | 唯一能让**全量**退款算对的路，但它要动权益模型与判定路径，是一个独立工作流 —— 见 §6 的终点。**本 ADR 不否认它是终点**，只否认"必须先有它才能退任何一笔钱"。 |
| **D. 按当前到期日倒推扣 30 天**（不冻 `period_days`） | 与 §2.2 第 1 条直接冲突：到期日可能已被更早的合法购买推到未来，"扣 30 天"扣的可能是别人买的时间。它**看起来**和正确做法一样，这正是它危险的地方。 |
| **E. 后台让运营填退款金额 / 天数** | 那是第二个事实源。金额只能等于结算冻下的实付，天数只能等于授予侧那一段；一旦可手填，三条 CHECK 就退化成装饰。实现上的对应做法：`requestRefund` **没有** `periodDays` 旋钮。 |
| **F. 部分退款（退少于一整段）** | 本档是"单次 30 天买断"，**没有可部分退的形状**。微信 API 支持多次部分退，我们不接：那需要一个"已退累计额"的账，而 §2 的域里没定义它。 |

## 4. 落地（每件事的唯一归属）

| 面 | 落点 | 判据 |
|---|---|---|
| 政策口径（窗口 / 全额 / 回收算法） | `server/src/billing/refund-policy.ts`（**纯函数**，唯一数字源） | `tests/billing-refund-policy.spec.ts` |
| `refunds` 表与三条 CHECK | 迁移 `20261014000000_add_refunds`（普通 DDL，不带 CONCURRENTLY） | PGlite 用例直接读**发布中的迁移文件**建表 |
| 状态机 / 冻结 / 唯一回收落点 | `server/src/billing/refund-store.ts` | `tests/billing-refund-store.pglite.spec.ts`（真 SQL：CHECK、条件更新行数、语句顺序、事务边界） |
| 通道退款调用 | `wechat.adapter.ts#refund`（`/v3/refund/domestic/refunds`）；`noop` 适配器**抛**而不是空操作 | `tests/wechat-adapter.spec.ts` 的 `refund()` 与「退款通知归一化」两组 |
| 退款通知进业务层 | `webhook.routes.ts`：`event.refundNotice != null` 走回收分支，**没有**任何授予路径 | `tests/billing-webhook-settlement.pglite.spec.ts` 的「webhook 退款分支 —— 通知走回收，不走授予」 |
| 运营审批面 | `admin.routes.ts` 四条（列表 / 申请 / approve / reject），在插件级 `requireAdmin` 之后 | `tests/billing-refund-admin-routes.spec.ts` |
| 审计 | `pricing_audit_log` 的 `refund_*` 一族（**每一次被拒也落审计**） | 同上两组用例里的 `auditActions(...)` 断言 |

适配器侧的取舍：`verifyWebhook` 现在**接受** `REFUND.SUCCESS / ABNORMAL / CLOSED`
（ADR-0026 洞 1 的那个 401 因此不再是终态），但归一化出来的事件带
`oneTimeGrant: null` + `userId: null` —— 🔴 **退款通知在类型上就给不出授予**，
它只能认领一张已存在的退款行。

## 5. 已知边界（不许读成"已解决"）

1. **"发出去但响应丢了"那一格**：`submitRefundToChannel` 不在事务里（不能让网络调用
   占住一个 `FOR UPDATE`），所以"通道收到请求"与"我们落状态"之间有一个崩溃窗口。
   重试会换一个新的 `out_refund_no`，第二次靠通道侧"累计退款 ≤ 订单额"挡下，
   失败如实落 `failed`。**这是本方案最粗的一处。**
2. **`failed → success` 这条边是被允许的**（只由签名有效的通知认领）。
   信任的是"验签通过 + `out_refund_no` 对得上"这一件事；
   而 `reconcile.ts` 的对账作业**只覆盖支付事件、不覆盖退款**，所以这条边没有兜底对账。
3. **`already-applied` 这个 outcome 名在两处共用**：真的重投，与"状态机不允许这一跳"
   （例如一条还停在 `requested` 的行收到 success）。审计里分不开这两种。
4. **行锁没有在本仓库实测过**：PGlite 是单连接的，两个 `BEGIN` 无法并存。
   "两个管理员同时点批准只有一个生效"的证据是**条件更新的行数**，
   不是"PostgreSQL 真的会阻塞第二个事务"。后者是文档保证的行为。
5. **没有一笔真实的退款通知**：全部证据在库层与单元层。
   仓库内没有配置任何支付通道（`WECHAT_PAY_ENABLED` 未设 ⇒ 生产 adapter 列表只有 `noop`），
   所以 §4 那四条通道/回调判据是**对着 APIv3 的形状**写的，未与真实载荷逐字段核对
   （ADR-0026 §6 同一条未核实项仍然成立）。
6. **`@@unique([userId, provider])` 仍然不存在**：回收按 `(userId, provider) LIMIT 1` 找订阅行，
   与授予侧同一个找法。"一行一用户"仍是意图而非约束。本 ADR **不**顺手加约束
   （`AGENTS.md §3.3`：那是独立的、更大的建模决定，属于 §6 第 1 条）。
7. 🔴 **对外说法还没改**：`7×24 小时全额退`这句临时口径目前**只存在于代码与本文**。
   把它写进 `server/legal/terms-of-service.md` 或任何界面承诺之前，需要业主确认
   （`AGENTS.md §8` 工作流第 18 条：能力变化要同步核对既有的对外说明；而"把这句写成承诺"
   本身不是编码决定）。
8. **`period_days BETWEEN 1 AND 366` 那条 CHECK 依赖"全仓只有一个授予时长"**。
   真要做 90 / 365 天的档，顺序必须是：先让每一单记住自己买了多久，再放宽这里 ——
   而不是把上界抬到 400 让回收量继续靠猜。
9. **success 那条 UPDATE 里的 `refunded_at IS NULL` 是冗余闸门，没有判据能咬到它**。
   迁移里 `refunds_success_needs_refunded_at` 是**双向**的
   （`status <> 'success' ⟹ refunded_at IS NULL`），而状态集合已经把 `success` 行排除在外，
   所以库里不存在一个让这两半给出不同答案的行。实测：把这一半拿掉，
   §4 那组用例**全部照绿**（变异臂存活）。这不判整条判据没牙 ——
   它判的是**这一半够不到任何可达形状**；真正的牙在 schema 那一侧，
   由「三条 CHECK 双向」那组咬住。留着的理由写在代码注释里：钱的路径上，
   一道冗余闸门比一道"以后 CHECK 被放宽了就静默失效"的闸门好。
10. 🔴 **后台的"审批面"今天是接口，不是界面**：`/api/admin/refunds*` 四条路由通了、判据齐了，
    但 `apps/web/src/features/admin/` 里**没有** refunds 这个 tab，
    `packages/app-host/src/admin-client.ts` 里**没有**对应的传输函数
    —— 现在能批准一条退款的，只有拿管理员令牌直接敲接口的人。
    补它不是一个改动而是五件：admin-client 传输 + web store 一片 + 面板一个 tab +
    `packages/i18n` 中英两条 + **真浏览器截图且人看过**（`AGENTS.md §6.2` 规定一）。
    本 ADR 把它记成边界，不记成"后台已可用"。
11. **`adminRequest` 把非 2xx 只落成 `reason + status`，不带响应体**：
    于是 409 里的 `reason:'WINDOW_PASSED' / 'ALREADY_REFUNDED'` 到不了界面。
    退款恰恰是"必须告诉运营**为什么**被拒"的那类操作 —— 接界面时这是第一件事，
    不是可选项（否则会再造一次"错误被折叠成一句'请求无效'"的形状）。

### 4.1 变异读数（2026-10-05，一次装置跑 14 臂）

逐臂把生产代码改坏、跑对应那一组用例，**要求它红**：
13 臂转红，且红的用例名与本 ADR §4 那一行对得上（例：拿掉"这一单已有开着的退款"那半 ⇒
`同一单不许有第二条开着的退款` 红；把审批路由的通道失败报成 502 ⇒
`通道抛错 ⇒ 仍是 200 + channel-failed` 红；把 adapter 挑通道改成"这台实例配的第一家" ⇒
`没注册那一单当初的通道 ⇒ 409` 红）。

存活的是**拿掉 `refunded_at IS NULL` 那一臂**（原因见 §5 第 9 条）；另有一臂
**第一趟存活、补强用例后转红**：
`amount.total` 那条用例原先两个金额都填 400 —— 标题断言的东西一个都没断言到，
改成 `refund 200 / total 400` 之后同一臂转红。**这条是本节里唯一一条"判据本身是假的"的发现**，
形状与 `AGENTS.md §7 第 33 条`（阈值要从被约束的常量推导）同一族。
装置与逐臂日志是一次性的，不入库（本表就是它的读数存处）。

## 6. 终点（什么时候本 ADR 该被取代）

1. **逐笔支付权益账本**（§3 选项 C）落地：那时"可退的域"不再需要收窄，
   本 ADR 的 §2.1 整张表会被"任何一笔到账都可退"取代。
2. **退款进入对账**：`reconcile.ts` 开始按 `out_refund_no` 与通道核对退款状态，
   §5 第 1、2 条那两格崩溃窗口才算有兜底。
3. **出现部分退款 / 多档时长需求**：§5 第 8 条的顺序要求生效，本 ADR 的
   「回收量 = 常量那一段」不再成立。
4. **业主定下正式退款政策**：`refund-policy.ts` 那两个常量改写，
   对外文案同步（§5 第 7 条）—— 政策变了本 ADR 不必重写，它管的是**域与不变量**，
   不是天数。
