# ADR-0055：账号注销写**墓碑**，恢复时以墓碑**拒绝复活**

> 状态：已接受（2026-10-05）
> 工单：[`trash-and-archive.md`](../plans/trash-and-archive.md) 批次 E / E5 的 **P-12**
> 前置：[ADR-0049](0049-account-closure-erasure-semantics.md)（注销的销毁语义，**本文不改它的结论**）、
> [ADR-0050](0050-e2ee-key-lifecycle-and-recovery.md)（服务端不持有可解全量的托管恢复密钥）
> 调研：[`backup-side-erasure.md`](../research/backup-side-erasure.md)（监管要求与"为什么逐账号 crypto-erase 在本仓是堵死的"在那份）
> 取代：无

---

## 1. 背景：注销在活库里是真删，在备份里没有"把某一个人单独删掉"这一说

`DELETE /account` 删账号行，Prisma schema 上的级联带走 operations / devices / syncState /
passkeys / 密钥包。所以**从注销那一刻起，之后的每一份新备份都不再包含这个账号** ——
这一条不是本文要新增的能力，它是硬删的既有后果（现量：`run_pg_dump` 读的是活库）。

真正缺的是两件事：

1. **没有任何东西记住"这个 id 曾经被注销过"**。于是恢复一份旧备份就是把这个人带回来，
   而界面、日志、库里都不会有一个字提到这件事发生过。
2. **本仓今天根本没有恢复脚本**（`server/scripts/` 里只有 `backup.sh` 那一族），
   所以"恢复"这一步的全部纪律只存在于文档里的一句话。

法务侧因此只能写成"随保留期自然过期"（`packages/legal` 那三处）。ICO 对备份的口径是
**不要求立刻删**，但要求过渡期"beyond use"、要求按既定 schedule 被覆盖掉、
且**任何一次恢复都不许把已注销的人复活**。第三条是本文落地的那一条。

---

## 2. 决策

**新增一张不带外键的 `account_tombstones`，两条面向用户的注销路径在删账号的同一个事务里写它；
新增一枚 `restore.sh`，导入完成后按它删掉复活行、再逐个墓碑断言 0 行，不成立就退出非零、
不打印可被照做的成功行。**

### 2.1 这张表**故意没有**指向 `users` 的外键

形状与 `RevokedSyncDevice`（`schema.prisma:373`）几乎一样，而那一族带
`onDelete: Cascade`。这里不能抄：**这张表存在的唯一理由，就是在账号行已经不存在之后
继续记录这件事发生过。** 上级联外键会让删账号顺手把墓碑删掉 —— 症状不是报错，
是恢复时没有任何一层知道该拒绝谁。

判据在 `server/tests/account-tombstone.pglite.spec.ts`：删号之后必须还数得出那一条墓碑
（配上"那一行用户确实没了"的阳性对照），而这条用例的存在意味着**将来有人在迁移里
补一个级联外键会当场红**。

### 2.2 只存 SHA-256 hex，并由 CHECK 钉住

`email_hash` 是这张表里唯一的身份残留。迁移里那条
`CHECK ("email_hash" ~ '^[0-9a-f]{64}$')` 是 Prisma 表达不了、而 `TEXT` 又拦得住明文邮箱的那一格：
少了它，某次"顺手把邮箱也带上"会把明文身份写进一张**每晚都进备份**的表 —— 正是这次变更要消除的东西的反面。
归一化沿用 `admin/admins.ts:48` 的 `trim().toLowerCase()`，不另起一套。

### 2.3 恢复闸：判据是"逐个墓碑现在 0 行"，不是"删了几行"

`DELETE … RETURNING` 的计数在"本来就没有复活行"时是 0 —— 那是**通过**而不是**证据**。
所以脚本在删之后跑一条 `WHERE EXISTS` 的断言，返回任何 id 都以 `RESTORE=GATE_FAILED`
非零退出。两条 SQL 只有一份作者（`restore.sh` 里带 `# GATE_DELETE_SQL:` /
`# GATE_ASSERT_SQL:` 标记的行），PGlite 用例**现读脚本**去真库上跑它们 ——
控制流与语句各自有证据，而没有任何一处抄第二遍。

另外两处形状是承重的，都有用例：
- **表不存在时在导入之前就把话说明白**（`NO_TOMBSTONE_TABLE`）：否则闸会在一个
  它读不到的库上汇报"通过"；
- **导入失败时闸根本不该跑**：否则"闸通过"是在一个半途的库上说的。

### 2.4 墓碑必须随账号面产物走

`backup.sh` 的 accounts 那份原来只 dump `users + passkeys`。加上 `--table=account_tombstones`
之后，"只恢复账号面"这条既有恢复路径才带着闸的输入。整库那份本来就从活库读，
两张表都在。

## 3. 被否决的选项

| 选项 | 否决理由 |
|---|---|
| 逐账号 **crypto-shredding**（每账号一把密钥，销毁密钥即销毁数据） | 前提不成立：根密钥客户端生成、服务端只存包裹串，能解密的唯一路径是离线拿到用户口令（ADR-0050 那条"不在服务端保存可解密所有数据的托管恢复密钥"）。要么让服务端能解密（直接破坏 E2EE），要么按账号分片加密备份（备份/恢复一致性重做）。Thoughtworks 那条定位的适用条件是"控制一小撮密钥"，本仓恰好不是 |
| 把 accounts 产物改成**行级过滤导出**（`COPY … WHERE id NOT IN (SELECT …)`） | **现量否证**：调研文档 §4 B.2 建议的那一半其实没有兑现对象 —— 硬删发生在活库上，新备份本来就不含已注销账号；行过滤只影响"旧产物"那一半，而那一半由留存窗口 + §2.3 的恢复闸覆盖。改产物格式要重做恢复路径，换来的是一条已被活库保证的承诺 |
| 在**注销之后**去改写/删除既有备份文件（gzip 里删行） | ICO 明说备份不需要立刻，而"能改 gzip 快照的删除器"是一件没人能验证的东西 |
| 给清扫**未验证注册残骸**那条路也写墓碑（`sync.service.ts:982`） | 语义不符：那张表说的是"这个人注销过"，而残骸清扫不是注销。已登记成白名单里**明示的例外**（`account-deletion-paths.spec.ts`），要改先改语义 |
| 直接把 `RevokedSyncDevice` 复用成账号墓碑 | 它的 PK 是 `(user_id, client_id)` 且带级联 —— 复用的第一步就是删掉那条级联，那会破坏它自己"挡住被撤销的离线客户端重新注册"的语义 |

## 4. 后果

- 多一张表、多一个 `DELETE /account` 内的事务边界。注销的**响应形状与状态码一字未改**，
  所以三端客户端与既有判据不受影响；`check:layering` 不涉及（全在 server 侧）。
- 恢复动作从"文档里的一句话"变成一枚**会拒绝**的脚本。
- **对外文案没有改**。法务那三句"备份随保留期自然过期"仍然成立 —— 现在它比从前多了一层
  代码兑现，但把那句话改成更强的承诺是**§5 第 3 块板**，不在本文授权范围内。
- 新增的 `restore.sh` 是运维动作，不会被任何现有门禁自动执行。

## 5. 仍然要产品负责人拍的三块板（都不是代码问题）

1. **`RETENTION_DAYS` 定多少** —— 现量冲突：`server/docs/backup-and-recovery.md` 的示例是 3、
   `backup.sh` 的默认是 14、法务那句写的是 14。数字越短，ICO 那条"age out"越硬。
   定下来之后才有资格做"脚本默认值 / runbook 示例 / 法务句子"的三方对账门禁。
2. **备份是否默认加密、密钥托管在哪** —— `server/tools/backup-encrypted.sh` 现在读的是
   **同机 root 可读的口令文件**，等于没有托管。这条同时是 ADR-0049 拒绝把加密备份接成默认路径的前置。
3. **是否接受"整库备份不定点删、账号面靠墓碑 + 恢复闸 + 留存窗口"作为对外口径** ——
   批准之后才改 `packages/legal` 那三处句子（含中英同步与版本号，那是进同意指纹的）。

代码侧不依赖这三块板，已按本文全部落地；三块板任何一块翻过来都只影响**文档措辞与运维默认值**，
不影响 §2 那四条的形状。
