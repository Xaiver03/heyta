# ADR-0006：同步与 AI 的供给模式 —— 自备与托管并存

- **状态**：已接受（2026-09-26 由产品负责人确认：自备与托管都提供）
- **日期**：2026-09-26
- **决策者**：产品负责人（指示："我们应该提供两种方案…他们自己接入 AI、自己配置 AI，和我们统一提供云服务的这种两种模式都需要提供。…我记得 Obsidian 就是这么做的。当然也可以用我们的服务。"）
- **影响层**：`packages/`（新增 `packages/ai`）、`apps/*`（设置页与出境披露 UI）、服务端（新增可选的托管 AI 网关）、产品与定价
- **关系**：**补充并部分修订 [ADR-0005](0005-ai-data-path.md)**。ADR-0005 判定"选项 A（云端 AI）明确否决"；本 ADR 把结论从"否决"改成"**提供但严格受限**"。**ADR-0005 的其余结论全部保留**（尤其 §3.1"AI 是输入法"与 §3.2 的单一 provider 端口）。
- **前置证据**：[E2EE 产品的 AI 做法](../research/e2ee-apps-ai.md)（调研进行中；本 ADR §2.1/§5.1 的对应条目据此标注为待核对）、[AI 竞品与架构调研](../research/ai-competitive-and-architecture.md)、[AI 功能格局](../research/ai-feature-landscape.md)

---

## 1. 背景

产品负责人要求 heyta **同时提供两种供给模式**：

| 维度 | 模式一：自备 | 模式二：heyta 托管 |
|---|---|---|
| **同步** | 用户自建服务端（Docker 自部署） | 用 heyta 的云同步 |
| **AI** | 用户自己配置 AI 接口（自己的 Key / 自己的端点） | 用 heyta 提供的云 AI |

并以 **Obsidian** 为先例（可自配 AI 插件、可自配同步，也可买 Obsidian Sync）。

这个要求**必须拆成两个维度分别回答**，因为它们的结论**完全相反**：

- **同步维度的答案是好消息**：两种模式**都不与 E2EE 冲突**。
  服务端从头到尾只见到密文（`violatesE2eeGate` 强制 `isPayloadEncrypted === true`，无开关），
  **所以"谁托管同步"是一个纯粹的部署选择，不改变任何隐私性质。**
  这个能力**今天就已经成立** —— 自建与托管跑的是同一个服务端二进制。
  → 结论：**同步两模式 = 一个 onboarding 选择，零架构风险。** 见 §3.1。

- **AI 维度的答案是硬约束**：**托管 AI 与 E2EE 在定义上不能共存。**
  模型要读明文才可能工作。若 heyta 托管 AI，那么**至少在被 AI 处理的那部分数据上**，
  服务端必须看到明文 —— 那就不是端到端加密了。
  → 结论：**AI 两模式可以都提供，但"托管 AI"必须是一个明确、可撤销、按功能开启的例外**，
  而不是一个全局开关。见 §3.2。

## 2. 关键事实

### 2.1 🔴 没有任何 E2EE 产品做到"厂商托管 AI 且维持 E2EE"（✅ 已确证）

调研（[`e2ee-apps-ai.md`](../research/e2ee-apps-ai.md)，192 处 ✅ 抓到官方全文）的**核心结论**：
**现有 E2EE / 本地优先产品要么不做 AI，要么只做本地接口 / MCP / BYOK。
在所有样本中，"厂商托管 AI + 维持 E2EE" 这条路线一个都不存在。**

**唯一正面回答此问的厂商是 Proton Lumo，而它的回答是"做不到"**，并给出了技术原因：

| 原文 | 说明 |
|---|---|
| 「**true E2EE that bypasses the LLM server would be far too slow** using homomorphic encryption…」 | 同态加密实测**响应超过一天** |
| 「**So we need to provide the LLM with cleartext messages.**」 | 给模型看的必须是明文 |
| 「**The server decrypts the message temporarily to process it through the language model**」 | 服务端临时解密 |
| 「we acknowledge this is **not the regular definition of end-to-end encryption**, which is why we prefer to call it **user-to-Lumo (U2L)** encryption」 | **主动改名以免误解** |

> 🔴 **Proton 的做法值得逐字学习：它没有含糊过去，而是改了自己的术语。**
> heyta 也应当如此 —— 见 §3.2 第 5 条。
> ⚠️ 但它的**静态对话历史仍是真 E2EE**（"no system at Proton can ever read a Lumo conversational history"），
> 这一点与 heyta 的处境**完全相同**：同步仍然端到端加密，出境的只有 AI 那一条路径。

**其它相关事实**：

- **Joplin Cloud AI** 是另一家厂商托管 AI，但文档明写「note content goes to the provider」，
  且 🔴「**Encrypted notes can't be used with the panel**」——
  它是**用"不覆盖加密笔记"来回避冲突**，不是解决冲突。
- ❌ **TEE / 机密计算 / 同态加密：未找到任何 E2EE 笔记或任务产品在用。**
- 「客户端解密后仅本地调用」不属于"厂商托管"，因此**不构成对 §2.1 的反例**。

这不是"我们还没找到做法"，而是一条**结构性结论**：
明文必须到达模型，而 E2EE 的定义就是"服务端到不了明文"。
两者在数学上互斥 —— 除非引入机密计算（TEE），
而 ADR-0005 §2 已经用证据排除过 TEE 作为地基
（DDRop 用约 $159–200 的 DDR5 interposer 即可重放 Intel TDX / SGX / AMD SEV-SNP 的加密内存；
且信任根与运营方是同一方）。

> **因此 heyta 不许宣称"托管 AI 也是 E2EE"。** 那不是取舍，是自相矛盾。
> 谁想宣称这句话，就得先推翻上面这条 —— 并且要解释为什么 Proton 的工程师错了。

### 2.2 ✅ Bear 给出了"最好的那条路"，而且它比托管更值得做

**Bear**（E2EE 笔记，Mac/iOS）的做法是本项目**最贴近的先例**
（`bear.app/faq/command-line-interface/`，2026-09-25 抓取全文）：

| Bear 的做法 | 原文 |
|---|---|
| AI 推理**跑在用户自己机器上** | "Everything runs locally. `bearcli` reads and writes your local Bear database on your Mac." |
| 不做批量上传 | "No bulk upload. **Connecting a tool does not share anything by itself.** The assistant only sees the notes a specific query returns." |
| 🔴 **加密笔记保持加密** | "**Encrypted notes stay encrypted. They can be listed, but never read or modified by any of these tools.**" |
| 作用域限制 | 提供 Only tags / Exclude tags |

**这是"F 分支"（只做接口）的一个完整、可验证的实现**，而且它解决了一个
托管 AI 永远解决不了的问题：**加密条目可以被列举、但永远读不到**。
→ 对 heyta 而言，这条路的**差异化价值高于托管 AI**，因为它给的是
**别人给不了的东西**（滴答清单、Todoist 都给不了）。

### 2.3 同类产品的"自配 AI"生态已经很大，但 key 存放是坑

- **Obsidian Copilot**：「Keys are stored in this device's **Obsidian Keychain**,
  not in the vault's `data.json`」；支持 Ollama / LM Studio / 任意 OpenAI 兼容端点。
  → **E2EE 应用必须把 Key 放系统钥匙串，不能放被同步的 vault** ——
  否则密钥会跟着密文一起走（ADR-0005 §3.2.1 已记录同一结论）。
  ⚠️ 但 Copilot 另有 **Copilot-hosted（厂商云）模式且后端闭源** —— 这一半不可学。
  ✅ **Obsidian 官方核心无 AI**，AI 全部来自插件（已抓到官方全文核实）。
- **Joplin**：见 §2.4 —— 本次调研里**唯一"核心自带 AI + 本身是 E2EE + 把取舍写成文档"**的样本。
- **Anytype**：Local API + 官方 **Agents' Skill**（localhost、可离线、多 key 可吊销），
  并有官方危险提示："**use only trusted extensions**"。

### 2.4 🔴 Joplin 是 heyta 最该逐条对照的模板（本次最重要的可执行发现）

Joplin 是**唯一**同时满足"核心自带 AI""本身是 E2EE 产品""把取舍写进文档"三点的样本。
它为此付出的设计代价，heyta **几乎可以逐条照抄**：

| Joplin 的做法 | heyta 应当怎么做 |
|---|---|
| 🔴 **双开关，且都默认关**：AI 总开关 + `Allow remote AI providers` | **照抄。** 一层"要不要 AI"，一层"允许不允许远程" |
| 🔴 **把 `.local` 按"远程"处理**，理由是 **mDNS 名字可指向当前网络内任意主机** | **已经照抄** —— `packages/ai/src/supply.ts` 的 `isLoopbackEndpoint` 只信字面回环 |
| MCP **11 个工具默认全关**，逐个开 | 照抄：能力逐个授权，不给"全部允许" |
| 只监听 `127.0.0.1` | 照抄：本地 API 不监听 `0.0.0.0` |
| token 用于防**本机其他程序** | 照抄：本机程序不是可信的（对照 Bear 的同类设计） |
| 端侧嵌入模型（140 MB），**索引不同步** | 参考：端侧派生物不进同步链路 |
| 🔴 **加密笔记直接拒绝 AI 面板**（"Encrypted notes can't be used with the panel"） | 照抄：**加密条目在托管模式下根本不许送** —— 比"披露"更强 |

**最后一条尤其重要**：Joplin 与 Bear 都选择了"**读不到就读不到**"，
而不是"读得到但先弹个窗"。这条线的**说服力远高于任何披露文案**。
→ 这正是 ADR-0005 §3.5 的 F 分支，也是 §3.3 把 F 排在托管之前的原因。

### 2.5 ⚠️ 端侧 AI 必然产生明文派生物（heyta 若做 B 分支要提前承认）

两条自曝的官方证据：

- **Anytype**：「**Indexes stay local and unencrypted**… assumes your local device hasn't been compromised」
- **Bear**：即使开启 ADP，「**notes' titles and tags' names remain unencrypted**」

🔴 而且**「只对非加密元数据做 AI」这条路**在样本中 **❌ 无任何先例**。
→ 所以 heyta 若做端侧索引/端侧模型，**必须提前说明"本机索引是明文"**，
不能把"端侧"讲成"零风险"。这是 ADR-0005 §4 那个负面后果的具体形态。

## 3. 决策

### 3.1 同步：两种模式都提供，且**都不改变隐私性质**

| | 自建 | heyta 托管 |
|---|---|---|
| 服务端看到什么 | 只有密文 | 只有密文 |
| E2EE | ✅ 保持 | ✅ 保持 |
| 谁付算力/存储 | 用户 | heyta |
| 数据主权 | 完全在用户 | 托管（**仍是密文**） |

**实现要求**：
1. Onboarding 必须让用户**显式二选一**（填自己的服务器地址 / 用托管），
   **不得默认静默选用托管** —— 默认值会变成事实上的选择。
2. 自建与托管跑**同一个服务端二进制**（已经如此），
   所以这不是"两套系统"，只是"一个 URL 的差别"。**不要为它分叉代码。**
3. 🔴 **一旦选了自建，客户端不得再向 heyta 的任何域名发数据**（含遥测）。

### 3.2 AI：两种模式都提供，但**托管模式是受严格限制的例外**

**默认必须是"自备"**（ADR-0005 的 C+D，同一个 provider 端口，只是 `baseUrl`/key 不同）。

**托管模式（heyta 云 AI）允许提供，但必须同时满足全部五条**：

| # | 约束 | 理由 |
|---|---|---|
| 1 | **按功能开启，不是一个全局开关** | "开启了 AI"不该意味着一整个 app 的数据都可能出境 |
| 2 | **开启前显示出境披露**：哪些字段、发给谁、保留多久 | ADR-0005 的 AI-0 ④；照 Apple PCC 与 Nextcloud Ethical AI Rating 的范式 |
| 3 | **随时可撤销，且撤销立即生效** | 撤销后不得再有新的出境请求 |
| 4 | **本地路径始终是一等公民**，不得为推托管而弱化自备 | 否则"可自备"是假的 |
| 5 | 🔴 **不得宣称托管模式是 E2EE** | §2.1 —— 那是自相矛盾 |

**并且**：
- **托管 AI 处理的数据不进入同步链路**（它不是 op，也不产生 op）。
  它只读**当次请求所需的明文**，用完即弃，不落库。
- **加密条目在托管模式下不得被读取** —— 这条比"披露"更强：有些数据我们**干脆不送**。
  ✅ **两家先例都选了这条更硬的路，而不是"弹窗披露"**：
  Bear（"**Encrypted notes stay encrypted… never read or modified by any of these tools**"）
  与 Joplin（"**Encrypted notes can't be used with the panel**"）。
  → **这印证了"读不到就读不到"比任何披露文案都有说服力。**
- 记账与限额与同步计费**分开**，避免"AI 用不了导致同步也停了"。
- ✅ **两层开关，都默认关**（照抄 Joplin，见 §2.4）：
  第一层"要不要 AI"，第二层"允许不允许**远程**"。
  只做一个总开关是不够的 —— 它把"本地推理"和"发给服务器"混成了一件事。

### 3.3 优先顺序：接口先行，托管最后

**先做 F（本地 API / MCP），再做自备，最后才做托管。** 理由是产品性的，不是技术性的：

1. **F 是唯一能给出"别人给不了的东西"的一条**（Bear 证明了：
   加密条目可列举不可读）。托管 AI 只是**追平**滴答清单/Todoist。
2. **F 不需要用户配置任何东西** —— 它直接对接用户已有的 AI 客户端
   （Claude Code / Cursor / 任意 MCP 客户端），绕开了"教育用户配 Key"这道坎。
   ADR-0005 §5.5 已记录：BYOK 在任务管理品类里**零先例**，教育成本是真实风险。
3. **托管 AI 的每一行代码都是需要长期承担的成本**（推理账单、滥用、合规、模型供应商关系），
   而它带来的差异化最低。**在 F 与自备被验证之前不该启动。**
4. ✅ **调研给出了同一条顺序的独立佐证**：在全部样本里，
   **没有任何一家把 AI 做成"只有托管才能用"** —— 自带供给免费、托管供给收费，
   且**安全性从不收费**。方向相反的做法（用隐私换 AI 收入）在这个品类里**没有成功先例**。

## 4. 后果

### 正面

- 用户要的两种模式**都提供了**，且同步维度的两模式**零风险**（今天就能做）。
- "托管 AI 不是 E2EE"被明确写下来 —— 这避免了最坏的一种结果：
  **对外宣称 E2EE、实际上为了 AI 开了口子。** 那是不可逆的信任损失。
- Bear 的范式给了 heyta 一个**托管 AI 永远给不了的**卖点。
- 计费与隐私边界清晰：**同步可以收费且不损隐私；AI 托管要收更多钱，因为它的代价更大。**

### 负面 / 需要接受的成本

- 🔴 **"提供云 AI"会让一部分隐私用户直接不信任我们** ——
  即使默认关闭、即使有披露。这是真实代价，且**必须接受**，不能靠话术化解。
  缓解方式只有一个：**默认关闭 + 别宣称它是 E2EE。**
- 托管 AI 需要长期现金投入（推理账单），而它可能与"开源核心 + 自建免费"的定位冲突。
  → 建议：**托管 AI 只在托管同步的付费档里提供**，不与自建版绑定。
- 三模式（自建同步 / 托管同步 / 自备 AI / 托管 AI）的组合会让**支持矩阵变复杂**
  （4 种组合 × 平台）。文档与测试必须显式覆盖，不能靠"应该没问题"。

### 需要靠规范/门禁兜住的

- ✅ **已落地**：`scripts/check-layering.mjs` 已从 4 条规则扩到 **6 条**，新增
  `no-model-endpoint-in-apps`（拦 `chat/completions`、`api.openai.com`、`:11434/v1` 等字面量）
  与 `no-vendor-ai-sdk-in-apps`（拦 `openai` / `@anthropic-ai/sdk` 等导入）。
  **已用 3 处注入违规验证能失败。**
  ⚠️ 诚实标注：它们的完整前提是 `packages/ai` 存在（现在存在了），
  但**不该被读成"出境已经完全受控"** —— 门禁只保证"调用点集中"，
  真正的受控要靠 `packages/ai` 的闸门被**实际使用**。
- ✅ **已落地**：`packages/ai` 实现了出境闸门，且授权**绑定在 `(功能, 目的地)` 上**。
  切换目的地时 `retainValidConsents` 会**删除**不匹配的旧授权 ——
  这是"同意了 A、做了 B"那类事故的止血点。
- **托管模式的开关状态不得进 op-log**（它是本机偏好，不是需要同步的业务数据）——
  否则"我在 A 设备关了 AI，B 设备却还开着"会变成一个隐私事故。
  > 这一点需要产品决策：**若用户希望多端一致，就必须接受"这个设置会同步"**。
  > 见 §5 未决项 5。
  > 🔴 2026-10-05 指针：上面这条引用指的是**未决项 5**（开关是否多端同步），
  > [ADR-0054](0054-managed-ai-retention-and-selling-preconditions.md) **没有**关闭它；
  > 它关闭的是 §5 未决项 4/6 里的「数据保留策略」**那一半**（DPA 那一半仍未签），
  > 而"服务端到底留了什么"的当前答案是 0054 **§4.1 的两个载体**（计数表 / 运维日志，
  > 两者上限的性质不同）—— 那边是裁决，这里不复制。

## 5. 未核实项

1. ✅ **已核实（原为待核对）**：`e2ee-apps-ai.md` 已于 2026-09-26 落盘（1096 行，
   192 处 ✅ 官方全文）。§2.1 的"没有一家做到"**得到确证，且拿到了 Proton 的逐字自述**。
   原先标记为"待核对，若有反例必须重写"——**核查完成，无返例，§2.1 与 §3.2 第 5 条保持不变。**
2. ✅ **已核实**：Obsidian Sync **默认是真 E2EE**（scrypt → HKDF → AES-256-GCM，官方教用户亲手验证），
   但**存在第二个"托管密钥"模式**（"or let our **managed server generate one** for you"）；
   原名 "managed encryption"，**因 Cure53 审计 `DYL-04-005`「Key mgmt. confusion」于 2024-10 改名**
   为 "standard encryption" 并改文档。另有 ToB 2025-12 审计点名的 3 条限制
   （确定性文件哈希可被用来确认用户是否上传过某文件等）。
   → 🔴 **对 heyta 的直接教训**：**"托管密钥"与"端到端加密"必须用不会混淆的名字**，
   否则会走到需要第三方审计来指出命名问题的那一步。
   ❌ 官方对"自建同步"的立场原话**未找到**（Obsidian 与 Bear 产品内都无自托管）。
3. ✅ **已核实，非返例，反而是最强证据**：Proton Lumo **明确承认做不到**，
   给出技术原因（同态加密响应 >1 天）并**主动改名为 U2L 加密**。详见 §2.1。
4. 🟡 **托管 AI 的定价与限额模型**仍无结论。竞品参考：Motion 按 credits（Pro 7,500/seat/月）、
   Notion 按 credits（$10 / 1000 credits）、滴答清单含在 Premium 且配额未公开。
   ✅ **但计费划线有一条压倒性共识**：**"自带供给免费、托管供给收费"** ——
   Joplin（自建同步免费 / Joplin Cloud 收费；Ollama 免费 / Cloud AI 收费）与

   **也没有一家把"AI 开关"做成付费墙**。→ heyta 不应把隐私做成付费项。
   > ✅ **2026-10-05 部分裁决**（产品负责人授权"连保留策略与售卖一起开"）：
   > 限额的**数字与单位**早已定案（¥12 / 300 次每计费周期，ADR-0020 §3.2），
   > 这一条真正缺的"计量与执行"现在有了落点 ——
   > `server/src/ai/metering.ts` + `ai_usage_counters` 表（计数唯一键是
   > `(user_id, period_anchor)`，裁决与占用在**同一条原子语句**里，见 ADR-0054 §2 与
   > AGENTS §8.15）。**仍未裁决的是 credits 这套单位要不要换成额度池** ——
   > 结论是**不换**：换单位会改落地页、法务与用户已看到的承诺，而 300 次这一档
   > 的单位经济已经按次算清（ADR-0021 §1）。

   > 托管代理路由在 `server/src/ai/managed-proxy.routes.ts`，`NOT_YET_DELIVERABLE_SKUS`
   > 已清空，`POST /api/billing/checkout` 对 `hosted-ai-monthly` 回 **200**（不是 409），
   > 订单落 `final_amount_minor = 1200`。
   > 🔴 但"可以下单"**不等于**"这一档对用户可用"：任何客户端都还没有那个开关
   > （ADR-0054 §8），所以对外文案仍按"打不开"写。

5. 🔴 **"AI 开关是否多端同步"仍是未决的产品决策**（见 §4 最后一条）。
   倾向：**同步**，但同步的必须是**加密后的载荷**，
   且**开启托管 AI 需要在每台设备上单独确认一次** ——
   否则一台设备的授权会静默扩大另一台设备的数据出境面。
   > ✅ 本 ADR 的实现已把这层保护做进了代码：
   > `packages/ai` 的授权**绑定在 `(功能, 目的地)` 上**，
   > 且切换目的地时 `retainValidConsents` 会**删除**不匹配的旧授权。
6. ⚠️ **本 ADR 未覆盖**：托管 AI 的模型供应商选择、数据处理协议（DPA）、
   以及对"AI 生成内容正确性"的责任划分（ADR-0005 §5.6 已登记同一缺口）。
   > ✅ **2026-10-05 逐项裁决**（[ADR-0054](0054-managed-ai-retention-and-selling-preconditions.md)）：
   > - **供应商选择**：已定 —— DeepSeek（ADR-0021），并且托管路径**只能接境内供应商**，
   >   那份白名单是可执行判据而不是形容词（`packages/ai/src/managed-endpoints.ts`
   >   + 保存/启用与发送**两个点**共用同一份判断 + ADR-0053）。
   > - **数据保留策略**：已定 —— 服务端对托管请求**不留正文，只留元数据**，
   >   而元数据是**两个载体、两种上限**（这一半是同日的落地更正，
   >   原文曾写成"只保留计数"一句带过 —— 少说一个载体和多说一个字段同样是披露失败）：
   >   ① **计数表** `ai_usage_counters`：列集合就是承诺本身
   >   （账号 / 计费周期 / 次数 / 最后使用时间，多一列即红），保留 **45 天**
   >   （= 一个计费周期 + 出账缓冲；依据是"能不能核对账单"，不写法规理由）
   >   **且该计费周期结束后**才删，删除由 `purgeExpiredAiUsageCounters` 执行；
   >   ② **运维日志**：每次调用一行（时间 / 账号 / 功能名 / 结果 / 字节数 / 耗时），
   >   上限是**容器日志容量**（`server/docker-compose.yml` 的 `10m × 30`）而不是天数 ——
   >   🔴 所以对它**不许写一个"保留 N 天"**，那是关于一个不存在的定时删除的承诺。
   >   ⚠️ 那句"字节数"会暴露请求体的**长度**，所以"不记任何由内容派生的量"这类
   >   绝对句已撤回；准确说法是"不记能还原内容或其含义的东西"（ADR-0054 §4.1）。
   >   `describeRetention('heyta-cloud')` 从此有真数字可说，
   >   `assertEnableable` 那条 `retention-undecided` 的**前提**已经消失，
   >   ✅ 而**闸门也已真的拆掉**（同日：该 reason 连同它的成员一起从
   >   `AiConfigError` 里删除 —— 没有构造点的成员不留）；
   >   法务文案与生成物版本号在同一个提交里跟着改，没有出现"先打开开关、再补说明"。
   > - **DPA**：仍未签 —— 这是**外部动作**，不在本仓库能自决的范围里。
   >   在它落地之前，对外文案只能陈述我们自己的处置方式（不保留正文、境内供应商），
   >   **不许**出现"已与供应商签署数据处理协议"这类没有凭据的句子。
   > - **责任划分**：仍按 ADR-0005 §5.6 的缺口登记（界面上 AI 内容一律标"建议"，
   >   写入必须用户确认，这一层结构上就限定了"AI 说错"能造成多大后果）。
   >
   > 🔴 措辞纪律（产品负责人 2026-10-05 定）：heyta **没有监管意义上的数据出境**。
   > 描述我们自己的托管路径一律用「离开本机／交给第三方处理」；
   > 唯一可能真跨境的是**用户自配的境外端点**，而那一档
   > `packages/legal/src/documents/ai-and-transfer.ts` 刻意**不下结论**，保持不下结论。
