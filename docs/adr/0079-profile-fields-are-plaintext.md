# ADR-0079：基础资料（昵称 / 头像）明文，端到端加密只留给实质内容

- **状态**：已接受（2026-11-01）· **产品负责人明示为绝对决策，不容篡改**
- **日期**：2026-11-01
- **取代**：[ADR-0073](0073-non-op-payload-keys-follow-the-session.md) 中**关于头像加密**的全部结论
  （该文关于"非 op 载荷跟着会话钥匙走"的推理仍适用于将来的其它加密载荷）
- **相关**：[ADR-0040](0040-email-password-auth-decoupled-from-e2ee.md)（登录口令与 E2EE 口令解耦）、
  [ADR-0050](0050-e2ee-key-lifecycle-and-recovery.md)（vault 根钥匙与解锁会话）

---

## 一、决策（一句话）

**昵称与头像是基础资料，一律明文存储、明文读写，不需要 E2EE 口令、不需要 vault 解锁。
端到端加密只用于实质内容（任务、便签、清单正文，以及将来的财务/账目这类绝对隐私）。**

这是产品负责人 2026-11-01 的原话，逐字记在这里：

> 「把这个彻底解决掉。头像是绝对不应该这么干的，基础用户资料里不应该加这个。
>  这完全是加重用户的UX负担……谁会把头像当成隐私？没有人会把头像当成隐私，
>  这绝对是错误的做法，一定要改过来。把这个作为关键的、绝对的、不容篡改的决策。」

> 「只有涉及绝对隐私，比如财务数据这种实质性内容时，才允许适用这种加密。
>  这种加密是保守策略，而不是太激进了。我们都允许自托管了，他们真的想要隐私，
>  保证隐私完全可以自托管。」

## 二、问题是什么

头像此前是**客户端加密后上传**的（R10 起）：
服务端只存密文、`GET` 回来要先用同步口令 / vault 根钥匙解开。代价不是理论上的：

- 登录态账号的钥匙只存在于**已解锁的 vault 会话**里，而钥匙从不落盘
  （ADR-0040 §7.2 / ADR-0050）。⇒ 刷新、重开应用之后，改头像会先撞上
  「端到端加密口令不在这台设备上 —— 解锁一次之后就能换头像」。
- 对一个**基础资料字段**来说，这等于把一次密码学操作塞进"换张照片"的动作里。
  多端还要分别处理"这台设备有没有钥匙"，移动端甚至长期只支持口令模式。

## 三、为什么不是"更安全一点"

加密在这里被误用成了**默认**。本条确立的取舍是：

| 数据 | 处理 |
|---|---|
| **实质内容**（任务正文、便签、清单、未来的财务/账目） | **端到端加密**。服务端看不到明文；这是产品的地基 |
| **基础资料**（昵称、头像） | **明文**。服务端按普通账号字段保存；界面不向用户索要任何密钥 |

两条判据：

1. **用户会在日常操作里被它挡住吗？** 会，就说明加密用错了层。换头像、改昵称是
   一天里可能发生几次的动作；输入口令去解锁一次不是这个动作该有的前置。
2. **这条数据的泄露是否构成"绝对隐私"级别的事故？** 头像与昵称不构成。
   真正需要的用户还有另一条路：**自托管** —— 服务端归他自己，隐私边界由部署形态决定，
   而不是由官方实例强迫所有人多背一层密钥。

⚠️ 自托管**不是**"把官方实例的承诺降级"的借口；它是"对隐私要求更高的用户可以自己承担
运维，从而拿到更强的控制"。官方实例对基础资料的处理就是本 ADR 写的明文。

## 四、落地的形状

- **契约**（`packages/shared-schema/src/account-profile-contract.ts`）：
  `PUT account/avatar` 收 `{contentType, dataBase64}` 明文载荷；
  服务端校验 MIME 白名单与**解码后的** 512 KB 上限（旧版服务端只能量密文长度）。
- **存储**（`UserAvatar`）：`data` 存图片字节，`content_type` 存 MIME，`hash` 是
  **图片字节**的 SHA-256（缓存失效键）。迁移
  `20261101000000_avatar_is_plain_profile_data` 清掉旧密文行 —— 服务端从来没有钥匙，
  换算不了，而 heyta 仍在开发阶段。
- **接口**：`GET /api/account/avatar` 仍要 Bearer，只回本人那一行；没有"按别人身份查资料"的端点。
  **明文 ≠ 公开**：开放他人可见是另一次独立决定。
- **两端**：web 删除 `useAvatarKey` 与"去解锁"整块；移动端不再要求口令。
  `resolveAccountAvatarImage` 只剩 `absent / ready / unreadable` 三种状态。
- **文案**：`packages/legal` 的隐私政策与个人信息清单改成"头像明文、不用于人脸识别或身份核验"；
  「生物特征不离开设备」的结论仍然成立，但**只指通行密钥的比对**，头像只是可选展示素材。

## 五、判据

| 层 | 判据 |
|---|---|
| 契约 / 服务端 | `server/tests/account-profile.spec.ts`：明文载荷落库；格式白名单与 512 KB 拒绝；GET 返回明文 |
| 存储迁移 | `server/tests/account-profile-schema.pglite.spec.ts`：`data` / `content_type` 列存在且旧列已改名 |
| 共享层 | `packages/app-host/tests/hosted-account-profile.spec.ts`：**没有钥匙也能**上传与读回 |
| web | `apps/web/tests/profile-panel.spec.tsx`：口令为空 / vault 未解锁时仍能上传与显示 |
| 真浏览器 | `e2e/tests/profile-avatar-plaintext.spec.ts`：不输入任何口令，换头像并刷新仍在 |
| 合规文案 | `packages/legal` 的单测与 `pnpm check:legal-*` |

## 六、后果

1. 服务端**能看到**头像图片。这是本决策明确接受的代价；对外文本已同步改口。
2. 旧加密头像**不可迁移**：服务端没有钥匙，迁移直接清空该表（开发者阶段，无用户）。
3. 头像不再与"能不能同步"耦合：只要登录就能改，离线本地任务仍不需要账号。
4. 🔴 **不可篡改**：任何"给头像/昵称加回 E2EE、口令解锁、按钥匙取密文"的改法都违反本 ADR。
   要推翻它，只能由产品负责人明确改判，并**新写一份 ADR**；不许在实现里顺手加回来。
