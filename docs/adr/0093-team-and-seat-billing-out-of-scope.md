# ADR-0093：团队 / 多人席位 / 工时审批不在 heyta 产品范围

> 状态：**提议（Proposed）**（是否采纳由产品负责人决定；本文件只给结论与理由）
> 日期：2026-11-26
> 相关：[ADR-0062]（共享清单与协作边界）、[`feature-matrix.md`](../research/feature-matrix.md) §11「明确不做的」
> 证据：[`ticktick-coverage-graph.md`](../research/ticktick-coverage-graph.md) §3 第 #65 行 + §3c「D 档归属①产品裁决不做」

## 1. 背景

覆盖图谱 #65「团队」是 D 双缺（没做、也没靶子），且 §3c 已把它归入「① 产品裁决『不做』」。
`feature-matrix.md` §11 也把「团队项目管理 / 甘特图 / 工时审批」列为**反需求**：那是另一条赛道。
但这条裁决此前只写在 research 层，没有一份 ADR 承接，于是 #65 一直挂在待办里。

## 2. 结论

**heyta 不做团队 / 多人席位 / 工时审批 / 甘特图。**

- **最小协作面已由「共享清单」覆盖**：邀请成员、成员角色、所有权转让、逐 op 签名、任务/便签/评论三族双向同步（见 `feature-matrix.md` §6.1/§6.3 与 ADR-0062）。这已满足"和几个人共用一份清单"的需求。
- **席位计费 / 组织管理 / 工时审批**与「本地优先、单人可自托管」的定位冲突：它们要求服务端持有权威的组织与计费模型。
- **不做 ≠ 不支持协作**：共享清单继续维护；只是不往"团队项目管理"那条赛道扩张。

## 3. 后果

- 覆盖图谱 **#65 从 D 改为「范围外（not applicable）」**，不计入「没学到」，不留待办。
- 引用纪律：任何"heyta 该不该做团队"的将来提问，答案指向本 ADR，不再重新讨论。
- 若日后真的要做团队，必须新写一份 ADR 取代本份（ADR 只增不改结论）。

## 4. 不做的事

- 不实现席位计费、组织层级、跨清单甘特、工时填报。
- 不给共享清单加"团队工作区"外壳去伪装成团队产品。
