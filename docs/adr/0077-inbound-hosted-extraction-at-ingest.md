# ADR-0077：托管档的「接收即抽取」——服务端读明文的唯一窗口，与它不许长出的东西

> 状态：**已接受（工程裁决 2026-10-27）**，功能**未上线**、**未对外披露**（§7、§8）。
> 相关：**限定** [ADR-0060](0060-automation-entitlement-and-retention.md) §4 那条 7 天保留在这一档上提前履行；
> 沿用 [ADR-0054](0054-managed-ai-retention-and-selling-preconditions.md) §3「请求体在服务器上活多久：一次调用」的形状与 §7「托管永远不叫端到端加密」；
> 沿用 [ADR-0064](0064-inbound-automation-commit-and-task-batch.md) 的提交许可与异构任务批（本档**不新增**许可路径，见 §3.4）；
> 沿用 [ADR-0059](0059-inbound-worker-authenticated-identity.md) 的 worker 身份边界（服务端这条腿不需要 worker 凭据，见 §3.5）。
> 落地计划：[`../plans/inbound-automation.md`](../plans/inbound-automation.md) 与
> [`../plans/inbound-automation-work-brief.md`](../plans/inbound-automation-work-brief.md) 的当天那节。

---

## 0. 一句话

自动收集的正文是**封给设备**的（HPKE 只加密到收件人公钥），服务端从设计上打不开自己刚写下的那一行 ——
所以"由我们来做抽取"只有一种诚实的做法：**在接收那一次 HTTP 请求里、明文还在手上的那一段**抽完，
把冻结结果**重新封给同一枚收件人公钥**，然后把源正文从那一行上抹掉。任务写回仍然是设备的事。

---

## 1. 起因与它真正问的是什么

产品负责人的原话（2026-10-26，本轮的起点）：

> "比如这个任务，我觉得明明可以这样：进数据的时候，每次可以给到一个回调地址。把回调地址给它，
> 它就会向这个回调地址发数据，数据直接由我们的 AI 分析就可以了。都已经用上 AI 了，
> 数据本来对我们来说就是可以读的，必须得是可读的。"

这句话里有一半是**事实**、一半是**当前不成立的假设**，分开处理：

| 那句里的成分 | 现量 | 结论 |
|---|---|---|
| "数据进我们服务端时是明文" | **成立**：`server/src/automation/inbound.routes.ts` 在校验通过后拿到 `rawBody`，直到那一行的写入事务为止，明文就在这次的内存里 | 抽取只有在这段窗口内做才不违反既有契约 |
| "数据对我们本来可读" | **不成立**：写入的是 `sealInbound(...)` 出来的收件密文，服务端只有公钥（`openInbound` 需要设备私钥）。落库之后再谈"读"就是空头支票 | 所以窗口**不能**挪到落库之后，也不能挪到"后台再扫一遍" |
| "给一个回调地址就行" | 已经在了：这条入站路由本来就是给第三方发数据用的回调地址 | 本 ADR 不改接法，只改接完之后那一瞬间做什么 |

另一句在前一轮问过的「自动收集不能由我们来提供常驻的服务吗？」在这里一并给结论：
**能**，而且这就是本档 —— 但"常驻"必须限定成"常驻的那台服务器在收到数据的当场做抽取"，
**不是**"服务端长期持有可读的正文"。差别就是这份 ADR 存在的全部理由。

## 2. 动手前的实测（`2026-10-27` 现量，别抄下面的数字）

```bash

grep -rln "managedAiProxyRoutes" server/src                 # 只有 server.ts 注册它
# 服务端能不能打开自己写下的正文
grep -rn "openInbound" server/src packages/inbound-core/src # 只在设备侧/测试里出现
# 这一行上正文与结果各住在哪
grep -n "payloadCiphertext\|resultCiphertext" server/src/automation/inbound.routes.ts
```

| 事实 | 位置 | 它为什么决定形状 |
|---|---|---|
| 入站那一行先封后写，服务端只持公钥 | `inbound.routes.ts` 的 `sealInbound(...)` 与它的事务 | 抽取窗口 = 这次请求；窗口外没有任何合法路径能读到明文 |
| 设备侧**早就**会恢复"别人替我抽好的"结果 | `packages/app-host` 的 `processInboundAutomationEvent` → `readAutomationPreparedResult`（开结果 → 校验摘要 → 领许可 → 写批） | **设备端零改动**就能承接服务端冻好的批；这是本档能做成"窄"的原因 |
| 行状态机已有 `queued/leased/prepared/needs-confirmation` 与租约代号 | `server/src/automation/events.ts` | 两条腿共用同一台状态机，不需要新状态、不需要新列族 |
| 托管发送腿的七道闸门顺序是**判据**，不是实现细节 | `server/src/ai/managed-proxy.routes.ts` 的文件头那张表与 `managed-proxy.routes.spec.ts` | 抽出来复用就必须**整段**搬走，摘一道就会红掉一条已有用例 |
| 额度只在 `consumeManagedAiRequest` 那一步原子消耗 | `server/src/ai/metering.ts`，被路由的第 ⑤ 道调用 | 第二条腿只要复用同一枚函数，就**天然**不会多扣一次 |
| 显式重试只认"结果不确定"那一档，且要求源正文还在 | `server/src/automation/events.ts::retryUncertainAutomationEvent` 里那句 `event.payloadCiphertext === null` 的拒绝 | 抽取成功后正文被抹 ⇒ 那一档根本不会进入重试，两条语义不打架（§4.3 说清后果） |

## 3. 决策

### 3.1 抽取只发生在接收那一次请求内，做完就把源正文从行上抹掉

`server/src/automation/hosted-extraction.ts::runHostedExtractionAtIngest` 一条腿走完：
**领活（租约）→ 当场抽 → 落终态**。成功落 `prepared`/`needs-confirmation` 时，同一条 `UPDATE` 里把
`payloadCiphertext` 写成 `null`；失败则**原样退回 `queued`**、密文与租约代号都不动，设备那条腿照旧兜底。

🔴 这条"失败退回 `queued`"是本档唯一的安全网：抽取失败**不许**丢数据，
所以对外可以说的话是"只可能更早，不可能更少"——早于设备自己抽，而内容不会比老路少一条。

留存上这不是新例外而是**提前履行**：ADR-0060 §4 批的是"保留 7 天"这个**上限**，
本档在同一批事件上把上限压到"一次请求"。7 天的清扫作业照旧存在，它扫的是失败/未抽取那些行。

### 3.2 冻结结果重新封给**同一枚**收件人公钥，AAD 换成 `purpose: 'result'`

服务端封的是它自己刚算出来的那份任务批，用的还是这一账号当前的收件人公钥与 `keyEpoch`。
密钥轮换后旧结果打不开这件事**不是**本档引入的：它与设备腿写下的结果密文完全同构，
走的是同一条 `keyEpoch` 判定。**服务端不曾、也拿不到**能打开它的东西。

### 3.3 模型怎么调：**把那条发送腿从 HTTP 路由里提出来，两条腿共用同一枚函数**

现量后有三个候选，选 (c)：

| 选项 | 判掉的理由 / 选它的理由 |
|---|---|
| (a) 让服务端自己 HTTP 调 `/api/ai/managed/chat` | 那一步要求 `authenticate`，服务端就得**替用户持有一张 JWT**（或绕过鉴权开内网口子）。前者比"读一次明文"坏得多——那是凭据保管；后者是给自己开一条没有鉴权的旁路。**判掉** |
| (b) 直接 `import` `managed-upstream.ts` 另写一次 fetch | 会长出**第二套**闸门顺序：境内白名单两处校验、额度先于发送、非 2xx 不回显、明文主机默认空表这四条纪律各得有一份抄件，而抄件会漂（本仓 §8 那条"两份事实源"）。**判掉** |
| (c) ✅ 把路由里的 ②'–⑦ 整段搬进 `server/src/ai/managed-completion.ts::invokeManagedAiCompletion`，路由退化成纯 HTTP 壳（解析 zod、拼错误形状），两条腿调同一枚函数 | 闸门顺序**只有一份**；额度消耗点只有一个（第 ⑤ 道），第二条腿天生不会多扣；搬动是纯结构调整，`managed-proxy.routes.spec.ts` 那 30 条用例一字未改就仍然全过——那正是"行为没变"的证据 |

🔴 这道"不许长出第二套发送腿"是有尺的，不是形容词：
`server/tests/inbound-hosted-extraction.spec.ts` 剥掉注释后在**整个 `server/src` 的代码**里数
`/chat/completions` 的出现次数并要求**恰好 1**。第一版它按**文件**计数，被自己的表头注释喂饱 ⇒ 恒绿；
变异臂 A6（改名）与 A9（另起一处拼接）现在一头一尾把它钉住（见 §5）。

### 3.4 服务端**不**写提交许可、**不**碰 op，任务写回仍然是设备

许可与 `createTaskBatch` 都在设备的周期里（ADR-0064）。本档**没有**为服务端开任何许可落盘路径，
也没有新增任何 op 写入口。这句话有**三把尺，各比一层**（少任何一把都留一处洞）：

1. **源码读**：`inbound-hosted-extraction.spec.ts` 里那枚结构性门槛，剥注释后读 `hosted-extraction.ts`，
   断言里面没有 `automationCommitPermit`/`commit_permit`/`createTaskBatch`/`dispatchValidated`，
   **也没有 op-log 真正的写入口 `operation.create` 与那本 `automationAiAttempt` 台账**
   （后两支 2026-10-28 补，原因见 §5 的第六处），并且给 `payloadCiphertext` 赋值**只有 `null` 这一次**
   （摘掉那次赋值 ⇒ 同一个门槛跟着红，见 A1）。
2. **写入计数**：同一枚 spec 里跑完成功那一趟，事务替身记到的"被写过的表"清单必须是空 ——
   经由任何 helper 伸进来的写都算，这一把不依赖字面名。A16/A17 各红这两把。
3. **真库那一档**（`H1`）：`automationCommitPermit.count=0`、`automationAiAttempt.count=0`（按 `userId`，不加别的限定），
   `inbound:<eventId>` 那枚 op 在设备 `sync()` **之前数不到、之后恰好 1 枚**，
   以及**这一趟前后按用户全量数的 op 差为 0**（臂 A18 往 op-log 注一枚合规的、id 形状完全不同的 op ⇒ 红的就是这一句）。
   ⚠️ 前缀那一枚单独不够：它证"设备那条链没凑出第二枚"，**证不了"服务端自己长出一枚别的 id 的 op"**。
   这是补第一把尺时在**同一族形状**（散文/标题比断言宽）上撞到的**第二处** ——
   那句"不写任何 op"原先就只由前缀计数撑着，而它看着已经比源码读那把"实"了。

⚠️ 前两把尺读的是源码与替身计数，它们证不了"设备那一腿接得住服务端冻好的那一行"。这个洞由
`server/tests/integration/inbound-dual-host-fault-windows.integration.spec.ts` 末尾那枚 `H1` 补上：
一枚真宿主经真 HTTP 与真库把整条链跑完 —— 设备先 recover 到冻结结果、**模型调用仍 1 次**（它没再抽一遍）、
本地 1 枚 op，服务端那三张表的读数即上面第 3 把尺那几句。变异臂 A12 把冻结那一步 AAD 的 `purpose` 写成 `input` ⇒
红的就是这条用例（单元那两面的封与解出自我自己写的 AAD，改哪儿都跟着一起改，量不到两档接不上）。

服务端唯一写的内容是：状态、租约、以及那一行重新封好的**结果密文**。

### 3.5 计量归属：额度恰好扣一次，且这条腿**不写** `automation_ai_attempts` 台账

`automation_ai_attempts` 是设备腿的"物理调用去重"账本（配合 worker 凭据与租约）。服务端这条腿
- 消耗额度：只发生在 `invokeManagedAiCompletion` 的第 ⑤ 道，与设备走代理时是**同一个函数** ⇒ 一次；
- 不写 attempts 台账：服务端没有 worker 身份（ADR-0059 那套凭据只发给设备），
  伪造一行台账等于把设备语义抄进服务端。
"结果到底抽没抽成功"的判定改用**租约持有者**：`claimAutomationEvent` 在过期租约回收那一支先看
`lease_worker_id`，命中 `HOSTED_EXTRACTION_LEASE_OWNER` 就直接转 `needs-confirmation` +
`model-result-uncertain`，要求用户显式重试，**绝不重发第二次物理调用**。
变异臂 A2 摘掉这个判定，红的正是"台账空着也照样拦"那一条用例。

⚠️ **A4（设备腿走托管代理时"预留 + 代理"各扣一次）不在本档里**，本轮没动、也不代拍：
它是既有设备腿的计费口径问题，归负责人。本档只保证**新增**这条腿不多扣一次。

### 3.6 开关是一列可空布尔，只有显式 `true` 才开

`automation_rules.hosted_extraction BOOLEAN`（**可空、无默认**）：
`NULL` = 这一列存在之前的规则 ⇒ 读成"归设备"，与今天的行为逐字节一致；`false` = 用户明确不开；
`true` = 唯一会触发服务端抽取的值。变异臂 A4 把判定改成"不是 `false` 就算同意"，红了 8 条，
其中就包括"只有显式 `true` 才开"那一枚专门为此写的用例。

为什么不 bump `CURRENT_SCHEMA_VERSION`、为什么写成可空：AGENTS §3.3 那条纪律针对的是
**客户端持久化字段**，而这一列只住在服务端的 Postgres 里；可空 + 无默认是为了
"存量行不被推断成同意"。为什么用布尔不用字符串枚举：今天只有开/关两态，
枚举的第三态会诱导"顺手加一个抽取模式"，而那需要新的披露与新的 ADR。

### 3.7 界面只在 web 的规则编辑器上有开关

`apps/web` 那份自动收集设置面板加了一枚勾选与一行说明；移动端**没有**规则编辑器，
所以这一档在 mobile 上不可开启（**已登记**，不是遗漏）。文案全部走 `packages/i18n`
（`web.ai.inbound.hosted.*` 四枚中英对称），面板里不许有第二份正文——A7 那一臂就是照这条红法造的。

## 4. 这一档的边界（读代码时要按这个来，别按"服务端帮我们做"来）

### 4.1 零日志：正文只在一次请求的内存里

判据是**标记串**，不是"我们说没有"：`server/tests/inbound-hosted-extraction.spec.ts` 把一段带唯一标记串的
正文喂进这条腿，然后断言那枚标记串**既不在写库参数里，也不在捕获到的全部日志输出里**；
失败时对外只披露稳定码（`model-request-failed` 这类），错误路径不回显上游响应体、不回显端点字符串。
这与 ADR-0054 对代理路由的约束同一条形状：**日志参数表就是保留清单**，没有接"内容"的位置。

⚠️ 上面那句原来只由单元档量着（假传输 + 捕获 logger），**真 HTTP 那一趟的对外响应体没量过**。
现在由 H1 补上，并且**按失法分臂**：路由里有**三行不同的 `202` 出口**（命中去重先返回、
抽取没成退回 `queued`、抽取成功把 `outcome.state` 写进状态词），A14 写坏第一行、A15 写坏第二行、
A22 写坏第三行，各只红一条 —— 合成一枚臂的话另一行被写坏时这把尺照样绿。
（第三行 2026-10-28 才补上：那半句"成功那一趟的对外响应"此前**只在单元档量着**，
而真 HTTP 上抽成功一度被认为不可能——实际是一条正当通道存在：守卫照原样跑，只把**发送那一层**桩住，
见 §6 第 7 条的改口。）

### 4.2 字段授权在发送之前，不是之后

`buildInboundModelInput(raw, allowedFields)` 在白名单投影**之后**才拼提示词。
系统提示词现在只有一个所有者：`packages/inbound-core/src/system-prompt.ts`（原来住在
`packages/app-host`，服务端不能依赖宿主包，所以**搬**而不是复制），三枚宿主都 import 它，
由 `scripts/check-inbound-system-prompt.mjs` 那把尺（五臂自检）看着。
A5 那一臂跳过投影直接把整个 payload 丢给模型，红的是"未授权的 `note` 根本不进那次提示词"。

### 4.3 抽取成功之后，"重新解析"这件事在物理上不可能

源正文已被抹掉，谁也抽不了第二遍。这不是缺陷而是本档的**定义**：窗口只有一次。
所以：
- 显式重试只对 `needs-confirmation` + `model-result-uncertain` 开放，而那一档要求 `payloadCiphertext` 还在
  （服务端抽取失败退回 `queued` 时密文原样保留 ⇒ 重试与设备兜底都仍然可用）；
- 用户对**已经抽好**的事件想"换个说法再抽一次"，只有一条路：**关掉这一档的开关**，让下一条新事件走设备腿。
  界面与帮助文档不许暗示"随时可以重抽"。

### 4.4 这一档不是端到端加密的例外

ADR-0054 §7 那句话照旧成立：托管不叫 E2EE。本档把"服务端读明文"限制在与那句完全相同的一个窗口里
（一次调用的内存），窗口外仍然是密文。§7 那张披露清单**没做完之前，这一档不许对外宣传、不许开生产开关**。

### 4.5 红线：服务端不许长出"打开入站正文"的能力面（不持收件私钥／Vault 根密钥）

这条以前只作为**现状**写在 §1 那张表里（"服务端只有公钥，`openInbound` 需要设备私钥"）。
现状不是约束：下一位完全可以在服务端 import 一把设备私钥或把 Vault 根密钥接过来，那时 §1 那句话变成假话，
而这条腿是唯一已经有 import 通道的位置（`server/src/automation/**` 里七枚文件、共九处从 `@heyta/inbound-core` 拿东西，
现量 `grep -rlF "from '@heyta/inbound-core'" server/src/automation | wc -l` 与
`grep -rhoE "from '@heyta/inbound-core'" server/src/automation | wc -l`）。所以现在把它写成**不许**，并配一把尺：

- **不许**：服务端这一侧的任何 automation 代码，不得进口或复刻"能解开入站信封"的那一面 ——
  具名的 `openInbound` 与它底下的原始件（`x25519` / `getSharedSecret` / `envelopeKey` / `aesDecrypt` / `diffieHellman`）。
  服务端手里的密钥材料只有两类合法：**收件人公钥**（只够重封）与**签发权益用的 issuer 私钥**
  （`entitlement-issuer.ts` 的 `privateKeySeed`，现量 `grep -rn privateKeySeed server/src/automation | head -1`）——
  后者与解密收件箱无关，把它当针会当场假红。
- **尺**：`server/tests/inbound-hosted-extraction.spec.ts` 里
  『服务端整个 automation 面不许长出"打开入站正文"的能力』那枚用例。它扫 `src/automation` 的整棵子树、先剥注释、
  并且**先断言扫到的文件数 > 0**（否则"哪都没命中"是零信息）。
- **臂**：A19 具名进口、A20 **改了名**的进口（针盯的是进口子句里必须出现的原名，所以调用点怎么改名都躲不掉）、
  A21 不进口而是把那五枚原语的形状抄进代码。三枚各红 1 条，红的那一条就是这枚用例。
  ⚠️ 这三枚注入**故意不调用**解密：真调用会缺私钥、缺字段 ⇒ 红的原因是崩溃不是判据（就是 §5 里 A16 那 5 条意外红的成因）。

  A10 钉"没有收件人公钥时仍然先 503、这条腿不许把自己降级成我们代读"，
  `H1` 钉"设备用自己那把私钥解得开服务端重封的那一行，而这一行的两列密文里搜不到标记串"。
  至于"服务端进程里此刻到底有没有一把私钥"，那是部署与密钥管理的题，不在本档能红的那一层。

跑这几轮**抓到六处自己的错**，都记在同一份证据文件里。前两处正是本仓那条元规则的现形：
"一把永远通过的判据比没有判据更糟"——① 判决从 ANSI 包裹的 `×` 字形数失败条数 ⇒ 恒绿；
② 门槛按文件计数 ⇒ 被同文件的表头注释喂饱 ⇒ 改名后照样绿。两处都是先跑臂才发现的。
中间三处（H1 那一轮）不是判据坏，是**装置读错**：断言只打形状不打原因 ⇒ 一次红四种可能撞成同一行；
把白名单的匹配键当成 `host:port`（其实只比 `hostname`）；`vitest list` 在整个 describe 被
`skipIf` 掉时打印 0 条而 rc=0，空读数差一点被读成"这枚文件没编译"。
🔴 **第六处的形状和前几种都不一样，而且它踩的是这条线最重的那道红线**：那枚结构性门槛的用例标题写着
"不碰 op 写入"，可 needle 里只有 permit 与任务批次那几个名字，**真正的 op-log 写入口
（`tx.operation.create` / `createMany`，现量 `grep -rn "operation\.create" server/src`）一枚都没在**。
A16 第一趟红 5 条、门槛那条**一言不发**（标题比断言宽），而那 5 条本身也是意外的：事务替身根本没有
`operation` 这个键，注入行当场抛 `TypeError` 把落库打断 —— 判据没比任何东西。
补上 `operation\.create` 与 `automationAiAttempt` 两支、并给替身装上那两张表加一枚计数断言之后，
读数降到**恰好 2 条**（门槛 + 计数），5 条意外红退回绿。
补完这两支之后 §3.4 那三把尺才**各归各位**：单元面那两把钉"这条腿自己不长出 op 写入"，
真库那把（`H1`）钉的是"设备那条链没凑出第二枚"，**而它按 op id 前缀数**，
所以"服务端写出一枚别的 id 的 op"这种失法在补之前**三把里没有任何一把看得到**。
🔴 **审这一处的时候在同族形状上撞到第二处**：H1 里那句注释"不写任何 `automation_ai_attempts`、不发提交许可、不写任何 op"，
底下撑着的三行断言里，op 那一行是**带前缀**的 —— 散文又一次比断言宽，而它看着已经比源码读那把"实"。
补了一枚**按用户全量、比这一趟前后之差**的断言，再给臂 A18 注一枚 schema 合法的 op 钉住它
（注**缺字段的**那种不行：缺字段会抛，红的是崩溃不是判据 —— 就是上面那 5 条意外红的成因）。
附带一条纪律：**臂的读数不能只数红几条，要先问每一红的原因是断言还是崩溃；
而"这条腿不写 X"这句，凡是散文里说了、断言只按某个 id/前缀/名字比的，都算没被量过。**
