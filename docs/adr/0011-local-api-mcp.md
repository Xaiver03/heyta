# ADR-0011：本地 API / MCP —— 默认关、只监听回环、加密条目可列举不可读

- **状态**：已接受（2026-09-26）
- **相关**：[ADR-0005](0005-ai-data-path.md)（AI 数据路径）、[ADR-0006](0006-supply-modes.md)（供给模式）、[ADR-0010](0010-ai-config-routing.md)（AI 配置路由）
- **实现**：`packages/local-api/`（35 条测试）
- **调研依据**：[`e2ee-apps-ai.md`](../research/e2ee-apps-ai.md)（Bear / Joplin 官方原文）

---

## 1. 背景与定位

[ADR-0006](0006-supply-modes.md) §3.3 把这一支排在最前，理由**不是技术性的**：
它是唯一一个**别人给不了**的能力。托管 AI 只是追平滴答清单；
"让 Claude Code / Cursor / 你自己的脚本安全地读写 heyta 的任务"
是 E2EE 产品才有的、别人抄不走的东西。

同时它还是 [ADR-0005](0005-ai-data-path.md) 记下的最大产品代价的**解药**：
默认保守意味着"用户不配置就没有 AI"，而本机 API 提供的是**零配置就有**的入口
（AI 工具本来就在用户手里，不需要 heyta 提供模型）。

---

## 2. 🔴 它是**独立于 `@heyta/ai` 的包**

两个包的方向**相反**：

| | `@heyta/ai` | `@heyta/local-api` |
|---|---|---|
| 方向 | **出站**（我们发给模型） | **入站**（别的程序打进来） |
| 谁在请求 | 我们 | 本机其他程序 |
| 主要风险 | 把用户数据送出去 | 别的程序把数据读走 / 乱写 |
| 默认 | 关 | 关 |

**放一起会在类型层面把"我们发数据出去"和"别人拉数据进来"混在一起**，
那正是最容易配错的地方 —— 例如把 AI 的"允许远程端点"开关
误当成"允许本机程序访问"。

分开之后：
- "回退不得跨越隐私边界"（[ADR-0010](0010-ai-config-routing.md) §3.3）
- "加密条目不可读"（本 ADR §3.4）

各自**只有一个地方能出错**。

---

## 3. 决策

### 3.1 默认关，且**每个工具**单独默认关

照抄 Joplin 的形状：它的 11 个 MCP 工具全部默认关，逐个开。

> **读工具也默认关。** 读走全部任务和改坏数据一样是问题 ——
> 甚至更隐蔽，因为它不留痕迹。

工具目录**刻意保持很小**（当前 6 个：3 读 + 3 写），并有测试断言不超过 10 个。
理由：**工具每多一个，"默认关"的清单就长一条，而用户不可能逐个理解它们的风险。**

### 3.2 只监听回环

`validateLocalApiConfig` 拒绝一切非回环地址。接受 `127.0.0.0/8`、`localhost`、`::1`。

🔴 **`0.0.0.0`、`::`、`*` 必须显式拒绝** —— 它们绑定所有网卡，
却最容易被误当成"本机"（字面上像"所有地址"，直觉上像"随便"）。
监听它们等于把用户全部任务暴露给同一网络里的任何人，
而"本机 API"这个名字会让用户以为它是本机的。

> **一条纪律**：关着的时候**允许**配置不完整。
> 用户可以先填一半再打开，不必先通过校验才能存草稿；
> 而真正开始监听的那一刻配置一定是安全的。

### 3.3 显式 token，且**防的是本机其他程序**

打开时必须非空。

它防的**不是**网络攻击（服务不出机器），而是**本机其他程序**：
没有 token 的话，用户装的任何一个程序、浏览器里的任何一个页面
都能直接打 `http://127.0.0.1:PORT` 读走任务。
（Joplin 的注释同样写着 token guards against local programs。）

🔴 **身份检查在工具存在性检查之前。** 反过来的话，一个没带 token 的调用方
可以通过"未知工具"与"未授权工具"两种不同错误**枚举出 heyta 有哪些工具**。
有测试断言"没带 token 时，已知工具与未知工具的错误信息**逐字相同**"。

token 比较用**定长比较**（逐字符累积差异，长度不同也不提前返回），
不用 `===`。对 localhost 场景这是偏执，但成本是零。

### 3.4 🔴🔴 加密条目：可列举，不可读

Bear 的底线，原文：

> "Encrypted notes stay encrypted. They can be listed, but never read or
>  modified by any of these tools."

在 heyta 里的实现：`LocalApiItem.readable`，由壳在
**解密失败 / 用户标记为保护 / 该条目不在本机可解密范围内**时置为 `false`。

| 行为 | `readable: true` | `readable: false` |
|---|---|---|
| 出现在列表里 | ✅ | ✅ **（"存在"必须可见）** |
| 标题 / 截止 / 优先级 / 完成态 | ✅ | ✅ |
| 备注正文等**正文类**内容 | ✅ | ❌ **剥掉** |
| `get_task` 读它 | ✅ 返回 | ❌ **明确拒绝** |

**两个刻意的设计选择：**

1. **元数据保留。** 让工具知道"这里有个受保护的任务"是有用的 ——
   否则用户会以为数据丢了，或者工具会以为自己查错了。
   **"存在"与"内容"是两件事。**

2. **`get_task` 拒绝，而不是返回空。** 列表返回"有我但不给你看"是**正确**的；
   而 `get_task` 被要求读正文，正确答案是**拒绝**，不是返回一个
   看起来像"这个任务没有备注"的空结果 —— 后者会让调用方**以为读成功了**。

🔴 **实现上用白名单重建，不用黑名单删除。**
黑名单（`delete item.body`）永远会漏掉将来新增的字段；
白名单不会 —— **新字段默认不暴露，要暴露得显式加进来**。
有测试模拟"以后有人加了 `attachments` 字段"，断言它默认不出现。

> ⚠️ 判定是**逐条**的，不是逐库的：同一个列表里可以有的可读、有的不可读。
> 所以判定必须发生在**每一个**返回数据的地方，而不是"打开数据库"时做一次。

### 3.5 写入只能经 `dispatch()` 形状的端口

`LocalApiWritePort` 只有一个方法 `submit(intent)`，形状即 `dispatch`。

🔴 本包**没有**任何 op 构造函数，`LocalApiWriteIntent` 是**封闭的三种动作**
（`create-task` / `update-task` / `complete-task`）。
→ 工具**在类型上表达不出**"随便改个字段"或"自己拼一个 op"。

为什么必须如此（[ADR-0005](0005-ai-data-path.md) §3.1）：
本机 API 如果直接改状态或自己拼 op，就会绕过
**向量时钟**（→ 同步冲突解不开）、**幂等**（→ 重试产生重复任务）、**冲突检测**。

⚠️ 本包**不 `import @heyta/op-log`**，用一个结构化的最小接口。
理由是 `@heyta/ai` 已有的同一条纪律：一旦能 import op 类型，
"不写 op"这条约束在类型上就失效了。

### 3.6 本包不实现 HTTP 服务，但**提供一个与传输无关的处理器**

按 [ADR-0003](0003-multi-platform-strategy.md)，业务逻辑在 `packages/`，`apps/*` 只放平台差异。
所以分工是：

| 层 | 位置 | 负责 |
|---|---|---|
| 契约 + 授权 + 协议 | `packages/local-api/src/{tools,mcp,server}.ts` | **这次调用允不允许、回什么** |
| 数据与写入翻译 | `packages/app-host/src/local-api-host.ts` | intent → 哪个 action、日期怎么换 |
| 怎么收字节 | `apps/node-host/src/local-api-server.ts` | socket、HTTP、读 token 头 |

`createLocalApiHandler` 收一个 `JsonRpcRequest`、回一个 `JsonRpcResponse`，**不碰 socket**。
好处：**授权规则只有一份实现**，而"怎么暴露"可以每个平台不同
（桌面用本地 HTTP、移动端可能用别的机制）。

### 3.6.1 🔴 鉴权曾经错误地依赖了**监听端口**

第一版里 `authorizeToolCall` 调的是 `validateLocalApiConfig(config)`，
而那个函数会连**端口**一起校验。后果是：

> 一份 token 完全正确、但端口写成 `0` 的配置，会让**每一次工具调用都被拒**，
> 而且报错说的是「本机 API 未启用」—— 排查方向被完全带偏。

端口是**监听**的属性，不是**鉴权**的属性。现已改成只查 token；
端口只在 `startLocalApiServer` 里检查一次（那里查错了才是真的起不来）。

这个 bug 是**先写测试才发现的** —— 测试用真实空闲端口，
而传给 `getConfig` 的却是原始的 `port: 0` 配置，于是立刻暴露。

---

### 3.7 两种传输，一份规则

| | HTTP | stdio |
|---|---|---|
| 怎么收 | `POST /` body | **stdin 逐行** |
| 怎么回 | HTTP 响应 | **stdout 逐行** |
| token 从哪来 | `x-heyta-token` / `Authorization` 头 | **环境变量 `HEYTA_LOCAL_API_TOKEN`** |
| 在哪 | `apps/node-host/src/local-api-server.ts` | `apps/node-host/src/mcp-stdio-server.ts` |

授权判定、工具过滤、受保护条目、写入路径 —— **一行都没有重写**，
因为它们在 `@heyta/local-api` 里。这正是 §3.6 分层表的目的：
**换一种传输不该让规则多一份实现。**

#### 3.7.1 🔴🔴 stdout 是协议专用的

stdio 传输最容易犯、也最难查的错：往 stdout 打一行日志。
MCP 客户端会把那行当成 JSON-RPC 去解析，然后**整条连接就废了** ——
而报错通常只说"协议错误"，不告诉你是哪一行。

所以 `mcp-stdio-server.ts` **绝不用 `console.log`**，所有诊断走 stderr。
有测试同时在两个层级钉住它：内存流层（4 条断言）与真实子进程层。

#### 3.7.2 token 在 stdio 上一样不能省

"是本机进程"不等于"是我授权的进程" —— 那正是 §3.3 的论点。
所以 stdio 也从环境变量取 token，且**每次请求现读**：
用户在设置里换了 token 应当立刻生效，而不是要重启子进程。

⚠️ token **只进环境变量**，不进命令行参数 —— 否则一次 `ps` 就能看到它。
与 ADR-0010 §3.6.1 的钥匙串是同一条理由。

### 3.8 🔴🔴 通知**不得**有响应（自己发给自己永远测不出来）

JSON-RPC 2.0 明确规定：**通知（没有 `id` 的请求）不得有响应**。

而 MCP 客户端在 `initialize` 之后**立刻**会发 `notifications/initialized`。

早先的实现写的是 `const id = request.id ?? null;` —— 于是通知会拿到一条
`-32601 Method not found`。**真实客户端会认为服务端违约。**

> ⚠️ 这是"自己发给自己"的测试**永远测不出来**的那类问题：
> 我写的所有 JSON-RPC 用例都带 `id`，所以从第一天起就是绿的。

修法：`LocalApiHandler` 的返回类型改成 `JsonRpcResponse | undefined`，
`undefined` 表示"这是通知，别回复"。
- stdio 壳：不写任何东西
- HTTP 壳：`202 Accepted` + 空 body（不是 `200` + 一条错误）

⚠️ 两个容易写错的边界：
- **`id: 0` 和 `id: ''` 都是合法 id**，不能被当成"没有 id"。有测试钉住。
- **未授权时的通知也是静默丢弃** —— 否则可以通过"响应差异"探测会话状态。

### 3.9 🔴 超长单行必须**真的关闭连接**，不能只丢缓冲

stdio 传输按行解析，单行上限 1 MB。超限时早先的写法是日志写
「连接将关闭」，然后**只把缓冲清空，并不关闭**。

两处都错：

1. **消息是假的** —— 它说关，实际没关。
2. **不关是危险的** —— 那一行的**剩余部分还会继续到达**，
   于是会被当成一条新消息解析。连接从此**失去同步**，后面全是
   JSON 解析错误。调用方看到的是"服务端在乱回错误"，
   而不是"我发的东西太长了"。

而且这里有安全含义：一个超长"单行"要么是客户端 bug，
要么是有人在试探内存上限。**两种都不该继续服务。**

### 3.10 🔴🔴 界面配的和服务的**不是同一份存储**（AI-5 的最后一公里）

设置面板**能**配本机 API：开关、token、逐个工具授权，全都有。
但它把配置存进 **浏览器的 `localStorage`**（`heyta.ai.settings`）。

而真正跑起来的 MCP 服务（`cli-mcp.js`）读的是
**`~/.heyta/local-api.json`**。

**在此之前没有任何代码写那个文件。**（实测：`grep` 全仓库，写入点为 0。）

于是：

> **在界面上把本机 API 配好，是一件没有效果的事。**
> 服务看不到那份配置。用户能配，但配了不生效，而且**不会有任何报错**。

两条存储各自都是对的 —— 缺的是把配置**落成服务能读的那份文件**。

#### 3.10.1 修法：`heyta-ai local-api init`

```
heyta-ai local-api init [--tools list_tasks,get_task] [--force]
heyta-ai local-api show
heyta-ai local-api off
```

`init` 生成 token、写 `~/.heyta/local-api.json`（**权限 0600**），
并打印 MCP 客户端要贴的那一段（token 走 `env`，不写进命令参数）。

四条安全约束，每条都有测试钉住 + 注入验证：

| 约束 | 为什么 |
|---|---|
| 文件 **0600** | token 是等价于"读走全部任务"的凭据 |
| `show` **永远打码** | `show` 会被贴进 issue/聊天记录/截图 |
| 已存在时**不覆盖** | 覆盖会换 token，已配好的客户端**立刻失效**且原因不明显 |
| `bindAddress` **只取回环** | 从参数读 = 能把用户全部任务暴露给整个局域网 |

⚠️ 覆盖时**必须显式 `chmod`**：`writeFileSync` 的 `mode` 只在**创建**时生效，
否则"改过一次再 init"会留下一个权限宽松的旧文件。这条有专门的测试。

#### 3.10.2 这一条是**端到端**验证的，不是单元验证

只测"文件写对了"不够 —— 要证明**服务真的吃它**。
`cli-local-api.spec.ts` 里真的 `spawn` `dist/cli-mcp.js`，喂
`initialize` + `tools/list`，断言：

- 服务起得来，`serverInfo.name === 'heyta'`
- 列出的工具**恰好**是授权的那些（默认只有 `list_tasks`）
- 换一个 token 会被拒
- `enabled: false` 时服务拒绝启动

### 3.11 配置面板必须说清"配在哪里才生效"

§3.10 修好了"没人写配置文件"，但**界面本身的误导还在**：
设置面板里的本机 API 区块读起来像是"我在这里打开，它就生效了"。

在这份诚实说明补上之前，用户看到的是一个**没有效果的开关**：
改了不会有任何反应，**也不会有任何报错**。

> 一个不会生效、也不会报错的开关，比"没有这个开关"更糟 ——
> 它消耗用户的信任，并且让用户以为自己已经配置好了。

所以面板上现在明写：

- 这些设置只存在**浏览器**里
- 真正生效的是 `~/.heyta/local-api.json`
- 用 `heyta-ai local-api init` 生成
- 两边**不会自动同步**

⚠️ 刻意**没有**做"一键把浏览器里的配置写成文件" ——
浏览器写不了 `~/.heyta/`，而且那会变成第三份配置真相。
**指路比伪造能力诚实。**

顺带：这段文案第一次写的时候被 `check:ui-language` 挡住了 ——
`<code>` 里只有 ASCII，门禁要求用户可见文案必须有中文。
**门禁在这里是对的**：它逼我把「文件」「命令」这两个中文前缀写出来，
而那恰好让这段说明对不懂技术的用户也可读。

### 3.12 🔴🔴 Bear 范式在**真实产品里是死的**（fail-open 的默认值）

要求写的是「加密条目可列举但不可读（Bear 范式）」。
机制、契约、单元测试**全都在**：`taskToItem(task, readable)` 会在
`readable === false` 时剥掉全部正文类字段。

但它**从来没有在产品里执行过**。原因是一行：

```ts
const isReadable = options.isReadable ?? (() => true);
```

`createLocalApiHost` 的这个缺省值意味着：**壳不传 = 一切都可读**。
而全仓库唯一的真实调用点（`cli-mcp.ts`）**从来没传过它**。

> 于是"可列举但不可读"这条隐私特性，在真实运行的程序里
> `readable` 恒为 `true`，**永不触发**，且没有任何地方提示这件事。

单元测试是绿的 —— 因为测试自己传了 `isReadable`。
它们证明的是**机制**成立，不是**接线**存在。

#### 修法：这一侧不允许静默

`isReadable` 改为**必填**，`options` 参数也改为必填。
壳必须**显式回答**"哪些条目读不出来"，答不出来就**编译不过**。

`cli-mcp.ts` 现在显式写 `isReadable: () => true`，并注明：
这是**产品现状**（还没有"受保护条目"这个概念，ADR-0011 §6.1），
不是实现细节 —— 将来改的就是这一行。

> **一个隐私相关的开关，不允许静默地失败在 "open" 那一侧。**
> 这与 ADR-0010 §3.2 的"闸门失败必须往更严的方向走"是同一条原则，
> 只是这次的闸门伪装成了"默认参数"。

⚠️ 一个容易看漏的细节：`getTask('不存在的 id')` **不会**调用 `isReadable`
（找不到的条目不涉及可读性）。这是对的，但写测试时容易误判成漏网。

### 3.13 🔴 写入路径此前**从未在真实二进制上跑过**

本文件 §3.10 之后，`tools/call` 在端到端里只跑过**空库上的只读工具**
（`BASE_CONFIG` 只授权 `list_tasks` / `get_task`）。

也就是说「写入必须经 `dispatch()`」这条核心约束，此前只在单元层被证明过 ——
而单元层证明的是**端口长得像 dispatch**，不是**真的写进去了**。

现在用**两个进程**证明：A 进程 `create_task`，B 进程 `list_tasks` 读到。
跨进程 = 真的落到了库里，而不是留在内存里。

顺带覆盖：未授权的写工具**拒绝且无副作用**（光断言"报错了"不够，
还要证明**真的没写进去**）、token 错时写请求被拒、缺必填参数回 `invalidParams`。

#### ⚠️ 注入验证本身踩的坑（值得记下来）

第一次注入"让写工具只回成功、不 submit"，测试**全绿** —— 看起来像是
"我的测试没抓住"。**实际是注入没生效**：
`@heyta/local-api` 在 node-host 里是 **external** 依赖，
运行时从 `packages/local-api/dist` 加载，所以**只重建 node-host 不够**。

> **这个端到端测试的注入面横跨两个构建产物。**
> 只重建一个包，注入就是空转，而结果会伪装成"测试没抓住 bug"。

重建 `local-api` + `node-host` 之后，注入正确地让跨进程用例变红。

## 4. 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 把本机 API 放进 `packages/ai` | 方向相反，会让两个不同的开关在类型层面混用（§2） |
| 默认开启工具 | 任何本机程序都能读走全部任务；Joplin 全默认关是正确形状 |
| 只做总开关，不做逐工具授权 | 用户无法"允许列任务、不允许读备注" |
| 监听 `0.0.0.0` 让局域网也能用 | 那是把"本机 API"变成"局域网 API"，而用户会以为它是本机的 |
| 不用 token（"反正是本机"） | 本机有几十个程序在跑，这是最常见的误解 |
| 用黑名单删敏感字段 | 永远漏掉将来新增的字段（§3.4） |
| `get_task` 对受保护条目返回空 | 调用方会以为读成功了 |
| 本机工具直接改状态 / 自拼 op | 绕过向量时钟、幂等、冲突检测（§3.5） |
| 本包内实现 HTTP 服务 | 违反 ADR-0003；且授权规则会随平台分裂成多份 |
| 把 `validateLocalApiConfig` 当鉴权前置 | 端口会参与鉴权，报错还指向"未启用"（§3.6.1） |
| 让 `apps/node-host` 自己翻译写入意图 | 日期与时区语义会随平台分裂（已发生过两次漂移） |
| 用 query 参数传 token（`?token=`） | 会进访问日志、shell 历史、Referer |
| 非法配置下"警告并继续监听" | 用户以为自己开的是"本机 API"，实际是局域网 API（§3.2） |

## 5. 后果

### 正面

- **唯一一个别人给不了的能力**（ADR-0006 §3.3）。
- 同时解决 ADR-0005 记下的最大代价：**零配置就有 AI 入口**。
- 授权规则只有一份实现。`@heyta/local-api` 73 条 + 适配器 26 条 + HTTP 壳 20 条测试，
  其中 **8 条承重断言已注入验证能失败**。
- 类型上：本包造不出 op、也造不出"读取受保护内容"的路径。

### 负面 / 需要接受的成本

- 🔴 **"可列举不可读"需要一个产品前置条件**：heyta 目前**没有"受保护条目"这个概念**。
  本 ADR 定义的是**契约**；`readable` 现在只能靠壳按"解密失败"来置位。
  要做完整的"用户手动标记为受保护"，需要一次**产品决策**（是否加该字段、
  加在哪一层、要不要同步）—— **本 ADR 不替它决定**。
- ✅ **协议层与两种传输层都已落地**：`createLocalApiHandler`（与传输无关）
  + `local-api-server.ts`（HTTP 壳）+ `mcp-stdio-server.ts`（stdio 壳，§3.7）。
  两种传输**共用同一份授权与工具规则**，没有第二份实现。
- ⚠️ **仍未用真实 MCP 客户端跑过**。`mcp-stdio-e2e.spec.ts` 真的 spawn 了子进程
  并用管道说 JSON-RPC，但没有握手协商、没有真实客户端的容错行为。
  这是没有客户端时能补上的最接近的一层。
  ⚠️ 但它已经**抓到一个真实客户端会撞上的违约**（§3.8 的通知）。
  这说明"照着规范自查握手序列"确实能替代一部分真实客户端验证。
- ⚠️ **"受保护条目"仍只有契约没有产品机制**（见上）。
- ⚠️ **没有任何真实 MCP 客户端端到端跑过**。测试都是自己发的 JSON-RPC，
  形状对了，但"Claude Desktop 真的能连上吗"还没被证明过。
- 工具目录只有 6 个，**第一批用户就可能不够用**（例如没有标签、
  没有搜索、没有批量完成）。倾向"将来加"而不是"现在多写"。
- ⚠️ **token 存哪**与 [ADR-0010](0010-ai-config-routing.md) §6.1 是同一问题：
  本机偏好、**不进 op-log**、不参与同步。仍未定案。

### 需要靠门禁兜住的

- ✅ 35 条测试。三条承重（均已注入验证）：
  1. 受保护条目正文必须消失（含"未来新字段默认不暴露"）
  2. 身份检查在工具检查之前（否则可枚举工具）
  3. IPv4 非回环必须拒绝
- ✅ 写入路径已接：`packages/app-host/src/local-api-host.ts` 只调 `TaskActions`，
  而 `TaskActions` 内部走 `dispatch`。有测试断言"写入真的产出了 op"（注入验证过）。
- ⏳ **尚未落地**：`check:layering` 还没有"`apps/*` 不得绕过 `LocalApiWritePort` 直接改状态"
  这条规则。现在 `apps/node-host` 里确实没有直接改状态的地方，所以这条规则
  仍然是在规定一个不存在的违规 —— 等有真实调用点再加。
- ⏳ `packages/local-api` 尚未登记进 `AGENTS.md` §2 仓库地图
  （仓库规则不允许单方面改 AGENTS.md 的规则章节）。

## 6. 未决事项

1. 🔴 **"受保护条目"的产品形态**（见 §5）。这是本 ADR 唯一的**真空白**：
   契约已定，但**没有产生 `readable: false` 的产品机制**。
2. ~~**token 的存储与轮换**~~ ✅ **已定**：`local-api init` 生成（32 字节随机），
   存 `~/.heyta/local-api.json`（0600），`--force` 重新生成。
   **多 token 仍不做** —— 本机场景下它只会让"哪个程序有权限"更难说清。
3. ~~**协议层**：MCP 用 stdio 还是 HTTP？~~ ✅ **已定**：两种传输都实现
   （`local-api-server.ts` HTTP + `mcp-stdio-server.ts` stdio），
   **共用同一份授权与工具规则**。协议用 JSON-RPC 2.0，工具 schema 见 `mcp.ts`。
4. **只读模式**：是否可以只开读、完全不开写？（当前 `grants` 已能表达，但没有 UI 引导）
5. **审计**：本机工具读写了什么，用户能不能事后看到？
   （考虑过"记录每次调用"，但那本身是一份新的敏感日志 —— 需要先想清楚它自己怎么受保护。）
