# ADR-0008：向量时钟上限从 20 提到 100 —— 把墙挪远，**不假装拆掉**

> 状态：**已被 [ADR-0046](0046-lossless-vector-clock-frontiers.md) 取代**
> 日期：2026-09-26
> 取代：无（修改了 vendored 的 `packages/sync-core` 的一个默认值，未取代任何 ADR）

## 1. 背景与约束

### 现象：一个会随运行次数漂移的验收台架

`pnpm verify:mobile-conflict` 有一轮开始**必红**，报的是第 5 步"**手机没有报冲突**" ——
看起来像手机的锅。查下去发现手机没错、笔记本也没错，**错的是这个测试账号的历史**。

证据链（全部实测）：

| 位置 | 观察到的事实 |
|---|---|
| 服务端 | 该实体只有手机的 `CRT`(seq 41) 与 `UPD`(seq 42)；笔记本那个 client **一条 op 都没有** |
| 笔记本本地 | 改名 op 在，但 `uploadStatus=pending`、`serverSeq=None` |
| 笔记本 CLI | `sync` → `{ok:false, kind:'conflict', errorCode:'CONFLICT_CONCURRENT'}`，附 `existingClock` |
| 逐键对比 | 本地时钟与服务端 `existingClock` 各 20 键，**只差一个键**：`muh8hc5b-1-buuvk168: 1`（服务端 seq 1） |
| 本地完整性 | 那条 op **在**本地库里（`seq=1`，本地 seq 1..43 **无缺口**） |

所以**不是下载漏了，是并入时钟时被裁掉了**。

### 根因比"上限太小"更深一层

`packages/sync-core/src/vector-clock.ts` 的 `MAX_VECTOR_CLOCK_SIZE = 20`，
`limitVectorClockSize` 超出就丢弃条目，保留自己的 `clientId` 与计数最高的那些。

🔴 **关键在于服务端的 head 自己也被裁到同一个上限，而两边决定"保留哪些条目"的规则并不一样：**

| | 保留策略 |
|---|---|
| 服务端存储时 | `limitVectorClockSize(op.vectorClock, [op.clientId, ...protectedIds])` —— 保护**自己 + head 已知的那些** |
| 客户端派发时 | `limitVectorClockSize(clock, [this.options.clientId])` —— **只保护自己** |

于是只要真实时钟超过上限，两边就可能对**同一份因果事实**得出不同结论：
客户端少一个 head 里有的键 → 它的时钟不再支配 head → 服务端把该设备写的**每一条** op
判成 `CONFLICT_CONCURRENT` 并**永久拒绝**。

**"客户端与服务端各自裁剪"这个形状本身就是错的；永久拒绝是它的必然后果，不是偶发。**

### 为什么以前绿、现在必红

不是代码退步，是这个账号**每跑一轮就多 2 个 `clientId`**（手机装一次包、笔记本建一次库），
第 11 轮越过 20。**一个会随运行次数漂移的验收台架本身就是缺陷。**

### 硬约束

- `packages/sync-core/` 是 **vendored**（AGENTS.md §2），改动必须同步更新 `PROVENANCE.md`。
- 这是**协议级常量**，服务端从它派生 `MAX_SANITIZE_VECTOR_CLOCK_SIZE = ceil(MAX × 2.5)`。
- AGENTS.md §8"不要擅自做的事"：**不在线协议上做"顺手改一下"**。
- 上游注释写着"用户要有 21 个以上不同 clientId 才会触发裁剪，极不可能" ——
  那是**假设**，heyta 的零 mock E2E 证明它可达。

## 2. 选项

| 选项 | 优点 | 缺点 | 关键证据 / 代价 |
|---|---|---|---|
| **A. 调大 `MAX_VECTOR_CLOCK_SIZE`** | 一行改动；客户端与服务端**自动保持同一常量**；语义不变、向后兼容（短时钟行为完全一样）；服务端 sanitize 派生值随之放宽 | **只是把墙挪远，不是拆掉**；最坏情况时钟变大 | 20 → 100：墙从"21 个 clientId"挪到"101 个"；最坏 ~100 条 ≈ 1.6 KB（6 字符 id） |
| **B. 让裁剪因果安全**（绝不裁掉 head 已含的键） | 真正对齐两边 | 客户端**派发时根本不知道 head**；要知道就得在派发前多一轮往返或读本地实体历史 —— 属于协议语义变更 | 需要改 `engine.ts` 的时钟构造，让它变成**实体感知**的 |
| **C. 按时间淘汰最老的 client** | 时钟有界且可解释 | 需要写下"超过 N 个设备时会丢什么"；且**淘汰的可能是因果上仍然必需的那一项** —— 与本故障同形 | 没有现成的可靠证据支撑一个阈值 |
| **D. 完全取消上限（无界时钟）** | 因果上**唯一正确**的解 | 服务端 `sanitizeVectorClock` 的 DoS 防护、存储裁剪、full-state op 路径**全都围绕 MAX 设计**；改成无界 = 一次真正的协议改造 | 爆炸半径远大于收益：100 已经比个人应用的现实设备数高一个数量级 |

## 3. 结论

**选 A，并把"看得见"补上。**

- `MAX_VECTOR_CLOCK_SIZE`：**20 → 100**。理由不是"20 有点紧"，而是**实测证明 20 会致命**，
  而 100 对个人任务应用实际不可达（一次安装 / 一个浏览器会话才 +1）。
- `limitVectorClockSize` 在**真的发生裁剪时打一条 `console.warn`**，带上实际条数与上限。
  **上一次这个故障最毒的地方是它完全静默**：客户端只报"同步不上"、服务端只报
  `CONFLICT_CONCURRENT`，没有任何一层说"你的时钟被裁掉了一项"，排查方向因此被带到
  同步协议上去。这条 warning 是这个已知限制**唯一的出口信号**。

**为什么不选看起来更"正确"的 B/D**：它们都对，但都是**协议语义变更**，
而这次事故的紧迫性是"某台设备写入被永久拒绝"。用一次协议的谨慎改造去换一个
一行的、可回滚的、向后兼容的改动，代价不成比例。
B/D 不是被否决，是**被排到后面** —— 见 §5。

## 4. 后果

1. **限制仍在，只是离得更远。** 超过 100 个 clientId 时故障形状**逐字不变**。
   `packages/op-log/tests/vector-clock-trim.spec.ts` 同时钉住两件事：
   ① 旧故障场景（21 个 client）现在**不再触发裁剪**（回归守卫）；
   ② 到 101 个时**照样**削掉一项、照样判并发（**不假装问题已解决**）。
   任何改动裁剪策略的人都会在这里红，红的时候必须读那段注释和本 ADR。
2. **warning 是唯一出口。** 真实用户环境若出现这条日志，说明这个上限已经不够用了 ——
   那时才该去付 B 或 D 的代价。
3. **`packages/sync-core` 的边界行为变了**，已按 AGENTS.md §2 更新 `PROVENANCE.md`。
4. **边界测试不许写死条目数。** 修改过程中发现 `packages/sync-core/tests/vector-clock.spec.ts`
   有 6 条测试用**写死的 20/21/25/35** 构造"超过上限"的时钟 —— 上限一改，它们**不再超限、
   裁剪不再发生**，但断言仍然"通过"。也就是说它们变成了**静默失效空转的测试**。
   已全部改成跟着 `MAX_VECTOR_CLOCK_SIZE` 走，并补了"输入确实超限"的前提断言。
   **这比这个常量本身更值得记：写死数字的边界测试会在常量变动时悄悄停止测试任何东西。**
5. 服务端的 `MAX_SANITIZE_VECTOR_CLOCK_SIZE` 由 `ceil(MAX × 2.5)` 派生，随之为 **250**。
   这是**有意的**：它继续比存储上限宽，从而保留"冲突解决期间时钟可以临时超限"的余量。

## 5. 当时的未核实项（历史记录）

- ⚠️ **旧账号的存量数据未处置。** 已经累积到 20+ clientId 的账号，其**磁盘上已裁剪过**的
  时钟不会因为改了常量而**自动长回来** —— 它丢掉的键已经不在本地了。
  理论上该账号的下一次成功同步会把 `existingClock` 合并回来，但
  **我没有实测过存量受害账号能否自愈**。若不能，它们需要人工干预。
- ⚠️ **没有实测 100 与 101 之间在真实同步链路（HTTP + 服务端 + Postgres）上的端到端行为**，
  只有单元层面的钉子。现有的 `pnpm verify:mobile-conflict` 用的是每轮新建账号、client 数远低于上限。
- ⚠️ **最坏情况下时钟体积的真实增幅未测**（估值 ~1.6 KB/op 是按 6 字符 id 手算的，
  没有实测 op 载荷大小的分布）。
- ⚠️ **`console.warn` 在 Hermes 上的可见性未验证** —— 它在 Android/iOS 上是否真能被
  `adb logcat` / 模拟器日志捞到，**没有测**。这条 warning 的价值完全取决于它可见。
- 因果安全的裁剪（选项 B）**没有做**。本 ADR 不声称问题已解决。

## 6. 2026-10-03 后续结论

本节更新当前状态，前五节保留当时的决策依据。

| 原未结项 | 当前结论与证据 |
| --- | --- |
| 已裁剪设备能否恢复 | 真实 P1 构造受损设备，从保留的完整历史/版本化 REPAIR 恢复 101 维前沿，重启后新写入被服务端接受；独立 observedClock 持久化不依赖可丢弃缓存。已不可逆丢失且没有其他副本的维度不能伪造恢复；旧拒绝 op 也不改写。 |
| HTTP/PostgreSQL 100/101 | 已实测；当前生产完整保存 101 维，另验证 4096 接受、4097 显式拒绝。见 A1 历史证据及 A2 当前协议证据。 |
| 时钟体积 | `research/tools/measure-vector-clock-a1.mjs` 给出多种 ID 长度下的 JSON 字节实测，替代单一手算估值。 |
| Hermes warning | `pnpm verify:mobile-aed` 在 Android 真 Hermes + op-sqlite 中验证库 warning 确实进入 logcat；同时验证 101 维持久恢复和 checkpoint 增量水合。这不是 iOS 日志验证。 |
| 因果安全压缩 | 生产路径取消 top-K，改用协商后的签名前沿 delta；只有原时钟支配前沿时才可省略相等分量，接收端精确展开。原始日志仍保存完整时钟。 |
