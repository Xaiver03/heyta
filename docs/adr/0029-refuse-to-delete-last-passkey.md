# ADR-0029：账号上最后一条通行密钥**不允许**被自助删除 —— 宁可拒绝，也不让用户把自己锁在门外

> 状态：**已接受**（取舍不变；**判据**于 2026-10-01 被
> [ADR-0041](0041-last-passkey-guard-keys-on-any-usable-entry.md) 修订 ——
> 从"是不是最后一条"改成"账号还有没有能用的入口"，因为邮箱 + 口令登录之后
> 这两件事不再等价。§3 那段代码里的谓词形状因此已经过期，见该 ADR §4。）
> 日期：2026-09-28
> 取代：无

## 1. 背景与约束

2026-09-28 之前，用户对自己账号上的通行密钥**没有任何可见性，也没有删除入口**：
服务端只有注册 / 登录 / 恢复三条路径，全都不返回"你名下有哪些凭据"。
一条在旧设备上注册、后来再也没用过的凭据，用户**无从清理**。

于是加了两个端点：`GET /api/passkeys`（列出自己的凭据）与 `DELETE /api/passkeys/:id`。
本节剩下的问题是：**删到只剩最后一条时，要不要拦？**

硬约束（决定了结论的是这几条，不是"哪个更好用"）：

1. **通行密钥可能是这个账号唯一的登录方式。** `User.passwordHash` 可空；浏览器端
   `AuthPanel` 提供的是通行密钥与邮箱魔法链接两条路，但**魔法链接依赖邮件可达**
   （自建实例上 SMTP 未必配好；本项目自己的生产实例就经历过 SMTP 从零配置）。
   也就是说，"删掉最后一条凭据后还能靠别的路进来"**不是一个可以假定的前提**。
2. **通行密钥的恢复路径是"再发一封邮件"，不是"验证身份"。**
   `POST /api/recover/passkey` 只要求提供一个邮箱地址，且响应是**中性的**
   （"如果这个邮箱存在，我们已经发了链接"——不泄露邮箱是否存在）。
   这意味着恢复通道的强度**不超过邮箱访问权**，而邮箱本身就是覆盖账号的手段。
3. 删除动作**必须是原子的**。本项目已经有过一次教训：跨会话的读-改-写会造出
   静默的数据丢失（见 `docs/plans/roadmap.md` 的同步游标条目）。"先查还剩几条、再删"
   这种形状在**两个标签页同时操作**时会让账号一条都不剩。

## 2. 选项

| 选项 | 优点 | 缺点 | 关键证据 |
|---|---|---|---|
| **A. 允许删到零**，之后靠恢复流程 | 实现最简；管理员/用户完全自主 | 用户点两下就可能把自己锁在门外；而恢复通道强度只等于邮箱访问权 —— 等于把"账号能否进入"降级成"邮箱能否进入"，且用户**不会预期**到这一点 | 恢复端点只凭邮箱地址发信，响应中性（`postmaster@finlaw.cloud` 实测投递失败过一次，见 `AGENTS.md` §7 陷阱 81） |
| **B. 允许删到零，但二次确认里写清楚** | 不挡用户；文案负责告知 | 确认文案**挡不住**已经下定决心清理旧设备的用户；而这恰恰是最可能触发它的场景（"我换手机了，把旧的删掉"） | 空状态与 409 文案已经证明"告知"不等于"可行动"（见 §4） |
| **C. 删到只剩一条时拒绝（409）**，要求先添加新的一条 | 代价是**一次额外操作**；把不可逆的自我锁定变成"先加后删"的自然顺序 | 需要**存在一条能用的"添加"通路** —— 而这条通路当时是坏的（见 §4 的发现） | 本 ADR 的结论；`deleteUserPasskey` 的原子谓词 |
| D. 完全不给删除入口 | 最安全 | 用户无法清理泄露/丢失设备上的凭据 —— 那是**真实且更紧迫**的安全需求 | 条目的出发点就是"没有删除入口" |

**否决 A 与 B 的核心理由**：它们都把"账号可进入性"的最终保障寄托在
**用户对一条文案的阅读**上，而这个操作发生在用户**正处于"整理/丢弃旧设备"的心理状态**时——
那是最不会细读文案的时刻。C 把这个决定从"用户有没有读懂"改成"系统结构上不可能发生"。

## 3. 结论

**选了 C**：`DELETE /api/passkeys/:id` 在删到只剩最后一条时返回 **409**
`code: 'last_passkey_required'`，并明确说明"先添加一条新的"。

实现上有一条**不是风格问题、而是正确性问题**的细节：这个判断写在 `deleteMany` 的
**谓词里**，而不是先查后删：

```ts
const deleted = await tx.passkey.deleteMany({
  where: {
    id: passkeyId,
    userId,
    // 只有该用户名下还存在**另一条**凭据时才允许命中这一行。
    user: { passkeys: { some: { id: { not: passkeyId } } } },
  },
});
```

它是**唯一的 TOCTOU 防护**：没有它，两个标签页各自删一条会让账号**一条都不剩**。
"没删掉"之后才去 `findFirst` 区分 409（是你的最后一条）与 404（不是你的/不存在）——
那次查询**只用来选错误码**，仍然限定在 `userId` 范围内，所以别人的 id 同样查不到，
两种失败因此**不可区分**。

## 4. 后果

- **"先添加一条"必须真的可行。** 写下这条文案的时候，**它其实是不可行的**，
  而且比"没有入口"更糟：邮箱注册路径 `verifyRegistration` 在
  `existingUser.isVerified === 1` 时**直接返回成功消息、却一条凭据都不写**
  （`server/src/passkey.ts`，防账号枚举的**有意**设计，`excludeCredentials: []` 同源）。
  一个照做的用户会看到"注册成功"、以为加上了、删掉旧的那条，然后**再也进不去**。
  ⇒ 本 ADR 的结论**依赖**一条**已认证的**"给当前账号再添一条凭据"通路。
  在该通路真正落地之前，这条 409 文案是**有害的**：它指挥用户去做一件会静默失败的事。
- 因此需要（并正在落地）一条已认证的添加通路：协议语义属于
  `packages/app-host/src/hosted-auth.ts`，UI 属于
  `apps/web/src/features/settings/PasskeyPanel.tsx`。
  ⚠️ **本 ADR 有意不描述该端点的形状**（路由名、参数、排除哪些凭据）——
  那是实现细节，会变；这里只钉住**它必须存在、且必须真的写入**这一条约束。
  在它落地之前，**不要**把 409 文案当成"用户能自己解决"的提示。
- **代价被限制在一次额外操作**：用户想换设备时的正确顺序是"新设备先注册 → 再删旧的"，
  这本来就是更安全的顺序。
- **没有做改名**：`Passkey` 表没有 `name` 列，加一列需要一次数据库迁移。
  本 ADR **不**为它背书，也**没有**为此造一个假名字段。
- 列表接口**不返回** `credentialId` / `publicKey`：因此界面只能显示
  `createdAt` / `lastUsedAt`。**这是有意的取舍** —— 代价是"哪条是哪条"只能靠时间推断，
  换来的是凭据 id 不出现在任何响应体里（测试断言响应键集合恰好是
  `createdAt / id / lastUsedAt`）。

## 5. 未核实项

- **没有在真硬件/真系统认证器上验证。** 全部自动化验证用的是**虚拟认证器**。
- **没有验证"用户被锁在外面的真实发生率"** —— 本 ADR 是一个**预防性**决定，
  不是因为观察到了这个故障。它的正当性来自 §1 的约束推导，不是来自数据。
- **多实例部署下 WebAuthn challenge 存内存**，所以跨实例的注册/登录可能失败；
  这与本 ADR 无关，但会让上面的"添加"通路在多实例下不可靠。
