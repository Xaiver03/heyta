## 1. 为什么需要这份 ADR

对标滴答清单的单任务界面时，它任务行菜单上的四项在我们这里**根本不存在**
（逐项对账见工单 §2）：置顶、放弃、分享（单条任务）、附件。
其中三项不是"加个按钮"，而是**会长期改变数据形状与对外承诺**的决定，
而仓库里已有的裁决恰好管着它们：

| 要做的事 | 撞上的既有裁决 | 冲突点 |
|---|---|---|
| 放弃 | [ADR-0048](0048-deletion-four-states-and-the-no-physical-erase-boundary.md) §2 | 它把任务生命周期钉成**四个**互相独立的状态。加第五态 = 改它的结论，按 AGENTS.md「不改已接受的 ADR 的结论，要变更就新写一份」 |
| 放弃的"隐藏" | 同 ADR 的 **I5**：「隐藏由层负责，不由调用点负责」 | 0048 用四条实测缺陷（D1/D8/D9/D11）证明：把"要不要显示"留在调用方手里，**必然**出现"同一件事两端不同答案，且都不报错" |
| 置顶 | `packages/domain/src/entities.ts:698-702` 与 `notes.ts` 文件头 | 已有明文规则：**一个字段同时就是"排在最前"**，不许另设 `isPinned` / `sortOrder`（两个字段必然在一次编辑里漂移） |
| 单条任务分享 | [ADR-0081](0081-encryption-is-opt-in-not-default.md) | 加密是**用户显式开启**的整库档位 ⇒ 任何"把内容交给服务端渲染"的功能，在开了 E2EE 的账号上行为不同 |

这四项里最贵的是**放弃**。它看起来是个字段，实际是给状态机加一格，
而加错形状的后果 0048 已经替我们付过一次学费。

## 2. 选项

### 2.1 「放弃」怎么表达

| 选项 | 优点 | 缺点 | 关键证据 |
|---|---|---|---|
| **A. 复用 `completedAt`，界面上叫"放弃"** | 零 schema 变更 | 撒谎。放弃的任务不该进"已完成"统计、不该算完成率、不该被重复任务推进到下一周期 | 完成语义由 `setCompleted` 与重复顺延共用（`packages/app-host/src/actions.ts:331-348`） |
| **B. 复用 `deletedAt`（进回收站）** | 零 schema 变更 | 后果不可接受：回收站里的任务会被"彻底删除"这条链走下去，而放弃的人并不想丢数据；且回收站有还原入口，语义与"我不做了但留着"不同 | ADR-0048 §2 的四态表 |
| **C. 新可选字段 `abandonedAt`，隐藏归**动作层的 list 分裂**** | 与 `Project.archived` 同一条已验证的形状（W9：`listProjects()` 不含归档 + `listArchivedProjects()` 只含归档）；不 bump schema；可逆 | 多一个态，所有 TASK 读路径都要检查自己是不是走的是分裂后的出口 | `packages/domain/src/search.ts` 的 `aliveTasks` 内部过滤（A1 已落）是同一形状的领域层版本 |
| **D. 新字段，但由各宿主自己 filter** | 最快 | 🔴 **正是 I5 点名的失效形状**。实测过：`archived` 的过滤当时只住在共享 UI（`packages/ui/src/projects/model.ts:107`），于是归档清单对 AI / MCP / CLI 全可见 | ADR-0048 §1 表格第三行 |

### 2.2 单条任务怎么分享

| 选项 | 优点 | 缺点 |
|---|---|---|
| **A. 公开只读链接**（服务端渲染） | 与滴答一致 | 🔴 可行性取决于对端账号的加密档位：默认 `readable` 的账号能做，开了 E2EE 的账号服务端读不到明文，只能把密钥塞进 URL fragment —— 那是一个**新的密钥分发面**，且链接一旦转发就无法撤销。同一功能两档不同答案，是 0048 表格里"两端不同答案"的形状 |
| **B. 发送到共享清单**（成员制） | 复用已落地的 share op-log 与 role 硬门（`server/src/shares/share.membership.ts`）；撤销 = 移出成员，语义现成 | 不是"发给任意一个人一个链接"，接收方要先在共享空间里 |
| **C. 复制到剪贴板（纯文本）** | 零风险 | 不算分享，且我们已有的是"导出"而不是它 |

### 2.3 附件的加密口径

| 选项 | 结论 |
|---|---|
| A. 附件一律端到端加密 | 🔴 违反 [ADR-0081](0081-encryption-is-opt-in-not-default.md)：加密不再是默认，也不该给某一类数据单独加档 |
| B. 附件一律明文 | 🔴 违反 ADR-0081 的另一半：开启 E2EE 的账号，整库都要跟着转密文，不能有例外 |
| **C. 跟随用户的整库档位** | ✅ 与任务正文同一条通道、同一次整库迁移覆盖，不新增"按钥匙取密文"的形态 |

## 3. 结论

### 3.1 「放弃」是任务的第五个独立状态，隐藏由**动作层**负责

```
   alive ──abandon──► abandoned ──unabandon──► alive
      │                                          ▲
      ├──complete──► completed ──取消勾选─────────┤
      │                                          │
      └──delete───► trashed ──purge──► purged    │
                     │                           │
                     └──── restore ──────────────┘
```

1. 字段是 `Task.abandonedAt?: number`（可选 + 运行时默认，**不 bump `CURRENT_SCHEMA_VERSION`**，
   依据 `packages/domain/src/subtasks.ts:592-602` 那条"加可选字段不用 bump"的实测论证）。
   清除写 `null`，reducer 翻成删除字段。
2. 🔴 **隐藏归动作层的 list 分裂**，照 `Project.archived` 的 W9 形状：
   默认出口不含已放弃，另给一个只含已放弃的出口。领域层的 `aliveTasks` 一类谓词
   **不**把"已放弃"算成"不存活"—— 它没进回收站，统计与恢复都要看得见它。
   判据与 0048 I5 同一条：**把原始任务表整个递给宿主，也不得出现已放弃的任务**。
3. 放弃与完成**互不推导**：放弃不写 `completedAt`，不计入完成率，
   不被重复任务的"完成即推进"顺移到下一周期。
4. 恢复 = `UPD { abandonedAt: null }`，回到 alive，不经过回收站。

### 3.2 置顶只有一个字段

`Task.pinnedAt?: number`，它**同时**是"排在最前"。不设 `isPinned`、不设 `sortOrder`。
先例是 `CountdownEvent.pinnedAt`（`entities.ts:702`）与 `Note.isPinnedToToday`。
排序里置顶的优先级高于既有排序键，但**只作用于同一分组内部** ——
把一条置顶任务从"明天"拽到"今天"是错的，那是排程语义，不是注意力语义。

### 3.3 单条任务分享走成员制，公开只读链**不在本轮**

选 **2.2 B**。公开链接要先回答"开了 E2EE 的账号怎么办"与"转发出去怎么撤销"两问，
那是一次独立的密钥分发设计，另立 ADR，不在本轮顺手做。
本轮界面上一律说「发送到共享清单」，**不许**写「分享链接」——那是对没做的功能的承诺。

### 3.4 附件跟随整库档位

新实体 `ATTACHMENT` 按 [REMINDER 的物化模板](../plans/site-and-parity-alignment.md)落地
（`ENTITY_TYPES` → `BUCKET_BY_ENTITY` → `EntityModelMap` → 写路径 → `ACTION_FAMILIES` 登记）。
字节走服务端 blob 通道，计量复用既有 `storageQuotaBytes` / `payloadBytes`。
加密口径按 §2.3 C。

## 4. 后果

1. **五个态而不是四个**，所有"这条任务算不算存在"的判断都要重新问一遍自己指的是哪一态。
   这是本 ADR 的主要成本，也是它必须落字的原因。
2. I5 的形状多一处要守：新增任何 TASK 列表出口（含 AI 工具、MCP、CLI、导出、搜索）
   都必须走动作层的分裂出口，不许直接吃物化状态里的原始 `tasks` 表。
   判据：把原始表整个递进去也不得出现已放弃任务 —— 这条要能红。
3. 「已放弃」需要一个用户看得见的出口，否则它是**只进不出**的抽屉。
   本轮同时交付出口（回收站旁边那一档），不做"放弃了但只能靠改数据找回"。
4. 公开只读链接这个决定**让后面更难做**：一旦有了成员制的任务分享，
   再引入公开链就要同时解释两种分享的区别。这是有意的取舍。
5. 附件进 `EntityModelMap` 那天，`check:ai-coverage` 的分母 +1，
   要么同批补读写工具，要么登记 `ENTITY_COVERAGE_DEBT`（`entity-types.ts` 里 COMMENT 那条已写明）。

## 5. 未核实项

1. **重复任务 × 放弃**：一条 `repeatRule` 的任务被放弃后，调度器会不会仍然生成下一周期？
   本轮按"不会"实现（放弃即停止推进），但这条**没有实测**，要有一条能红的用例。
2. **共享清单里的放弃**：成员 A 放弃一条共享任务，成员 B 的默认视图该不该看见它？
   本轮按"与个人任务同一条规则"实现，但共享场景的口径没人拍过。
3. **`abandonedAt` 与提醒投递**：已放弃任务的提醒要不要继续投递？
   0048 的 D1 记录过"已软删任务的提醒仍会投递"这个真实缺陷，本轮**只处理了软删那一支**，
   放弃这一支的投递行为要在验收时量一次，不许照抄"应该也滤掉了"。
4. **附件的配额与单文件大小上限**：`storageQuotaBytes` 是账号级总量，
   单文件上限与 MIME 白名单本轮取值是照头像那条先例定的，**不是**产品研究结论。
