# ADR-0005：AI 能力的数据路径 = 客户端内 + 用户自有推理端点

- **状态**：已接受（2026-09-26 确认；云端 AI 部分见 ADR-0006 / ADR-0013）
- **日期**：2026-09-25
- **决策者**：产品负责人（指示："筹划一下 AI 功能、AI 的分支"）
- **影响层**：`packages/`（新增 `packages/ai`）、`apps/*`（注入推理端点）、`packages/design-system`（隐私提示 UI 的语义 token）、**服务端不受影响**
- **前置证据**：[AI 竞品与架构调研](../research/ai-competitive-and-architecture.md)（结论有变时**新增勘误**，不改原文）
- 🔴 **后续修订**：**[ADR-0006](0006-supply-modes.md) 修订了本 ADR 对选项 A 的处理** ——
  A（云端 AI）从"明确否决"改为"**可以提供，但必须满足 5 条严格约束**"。
  **本 ADR 其余结论全部保留**（§3.1"AI 是输入法"、§3.2 单一 provider 端口、
  §3.2.1 Web 端不粘第三方 Key、§3.3"LLM 做得最少"）。
  两处冲突时**以 ADR-0006 为准**（它更晚、且基于新增的 E2EE 产品调研）。

## 1. 背景与约束

要做 AI 功能，先要回答一个本项目独有的问题：**推理时明文在哪里？**

滴答清单/TickTick 的 AI 是服务端侧的 —— 服务端本来就看得到用户的明文任务，加一个模型读它没有任何架构冲突。
**heyta 不能照抄这条路**，因为服务端的可见性被设计成了零。这不是"还没做"，是有门禁的既成事实：

```ts
// server/src/sync/sync.routes.payload.ts:47
export const violatesE2eeGate = (item: E2eeGateItem): boolean =>
  item.isPayloadEncrypted !== true || !isEncryptedPayloadTransportShape(item.payload);
```

该函数在**任何持久化动作之前**执行（文件头注释原文：callers must invoke this BEFORE request
fingerprinting, deduplication, quota work, snapshot preparation, or persistence），且**没有开关** ——
AGENTS.md §7「线协议与运行时不对称」第 1 条：`isPayloadEncrypted` 必须显式 `true`，明文一律 400。

因此推导结论的硬约束如下（前两条直接排除选项）：

| # | 约束 | 来源 |
|---|---|---|
| 1 | **服务端读不到用户明文，且不打算开这个口子** | 上引代码 + AGENTS.md §7 |
| 2 | **云端不是事实源**（数据先落本地） | AGENTS.md §1 |
| 3 | **回放/远端 op 不得触发副作用** | AGENTS.md §3.4 |
| 4 | **一个用户意图 = 一个 op**；不得 fan-out | AGENTS.md §3.4 |
| 5 | **默认不 bump schema；新字段一律可选 + 运行时默认值** | AGENTS.md §3.3 |
| 6 | **自建/自托管是目标形态** → 不能假设"我们有云端 AI 预算" | `docs/reference/architecture.md` §0 |
| 7 | 任何第三方组件要过**可维护性 + 许可证**两道门 | AGENTS.md §3.1–3.2 |
| 8 | 组件禁止裸值，取值只能来自 token | AGENTS.md §5 |

约束 6 值得单独说明：heyta 的商业模式是"开源核心 + 自建/托管收费"。如果 AI 依赖我们出钱调云端模型，
那么**每个自建部署者都在消耗我们的推理账单**，或者被迫自己配置。两种结果都不好。
**AI 的算力必须由用户自己提供** —— 这是产品形态决定的，不是省钱。

## 2. 选项

| 选项 | 优点 | 缺点 | 关键证据 |
|---|---|---|---|
| **A. 云端 AI（服务端解密后送模型）** | 效果最好；开箱即用；模型可随时升级；与滴答清单同构 | 🔴 **违反约束 1** —— 等于宣布 E2EE 是营销词。服务端要拿到明文就必须有解密路径，那条路径一旦存在，威胁模型就永久改变 | 约束 1；`violatesE2eeGate`。<br>🔴 **本行已由 [ADR-0006](0006-supply-modes.md) §3.2 修订**：A 可以提供，但必须是**按功能、显式披露、可撤销**的例外，**且不得宣称它是 E2EE** |
| **B. 端侧小模型**（WebGPU/ONNX/llama.cpp） | 数据**从不离开设备**；零 API 成本；离线可用；无第三方 ToS | 移动端算力与内存受限；模型要随包分发或下载（体积）；小模型质量上限；RN/Hermes 的运行时支持**未验证** | 见调研文档；本机未实测 |
| **C. BYOK：客户端直连用户自己的 API Key** | 效果好；零我们的成本；用户自带账号与合规关系；实现成本低（一个 `fetch`） | 🔴 **Web 端在架构上站不住**（见 §3.2）：LLM Key 是 bearer 凭据，必须明文放进 `Authorization` 头，WebCrypto 的非导出密钥只防"带走密钥"不防"使用密钥"，**防不住 XSS**；且各家 CORS 支持不一致、随时失效。**因此 C 只做原生壳** | 调研：`research/local-first-e2ee-ai-2026-09.md` §2.2 |
| **D. 用户自托管推理端点**（Ollama / vLLM / 自建网关） | 与"自建/自托管"的产品形态**完全同构**；数据在自己的服务器上；无 ToS 风险；**Web 端也成立**（浏览器直连的是用户自己的服务器，CORS 自己可控） | 只有技术型用户会部署；需要内网穿透/局域网发现；延迟取决于硬件 | 同上；OpenAI 兼容 `/v1/chat/completions` 已是事实标准 |
| **E. 机密计算 / 私有云推理**（Apple PCC 等） | 理论上兼顾效果与隐私；Apple PCC 机制公开且可审计（SEP 每重启随机化数据卷密钥、无远程 shell、RSA 盲签名凭证 + OHTTP 中继、镜像公开 + 只追加透明日志） | 🔴 **TEE 对软件层运营方成立，对硬件层不成立**：DDRop（CCS 2026）用约 **$159–200 的 DDR5 interposer 即可重放 Intel TDX / SGX / AMD SEV-SNP 的加密内存**。且 PCC 的信任根与运营方是同一方（"信任分离"评分为 ○）、不能独立复现构建；平台锁定，**自托管场景不适用** | 调研：`research/privacy-enhancing-cloud-llm-inference-2026.md` |
| **F. 不做 AI，只做"AI 的接口"**（本地 API / MCP server / 导出） | 零隐私风险；零成本；用户拿自己的 AI 客户端接进来；与约束 6 天然一致 | 不是"我们有 AI 功能"；需要设计鉴权与权限范围；文档与支持成本 | 见调研文档 |

## 3. 结论

**默认组合是 C + D（同一个端口），B 作为渐进增强，F 并行推进且不算 AI 分支，A 明确否决，E 观望。**

> 🔴 **上句中的"A 明确否决"已由 [ADR-0006](0006-supply-modes.md) 修订为
> "A 可以提供，但受 5 条严格约束"**（按功能开启 / 显式出境披露 / 可撤销 /
> 本地路径是一等公民 / **不得宣称托管模式是 E2EE**）。
> 原因是产品负责人要求"自备与托管两种模式都提供"。
> **其余部分不变**：默认仍是 C+D，B 仍是渐进增强，F 仍是并行且不算 AI 分支，E 仍是观望。

### 3.1 决定性的一条：AI 是**输入法**，不是业务规则

这是本 ADR 唯一需要被后人记住的判断。

把 AI 放在 **`dispatch()` 之上**，让它只产出 `OpIntent`（或产出"待用户确认的建议"），
**永远不出现在 reducer / `applyOperation` / 冲突解决路径上**。于是：

| 约束 | 为什么自动满足 |
|---|---|
| 3（回放不得触发副作用） | 回放路径里根本没有 AI 代码。AI 只在用户主动触发时运行一次 |
| 4（一个意图一个 op） | AI 是"产生意图"的一方，意图仍逐个走 `createTaskActions`（`packages/app-host/src/actions.ts`） |
| 5（不 bump、字段可选） | AI 的输出落成**已有字段**（`title` / `priority` / `important` / `dueDate` / `note`），不新增实体、不新增必填字段 |
| 老客户端优雅降级 | 对端收到的就是一条普通任务。**它不知道也不需要在知道**这条任务是人写的还是 AI 写的 |
| 分层（ADR-0003 §2.1） | AI 编排在 `packages/ai`，`apps/*` 只注入"用哪个端点" |

反过来，如果把 AI 做成"reducer 里发现任务没拆解就自动拆"，就会同时违反 3、4、5 ——
而且是**静默**违反：本地看起来对，对端会看到重复拆解，或者每台设备各拆一遍。

> 与 `docs/research/feature-matrix.md` §11 的关系：该节把"内嵌 AI 聊天助手"列为反需求。
> **本 ADR 维持那条禁令** —— 不做聊天助手。本 ADR 允许的是**AI 作为输入方式**（把一句话变成结构化的任务字段），
> 这两件事的隐私面、工程面和失败模式都不同，不应混为一谈。

### 3.2 一个端口，两个后端 —— 以及 Web 与原生端**能力不同**

`packages/ai` 暴露 `AiProvider`，宿主只注入实现：

```
packages/ai
├── provider.ts        # AiProvider 端口：complete() / capabilities()
├── providers/
│   └── openai-compat.ts # C + D 共用：OpenAI 兼容 HTTP（baseUrl + 可选 apiKey + model）
├── tasks/             # 各能力分支的 prompt + 输出 schema + 校验
└── privacy.ts         # 数据最小化与"将要发送什么"的载荷构造
```

🔴 **C（BYOK）与 D（自托管）在实现上是同一个 provider** —— 只是 `baseUrl` 与是否带 Key 不同。
所以端口只需要一个，不需要为两家写两套。

#### 3.2.1 🔴 BYOK 只做原生壳；Web 端只能指向用户自己的端点

这一条是**调研之后从"未知风险"变成的硬约束**，必须写下来，否则一定会有人试图在网页上做"粘贴 API Key"：

| 端 | 允许 | 不允许 | 为什么 |
|---|---|---|---|
| **原生壳**（iOS / Android / 桌面） | ✅ BYOK（Key 存系统凭据库）+ ✅ 自托管端点 | — | 无 CORS 约束；Key 可存 Keychain / Keystore |
| **Web** | ✅ **只允许指向用户自己的 OpenAI 兼容端点** | 🔴 **不允许让用户粘贴第三方 API Key** | 见下 |

**Web 端为什么不行**（三条都是具体的，不是洁癖）：

1. **Key 是 bearer 凭据，WebCrypto 救不了。** 非导出密钥只防"把密钥带走"，**不防"用这个密钥发请求"**。
   任何 XSS 都能以用户身份调用。
2. **Anthropic 的官方 opt-in 头自己说明了问题**：浏览器直连需要显式设置
   `anthropic-dangerous-direct-browser-access: true`。**这个头的命名就是警告。**
3. **OpenAI 的 CORS 支持不稳定**：有用户报告 Responses API 已停止发送 `Access-Control-Allow-Origin`。
   把它做成产品功能 = 把功能可用性绑在别人的一个响应头上。

**推论**：Web 端要支持"用户自己的模型"，唯一站得住的形态是
**用户自己部署的端点**（CORS 自己可控），而这恰好是选项 D ——
**它同时也是与"自建/自托管"产品形态最一致的那一个**。所以这个限制不是砍功能，是把 Web 端引到更对的那条路上。

**密钥存储**（原生端，调研已核实）：

| 平台 | 做法 | 陷阱 |
|---|---|---|
| iOS / macOS | Keychain，`kSecAttrAccessibleWhenUnlockedThisDeviceOnly`（不随备份迁移到新设备） | — |
| Android | DataStore + Tink + Keystore | 🔴 **`EncryptedSharedPreferences` 已在 1.1.0 正式弃用**（网上教程大量过时）；且 Keystore **不防 Frida 运行时钩子**（OWASP MASTG 有提取 demo） |
| 桌面 Electron | `safeStorage`（落到 Keychain / DPAPI / libsecret） | — |

> 参考先例：**Obsidian Copilot 把 Key 存在系统 Keychain 而不是 vault 的 `data.json` 里** ——
> 对 E2EE 应用这是正确做法（否则密钥会跟着被同步的密文一起走）。heyta 照此办理。

🔴 **不引入各家厂商 SDK。** 理由是具体的：Ollama、vLLM、DeepSeek、豆包、OpenRouter、
以及 OpenAI/Anthropic 本身**都提供 OpenAI 兼容的 `/chat/completions`**，一个 `fetch` + 一个
`zod` 输出校验就够了（`zod` 已在依赖里，AGENTS.md §3 已登记）。每加一个厂商 SDK 就多一份
许可证登记、多一份升级负担、多一个体积。**能力分支不得自行引入 SDK。**

### 3.3 🔴 工程原则：LLM 做得最少

这条不是设计偏好，是从一份**生产级端侧 LLM 应用的失败复盘**里得来的（调研已核实）：

> 一个生产 Android 应用（Gemma 4 E2B 2.6B + Qwen3 0.6B）最初的架构是
> "**让 LLM 生成完整的结构化 JSON**"，最终**被迫退化**为
> "**词表提供词，LLM 只写 3 条短提示，失败有确定性回退**"。
> 其结论原话：**"最可靠的端侧 LLM 功能，是 LLM 做得最少的那个功能。"**
> 来源：`research/local-first-e2ee-ai-2026-09.md` §1.5（arXiv:2604.24636）

同一份复盘记录了五类端侧故障，其中两条特别值得记：
**模型持续把 JSON 包在 markdown code fence 里**、**三次生成后因 KV cache 饱和而质量下降**。

**质量天花板也有数据**（SOB 基准，21 个模型 / 8B–358B）：所有模型 JSON 合规率 >84%，
但**没有一个模型的 Value Accuracy 超过 80.4%**（文本域）；8B 级与前沿模型在文本抽取上只差约 2–3 个百分点。
**"格式对"和"值对"是两件事** —— 后者才是"任务日期解析错了"的来源。

**因此落到设计上**：

| 规则 | 内容 |
|---|---|
| 规则优先 | 高频表达由 `chrono-node`（已登记、MIT、含中文）解析，**AI 只在未命中或低置信度时被调用**（AI-1 的验收判据②就是钉这件事） |
| 输出约束 | 用 `zod` 校验；**校验失败必须走确定性回退**，不允许"让模型再试一次"作为唯一兜底 |
| 会话轮换 | 不把同一 session 连续用于多次生成（KV cache 饱和会导致质量下降） |
| 字段最小 | 模型只填"它必须填的那几个字段"，不要让它生成整个任务对象 |
| 失败可见 | 解析失败要告诉用户"没识别出时间"，而不是静默猜一个 |

### 3.4 数据最小化是默认，不是选项

每个能力分支只能发送**它当下需要的那一小段明文**：

| 能力 | 发送的内容 | **不**发送 |
|---|---|---|
| 自然语言录入 | 用户刚敲的那一句话 | 任务库、清单名、历史 |
| 拆解任务 | 这一个任务的标题（+ 用户可选的备注） | 其他任务、清单结构 |
| 象限/优先级建议 | 这一个任务的标题 + 截止时间 | 其他任务、习惯、专注记录 |
| 复盘摘要 | 🔴 **这一条与上面全部不同** —— 需要一批任务。见 §4「负面」 | |

这条规则让"AI 看得到你多少数据"变成**可陈述的**（每个分支一句话说清），
而不是"我们尽力保护你的数据"。

### 3.5 F 不是 AI 分支，是数据主权分支

本地 API / MCP server / 全量导出**不该被算进 AI 的排期**，因为：
它不做任何推理，没有模型、没有 prompt、没有幻觉，隐私面为零，而且**在没有 AI 的今天也有独立价值**（备份、自建看板、迁移）。

把它和 AI 混在一个分支里，会得到两个后果：AI 的隐私争议拖累一个本来无争议的功能；
以及"我们做了 AI"的假象掩盖了"其实只是开了个接口"。

## 4. 后果

### 正面

- **服务端一行不用改。** 这是本决策最实在的好处：`server/` 的 E2EE 门禁、冲突检测、限流全部不受影响，
  也不会有"AI 走的那条路径忘了加密"这类新风险面。
- **自建部署者不承担我们的账单**，符合约束 6 与商业模式。
- **同步层零风险**：AI 产出的是普通 op，P1/P2 已实测的冲突闭环、墓碑、向量时钟闸门全部照旧适用。
- 隐私成为**可宣传的差异点**而不是免责声明："AI 在你的设备上，或在你自己指定的端点上。"

### 负面 / 需要接受的成本

- 🔴 **我们提供不了"开箱即用"的 AI。** 用户不配置 Key / 端点，AI 就是灰的。
  这是本决策最大的产品代价，必须诚实承认 —— 滴答清单的 AI 体验优势有一部分正来自"服务端替你办好了"。
  **对策**：A0（自然语言录入）必须能在**完全无 AI** 时也工作（`chrono-node` 已在依赖表里、MIT、
  含中文 locale，见 `docs/plans/roadmap.md` §3）。AI 只做长尾兜底，不做地基。
- **BYOK 的体验门槛**：移动端让用户粘贴 API Key 是真实的流失点。需要**引导页 + 连通性自检 + 明确的失败原因**
  （区分"Key 错""额度用完""被网络阻断"）。
- 🔴 **"复盘摘要"这个分支与 §3.4 冲突。** 它要读一批任务才能总结，一旦发送就突破了数据最小化。
  因此它**不能默认做**，要么在端侧做，要么由用户逐次勾选范围并明示"这 N 条将被发送"。
  **在本 ADR 下它是受限分支，不是常规分支。**
- 🔴 **端侧模型（B）在 RN 移动壳上比预期难得多。** 原以为"未验证"，现已核实为**结构性障碍**：
  Hermes 缺 `WebAssembly`（AGENTS.md §7 陷阱 #26，真机实测、无 polyfill），
  而 `transformers.js` / `web-llm` 都建立在 WASM 之上 → **全部出局**；
  Apple 的 `@Generable` 是捷径但 Swift-only。**移动端端侧推理 = 原生绑定工程量。**
  → B 的排期**不能**按"装个包就有"来估（见 §5.2）。

### 需要靠规范/门禁兜住的

- 🔴 `apps/*` 不得自己直连模型端点。当前 `scripts/check-layering.mjs` 的 4 条规则管不到这件事，
  **需要加规则**（例如禁止 `apps/*` 出现 `api.openai.com` / `chat/completions` / `Bearer sk-` 形状）。
  按仓库既有纪律（AGENTS.md §3.5、CONTRIBUTING.md §4"门禁是否真的会失败"），
  新规则必须**先用注入违规文件验证它会红**再合入。
- **隐私提示 UI 的规范**：发送前必须展示"发给谁 + 发什么"。相关色值只能在 `tokens.css` 里加语义 token
  并通过对比度测试（AGENTS.md §5）。**不能**用裸 hex 表达"这是敏感操作"。
- **能力分支不得各自发明 prompt 调用方式** —— 统一走 `packages/ai` 的 provider 端口与输出校验。

## 5. 未核实项

> ✅ **2026-09-25 更新**：本 ADR 起草时有 4 项技术未知，**其中 4 项已在随后的调研中核实**，
> 结论均已并入 §2 / §3（证据：`docs/research/ai-competitive-and-architecture.md` §3）。
> 下面保留原条目并标注结果 —— **不改写已成立的结论，只补证据**（ADR 只追加，见 `docs/adr/README.md`）。

1. ✅ **端侧小模型在"中文自然语言 → 结构化任务字段"上的实际质量** —— **已核实**。
   格式合规 >84%，但**取值（Value Accuracy）没有一个模型超过 80.4%**（SOB 基准，21 个模型 / 8B–358B）。
   更关键的是工程现实证据：一个生产端侧应用从"LLM 生成完整结构化 JSON"**被迫退化**为
   "LLM 只写几条短提示 + 确定性回退"，其结论是**"最可靠的端侧 LLM 功能，是 LLM 做得最少的那个功能"**。
   → **原判断成立且被加强**：B 保持"渐进增强"，并新增 §3.3 的工程原则。
2. ✅ **RN / Hermes 上端侧推理运行时是否可用** —— **已核实，且是坏消息**。
   🔴 **Hermes 缺 `WebAssembly`**（本仓库真机实测，AGENTS.md §7 陷阱 #26，**且无 polyfill 可装**）。
   → **`transformers.js` / `web-llm` 等 WASM 基座在 RN 移动壳上全部出局**；
   Apple `@Generable` 虽是捷径但 **Swift-only**（ADR-0004 选了 RN）。
   **移动端要做端侧推理 = 原生绑定工程量，不是装 npm 包。**
   → 这条**进一步支持**把 B 定为渐进增强；同时说明"端侧"在移动端的成本被低估了。
3. ✅ **各家 API 是否允许浏览器/移动端直连（CORS）** —— **已核实，并落成硬约束**。
   原生端可直连；**Web 端架构上站不住**（Key 是 bearer 凭据，WebCrypto 防不住 XSS；
   Anthropic 需 `anthropic-dangerous-direct-browser-access: true`；OpenAI 的 CORS 支持不稳定）。
   → 见 §3.2.1：**BYOK 只做原生壳，Web 端只允许指向用户自己的端点。**
4. ✅ **Apple Foundation Models 的可用范围与许可条款** —— **已核实**。
   iOS 26.0+；**不是仅端侧**（统一访问设备端与 Private Cloud Compute）；
   **上下文硬上限 4096 token/session**（中文约 1 字/token）；`@Generable` 提供结构化输出强保证；
   随 SDK 分发（非开源，但调用系统框架不构成依赖许可证问题）。
   → **结论不变**（B 是增强不是地基），但"iOS 端侧"的可用面比预期窄。
5. 🟡 **用户是否真的愿意自带 Key。** 这是产品假设，不是技术假设。**仍然未核实，且证据比初稿时更不利。**
   > 🔴 **2026-09-25 补记**：横向调研（13 个产品，`docs/research/ai-feature-landscape.md` §6.1）结论是 ——
   > **在本轮覆盖的产品里，没有任何一家支持"用户自带自己的 LLM API Key"来驱动它内置的 AI 功能。**
   > 它们的模式**全部是厂商代管**：用户付费给产品，产品再去对接模型供应商。
   >
   > **这意味着 C（BYOK）在任务管理品类里没有先例。** 它既是**机会**（无人占据的位置），
   > 也是**风险**（没有先例 = UX 未被验证，用户教育成本真实存在）。
   > 调研给出的可检验解释：这一品类的 AI **都发生在服务端可计量的地方**，
   > 因为**服务端才能按 credit / 点数 / 额度收费** —— 端侧与 BYOK **无法计费**。
   >
   > **对策不变且更强**：用最小可用版本先验证，而不是先建完整基础设施。
   > 且 **AI-5（接口 / MCP）应当先做** —— 它把"让用户用自己的 AI"这件事
   > 交给用户已有的客户端，**绕过了"heyta 自己教育用户配 Key"这道坎**。
6. ⚠️ **本 ADR 未覆盖**：AI 生成内容的**正确性责任**（用户按 AI 的拆解做事，出了问题算谁的）、
   以及是否需要"这是 AI 生成的"标记。后者若要做标记，就涉及"往持久化模型加字段" ——
   必须走 AGENTS.md §3.3 的可选字段 + 运行时默认值，且**不得**新增必填字段。
7. 🔴 **新增未核实项（本次调研发现的）**：
   **"E2EE + 客户端本地明文 API"的完整公开威胁模型文档 —— 未找到公开信息。**
   已知的定性事实：客户端解密后交给本地 API **不改变服务端的可见性**，
   但**把风险下移到"本机其他进程与扩展"**；公开表述是"如果威胁模型包含被攻破的浏览器或恶意扩展，
   客户端侧加密提供不了任何保护"。**这份威胁模型 heyta 得自己写**，否则 §3.5 的 F 分支
   会在"我们开了本地 API"这句话上给出过度承诺。
