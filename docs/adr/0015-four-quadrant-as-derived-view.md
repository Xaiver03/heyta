# ADR-0015：四象限是**派生视图**，且只有一个轴由用户回答

> 状态：**已接受**
> 日期：2026-09-26
> 决定：**四象限不建模成实体；两个轴一个由用户回答、一个由 `dueDate` 推导；
> 界面入口放在「任务」tab 内的视图切换，不新增第 5 个 tab**
> 依据：[ADR-0003](0003-multi-platform-strategy.md)（多平台分层）、[ADR-0004](0004-ui-stack.md)（导航 = 4 tab）

---

## 1. 问题：一个被宣传了、却不在 app 里的核心能力

落地页把四象限当作产品支柱之一在讲：

> 清单、日历、**四象限**、习惯打卡、番茄钟。每一块都有成熟做法，难的是让它们共用同一份数据、同一套同步规则。
>
> 重要与紧急拆成两轴，**任务拖进哪一格就归哪一类**。紧急程度由截止时间推导，不由你手填。

但 app 里没有它。导航是 4 个 tab：任务 / 日历 / 专注 / 我的。

**这是最不该出现的一类不一致：落地页承诺了、产品没做。**
它比"功能没做"更贵 —— 用户是照着那句话来的。

真实状况是：**体系已经建好了，只缺壳里的界面。**

| 层 | 状态 | 位置 |
|---|---|---|
| 数据模型的两个轴 | ✅ | `packages/domain/src/entities.ts` — `important?: boolean`、`dueDate?: number` |
| 派生逻辑（纯函数） | ✅ | `packages/domain/src/quadrant.ts`（160 行，已从 `index.ts` 导出） |
| 写入口 | ✅ | `packages/app-host/src/actions.ts` — `setImportant`、`setDueDate` |
| i18n | ✅ | `packages/i18n` — `landing.quadrant.q1..q4`、`dropHere` |
| **壳里的界面** | ❌ | — |

## 2. 决定一：**不建模成实体**

`ENTITY_TYPES` 里**不能**出现 `EISENHOWER` / `QUADRANT` / `TODAY` / `CALENDAR_VIEW` / `BOARD`。
这条已有测试守住：`packages/storage/tests/entity-model.spec.ts` 的
「不把视图建模成实体」。

理由是经典的**双写不一致**：一旦象限归属被存成一份独立数据，它就会和
`important` / `dueDate` 漂移 —— 用户改了截止时间，象限数据没跟上，
于是"同一个任务在两个地方归两类"。而这类 bug **不会报错**，只会让人不再信任界面。

派生还能白拿三件事：离线可用、无需新增 op 类型、多端天然一致
（三端跑同一个纯函数，不可能算出不同结果）。

## 3. 决定二：**只有一个轴由用户回答**

| 轴 | 来源 | 为什么 |
|---|---|---|
| **重要** | 用户显式设置 `important` | "这件事重不重要"是**主观**的。任何算法都猜不对，猜错还会让用户觉得产品在替他做主 |
| **紧急** | `dueDate` 推导（窗口内或已逾期） | 这是**客观**的：截止时间就在数据里，让人再填一遍是纯粹的重复劳动，且两个字段一定会不一致 |

规则细节（`quadrant.ts`，已有测试）：

- **已完成的永不紧急** —— 它已经不需要做了。
- **无截止时间 → 不紧急**。不猜。
- **`isImportant` 的优先级回退**：显式 `important` 优先；没有时回退到 `Priority.HIGH`。
  **故意不把 `MEDIUM` 当作重要** —— 那会让"重要"占绝大多数，象限失去区分度。

> ⚠️ **为什么需要回退**：`important` 是后加字段，老数据没有它。
> 若直接判为"不重要"，所有历史任务会**同时**挤进"不重要不紧急"，
> 象限视图看上去像坏了。这是**前向兼容问题，不是排序问题**。

## 4. 决定三：入口在「任务」tab 内，**不新增第 5 个 tab**

ADR-0004 定的导航是 4 个 tab（任务 / 日历 / 专注 / 我的）。四象限是**同一份任务的另一种投影**，
不是第四个功能域 —— 给它一个 tab 会暗示"这里有一批新数据"，而其实一条都没有。

所以入口是「任务」页顶部的**视图切换**：

```
任务
├─ 列表（默认，按今天分组）
└─ 四象限
```

代价与收益：

| | 新增第 5 tab | tab 内切换（**选它**） |
|---|---|---|
| 导航 | 改 ADR-0004 | 不动 |
| 心智 | 暗示是新数据域 | 明确是同一批任务的另一种看法 |
| 发现性 | 高 | 够用（就在任务页） |
| 与 TickTick 的一致性 | 它也放在清单区而非主导航 | ✅ |

## 5. 决定四：拖动**必须走 op-log**，不得直接写库

"把任务拖进某个象限" = 一次字段修改，必须经 `packages/app-host`：

| 拖到 | 发出的动作 |
|---|---|
| Q1 重要且紧急 / Q2 重要不紧急 | `setImportant(id, true)` |
| Q3 紧急不重要 / Q4 不重要不紧急 | `setImportant(id, false)` |
| 任何一格 | 需要改截止时间时另发 `setDueDate(id, …)` |

**禁止**在界面里直接改本地状态再补一条 op —— 那会绕开 `op-log` 这个唯一写入口
（AGENTS.md §3.5）。多端一致性完全依赖"改动 = 一个 op"。

> 强行清掉截止时间来"变不紧急"会**销毁用户数据**。
> 正确的语义是：拖动只回答"重要吗"这一个问题。~~

## 6. ⚠️ 更正：上面那段推论是错的（同日，读完已上线的实现之后）

上面那段推论**是错的**，写它的时候我还没读 `apps/web` 的实现。

错在哪：**紧急既然是推导出来的，"不改 `dueDate`"就等于"拖到 Q1/Q3 根本落不进去"**。
一个 10 天后到期的任务被拖进 Q1 时，只设 `important` 不会让它变紧急 ——
它会**弹回 Q2**。所以"只回答重要吗"不是一个更安全的方案，
它是一个**让拖拽失效**的方案：用户拖了，任务没动，界面上还没有任何解释。

正确的结论是「**拖拽必须动 `dueDate`，但动了就必须说**」：

| 拖到 | `important` | `dueDate` |
|---|---|---|
| Q1 / Q2（重要侧） | `true` | 紧急侧需要时推进窗口内（1 小时），已紧急则**不动** |
| Q3 / Q4（不重要侧） | `false` | **清除**（这一格的语义就是"没有迫近的期限"） |

清除确实是**用户数据的删除**，所以不能无声 —— 领域层的 `planQuadrantDrop`
会在 `dueDateChange` 里如实报告 `'pushed'` / `'cleared'`，界面据此说明。

这条更正也顺带修掉了实现的三个缺陷（详见 §7）。

> **记账**：上面那段被划掉的推理我保留在这里，因为"我当初为什么会那么想"
> 比"现在结论是什么"更值得留下 —— 它是"没读代码就先写结论"的一个样本。

## 7. 实现里读出来的三个缺陷（2026-09-26）

`apps/web/src/features/quadrant/QuadrantBoard.tsx` 的拖放处理原先是一段手写逻辑：

```js
// 一次操作 = 一条 op（AGENTS.md §3.4）：两个字段一次写完
await store.setImportant(taskId, important);                    // ← 第 1 条 op
if (urgent && task.dueDate === undefined) {
  await store.setDueDate(taskId, Date.now() + 60 * 60 * 1000);  // ← 第 2 条 op
} else if (!urgent && task.dueDate !== undefined) {
  await store.setDueDate(taskId, undefined);
}
```

| # | 缺陷 | 后果 |
|---|---|---|
| 1 | `urgent && task.dueDate === undefined` **只处理"完全没有截止时间"** | 拖"10 天后到期"的任务进 Q1 → 只设了 important → 仍然不紧急 → **弹回 Q2**。拖了等于没拖，无解释 |
| 2 | 注释写「一次操作 = **一条 op**…两个字段一次写完」，代码是**两次 `await`** | 注释描述意图，代码做另一件事；且中间态"重要已改、期限未改"**可见**，此刻同步或崩溃会留下改了一半的任务 |
| 3 | 清除截止时间**无任何提示** | 用户设的"周五交报告"被一次拖拽静默删掉 —— 最容易被记成"数据丢了"的一类 bug |

**根因不是"偶发 bug"，是逻辑放错了层**：产品语义写在组件的事件处理里，
而这块看板**至今一个测试都没有**。两件事互为因果。

修法：语义移到 `packages/domain/src/quadrant.ts` 的纯函数 `planQuadrantDrop`，
配套 6 个测试（含"4 象限 × 3 种截止时间状态必须真的落在目标格"的穷举），
写入口收成 `TaskActions.setQuadrantDrop`（**一条 op**）。

**证伪记录**：把实现改回旧行为（只在 `dueDate === undefined` 时才补），
两条测试立刻变红，其中穷举那条给出的诊断是：

```
AssertionError: 目标=1 / 起点=窗口外 时没有落在目标象限: expected 2 to be 1
```

即"拖进 Q1，落在 Q2"——缺陷被完整复现并命名。恢复实现后 58 项全过。

## 8. 后果

**变简单的**：三端共用同一个 `classifyQuadrant`，不可能算出不同结果；
离线可用；不需要新 op 类型；不需要迁移。

**变复杂的**：紧迫窗口（`DEFAULT_URGENT_WINDOW_DAYS = 2`）是个**全局参数**，
改它会让所有用户的象限归属同时变化。目前按常量处理；若将来要可配置，
必须作为**偏好**走同步，而不是每端一个本地设置 —— 否则两台设备会对同一个任务
给出不同象限，而用户看不到任何解释。

**明确不做**：不做"自动把紧急任务标成重要"。用户没有授权这件事，
而且它属于 §3 里说的"主观问题用算法猜"。
