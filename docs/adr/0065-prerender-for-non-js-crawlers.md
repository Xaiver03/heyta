# ADR-0065：为**不执行 JS 的爬虫**预渲染站点正文

> 状态：**待确认**（草案，2026-10-19。产品负责人尚未拍板 —— 见 [SEO 计划](../plans/seo-program.md) §6.1）

## 1. 背景：一个已经量出来的空格子

站点是"多 HTML 入口"架构（[ADR-0033](0033-multi-page-site-and-bidirectional-reachability.md)）：
每个页面 × 每种语言 = 一份独立的静态入口，**头部**（`<title>` / description / canonical /
hreflang / `og:*` / JSON-LD）全部由生成器写进那份字节里。

但**正文不在里面**。实测（2026-10-19）：

```
$ curl -s https://heyta.waytofuture.cn/features/ | grep -o 'id="root"[^>]*>[^<]*'
id="root">

$ # 用不执行 JS 的抓取器读同一页，能拿到的全部内容：
功能介绍 —— heyta
```

ADR-0033 §7.1 在 2026-09-28 就把这件事如实登记过，并明确写了：

> 要兑现后者（无 JS 首屏）需要预渲染或 SSR，**那是另一份决策（本 ADR 未做，也不据此声称）**。

**本 ADR 就是那份决策的位置。**

### 1.1 它影响谁、不影响谁

| 爬虫 | 执行 JS？ | 受不受影响 |
|---|---|---|
| Googlebot、Bingbot | ✅ 会（有渲染队列，有延迟） | 影响有限 |
| **百度、搜狗、360** | ⚠️ 不可靠 / 基本不执行 | 🔴 **看到的是空正文** |
| 分享卡片与预览抓取器（Slack / 微信 / 各家 IM） | ❌ 不执行 | OG 卡片刻意只依赖 head，**不受影响** |
| 结构化数据消费者 | — | 也只在 head，**不受影响** |

⇒ **这不是"SEO 万能药"**：它换来的主要是中文搜索引擎侧的可索引正文。
把它当成"做完就能被搜到"是错的 —— 真正的总闸是**站长平台接入**（[计划](../plans/seo-program.md) §6.2）。

## 2. 选项

### A. 构建后快照式预渲染（**推荐**）

`vite build` 之后，本地起一个静态服务指向 `dist`，用 **Playwright**（已在仓库里：
`e2e/` 工作区，`@playwright/test@1.63.0`，Apache-2.0 且**已登记**在
`THIRD_PARTY_LICENSES.md`）逐页访问、等 React 挂载完成，把结果 DOM 写回入口 HTML。

- ✅ **零新增第三方依赖**（许可与可维护性两道门都不用重过）
- ✅ 产物对爬虫与浏览器是**同一份字节**（不存在"给爬虫看另一套"的问题）
- ✅ 已有接缝可复用：`research/tools/publish-public-sites.mjs` 里那条
  `pnpm --dir e2e exec playwright …` 就是"仓库脚本调 e2e 工作区的 Playwright"，
  **不需要往 `apps/landing` 加依赖边**
- 🔴 最大的风险是**确定性**与**把瞬时状态烤进静态字节**（见 §3）

### B. 自建 SSR（React 19 `renderToString`）

- ✅ 语义最正，产物天然确定
- 🔴 代价大得多：组件树得先过一遍"SSR 安全"（`window`/`document` 不能在模块顶层被读），
  而站点有**同步执行的主题引导脚本**、`three` 场景、`motion` 动效与按语言动态 `import` 的词条表
- 🔴 引入一条**构建期 Node 运行时**路径，与"站点只是一堆静态文件"的现状相比是范式变化
- 结论：**现在不做**。若 A 的确定性收不住，再回来评估 B

### C. 按 UA 分流（dynamic rendering）

给已知爬虫 UA 返回预渲染 HTML，给真人返回原 HTML。

- ❌ **明确否决**。它要求维护一张"哪些 UA 算爬虫"的清单，而清单会**静默漂**
  （新增一个爬虫不会报错，只是那一家的收录悄悄少一份 —— 这正是本仓库最忌讳的失效形态）；
  各家搜索引擎也都把它当 workaround 而非答案

### D. 不做

- ✅ 成本为零，且如果主战场只有 Google/Bing 就够用
- ⚠️ 代价是百度/搜狗侧**正文永远进不了索引**，而那是中文市场的主要入口

## 3. 推荐方案 A 的**硬约束**（先写下来，拍板后照此落地）

这一节是这份 ADR 真正承重的部分：A 的失败方式**全是静默的**。

1. **必须在 `prefers-reduced-motion: reduce` 下取快照**，并在取之前显式等待
   "页面稳定"信号。理由本仓库有前科：启动动画第一版 `opacity: 0`，
   **真浏览器 t=0 截图上三道字形全透明**，而 22 条 CSS 断言全绿
   （它们断的是"元素在不在、色对不对"，不是"这一帧看不看得见"）。
   在动效中途取快照 = 把"不可见"烤进线上 HTML，**同时烤进爬虫读到的那份**。
2. **必须对 `dist` 取，不能对 dev server 取** —— 否则入口 HTML 里引用的 chunk 名
   与线上不一致（dev 不打 hash），产物自洽性判据会红。
3. 🔴 **`check:entries` 的覆盖范围必须一起改。** 今天它对生成物做**逐字节**对账。
   预渲染之后入口有了**两段来源**（生成器 + 快照）。若只改生成器不改判据，
   门禁会**绿着一份过期的快照** —— 那是"测试全绿 ≠ 这是当前产物"那条元规则的又一次实例。
   做法二选一：把预渲染并进 `gen-entries.mjs` 的同一条命令（同一道 `--check` 覆盖两段），
   或新加一条只针对快照的对账脚本。
4. **Playwright 版本钉死**（当前 `1.63.0`）—— 不同版本的序列化输出可能不同，
   而它现在是**产物字节的一部分**。
5. **Hydration 是子问题，必须一起答。** `apps/landing/src/main.tsx` 现在用 `createRoot`：
   预渲染之后浏览器会**丢弃**那份 DOM 重新渲染（真人可能看到闪一下）。
   改成 `hydrateRoot` 能消掉这一下，但前提是"快照与客户端首帧逐字一致"——
   若做不到，宁可不改（保留一次重渲染），也不要 hydration mismatch。

## 4. 分阶段（建议，不是决定）

不要把 76 份一次做完。先做**能被搜到的那一批**：

- 第一批：`/`、`/features/`、`/download/`、`/platforms/`、`/pricing/`、`/docs/`（枢纽）
  ≈ 6 页 × 2 语言 = 12 份
- 第二批：`/docs/` 下的帮助文章（20 篇 × 2）—— 价值低得多（产品还没有用户，
  长尾查询也还没有），**但成本相对固定**，等第一批的确定性收住了再上

## 5. 验收判据（拍板后按此写）

- 🔴 **能失败的那条**：不执行 JS 取 `/features/` 的字节里，必须出现该页 `<h1>` 的**同一段文字**
  （文字从 `packages/i18n` 的词条表推导，**不抄字面量** —— 抄了就会在改文案那天静默恒真）
- 同一份入口：真浏览器渲染出的 DOM 的 `<h1>` 文字与导航链接集合，与快照里的**一致**
- 构建加时与入口体积**现量登记**（不预设阈值；抄一个数字进去就会漂）
- 变异验证：手动把快照换成"未预渲染"的那份，第一条必须变红

## 6. 后果

**正面**：百度/搜狗/360 与其它非 JS 抓取器第一次能读到正文；产物仍是纯静态、
仍可 `rsync` 上线；不引入第三方依赖。

**负面**：构建要起浏览器、加时；产物字节开始依赖 Playwright 版本与取快照的时机，
于是"确定性"从一个免费获得的性质变成**要主动维护**的性质；76 份入口的体积上升。

**中性但要知道**：它**不改变** Google/Bing 侧的收录结果（它们本来就渲染 JS），
也**不替代**站长平台接入。

## 7. 本 ADR 没有决定的事

- 做不做（**等产品负责人拍板**）
- 什么时候做（排在站长平台接入之前还是之后 —— 建议**之后**：没提交就谈不上抓取）
- 要不要顺手改 `hydrateRoot`
- 第一批到底做哪几页（§4 是建议）
