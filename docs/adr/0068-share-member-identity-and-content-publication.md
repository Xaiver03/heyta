# ADR-0068：共享清单的成员侧身份、清单记录本身的归属，与存量内容发布

> 状态：**已接受（工程裁决 2026-10-22）**。
> 本 ADR 做两件事：① **收窄 [ADR-0067](0067-shared-list-write-routing-and-merge.md) 裁决一在 `entityType === 'PROJECT'` 那一支的推论**
> （0067 其余每一条一字不动，包括它自己的判据"所属清单的 `shareId` 是否在册"）；
> ② 补上 0067 **没答**的两格 —— 成员侧那条清单行是哪来的、一条已有内容的清单变成共享时它的存量条目怎么走。
> 触发方式与 0067 同一条：不是设想出来的问题，是实施 M2 到"读侧合并"那一步时**代码现量**出来的。

## 背景：写路径一接，"两个成员是不是同一条清单"这个问题就躲不掉

0067 把"哪些 op 进 share log"定了。它没定、也没法在写代码前定的是**读的那一半**：
共享内容进了另一本 log 之后，界面上要把它摆回**哪一条清单**。而这一问的答案由三格代码事实决定，
三格都在下面，每条带现量命令。

## 事实基线（每条都带现量命令，别按本节文字推断）

1. **一份 share 没有"清单 id"。**
   `grep -n 'model Share' -A 12 server/prisma/schema.prisma` ⇒ `Share` 的列是
   `id / ownerUserId / keyEpoch / lastServerSeq / createdAt / deletedAt` —— **没有任何指向清单实体的列**。
   服务端从设计上不认识"清单"这条内容实体（它在密文里）。
   ⇒ share 与 `Project` 的关联**只存在于客户端个人 log 的 `Project.shareId` 字段**。
2. **成员侧那条清单行是各设备自己建的，id 必然不同。**
   `apps/web/src/features/share/JoinSharedListDialog.tsx:190-198` ⇒ 接受邀请时先
   `addProject(name)`（本机生成的新 id，名字由**加入者**当场填），再 `setProjectShare(projectId, shareId)` 挂上。
   同一段注释还钉死了"同一时刻只建一行"（实测过重复建行的形状）⇒ **一台设备上，一条 shareId 最多对应一行**。
3. **任务批量那一条 reducer 形状会盖自动化出处。**
   `packages/op-log/src/state.ts:651-661` ⇒ `hasTaskBatchMarker` 那条路把每条成员强制成
   `opType: Create` 并写进 `automationSource`（ADR-0064 入站自动化的形状）。
   ⇒ "一次意图发 N 条任务"这个形状**已经存在**，但它的语义是"这些任务由某个自动化产生"，不是"这些内容被发布进一份共享"。
4. **提醒不在这份共享的可写词表里。**
   `grep -n SHARE_WRITABLE_ENTITY_TYPES server/src/shares/share.membership.ts` ⇒ `TASK / PROJECT / TAG / NOTE / COMMENT`，**没有 `REMINDER`**。
5. **个人 log 里从来不会有 COMMENT。** `packages/op-log/src/state.ts:98-101` 的字段注释是这条的正面表述。

## 一、清单**这条记录本身**不是共享内容（收窄 0067 裁决一的 PROJECT 那一支）

`entityType === 'PROJECT'` 的 op **一律进个人 log**，即使这条清单的 `shareId` 在册。

两条理由，缺一不可：

1. **share log 里没有"那条清单"这个实体。** 事实 1 + 2 ⇒ 每个成员持有的是 id 各不相同的本机一行。
   把 A 的 `PROJECT UPD` 路由进 share log，B 侧物化出的是一条**本机没有对应行的记录**；
   要把它显示出来，只能把"多条 id 分歧的记录"并成一条 —— 那是**跨记录字段合并**，
   正是 0067 裁决二明令不许新建的第二套合并语义。
2. **清单名字是"我怎么称呼这份共享"，不是内容。** 事实 2：加入流程里这个名字是加入者当场填的、
   默认值来自本机词表。把它变成共享写，等于让"别人起的名字"覆盖我的界面。

代价，写清楚不藏：**改名 / 归档 / 颜色不跨成员同步** —— 同一条 share 在不同成员侧显示各自的名字。
这是本 ADR 选择的失真，不是遗漏。
**翻案条件**：若产品要"所有者定的共享清单名"，前置是先给 share 立一枚**跨成员唯一的清单 id** ——
要么服务端加列（迁移 + 隐私政策登记「清单标识可见」），要么 share log 里放一条权威 `PROJECT CRT`
再让**所有**读写做 id 别名翻译。两条都比"本机起个名字"重得多，届时另立 ADR，不在本条上改。

落地形状（改的是 0067 落地的代码，不是它的判据）：
`packages/app-host/src/share-routing.ts` 的 `isRoutableKind` 去掉 `PROJECT`
⇒ PROJECT 一律 `kind-not-routable` ⇒ 走个人 log；
`packages/app-host/src/share-client.ts` 的 `SHARE_ACTION_TYPES` 里 `PROJECT:*` 那几行删除。
⚠️ 删除的安全性建立在一格现量事实：**今天没有任何一条 PROJECT 族 share op 上过线**
（M2 写侧未接线，历史上进过 share log 的只有 COMMENT 族）⇒ `actionType` 进了 AAD 也不会影响任何存量密文。

## 二、成员侧的共享内容**按 `shareId` 归到本机那一行**（读侧合并的唯一规则）

合并视图是**派生读视图**，不写任何东西、不改 reducer：

- 逻辑只许住 `packages/app-host`；端壳递进来的只有两样 —— 个人物化状态、一枚"按 shareId 读物化状态"的函数。
- 四条规则：
  1. **只为"本机有清单行挂着它"的 share 合并**。没有这一行（含"本机已取消共享"那一形）⇒ 这份共享在本机不可见。
     这条不是保守：内容在别人的 log 里，本机那行没了就等于本机没有视图锚点，硬塞会把它塞进"未归属"。
  2. share 状态里的 **TASK / NOTE 整条覆盖**个人状态同 id 的那条，并把 `projectId` 改写成本机那一行的 id。
     覆盖是对的方向：共享之后这些实体的写**不再进个人 log**，个人那份是绑定那一刻的冻结副本。
  3. **COMMENT 直接并**（事实 5 ⇒ 没有同名冲突可言）。
  4. **TAG 只并被这份共享的任务引用到的那些，且同 id 时以个人侧为准**。
     补一（0067）发布的标签本来就是同 id 同内容；本机词表是权威，共享侧只补本机没有的名字。
- 为什么是"改写 `projectId`"而不是"给 share 立规范 id"：事实 1/2 ⇒ 规范 id 要动不可逆层；
  而一条 share 在一台设备上恰好对应一行（事实 2 的独占注释），所以"这本 log 里的全部内容都属于那一行"**无歧义**，
  不需要别名层。
- 🔴 **如实登记这条规则的失真**：合并后本机的 `task.projectId` 指向本机那一行，而**线上那条 op 的 payload 仍写着作者本机的 id**。
  这是视图层的重定位，不是数据篡改；要审计"这条任务原本挂在谁的哪条清单"必须读 share log 原文，**不能读合并视图**。
- 判据要能红（形状见 `packages/app-host/tests/share-view.spec.ts`）：漏并一族 ⇒ 那一族的共享改动在界面上消失；
  本机没有清单行 ⇒ 零合并；同 id 时个人侧冻结副本不得盖回 share 的新值。

## 三、把一条**已有内容**的清单变成共享，需要一次显式的「发布快照」

不做这一格会出现的症状（是本 ADR 立项的直接原因）：
共享一条已有 30 条任务的清单 ⇒ share log 是空的 ⇒ 成员看到 0 条；
而 A 之后改第 7 条时，路由会把一条 **`TASK UPD` 发进 share log**，
对面物化出一条**只有那一个字段**的任务（`addFieldVersion` 对不存在的实体同样是新增版本）
⇒ 成员界面里是一枚解不出标题的残条目，而 A 自己看不见任何异常。

- **裁决**：绑定时由宿主编排一次发布 —— 把这条清单**现有**的任务与便签、以及被它们引用的标签，
  逐条各发一条 `Create` op 进 share log。幂等判据 = 这个 id 已在 share 状态里就不重发。
  跳过墓碑（`deletedAt` / `purgedAt` 有值）：回收站里的东西不是共享内容。
- **为什么不塞进"绑定那一条 op"**：绑定是个人 log 的一条 op，发布是往**另一本 log** 写 N 条，两本 log 各写各的意图
  （与 0067 补一同一条理由）。要压成一条只有两条路：用批量那条形状（事实 3 ⇒ 它会把共享发布伪装成入站自动化，
  出处是错的），或新造一种 payload 形状（不可逆层，需迁移与线协议变更）。逐实体一条 op 让每个对象之后可独立寻址、
  重发布幂等。
- **失败形状**：中途某条上传失败 ⇒ 已发的留下，未发的不假装成功；返回一份「发布了几条 / 剩几条」的报告，界面按报告说话。
  **不撤销**：取消共享不把已发布的密文从别人手里收回来（0067 补二的同一条理由），界面上也不许出现这种暗示。
- 归属：发布逻辑住 `packages/app-host`，触发点（共享流程那一步、以及给存量共享清单的"补发布"入口）住 `apps/*`。

## 四、提醒不共享（把服务端词表在客户端说明白），并登记一条**待实测**的连带形状

事实 4 ⇒ `REMINDER` 的 intent 在路由里是 `kind-not-routable` ⇒ 走个人 log：
**每条共享任务在每台设备上各自设提醒、各自响**，成员的提醒规则不互相可见，也不互相覆盖。这是选出来的形状，不是遗漏。

⚠️ 但有一格连带形状本 ADR **不下结论**，交给 M2 实施时实测：
`packages/op-log/src/state.ts:626-649` 那条"完成一次重复任务"的 op，`entityType` 是 `TASK`（会路由进 share log），
而它的 payload 里**顺带**改写了 `REMINDER` 那几条字段。两侧各会怎样：
- 服务端只看 `op.entityType`（`server/src/shares/share.routes.ts` 的 `decideShareOpWrite`）⇒ 不会拒；
- 客户端 reducer 会把那些提醒更新落到**share 状态**的 reminders 桶里，而裁决二不合并提醒 ⇒
  作者本机的提醒停在旧的那一次。
**症状候选**是"重复的共享任务完成后，下一次提醒不再按时出现"。它是**候选**还是**已被别的机制兜住**
（比如投递面会因为任务已完成而跳过），必须现测后再写计划，不许在这一节里当结论抄。
两条可能的处方，都不在本 ADR 里选：(a) 该意图的提醒那一半留个人 log（两本 log 各一条，与补一同形）；
(b) 共享清单里的重复任务完成时不重排提醒，界面上如实说明。

## 五、明确不做什么

- 不做跨成员统一的清单身份（见一·翻案条件）。
- 不做共享内容的 per-op 签名 → M4（0067 裁决四已一次定下形状）。
- 不做移动端 → M6。
- 不 bump `CURRENT_SCHEMA_VERSION`、不加持久化字段、不动 `packages/shared-schema` 的线协议词表
  （本 ADR 四条裁决**全部**落在客户端读视图与写编排上）。
- 不撤"共享入口默认隐藏"（P-1）：share 通道今天是**先上传再落本地**，与本地优先有张力，
  离线写那一格留给下一批第一格。

## 落地顺序

M2-f 读侧合并（裁决二）→ M2-g 发布快照（裁决三）→ 写侧接进 `dispatchIntent`（0067 裁决一 + 裁决一）
→ 因果时钟回流（0067 裁决二）→ 并发可见（0067 裁决三）→ 验收扩臂 + 两台真浏览器那一格。

顺序里有一条硬约束：**读侧合并必须先于写侧接线**。只接送侧不建读侧的后果是作者连自己的改动都看不见
（共享内容离开了个人状态，而界面只读个人状态）—— 那不是"还没做完"，那是一条新引入的静默失效。
