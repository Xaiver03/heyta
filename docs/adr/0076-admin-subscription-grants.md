## 1. 背景与约束

### 1.1 起因

产品负责人在本轮的原话：

> "管理后台目前至少要具备给别人升级、免费升级、赠送订阅这几种方式，
> 因为我肯定在测试阶段一定要用到。"

注意这句话的**用途是测试期**：发放大多是发给自己的测试账号或内测者，
所以"防运营者自己"不是这一版要解决的问题（§4.3 会说为什么）。

### 1.2 动手前的实测（`2026-10-25` 现量，别抄下面的数字）

```bash
grep -cE "fastify\.(get|post|put|delete)\('" server/src/admin/admin.routes.ts   # 21 条路由
grep -n '\*\*不做\*\*：改订阅' server/src/admin/admin.routes.ts                         # 文件头仍然这么写
```

| 事实 | 位置 | 它为什么决定形状 |
|---|---|---|
| 权益判定是**跨行并集**：任一行在当下有效且覆盖该能力即放行 | `server/src/entitlement.ts` 的 `evaluateCapabilityAcross` | 它的头注释里把每一行称为"一个独立的权益来源（付费、邀请、**将来的运营赠送**）" —— 本 ADR 就是那个"将来"落地的时刻，**不需要新判定逻辑** |
| 邀请奖励已经是一条**非购买的**订阅行 | `server/src/activity/invite.ts::grantInviteReward`（`provider='invite'`、`priceId: null`、`grants:['hosting']`） | 先例可抄：不编 `priceId`、复用 `extendSubscriptionPeriod` |
| SKU → 能力的唯一真源，且**未知返回 `null` 而不是 `[]`** | `server/src/billing/price-book.ts` 的 `SKU_GRANTS` / `grantsForSku` | 发放不许接受客户端传来的 `grants`，必须从这里派生（`[]` 是"这档确实不给"，`null` 是"不知道这档是什么"，混用等于给自己发一个说不清的东西） |
| "已定价但交付不了"的清单与它的执行点 | 同上 `NOT_YET_DELIVERABLE_SKUS` / `notSellableReason`，`checkout.routes.ts` 在报价前问一次 | 收银台挡住了，发放也得挡住 —— 否则后台变成收银台旁边那扇没锁的门 |
| 营收看板只读 `checkout_orders.paid_at` 与 `refunds.refunded_at` | `admin.routes.ts` 的 `/revenue` | **发放不建订单行 ⇒ 结构上进不了营收读数**，这条是可以用一条测试钉死的性质 |
| `subscriptions.provider` 是自由文本（只有 `grants` 有 DB CHECK：⊆ `hosting/ai/automation`） | `server/prisma/schema.prisma` `model Subscription`、迁移 `20261018000000_add_automation_grant` | 新增一个 provider 取值**不需要动列**，也就不需要 bump 任何 schema 版本 |

### 1.3 硬约束

1. **不碰钱**：发放不产生 `checkout_orders` 行，不进价目表审计（`pricing_audit_log`），
   因此不出现在营收看板与对账口径里。它动的是**权益**，不是**账**。
2. **改写已有的行 = 伪造购买事实**。一行 `provider='wechat'` 的订阅是"有人付过钱"的证据；
   把它的 `priceId`/`grants` 改掉，等于把一笔没发生的购买写进账本，而且**不可还原**（改前的值没有别处存）。
3. **门禁不因"是后台"放宽**（ADR-0038 §1.3.2）：design/tokens/ui-language/迁移纪律照旧。
4. **交付不了就不许给**（ADR-0023 §3.1 的立场）：`notSellableReason(sku) !== null` 的档位，
   收银台收不了钱，后台也不该把它发出去 —— 发给用户只会制造一个"付了钱/被送了权益却用不了"的客诉。

## 2. 决策

### 一、三种动作 = 两条写路由 + 两条读路由

| 动作（界面上的名字） | 语义 | 路由 | 幂等/并发 |
|---|---|---|---|
| **赠送订阅** | 在该用户的**发放行**上把周期延长 N 天，档位设为所选 SKU；没有发放行就建一条 | `POST /api/admin/subscriptions/grant` | 读-改-写在同一个 `prisma.$transaction` 里；`max(now, 已有到期) + N 天`（同一个 `extendSubscriptionPeriod`） |
| **免费升级** | 只换发放行的**档位**（能力上移），**不加天数**；没有发放行 ⇒ 明确拒绝，不偷偷送一段时间 | `POST /api/admin/subscriptions/upgrade` | 同一事务；换档不改 `currentPeriodEnd` |
| **收回发放** | 把发放行判死（`status='canceled'` + `currentPeriodEnd = now`），**行留着** | `POST /api/admin/subscriptions/revoke` | 没有发放行 ⇒ 404，不折成"已完成" |
| 档位投影 | 后台的档位下拉从服务端取（SKU + 能力 + 当前价 + 是否可交付） | `GET /api/admin/skus` | — |
| 发放记录 | 审计表分页回显 | `GET /api/admin/subscriptions/grants` | — |

⚠️ 名字与语义的对应**不是**"三个按钮三种代码路径"：赠送与升级写的是同一行、
走的是同一套派生规则，区别只在**动不动天数**。写成两条路由是刻意的（见 §3.4）。

### 二、发放只写 `provider = 'admin-grant'` 的那一行

一个用户最多一条发放行（按 `userId + provider='admin-grant'` upsert，与 `invite` 同形）。
**任何其他 provider 的行都不许被这三条路由写到** —— 这条是判据，不是纪律：
`server/tests/admin-subscription-grant.spec.ts` 里有一项"给一个付费用户发放再收回后，
付费行的 `priceId`/`grants`/`status`/`currentPeriodEnd` 逐字段不变"。

为什么这样能同时满足"升级"和"安全"：权益是**并集**，所以把发放行设成更高档
就在发放期内抬高了用户的能力；发放行到期或被收回后，用户回到他**付过钱**的那一档。
收回一个付费用户**不会**让他失去已付费的东西 —— 那仍然是退款（ADR-0053）的唯一职责。

### 三、能力一律服务端从 SKU 派生；不可交付的档位拒绝发放

写入路径上的三道闸门，缺一即 400/409 且**不落库、不留审计**：

1. `grantsForSku(sku) === null` → 拒（价目表与能力表不同步，不是"给零项能力"）；
2. `notSellableReason(sku) !== null` → 拒（交付不了的不发）。响应里带的是**码** `SKU_NOT_DELIVERABLE`，
   `NOT_YET_DELIVERABLE_SKUS` 里那句中文散文**不进响应体** —— 那是
   [ADR-0074](0074-checkout-rejection-reason-is-a-token.md) §三.1 给收银台定下的同一条规矩
   （码进线协议、散文进日志），发放这条路没有理由例外：一句服务端中文会绕过词条表，
   切英文的运营看到的就是一串没人能翻译的字。
3. `days` 非有限整数或不在 `[1, 3650]` → 拒（上限防一次手滑发出一百年）。

客户端**永远不能**提交 `grants`。请求体是 zod `strictObject`：多一个键就 400，
所以"偷偷发一个不存在的能力"不是"我们没做校验"，而是**结构上发不出来**。

### 四、加一张 `subscription_grants` 审计表

这正是 ADR-0038 §4.2 预留的那一步——"要合规级审计就新发 ADR，不悄悄加表"。
本 ADR 就是那份。

| 列 | 为什么必须有 |
|---|---|
| `user_id` | 作用对象。**没有外键**：与 `refunds.requested_by`、`announcements.created_by` 同一处理 —— 账号注销不该把发放史一起带走，也不该因为挂着审计而删不掉账号 |
| `actor_user_id` | 谁点的。后台只有一位运营者，但"只有一位"会变成"有两位"，那时这一列是唯一能追溯的东西 |
| `action` | 封闭词表 `grant` / `upgrade` / `revoke`，**不存中文**（存语义，展示名归 i18n，同 ADR-0038 §3 那条通知立场） |
| `sku` / `days` / `grants` | **写入时快照**：之后运营改价目表不会改写这条历史，正如 `refunds.period_days` 把"当初授予了多少天"冻在退款行上（`server/prisma/schema.prisma` 的 `Refund.periodDays`：冻下来，回收才是可重放的减法而不是对当前状态的猜测） |
| `before_period_end` / `after_period_end` | 能回答"这次动完之后他到哪天花掉"，也能让人一眼看出某次发放是接在旧到期日后面还是重新开始 |
| `reason` | 强制非空。这是 ADR-0053 给退款批准立的那条规矩的直接沿用：**一个会静默改变别人能用什么的动作，必须留下一句人话** |
| `created_at` | 排序与"什么时候点的" |

审计行与订阅写在**同一个事务**里。不是"写完再补日志"：那样崩溃时会出现
"权益已经发出去了但没人知道是谁发的"，而这张表存在的全部理由就是不让那一刻发生。

## 3. 为什么不选看起来更显然的方案

### 3.1 为什么不"就地改用户那条付费订阅的档位"

这是"给别人升级"最字面的实现，也是**唯一被明确否决**的一种。三条理由：

1. **它伪造购买事实**。那一行是"这个人在 X 时刻按 Y 价买了 Z 档"的证据。
   改了它，账本上就多了一笔没有发生的购买，而 `checkout_orders` 里找不到对应订单 ——
   对账时表现为"有条 ¥12 的订阅没有 ¥12 的单"，而那是**真的下过单的人也会被怀疑**的形状。
2. **它不可还原**。改前的 `priceId`/`grants` 只在内存里存在过。要做"可撤销的就地改"，
   就得先存一份改前快照 —— 那张快照表就是本方案的第二步，只是少了一个动作的名字。
3. **它把"钱"和"权益"两套口径焊死**。分开发放行之后，营收读数是钱、发放表是赠送，
   两者可以在同一张订阅列表里并排显示；焊死之后每个读数都要解释"这行是买的还是送的"。

### 3.2 为什么不复用 `provider = 'invite'`

邀请那条是**自动结算**的：它的触发条件是"被邀请人验证了邮箱"，
`settleReferralActivation` 用 CAS 保证一条推荐只结算一次。
把人工发放塞进同一行，会让"邀请奖励发过没有"这个判据变成"这一行存在过"，
而后者是运营手点的 —— 于是奖励的幂等性被一次手工发放破坏（发一次就把奖励标记成已结算的样子）。

### 3.3 为什么不让运营直接填 `grants`

"灵活"的代价是价目表不再是能力的唯一真源：`pnpm check:pricing` 钉的是
`SKU_GRANTS` ↔ 文档 `pricing-ssot` 块 ↔ 词条 ↔ DB CHECK 四处一致。
允许手填 `grants` 等于开一条**绕过这四道**的旁路，而旁路上没有任何门禁。

### 3.4 为什么"赠送"与"升级"是两条路由而不是一个带开关的路由

两者唯一的差别是**动不动天数**，一个 `addDays` 开关看起来更省。分成两条是因为：

- 开关会造出一个**没人核对过的组合**（`upgrade` + `days=30` 是什么？它同时是两条语义）；
- 判据要能红。两条路由 ⇒ 两条"这条不改那一列"的断言各钉一个位置；
  一条路由 + 开关 ⇒ 断言必须写成"`addDays` 为假时不许碰 `currentPeriodEnd`"，
  那种条件断言在变异验证里**很容易两头都测不到**。

### 3.5 为什么表名不是 ADR-0038 §4.2 提的那个 `admin_audit_log`

§4.2 第 4 条预留的是"一张**通用的**后台审计表"。真做的时候分成了两张形状不同的东西：

| 表 | 记什么 | 已有/新增 |
|---|---|---|
| `subscription_grants` | **一类动作**的完整业务参数（发给谁、哪一档、多少天、动完到期日是哪天、理由） | 本 ADR 新增 |
| `pricing_audit_log` | 改价 | 已存在（ADR-0018） |

一张 `admin_audit_log` 要同时装下"改价"和"发放"，它的载荷只能是 `target` + 两个 JSON 串——
那正是 `pricing_audit_log` 现在的样子，而**它已经在为这件事付出代价**：查"某人被发过几次"
要 `LIKE` 一个 JSON 文本。发放需要的列（`user_id`、`sku`、`days`、前后到期日）每一个都是
要被**查**的，不是要被展示的；一张通用表会把它们全部降级成字符串。

所以这一版的立场是：**一类会改别人处境的写动作，配一张它自己的动作表**。
通用日志留给"点了什么"这种不需要被查的足迹（那仍然是 `Logger`，§4.2 那条判断没被推翻，
只是它适用于足迹，不适用于权益）。

## 4. 后果

### 4.1 对 ADR-0038 的影响

§2 第三条「不做：改订阅／退款／发券／群发通知」：

- **"改订阅"一项被本 ADR 部分修订** —— 后台现在**会**写 `subscriptions` 表。
  但**仍然不改写已经存在的行**：三条路由要么新建发放行、要么改发放行。
  所以那句话的**结论**变了，它的**理由**（"需要幂等键、审计与回滚"）由 §2 四 + §2 二 逐条补齐。
- **"发券"与"群发通知"两项没动** —— 没新增 `Coupon` 写面，没新增通知 `kind`。
- **§2 第二条（单级 `isAdmin`，不做 RBAC）没动** —— 新路由挂同一个插件级
  `addHook('preHandler', requireAdmin)`。出现第二位运营者时该重判的仍是那一条。

### 4.2 接受的成本

- 后台第一次能"无中生有"给用户能力。这**扩大的是运营者的权限面**，
  不是外部攻击面（三条写路由都在 `requireAdmin` 之后）。
- 一张新表 = 一次迁移。迁移是只建新表 + 普通索引（表是空的，不需要 CONCURRENTLY）。
- 界面多一个 tab。它必须与"订阅"tab 并存而不是塞进去：发放记录是**动作史**，
  订阅列表是**当前状态**，两者读者问的问题不同（§4.1 那次分家在同一层的延续）。
- **发放不进营收**是一条需要有人守的立场。它靠两条测试守：
  "发放后 `checkout_orders` 行数不变" 与 "`/revenue` 读数在发放前后逐字段相同"。

### 4.3 本版**故意没做**的三件事（不是忘了）

1. **没有防"运营者给自己发"**。测试期这是主要用法；把它做成禁令会让这个能力在第一周就不可用。
   代价是审计表里 `actor === user` 的行需要有人看 —— 它至少是**可见的**。
2. **没有"撤销 = 恢复发放前状态"**。收回就是把发放行判死；如果同一账号之前有
   两次发放，收回作用在**那一行**（一个用户一条发放行），不是撤销"那一次动作"。
   要做逐笔撤销需要"每次发放一行"的模型，而那会让并集出现 N 条赠送来源 ——
   **触发条件是**：出现"要只撤掉某一次赠送"的真实运营场景。
3. **没有额度/上限**（每人最多被发多少天）。当前只有一个运营者、发放对象是内测账号。
   **触发条件**：外部的人能申请发放，或发放变成常规客服动作。

## 5. 未核实项

- ⚠️ 微信/Stripe 的**webhook 回调**会不会把发放行覆盖掉：回调按
  `(provider, providerEventId)` 定位，`admin-grant` 行没有 `externalSubscriptionId`，
  理论上不会被匹配到；测试里钉了"provider 不同的行不受影响"，但**真实回调重放**
  没在生产的订阅表上验过。
- ⚠️ 发放行是否会让 `selfhost-online` 那侧的自动收集判定产生意外：该模式的权益来源是
  官方签发的在线票据，不是本机订阅（`entitlement.ts` 的 `AUTOMATION_ENTITLEMENT_MODES` 注释），
  所以理论上无关；**但官方实例发放 `hosted-ai-monthly` 后自托管端能不能用，本轮没有实测**。
- ⚠️ `days` 上限 3650 是按"十年不会是误操作之外的正常需求"拍的，没有需求侧依据。
- ⚠️ **本轮写判据时撞见的一处既有偏差**（不在本 ADR 的改动面里，登记而不顺手改）：
  `server/src/billing/checkout.routes.ts` 的分支 ①（`PRICE_NOT_SELLABLE`）仍然把
  `notSellableReason(...)` 的那句**中文散文**放进响应体的 `reason`，而 ADR-0074 §三.1
  定的正是"这里只许是码"。它今天**不可达** —— `NOT_YET_DELIVERABLE_SKUS` 是空的，
  那句 `if` 永远不成立 —— 所以下一次往那张清单里加档位时，第一现场会是"英文界面漏出一句中文"。
  判它的断言：那一支的 `reason` 必须匹配 `/^[A-Z0-9_]+$/`（本 ADR 给发放那条路写了同款判据，
  收银台那一支的对应断言**还没有**）。
