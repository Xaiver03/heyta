# 0044 · 倒数纪念日：新增 `EVENT` 实体、农历走 `lunar-typescript`、节假日数据分发、图片走双档

> 状态：**已接受**（2026-10-03）
> 授权依据：产品负责人 2026-10-02 / 10-03 逐条拍板 —— ①"节假日一定要做，不需要联网"；②调休走管理后台、自托管不提供该档；③闰月生日"要么按农历过要么按公历过，这很简单"；④农历用库；⑤图片走双档，"看什么形式最合规"；⑥`EVENT` 实体由本 ADR 下判断。
> 证据基础：[`../research/countdown-anniversary-data-and-images.md`](../research/countdown-anniversary-data-and-images.md)（2026-10-02 实测）。落地工单在 [`../plans/countdown-anniversary.md`](../plans/countdown-anniversary.md)。
> 它同时是 [`../plans/goal-layout-audit.md`](../plans/goal-layout-audit.md) §4 那条「节日标注如要做**需先立数据源 ADR**」所等待的落点。

**为什么四则合一份**：这四条互相咬合，拆开写会让"为什么"断链——建 `EVENT` 才需要部署顺序；走农历库才有 bundle 体积这笔账；图片双档里的"明文档"决定 L 系列法务工单要不要进关键路径。它们是一次拍板。

---

## 1. 背景

heyta 里**从来没有**倒数纪念日这一层：实体清单没有、`packages/i18n` 零词条、`apps/web` 23 个功能面板没有对应目录。零件倒是齐了一半——`Recurrence.yearly()` 已存在但界面没有"每年"这一档，提醒是独立实体但档位只到"提前 1 天"。

调研推翻了此前"无任何节假日数据源"的判断（两个 MIT 且 2026 年仍在提交的来源），并确立了一条必须分清的界线：

| | 可否纯离线预测 | 本 ADR 怎么处置 |
|---|---|---|
| **A 历法**（农历↔公历、闰月、干支、节气） | ✅ 纯算法，零数据文件 | 走库（§2.3） |
| **B 节日**（公历固定 / 农历固定 / 节气 / 第 N 个星期几） | ✅ 全部算得出 | 随包规则表（§2.4） |
| **C 放假安排**（哪几天休、**哪几天补班**） | ❌ 国务院每年 11–12 月发布的行政决定 | 运营录入 + 客户端拉取（§2.4） |

---

## 2. 决策

### 2.1 新增 `EVENT` 实体，不复用 `TASK`

**结论**：建。可加性变更，**不 bump `CURRENT_SCHEMA_VERSION`**（ADR-0014 §3.2 的机制：`applyOperation` 对未建模实体静默忽略）。

**决定性理由不是技术，是语义污染**：`TASK` 的核心语义是**可被勾选完成**——今日视图、四象限、收集箱、习惯、统计全都建立在"完成"这个动作上。倒数日没有"完成"：勾掉一条"母亲生日"要么它消失、要么它顺延，**两种都是错的**，而用户会去点它，因为界面把它摆在今日待办里。这不是实现细节，是把两类东西放进同一个容器后必然产生的错误 affordance。

**否决的替代方案**：`TASK` + payload marker（"它其实不是待办"）。它的问题是把判断推给每一个消费者——此后每一处 `TASK` 的读路径（今日、四象限、时间线、搜索、回收站、导出、AI 工具、小组件）都要各自记得排除一次。**漏一处的症状是"生日出现在今日待办里"，而那正是用户会截图来问的那类问题。** 独立实体让这类错误在类型上不可能发生。

**代价是有界且已付过两次的**：`REMINDER`、`NOTE` 是先例（独立实体 + 服务端白名单 + 不 bump）。

### 2.2 部署顺序是硬的：服务端先于客户端

`packages/shared-schema/src/entity-types.ts` 文件头写明**服务端拒绝未知实体类型**。⇒ `EVENT` 必须**先上服务端、再上客户端**；反过来老服务端会把新客户端的写入整条拒掉，而按 [`../reference/environment-traps.md`](../reference/environment-traps.md) 第 34/41 条的历史，一条被硬拒的 op 曾让设备**永久同步不了**。

自托管部署者会天然落后于我们的服务端 ⇒ 这条不能只写在文档里，要落成一次可判的兼容性检查（计划 W2 的判据之一：**老服务端 + 新客户端必须响亮失败**，不是静默丢数据）。

### 2.3 农历走 `lunar-typescript`，但**体积实测是前置闸门**

**结论**：用库，不自研月表。

依据：MIT、最后提交 2026-08-13、最新发版 v1.8.6（2025-11-05），**两道门都过**（AGENTS §3.1 维护 + §3.2 许可）；README 自述农历/闰月/干支/节气全部内部算法、"无第三方依赖"。同作者的 `lunar-javascript` 更Popular 但更新更慢（2025-11-05），不选。

🔴 **前置闸门**：它是"全量历法 + 黄历宜忌 + 八字"的大集合，我们只用农历换算那一小块，**bundle 体积未实测**。计划 W1 的第一个动作就是量它进包后的字节数；不可接受就退到自研月表（约一张 1900–2100 的月表 + 节气常数）。**这条不是形式**——AGENTS §3.1 被违反过太多次，而"过门"只证明它在维护，不证明它进包后我们付得起。

### 2.4 数据分发按 A/B/C 三档分别定，且**都不进 op-log**

| 档 | 分发方式 | 自托管部署 |
|---|---|---|
| A 历法 | 库/算法，随包 | 有 |
| B 节日规则 | 随包静态表（照 `server/src/*.generated.ts` 的"生成物 + `--check` 门禁"形状） | 有 |
| C 放假安排 | **管理后台运营录入 + 客户端拉取 + 本地缓存**（计划 W4b） | 🔴 **不提供该档**，界面必须**安静降级**（不显示休/班，不报错、不留空块） |

三条共同的硬约束：

1. **不进 op-log、不进用户库、不加密**——它是公共事实不是用户数据。走 op-log 会让每次同步都带上它，并把它伪装成用户写入（违反 AGENTS §3.4「一个用户意图 = 一个 op」）。
2. 🔴 **C 是本仓库第一条"服务端→客户端下发内容"的通道**（今天下行只有密文 op-log 与计费元数据）。它与 AGENTS §1「云端只是同步通道，**不是事实源**」字面冲突，本 ADR 给出定性口径：**那句话约束的是用户数据；公共事实由部署方下发不构成例外**。这个口径是承重的——它会被后面的人拿去判别的东西能不能走这条通道，所以计划 §7 第 7 条要求同时立一条限制（该通道只允许 `days[]` 这一种形状）。
3. **必须保留公告原文出处**（`papers` 里的 gov.cn 链接）随数据入库并能在后台回显。抄进代码那一刻就失去了举证能力。
4. C 要录入就必然给管理后台开一类新资源 ⇒ **回写 ADR-0038 的范围表**，不登记就是边界漂移。

### 2.5 闰月生日：**归一化到同名正月**，闰月那年可选再过一次

产品负责人说得对，这是常识，我此前把它当悬案是错的。两层结构：

- **第一层（用户的选择）**：这条生日按**公历**过还是按**农历**过。界面上就这两个，与滴答的公历/农历切换同形。
- **第二层（只在"按农历"且生日落在闰月时才存在）**：默认**归一化到同名正月**——即民俗口径「**逢闰过正**」，闰五月出生的每年过农历五月，不在闰月年过两次。

🔴 **但真正的理由是技术必然性，不是民俗偏好**：闰五月不是每年都有的（它隔 8 或 11 年才出现一次），所以"只认闰五月"会让大多数年份**算不出下一次**。归一化是唯一能让"下一次"年年有解的做法。**用户可选的从来不是"要不要归一化"，而是"闰月那一年要不要额外再过一次"**（那是加一条提醒，不是替代规则）。

⚠️ 民俗口径的取证来自生活方式类站点（非权威），但本决策**不依赖它的正确性**——依赖的是上面那条"年年有解"的必然性。滴答在闰月上具体怎么处理**未取证**（截图里农历月份下拉有没有"闰八月"这一项看不出来）。

### 2.6 素材图片走**双档**，默认端到端加密

**结论**：默认档 = 图片在**客户端加密后才出设备**；自托管部署方可**显式开启明文档**；**我们托管的实例永不启用明文**。

决定性依据不是"隐私优先"，是实测：Apple 高级数据保护把**照片**纳入端到端加密（25 类数据），它放弃的**全是运营方能力**（服务端索引、服务端搜图、iCloud.com 直读、代客恢复、共享相册），**用户侧功能一项没少**；Ente 是整站在架的端到端加密云相册。⇒ "要图片"与"服务端能读图片"是两件事，这里不存在"为了隐私牺牲功能"的取舍。

反证明文档的代价（这是"看什么最合规"那条指令的答案）：明文图片的处理对象是人脸/儿童/行程/医疗与财务场景，按 PIPL 第 28 条属**敏感个人信息**，随之需要 ①**单独同意**（第 29 条，独立可拒）②**监护人同意**并改 `packages/legal/src/documents/minors.ts` ③**个人信息保护影响评估**（第 55 条）——而实测 `packages/legal` 搜「影响评估」**零命中**，这份文件**现在根本不存在**。客户端加密之后这三件事整块不发生。

三条必须如实接受的代价（不许略过）：① 忘记密码 = 素材图**不可恢复**（除非走我们已有的恢复凭据那套）；② 服务端不能生成缩略图 ⇒ 客户端生成；③ **校验与时间戳仍会泄露元数据** ⇒ 政策要写"我们留什么"，**不能写"我们什么都看不到"**。

🔴 **第一版不触发这一条**：卡片背景用预置模板（配色/排版/图标），零上传、零新通道、零法务变更。区分在于**成品图**（设备上渲染导出的卡片）≠ **素材图**（用户实拍）。

## 3. 后果

1. **法务不是收尾动作，是前置闸门**（计划 §4 的 L 系列）。`packages/legal/src/documents/permissions.ts` 现在写着「heyta **不申请**…照片…相机…权限」——**能选照片的构建一出厂这句就是假话**。所以 L1/L4/L5 挂在"第一个带照片的构建"之前，不是之后。倒数日纯文字版不触发。
2. **落地页不许手改**：文案是 `packages/legal` 的生成物（`check:legal-copy`，实测已在 `pnpm check` 链里）。改真源 → 重跑生成 → 门禁保证不漂移。
3. **`EVENT` 不会让任何 AI 门禁变红**：`scripts/check-ai-tools.mjs` 钉的是"确认前不得落 op"，`scripts/check-ai-coverage.mjs` **由 `AiFeature` 联合类型驱动而非实体清单**。⇒ 加了实体却漏接工具目录是**静默通过**，正是 `check-ai-coverage.mjs` 文件头自陈"仓库里已出现 12 次以上"的那类失效。本 ADR 要求把工具目录改成由 `ENTITY_TYPES` 驱动（计划 W10），否则这条决策在 AI 侧等于没做。
4. **PIA 缺口独立于本功能存在**（委托处理腾讯云按第 55 条第 3 项也可能触发）⇒ **单独立项**，不塞进倒数日。
5. `EVENT` 与 `TASK` 共用 `REMINDER` 实体，而它的 id 形状是 `taskId:triggerAt` ⇒ 要么扩这个形状、要么给 `EVENT` 的提醒另立，**不能假装它不存在**（计划 §7 第 6 条）。

## 4. 明确不做

- ❌ 世界其他国家节日：`commenthol/date-holidays` 的数据是 **CC-BY-3.0**，不在 AGENTS §3.2 允许表内（表里只有 CC0），要用得先在 `REVIEWED_OTHER` 逐项登记 + 生成署名文件。
- ❌ 内置图标的**预置含义**（旅行/发工资/信用卡还款…）：给图标不给含义，与 ADR-0022 那条"颜色由用户赋义、App 永不判断健康/不健康"同构。
- ❌ 判负表达：逾期不飘红、不弹"你忘了"。倒数日的"已经 N 天"必须只与自己的过去比（AGENTS §9 激励红线）。
- ❌ 共享/协作倒数日：E2EE 下排行榜/联赛那类结构上不可能，同一条理由适用于"两人共管的纪念日"。

## 5. 勘误段（2026-10-03 追加；按 `docs/adr/README.md` 里「1a. 勘误段」那一节，正文一字未改）

**§2.3 里那句"退路是**自研月表**（约一张 1900–2100 的月表 + 节气常数）"是错的，而且错在低估了成本。**

追加这条不是为了记录一次失手，是因为**这句话会被下一个人当作工作量依据**——它把退路描述成"抄一张表"（约 2–4 KB 的体力活），而实测的真相是：

- 体积闸门实测（2026-10-03）：整包 `dist/index.mjs` **424,612 B**（gzip 108,026 B）；`sideEffects` 未声明、`exports` 只有一个 `.`。
- 🔴 更关键的是**没有表可抠**：`LunarYear.compute()` 是**算法型**——用 `ShouXingUtil`（66,456 B 天文常数表）实时求朔日与节气，不查任何 1900–2100 的编码月表。
- 且 `Lunar.mjs` 直接 import `EightChar` / `NineStar` / `ShuJiu` / `Fu` / `Foto` / `Tao` / `JieQi` / `LunarTime` / `LunarYear` ⇒ **"只取农历那一小块"在这个库里不成立**。所谓最小闭包实测 194,668 B，仍接近整包。

⇒ 因此本 ADR §2.3 授权的退路分支被触发，但退路的**真实形状**改判为：

> **构建期生成 + 运行时查表**：用公开天文算法（Meeus 新月 JDE 序列 + 太阳黄经求中气，定朔、东八区）在 `scripts/` 里**离线生成** 1900–2100 的农历编码表，产物作为 generated 文件随包（照 `server/src/*.generated.ts` 那套"生成物 + `--check` 门禁"先例），运行时只查表。
>
> 这样做的三个理由：① 运行时体积是**数据**（约 2 KB）而不是算法；② 天文算法只出现在构建期，不进四个端的包；③ 公式是数学、不受著作权保护，**避开了"复制别人那份编码数组"的许可问题**（那才是查表型方案真正的雷）。

**取证边界必须如实说**：生成的表只在 **2007–2027（holiday-cn 覆盖的 21 年）** 有权威反证——判据是"算法算出的正月初一/五月初五/八月十五必须落在国务院公告给出的春节/端午/中秋放假日期集合内"。1900–2006 与 2028–2100 这些年**功能可用但无独立验证**，界面上不得暗示全区间都被证明过。

⚠️ 本段只追加，不改 §2.3 正文一字（`docs/adr/README.md` 里「1a. 勘误段」那一节 的硬边界）。§2.3 的**结论**（先实测体积、不可接受就走退路）依然成立且刚刚被证明是承重的——它拦下的不是"体积大一点"，而是**把八字/宜忌/吉凶整套塞进四个端**，那与 AGENTS §9「App 永不判断某个活动健康／不健康」的红线方向相反。

### 5b. 第二次勘误（2026-10-03 批次一落地时追加；§5 正文一字未改）

**§5 提议的退路形状——"用公开天文算法（Meeus）离线生成随包表"——落地时被改判为：随包数据源取 `lunar-typescript`（只在构建期），Meeus 实现降格为独立反证。**

改判的依据不是偏好，是**实测出来的两个错日**：本仓库自带的那份 Meeus 实现（新月 JDE 序列 Ch.49 + 太阳视黄经 Ch.25，含 ΔT 与全部规范小项）把

| 年 | 随包数据源 | Meeus 独立实现 | 公开日历 |
|---|---|---|---|
| 1988 | 正月初一 **02-17** | 02-18 | 02-17 |
| 2030 | 正月初一 **02-03** | 02-02 | 02-03 |

成因是这两年的合朔压在**东八区子夜 ±11 分钟**内，级数截断误差足以判到另一侧。⚠️ 关键是它的**表现形态**：不会崩、不会报错，只会让"1988-02-17 出生的人农历生日显示成腊月三十"——而**没有人会把这种错归因到历法表**。§5 原本把"公式是数学、不受著作权保护"当成选 Meeus 的理由之一，这个理由成立；但"谁算得对"它没有回答，而随包数据必须回答。

⇒ 裁决口径（写下来，供后来者复用）：**随包的那一份必须与用户在别的公开日历里看到的日期一致**。界面说"今天是正月初一"而全社会的日历说不是，那是应用在用户对说谎，不是"算法流派差异"。两源分歧因此不藏、不改判据绕开，而是**登记成判据**（见下）。

**同时更正 §5 最后一段的取证边界**：原文写"2007–2027（holiday-cn 覆盖的 21 年）"。**2027 的国务院公告当天根本还不存在**——上游 master 的最新数据发布是 2026-01-01，实际覆盖 **2007–2026 共 20 年**（2026-10-03 实测）。这个错误恰好是本 ADR §2.4 那条 C 类判定的活样本：调休/放假安排只在公告发布后可知，**任何把区间上界写成一个还没被证明的年份的做法都是在造空头承诺**。现在这个上界**由 `scripts/vendor/holiday-cn/` 里实际存在哪几年推导**，不由人写死。

🔴 **`--bundle` / `--verify` 现场打印的数字不要抄进任何文档**（包括本节）。分母（公告条数 / 自洽年数 / 扫描文件数 / 入口字节数）会随 vendor 目录与依赖版本变，抄一份就漂一份。要看就跑 `pnpm check:calendar`。

落地后的反证结构（三条互相独立的证据链，取代 §5 设想的那一条）：

| 反证 | 谁对谁 | 抓到过什么真缺陷 |
|---|---|---|
| ① 双实现 | 随包数据 vs 本仓库自带 Meeus，逐年比正月初一 / 闰月月序 / 清明 | 1988、2030 的春节各差一天；2033 的闰月两源口径不同 |
| ② 公告 | 算出的节日日期 ∈ 国务院公告的**放假日期集合** | lunar-typescript 的闰月月序是**负数**，`& 0xf` 存成 11 ⇒ 一次照出 **10 条**不一致 |
| ③ 内部自洽 | 每年 13 个月长之和 = 次年正月初一 − 本年正月初一 | 补上①②盖不到的 bit 位（翻掉 2020 年"九月"那个 bit，①②都不动，③会红） |

三处分歧（1988 / 2030 / 2033）登记成**集合相等**而不是"跳过这些年"：多一年是红，少一年（被修好了却没删登记）也是红。理由同 §5 的立场——**豁免是断言**。
