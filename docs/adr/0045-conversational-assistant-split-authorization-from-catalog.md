## 1. 背景

### 1.1 触发这件事的实测

产品负责人给了竞品「滴答助手」的 4 张截图（2026-10-02 拍摄）。它一句话"14 号去上海谈业务"之后，
界面显示"**已调用 4 个工具**"，展开是思考块与工具块交替：
`search_tools` → `UserPreferencesTool` → `CalendarInfoTool` → `TaskCreateBatchTool`，
最后落一张**可交互的任务卡片**（勾选框 / 标题 / 橙色日期 / 所属清单）。

对照 heyta（全部 `file:line` 见审计文档）：

- **形态是严格单轮**：请求体的 `messages` 在 `packages/ai/src/routing.ts` 里**写死成 `[system, user]` 两条**，
  `AiInvocation` 没有 `messages` 也没有 `history` 字段 ⇒ **第二轮在类型上表达不出来**。
- **工具目录 6 个**（3 读 3 写），只碰 `TASK` / `PROJECT`；竞品对外目录 **51 个**。
- **单步锁**：`packages/app-host/src/ai-tool-call.ts` 遇 `calls.length > 1` 直接判失败
  （"当前只支持单步"）。而 `get_task` / `update_task` / `complete_task` 要 `taskId`，
  拿 `taskId` 必须先读一次 ⇒ 两次调用 ⇒ **这 3 个工具已实现，但在 AI 路径上结构性不可达**。

⇒ 结论：**写入能力今天是可达的**（`requestToolCall → runSelectedTool → 提案 → confirmAiToolProposal`），
挡住的不是缺零件，是**一个架构约束**。这条区分是本 ADR 存在的前提 ——
它意味着"做助手"的主体工作是**放开约束 + 补目录**，不是重写执行层。

### 1.2 为什么"当初的禁令"今天不再成立

ADR-0005 给的否决理由有三条（隐私面 / 工程面 / **失败模式**不同）。逐条重判：

| 当初的理由 | 今天成立吗 | 判定 |
|---|---|---|
| 隐私面不同 | **仍然成立，但已被解掉** | ADR-0035 早已给出多步的出境解法："循环**开始前**按可达工具集算出字段并集**一次性披露**；步骤要发集合外字段 → **停**"。⇒ 多轮**不需要**推翻逐字段披露，见 §2.3 |
| 工程面不同 | **成立，且是成本** | 承认：多轮要改数据面契约、要处理会话持久化。这是本 ADR 接受的代价，不是被反驳的论点 |
| 失败模式不同（"单点面板错了只错一个字段，agent 会连续做错五件事"） | 🔴 **仍然成立，是本 ADR 的主要风险来源** | ⇒ §2.4 那五条不变量**一条都不许动**，并新增硬上界（§2.3） |

⚠️ **诚实的一条**：本 ADR 不是"当初判断错了"，而是"**当初挂的那个条件现在成立了**"。
`feature-matrix.md` §11 写的是"内嵌 AI 聊天助手（**除非明确有差异化价值**）"。
差异化价值现在的形状是：**竞品在 2026-09-29 才上线这个形态**（三区 release notes 同一句），
而 heyta 有一件它结构上给不出的东西 —— §2.4 的"AI 改不动你的数据，除非你点头"。

## 2. 决策

### 2.1 内置 AI 助手 = 对话式、多轮、多步，**以一次写提案收尾**

- 一个 `assistant` 会话形态：模型可以在一次用户轮次里连续调用多个**只读**工具，
  看到结果再决定下一步，**最后至多产出一个写提案**。
- 🔴 **"至多一个写提案"是本 ADR 的核心约束，不是性能限制。**
  理由：一次对话里连续落 5 个 op，等于让模型替用户做了 5 次"要不要改"的判断，
  而 §1.2 那条"失败模式"风险恰恰只在写入上不可逆。
  所以循环放开的是**读**，写仍然**一次一个、一次确认**。
  ⚠️ 这**不等于**不能建多条任务 —— 那是**一个**提案内含多条（对齐 ADR-0035 §"一个意图一个 op" 与
  AGENTS §3.4"多实体变更要在一次操作里完成"），见 §2.5。
- 会话历史**持久化在本地**，是**用户数据**：它进 op-log 还是只进本机库，见 §5 待决 D-4。
  本 ADR 只定：**默认不出境**，出境的是"这一次请求实际带的消息"。

### 2.2 一份工具目录 + 一个执行核 + **两个授权前端**

产品负责人那句"在 AI 助手当中直接就改完了，没有必要用 MCP"——**说对了一半，说错了对象**。

- ✅ **对的那一半**：内置助手**不该**沿用入站 MCP 那套"每个工具单独默认关、用户先去设置页逐个打开"的授权模型。
  两者是**不同的信任上下文**：入站是**不认识的外部程序**要读用户的密文；
  内置是**用户自己的应用**，而用户已经在对话框里说了"去做"。
  把它们绑成一份（ADR-0035 §2 第 2 条）的实际后果是：助手想改一条任务，
  用户得先跳去设置页开六个开关 —— **这就是今天"AI 只能读不能干"的直接原因之一**。
- ❌ **错的那一半**：`packages/local-api` 不是"助手内部走的一条路"，它是**另一个产品功能** ——
  入站接口，让外部 AI 客户端（Claude / Cursor / 豆包）来开 heyta。
  竞品两件事都做了（应用内 AI 助手 + `mcp.dida365.com`）。**删掉入站侧不会让助手变强，只会少一个功能。**

**结论**：拆**授权层**，不拆**目录层**。

| 层 | 份数 | 位置 | 为什么 |
|---|---|---|---|
| 工具目录（名字 / schema / 说明 / 读写属性） | **1** | `packages/local-api/src/tools.ts` | ADR-0035 的原判据不变：**两份目录一定漂**，而目录本来就是"给模型看的" |
| 执行核（授权复查 / 参数语义 / 读执行 / 写意图） | **1** | `runSelectedTool()`（`ai-tool-run.ts`） | 同上。"同一个判断写四遍"是本仓库付过学费的形状 |
| **授权前端** | **2** | 入站：`localApi.grants`（逐工具默认关）<br>助手：**能力档位**（读 / 写两档，或会话级临时授权） | 信任上下文不同 |

- 🔴 `isToolGranted()` 收成**单一实现**，两个前端各自注入自己的 grants 来源。
  **不许**出现第二个"判断有没有授权"的函数。
- ⚠️ **副作用要写明白**：助手侧不再逐工具授权后，**目录里每加一个工具，助手就自动多一个能力**
  （入站侧不受影响，它仍默认关）。这正是 §2.7 那条门禁能成立的前提，
  也是为什么能力清单必须**生成**（§2.6）—— 手工维护的清单在目录一扩就立刻说谎。
- 入站侧**一条判据都不改**：默认关、只监听回环、令牌检查先于工具查找、未授权即不可见、加密条目可列举不可读。

### 2.3 多轮与多步的数据面：消息数组 + **一次性并集披露** + 硬上界

- `AiInvocation` 的 `system` / `user` 两个字符串 → **`messages` 数组**（`role` + `content`）。
  `routing.ts` 不再写死两条。
- 🔴 **出境授权不逐轮重问，但也不无限扩**。沿用 ADR-0035 已给的解法并落成实现：
  1. 循环开始前，按**本次可达的工具集**算出字段并集，**一次性**披露给用户；
  2. 任何一步要发**集合外的字段** ⇒ **停**，返回一个独立原因（不复用 `network`、不静默放行、不自动重试）；
  3. 用户看到的披露里**必须包含工具名**（`provider.ts` 的既有立场：工具名本身也是出境数据）。
- 🔴 **新增硬上界**（§1.2 那条"失败模式"风险的直接对策）：
  单次用户轮次内的**最大工具步数**、**最大消息数**、**最大出境字节数**三个常量，
  全部从 `packages/ai` 导出、有测试钉住、触顶时**明确报"我停在这里"**而不是静默截断。
  理由：没有上界的多步循环，出境量是**模型决定的**，而 ADR-0010 的立场是出境量由**用户批准的集合**决定。
- 会话历史的**保留与导出**沿用既有导出纪律（含墓碑、可核对 `counts`），不另开一套。

### 2.4 五条**一条都不许动**的不变量（本 ADR 的边界）

这五条是 heyta 在 E2EE 前提下唯一不可让渡的资产。任何"向竞品看齐"的改动以它们为代价，
**则该改动作废，不是它们作废**：

1. **AI 类型上产不出 op**（ADR-0005）。`AiSuggestion` 里没有 `OpType` / `entityId` / 向量时钟。
2. **全仓 `host.submit` 恰好一处**，在 `confirmAiToolProposal()`，由 `check:ai-tools` 静态钉住
   （钉的是"**恰好**一处"，不是"在确认函数里" —— ADR-0035 明确说过 weaker 判据会漏）。
3. **出境逐字段披露**，`fields` 必填，工具名也算出境数据。
4. **回退不得跨越隐私边界**（`fallback-needs-consent`，从不自动重试到另一目的地）。
5. **入站本机 API 默认关 + 只监听回环 + 逐工具授权**（ADR-0011）。

⚠️ 竞品在 1–3 上**都不如我们**：它的"先展示方案等我确认"是**写在帮助文档的示例 prompt 里**、
靠用户自己粘上去；它**没有**逐工具授权，读写同一个 OAuth 级别，
唯一的危险提示是一句散文"删除后将无法恢复，请谨慎操作"。
⇒ 本 ADR 放开多步**之后仍然保留确认**，是**有意比竞品严**，不是没跟上。

### 2.5 批量：一个提案可以含多条变更，但**限制批量大小**

竞品的 `batch_add_tasks` / `complete_tasks_in_project` 带**单次上限 20**，
`list_undone_tasks_by_date` 带**跨度上限 14 天**，`upsert_habit_checkins` 带**回填范围最近 90 天**。

**采纳这个形状**。理由不是"它也这么做"，而是**上限同时是三件事**：
出境数据量的上界（§2.3）、一次确认的认知负荷上界（§2.4 第 2 条）、
以及"一个用户意图 = 一个 op"（AGENTS §3.4）在多条变更时的**唯一合法表达方式** ——
一个提案、一次确认、一次 `submit` 里落多条，而不是 fan-out 成 20 次确认。

### 2.6 能力清单必须**生成**，且拒绝话术必须区分两件事

竞品在截图里那句"纪念日在我们只能查看、不能新建"——**对用户是一句产品谎言**：
它的产品本身支持公历/农历生日 + 多提醒 + 重复，只是**没给 AI 配那个工具**
（官方目录里纪念日只有 `list_countdowns` 一个只读工具）。

- 🔴 **纪律一**：能力清单（"哪个实体、哪些字段、可读还是可写、还是根本没有工具"）
  **只能从工具目录与 `EntityModelMap` 生成**，配 `--check` 门禁，不一致 exit 1。
  **禁止手写** —— 手写抄件必然漂（本仓库立场），而漂了的清单会让模型**自信地说不存在的不存在**。
- 🔴 **纪律二**：拒绝话术必须区分「**我没有这个工具**」与「**产品做不到**」。
  正确形状："我做不到这件事（没有对应工具），但产品支持它，路径是 Y。"
  ⇒ 这条是**产品行为**要求，落成 §2.7 门禁的一部分。
- **与 [ADR-0044](0044-countdown-anniversary-entity-calendar-data-and-image-tiers.md) 的咬合**：
  `EVENT` 实体与其 AI 工具**同批**。这既是产品负责人"倒数日我们就应该支持"的落点，
  也是唯一一处能在同一个功能上**比竞品先做对**的机会。

### 2.7 新不变量：**AI 覆盖面 = 界面功能面**

产品负责人原话："我们界面当中有的功能都支持通过 AI 去直接改。"
落成**门禁**而不是愿景：

> `EntityModelMap` 里每个**用户可操作**的实体，必须有工具；每个工具必须有一条模型可选得到的路径。

- 分母口径必须钉死（审计 §3.2 的三个易混点）：
  `EntityModelMap` 有 10 个成员，但 `AI_FEEDBACK` / `PREFERENCE_CORRECTION` 是 AI 反馈的**落库载体**、
  用户不直接创建 ⇒ 分母是 **8**；
  **四象限 / 今日 / 搜索不是实体**（`entity-types.ts` 设计原则第 2 条"视图不建实体"）⇒ **不进分母**，
  否则门禁的分母会随视图增删漂移；
  `TASK_REPEAT_CFG` 在 `ENTITY_TYPES` 里但**不在** `EntityModelMap` ⇒ 它算"动作"不算"已物化实体"。
- 现状基线：**2/8**。
- 🔴 这条门禁**必须能失败**：先用"删掉一个工具"跑出红，再补绿。

## 3. 否决的选项

| 选项 | 为什么否决 |
|---|---|
| 新建 `packages/ai-tools` + 第二份工具目录 | ADR-0035 的原判据**继续有效**：目录、schema、执行器、写入口都已存在，两份一定漂。**本 ADR 拆的是授权，不是目录** |
| 助手侧沿用 `localApi.grants`（现状） | §2.2：不同信任上下文共用一份授权，后果是"用户想改一条任务得先开六个开关" |
| 放宽入站 MCP 的逐工具默认关，好让"两边一致" | 🔴 那是**降低安全基线来迁就便利**，方向反了。要一致就往**更严**一致，且入站侧的严格是 ADR-0011 的立身理由 |
| 循环里允许多个写提案（"一步一确认，用户点五次"） | §2.1：一次对话连续落多个 op = 让模型替用户做多次不可逆判断，正是 §1.2 那条失败模式。**读放开、写不放开** |
| 靠 `AiFailureReason` 加一条"来源被拒"来诊断本机端点 403 | 🔴 **技术上不可能**（§4 实测：403 不带 `ACAO` ⇒ 浏览器拦成 `TypeError`，JS 根本看不到状态码）。改成**上下文推导**，见 §4 |
| 手写一份能力清单喂模型 | §2.6 纪律一：抄件必漂，而漂了的清单**主动**制造错误结论 |
| 顺手"接通"托管 AI 以让助手可用 | ADR-0013 / ADR-0023：`assertEnableable()` 抛 `retention-undecided` 是**有意的失败**，且 `hosted-ai-monthly` 在计量存在前**不得售卖**。本 ADR 一条都不碰它 |

## 4. 同批必须修掉的一条：本机端点的跨源失败**今天被说成"暂时性网络问题"**

这是实施前的实测（2026-10-02，本机 Ollama 0.23.2，四个探针）：

| 探针 | 结果 |
|---|---|
| 无 `Origin`（非浏览器） | **200** |
| `Origin: http://127.0.0.1:4321` | **200** + `Access-Control-Allow-Origin` **回显该来源** + `Vary: Origin` |
| `Origin: https://heyta.waytofuture.cn` | **403，`Content-Length: 0`，且完全没有 `ACAO` 头** |
| 坏来源下的 `OPTIONS` 预检 | **403，无 `ACAO`** |

三条后果，逐条都是**已核实的代码事实**：

1. 因为 403 **不带 `ACAO`**，`fetch` 抛 `TypeError` 且 **JS 拿不到状态码** ⇒
   `packages/ai/src/routing.ts` 的 catch 分支归成 **`'network'`**，**不是** `'http-error'`。
2. 而 `apps/web/src/features/ai/ai-failure-copy.ts` 给 `'network'` 的注释与设置跳转目标分别是
   "网络与空响应是**暂时性**的，设置里改什么都修不好" 与 `undefined`（不给"去设置"）。
   🔴 **这句注释就是 bug 本身** —— 对本机端点而言它既不暂时、设置里也确实有该说的话。
3. Ollama 默认放行的是 **loopback 来源** ⇒ **只有开发机上的 localhost 页面能用本机端点**。
   生产 Web 壳（HTTPS 域名）、macOS 壳（`heyta-local://app`）、Windows 壳（`https://heyta.local`）
   **全部必然撞上它**。这也解释了为什么它至今没被发现：**所有人都在 localhost 上测**。

**为什么探针一直看不见**：`e2e/stub-provider.mjs` 的假端点**不是不懂 CORS** ——
它的文件头把这类症状的误导性写得极准（"CORS 拒绝 → 应用层拿到 `Failed to fetch` →
界面渲染成'无法连接端点'，而假端点其实活得很好"）。但它**无条件回 `ACAO: *`、从不拒绝** ⇒
**知识在本仓库是已有的，判据只测了放行那一侧。**

**处置**（写进 §2.7 的同一批工单，W1）：

- 分类**不在** `AiFailureReason` 上做（技术上看不见状态），而是加一层**上下文推导**：
  给定 `(reason, 端点是否 loopback 预设, 页面自身 Origin)` 纯函数地判
  `origin-likely-rejected` vs `transient-network`。`AiFailureReason` 那个封闭词表**不动**。
- 界面文案改为**带具体值**：把用户该放行的 Origin 原文打出来 + 可复制，
  并指向 runbook。**不硬编码域名**（域名会变）。
- 🔴 **根因级判据**：假端点必须能配置成"**读 `Origin` 并按白名单拒绝、且不带 `ACAO`**"，
  否则这条缺陷结构上不可能被任何 e2e 抓到。
- 变异要求：把推导函数改成恒返回 `transient-network` ⇒ 相关用例必须红。

## 5. 后果与待决

**后果（接受的代价）**：

1. **数据面契约变了**：`AiInvocation` 从两个字符串变成消息数组 ⇒ 四个既有面板全部要过一遍，
   且"给四个既有功能加工具线格式对它们零影响"那条既有保证要重新验证。
2. **目录扩了助手就自动多能力**（§2.2 的副作用）⇒ §2.6 的生成式清单从"更好"变成**承重**。
3. **还结构债是前置**，不是并行：`describeRoutedFailure` 实测**抄了四遍**、
   `createProvider` 与 `invokeRouted` 两套请求组装并存。现在加 loop，**重复会乘二**，
   而失败分类一旦漂移，**出境披露的措辞会跟着漂**（那是隐私文案，不是日志）。
4. **回退不干净**（这是本 ADR 最需要被记住的一条）：多步一放开，出境口径就从"一次调用"变成"一次会话"。
   ⇒ **回退必须连带让已发放的会话级同意全部失效**，实现上要求同意里带**代际号**，
   回退时代际号 +1，旧同意逐条自然不匹配。**不许**留成"降级后旧同意继续生效"。
5. 移动端与 Electron 壳**仍然零 AI 入口**。本 ADR 不解决覆盖面，只解决形态与能力。

**待决**：

- **D-4 会话历史落在哪**：进 op-log（跨设备同步、但历史本身是明文语义的敏感数据）
  vs 只进本机库（换设备要重学）。**默认本机**，但这是产品判断，未拍。
- **D-5 助手侧授权档位粒度**：两档（读 / 写）vs 按实体分组 vs 会话级临时授权。
  §2.2 定了"要拆"，**没定拆成几档** —— 实现按两档起步，改主意只动一个前端。
