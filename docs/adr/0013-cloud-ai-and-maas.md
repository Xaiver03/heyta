# ADR-0013：云端 AI 与 MaaS —— 方向已定，但**开放条件仍然未满足**

- **状态**：已接受（2026-09-26）
- **相关**：[ADR-0006](0006-supply-modes.md)（供给模式）、[ADR-0010](0010-ai-config-routing.md)（配置路由）、[ADR-0011](0011-local-api-mcp.md)（本机 API / MCP）
- **取代**：[`docs/plans/ai-open-decisions.md`](../plans/ai-open-decisions.md) 决策 2 的**结论**（原为"暂不提供托管 AI"）

---

## 1. 背景：产品方向由产品负责人明确

在此之前，我在 [`ai-open-decisions.md`](../plans/ai-open-decisions.md) 的决策 2 里
按自己的建议**定案为"暂不提供托管 AI"**，并写进了界面文案
（`data-testid="managed-ai-note"`）。

产品负责人随后明确：

> 「我们肯定也会提供云 AI 呀……我们肯定会在云端提供一个统一的 AI 服务，
> 然后根据这个来收费。就是后面的话我们会提供 MaaS，我们会把 API 接进去，
> 然后我们只要在软件当中集成一下 Harness 就好了。」

**这推翻了那个结论。** 托管 AI 不是"不做"，而是"还没到时候"。

> ⚠️ 我当时的错误不在于判断保守，而在于**把"我暂时无法决定"当成了"决定不做"**。
> 并把那个结论**写进了用户可见的界面文案** —— 那是最贵的一种错，
> 因为它会变成产品对用户的承诺。

## 2. 决策

1. **heyta 会提供统一云端 AI 服务**，并按此**收费**。
2. 后续提供 **MaaS**（把模型 API 接进来对外提供），
   客户端侧只需集成 **Harness**。
3. 因此 `AiSupplyMode` 的 `managed` 分支**是产品要走的路线**，不是死代码。

## 3. 🔴 本 ADR **不**改变 ADR-0006 的任何结论

这条必须写清楚，因为它是整件事里最容易出事的地方。

[ADR-0006](0006-supply-modes.md) 的结论是：

> 托管 AI **可以提供**，但**绝不能**被描述成端到端加密。

这个结论**依然成立，且现在变得更关键**：既然托管 AI 确定要做，
那么"用户的任务内容会以明文到达 heyta 服务器"这件事就**一定会发生**。
ADR-0006 不是"如果做的话要小心"，而是"做的时候必须这样标注"。

对比一下两条产品线的性质差异（这是本 ADR 的核心判断）：

| | 自托管同步 | 托管 AI |
|---|---|---|
| 数据到了谁的机器 | 用户自己的服务器 | **heyta 的服务器** |
| 与 E2EE 的关系 | 中性（密文上传） | **互斥（必须解开才能送模型）** |
| 结论 | 两种都提供 | **提供，但必须标注为例外** |

## 4. 要真正开放托管 AI，还差什么（诚实清单）

`assertEnableable()` 目前**故意抛错**挡住 `managed`。
我的判断是：**这个拦截现在仍然应该留着** —— 因为下面 5 件事没有一件完成。

| # | 缺什么 | 性质 | 为什么它挡着开放 |
|---|---|---|---|
| 1 | **服务本体** | 工程量 | 还没有任何云端 AI 服务可指 |
| 2 | 🔴 **数据保留策略** | **产品/法务** | ADR-0006 §5：未定案就不开放。`describeRetention('heyta-cloud')` 现在返回 `undefined`，披露里会显示"未定案" |
| 3 | **计费与计量** | 产品 + 工程 | "按此收费"要求服务端能计量；这又要求记录用量，而**用量记录本身就是一种数据保留** —— 与第 2 条是同一件事的两面 |
| 4 | **Harness 集成的边界** | 架构 | 见 §6（我需要先确认"Harness"具体指什么） |
| 5 | **"哪些任务允许上云"的粒度** | 产品 | 全库上云 vs 逐条选择，对 E2EE 产品的用户是完全不同的承诺 |

### 4.1 为什么第 2 条和第 3 条是同一件事

"按用量收费"意味着服务端必须知道**用量**。而 AI 用量和内容强相关
（token 数由内容长度决定）。所以：

> **计费一旦落地，就必然产生一份"谁在什么时候用了多少"的服务端记录。**
> 那份记录本身就是保留策略要回答的东西。

所以不能"先把计费做了，保留策略以后再说" —— 那样会先产生数据，再补规则。

## 5. 界面上现在应该怎么写（本轮已改）

`managed-ai-note` 的文案必须改：它现在写的是
「我们没有提供『heyta 托管的 AI』。这不是还没做……」——
**这句话现在是错的**，而且错在产品对用户的承诺上。

改成：**"即将提供"**，并明说它的性质（内容会到 heyta 服务器、不是端到端加密），
而不是说"我们不做"。

## 6. 未决：需要产品负责人澄清的一点

「在软件当中集成一下 **Harness**」里的 Harness，我需要确认指的是哪一个：

- **A. DeepSeek Harness（本机这个 agent 运行时）** —— 那么它的运行位置决定了
  数据路径：跑在用户设备上 vs 跑在 heyta 云端，是两套完全不同的隐私承诺。
- **B. 某个自研的 agent/编排框架** —— 那么它是一个新的依赖，要过两道门
  （可维护性 + 许可证，见 `AGENTS.md` §3.1–3.2），并登记。

⚠️ 我**不猜**这一点：选错会让整个托管 AI 的数据路径设计跑偏，
而这正是本 ADR 最核心的那条线（§3）。

## 7. 后果

- `assertEnableable` 继续挡住 `managed`，直到 §4 的第 1、2、3 条完成。
- 界面文案从"我们不做"改为"即将提供 + 它的性质"。
- `AiSupplyMode` / `EgressDestination` / `describeRetention` 的设计**无需改动** ——
  它们当初就是按"托管会来"写的（这算是那部分设计做对了）。
- 决策 2 从"已定案（不做）"改回"**方向已定，开放条件未满足**"。
