## 5. 设计系统（UI 代码必读）

**唯一事实源：[`packages/design-system/src/tokens.css`](../../packages/design-system/src/tokens.css)。**
规则与理由见 [`design-system/heyta/MASTER.md`](../../design-system/heyta/MASTER.md)（**不复制取值表**）。

**色系：蓝白。** 主蓝 `#2563EB`，近白底 `#F8FAFC`，冷调石板灰中性色。

### 🔴 三条硬规则

1. **组件禁止裸值** —— 不得出现裸 hex / px / ms / z-index / rgb()。
   用 `cssVar('color.foreground')`（类型安全，拼错编译期报错）。
2. **语义名，不用外观名** —— `--ht-color-danger` 而不是 `--ht-red`。
   组件只消费语义层，原始色阶（`--ht-blue-600`）留给设计系统内部。
3. **要新变量，先加 token** —— 先改 tokens.css 与 `TOKEN_GROUPS`，再消费。
   **加 token 的成本是刻意的**，它逼你想清楚这个值是不是一次性的。

```bash
pnpm check:design     # 非零退出 = 有裸值
```

#### 🔴 文字层级（2026-09-30 增：排版审计实测"一页八个页标题"）

语义文字样式的唯一规范是 `packages/design-system/src/typography.ts` 的
`TEXT_STYLES`（字号+字重+行高+字距**整条消费**，不许只挑字号）。web 的映射：

| 角色 | 值 | 例 |
|---|---|---|
| 页标题（一屏一个） | xl + semibold（`.ht-header__title`） | 设置 / 收集箱 |
| 区块标题 | **lg + semibold**（= 共享层 `section-title`） | 设置的"功能模块/提醒通知"、任务分组头 |
| 子块/卡片标题 | base + semibold（`.ht-settings__h3`） | 面板里的小节 |
| 正文 | base + regular，行高 `--ht-line-height-normal` | |
| 辅助/说明 | xs 或 sm + muted 色 | 卡片描述、表单注释 |

反例（已修）：设置面板标题曾是 xl + bold —— 与页标题一般大，层级全塌。

> 该检查器已用**注入违规文件**验证过能失败（它扫的类别数由自己打印，现量看 `pnpm check:design` 第一行；
> 这一句原先钉着的类数早已落后于实现）。⚠️ 它只证过**注入的那几类**会红，
> **不等于每一类都有注入证据** —— 要新增一类就先补一枚能红的臂，别替它吹。
> **不能失败的检查没有价值。**

### 🔴 对比度是测试保证的，不是文档保证的

`pnpm --filter @heyta/design-system test` 会解析 tokens.css、递归展开 `var()`、
按 WCAG 公式**真实计算**每一对前景/背景对比度，不达标就失败。

> **这个测试已经抓到过真问题**：`quadrant-3` 原用 amber-600（`3.19:1`）不达正文标准，
> 已改为 amber-700（`5.02:1`）。写在文档里的"4.5:1"是拦不住的。

### 🔴 交互控件的档位只有一处定义（2026-10-28，全局 UX 线 P4）

一枚按钮"长什么样"的答案**只许住在一个地方**：`packages/ui/src/control/states.ts` 的
`CONTROL_PALETTE`（色调 `primary`/`secondary`/`ghost`/`danger` × 重量 `inline`/`commit`）。
表里写的是 **token 名**，不是色值也不是类名 —— Web 把它翻成 `var(--ht-…)`，
移动端把它翻成 `HeytaNativeTokens[name]`。**翻译可以两份，判断只许一份**（AGENTS §3.5）。

三条会踩到的：

1. **不许有不带色调的 `.ht-btn`**。立项现量 18 处（AI 面板、隐私同意层、危险确认的「取消」），
   它们没有底也没有 hover 底，图上读起来就是说明文字。今天归零，`check:control-semantics` 的 A8 守住。
2. **危险动作分两档，按位置选**：列表行/设置项里那枚是 `inline`（透明底 + 危险色字），
   确认层里唯一要按下去的那枚是 `commit`（实底 + `color.on-danger`）。
   两端原本各对一半（Web 恒为透明底、Mobile 恒为实底），缺的是"这一枚站在哪个位置"这一格判断。
   ⚠️ 实底那枚的前景**不许**用 `foreground-inverse`：暗色的 `danger` 是提亮后的浅红，
   白字压上去只有 2.77:1，`on-danger` 换深之后是 7.29:1 —— 这两个数由对比度套件现算。
3. **功能 CSS 不许重声明控件外观**（`background`/`color`/`border`/`box-shadow`/`opacity`/`outline`），
   布局（`flex`/`inline-size`/`padding`）归宿主、一律放过。

门禁：`pnpm check:control-semantics`（14 枚 self-test 臂 + 两次真树变异取证）。
它**看不到**的那一格诚实登记在脚本头部：选择器里不写控件族类名、只写宿主自己那枚 class 的
外观覆盖 —— 那一格归"真实浏览器逐态读计算样式"（`e2e/tests/control-semantics.spec.ts`）。

### 🔴 行内动作条：每一枚动作都是 `.ht-chip`，不许裸 `<summary>`

`.ht-compose-actions__items` 这一排（备注 / 子任务 / 截止 / 提醒 / AI …）里，
动作的**字号不属于组件，属于这一排**：`.ht-chip` = `font-size-2xs`（11px）。
一枚裸 `<summary>` 只写 display/gap/color 时，字号会**回落到从行的 16px** ——
于是同一排出现 11px 与 16px 两档，而所有测试都是绿的。

2026-10-21 实测（1012×632 打开「更多」）：`备注/子任务/提醒` = 11px，`截止` = **16px**，
用户一眼看出来（"截止这两个字也太大了吧"）。修法是把它收进 `.ht-chip`，
判据是 `e2e/tests/ai-panel-layout.spec.ts` 里那条**同一排 font-size 必须只有一档**。

### 🔴 把 RN 组件嵌进 web 的 flex 行：必须显式给它 `flex` / `max-inline-size`

React Native 的 `View` 默认 `flex: 0 0 auto`（与 CSS 的 `0 1 auto` **不同**），
`width: auto` 于是解析成 **max-content**。嵌进 web 的 flex 行时，它会**既不收缩也不换行**，
把容器撑破。实测：AI 提案面板（RN `View`）在 384px 的行内浮层里量到 **493px**，
左溢 121px 压住任务列表 —— 原因是 note 那一整行 469px + 内边距 24px。
判据与修法都在 `apps/web/src/styles/app/controls.css` 的
`.ht-compose-actions__items > [role='dialog']` 那一段（`flex: 1 1 100%` + `min-inline-size: 0`）。

### 容易犯的几个错

- ❌ **用 emoji 当图标** —— 跨平台渲染不一致且不受 token 控制。统一用 **Lucide**。
- ❌ **`outline: none`** —— 抹掉焦点环是最常见的可访问性回归。用 `:focus-visible`。
- ❌ **hover 用 `translateY` 位移** —— 扁平风格用**边框**表达层次；阴影**不靠位移伪造深度**。
  ⚠️ **2026-11-02 精确化（不是推翻）**：原句是"阴影只给真正的浮层"，实测后补一条边界 ——
  **静态卡片在"边框分不开"时可以用 `shadow-sm`/`shadow-md`**，因为这类卡片不是浮层、也不动效。
  依据（同一轮亲测）：卡片 `#fff` 与页面 `#f8fafc` 只差 **7/255**，一屏三张卡读成一片白；
  而"压深页面底色"这条路被四端 AA 用例否决（`foreground-subtle` 4.34:1 < 4.5，
  且它已是最浅一档文字色，再深就与 `muted` 合并）。DSH 自己的设置页也用 elevation
  （`--dsw-elevation-prominent`），所以这不是"跟它对着干"。
  ⇒ **仍然禁止**：hover 位移、给浮层以外的东西加 `shadow-lg`、用阴影代替边框。
- ❌ **不测暗色主题就交付** —— 暗色不是亮色的反相，必须**实际切换查看**。
- ❌ **数字不加 `.tabular-nums`** —— 番茄钟计时与统计数字的宽度会跳动。
- ⚠️ **兜底界面的裸值不是违规，但也只有两处**（2026-11-09 立账）：崩溃兜底屏与
  「产物缺失」兜底页**设计上就不能取 token**（崩溃时 `ThemeProvider` 可能正是崩掉的那一环；
  `data:` URL 兜底页此时连样式表都没加载）。它们登记在
  `design-system/heyta/check-hardcoded.mjs` 的 `FALLBACK_FILE_ALLOW`，**带 count 只许变小**：
  多一处 ⇒ 红（不放行）、少一处 ⇒ 也红（要求改小）。自检：
  `node design-system/heyta/check-hardcoded.mjs --self-test`（三条臂：基线绿 / 多一处红 / 少一处红）。
  🔴 **不要**为了多写一处裸值去改那两个 count —— 那和"往豁免表里加路径让判据变绿"是同一件事。

### 🔴 表面预设（warm / mist）：一份 CSS，两种发射形态（2026-11-09）

预设只换**表面色系**（不含语义色 primary/danger/success/warning），所以它必须**只有一处定义**：
`tokens.css` 的 `[data-theme-preset='…']` 块。web 靠 `applyThemePreset()` 写 `<html>` 的
`data-theme-preset` 消费它；RN 侧走**生成器**：

1. `buildPresetTokens()` 用 `extractPresetOverridesVars()` 只取块里**显式写出**的变量
   （用合并表去判会把每个 token 都算成"有覆盖" ⇒ 一张与基准等大的假预设表）；
2. 发射成 `generated/tokens.native.ts` 的 `presetTokens`（亮/暗各一份，值已按各自主题解析）；
3. `tokensForTheme(theme, preset)` 合并 → `resolveHeytaUiTheme({ preset })` → `useHeytaTokens()`。

🔴 **不许**在 RN/移动端手抄一份表面色 —— 那就是第二份表，`check:theme` 会红，两份一定漂。
判据：`packages/design-system/tests/preset-native.spec.ts`（同源 / 稀疏 / 正交三组，16 条）。
⚠️ 生成物改动必须走 `pnpm --filter @heyta/design-system run generate`，`run generate --check` 会比对漂移。

## 🔴 设置界面里**禁止**写说明文字（2026-10-24，产品负责人下的禁令）

原话（第二次说的时候已经很生气，所以这条是**禁令**，不是建议）：

> 「严禁说明文字出现，严禁说明文字直接写进去。只允许用那种"一个圈里面一个问号"的，
>   hover 上去有。把这种东西写成严格的代码禁令……彻底禁止！」

**规则**：设置界面的每一个控件旁边，只许出现**控件本身**（标签、开关、输入框、按钮）。
任何"这个是什么 / 为什么这样 / 会怎样"的句子，一律进 `?`：

| 端 | 合法载体 |
|---|---|
| web | `SettingsInfoTip`（`apps/web/src/features/settings/SettingsInfoTip.tsx`），渲染成 `?`，悬停**或**聚焦展开，`Esc` 收起，正文常驻 DOM 由 `aria-describedby` 指向 |
| mobile | 共享层那份 `SettingsInfoTip`（`packages/ui/src/settings/Settings.tsx`，RN 原语，**点一下**展开 —— 原生没有 hover）。它与 web 那份只差开合方式，语义同一（`aria-expanded` / `accessibilityRole`） |

> ⚠️ 这一行**曾经写着"mobile 尚未建"**，而共享层那份早就在用（`grep -rn "SettingsInfoTip" apps/mobile/src` 现量）。
> 状态一变注释不会自己跟着变 —— 要核载体在不在，读那份 `export function` 与它的调用点，别读这句话。

三条例外（**写清楚才好反驳**）：

1. **反馈**：失败 / 成功 / 进行中 / 空态 / 读数。`role="alert"`、`aria-live`、
   `ht-settings__danger`、testid 里带 failure/error/status 的那些 —— 把"这一单没下成"
   塞进气泡是另一种错：用户得先点一下才知道出了什么事。
2. **披露**：ADR-0054 §7 要求"对话之前就看得到"的出境披露（助手那一块）。
   藏进悬停气泡就不再是披露。用 `data-settings-disclosure="true"` 显式登记。
3. 页面标题的副句（`web.profile.overview.lead`）—— 它是"我在哪一屏"的确认，
   不是某个控件的解释。**只有这一处**，也记在账本里。

**判据**：`pnpm check:settings-prose`（`scripts/check-settings-no-prose.mjs`）。

它是**账本制**（与 `check:overlay` 同一条纪律）：

- 账本外新增 ⇒ 🔴 红（新写的说明文字一天都进不来）；
- 账内读数涨了 ⇒ 🔴 红；
- 账内读数掉了却没改账本 ⇒ 🔴 红（这一条是"它真的在缩"的唯一读数）。

账本：`scripts/settings-prose-ledger.json`。清理时**只许改小**：
`node scripts/check-settings-no-prose.mjs --update`。

⚠️ 为什么不是一次清完：存量横跨两端、十九个文件；一次改完会把"删说明"与
"重写控件"混成几百行，而那种改动的判据只有"跑起来了"。账本让每一屏的收缩都可读。

### `?` 的位置与数量（2026-10-31）

产品负责人第二次实拍：「信息架构重复了，另外 tooltip 过于泛滥，而且位置不统一」。

| 规则 | 为什么 | 判据 |
|---|---|---|
| **设置内容面不画节标题**。左栏已用 `aria-current="page"` 指出所在节；内容面的节名改挂 `<section aria-label>`，不再有 `<h2>` | 「个人资料」紧挨着「个人资料」= 同一份信息架构画了两遍，两行同名字并排像两个层级 | `apps/web/tests/settings-sheet-ia.spec.tsx`「内容面不重复侧栏已经指出的节标题」 |
| **一枚 `?` 紧跟它所解释的标签或小标题**（同一段文字之后），**值那一列不许出现问号** | 同一屏里一半问号在标签后、一半在值下面，读起来像"这个值自己的注释" | 全仓调用点：`pnpm check:tip-adjacency`（账本制）；单屏形状：`apps/web/tests/profile-panel.spec.tsx`「问号只挂在标签/小标题后面」 |
| **同一事实只出现一次**（例：当前登录邮箱只在「邮箱」行，换邮箱块不再回显） | 两个同值字段挨着，用户要逐字比对才敢确认不是两个地址 | 同上「登录邮箱只显示一次」 |

### `?` 的位置这一半，2026-11-04 起有尺了（`pnpm check:tip-adjacency`）

上面那条口径原来**只有 `profile-panel.spec.tsx` 一枚断言**在管，而且只管个人资料那一屏 ——
其余调用点违反它**不会有任何测试变红**，症状是屏幕上出现一枚**没有归属的孤零零问号**
（真浏览器截图在 `PasswordPanel` 抓到两枚：代码注释自己写着"按钮旁的 `?`"，代码却把它排在段落之后）。

尺认四种合法位置（调用点总数由 `node scripts/check-tip-adjacency.mjs --report` 逐条列出来，
2026-11-04 那一趟读到 33 枚 —— **这个数会随面板动，要现量**）：

| 合法形状 | 例子 |
|---|---|
| 标签/小标题/正文节点**内部**（`label` `legend` `h2` `h3` `h4` `span` `p` `dt` `summary`） | 各面板 `<h2>标题 <SettingsInfoTip/></h2>` |
| 标题/标签那一格容器里（className 含 `__h3` / `ht-type-headline` / `ht-type-row-title` / `__help-line` / `__labelcell` / `__row-label` / `__actions`） | 动作块旁的那枚后果 `?` |
| **紧跟**它所解释的那个标签/控件那个兄弟之后 | `.ht-settings__toggle` 那一行：`<label>…</label>` 之后一枚 `?` |
| 作为 **prop** 交给原语（`labelTip={…}` / `tip={…}` / `SettingsSection.titleTip`） | 位置由原语保证，调用点不需要自己排 |

> ⚠️ 两件事一起做才算闭环：① `SettingsSection` 原来**没有**能把 `?` 挂到分组标题旁边的口子，
>    宿主只能把它当 children 排在整组之后 —— 那个缺口现在由 `titleTip` 补上（与 `FormField.labelTip` 对应）；
>    ② 存量（**处数只由 `cat scripts/settings-tip-ledger.json` 给**）进账本，**只减不增**：
>    新增一枚即红，缩了不回来改账本也红。账本里剩的都是各自那一屏的格子，本线不代改。
>    那几处合法的改法就是上面那张表里的某一种。

⚠️ 这三条约束的是**位置与重复**，不是"每行都要挂问号"：没有值得问的句子就不挂。
删掉解释**不会**违反上面的禁令（禁令管的是"不许内联"，不是"必须有 `?`"）。

### 那道门有一道**已知的缝**，缝上补了两道判据

`check:settings-prose` 扫的是**调用点**（`ht-settings__*hint*` 容器、行模型里的 `hint:` 字段），
**不扫组件内部**（理由写在脚本头部）。于是有一种改法它看不见：

```diff
- {row.hint === undefined ? null : (<SettingsInfoTip text={row.hint} … />)}
+ {row.hint === undefined ? null : (<Text>{row.hint}</Text>)}
```

调用点一个字节没变 ⇒ 门禁照样绿，而屏幕上一整句说明又回来了。**2026-10-24 实测过**
（当时是为了证明设备腿会红）：`check:settings-prose` ✅、设备腿 ❌。

现在这条缝由两道互补的判据堵着：

| 判据 | 成本 | 抓的是 |
|---|---|---|
| `packages/ui/tests/settings-hint-through-tip.spec.ts` | 毫秒 | **源码形状**：`Settings.tsx` 里每处 `row.hint` 必须交给 `SettingsInfoTip` 或存在性守卫 |
| `pnpm verify:mobile-ios-subscription` | 一枚模拟器 + 一次构建 | **行为**：hint 默认不在 AX 树上、点 `?` 出现、再点收起 |

两条分工是刻意的：**同一个判断不在两个地方长牙**，但"入口"必须有一道零成本的。

### `?` 的贴合位置（2026-10-24 修）

行首那一列是 `actionHead`。它原来是 `alignItems: 'center'`，于是 `?` 展开时那一列多出一行正文、
居中对齐把**图标本身**也一起挪位（设备截图上看得见：展开后 `?` 比标题高出一截，点一下动一次）。
改成 `'flex-start'`：图标只随标题首行定位，开合都在同一处。
⚠️ 这条的证据是**两张图**，不是像素读数 —— 展开会重排列表，跨图比绝对 y 会被滚动锚点混淆
（三种探针实测不稳）⇒ 只主张看得见的那件事。

## 🔴 响应式断点：一把尺，两个轴（2026-10-26）

产品负责人的原话：

> 「电脑端的话，Web 端也需要根据手机端实际来自适应。比如我用手机浏览器打开对应的界面，
>  并且登录了，也要按照移动端来显示。**整个项目必须完整做好响应式布局。**」

### 事故的形状：不是缺规则，是**没有一把尺**

收口之前（`apps/web/src`，`@media` 与 `matchMedia` 两侧合计 **33 处**）实测 **9 种宽度值**：

| 原值 | 处数 | 它当时在解什么问题 |
|---|---|---|
| `30rem` | 6 | 弹层整屏贴底、按钮铺满一行、藏装饰 |
| `36rem` | 3 | 弹层贴底、表单标签换行、AI 页头改列 |
| `40rem` | 7 | 设置行改单列、卡片头改列、面板收窄 |
| `48rem` | 4 | 单栏底部弹层、设置双栏→单栏、AI 历史栏变浮层 |
| `64rem` | 2 | 设置侧栏→横条 |
| `768px` | 6 | 底栏导航、详情列不出、成长热力图 |
| `769px` | 2 | 上面那条的**互补另一半** |
| `1023px` | 2 | 详情列的互补上限 |
| `1024px` | 1 | 详情列下沿（JS 侧） |

三个读法（都能从这张表直接看出来，不需要"感觉"）：

1. **同一个阈值有两种拼法**：`48rem` 与 `768px` 是同一个数（10 处），`64rem` 与 `1024px` 也是。
   它不影响渲染，但它让 `grep 768` 与 `grep 48rem` 各看见一半。
2. **互补的两半被写成两个互不相干的字面量**：`max-width: 768px` / `min-width: 769px`、
   `max-width: 1023px` / `min-width: 1024px`。差一像素是真的（CSS 媒体查询没有"严格大于"），
   但**这两个数谁都看不出是从哪来的**，改档时只会改一半。
3. **480 / 576 / 640 三个值在解同一类题** —— "两栏放不下了，改一栏"。这类取值每屏一个，
   于是"再窄一点"这个判断在仓库里有三个答案。

而真正**结构性的**换档只有两处：**底栏导航/设置双栏塌缩（768）** 与 **三栏成立（1024）**。

### 尺

**宽度轴（只有 4 个登记值，后两个是前两个算出来的）**

| 登记值 | px @16 | 在判什么 |
|---|---|---|
| `48rem` | 768 | 紧凑档上沿：导航变底栏、设置双栏→单栏、详情列不出、行解剖 `inline`→`stacked` |
| `48.0625rem` | 769 | 紧凑档的**互补下限**（= 48rem + 1px） |
| `63.9375rem` | 1023 | 宽屏档的**互补上限**（= 64rem − 1px） |
| `64rem` | 1024 | 宽屏档下沿：三栏成立 |

**高度轴（另一根轴，不是第 4/5 档宽度）**

| 登记值 | px @16 | 在判什么 |
|---|---|---|
| `29.9375rem` | 479 | 矮屏上沿。出处：Android 窗口尺寸类的**高度** Compact = 高 <480dp（`narrow.css` 逐字引过调研 A1） |
| `30rem` | 480 | 矮屏的互补下限 = "两栏可行" |
| `36rem` | 576 | AI 欢迎内容比面板高时的内部塌缩点 |

⚠️ **高度不是宽度的一档**：`(max-width: 480px)` 与 `(max-height: 480px)` 是两道完全不同的题。
门禁按轴分开登记，串轴即红。

### 🔴 `@media` 里用不了 CSS 变量，所以这把尺只能靠**约定 + 门禁**

这不是懒：媒体查询的条件在**变量解析之前**求得，规范如此。所以尺不可能住进 `tokens.css`。
它由两条腿同时钉住：

| 腿 | 载体 | 管什么 |
|---|---|---|
| 约定 | 本节（你正在读的这张表） | 人读到"哪一档、在判什么" |
| 门禁 | [`scripts/check-breakpoints.mjs`](../../scripts/check-breakpoints.mjs)（`pnpm check:breakpoints`） | 机器读到"出现没登记的值就红" |

唯一一枚**已经住进 `tokens.css`** 的是 `--ht-layout-two-column-min: 768px`（倒计时/四象限
读它来数格子）。门禁 B8 判它必须与 `48rem` 是同一个数 —— 两处漂了就红。

**JS 侧只有一个出口**：`apps/web/src/lib/breakpoints.ts` 导出
`COMPACT` / `ABOVE_COMPACT` / `BELOW_WIDE` / `WIDE` / `SHORT` / `TALL` / `DETAIL_FITS_QUERY`。
`apps/web/src` 里**别的** `.ts`/`.tsx` 再写宽度字面量即红（B5）—— 立项当时有三份抄件
（`useNarrowLayout.ts`、`ScopeDrawer.tsx`、`detail-pane-visible.ts`），CSS 改了它们不会跟着改。

### 判据：`pnpm check:breakpoints`

- 未登记的值 ⇒ 🔴；登记值的 **px 拼写** ⇒ 🔴（`768px` 就是这一型）。
- 一像素派生写错 ⇒ 🔴（B3 算术：互补侧必须是 ±1/16 rem）。
- 落点数塌到基线以下 ⇒ 🔴（B4：扫描坏了不许算绿）。
- `@container` 无名，或 (容器名, 阈值) 没登记 ⇒ 🔴（B6）。
- `--self-test` 有 **17 枚臂**，含"迁移前那 9 种值喂进去必须红"那条。

### 容器查询是**另一根轴**，不许混进这把尺

`@media` 量**视口**，`@container` 量**容器**。同一个 `26rem` 在两处是两件事：
视口 416px 是"一台很窄的窗"，`habit-detail` 容器 416px 是"这一栏刚好够画"。
`habits.css` 文件头已经把这个账算过一遍（"用视口媒体查询会得到『视口够宽而这一列其实很窄』
的错判"）。所以容器阈值按 **(容器名, 值) 对**单独登记，且**必须带容器名** ——
无名容器解析到"最近的容器祖先"，改一层 DOM 就换一把尺，而它不会红。

今天登记的 4 对：`habit=33rem`、`habit-detail=26rem`、`ai-panel=26rem`、`ai-panel=42rem`。

### 🔴 判据是"窄屏 **或** 粗指针"，不是只看宽度

手机横屏（844×390）、折叠屏外屏、部分 WebView 的 CSS 宽度都在 768 以上 ——
**只看宽度会把它们判成桌面**。产品负责人要的是"用手机浏览器打开就是移动端"，
所以凡是"这是不是一个触屏设备"的判断，条件写成**并集**：

```css
@media (max-width: 48rem), (pointer: coarse) { … }
```

已按这条落地的是认证弹层（`features/auth/auth-dialog.css`，2026-10-26 从 `30rem` 改过来）。
取值依据同 `AuthPanel` 用 `pointer: coarse` 判"口令要不要默认遮住"（NNG/NIST：
肩窥与单手错字的权衡）—— **不是新发明的一套判断**。

⚠️ **取舍是"手指优先"**：触屏笔记本会跟着变成移动版式。理由写在那一处的注释里 ——
那个版式的每个控件仍然可点、可键盘 Tab，而反过来（把手机判成桌面）会让手机用户
掉进一个两栏布局，那才是真的用不了。

**还没按这条落地的地方**（在册，不装作已经做完）：整壳（rail/sidebar/详情列）仍只有宽度判据。
手机横屏在壳上是"中等档"（详情列不出，但 rail + sidebar 还在）。要不要把
`(pointer: coarse)` 也并进壳，是一个**产品决定**（它会一起改掉触屏笔记本），不是重构。

### 迁移的取舍（写清楚才好反驳）

`30rem` / `36rem` / `40rem` 三个值（共 16 处）**全部并入 `48rem`**，没有保留第二档。理由：

- 它们解的是同一类题（"两栏放不下了"），没有一处标志着**结构**换档；
- 壳在 768 已经宣布"这是移动版式"（底栏导航）——一个在 480 才变单栏的弹层，
  在 600 宽的窗口里得到的是"手机导航 + 桌面弹层"，那正是第二把尺；
- 代价是**可见的**：641–768 的窗口里，设置行现在提前变单栏、AI 页头提前改列、
  认证弹层的装饰卡片提前收起。这一档今天没有真实设备（768 是 iPad 竖屏下沿），
  而 768 以下本来就该是移动版式。**这条取舍是这一轮唯一改变渲染的地方**，
  其余 6 种改动都是"同一个数换一种拼法"。

### 已知边界

- **没有自动化看图判据**：门禁只判"值合不合法"，不判"这一档选得对不对"。
  `sheets.css` 里有一处用紧凑档做了一张卡片的塌缩 —— 值合法、语义可疑，那一格归评审。
- **e2e 的视口矩阵没扩**：`e2e/tests/global-responsive-ux.spec.ts` 量 1440/1024/768/390/375，
  640 与 900 这两档没有截图证据（640 这一档是本轮语义变化最大的一档）。
- **`apps/mobile` / `apps/landing` 不在扫描面**：前者是 RN（没有媒体查询），后者是另一张脸。

## §4.9 逐屏审查的两条硬规矩（2026-11-15，40 轮实测）

**这两条不是审美偏好，是"不遵守就会白干很久"的代价记录。**

### 4.9.1 连续调同一个数值第 3 次无效时，停下来问"这个东西该不该是这个形态"

**实测代价**：四象限卡片高度调了 **8 次**（`flexGrow` 三次、`minHeight`、`flex`、
`maxHeight(700)`、`maxHeight(400)`、`empty` 的 padding），每次截图逐像素未变。

真因不是尺寸 —— 那次要的根本不是"矮一点的单列"，而是**坐标系**（四格并置 + 十字 + 两轴）。
换成 `twoColumns` 之后，高度问题**自动消失**。

**判据**（三条任一成立就停手，先重述问题）：

1. 同一个属性改到第 3 次仍然"文件写对了、行为没变"；
2. 探针显示"改的值生效了"，但目标量没动 —— 说明控制它的不是这一层；
3. 你能描述"我要的样子"，但当前改法描述不出它（"矮一点" vs "并置"）。

**探针阈值要先算**：`maxHeight: 700` 对合计 652dp 的内容**根本不触发**，
读起来像"改无效"，实际是探针没咬到。

### 4.9.2 改完一处要把那一屏整屏看完

**实测代价**：给「我的」页加账号头部时，只确认了"头像出来了、蓝按钮没了"就提交 ——
没注意说明折成两行、卡片从 380px 被撑到 470px。**16 轮之后**回归抽查才发现。

**判据**：提交前那一屏的截图**必须整屏看过**，不是只看自己动的那个元素。
尤其当改动涉及**文案长度**（它会改换行、改卡片高度）或**插入/删除一行**。

### 4.9.3 「看起来不对」是假设，不是结论

同一轮里三次差点报假问题：

| 看起来 | 实际 |
|---|---|
| 「专注」页「今天」被 TabBar 裁了 | `screen-bottom-inset` 88 > `tab-bar-height` 64，**没裁**，只是滚动区 |
| 「外观与语言」卡内标题不一致 | 24 处 `SettingsSection` 全用 `variant="card"`，**内部一致** |
| 「关于与帮助」只有一行像漏了 | `isOfficialHostedInstance` 门控 —— 备案号只在官方托管实例显示 |

**判据**：报形状问题之前，**先读渲染代码或量数值**。只看截图的边缘/差异就下结论，
平均三次里会有一次是假的。

### 4.9.4 多端列数：比"能放下几列"，不比"窗口多宽"

**像素断点在不同设备上是不同的物理尺度** —— 手机横屏 768、iPad 竖屏 768、
Mac 窗口 768 是三件不同的事。

用 `packages/ui/src/layout/form-factor.ts`：

```ts
formFactorOf(width)   // 这个端是什么档：compact / regular / expanded
canPairColumns(width) // 这块够不够并排两块（默认就该并排的视图用它）
```

🔴 **两种判断不能混用**。四象限用 `formFactorOf` 会退回单列（`compact` → 1 列）——
那正是 2026-11-15 修复前的坏状态。判断应该是"**窄到读不出字才退回单列**"，
不是"宽了才并排"。

🔴 **不要用 `Dimensions.get('window').width`**：那是物理屏宽，桌面上永远"够大"。
用容器 `onLayout` / `clientWidth`。

## 4.9.5 动效参数：别人给的 (k, c) 要先换算，再看它撞了哪条

> 2026-11-15，来源是一篇「6 种按钮动效的 AI 提示词」笔记 —— 每条都带了
> `刚度 260 / 阻尼 12` 这类物理三件套。它的价值不在那 6 段提示词（那些直接发给 AI
> 只会得到 6 段各自为政的代码），而在**它让我们把"这条动效该不该收"变成了一道算术题**。

### 判据一：`(k, c)` 不是审美，是阻尼比

本仓的弹簧只有两个自由度（`tokens.css` §3c）：**阻尼比 ζ** 与 **响应**。
别人给的是 `(stiffness, damping)`，换算是一条恒等式（`√k = ω₀`）：

```
ζ = c / (2√k)          response = 2π / √k
过冲 = exp(−πζ / √(1−ζ²))   （ζ ≥ 1 时为 0）
```

过冲量是这条式子里**唯一能证伪"略带过冲"这种描述**的量：

| 笔记参数 | ζ | 过冲 | 判定 |
|---|---|---|---|
| 260 / 12（按压） | 0.372 | **28.4%** | 明显在颤 |
| 200 / 14（开关） | 0.495 | **16.7%** | 在颤 |
| 300 / 10（点赞） | 0.289 | **38.8%** | 剧烈 |
| 150 / 15（磁吸） | 0.612 | 8.8% | 接近我们的动量档 |

对照本仓：默认 `ζ=1`（0%）、动量档 `ζ=0.8`（1.5%）。

🔴 **过冲 > 10% 就该追问那句话**：这个动作**本身带速度**吗？
带（甩、扔、拖拽释放）→ 用动量档，但也不到 10%；
不带（按下、切换、淡入）→ 只能用临界阻尼，28% 的过冲会读成"这个按钮在抖"。

### 判据二：裸 ms 要能落到五档里

`--ht-duration-{instant 80 / fast 150 / normal 200 / slow 300 / exit 140 / press 100}ms`。
笔记里的 `450ms`（波纹）> slow，`280ms`（开关底色）落在 normal 与 slow 之间 ——
**落不进任何一档就是裸值**：它不随设计系统调参变化，也不会随 `prefers-reduced-motion` 归零。

### 判据三：拉伸 / 位移类必须有上限

磁吸那条给的是"强度 0.35，无上限"。实测：指针离中心 233px 时按钮位移 **81.6px**，
直接飞出容器。本仓 `Magnetic.tsx` 的 0.2 + 8px 钳制是同一个交互的克制版。

### 试验台（可复现）

```bash
cd apps/landing && pnpm lab      # vite src/lab --port 5190
```

`apps/landing/src/lab/` 是**dev-only**：不在 `src/site/pages.ts` 注册表里，
不进生产构建、不进 sitemap。左侧是笔记原参数、右侧是设计系统改法，两栏都能点。

实测数据（Playwright 采样 computed transform，2026-11-15）：

| 量 | 笔记版 | 设计系统版 |
|---|---|---|
| 按下最低 scale（目标 0.94 / 0.97） | **0.9231**（理论 0.9230，冲过头） | 0.9700（精确停住） |
| 松手回弹峰值 | 1.0168（越过 1） | 1.0000 |
| 开关滑块 scaleX 峰值 | 1.35（右端被轨道裁掉一角） | 1.00 |

### 六条的结论

| 动效 | 结论 | 对 heyta 的意义 |
|---|---|---|
| 按压回弹 | 🔧 参数要换 | 已落地：`press-scale 0.97` + `duration-press` |
| 弹性开关 | 🔧 参数要换 | 1.35 拉伸与临界阻尼冲突，无新 token 需求 |
| 波纹跟手 | 🚫 不建议 | Material 语言；本仓按下是 `state-pressed` 8% 叠加层 |
| 点赞 | 🎯 值得改造 | 没有"点赞"，但有更高频的等价动作：勾完任务 |
| 复选框 | ✅ 开箱就对 | **唯一可直接上的一条**：0.8→1 用 ζ=1/0.3，勾 300ms = slow |
| 磁吸 | ✅ 已有 | 仓库实现比笔记更克制，产品内不需要 |

🔴 **不要照抄提示词里的参数**。六条里四条弹簧过冲 >8%，而本仓只有两档（1.0 / 0.8）。

### 落地情况（2026-11-15）

| 动效 | 落在哪 | 实测 |
|---|---|---|
| 复选框 | `packages/ui/src/control/checkbox-motion.ts`（判定）+ `TaskRow.tsx`（渲染） | web 实测 scale **0.8015 → 1**；减动效**全程 1.0** |
| 弹性开关 | 同一套判定复用；`settings/Settings.tsx` 的 `ToggleLine` | 底色渐变实测 **200ms 整**（= `duration.normal`）；减动效 **0ms** |
| 按下扩散 | `apps/web/src/lib/press-origin.ts`（圆心）+ `controls.css` 的 `.ht-btn::after` | 圆心跟随 20% → 80.93%；按下点 vs 对侧像素差 **18（约 6%）**；减动效 `content: none` |
| 点赞 | 融进勾选那一条（勾完那一下就是"一记明确的回应"） | 不加粒子、不加第二段脉冲 |
| 磁吸 / 按压 | **不动** | 见下 |

### 按下扩散为什么峰值是 8% 的 1.75 倍

第一版直接用 `--ht-state-pressed-opacity`（0.08），实测按下点与对侧的像素差
只有 **5/255（约 2% 亮度）**，肉眼读不出来。原因不是"8% 太小"，是**形状不同**：
整块叠层 100% 面积均匀 8%，而径向渐变的平台区只有约 57% 面积，其余在衰减。

`1.75 = 1 / 0.57`，把"面积"折回"峰值"。补偿后实测 6% 亮度差、白字对比度
8.72 → 6.23（仍过 AA）。**这不是给动效开口子**：同一份 token 在两种形状上
本来就该按形状补偿，否则"8%"这个名字代表的强度会随形状漂移。

### 两条不动的理由（都带量）

- **磁吸**：`Magnetic.tsx` 已经比笔记克制（吸偏 0.2 / 位移上限 8px），
  产品内没有对应场景。
- **按压（移动端）**：不是"没时间做"，是**做了看不出，且方向与 token 的意图相反**。
  - `tokens.css` §3c 的 `--ht-motion-press-scale` 注释写的是「这是**视觉时长**
    不是弹簧」—— 按压反馈本来就该是时长量，不是弹簧量。
  - 量：44px 高的按钮 × 3% = **1.32px** 位移。在这个幅度上加 400ms 的弹簧回弹，
    改的是"过程的形状"，而触屏上手指就盖在按钮上，这 1.3px 的过程读不出来。
  - 端与端本来就该不同：web 的 `.ht-btn:active` 走 `duration-press`(100ms)，
    鼠标需要一点"动画感"；触屏上延迟 100ms 会显得迟钝，iOS 的控件按下就是即亮的。
    两端各用自己的那一档，正是 `control/states.ts` 已经写下的分工。

### 新增的两条判据（这一轮补的）

1. **首次挂载不播。** 已完成的行滚进视口时弹一下，是噪音不是反馈。
   `planCheckboxMotion` 的 `mounted` 参数就是为它留的 —— 而对应的测试**第一版
   写错了**：用了 `(true, true, false)` 的输入，它确实返回 none，但返回原因是
   "值没变"，`mounted` 那一支根本没被走到（把判定整行删掉照样绿）。改成
   `(false, true, false)` 之后才真的能红。
2. **勾上与撤销不对称。** 勾完有仪式（0.8→1 + 勾淡入），撤销没有（不缩放，只淡出）。
   两个方向用同一套动画，连续勾选/取消会读成抽搐。
