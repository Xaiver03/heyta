# 入口分层：一个动作该从哪一层出来

> **本文件是规则，不是计划。** 上游取证：[UX 信息架构与入口链路](../research/ticktick-ux-ia-and-entry-paths.md) §2/§3/§7；
> 账本（动作级现状）：[`r14-entry-table.md`](../plans/r14-entry-table.md)；判据：`pnpm check:entry-table`。
>
> 为什么这条规则需要单独一份文件：它原来是 PRD 的 R14，**规则正文活在 `docs/plans/` 里**。
> 计划会随排期变，规则不会 —— 而 `AGENTS.md` §4 自己的话是「新增子文件必须回本表登记，否则它是孤儿文档」。
> 反过来说：**没登记成规则的规则会漂**。所以这里是从计划里提出来的，`r14-entry-table.md` 继续当账本用。

---

## 0. 什么时候读这一份

**任何一次"加一个按钮 / 加一个菜单项 / 加一个快捷键 / 加一个设置项"之前。**

它回答的只有一个问题：**这个动作，用户应该在哪一层找到它。**
它**不**回答：那一屏长什么样（[ux-principles.md](ux-principles.md)）、浮层怎么关（[overlay-feedback.md](overlay-feedback.md)）、
有没有这个功能（PRD）。

## 1. 四层：按"动作改什么"划分，不按"重要程度"

| 层 | 判据（动作改的是） | 例子 |
|---|---|---|
| **全局** | 与"当前选中什么"无关 | 显示/隐藏窗口、快速添加、退出 |
| **视图** | **一个视图的读法**（排序 / 筛选 / 范围 / 分享 / 进入多选） | 排序、筛未完成、多选模式 |
| **对象** | **一条或多条任务本身** | 完成、删除、移清单、放弃、加子任务 |
| **字段** | **一个字段的值** | 截止、优先级、标签、标题 |

🔴 **分层不按"这个动作重要不重要"。** 重要程度是主观的，会让同一个动作在不同人手里落到不同的层；
「改什么」是可判的。取证里七个真动作逐条验过这条规则（J1–J6）。

### 1.1 三个副规律（同样可判）

| 副规律 | 判据 | 违反的样子 |
|---|---|---|
| **需要参数的动作从全局层消失** | 全局层条目不接受输入 | 托盘里放「改截止时间」 |
| **代价决定深度**（J5） | 不可撤销的动作再深一层 | 删除与放弃都在对象层，但删除在分隔线以下 |
| **频次决定进不进「更多」** | 高频结构动作直接暴露，低频进一跳 | 把"移清单"藏起来，把"加子任务"摊开 |

## 2. 六条硬规则（每条都能判红）

### R1 · 一个字段只有一个编辑落点

同一条任务的同一个字段，**有且只有一个"编辑落点"**。可以有多条**输入通路**（右键 / 键盘 / 详情按钮）
指向同一个落点，但不许两个落点。

**为什么**：两个落点必然漂 —— 一处支持"清除"另一处不支持，一处写一条 op 另一处写两条。

**判据**：`scripts/check-field-single-source.mjs` 扫渲染点，每个字段的落点文件数必须 = 1。
🔴 **这个脚本今天不存在**（P10 §7 R1 要求的，本轮复查确认仍缺）。
现状手工读数：due / priority / tags 各 1 处；**「清单」2 处**（`TaskDetailCard.tsx:886` 字段 + `App.tsx:3518` 看板拖拽），
且这处**入口表看不见它** —— 因为看板拖拽是隐式落点，没被登记成「编辑入口」。

### R2 · 入口进账本，只减不增（涨、掉都红）

每个用户可执行的动作，把它**用户可见的触发点**写进 [`r14-entry-table.md`](../plans/r14-entry-table.md)。
账外出现红；账内条数**涨了**红；**掉了也红**（要求同步把账本改小）。

**为什么**：「入口多」不是问题，「**没人知道现在有几个**」才是问题。

**判据**：`pnpm check:entry-table`（11 条规则 + 9 条 self-test 臂）。**现量 rc=0，42 行账、9 个共享动作 id 全覆盖。**

### R3 · 全局层只许放镜像，不许发明新动作

托盘项、全局热键、应用菜单项引用的动作 id，**必须**同时出现在视图层或对象层。
否则红 —— 那说明这个动作只从"全局"可达，**它没有归属地**。

**判据**：`scripts/check-global-mirror.mjs`。🔴 **这个脚本今天不存在**，现状是手工判绿。
唯一的合法例外是 J4：`quit` / `showMainWindow` 这类**它们的归属地就是窗口本身**，不在任务语义里。

### R4 · 空态动作必须是别处也存在的同一入口

空态里渲染的动作，它的 testid 必须**也**能在非空态找到。空态**不许**成为某动作的唯一入口。

**为什么**：空态是「用户什么都还没有」的状态 —— 这时才出现的动作，用户第二次就再也找不到。
它是**引导**，不是**入口**。

**判据**：账本上的 `emptyState` 列 + `empty-state-action.spec.tsx`。**现量绿，且是空集**。

### R5 · 从主界面到"改一条任务"≤ 3 层

任何一个改单条任务的动作，从主界面出发**最多 3 层**。第 4 层就是「藏起来」。

**为什么**：这不是审美判断 —— 它自己给了对照实验：同一动作在 macOS 是 3 层、在 Windows 是 4 层，
**同一家公司的两个端，一个越了线**。

**判据**：`e2e/tests/r5-entry-depth.spec.ts`。口径 = **1 + 同屏可见可交互表面数**。
**现量：三条链路都是 2 层，点击 1~4 次。**

### R6 · 页头/工具条只放「与选中无关」的动作

**判据**：`pnpm check:surface-budget`（页头可交互件上限 2）。

**为什么它在这里**：它和 R2 是同一族（预算），只是管的是**同一层里的件数**而不是**动作的落点**。
写在规则里，是因为「这个按钮放页头还是放行菜单」恰恰是最常见的越层错误发生的时刻。

## 3. 预算：常驻动作数由**容器高度**决定

对象层（行菜单 / 详情底栏）的常驻动作数**不是一个常数**，它由容器高度预算决定，其余进一跳。

🔴 **「5 枚」是它的读数，不是判据**（取证里那 5 枚是数出来的，不是它定的规则）。
可迁移的是**"常驻数由高度算"**这件事：底栏高度写死 ⇒ 常驻数成为常量。

**现状**：页头有件数预算且能红；**对象层没有预算** —— 行菜单 9 个 id（两对同槽位 ⇒ 单条最多 7 项）、
详情面 3 枚，全靠约定。这是本文件**唯一一条"新"的预算条文**，也是 R14 那五条之外补的第六条。

**判据（建议）**：给对象层一条像 `check:surface-budget` 那样的件数上限，超出必须登记处置。

## 4. 与别处的分工（不重复，只划界）

| 那一份 | 它管什么 | 本文件管什么 |
|---|---|---|
| [ux-principles.md](ux-principles.md) | 界面**解剖**：控件高度一档 / 一行一容器 / 动作区常驻 / 配置收起 | 跨对象的**放置规则**：这个动作属于哪一层 |
| [overlay-feedback.md](overlay-feedback.md) | 浮层**行为**：怎么关 / 多危险 / 多久消失 | 浮层**在层级里的位置** |

| [`r14-entry-table.md`](../plans/r14-entry-table.md) | **账本**：每个动作现在在哪、有没有第二入口 | **规则**：它应该在哪 |
