## 3. 硬性约束（违反即打回）

### 3.1 可维护性门槛

引入任何第三方组件前，**必须确认它在 2021 年之后仍在持续更新**。否则排除，无论许可证多宽松。

```bash
python3 research/tools/ghinfo.py owner/repo    # 查最后提交/发版时间
```

已因此被排除的例子：`rrule.js`（停在 2023）、`cal-heatmap`（停在 2024）。
**不要因为它们"看起来成熟"就放行** —— 这个门槛是有意的。

### 3.2 许可证

- ✅ **允许**：MIT / Apache-2.0 / BSD / ISC / MPL-2.0 / 0BSD / Unlicense / CC0
- 🔴 **禁止**进入产品代码：**AGPL / GPL / LGPL / BUSL / FSL / Elastic License / SSPL / CC-BY-NC**
- **无 LICENSE 文件 = 无授权 = 一行都不能用**

每个依赖必须**逐项登记**。门禁：

```bash
node research/tools/license-inventory.mjs      # 非零退出 = 有不合格依赖
```

它扫描的是**实际安装的依赖树**，并已通过"注入假 AGPL 包"验证过**能失败**。

🔴 **白名单外默认失败。** 不在上面那张表里的许可（例如 `caniuse-lite` 的 `CC-BY-4.0`）
一律算**不合格**，除非在 `research/tools/license-inventory.mjs` 的 `REVIEWED_OTHER`
里**逐项登记它为什么可以接受**。加一条的成本是刻意的 —— 它逼人为这个许可做一次
真正的判断，而不是让它悄悄混进"全部宽松"里。

> **这条以前是坏的，而且坏得很典型**：脚本把"白名单外"（`other`）**只打印、不判定**，
> 打印完 `❔ 其他（需归类）: 1` 之后接着报 `结论：全部依赖均为宽松许可 ✅` 并退出 **0**。
> 也就是说**这一档永远不会失败** —— 而白名单想拦的，恰好就是不在表里的东西。
> 成因是失败判据被**抄了三遍**（`--json` / `--flagged` / 汇总）且三遍都漏了 `other`；
> 漂移就是从"同一个判断写三次"开始的，现在只有一个 `failing` 常量能决定失败与否。
> 已用 4 种注入验证会红，其中一种是"把 `CC-BY-4.0` 的登记拿掉"—— 它证明这条登记是
> **承重的**，而不是"CC-BY-4.0 被全局放行"。

> 已知雷区：`@nextcloud/cdav-library` 是 **AGPL-3.0-or-later**，已被上游生产代码引用。
> heyta 的 CalDAV 要么自研，要么换 `tsdav`（MIT）。**不要引入任何 Nextcloud 服务端组件。**

### 3.3 schema 与持久化字段

- **默认不 bump `CURRENT_SCHEMA_VERSION`**。bump 是近乎单向的栅栏、且即使安全也不免费（要长期养一条迁移链）。
- 新增语义要能用 **payload marker / 惰性标记**向前兼容 —— 理由是**磁盘上和服务端库里已经写进去的数据会长期存在**（我们自己的开发机、测试库、服务器库都算），不是"要救老用户"。
- 🔴 **给持久化模型新增"必填"字段会在 hydration 时炸**：已经落盘的数据里没有这个字段。
  **新字段一律写成可选（`?`）并给运行时默认值。** **TypeScript 只保护新数据，构建会绿，炸在运行时** —— 这才是要防的东西。

### 3.4 op-log 纪律（P1 起）

- **一个用户意图 = 一个 op。**
- **被回放/来自远端的 op 不得再次触发副作用。** 否则会出现"同步回来又写一遍"的双向灾难。
- **op-log 是唯一写入口**：UI 不得绕开它直接改状态。详见 [`P1 计划`](../../docs/plans/archive/phase-1-single-client-loop.md) 的 D4。
- 多实体变更要**在一次操作里完成**，不要 fan-out 成多个 op。

> 依据：上游 `src/app/op-log/` 那 5 万行是**用真实故障换来的规格书**。改动同步逻辑前先读它，
> 但**移植语义，不要拷贝代码**（它绑定 Angular + NgRx）。

### 3.5 宿主外壳的边界（`packages/app-host`）

ADR-0003 §2.1 的分界线原来有个说不清的地方：把零件接起来算"业务逻辑"还是"平台外壳"。
结论是**两者都不是** —— 它是每个宿主都要做、且**一模一样**的管道。

所以：**`apps/*` 只允许有一处平台差异** —— 注入哪个 SQLite 驱动。

| 允许出现在 `apps/*` | 必须出现在 `packages/app-host` |
|---|---|
| `driverFactory: () => new NodeSqliteDriver(path)` | `SqliteAdapter` 的 schema 与初始化顺序 |
| 库文件路径 / 库名 | `clientId` 的读取与持久化 |
| UI 组件与平台 API | 同步游标读写、`SyncClientOptions` 的十几个回调 |
| | **任务 op 的构造**（`createTaskActions`） |

判断方法很直接：**这段代码里有没有任何一行在决定"业务上该怎么做"？**
有就是提取得不够。`addTask` 该写哪些字段、软删除发 `DEL` 还是改标志位、
清除字段该写 `null` 还是 `undefined` —— 全是产品语义，**一律不许出现在 `apps/`**。

> 实测代价：抽出来之前，`apps/web` 与 `apps/node-host` 各有一份任务 op 构造，
> 而且**已经漂移了**：`node-host` 用 `crypto.randomUUID()` 生成 entityId 且没有回退，
> 而 `apps/web` 用的是 `Date.now()+counter` 且有回退。移动端（Hermes）没有
> `randomUUID` 时会**在用户点"新建任务"的那一刻抛异常**。

**同形状的第二次，发生在同步接线上。** `SyncClientOptions` 有 12 个回调，
`packages/app-host` 与 `apps/web` 里**各写了一份，逐字相同、连注释都是复制的**；
clientId 的回退逻辑还真的漂移了（`randomId()` vs 自己写的 `Math.random()`）。
clientId 是 LWW 的决胜依据 —— 两份实现 = 两套裁决标准。
现已抽成 `packages/app-host` 的 `createSyncClient()`，并由
`pnpm check:layering` 钉住（**规则条数由它自己打印，别在这里抄** —— 这一句原先钉着"4 条"，而现量早已不是那个数；已用注入违规验证能失败）。

> 教训：**"抽出了一个共享实现"不等于"重复被消除了"。** `ids.ts` 抽出来了、
> 文件头还专门列了一张漂移对照表 —— 但 `apps/web` 那份**从没被删掉**，
> 表里列着它，它却一直活在代码里。抽取的收尾动作是**删掉旧的那份并加门禁**，
> 不是写一个更好的新版本。

### 3.6 端到端加密的作用域：**只覆盖实质内容**（2026-11-01，绝对决策）

产品负责人 2026-11-01 拍板（原文见 [`ADR-0079`](../../docs/adr/0079-profile-fields-are-plaintext.md)）：

> 「只有涉及绝对隐私，比如财务数据这种实质性内容时，才允许适用这种加密。
>  这种加密是保守策略，而不是太激进了。我们都允许自托管了，真的想要隐私，
>  保证隐私完全可以自托管。」

| 层 | 处理 | 例子 |
|---|---|---|
| **实质内容** | **端到端加密**（服务端看不到明文） | 任务/便签/清单正文；将来的财务、账目这类绝对隐私 |
| **基础资料** | **明文**（普通账号字段） | 昵称、头像、邮箱、语言 |

🔴 **不许给基础资料加 E2EE**：头像/昵称的读写**不得**要求 E2EE 口令、vault 解锁或任何按钥匙取密文的形态。
旧版头像曾整块加密上传，代价是"换张照片先输入一次密钥"——那是纯加到用户身上的负担，已被推翻。

- 明文 **≠** 公开：`GET /account/avatar` 仍要 Bearer、只回本人；开放他人可见是另一次独立决定。
- 想要更强隐私的用户走**自托管**：服务端归他自己，而不是让官方实例的所有人多背一层密钥。
- 判据：`packages/app-host/tests/hosted-account-profile.spec.ts`（无钥匙也能读写）、
  `apps/web/tests/profile-panel.spec.tsx`、`e2e/tests/profile-avatar-plaintext.spec.ts`、
  `server/tests/account-profile.spec.ts`（服务端自己校验格式与大小）。
- 合规文案必须与实现同步：头像在隐私政策里写"明文、不用于人脸识别或身份核验"。
  「生物特征模板离开设备」这一结论**只指通行密钥的比对**。

### 3.7 产品设计的第一性判据：**用户价值**。约束要说明代价，不得当设计禁令 🔴

**产品负责人 2026-11-02 的原话（同一个错重复两次以上之后的重申）：**

> 「不要那么把那个用户需求、什么隐私需求当做什么阻碍产品发展的、阻碍产品需求的、
>  阻碍产品实现的一个因素。因为这真的太恶心了…… 因为这个隐私真的严重阻碍了我们对产品的设计，
>  根本就没有必要做的那么那么严格。你有就可以了，而且那些东西都是我们默认都是走云端托管的，
>  默认就是公开的，没问题啊。」

> 「你不能因为那个什么隐私问题，让每个 C 端用户都自己部署一套模型吗？这是绝对不可能的呀。」

**规则只有一句：任何「做不了 / 不该做 / 要加确认 / 要加开关 / 要用户自备」，
理由若落在隐私、合规、自托管、授权档位、入口数量……这一侧，结论默认不成立。**
这些是**约束**：它们决定**怎么做**（如何标注、如何告知、默认值是什么），
**不决定做不做**。判「做不做」的尺只有两条：**用户要不要它**、**我们能不能交付**。

#### 3.7.1 五类被禁用的「否定式理由」

下表每一行都真的在本仓出现过，并挡掉过一次产品功能。看到它们作为**结论**出现，就是违规：

| 被禁的否定理由 | 它曾被用来挡什么 | 正确的处理 |
|---|---|---|
| 「为了隐私 / 不被服务端读到 ⇒ 这个功能不做，或先做加密」 | 托管 AI、头像、跨设备可见的资料 | **照做**。默认托管、默认明文、默认公开；需要更强的用户走自托管，**那是对少数人的加值通道，不是对所有人的前置条件** |
| 「合规没定论 ⇒ 先不开 / 先标 blocked」 | 软著、备案链上的功能 | 功能先做，**文本随后对齐**；不确定的部分写进披露与计划，**不写进产品决策** |
| 「用户自己部署 / 自己配 Key ⇒ 那这类功能就属于高级用户」 | 内置助手的默认供给 | 🔴 **绝对禁止把「用户自己部署一套模型」当作 C 端方案**。C 端默认的就是**我们托管** |
| 「需要再加一层授权 / 加一个确认 / 加一个开关才安全」 | 助手权限档（ADR-0082 已删）、出境授权档位 | 安全靠**已有**的风险闸门与一次性披露；**不新增用户要先拨对的开关**。见 [ADR-0082](../../docs/adr/0082-assistant-has-no-permission-tier.md) |
| 「入口 / 开关 / 档位数量快超预算了 ⇒ 这个能力不进去」 | 功能模块可见性 | 预算是**界面整洁**的约束，不是**功能取舍**的约束。该给的能力给，然后用布局与分层消化，见 [entry-layers.md](entry-layers.md) |

#### 3.7.2 约束被允许出场的唯一形态：**「做了什么 + 代价是什么」**

约束不许删功能，但**必须**出现在**披露**里，且必须是可以被验证的具体句子，不是形容词：

| 位置 | 写什么 | 反例（禁写） |
|---|---|---|
| 隐私政策 / 收集清单 | 哪类数据、以什么形态、存在哪里、谁能读 | 「我们高度重视您的隐私」 |
| 出境 / AI 披露 | 哪些字段会发出去、发给谁、留存多久 | 「已采用业界领先的加密保护」 |
| 设置页开关 | 关掉会发生什么（具体到功能灰掉 / 内容变成明文） | 「为了您的安全，此功能默认关闭」 |

⚠️ **「如实说」不是「用来说服用户放弃」。** 一条约束唯一被允许的效果是让用户**知情**，
不是让我们**少做**。

#### 3.7.3 三条自检（提交产品决策前逐条回答）

1. **这个「不行」，把隐私 / 合规那四个字去掉之后还成立吗？** 不成立 ⇒ 结论作废，重来。
2. **我有没有把「少数人要的强隐私」变成「所有人要付的成本」？** 是 ⇒ 反过来：默认轻量，深选项放设置或自托管。
3. **我给的替代方案，需不需要用户部署、输入 Key、或理解一个机制？** 需要 ⇒ 那是**小众通道**，不能拿它当 C 端方案的交差。

#### 3.7.4 与既有决策的关系

- [ADR-0079](../../docs/adr/0079-profile-fields-are-plaintext.md)（基础资料明文）、
  [ADR-0081](../../docs/adr/0081-encryption-is-opt-in-not-default.md)（默认不加密）、
  [ADR-0082](../../docs/adr/0082-assistant-has-no-permission-tier.md)（助手不设权限档）
  是这条规则的**三个已落地样本** —— 它们当时都被写成「绝对决策」，正是因为同一个错重复了三次。
- 🔴 反过来：本规则**不**取消 §3.2 许可证与 §3.1 可维护性两道门 ——
  那两道门管的是**能不能用某个东西**（法律与工程事实），本规则管的是**该不该做某个功能**。
  两者没有交集，**不要拿本规则去绕许可证**。
- 判据：`pnpm check:privacy-as-blocker`（`scripts/check-privacy-as-blocker.mjs`，2026-11-08 实装）。
  扫 `docs/agents/`、`docs/adr/`、`docs/plans/` 共 **245** 个 `.md`，三条判据 R1/R2/R3，
  自检 **11 条臂**（现量由脚本自己打，别在这里抄死）。真仓库现量 **0 处违规 / 2 行登记豁免**。

  **射程与盲区（🔴 写在这里，因为"不知道它管不到什么"比没有门禁更危险）：**

  | 它能判 | 它判不了（已知盲区） |
  |---|---|
  | **R1** 显式因果句式：`因为/出于/考虑到 → 隐私/合规/自托管/E2EE/出境 → 不做/放弃/暂不提供`，且带功能客体 | 跨句推理（"隐私很重要。"换一行"这个功能先放放。"）—— 本门禁**只认单句** |
  | **R2** 把"用户自己部署 / 自备 Key"明说成**方案**（`当作方案`/`就是方案`/`就是默认`） | 隐性自备（"这类能力属于高级用户"） |
  | **R3** ADR-0081 已推翻的绝对句（`从设计上就看不到…明文`）连同语序变体 | 换一个说法讲同一件事（"服务端拿不到内容"）它不认 |

  ⚠️ **判据为什么只认句式、不认词**：第一版把 `不得/不能/禁止` 当否决词，真仓库上红了 **221** 处；
  收窄到功能动词后仍有 **22** 处误报。原因是中文技术文档里 `不得` 绝大多数是**操作纪律**
  （"token 不得进入日志"、"托管 AI 与 E2EE 不能共存"），那讲的正是**怎么做**，是 §3.7 允许的形态。
  最终版是**有序三段**（因果标记 → 隐私侧 → 否决侧）+ 四条豁免，才落到 0 处误报。

  **四条豁免（每一条都对应真实现量，且各有自检臂；删掉任何一条对应臂立刻红）：**

  | 豁免 | 为什么必须放过 | 对应臂 |
  |---|---|---|
  | 带"代价/披露/默认/可选"等限定词 | 这就是 §3.7.2 允许的「做了什么 + 代价是什么」 | 臂 2 / 臂 5 |
  | **引号内**的引用，以及"不是…隐私"的反驳式因果 | 台账在**引用旧承诺以便证伪**它；反驳隐私优先正是本规则被**执行**的样子 | 臂 7 / 臂 8 / 臂 11 |
  | `明文` 不算隐私侧立场词 | `明文` 在本仓多指**传输工程**（"拒绝远端明文 HTTP"、"明文一律 400"）；把它算进去会判红正确句子 | 臂 9 |
  | 本行在**禁止**自备当方案 | §3.7 原文就写着"绝对禁止把用户自己部署当方案"，不豁免则规则**判自己红** | 臂 10 |

  🔴 **不要往豁免表里加路径或放宽词表来让某一行变绿** —— 那是把尺子调软，下一次它就不红了
  （本仓元规则 2）。要么改写那句话，要么按上面四条对照它到底属于哪一类。
