# 需要裁决的三件事（阻塞交付与 R13b 收口）

> 三条都不是"写代码没写完"，而是**方向没定**。每条都给了现量、选项与后果，
> 目的是一句话就能拍板，而不是让人重新调研一遍。

---

## ① 移动端在 `readable` 账号上同步不出去（**阻塞四端交付**）

**现量**（三个独立信源同时成立，见 [`mobile-plaintext-sync-gap-2026-11-08.md`](mobile-plaintext-sync-gap-2026-11-08.md)）：
服务端 `/api/sync/payload-mode` 回 `{"mode":"readable"}`；客户端每次上传都触发一条
`PLAINTEXT_REQUIRED`（不重装、不改代码当场复现 +1）；该账号 `latestSeq` **恒 0**。

**选项**：

| | 做法 | 代价 | 我为什么没直接做 |
|---|---|---|---|
| A | 让**宿主自己选**的 `encryptionMode` 与**服务端模式**冲突时以**服务端**为准 | 1 处（`host.ts:778` 的两个分支各加一个条件）+ 判据 | 会静默推翻"用户显式开了 vault 加密"这个意图 —— 需要产品点头 |
| B | 冲突时**明确失败并分档**（新增 `SyncFailureReason`） | 一个原因码 + 两端词条 + `satisfies` 见证表 | 用户仍然同步不了；但它诚实，且把"网络抖了 vs 配错了"分开 |
| C | 要求"选 vault 加密"时服务端必须切到 `e2ee`（跨端一致性） | 服务端要能改账号模式 + 桌面端也要跟 | 越出单端修复范围 |

**我的建议**：**B 先落**（今晚就能做，且任何方向下都需要的诚实性），
再把 A 作为"用户没显式选 vault 时"的默认。两者不冲突。

## ② 本地库与上传是否必须同模式（ADR-0080 的承重假设）

> 🔴 **这一条今天可以自己结掉一半 —— 而且结掉的那一半正好是"不能擅自动手"的支点。**
> 现量：`packages/app-host/src/payload-mode-migration.ts` 文件头已经把这个问题的答案
> **写在代码里**了：
>
> > 「关闭 = 用同一套 staging（manifest → chunk → commit）把每一条都换掉」
> > 「如果只把'往后写的'改成明文，历史仍是密文，于是：新设备不带钥匙时读不到旧历史；
> > 冲突合并要同时处理两种形状，而**"整库同模式"正是这套设计的承重假设**」
>
> 而且迁移的**存储侧**也已经在了（ADR-0080 §5.2 的 staging，`payload-mode-migration.ts`
> 136 行之后就是 chunk/commit 落地）。
>
> ⇒ 所以"本地库与上传是否必须同模式"这个问题**不是开放问题**：它已有答案（必须），
> 而且有实现（整库迁移）。真正缺的只有一处：**移动端从来没有走过那条迁移**。



设备上的 op 是**明文**存进本机库的，而上传那条是密文。若答案"必须同模式"，
那**切换 payload mode 时要重建/迁移本机库**，而仓库里没有任何这样的机制。
这一条不裁决，①的修法就只能局部修上传侧，留下"本地明文 / 云端密文"的组合。

## ③ R13b 剩下四维要不要做、按什么档做

字号档 / 密度 / 行着色三态 / 纯色自定义（应用图标按 ADR 不做）。
四格各自需要先定方案，见 [`p2-remaining-scope-2026-11-08.md`](p2-remaining-scope-2026-11-08.md)。
最小可交付的一种切法：**只做"行着色三态"**（它零写入、且是滴答对标里最常被点名的那个），
字号与密度留到"排印与间距 token 族"那一单。
