## 1. 这条需求从哪来

来自一位真实用户的反馈（原话）：

> 除了时间统计的基础功能，还可以给学习、运动、社交、深度工作等等不同板块分很细致的颜色，
> 对于人脑来说可视化效应很强（比如把自己不太健康但老戒不掉的那种活动定成红色，每周一看会很醒目）

这句话里**包着两件不同的事**，必须拆开，因为它们一个该做、一个不该做：

| | 用户的诉求 | 判断 | 理由 |
|---|---|---|---|
| (a) | **让那个活动一直在视野里，不能被遗忘／被合理化掉** | ✅ **这就是真正起作用的机制** | 颜色是**前注意属性**，在被"看"之前就已经分好组 —— 一片红会自己跳出来，不需要阅读 |
| (b) | **因为它是"坏的"所以给红色**（App 赋予褒贬） | ❌ **不做** | 见 §3。这与本仓库已记录的三种伤害模式同形 |

**承认 (a) 是对的，同时拒掉 (b)，是本计划的核心。** 不做 (b) 的代价是零 —— 因为 (a) 需要的是
**辨识度 + 具体量 + 与自己过去比**，**不需要**褒贬。

## 2. 已拍板的决策

| # | 决策 | 拍板人 |
|---|---|---|
| D1 | **颜色由用户自己赋义**：我们只提供 8 个色槽位，保证彼此可区分 | 用户 |
| D2 | **App 永不判断某个活动"健康／不健康"**，也永不自动上色 | 用户 |
| D3 | 先落地激励体系，本特性**另开一个增量** | 用户 |

D1 + D2 合起来是一句话：**调色板由我们给，褒贬由用户自己赋。**

用户想把短视频设成红，完全可以 —— 那时红色是**他的**信号，不是我们的说教。
而且**自赋的红没法反驳**：一个人不会跟自己定的规矩争辩，却会立刻反驳 App 派发给他的道德判断。
这也正好落在 SDT 的自主感上，与已定的「**只与自己的过去比**」是同一条线。

### 反需求（写死，防止后来"好心"地加回来）

- ❌ **自动健康度评分 / 自动"好活动／坏活动"分类**
- ❌ 因为超支而变红（**渐进的红色预警**也是自动褒贬的一种，同样不做）
- ❌ 按分类排名、按分类打分、"本周最差分类"之类的措辞
- ❌ 任何形式的"你这个月很失败"结论文案

## 3. 为什么 App 不碰褒贬（三条理由，按重要性）

1. **它会把判断权从用户手里拿走。** 「社交」可能是陪家人，也可能是刷短视频；
   「游戏」可能是放松，也可能是逃避。**App 判错别人对自己生活的评价，比沉默糟得多。**
2. **对"戒不掉"的活动，内疚框架的预测是「不记录了」，不是「改了」。**
   看报告会难受 → 少看报告 → 数据没了 → **连"一周 12 小时"这个事实都看不见了**。
   这正是仓库已引过的 abstinence-violation 效应的近亲。
3. **仓库自己已经踩过这个形状。** [`../research/competitor-incentive-teardown.md`](../research/competitor-incentive-teardown.md)
   里「羞耻／内疚」作为**伤害模式**出现了三次：

   | 产品 | 伤害机制（原文） |
   |---|---|
   | Forest | 枯树 + 连坐**制造 guilt**，把"我的专注"变成"我对朋友的义务" |
   | Habitica | **guilt / 责任压力最重**——"我漏做 Daily，队友掉血"；死亡惩罚对低动机用户是退出按钮 |
   | 番茄Todo | **排行榜焦虑最典型**——"别人 10+ 小时"对低产出日是**羞耻来源** |

   与「从不制造愧疚」这条红线直接冲突。

### 那"醒目"从哪来？

从**辨识度**来，不是从褒贬来：一片红之所以跳出来，是因为它在调色板里**罕见而独特**，
不是因为它代表"坏"。所以我们要保证的是**颜色彼此可区分**（含色觉障碍下的区分），
而不是**颜色带有对错**。

### 数字比颜色有力

让人震动的从来是「**这周 12 小时**」，红色只是把这件事变得刺眼。
**刺眼的东西会被回避，具体的东西会被面对。** 所以分类视图必须同时给出**量**：
小时数 / 次数 / 占比，且可点开看明细。

## 4. 真正的工程量在**时间归因**（颜色是最后 10%）

「按分类统计时间」的前提是**时间能归到分类上**。现在 heyta 只有一处产生时长：番茄钟（`FOCUS_SESSION`）。
`HABIT.target + unit='分钟'` 也能贡献时长。

🔴 **好消息：零新增字段就能跑通第一版。** 全部链路都已存在，缺的只是渲染：

```
FOCUS_SESSION.taskId  →  TASK  →  PROJECT.color
HABIT.target + unit   →  HABIT.color
```

| 已存在的字段 | 位置 |
|---|---|
| `Project.color?: string` | `packages/domain/src/entities.ts:126` |
| `Tag.color?: string` | `packages/domain/src/entities.ts:133` |
| `Habit.color?: string` | `packages/domain/src/entities.ts:196` |
| `FocusSession.taskId?: string` | `packages/domain/src/entities.ts:225` |

⚠️ **实测：这三个 `color` 字段目前在代码里完全没被消费** ——
`apps/web`、`packages/app-host`、`packages/domain` 里一处 `.color` 读取都没有。
它们是躺着的能力，不是已有功能。

**归不了类的**：无任务的纯计时（`taskId` 为空）。
→ **直接不计入分类统计，不为它加字段**（"无归属"本身就是一个诚实的分类）。

## 5. 可视化形状

### 5.1 不改现有热力图

现有热力图（`apps/web/src/lib/heatmap-theme.ts`）一格 = 一天，用 `heat-1..4` 编码**一个**量（强度）。
文件里那条注释已经把话说明了：

> ⚠️ 四档活动色用 `heat-1..4`，不要全部用 `primary`：色阶的意义就是**一眼看出多少**，
> 四档同色等于把"这周很密"和"只打过一次卡"画成同一个样子。

用户想要的是**第二个轴**（类别）。**一天有多个分类，一格画不了两个色** ——
硬塞只能二选一，必然丢信息。所以**别改它，加新形状**。

### 5.2 主形状：分类泳道图（small multiples）

```
深度工作  ▓ ▓ ▓ ░ ▓ ▓ ·      ← 每行一个分类
学习      ▓ ░ ▓ ▓ ▓ ░ ▓
运动      ░ · ░ ░ ▓ · ·
社交      ▓ ▓ ░ ░ ░ ▓ ▓
短视频    █ █ █ ░ █ █ █      ← 用的也是强度色阶，不是"警告红"
```

每个分类一行，行内是**强度**色阶。形状取自 GitHub「每个仓库一张图」与 Apple Health「每个指标一张卡」。

**为什么它是对的**：

- 用户要的场景是「每周一看会很醒目」→ 泳道图的对比是**跨行**的，
  **一行满 vs 一行空**一眼就出来，而单行内部的颜色浓度反而不重要。
- **它用位置表达类别、用文字标签命名，颜色只编码强度** ——
  天然满足仓库那条硬规则「**不许只用颜色表达信息**」（已写进
  `apps/web/src/features/timeline/GanttChart.tsx:36`、`features/settings/AiSettings.tsx:17`、
  [`ai-capability-branches.md`](ai-capability-branches.md)）。
  **不需要为这条规则做任何妥协。**

### 5.3 辅形状：周堆叠条

一周一根柱，按分类堆叠，配文字总量：适合「总共 40 小时里 12 小时是 X」这种陈述句。

### 5.4 用户赋义的入口

分类本质上是**清单／标签／习惯**（已有实体），所以赋义入口就是它们的编辑界面：
给一个清单选一个色槽位。**不新增"分类"实体。**

## 6. 工程约束（真成本在这里，别想着绕过）

| 项 | 约束 |
|---|---|
| 🔴 **`color` 存什么** | **不能存裸 hex**（跟不了暗色主题、对比度无法保证、违反"token 是唯一事实源"）。**存槽位号 `1..8`**：数据只存**不变量**，颜色长什么样留给 UI 层。改调色板不影响磁盘上的旧数据。 |
| **加分类色 = 加 token** | 现在语义色里分类只有 `quadrant-1..4`（4 个）。每加一个色都要在 `packages/design-system/src/tokens.ts` 的对比度清单里登记 `(fg, bg, min, why)` —— **对比度是测试实算保证的**，不是文档保证的。 |
| **暗色** | 不是亮色反相，**必须实际切着看**（AGENTS.md §5）。 |
| **旧数据** | 槽位号是**新语义** → 必须**可选 + 运行时兜底**（不认识的值 → 无色），不许必填。见 AGENTS.md §3.3。 |
| **不许只用颜色** | 每行每块必须有文字标签。已定规矩，本特性不需要新定。 |
| **派生纯函数** | 统计口径（每分类时长、每周堆叠）一律在 `packages/domain`，`apps/web` 只扁平化并注入 `now`。 |
| **零 schema bump** | 复用既有可选字段，不新增实体、不加必填字段。 |

## 7. 待拍板（下一轮开工前要定的）

1. **色槽位是 8 个还是更少？** 越少越可区分（也越不容易撞色），但用户"分很细致"的诉求越难满足。
   我倾向 **8 个**（够细，且能保证两两可区分）。
2. **清单是唯一赋义入口，还是标签／习惯也能赋义？** 三者都有 `color` 字段；
   但"同一个活动既能按清单算又能按标签算"会得到两套统计口径 —— 需要定**谁优先**（我倾向：清单优先，标签不参与时长归类）。
3. **无任务的纯计时**要不要允许事后补一个分类？现在计划是"不计入"。
4. **泳道图放在哪个视图**：`growth`（我的）还是 `focus`（专注）还是新建？需要看现状再定。
5. **色觉障碍的区分保证做到哪一档**：只保证两两可区分，还是要做色盲模拟下的验证？
