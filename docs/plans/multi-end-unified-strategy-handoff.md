## 3. 当前卡在哪（诊断链，按发现顺序）

### 3.1 症状

`verify-mobile-ios` 第 5 步：

```
✅ 已清除本机凭据，三个字段都就位（等了 1 秒）
✅ 已填写「服务器地址」
✅ 「端到端加密口令」输入框不在树上（可能已经设好、被页面收起）—— 跳过填写
✅ 「访问令牌」输入框不在树上（…）
❌ 凭据填齐了但「立即同步」仍是禁用 —— 字段没真的写进活配置
❌ 笔记本 300 秒内没读到 …；❌ uploadStatus 仍是「pending」
```
⇒ 凭据进不了活配置 ⇒ 同步出不去、实时连不上 ⇒ **后面 7 项连带失败**（共 9）。

### 3.2 🔴 最可能的根因（已由三组**互为对照**的探针钉死）

| 探针 | `idb ui set-value` 的表现 | 树上的结果 |
|---|---|---|
| 状态机探针（进「我的」→清除×2→离开再回来） | 全程**没写过** | **三个字段在每个状态下都在** |
| 孤立写入 | **rc=0（成功）** | 「访问令牌」与「端到端加密口令」**双双消失** |
| 孤立写入（第二次） | **rc=1（失败）** | 三个框**原样都在**、值也没变 |

**确定模型（三条）**：
1. **没有"字段可见性状态机"** —— 三个框本来一直在（我一度以为是状态机，查了两轮，错了）；
2. **"框消失"是写成功之后的行为**（rc=0 才消失）⇒ 所以 `set_field` 必须**先口令、后令牌**（顺序是语义）；
3. 🔴 **`idb ui set-value` 本身时好时坏**（同一条命令 rc=0 / rc=1 都出现过）。

**而 shim 把 rc 吞掉了** ⇒ "工具失败"与"写进去了"在调用方看来**完全一样**（都是 `detail=""`）。
**这一整轮的排查方向（状态机、填写顺序、坐标过期）全被这个假象带着走。**

### 3.3 已经**排除**的假设（别再查一遍）

| 假设 | 为什么不成立 |
|---|---|
| AX 树读不到 | **读得到**。之前"连可见的「任务」都找不到"是因为我用了 `~/.local/bin/idb`，而脚本解析的是 `~/.heyta-tools/idb/venv/bin/idb` |
| `idb ui set-value` 不存在 | **存在**（在 venv 那个里，带 `--value/--match-key`）。同上：查错了二进制 |
| 字段不接受 `set-value` | 不接受的是**那段表单**，不是命令。认证页的字段 rc=0 正常写入 |
| 坐标过期 | 重读 frame 后用新坐标，rc 仍时好时坏 ⇒ 不是坐标问题 |
| 页面按状态隐藏字段 | 三组探针对照后否定；隐藏的触发是"**写成功**"，不是状态 |
| 凭据只在内存（重启即失） | 对，但**同一进程内**保留；`erase` 清磁盘清不掉进程内存 —— 这是它**时红时绿**的原因 |

### 3.4 ⛔ 结论：那条路径**本身走不通**

手动凭据表单**不是为一个字段一个字段地写设计的**（写成功一次就收起这一段）。
而页面自己写着：「**下面是手动填写凭据的兜底路径**」。
⇒ 继续在这条路径上修是**修错了对象**。**应当搬到主路径**（§5）。

## 4. 本轮（第 27–32 轮）实际修好的东西

### 4.1 🔴 `verify-mobile-ios.sh` 的四层"绿而无效"（已全修）

| 层 | 症状 | 修法 |
|---|---|---|
| **不构建** | 前置写着"已装好 Release 版"，**全仓没有一处 `simctl install`** ⇒ 验的是模拟器上那个旧包 | 默认 `xcodebuild` + `simctl install`；`HEYTA_IOS_SKIP_BUILD=1` 可跳过 |
| **bundle id 过期** | 工程是 `com.heyta`，脚本默认 `org.reactjs.native.example.HeytaMobile`（RN 模板值）。`install` 装的是前者（**exit 0**），而脚本查/启动/读 SQLite 的都是**另一个 app**。设备上积了**三个容器**（09-27 / 09-28 / 09-29），解析到最旧那个 | 两个脚本的 `BID` 默认值改为 `com.heyta`；加了"解析不到就红"的断言 |
| **我写的新鲜度判据恒真** | `find … -newer /dev/null`（`/dev/null` 的 mtime 是**当下** ⇒ 恒假、匹配 0 个）+ `xargs stat`（路径含**空格** `All in one Data` ⇒ 切分错 ⇒ 0 行）⇒ `SRC_MTIME=0` ⇒ 恒真 | 去掉 `-newer`、改 `-print0` + `xargs -0`；**算不出输入时判红**而不是放过 |
| **我的等待条件写错** | 等"按钮出现"，而按钮**一直都在**（变的只是 `enabled`）⇒ 等于没等 | 改等 `found && enabled` |

### 4.2 🔴 一个真死导出：`notifyConfigured()`

`apps/mobile/src/sync/auto-sync.ts` 里**被导出**、文档写着"用户刚保存了同步凭据 —— 立刻同步一次"，
而**生产代码零调用点**。同步还能发生是因为走的是 `write-signal` 的"本地写入"那条路；
而它承载的另一件事 —— **启动实时通道** —— 永远不会发生。

**修**：在三处保存凭据的地方配对通知（`auth/session.ts`、`ProfileScreen` 的 effect 与 `onSync`），
并加**结构性**判据：每个 `writeSyncConfig(` 调用点后 25 行内必须有 `notifyConfigured();`
（**先剥行尾注释再判** —— 第一版把注释掉的调用也算成调用，注释掉照样绿）。
故障注入：注释掉 ⇒ **红**（`auth/session.ts:63 写了同步凭据，却没通知`）；还原 12/12。

⚠️ `session.ts` 里只能用**动态 `import()`**：静态引 `auto-sync` 会把 `react-native` 拖进 node 测试，
实测 `RolldownError: Flow is not supported`，整个 `auth-flow.spec.ts` 连**加载**都过不去。

### 4.3 实时通道的**端点 P0**（上一轮）

`buildRealtimeUrl` 拼 `${origin}/ws`，而服务端注册在 `prefix: '/api/sync'` ⇒ 真实端点 `/api/sync/ws`。
实测 `/ws`→**404**、`/api/sync/ws`→**101**。
**为什么长期没发现**：`packages/sync-client/tests/realtime.spec.ts` 把**错路径逐字断言**了下来
（测试与实现一起错），而两个宿主的接线测试用**假 WebSocket**（任何 URL 都接受）。
**修**：路径改对 + 改掉那 4 处断言；`verify-realtime-push.mjs` **直接 import `buildRealtimeUrl`**（不手拼），
于是"客户端改错，这里就红"。故障注入：改回 `/ws` ⇒ 红（404）；还原 diff 空、7/7 绿。

### 4.4 shim 吞掉 `set-value` 的退出码（第 31 轮）

`scripts/tools/ios-ax-shim.py` 的 `--set` 原本 `subprocess.run(..., capture_output=True)` 后**丢掉返回值、异常也 `pass`**。
**修**：现在 emit `setRc` / `setErr`（异常分类成 `-1` 超时 / `-2` OSError）；
`verify-mobile-ios.sh` 的 `set_field` **先看 rc**，非 0 直接报「写 X 时 idb 自己失败了（rc=…）：<stderr>」。

**5.1a 主路径已接进脚本（第 33 轮），42 通过 / 3 失败 —— 而 3 项**收敛到一把锁**

第 33 轮把第 5 步改成**先走主路径**（`注册 / 登录` → 填字段 → `验证并登录`），
成功就**跳过**兜底填写。脚本现在这一段长这样（`CREDS_OK` 控制）：

```
✅ 已进入认证页（主路径）
✅ 已填写「服务器地址」
✅ 已填写「邮箱」
✅ 已填写「端到端加密口令」（secure 框回读为掩码，长度 20）
❌ 写「粘贴邮件里的链接或令牌」连续 5 次都失败（idb rc=1）：
   The axbridge backend found no element at (201.0, 1018.0); the point is empty
✅ 认证页上有提交按钮「验证并登录」
❌ 主路径没能把凭据带进活配置 —— 退回下面的兜底路径
```

🔴 **那把锁是一句话**：**「粘贴令牌」字段在屏幕外**。
实测 frame `y ≈ 1018`，而屏幕只有 **874** 高 ⇒ 按坐标写的 `set-value` 够不到它。

⚠️ **不能靠滚动解决（已实测，别再试）**：
- `idb ui swipe 200 700 200 300 --duration 400` → **挂死**（`time` 实测 1m30s 不返回，等于超时）；
- `idb ui scroll down` → 报错且什么都不做（`AGENTS §7` 记过）。

⇒ **唯一可行的办法是抢在键盘弹出与该段重排之前填它** —— 即**令牌第一个填**（已改，见脚本注释）。

⚠️ 同时注意：兜底路径那三句"框不在树上"是**后果不是原因** ——
主路径失败后 `ax "返回"` 没把页面切回「我的」，兜底那三句是在**认证页**上找手动凭据的框。

**5.1b 第 34 轮：它红在**更早**的第 4 步 —— 而根因是"**夹具不可重跑**"**

把令牌改成"最先填"之后重跑，**反而更差**（18 通过 / 3 失败），而且红在第 **4** 步
（`按了「添加」但 Composer 还开着`）—— **而那一轮我根本没改第 4 步**。

**根因**：app 的状态**跨轮残留**。上一轮（`ios18`）主路径失败后停在**认证页**，
而脚本刻意**不 terminate**（会话内已派生过 Argon2 密钥，terminate 会白花 30–40 秒），
于是这一轮从"认证页"起步 ⇒ 第 1 步的 `ax "任务"` **点不到**（模态盖住标签栏）
⇒ 后面全歪。

⇒ **这是夹具的真缺陷：它不可重跑。** 一条"跑第二次结果不同"的验收**不能算验收**。

**修**：在切标签之前，先按 `取消 → 关闭新建面板 → 返回` 逐个尝试关掉模态，
**判据是"任务标签点得到"**，而不是"关掉了几个东西"。

**5.1c 第 34 轮收尾：**唯一**卡点确认，而它是**工具能力的边界**，不是产品缺陷**

归一化起点之后，结果**可重跑**了（两次都是 **42 通过 / 3 失败**，同一处）：

```

✅ 已填写「服务器地址」      ← 主路径的字段**接受写入**
✅ 已填写「邮箱」
```

**5.1g 🎯 第 36 轮：那个"够不到的字段"其实是**一个 iOS 系统弹窗**盖住了整个页面**

```
[以后]  [保存]
```

iOS 在 `secure` 字段填过字之后会弹这个**系统**对话框。它的两个后果**都不留痕迹**：

而且**跨应用重启存活** ⇒ 上一轮留下的会**污染下一轮**（这正是"同一份代码时红时绿"的来源）。

**5.1i 第 37 轮：滚动原语**找到了**，但脚本里没复现出来；另有**两次我自己造成的损坏**

**（a）找到的真正有效的滚动手势**（手动探针，四个方向各测一遍）：

| 手势 | 结果 |
|---|---|
| `(200,750)→(200,250)` | ✅ **有效**：y `1031 → 997`（每次约挪 **34–50px**） |
| `(200,760)→(200,300)` | ❌ y 不动 —— 起点 760 很可能已落在 **ScrollView 之外**（标签栏/Home 指示条那带） |
| `(380,700)→(380,300)` / `(380,300)→(380,700)` / `(200,250)→(200,750)` | ❌ 都不动 |

⇒ **第一次测出"idb 不能滚"是错的**（那次实验根本没进认证页、字段不在树上）。
`idb ui swipe` **rc=0、返回很快、确实会滚**，只是**每次挪很少**，所以需要十几次。

⚠️ **但把它写进脚本之后仍不生效**（`scroll_into_view` 每次都报"滚不到"，y 恒为 1031）。
手动能滚、脚本里不能 —— **差异还没定位**（键盘状态？坐标时机？）。这是下一轮的第一件事：
**在脚本运行的同一时刻打印 y 的前后值**，而不是只打印最终结论。

**（b）🔴 两次我自己造成的损坏 —— 都是"盲字符串替换"**

我为了修 `$VAR` 紧跟中文那个坑，写了一句**全量替换** `s.replace('$'+name, '${'+name+'}')`。
它**会命中共享前缀的更长变量名**：

| 原意 | 被改成了 | 后果 |
|---|---|---|
| `$y2`（变量 `y2`） | `${y}2`（变量 `y` + 字面 `2`） | 滚动助手静默判错 |
| `$yy` | `${y}y` → 我"修"成 `${yy}` | ✅ 这个是真损坏，改对了 |
| `${FW}x${FH}`（宽 × 高，如 `56x56`） | `${FWx}${FH}` | `FWx: unbound variable`，第 1 步直接崩 |
| `${UDID}_companion` | `${UDID_companion}` | sock 路径错 |

而我**用来修它的那次扫描**又是一次盲替换，于是**把两处合法的写法也改坏了**。

⇒ **教训（已够格进 `AGENTS §7`）**：
**变量名的批量替换必须带词边界**（`\$name(?![A-Za-z0-9_])`），
**而且改完必须逐处看 diff**，不能只看"脚本语法通过"——
`bash -n` 对 `${FWx}` 是**通过**的（它只是个未定义变量，运行时才炸）。

**5.1j 🔴 第 38 轮：定位完成 —— 这是**产品缺陷**，而且是目标里"无断点"要判的那一类**

```
[滚动 3..14] y 1031 → 1031  ← 卡住，再也上不去
```

| 元素 | AX 报的 y |
|---|---|
| 「粘贴邮件里的链接或令牌」 | **1031** |
| 「验证并登录」（提交按钮） | **1090** |
| **应用窗口高度** | **874** |

**决定性证明**（不是推理）：按坐标点 `(201, 1090)`（提交按钮报出来的位置）——
结果是 **切到了「我的」标签**。那个坐标被**钳到屏幕底部、打在标签栏上**，
**根本没有到达按钮**。⇒ **用户点不到它。**

如果只看退出码，会得出"按钮能点"的结论 —— 这正是本仓那条

这意味着 **"粘贴令牌"这条登录路在 iPhone 上走不完** —— 正是目标里

`ScrollView` 是标准写法，所以成因不在那几行 —— 更像是某个子元素撑破了测量）。
**我不在上下文余量只剩一点的时候去改一个我不确定的布局根因。**

**5.1k 第 39 轮：更正 —— 不是"完全够不到"，而是**可滚范围被低估了约 174px**（量化了）

截图（`/tmp/authpage.png`）纠正了我上一轮的一个说法：认证页**是**一个会被底部标签栏截断的


| 量 | 值 |
|---|---|
| 内容实际延伸到 | **y ≈ 1100** |
| 窗口高度 | **874** |

**下一轮的第一件事（已经不必再摸索）**：查**哪一个子元素没把高度报给 ScrollView**。
最强候选：`Screen` 的 `body` 是一个带 `gap: t['space.4']` 的纵向 `View`
（`apps/mobile/src/ui/kit.tsx:233`），而认证页有**约 10 个子元素**
—— 若 `gap` 未计入内容高度，差额约 `9 × 16 ≈ 144px`，**与实测的 174px 同量级**。
⇒ 先在探针里量"子元素高度之和 + gap 之和"与 ScrollView 自报内容高度之差，**再动手改**。

**5.1l 第 40 轮（最后一轮）：`gap` 假设被**干净地否定**，已回退**

按 §5.1k 的线索做了那个决定性实验：把 `Screen` 的 `body` 从
`gap: t['space.4']` 改成**显式 spacer**（`marginTop`），重建 + 重跑。

**结果：y 的数值逐字相同** ——

```
[滚动 1] y 997 → 1049
[滚动 2] y 1049 → 1031
[滚动 3..14] y 1031 → 1031（卡住）
```

⇒ **`gap` 不是成因。** 假设被推翻，**改动已回退**（它对**每一个屏**的布局都动了，
而没有被证实有效 —— 留着它就是把一个未验证的改动留在主路径上）。
回退后：`tsc` 0 错、移动端 **418 通过**、`kit.tsx` 回到 `gap: t['space.4']`。

🔴 **这个否定结果本身是有价值的**：它把"内容高度被低估"的成因**从 `gap` 上排除掉了**，
而剩下最可能的方向是：

1. **视口高度的扣除**：`Screen` 的 `ScrollView` 只被 `flex: 1` 约束，
   而**底部标签栏是导航器画在它上面的** —— 如果导航器没有为标签栏预留空间，
   视口就比实际可见区**高**约一个标签栏（≈83px），
   而 AX 报的 y 是**窗口**坐标 ⇒ 二者之间会有一个固定差额；
2. **`AppBar` 的高度**是否被正确扣除；
3. 也可能**根本不是布局缺陷**：`ScrollView` 的内容高度是对的，
   而是**滚动被别的什么截住了**（例如手势被某个子元素捕获）。

**下一轮的第一件事**：量**这三个量**，而不是继续改布局 ——
`ScrollView` 视口高、`AppBar` 高、底部标签栏高，以及"内容高度 − 视口高"与
"实测可滚范围（52px）"之差。**先把差额归到哪一项上，再动手。**

**5.1m 🔴🔴 第 41 轮：**`idb ui swipe` 根本驱动不了滚动** —— 于是"产品缺陷"这个结论**不成立**，撤回**

在一个**明显可滚**的页面上定标（「我的」页内容延伸到 **y=2684**，窗口 874 —— 它**必须**能滚）：

```
起始 y(账号) = 143
上拖 ×3 → 143, 143, 143
下拖 ×3 → 143, 143, 143
长 duration（--duration 600）发出后 8/14/20/28 秒 → 全部 143，进程一直挂着
```

⇒ **一次都没动，28 秒也没动。**

🔴 **这推翻了我第 38/39 轮的结论。** 当时我在认证页上看到 y 在 `997 ↔ 1049` 之间摆动，
就断定"`ScrollView` 的可滚范围只有 52px、被低估了 174px"。而真相更可能是：

**那 ±34px 是 idb 手势的噪声，不是滚动极限** —— 因为**同一个手势在一个必须能滚的页面上
一次都不生效**。⇒ **"认证页底部够不到"这件事，我只证明了"AX 夹具够不到"，
没有证明"用户够不到"。**

⚠️ **这个错误的形状与我第 39 轮自己记下的那条完全相同**（"把工具边界当用户边界"），
**而我在记下它的同一轮里又犯了一次**，并且这次还把它写成了"真产品缺陷"、
还据此**改了 `Screen` 的布局**（那处改动已回退）。

**⇒ 撤回三处**：
1. §5.1j 的"**这是真产品缺陷**" —— 改为"**未验证**：AX 夹具够不到，用户能否够到未知"；
2. §5.1k 的"可滚范围被低估 174px" —— 改为"**那个量测的是 idb 的手势，不是 ScrollView**"；
3. §5.1l 的"下一轮量这三个量" —— 那个方向基于同一个错误前提，**降级为"可选"**。

**⇒ 现在的正确结论**：`idb ui swipe` **不可用于本项目的滚动**
（在与本项目无关的、必须能滚的页面上也不生效）。要验"底部内容可达"，得先找到
**另一个能滚的机制**，或者**换一条不需要滚动的验收路径**。

**✅ 而"不需要滚动"的那条路已经找到了**：「我的」页的**手动凭据表单**三个框实测在
**y=488 / 647 / 733** —— **全部在可见区内**（窗口 874）。所以本轮改了兜底路径：
**先确认真的回到了「我的」页**，再填那三个框（口令先、令牌后 + rc 重试）。

**5.1n 🔴🔴 结论性判断：`verify-mobile-ios` 的**判定不可信**，不是产品不可用**

到第 41 轮为止，同一份代码连续几轮**红在不同的地方**：

| 轮 | 红在哪 | 当时的表现 |
|---|---|---|
| ios19 / ios21 | 第 4 步 | `按了「添加」但 Composer 还开着`，而 press 走的是 **`success`** 分支 |
| ios30 | 第 5 步 | 滚动助手滚不动（后来证明**手势本身就不生效**） |
| ios32 | 第 1 步 | `label 数 6` —— 停在**欢迎页**，说明 0.5 步的「先离线使用」**点击没生效** |

⇒ **共同的病**：这个夹具的**坐标点击与滑动都不可靠** ——
shim 报 `success`、应用没收到；而**同一个手势在"必须能滚"的页面上一次都不生效**（§5.1m）。

🔴 **所以准确的结论是**：
**"iOS 认证旅程在真机上有缺陷"这件事，我没有证据。**
我有的证据是"**这套 AX 夹具够不到/驱动不了某些东西**"。
两者不是一回事 —— 而我在第 38/39 轮把它们混成了一件，还**据此改了 `Screen` 的布局**（已回退）。

**⚠️ 下一个人接手时，先读这一条**：`verify-mobile-ios` 目前 **47 通过 / 3~4 失败**，
而**那些失败不是产品判决**。在把它的红当成缺陷之前，先回答一个问题：
**"是产品做不到，还是这套夹具做不到？"**
本仓已有的答案模板是 §7 的 `tap-blocked-by-keyboard` —— 那是**结构性**判据（键盘按键带
`KeyboardKey` trait），所以它可信；而**"按坐标点没反应"目前没有结构性判据**。

**⇒ 下一步真正的优先级**（不是继续修 iOS 夹具）：
1. 给 shim 加一条**结构性**的输入确认（不是"tap 返回 success"，而是"点完之后**回读到了预期变化**"）；
2. 或者**换一条不依赖坐标输入的验收路径**（例如 `verify-mobile-auth.sh` 走的 Android 那条 —— 但它被 AVD 阻塞）；
3. **或者**承认这一段验不了，如实登记 —— 而不是让它继续产出**看起来像产品判决的红**。

**5.1o 第 41 轮的实施：把「按了要回读」做成机制，而不是靠人记得**

按 §5.1n 的优先级，给夹具加了**结构性**的输入确认（`scripts/verify-mobile-ios.sh`）：

```bash
# press_until <要按的> <应出现的> [尝试次数]
#   点完之后**回读"另一件事真的发生了吗"** —— 不是看 `--press` 返回了什么
press_until() {
  for i in $(seq 1 "${tries}"); do
    [ found(want) = True ] && return 0
    ax "${do_lbl}" --pressable --press
    sleep 2
  done
  ...
}
```

已接到三处**历史上真的咬过人**的地方：

| 位置 | 回读判据 | 历史事故 |
|---|---|---|
| 0.5 步 `先离线使用` | 出现「任务」 | 第 1 步 `label 数 6`（app 停在欢迎页） |
| 导航 `我的` | 出现「注册 / 登录」 | 兜底路径的框"不在树上" |
| 进认证页 `注册 / 登录` | 出现「邮箱」 | — |

🔴 **并且：`FIXTURE_UNRELIABLE` 一旦置位，`summary` 会先打印醒目告警。**

```bash
eval "$(declare -f summary | sed '1s/^summary ()/summary_lib ()/')"   # 原函数改名保留
summary() {
  [ "${FIXTURE_UNRELIABLE:-0}" = "1" ] && echo "⚠️⚠️ **本轮夹具自身不可信 —— 上面的通过/失败都不是产品判决**"
  summary_lib "$@"
}
```

⚠️ **不改共享 lib**（`scripts/lib/mobile-e2e.sh` 的 `summary` 被**全部**移动端脚本用）——
用 `declare -f` 把原函数改名保留再包一层，**只影响本脚本**。

⇒ **这条的意义**：在此之前，这个脚本的红**看起来像产品判决**，而它其实是夹具判决。
现在它**自己会说这句话** —— 一份"看起来像产品判决"的红，比一句"我验不了"更危险。

**5.1p 第 41 轮结果：**iOS 从 47 → 51 通过**，而剩下 5 项现在**正确地被归给夹具**

加完结构性判据之后连跑几轮，最好一轮：**通过 50~51 / 失败 4~5**（本轮起点是 47/4）。

`0.5 → 1 → 2 → 3 → 4 → 5a` **全部通过**，其中：

```
✅ 「先离线使用」真的把 app 带进了主界面（**判据是欢迎页的标志消失**）
✅ 已进入认证页（**回读到「邮箱」才判成功**）
✅ 已填写「服务器地址」 / ✅ 已填写「端到端加密口令」（secure 框）
❌ 没回到「我的」（离开认证页=1，到达「我的」=0）
```

🔴 **最后那一行就是这一轮最重要的产出**：它把"夹具做不到"与"产品做不到"**分开了** ——
`press_until "我的" "服务器地址"` 试了 3 次也没到，于是它报"**没回到「我的」**"，
并置位 `FIXTURE_UNRELIABLE`，而 `summary` 会打印
**「本轮夹具自身不可信 —— 上面的通过/失败都不是产品判决」**。

⚠️ **而加这个机制的过程本身又抓出我自己三次假绿**（都记在 §5.1o 与下面）：

| # | 我的判据 | 为什么是假绿 |
|---|---|---|
| 1 | `press_until "先离线使用" "任务"` | **欢迎页背后就是标签栏** ⇒ 一进来 `found("任务")=True` ⇒ **一次都没按**就返回成功 |
| 2 | `press_until_gone "返回" "邮箱"` | 「邮箱」消失只说明**离开了认证页**，不说明**到了「我的」**（实测它绿了，而紧接着三个框"不在树上"） |
| 3 | `$LEFT，` | 变量紧跟**全角逗号** ⇒ `set -u` 报 `unbound variable`（**这个坑本 session 第四次**，而 `AGENTS §7` 里早就写着） |

⇒ 修法分别是：**判"消失"而不是"出现"**、**判据要合取**（离开 **且** 到达）、**`${VAR}` + 词边界替换**。

**5.1q 第 42 轮：修掉**弹窗的时机**、**导航判据**，并收窄了"点击不可靠"这句话**

连跑几轮，**两个此前一直挡路的东西被修好并验证**：

```
✅ 已按坐标关掉 iOS「保存密码？」系统弹窗（它不在应用树里，只能按坐标点）
✅ 已离开认证页**并**到达「我的」（判据是「邮箱」消失 **且** 「服务器地址」出现）
```

**（a）弹窗的时机错了** —— 这是这一轮找到的真 bug：

- 弹窗是在 `secure` 字段**失焦/表单提交之后**才出现的，而我的 `dismiss_ios_save_password()`
  只在**填完那一刻**调过一次 ⇒ 到后续步骤时**树已经退化**（实测：9 个标签**一个都查不到**，
  现场 dump 全空），而症状是"按了「我的」没反应"。
- ⇒ **修**：离开认证页之后**再清一次**。现在它**真的触发了**。

**（b）而守卫本身也被骗过**：第一版用「注册 / 登录」当"没有弹窗"的证据 ——
**而认证页的页面标题正好就是「注册 / 登录」** ⇒ 守卫在弹窗盖着时照样认为没弹窗。
⇒ 改成"**两个底部标签（「任务」/「我的」）都不在**"（弹窗态下都不在；连认证页上「我的」都还在）。

**（c）"坐标点击不可靠"这句话要收窄** —— 同一轮实测：

| 动作 | 结果 |
|---|---|
| `ax "任务" --pressable --press` | ✅ 切过去了 |
| `ax "我的" --pressable --press` ×3 | ✅ **3/3 全成功** |

⇒ **标签导航是可靠的。** 之前的失败**不是**"点击不可靠"，而是**当时树是退化的（弹窗盖着）**。
⚠️ 而我在第 41 轮把结论写成了"坐标点击与滑动在这个应用上不可靠" —— **那句话太宽**，
它会把下一轮的人带去换输入通道，而真正的问题是**弹窗的时机**。

**（d）顺带确认了一个结构**：树里 label 为「我的」的节点有**两个** ——
AppBar 的**标题**（`AXStaticText`，y=80）与底部**标签**（`AXGenericElement`，y=776）。
shim 的 `--pressable` 过滤**取对了**（y=776）✅ —— 这一条没问题，别再查它。

**（e）手动凭据表单仍然不能逐字段填**（复现了第 32 轮的结论）：
填完「服务器地址」之后，另外两个框**又消失了** —— 与"任何一次写成功都会收起这一段"一致。

| **同名二进制能力不同** | `~/.local/bin/idb`（旧、**无** `set-value`）vs `~/.heyta-tools/idb/venv/bin/idb`（脚本用的、有）。我用错的那个下了**反向结论** | 手工复现一律用 `resolve_idb()` 解析出来的那个（`scripts/lib/mobile-e2e.sh`） |
| **`$VAR` 紧跟中文** | `$BID）`、`$_lbl」` ⇒ bash 把中文并入变量名 ⇒ `set -u` 报 unbound variable | 一律写 `${VAR}` |
| **Python heredoc 里 `\"`** | r-string 中 `\"` 是**字面两字符**；写进 bash 就变成"转义引号 ⇒ 引号不闭合"。本轮踩了**两次** | 中文引号，或分开 `-c` 调用；改完必 `bash -n` |
| **`/dev/null` 的 mtime 是"当下"** | `find -newer /dev/null` **恒假、匹配 0 个文件** ⇒ 判据恒真 | 别用它当"全都要" |
| **`xargs` 默认按空白切分** | 本仓路径含空格 ⇒ `stat` 收到不存在的路径、错误被吞 ⇒ 0 行 | `-print0` + `xargs -0` |
| **门禁消费 `apps/web/dist`** | 不重建就测旧代码 | 跑 `check:macos-window` 等之前先构建 |
| **并发重负载 → 假红** | `check:macos-window` 在多个后台任务并行时偶发红，单独跑 exit 0 | 重负载下别信单次红，单独复跑 |
| shim **没有 `--dump`** | `ax - --dump` 走 argparse 报错、**静默输出空**（`scripts/lib/mobile-e2e.sh` 的 `ax_dump()` 因此是坏的） | 用宽泛 label 的 `--list --json` 去问 |
