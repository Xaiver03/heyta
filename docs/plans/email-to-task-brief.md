## 0. 为什么这是一条线，而不是自动收集的一个勾选框

用户嘴里的"自动收集"九成指邮件（原话口径记在开工单 §6 第 5 格）。而首版自动收集收集的是
**能主动发 HTTP 回调的来源**：签名 webhook → 服务端加密排队 → 设备领取 → 抽字段 → 落待办。
邮件不是"再来一条 webhook"，它换了三件事：**谁把内容送到我们手里**、**这封信凭什么算这个人的**、
**正文在链条的哪一段才第一次变成明文**。这三件每一件都是设计，不是配置。

🔴 因此这份工单的第一条纪律：**别把它做成"给现有规则表加一个 source=email"**。
加一枚枚举值在编译期是最便宜的，在合规与隐私上是最贵的。

## 2. 六个必须先回答的问题（每个都带一个能红的判据）

1. **投递方式选哪条**：专属地址（每人一个带令牌的收件别名，转发到我们的接收端）· IMAP 拉取
   （要用户交邮箱凭据）· 自建 MX（要域名、反垃圾、可用性 SLA）。
   判据：选定后本文件必须写清"谁付这台服务器的钱、邮件停在谁的盘上几天"。
2. **归属证明**：一封信凭什么算这个账号的？发件地址绑定、专属令牌、还是首次确认邮件？
   判据：一条用例——同一封信投给两个账号，只有被证明的那一个领得到。
3. **明文第一次出现在哪**：端到端加密是本产品的地基。若正文在接收端就是明文，
   那等于新增一类服务端可见的用户内容，与 `AGENTS.md` §1 的前提直接对冲。
   判据：披露块（`web.ai.disclosure.*` 那一族）必须逐字说出邮件正文的处置；
   两壳对账尺会把不一致念成红（`apps/mobile/tests/ai-copy-parity.spec.ts`）。
4. **长文与格式**：HTML、引用链、签名档、转发嵌套、附件、多任务一封信。
   判据：`needs-confirmation` 那一档要能承载"模型没把握的一整段"，不许退化成整封塞进 `note`。
5. **额度与计费**：一封邮件可能拆成 N 个待办，扣一次还是 N 次？现有计量口径见
   开工单 §3 A4（那次"一次调用扣两下"的确证）——邮件这条入口**别在计费口径未拍之前上线**。
   判据：一条真库用例钉"一封含 3 个可执行项的邮件 = 几次模型调用 = 几次计量"。
6. **合规与对外**：域名、ICP/备案口径、留存与删除请求（GDPR 式"删掉我的邮件"），
   以及"这台实例到底替不替你存正文"这句话怎么写。
   判据：`docs/reference/inbound-automation-protocol.md` 的保留那一节必须能逐句对上真实实现
   —— 现成的范本是那把 7 天保留对账尺（`scripts/check-retention-window-parity.mjs`，
   A6 那一格入库的）。

## 3. 建议的第一刀（最小闭环，且不许越界）

**P0 = 专属地址 + 明文不进服务端**：给每个账号一枚一次性本地部分（`+<token>` 别名或独立域），
只接**这一类**信，接收端做与现在 webhook 同样的动作——**HPKE 封存后排队**，设备领取时才解密。
这一刀的价值是把"谁把内容送到我们手里"和"归属"两格落地，同时**不新增服务端可见的正文**。

明确不做（P0 地界外）：自建 MX、反垃圾训练、附件解析、日历邀请（iCalendar）解析、邮件线程合并。

## 4. 归负责人、执行 AI 不许拍的格子

1. 用哪个域名/谁出这台收信服务器，以及它是否进 heyta 的在册部署。
2. 是否接受"用户交 IMAP 凭据"这种产品形态（它会把我们的支持面放大一整层）。
3. 第 2 节第 5 问那句计费口径（与开工单 §6 第 3 格是同一件事）。
4. 对外怎么宣传这条入口——尤其"任何邮件都能收"这种话，在 P0 那一刀之后仍然不成立。
5. AC 的勾（这条线如果要开 AC-9～AC-n，勾法沿用自动收集那份计划的纪律）。
