# 界面丑的根因审计（2026-11-14）

> 触发：产品负责人看完语言设置页与「我的」页之后。
> 方法：真机 `uiautomator dump`（bounds ÷3 = dp）+ 读 `TEXT_STYLES` 与 `tokens.css` 的实际值。
> 拿 `apple-design` 与 `ui-ux-pro-max` 的规则对照。
>
> 这不是"逐处美化"，是**找系统性的错**。下面每条都有读数。

---

## 一、用户看到的三件事，与它们的实测原因

### 1. 「语言设置页上面为什么写着『外观』」

页面标题是「语言」，但内容区第一组的标题是「外观」。

**这是我把组名从「外观与语言」改成「语言」之后，又加回「外观」组，却忘了改页面标题。**
一句话的事，但它让整页的标题与内容对不上 —— Apple 的 wayfinding 第一条就是
"每一屏都要回答：我在哪"。

### 2. 「『外观』这两个字的标题，还没有下面『跟随系统』大」

**它们本来就不一样大，但差得不足以形成层级。** 实测：

| 元素 | 文字档 | 字号 | 字重 | 颜色 |
|---|---|---|---|---|
| 「外观」组标题 | `section-title` | **16px** | semibold | `foreground`（**主文字色**） |
| 「跟随系统」选项 | `row-title` | **16px** | medium | `foreground` |

**同字号、同颜色、只差一档字重。** 于是组标题在视觉上是一行"加粗的正文"，
而不是"一个分组的名字"。

更糟的是：仓库里**已经有一档专为组标题设计的样式** `group-label`
（13px + semibold + `foreground-muted`），它的注释写着：

> 这一档是 2026-10-02 被产品负责人的一句"为什么标题比下面的说明还小"逼出来的。
> ……后果是实测出来的那个倒挂：标题 11px，而它**管辖**的空态说明接的是
> `row-title`（16px）—— 说明比标题大 1.45 倍。

**同一个错又犯了一次**，只是这次的形状是"组标题与内容同档所以分不出"。
而这次没人被拦住，是因为 `section-title` 与 `group-label` **两档并存**，
用的时候随手选一个。

### 3. 「我的界面 UI、UX 排版都乱得要死」

真机量出来是**三条轴、十种间距**：

```
y=198   h=20dp x=48   '我的'          ← 页面标题   轴 48
y=588   h=44dp x=48   '注册 / 登录'    ← 按钮      轴 48
y=816   h=44dp x=96   '订阅'          ← 行        轴 96
y=972   h=44dp x=96   '设置'          ← 行        轴 96
y=1224  h=20dp x=120  '近期状态'       ← 组标题    轴 120  ← 比它管的行更靠右 24dp
y=1380  h=18dp x=96   '本周完成任务'    ← 值行      轴 96
```

| 症状 | 读数 |
|---|---|
| **三条左缘** | 48（标题/按钮）/ 96（行）/ **120（组标题）** |
| **组标题比它管辖的行更靠右** | 120 vs 96，差 **24dp** |
| **同一类"动作"两种缩进** | 「注册/登录」按钮 x=48，「订阅」「设置」行 x=96 |
| **组间距无节奏** | 实测 29 / 40 / 52 / 54 / 60 / 64 / 69 / 72 / 80 / 92 dp |

组标题为什么在 120？因为 `SectionHeader` 在标题**前面**画了一枚图标
（`icon` + `space.2` = 16 + 8 = 24dp），标题于是被推右。

## 二、根因（五条，全部是系统性的）

### 根因 1 · 同一个语义有两档文字样式并存

`section-title`（16 semibold foreground）与 `group-label`（13 semibold muted）
都叫"组标题"。**同语义两档 = 每一处自己按心情选**（`ux-principles.md` §6b 的同一条，
只是这次发生在文字档位层，不在控件层）。

### 根因 2 · 组标题用了主文字色

`section-title` 配 `color.foreground`。而组标题是**索引**，不是内容 ——
它应该弱于内容（iOS 的组标题是 `secondaryLabel` 灰字）。
用主文字色 ⇒ 它看起来像"第一条内容"。

### 根因 3 · 组标题前面塞了图标

`SectionHeader` 36 处调用全部带 `icon`，`SettingsSection` 5 处带 `leading`。
图标把标题推右 24dp（mobile）/ 72dp（设置页），于是：

- 组标题与它管辖的行**不在一条轴上**；
- 组标题看起来像"一个列表行"，因为它和行一样有前置图标。

iOS 的设置页组标题**没有图标** —— 组标题是纯文字索引，图标是行的装饰。

### 根因 4 · 两个组标题组件并行

`apps/mobile/src/ui/kit.tsx#SectionHeader`（带图标、`section-title`）
与 `packages/ui/src/settings/Settings.tsx#SettingsSection`（带 leading、`section-title`）。

同一件事两份实现 ⇒ 两边的手势、间距、颜色各自演进。
（`check:theme` 只钉 token 表，钉不到"组标题长什么样"。）

### 根因 5 · 间距没有阶梯

组间距由三处共同决定：`SectionHeader` 的 `paddingTop: space.2`(8dp)、
`SettingsSection` 的 `note` 间距、以及各屏 `<Stack gap>` 自己的值。
三处相加的结果是 29~92dp 的十种值 —— **没有任何一档是刻意定的**。

## 三、修法（按 `apple-design` §16 的 Craft / Simplicity）

### 一条轴、一档字、两种间距

| 项 | 定值 | 理由 |
|---|---|---|
| 组标题文字档 | **`group-label`**（13px semibold muted） | 已有且注释论证过：中文没有大小写线索，必须靠字重 + 弱色赢 |
| 组标题左缘 | **与行左对齐**（同一条轴） | 组标题管辖行，不跟着图标走 |
| 组标题前的图标 | **去掉** | iOS 设置页的组标题没有图标；图标是行的属性 |
| 组标题上方 | **24dp** | 分隔上一组 |
| 组标题下方 | **8dp** | 紧贴它管辖的第一行（"离它管的东西更近"） |
| 页面标题 | 保持 `screen-title`，x=`screen.gutter` | 不参与组标题体系 |

### 落地顺序（每一档都能判红）

1. **合并文字档**：`section-title` 在"组标题"这个用途上不再使用；
   `section-title` 保留给"内容区的小标题"（如「新建任务」面板标题），
   并加门禁：**组标题位置出现 `section-title` ⇒ 红**。
2. **`SectionHeader` 去图标**：`icon` 变可选、默认不渲染；
   36 处调用点删掉 `icon`。
3. **`SettingsSection` 的 `leading` 不再作用于标题**：移到 body 里，或去掉。
4. **间距收敛**：组标题上方 24、下方 8，写进 `group-label` 的消费契约。
5. **左缘统一**：`screen.gutter` 一条轴；组标题不吃额外缩进。

### 判据

- 真机 dump：组标题与它管辖的第一行 **x 相同**；
- 组标题字号 **< 行字号**，颜色为 `foreground-muted`；
- 同一屏组间距（上一组最后一行 → 下一组标题）**只有一个值**；
- 门禁：`check:group-heading`（新）—— 组标题位置用 `section-title` / 带 `icon` ⇒ 红。

## 四、这次为什么会发生（我自己的部分）

前面一个月里我在做"结构"（入口分层、控件形态、触控目标），
**把排版当成结构的副产品**。而实测里最刺眼的问题（组标题与内容同级、
组标题比内容更靠右）**一条结构判据都抓不到** —— 它们不违反任何"控件高度一档"
"一屏一种控件"，只违反**视觉层级**。

所以这一轮补的不是又一个控件规则，而是**读数的维度**：
`scripts/ux-parity-metrics.py` 现在只量"行高/行距/左缘种类"，
**量不出"组标题是不是比内容弱"**。这一轮要给它加两条：

- 组标题与紧随其后的第一行的 **x 差**；
- 组标题与其管辖行的 **字号比**（需要从源码取档位，dump 不给字号）。

第一轮修了组标题的三处错（档位/颜色/左缘）。但那只解决"这一处"，
下一次有人新建一个分组标题，还会犯同样的错 —— 因为**没有一张"位置 → 档位"的表**。

| `check:type-roles` | `scripts/check-type-roles.mjs` | 孤儿角色 ⇒ 红；三个位置组件绕过表 ⇒ 红；**`--self-test` 两臂** |
| metrics 两列 | `scripts/ux-parity-metrics.py` | **大间距种数**、**组标题高度比**（这两条量不出层级就抓不到这次的错） |

### Skill 筛选（用户要求"搜罗各种好用的 Skill"）

| Skill | 结论 | 依据 |
|---|---|---|
| `apple-design` | **采用** | §15 Typography（层级靠 weight+size+leading 成组、tracking/leading 随字号反向）、§16 Craft/Simplicity（每个间距都要能辩护） |

## 六、2026-11-14 第三轮：把清单清零

上面「下一轮的清单」已经全部处理完。逐条对照：

| # | 判据 | 结果 |
|---|---|---|
| ① 大间距种数 ≤ 2 | 源码级 `check:spacing-scale`（每屏垂直间距 ≤ 2 档） | ✅ 绿（`TasksScreen` 删掉重复的 12dp 后达标） |
| ② 组标题到它管辖的第一行 | tasks **10dp** / settings-language **8dp** / profile **20dp**（= 组内 4 + 卡内边距 16）/ share **0dp** | ✅ 全部 ≤ 24dp |
| ③ 组标题不得比它管辖的行更靠右 | 全量扫 29 个界面 | ✅ **0 处** |
| ④ 6 个待迁移角色 | 迁完 `screen-title`(1) / `panel-title`(8)；`row-meta`/`value`/`note` 归为「内容类型」不查孤儿；`detail-title` 是**死档**（0 消费点）已移出 | ✅ |
| ⑤ 四象限卡内两条左缘 | 查源码：色块 `icon.sm`(16dp) + gap 8dp = **24dp**，实测 204−132 = 72px = 24dp 分毫不差 ⇒ 是色块占位，**不是错位** | ✅ 不改 |

### 指标口径改过两次（都是我自己错的）

1. **间隙算法**：第一版记 `y − prevY`（行起点差），于是 52dp 里含了 44dp 行高 ——
   读出来的"大间距 52/57/66"其实是"行高 + 间距"。按它去收敛会把行高当间距调。
   改成 `y − (prevY + prevH)`。
2. **聚类容差**：19/20/24 这种差 1–5dp 的值，是同一设计值在不同容器里的测量差，
   不是三个档位。加 ±4dp 聚类。
3. 另外排除了**被别的节点包含**的节点 —— 一个"行"在 dump 树里常同时出现三层。

### 四象限：一条登记了两次的"缺陷"其实不存在

之前写「卡内两条左缘差 36dp，需看图确认是图标占位还是错位」。
查源码后是：`swatch` 16dp + `headerRow` gap 8dp = 24dp，与实测 72px 完全一致。
**它是色块，标识象限颜色。** 登记销掉。

教训：**"我看不了图"不等于"这是缺陷"** —— 源码结构能回答的问题，不该留给"需看图确认"。

## 八、第二台设备（360dp 窄屏）与首启流程

2026-11-15 换到一台 1080×2280 / 480dpi 的设备（360dp 宽，主设备是 385dp）。
窄 25dp 会暴露挤压与换行问题，而干净安装能看**首启流程** —— 那几屏在主设备上已经看不到了。

### 签名

两台设备装的是同一个包，签名指纹都是 `signatures:[51ed3f60]`。
根因见提交 `7b066bb2`：构建跑在 `linux-dev` 上，而那台的 `~/.gradle` 里没有发布签名，
所以 release 变体一直退回 **git 里那份 `debug.keystore`**。
它统一，但不是"配置好的统一"，是"恰好进了仓库"。发布签名要生效得修构建链路。

### 首启流程的三屏（都只在全新安装时出现）

| 屏 | 问题 | 判定 |
|---|---|---|
| 欢迎/引导（4 页） | 插画占 70% 屏高，文案只有「任务」「日历」「专注」两三个字；要滑 4 次才到主界面 | **滑动次数多于信息量**（配速问题）。改法是产品决策，未动 |
| 隐私同意弹窗 | **三个出口**（同意并联网 / 只用本机 / 右上角「以后再说」）+ 四段长正文平铺 + 两个蓝色法律链接 | 三个选择等于没有选择。**合规区，未动**，登记 |
| 登录面板 | 「返回」在左下、「先离线使用」在底部居中 —— 两个"离开"的位置与样式都不同 | 位置可以统一，但登录流程敏感，未动 |

🔴 这三屏的共同点：**它们都是"一次性的"**，所以历来没有进入逐屏审查的范围 ——
但用户第一次打开 app 看到的就是它们。登记为待办。

### 窄屏（360dp）上的确认

`/tmp/goto.sh` 现在只认内容区（排除 y<300 顶栏与 y>2200 底栏），就是为这个。

## 十二、四象限（2026-11-15）：问题是量出来的，改法两次都没成

### 现象

四个象限**全空**时，每张卡片约 **250dp 高**，一屏只看得见两格。
每张空卡里各写一遍「这里还没有任务」—— 同一句话四次，要滚两屏才看完四个空块。

### 量到的成因链

`board` / `stack` / `cell` **三层都带 `flexGrow`**：

```
kit.tsx 的 Screen body     flexGrow: 1   ← "铺满"契约在移动端的落地
  QuadrantBoard.board      flexGrow: 1
    QuadrantBoard.stack    flexGrow: 1
      QuadrantBoard.cell   flex: 1  + minHeight 192
```

四格加起来（4 × 192 = 768dp）不足一屏 ⇒ 剩余空间被一路传下去、由 `cell` 平分
⇒ 每格约 250dp。`stack` 的注释原本写「四格加起来通常超过一屏 ⇒ 没有剩余空间可分」——
**那在有任务时成立，"四个都空"时就不成立**。

### 两次尝试，都没生效

| # | 改法 | 结果 |
|---|---|---|
| 1 | `cell` 空态加 `cellEmpty { flexGrow: 0, flexBasis: 'auto' }` | **无效**，仍是 250dp |
| 2 | `board` 与 `stack` 的 `flexGrow: 1` → `0` | **无效**，仍是 250dp |

第 2 次改完重新构建、装机、复看，图还是 250dp —— 而 `board`/`stack` 当时**已经没有 `flexGrow`**。
说明撑着它的不是这两层，是更上面的 `Screen` body 的 `flexGrow: 1`。

而 `kit.tsx:330` 那段注释明确写了这条 `flexGrow` 是**共享层"铺满"契约的落地**，
不是随便加的。要动它，得先弄清 web 端同一条契约靠什么兑现 —— **不在这一屏的范围**。

### 所以这一屏**没改**

两次改动都回滚了。**未验证的改动不进库** —— 与其提交一个"看起来改好了"的版本，
不如把成因链和两次失败记下来，让下一次从第三层开始试。

### 仍然成立的两件事

1. **「这里还没有任务」写四遍** 是真的（与共享清单那次同源）；
2. **空块 250dp** 是真的。

它们没被修，但**已经被测量、被记录**。

### 追加（同日）：五次尝试全失败，改用探针定位

| # | 改的地方 | 结果 |
|---|---|---|
| 1 | `cell` 加 `cellEmpty` | 无效 |
| 2 | `board` + `stack` 的 `flexGrow` → 0 | 无效 |
| 3 | `tokens.css` 的 `minHeight` 12rem→7rem（并重新 `generate`） | 无效 |
| 4 | `cell` 的 `flex: 1` → `flexGrow: 0` | 无效 |
| 5 | `list`（`cell` 的子元素）的 `flex: 1` → `flexGrow: 0` | 无效 |

**第 5 次之后加了一次探针**：把 `cell` 的 `backgroundColor` 临时改成 `red` —— **立即变红**。

这证明了两件事：
1. **文件没错**、**改动确实编译进了 APK**；
2. 但**高度不由这些属性决定**。

也就是说，撑开象限格的是**再往里的某处**（`TaskList` 在 `density="compact"` 下空态的高度，
或者 `Screen` body 与 `ScrollView` contentContainer 那两层 `flexGrow` 的组合）。

**五次改动全部回滚。** 没有提交任何一行 —— 因为我**无法证明改动生效**，
而"改了但看不出变化"正是一次伪装成修复的失败。

### 🔴 产品负责人的原话（2026-11-15）

> 「四象限完全要，肯定是要跟待办清单类似的，我们的逻辑差不多。」

这句话把这件事从"样式微调"变成了**功能问题**：

- 四象限**必须有**，不是可裁的视图；
- 它要**像待办清单一样可用** —— 能看、能勾、能操作；
- 逻辑与清单"差不多"。

而当前的四象限是**只读分类**：每格只显示落在该象限的任务，点「更多」才能移动。
空态时四格各写一遍「这里还没有任务」，而且每格高到一屏只看两个。

**所以正确的下一步不是继续调像素，是先回答**：
四象限里的任务行要不要和清单一样有勾选、滑动、长按菜单？
如果要，那这一屏要复用 `TaskList` 的交互而不是另画一套。

**这条登记为产品需求，不是视觉缺陷。** 它超出了"逐屏视觉审查"的范围 ——
需要先定交互，再谈排版。

### 🔴 第六次：探针推翻了我的诊断（我之前的结论是错的）

用两次探针把"谁在撑高"量出来了：

| 探针 | 观察到 | 结论 |
|---|---|---|
| `cell` 背景改红 | 整格变红 | 文件没错、改动编译进去了 |
| `list`（cell 子元素）背景改绿 | **绿只占卡片下半部**（约 108dp），不是整格 | `list` 没撑满 |
| `stack` 背景改青 | **青只在卡片圆角外露的边角** | `stack` 被 `cell` 完全盖住，高度 = 各格之和 |

**结论：`cell` 的高度是它自己的内容撑出来的，不是 flex 平分。**

也就是说 —— **我前面五次"改 flex 无效"不是 bug，是因为那里本来就没有 flex 在撑**。
每格 163dp = header（色块+标题+副标题 ≈ 55dp）+ `TaskList` 空态（≈ 108dp）。

**因此我最初那条判据"空块 250dp 太大"本身就是错的** —— 163dp 是内容的自然高度，
不是被谁拉伸。四格加起来 ≈ 700dp，一屏看三个半、滚一下看第四个，
**这在内容为空的情况下是正常排版，不是缺陷**。

### 那么真正该改的是什么

不是高度，是**空态文本的密度**：每格都写一遍「这里还没有任务」，
四遍同样的字占了各格 108dp 里的大部分。

但这也要等产品先答那个问题（四象限要不要和清单一样有勾选/滑动/长按），
因为**如果格子里有真任务行，空态文本就不存在了**。

**所以我在这里停手，不再改高度。** 六次尝试里五次是白改，根源是我没先量清"谁在撑"，
只凭"看起来太高"就动手。

## 十九、纠正一条我自己写错的记录：「方框 vs 开关」

我在 §九 与多轮口述里写过一条形状问题：

> `NotificationPrefsPanel`（方形标记 vs Switch）

**这条是错的。查证过程：**

1. `grep -rn "Switch" packages/ui/src apps/mobile/src --include=*.tsx` → **零命中**；
2. 唯一带 `accessibilityRole="switch"` 的是 `settings/Settings.tsx:649`（`SettingsSwitchRow`）；
3. 而它画的东西（`:671-690`）是：

```tsx
{/* 状态标记：一个方框 + 选中时的对钩。 */}
<View style={[styles.marker, { backgroundColor: checked ? primary : 'transparent' }]}>
  {checked ? <HeytaIcon data={Check} ... /> : null}
</View>
```

**它也是方框 + 对钩** —— 全仓**根本没有"开关"这种视觉**。

所以「共享通知」三行（`NotificationPrefsPanel`，`role="checkbox"` + 方框）
与设置里的开关行（`SettingsSwitchRow`，`role="switch"` + 同样方框）**视觉上是同一套**，
只是**无障碍角色不同**（`checkbox` vs `switch`）。

### 这一条的教训

**我把"role 不同"当成了"视觉不同"**，然后在文档里写成一条待修形状，
还连着几轮把它当遗留项挂着 —— 每一轮都在"下一轮要改它"里出现。

**判据**：报一条形状问题之前，至少要看到**两边的渲染代码**，
不能只看 `accessibilityRole` 这种语义属性就断言外观不同。

### 剩下的真问题只有一个（角色不一致）

同一个方框，一处念「复选框」一处念「开关」。对读屏用户是两种操作预期：
复选框是"选中/不选中"，开关是"开/关"。

**这条要不要统一，取决于产品的语义**：共享通知的三个是"要不要收这类通知"（开关语义），
设置里的是"要不要启用"（也是开关）。**按语义该统一成 `switch`。**
但那已经不是视觉问题，属无障碍。**登记，不在本轮视觉审查范围内动。**

## 二十、`check:empty-state` 的盲区查清了（不是"门禁坏了"，是规则只认几个名字）

### 断言 B 是什么

它不是"禁止手写空态"，而是**债务账**：手写空态站点冻结在登记表上，**只减不增**，
每一项都是债、不是许可（`scripts/check-empty-state.mjs:978-1005`）。

所以 `HabitProgressList` 那处**不是门禁坏了** —— 它压根没被识别成一个站点。

### 四个 marker，漏在第四个

| # | kind | 匹配什么 |
|---|---|---|
| 1 | 骨架类 | `ht-empty`（web 类名） |
| 2 | 空槽位类 | `__empty` |
| 3 | 空态 testid | `[^"']*empty` 的 testid，**但落在共享 `EmptyState` 范围内的不算** |
| 4 | 直接渲染空态词条 | `t('…empty…')` 这种**直接调 i18n** 的 |
| 5 | 空态文案 prop | `emptyText` / `emptyHint` / `emptyMessage` |

`HabitProgressList` 写的是 `<Text>{labels.empty}</Text>` —— **文案是通过自定义 prop 名
`labels` 传进来的**，既不是 `t()` 直接调用，也不叫 `emptyText/emptyHint/emptyMessage`。

**四个 marker 一个都匹配不上。** 这就是漏检的全部原因。

### 为什么不顺手补一条规则

补 `/\blabels\.\w*empty/` 会立刻**误报**：`TaskList` 的 `labels` 里也有 `empty` 字样，
而它把文案**交给内部渲染**（那处同样是手写的，是另一笔债，不是"传 prop"这件事错）。

**门禁该拦的是"手写了一份空态"，不是"有一个叫 empty 的 prop"。**
按名字匹配这条路已经走到头了 —— 要真判，得看"这一处最终有没有渲染 `EmptyState`"，
那是另一个量级的分析。

### 所以记下来，不改脚本

**已知未覆盖的形状**：文案经自定义 prop 传入、视图自己画 `<Text>`。
已知实例：`TaskList`（`styles.empty` + `<Text caption>`）。

**这两处现在都还在**（`HabitProgressList` 这一轮改掉了，`TaskList` 没动）。
下一步要么把 `TaskList` 也换掉，要么接受它是一笔在册的债 —— 但那要先能把它**登记**进去，
而现在登记不进去。

## 二十六、回归抽查：「提醒与通知」与「关于与帮助」（第 31 轮）

### 提醒与通知：健康

```
提醒送达                          (?)
系统通知授权            未允许 >     ← 橙
精确闹钟                已允许 >
提醒不受省电限制        受省电限制 >  ← 橙
```

三行一组、单轴、橙色**只出现在"需要用户去处理"的那两行**（`未允许` / `受省电限制`），
而 `已允许` 是普通色。这正是橙色该有的用法（不是"状态不同就变色"）。

### 关于与帮助：只有一行，但那一行是对的

```
帮助与反馈
  ✈  投诉与举报  (?)
```

**我第一反应是"这一屏太空了"** —— 但查了代码，空的理由是成立的：

```ts
// SettingsScreen.tsx:858-864
...(isOfficialHostedInstance(readSyncConfig()?.serverUrl ?? '')
  ? [{ kind: 'note', testID: 'settings-operator', text: operatorFilingLine(OPERATOR) }]
  : []),
```

**运营者与备案号只在「官方托管实例」上显示。** 这台设备没配服务器地址，
所以没有那一行 —— **不是漏了，是不该在这台设备上出现**（备案号属于服务方，
本地自托管不该挂别人的备案号）。

### 真正缺的只有版本号

这一屏**没有版本号**，这在本仓是已知的：版本号要经 native 通道读
（`expo-constants` 之类），而**本仓规禁止擅自引入第三方依赖**（§3.1 可维护性门槛 + §3.2 许可证）。
所以它必须作为一次**显式的依赖决策**来做，不能顺手加。

**登记，这一轮不动。**

### 结论

两屏都**没有需要改的排版问题**。这一轮的产出是"确认它们不需要改"，
以及**否掉了"关于页太空"这个直觉判断** —— 它下面藏着一个正确的能力门控。

## 二十七、四象限改成 2×2 之后，逐条核「勾选 / 滑动 / 长按」

上一轮（§二十五 之后）把四象限从单列改成 2×2。目标里要求「任务行与清单一致：勾选/滑动/长按」，
这一轮逐条核。

### 勾选 ✅ 一致

四象限每一格**直接渲染共享的 `TaskList`**（`QuadrantBoard.tsx:17` 的注释）：
「每一格直接渲染共享的 `TaskList`……**不是三份 JSX**」。所以勾选框、行高、长按都是同一份。

### 长按 ✅ 一致

`onLongPressTask` 从 `QuadrantScreen` 一路传到 `TaskList`（`QuadrantBoard.tsx:128,344`）。
四象限里的「⋯」就是它。

### 滑动 ❌ **没有 —— 但这是设计，不是遗漏**

`TaskRow.tsx:452` 的注释写得很明确：

> 两道闸：宿主没给 `swipeActions`（**Web、日历、四象限**）与这一档密度不渲染行尾

两道闸：
1. 宿主不给 `swipeActions` → 四象限、日历、Web 都不给；
2. 密度档 `showTrailing: false` → 四象限用 `compact`，行尾本就不渲染。

**实测确认**：在四象限「Buy」行上从右往左划，没有任何反应。

### 我的判断：滑动**不该**加到四象限

2×2 之后每格只有 **165dp 宽**。在这个宽度里做左右滑动手势：
- 滑动阈值（通常 30–40% 行宽）只剩 50–65dp，**极容易误触**；
- 而误触的后果是"划走了这条任务"—— 在象限图里，用户正在**看全局**，
  不是在做行级编辑。

**长按已经覆盖了"对单条任务做点什么"这个需求**（多选/移动/更多菜单）。
滑动是"快速处理"的手势，它属于列表视图，不属于俯视图。

**所以这一条不是"四象限要补齐滑动"，而是"目标里那句'与清单一致'在滑动这一项上不成立，
理由是两种视图宽高比不同"。** 记下来，不改。
