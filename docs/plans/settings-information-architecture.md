# 设置页信息架构（IA）调研与改造方案

> **状态**：调研完成，方案待产品拍板。**本文档不改任何代码。**
> **范围**：移动端 `apps/mobile`、Web `apps/web`、桌面三壳 `apps/desktop{,‑macos,‑windows,‑linux}` 的设置面与「我的」页。
> **不在范围**：登录/注册页（`WelcomeScreen` / `AuthScreen` / `features/auth/**`）、样式表（`apps/web/src/styles/**`）。
> **上游依据**：[`account-information-architecture.md`](../reference/account-information-architecture.md)（现有产品裁决）、[`ux-principles.md`](../agents/ux-principles.md) §1/§4/§6/§10、[`overlay-feedback.md`](../agents/overlay-feedback.md) §2、[`design-system.md`](../agents/design-system.md)。

## 0. 一句话结论

**现在的分组不是按"用户想干什么"分的，而是按"代码里谁先实现"分的。**

三端一共长出了 **4 条互相冲突的分组轴**——按对象（个人资料 / 数据管理）、按能力（同步 / AI）、按合规（隐私）、按商业（订阅），再外加两个**无意义的桶**（移动端「常规」、Web「任务与显示」）。结果是：用户在「我的」页要**扫 16 行**才能确认"设置在哪"，而进去以后又要**再选 7～8 组**，其中至少 **10 项**在两屏各有一个入口、**1 段 React 节点**被同时渲染在两个地方、**3 个高频项**被埋在 2～3 层之下。

参考产品的结构（账号卡 / 商业横幅 / 功能模块 / 大分组 / 关联与导入 / 福利活动）**是配它的**：它有等级、有勋章、有福利活动、有"关联与导入"这类独立业务域，我们没有。它的**分类逻辑**（按用户意图分、商业化单独拎出来、账号只有一行）可以借用；它的**分组清单**不能照抄。

### 2.4 桌面三壳（`apps/desktop*`）

**没有独立设置 IA**——三壳都是把 web 产物当载荷：

| 壳 | 载荷 | 代码 |
|---|---|---|

### 3.2 同一段 React 节点被同时渲染在两个地方

`ProfileScreen.tsx:1102-1146` 定义了 `const syncStatus = (<>…</>)`（含"状态"标题 + 状态卡 + 待上传 + 最后同步 + 「立即同步」按钮 + 未配置提示 + 慢 KDF 提示）。

- 它被渲染在「我的」：`:1374` 之外的 `:1108-1146` 直接出现在本屏滚动流里；
- **它同时被当作 prop 传进设置面**：`:1431` `syncStatus={syncStatus}`，然后在 `SettingsScreen.tsx:618` `{syncStatusVisible ? syncStatus : renderSyncConfiguration()}`。

⇒ 打开设置 → 同步与隐私时，**同一份同步状态会被挂载两次**（Modal 覆盖在「我的」之上，「我的」不卸载——这正是 `check-mobile-settings.mjs` R1 刻意保住的性质）。

后果不只是"多画一遍"：两处各自持有 `StatusRow` 的本地 state，冲突按钮（`:1114-1116` 与 `:1541`）会出现两个可点实例，而它们的 `onOpenConflicts` 分别拨 `conflictsOpen`——**同一个 `ConflictSheet` 被两个触发器指向**。这属于"同一件事两份实现"的变体：一份 JSX、两个挂载点。

### 3.3 三个高频项被埋在 2～3 层之下

| 项 | Web | 移动端 | 差 |
|---|---|---|---|
| 回收站 | 1 次（rail 工具 tab，`view-tabs.ts:264`） | **3 次**（我的 → 设置 → 数据管理 → 回收站） | **+2** |
| 账号与安全（改密码/退出登录） | 2 次（头像 → 设置 → 左栏「账号与安全」，面板内联） | **3 次**（我的 → 设置 → 账号安全 → 账号与安全 → 690 行的 `SecurityScreen` 里再选） | **+1 层 + 一个整屏** |
| 提醒被拒后的再授权 | 2 次（头像 → 设置 → 任务与显示 → 提醒） | **3 次**（我的 → 设置 → 常规 → 提醒送达） | **+1** |

第三条有一个**写在代码里的自相矛盾**：`SettingsScreen.tsx:69-71` 的注释说

> 提醒送达那一节：拒绝授权之后**唯一**的再授权入口（用户得先知道它被拒了，而入口必须和那句话在同一屏上 —— 挂在详情面板里等于要用户再找第二条路）。

**"必须和那句话在同一屏上"是对的**，但它同时说明：一旦用户关掉设置面，"提醒不会响"这件事在应用里就**没有任何常驻提示**了。真正的修法不是在「常规」里保住这一节，而是让"提醒不响"在**提醒设置所在的一级**（本方案 G4）常驻一行红点。

### 3.4 分组命名逻辑不一致：四条轴混用

把三端 15 个组合位（去重后 **10 个不同组名**）按"它按什么轴命名"摊开：

| 轴 | 组名 | 依据 |
|---|---|---|
| **按对象**（"这是关于什么东西的"） | 个人资料、数据管理、账号与安全 / 账号安全 | 名词 |
| **按能力**（"这里是哪套技术"） | 同步与隐私、AI 与集成 | 技术模块名 |
| **按合规**（"这里有个法律要求"） | 隐私（并入同步组） | 法条 |
| **按商业**（"这里要钱"） | 订阅 | 商业 |
| **按"别的都不是"**（垃圾桶） | **常规**（移动）、**任务与显示**（Web） | 无 |
| **按功能**（"这里有个页面"） | 关于与帮助 | 内容 |

🔴 判据：**同一个用户在同一次滚动里遇到两种命名轴，就必须先猜"这个词是按什么分的"**。10 个组名里出现 5 种轴，用户每次进设置都要重建一次心智模型。这是"找不到东西"的第一成因，比组数多少更严重。

对照 [`ux-principles.md`](../agents/ux-principles.md) §6「线数 = 组数 − 1」的意图：分隔线**只**在语义真的分组处画。现在的问题是**线画得对，组名的语义不对**——所以线在提示"这些是一类"，而组名在说另一类。

### 3.5 两个无意义的桶

**移动端「常规」**（`SettingsScreen.tsx:431`, `renderGeneral:624-711`）的内容：

| 内容 | 频率 | 类型 |
|---|---|---|
| 提醒送达（1–3 行系统授权状态） | 偶发 | 系统权限 |
| 小组件旅程（5 段说明 + 1 个隐私开关） | 首次配置 | 设备能力 |
| 语言（2 chips） | 偶发 | 显示偏好 |
| 反馈（打开邮件） | 一次性 | 支持 |
| 运营者与备案号（只读） | 只读 | 法务 |

⇒ **1 个组里 5 种东西、4 种频率、0 个共同点**。它存在的真实原因可以从 `:639-641` 读出来：那里先画了一句 `mobile.profile.footnote`（"凭据只保留在内存中…"），说明这段代码是**从「我的」页原样搬过来的残留**，不是按功能设计的。

**Web「任务与显示」**（`App.tsx:3327-3450`）：

内容 = 日期/倒计时显示 + 详情栏默认 + 语言 + 主题 + **功能模块开关（7 个）** + 提醒开关 + 小组件旅程 + 小组件推送。

⇒ 组名叫"任务与显示"，实际装了**功能模块（应用长什么样）+ 提醒（什么时候吵你）+ 小组件（桌面长什么样）**。这正是 `App.tsx:3428-3433` 注释自己承认的：

> 🔴 **功能模块放在设置页最前**：它决定的不是某一项配置，而是**这个应用长什么样**（关掉的模块从左侧导航消失）。放在最后会变成"翻到底才发现原来能关"。

**注释是对的，组名是错的**：它论证了"功能模块应该靠前"，但没论证"它应该和主题、语言、提醒挤在同一组"。

### 3.6 危险动作与日常开关同组同权重

移动端 `renderSecurity`（`SettingsScreen.tsx:713-768`）自上而下是：

1. `账号与安全`（普通行，`:715-723`）
2. `注销账号`（普通行，由 `securityActions` 传入，`:721`）— **不可逆**
3. `VaultSettingsSection`（`:724`）— 创建/解锁/轮换根密钥/撤销设备/显示恢复码，日常到高危全在里面
4. `清除本机凭据`（`:762-766`）— **`tone="ghost"`**，全组最弱强调

⇒ 三个问题：

- **不可逆动作（注销账号）与日常动作（账号与安全）同行同权重**，只有 `hint` 一句区分（`:935` `common.accountClosure.entryHint`）;
- **最危险的"把手机给别人之前的清空"反而是最弱的样式**（`tone="ghost"`）。`:753-761` 的注释解释了它为什么**不能灰掉**（冷启动后凭据为空，灰了就"想清也清不了"），但没解释为什么它要**最不显眼**；
- `overlay-feedback.md` §2 的危险四档（`undo` / `popconfirm` / `alert` / `typed-alert`）管的是**确认框**，不管**分组**。确认框分档正确 ≠ 分组正确。

Web 侧同形：`PasskeyPanel` / `PasswordPanel` / `SessionsPanel` / `CloseAccountPanel` 四个 `.ht-settings` 面板连续排（`App.tsx:3533-3549`），注销账号是最后一个块，与前三个**同族同名**。

### 3.7 商业化入口：两端各走一个极端

| 端 | 现状 | 问题 |
|---|---|---|
| 移动端 | 「我的」页给订阅**单开一个 `SectionHeader` + `Card`**，整组只有一行（`:1392-1406`） | 一个商业入口的视觉权重**高于**通知、安全、整理与记录——但它并不是高频动作。这读起来像广告牌占了导航位 |
| Web | 订阅是左栏并列的一节（`SETTINGS_NAV_ITEMS:271`） | 与"个人资料""数据管理"完全同权重，商业与功能混排 |

参考产品把商业**单独拎成一条主色横幅**放在账号卡下面，功能列表**另起一组**。它这么做的好处是：商业有独立位置、功能列表不被污染、而且横幅的视觉强度**由它的位置定义**，不需要占用列表权重。**这个"位置分开"的思路值得借，横幅这个形态不值得抄**（原因见 §4.3）。

### 3.8 三端分组不同构（15 项对照）

| 功能 | 移动端父级 | Web / 桌面父级 | 同构？ | 有理由吗 |
|---|---|---|---|---|
| 个人资料 | 个人资料 | 个人资料 | ✅ | — |
| 登录/切换账号 | 「我的」页账号卡下 | 头像菜单 + 账号与安全 | ⚠️ 半同构 | 容器不同（无菜单外壳），可接受 |
| 注销账号 | 账号安全 | 账号与安全 | ✅ | — |
| 会话/退出登录 | 设置→账号安全→**整屏** | 账号与安全→**面板** | ⚠️ 版面差异 | ✅ 有（`ux-principles.md` §9：版面可随容器走） |
| 订阅 | 订阅 | 订阅 | ✅ | — |
| 语言 | **常规** | **任务与显示** | ❌ | ❌ 无理由，纯历史 |
| 主题 | **无** | 任务与显示 | ❌ | ✅ 有（`App.tsx:346`：移动端 `useColorScheme()` 是唯一来源，跟随系统） |
| 提醒送达 | **常规** | 任务与显示 | ❌ | ❌ 无理由 |
| 桌面小组件 | **常规** | 任务与显示 | ❌ | ❌ 无理由 |
| 保险库 | **账号安全** | **同步与隐私** | ❌ | ❌ 无理由，且**语义分错**（见 §3.1 末行） |
| 功能模块开关 | **无** | 任务与显示 | ❌ | ✅ 有（`account-information-architecture.md` §4：移动端用固定二级目录，没有模块开关） |
| 通知中心 | 「我的」一行 | 头部铃铛（`features/inbox/InboxBell.tsx`） | ❌ | ✅ 有（容器不同：无 rail） |
| 回收站 | 设置→数据管理 | rail 工具 tab | ❌ | ❌ 无理由，且移动端多 2 层（§3.3） |
| 帮助/文档/更新/价格 | **无** | 关于与帮助 | ❌ | ⚠️ 有登记但值得重审（见 §3.9） |
| 隐私政策 / 服务条款 | **仅首启同意面板** | **仅首启同意面板** | ✅（两端一样） | ⚠️ 两端**都缺**常驻入口（见 §3.9） |

⇒ **15 项里 9 项不同构**，其中：**3 项有理由**（主题 / 功能模块 / 通知中心 —— 都是容器或平台能力差异，按 `ux-principles.md` §9 可以不同）；**5 项给不出任何理由**（语言 / 提醒送达 / 桌面小组件 / 保险库 / 回收站）；**1 项的理由已经失效**（关于与帮助 —— `account-information-architecture.md` §3 说「移动端尚无对应的真实内容」，而移动端「常规」里早就有反馈入口与备案号，见 §3.9）。

按 [`ux-principles.md`](../agents/ux-principles.md) §9：判断与字段解剖必须一致，**版面**可以不同。而"同一项设置挂在哪个父级下"**既不是判断也不是版面，它是信息架构**——它必须一致，否则用户换端要重新学一遍。

### 3.9 权威 IA 文档已经漂移，且法务入口两端都缺

`docs/reference/account-information-architecture.md` §3 第 41 行写着：

> 当前桌面设置是**七组**，移动端设置目录是**六组**。

实测：**web 8 组、移动端 7 组**（订阅是 2026-10-24 加进去的，`App.tsx:265-271` 与 `SettingsScreen.tsx:144-147` 各自留了注释，但那份 IA 文档没回写）。同一节还说

> 关于与帮助暂不进入移动目录，因为**移动端尚无对应的真实内容**；这是一项范围决策，不是遗留待办。

实测（`SettingsScreen.tsx:660-709`）：移动端「常规」里**已经有**反馈入口和运营者备案号——也就是说"关于"内容**存在**，只是被塞进了垃圾桶组。所以那句"尚无对应的真实内容"**已经不成立**。

还有一个更硬的问题：**隐私政策 / 服务条款在两端都只能在首启同意面板里打开一次**。

- 移动端：`PrivacyConsentSheet.tsx:208` 与 `LegalReconfirmSheet.tsx:143` 是唯二的 `Linking.openURL` 法务链接；

PIPL 第 15 条讲的是"便捷的撤回同意"（这条做对了），但"**可查阅**"是另一条独立义务。这不是 IA 审美问题，是合规缺口。

## 4. 对照参考产品

> ⚠️ 再次声明：本节只依据**文字描述**的结构，不含截图本体。

### 4.1 它的分组逻辑是什么

它自上而下是：

1. 账号卡（头像 + 昵称 + 等级/勋章 + 右侧箭头）——**一行**
2. 主色商业横幅（高级会员 → 立即升级）——**一条**
3. 独立分组：功能模块
4. 大分组（纯列表，每行 = 图标 + 名称 + 右箭头）：外观 / 日期与时间 / 声音、提醒与通知 / 桌面小部件 / AI 功能 / 更多设置
5. 独立分组：关联与导入
6. 独立分组：福利活动

**四种不同的容器在表达四种不同的"这件事有多重"：**

| 容器 | 装什么 | 传达 |
|---|---|---|
| **一行卡片** | 账号 | "你是谁"——**只值一行**，但永远在最上面 |
| **一条主色横幅** | 商业 | "这不是设置，这是提议"——用颜色和位置把它**从列表里移出去** |
| **一个大分组（纯列表）** | 偏好（外观/时间/声音/小部件/AI） | "这些都只是'调一下'，彼此同级" |
| **多个独立小分组** | 关联与导入 / 福利活动 | "这些是**别的业务**，不是设置" |

🔴 **关键判据：它按"用户想干什么"分组，不按"代码里谁实现了它"。** 证据是第 4 组那六行的名字——"外观""日期与时间""声音、提醒与通知""桌面小部件""AI 功能"——每一条都是**用户会在脑子里说出口的一句话**，没有一条是技术模块名（没有"通知服务""同步引擎""AI 提供商配置"）。

### 4.2 它为什么能这么分（我们不能直接搬的原因）

| 它的前提 | 我们有吗 | 结论 |
|---|---|---|
| 有等级/勋章体系（账号卡右侧） | ❌ 我们只有昵称/头像/邮箱（`account-information-architecture.md` §4 明确"不为徽章发明新的持久化事实"） | **不照抄**——账号卡只放身份，不放"等级"占位 |
| 有"福利活动"业务 | ❌ 我们没有运营活动域 | **不照抄**——不造一个空组 |
| 有"关联与导入"独立域（第三方账号绑定） | ⚠️ 我们只有 `TickTickImportPanel` + 导出/恢复 | **半照抄**——"导入导出"值得独立成一组（我们现在把它埋在"数据管理"里只有两行） |
| 商业是**订阅制会员**，横幅有明确 CTA | ✅ 我们有托管订阅（`SubscriptionPanel` / `RenewSection`），但**还没到能天天劝升级的阶段** | **借位置，不借形态**：给订阅一个独立位置，但**不做常驻横幅**。理由见下 |
| 桌面小部件是独立一行 | ✅ 我们有（`WidgetJourneyPanel` / `WidgetPushPanel` / 移动端小组件旅程） | **照抄这一点**：小组件值得自己一行，不该跟"提醒"和"语言"挤在一个桶里 |
| 声音是独立一行 | ❌ 我们没有"提醒声音"设置（只有系统授权状态） | **不照抄**——等真有声音设置再开一行 |

### 4.3 照抄 / 不照抄 清单

| 参考产品的做法 | 我们的裁决 | 理由 |
|---|---|---|
| ✅ **分组标题 = 用户意图，不 = 技术模块** | **照抄** | 这直接治 §3.4 的病 |
| ✅ **同类项合成一个大分组（纯列表）** | **照抄** | 治 §3.5 的垃圾桶 |
| ✅ **账号只在最上面、只占一行** | **照抄** | 移动端现在账号卡 + 登录按钮 + 设置行 + 5 段状态 = 6 块（§2.1 #1–#7） |
| ✅ **商业化单独一个位置，不与功能混排** | **借位置，不借形态** | 我们给订阅**独立一组**（见 §5.1 G2），但**不做主色横幅**：常驻横幅在每月只被看一次的东西上烧首屏像素，而且我们的订阅页里明确写了"这台实例没有配置收款通道"（`web.subscription.notice.*`），横幅会把一句可能在说"没有"的话做成广告 |
| ✅ **危险动作不放在日常列表里** | **照抄（但用组内分节，不用独立组）** | 参考产品的"更多设置"里看不出危险区；我们的做法是 G1 组内最后一节 + 分隔线（`ux-principles.md` §6） |
| ❌ **等级/勋章** | **不照抄** | 我们没有这套事实，造一个假的就是"发明新的持久化事实" |
| ❌ **福利活动组** | **不照抄** | 没有业务就不开组——空组比没有组更坏 |
| ❌ **"更多设置"这个兜底组** | **不照抄** | 它就是把垃圾桶换个名字。我们的对策是**把桶拆掉**（§3.5），不是给它改名 |
| ❌ **主色商业横幅** | **不照抄** | 见上 |

### 5.5 三端同构裁决

**同构的部分（必须一致）**：7 个组 key、组标题、每一项挂在哪个组、组内顺序。

**不同构但**有理由**的部分（各自说明）**：

| 差异 | 端 | 理由 | 依据 |
|---|---|---|---|
| 主题切换只在 web / 桌面 | 移动端无 | 移动端 `useColorScheme()` 是唯一来源，跟随系统是平台惯例 | `apps/mobile/src/App.tsx:346` |
| 详情栏默认只在 web / 桌面 | 移动端无 | 移动端没有详情栏（单列） | 容器差异 |
| 功能模块开关只在 web / 桌面 | 移动端无 | 移动端用固定二级目录承载功能域 | `account-information-architecture.md` §4 |
| 小组件推送（Web Push）只在 web | 移动端无 | 移动端有原生小组件（`widget-bridge`），通道不同 | 平台能力 |
| 通知中心：web = 铃铛，移动 = 「我的」一行 | 两端 | 移动端没有 rail 顶栏位置 | 容器差异 |
| **G7 的"价格页"**：web = 站内 `/pricing` 外链；移动 = 只显示档位 | 两端 | 移动端外链策略未定（`SubscriptionSection.tsx` 文件头登记：`check:legal-links` 按站内路径对账） | ⚠️ 这不是"理由充分"，是"已知缺口"——见 §8 |

**不同构且**没有理由**、本方案要求拉齐的部分**：

| 差异 | 现状 | 拉齐成 |
|---|---|---|
| 语言 | 移动「常规」/ web「任务与显示」 | 都是 **G5** |
| 提醒 | 移动「常规」/ web「任务与显示」 | 都是 **G4** |
| 小组件 | 移动「常规」/ web「任务与显示」 | 都是 **G4** |
| 保险库 | 移动「账号安全」/ web「同步与隐私」 | 都是 **G3** |
| 回收站 | 移动 设置→数据管理 / web rail 工具 tab | 都是 **G3**；但**移动端必须 1 次可达**（见下） |
| 关于/帮助 | 移动 = 塞在「常规」里的 2 行 / web = 独立一组 | 都是 **G7** |

**移动端 G5（外观与语言）会很薄，本方案接受。** 移动端没有主题、没有详情栏、没有日期显示方式，G5 只剩「语言」一项（未来可能加"一周从哪天开始""时间格式"）。这**不违反** §3.7 对订阅的批评：§3.7 批评的是「我的」页给了一个商业入口 **`SectionHeader` + `Card` 独占一块**的视觉权重；而 G5 在设置目录里只是**7 行中的 1 行**，权重与其他 6 组完全相同。**判据是权重，不是项数**——如果一个组在目录里多占一格就算罪，那 7 组本身就不成立。

**"回收站 1 次可达"怎么同时满足两端**：`回收站` 放进 **G3**（唯一归属），但在移动端**额外**允许一个上下文入口——任务列表页的溢出菜单（与"筛选""排序"同层），并在 G3 里保留同一行。**这是"唯一归属 + 允许上下文快捷"，不是"两个归属"**。区分标准：快捷入口不定义自己的文案与行为，只 `push` 同一个目的地。

### 5.6 分批迁移（顺序 + 每批验收判据）

> 原则：**先改"读起来"（组名 + 说明文字），再改"装着什么"（去向），最后才动「我的」页行数。** 因为前两批不动 `ProfileScreen`，与其他三条并行轨道不撞车。

| 批次 | 动什么 | 不碰什么 | 验收判据（每条都能判红） |

### 6.2 判据的整体脆弱度（要先承认的事实）

12 条移动端判据里 **8 条读源码字符串**（`readFileSync` + `toContain` / `toMatch`），只有 4 条读行为或纯逻辑。这意味着：

- **重构的代价被记在了错误的账上**：真正的风险是"用户找不到"，而红的却是"某个字符串不在某个区间里"；
- 但**不能**因此把它们全删——它们当中每一条都对应一个真实事故（`profile-settings-ia.spec.ts` 的 `:65` 三元断言对应"Android 返回键关不掉设置面"，`:96` 对应"未配置时显示一张假的状态卡"）。

**处理原则（写死在本方案里）**：

1. **先问这条判据的意图能不能用行为表达**。能，就换成行为断言（移动端没有 RN 组件测试栈，那就用**结构不变量**：类型值集合、testID 集合相等、穷尽 switch）。
2. **不能换的（比如"某段 JSX 只渲染一次"），把它变成可计算的**：例如 §3.2 那条，可以写一条静态判据"`syncStatus` 这个标识符在 `ProfileScreen.tsx` 里只能出现在 `syncStatus={syncStatus}` 这一种位置"——它能判红，且不依赖行号。
3. **顺序永远是：先改产品行为，再改判据的**表达方式**，最后才允许改判据的**强度**。** 任何一次"把 `'general'` 换成 `'notifications'` 就算绿"都算 §3 的错误做法。
4. **判据变严要写理由**（`--rebaseline "..."` 已经是这个形状，本方案沿用）。

### 6.3 与并行轨道撞车的风险

仓库里另外三条子 Agent 正在改代码。本方案的 B0/B1 只碰 `SettingsScreen.tsx` + 一份门禁脚本 + 词条表；B2 起才碰 `ProfileScreen.tsx`（那条轨道正在改的正是 `ProfileScreen`）。⇒ **B4 必须等另外两条轨道落地后再排期**，B0–B3 可以先行。
