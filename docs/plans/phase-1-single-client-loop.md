# P1 详细计划：单端闭环

> 状态：**规划中**
> 上级：[总路线图](roadmap.md) ｜ 依据：[复用方案](../research/reuse-plan.md)、[组件决策](../research/reusable-components.md)、[功能矩阵](../research/feature-matrix.md)

## 1. 目标

**Web 端把核心功能跑通，并且能同步。**

| | 内容 |
|---|---|
| **交付判据** | 任务 / 清单 / 四象限 / 习惯 / 番茄钟可用；两个浏览器配置文件之间能同步 |
| **成功标志** | 用户能在 A 上建一个任务，在 B 上看到它；断网改，恢复后自动合并 |
| **不追求** | 好看、桌面/移动端、第三方集成、性能优化 |

### 明确不做（留给 P2/P3）

- 桌面（Tauri/Electron）与移动（Capacitor）外壳
- 系统级通知、小组件、后台同步
- CalDAV / 日历订阅
- 看板、甘特、时间线
- 导入导出、多语言

## 2. P1 必须定下的架构决策

P0 定的是**不可逆层**（协议、实体、服务端）。P1 定的是**可替换层**，但其中两条会隐性地变成长期约束，需要显式决策：

| # | 决策 | 倾向 | 为什么现在必须定 |
|---|---|---|---|
| D1 | UI 框架 | **React 19 + Vite** | 定了就很难换；组件生态与后续 Tauri/Capacitor 共享都依赖它 |
| D2 | 状态管理 | **Zustand** | 与 op-log 的接线方式决定了整个数据流形状 |
| D3 | 本地存储 | **IndexedDB**（实现 `packages/storage` 已定义的接口） | 接口已定，P1 只是落实现 |
| D4 | **op-log 与状态层的边界** | **op-log 是唯一写入口**，UI 不直接改状态 | 🔴 **这条最重要**。定错会导致 SP 那 5 万行踩过的坑重演 |

> D4 展开：SP 的教训是"一个用户意图 = 一个 op"，且被回放的 op **不得再触发副作用**。
> 如果允许 UI 直接改状态然后补记一个 op，就必然出现"本地生效了但没同步"或"同步回来又触发一次"的双向 bug。
> P1 必须从一开始就把 UI → op → apply → 状态 这条链做成**单向**的。

## 3. 任务分解（按依赖顺序，不是按功能）

顺序不是随意的：**每一阶段都能独立验证，且后一阶段不返工前一阶段。**

### 3.0 领域层（无框架依赖）

| 任务 | 产出 | 判据 |
|---|---|---|
| 领域模型定义 | `Task` / `Project` / `Tag` / `Habit` / `HabitLog` / `FocusSession` 的类型与不变量 | 与 `@heyta/shared-schema` 的 13 实体对齐 |
| 纯业务逻辑 | 四象限归类规则、重复规则求值、习惯连续天数、番茄钟状态机 | 单测覆盖，**不 import 任何框架** |
| 重复规则 | 基于 `ical.js` 的 RRULE 求值（`rrule.js` 已被可维护性门槛排除） | 覆盖"每周几/每月第几个周几/结束条件" |

> **为什么先做这个**：它是纯函数，最容易测，且 op-log 的 apply 逻辑完全建立在它之上。
> 这一层有任何框架耦合，后面都会被放大。

### 3.1 存储层落地

| 任务 | 产出 | 判据 |
|---|---|---|
| IndexedDB `DbAdapter` 实现 | 落实 `packages/storage` 的 `DbAdapter` / `DbTx` 接口 | 合约测试（同一套测试跑内存实现与 IndexedDB 实现） |
| IndexedDB `OpLogStore` 实现 | 落实 `OpLogStore` 接口 | 同上 |
| 破产/配额处理 | 存储写满、浏览器清数据后的恢复路径 | 有明确错误码，不静默丢数据 |

> `packages/storage` 在 P0 已定义好接口与内存实现（15 个测试）。
> P1 要做的是**同一套合约测试换一个后端** —— 这正是当初抽接口的目的。

### 3.2 op-log 编排引擎 🔴 **主要工作量**

这是整个 P1 最大的部分，也是复用调研里明确指出的"省不掉"的部分。

| 任务 | 说明 | 判据 |
|---|---|---|
| op 捕获 | 用户意图 → 一个 op（含实体、动作、载荷、向量时钟） | 一个意图恰好产生一个 op |
| op 应用（apply） | op → 状态变更，**幂等、可重放、无副作用** | 同一 op 应用两次结果相同；重放不触发新 op |
| 向量时钟 | 复用 `@heyta/sync-core`；`MAX_VECTOR_CLOCK_SIZE = 20` 的裁剪语义 | 与 `verify:sync` 的冲突用例一致 |
| 冲突解决 | LWW + `clientId` 确定性打破平局 | 与 SP 语义一致，有单测 |
| 崩溃恢复 | 写到一半崩溃后的状态机 | 有明确的不变量与恢复测试 |
| 墓碑与回收站 | 软删除 + 恢复（功能矩阵标为 P1 必备） | 删除可同步、可恢复 |

> **参考资料**：上游 `src/app/op-log/`（166 文件 / 51,708 行）是**可读的参考答案**，
> 它记录了真实踩过的坑（崩溃恢复状态机、墓碑、向量时钟裁剪、并发边界）。
> **移植语义，不拷贝代码** —— 它绑定 Angular + NgRx，无法直接搬。

### 3.3 同步客户端

| 任务 | 说明 | 判据 |
|---|---|---|
| 认证 | 登录 / 注册 / token 刷新 | 对接已有服务端接口 ✅ |
| 上传 | 加密后的 op 批量上传 | 满足服务端 E2EE 门禁 ✅（逐条检查 `accepted`） |
| 下载 | 增量拉取（`serverSeq` 游标） | 断点续传正确 ✅（游标用 `latestSeq`，不是最后一条的 `serverSeq`） |
| 同步状态 | 界面能看出"已同步 / 同步中 / 冲突 / 离线" | 用户可感知 ✅（`SyncBar`，图标+文字，不只靠颜色） |
| 离线队列 | 断网时排队，恢复后重放 | 断网→联网→数据一致 ✅（`uploadStatus` 索引，非内存列表） |

> ⚠️ **实测发现必须落到实现里**（见 [runbook](../runbooks/local-server-verification.md)）：
> 1. 服务端**强制 E2EE 且无开关**，明文上传一律 400
> 2. 线协议 schema **不校验实体成员**，客户端必须先用 `isEntityType()` 自查，否则要到上传后才发现拼错
>
> **3.3 实现时又实测出四条，全部只在真实服务端上暴露 —— 单元测试的 mock 全绿**：
>
> | # | 事实 | 只信 mock 的后果 |
> |---|---|---|
> | 3 | `opType` 词表是 **`CRT`/`UPD`/`DEL`**，不是 `CREATE`/`UPDATE`/`DELETE` | 服务端逐条 `INVALID_OP_TYPE` 拒绝**每一个** op |
> | 4 | 上传结果字段是 **`opId` + `accepted`**（不是 `id`/`status`），且 HTTP **200 也可能是拒绝** | 客户端报"已同步"，而服务端一条都没收 —— 最坏的一类 |
> | 5 | 下载的 op 是**嵌套**的 `{serverSeq, op, receivedAt}`，不是扁平结构 | `op.id` 恒为 undefined，数据"静静地没进来" |
> | 6 | 向量时钟**必须包含本次写入自己的递增** | 每台设备的**第一条 op** 时钟为空 → 对端判 `EQUAL`（"已见过"）→ 静默丢弃；本地正常、服务端收到、对端永远看不到 |
>
> 第 3、6 条的根因是同一个：**两套并行词表 / 两套时钟语义**。
> 词表只有一份（`sync-core` 的 `OpType`），时钟语义只有一种（写后即含本次）。
>
> **结论：mock 是按实现者对协议的理解写的。理解错了，mock 跟着错，测试照样全绿。**
> 所以必须有 `pnpm verify:p1` —— 真引擎 → 真 IndexedDB → 真 HTTP → 真服务端，零 mock。

### 3.5 P1 验收

| 场景 | 判据 |
|---|---|
| 双端同步 | 浏览器配置文件 A 建任务 → B 可见 |
| 离线合并 | A 断网改 + B 在线改 → 恢复后无数据丢失，冲突可判定 |

## 4. 依赖顺序（关键路径）

```
3.0 领域层 ──┬─→ 3.2 op-log ──→ 3.3 同步客户端 ──→ 3.5 验收
             │        ↑
3.1 存储层 ──┴────────┘
                             3.4 UI ──→ 3.5 验收
```

- **3.0 与 3.1 可并行**（互不依赖）。
- **3.4 UI 可以与 3.2/3.3 并行**：UI 只依赖领域层类型 + op 派发接口，不依赖 op-log 内部实现。
  这正是 D4（op-log 是唯一写入口）带来的好处 —— 接口一旦定死，两边可以同时推进。
- **关键路径是 3.0 → 3.2 → 3.3**。UI 不在关键路径上，别让 UI 的进度反过来逼迫 op-log 的接口。

## 5. 风险

| 风险 | 影响 | 对策 |
|---|---|---|
| **op-log 被低估** | 🔴 最高。它是 P1 的绝大部分工作量，且错了会静默损坏用户数据 | 先做 3.0 领域层让 apply 逻辑可测；把 SP 的 op-log 当规格书逐条对照 |
| UI 先跑起来、op-log 被绕开 | 🔴 高。会永久破坏 D4 的单向数据流 | 外壳阶段就先接一个"假 op-log"，强制所有写操作走 op 通道 |
| 习惯模块语义不清 | 🟡 中。SP 的习惯是 SimpleCounter（无目标/单位），语义不同 | 先把 `HABIT` / `HABIT_LOG` 的语义定死再写 UI |
| 四象限"自动归类"体验 | 🟡 中。实现不难，难在归类规则让用户满意 | 先做手动拖拽 + 一个简单默认规则，把自动规则留到经验反馈 |
| IndexedDB 被浏览器清数据 | 🟡 中。本地优先架构下的真实丢数据路径 | 3.1 必须有明确的错误码与恢复提示，不静默失败 |
| 重复规则（RRULE）边界 | 🟡 中。每月第几个周几、完成后顺延是经典难点 | 用 `ical.js`（已核实有完整 `Recur`/`RecurIterator`），写足边界测试 |
