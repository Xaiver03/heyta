## 0. 诊断：缺的不是功能，是**回路**

把现有能力放进 Hook 模型（[证据 §1.2](../research/motivation-psychology.md)）里对照，问题一眼可见：

| Hook 四步 | heyta 现在 | 直接后果 |
|---|---|---|
| **触发 Prompt** | **没有**。没有时机判断、没有通知策略、没有"现在该做什么"的入口 | 用户想起来才打开（B=MAP 里 P 缺失） |
| **行动 Action** | **最完整**。四象限、习惯打卡、番茄钟都能跑 | 门槛已经不是瓶颈 |
| **奖励 Reward** | **缺失**。勾完任务界面无任何回应；专注结束后只有一条记录 | 做完一件事的 3 秒里，产品什么都没说 |
| **投入 Investment** | **不成立**。用户投入的打卡/专注数据只是一份留档，读不回来 | 三个月后，产品只还他一张热力图 |

**一句话诊断：现在的 heyta 是一个「记账本」，不是一个「成长记录」。**
记账本给人的是安全感（数据没丢、多端一致），成长记录给人的才是成就感（我真的在变成另一个人）。
两者**数据完全同源**，差的是渲染方式与反馈设计。

> 这也解释了为什么"用户旅程看起来就是个同步"——同步是**记账本的核心竞争力**，
> 但它不是用户留下来的理由。同步做好了用户会"放心"，不会"想回来"。

## 1. 设计原则（每条都可追溯到证据）

| # | 原则 | 依据 |
|---|---|---|
| **P1** | 先补**提示**与**完成反馈**，再谈奖励体系 | Fogg B=MAP：缺 P 时加 M 无效 |
| **P2** | **中断不等于归零** —— 屏幕上永远至少有一个只增不减的数字 | abstinence violation effect；"绝不错过两次" |
| **P3** | **不发行货币**。不把打卡、专注、连续天数兑换成任何可积累的通货 | 过度理由效应；Deci 1999 元分析（d=−0.40/−0.36/−0.28） |
| **P4** | 进步必须**可见**，且越接近终点显得越快 | 目标梯度效应；禀赋进度 |
| **P5** | **只与自己比**。唯一允许的对外形态是用户自愿导出的分享物 | 排行榜证据（激励 vs 威胁两极）；feature-matrix §11 |
| **P6** | **全部本地计算**，可导出、可关闭、可离线判定 | ADR-0005 / ADR-0006 / 项目原则 3、5 |
| **P7** | **不制造愧疚**。没有惩罚、没有红点堆积、没有"你害了别人" | Habitica 掉血 / 组队连坐 / Forest 枯树的教训 |

P2 和 P7 是本设计与 Duolingo / Habitica / Forest 的**分道扬镳处**，也是最容易被后来的实现者"顺手优化掉"的地方，所以放在最前面。

## 2. 架构：三层 × 四个循环

### 2.1 三层激励

| 层 | 时间尺度 | 满足的需求 | 核心机制 | 主要失败模式 |
|---|---|---|---|---|
| **L1 即时反馈** | 秒 | 胜任 | 完成动效、今日进度、一键闭环 | 动效过重变成打扰 |
| **L2 连续性** | 日 | 胜任 + 自主 | streak 三指标并存、冻结、续接、重新开始 | 断签悬崖；数字焦虑 |
| **L3 叙事** | 周 / 年 | 自主 + 归属 | 复盘信、里程碑地图、身份标签、年度视图、分享卡 | 变成刷分游戏 |

三层是**并列**关系，不是替代关系：L1 让人今天有感觉，L2 让人明天回来，L3 让人一年后觉得值。

### 2.2 四个循环（这是"用户旅程"的真正骨架）

现在的用户旅程只有「一次动作」这一个循环，而且没有闭环。需要补上另外三个：

```
一次（秒）   打开 → 看见"今天要推进什么" → 完成 → 立刻得到回应        ← L1
一天（日）   早上提示 → 打卡/专注 → 今日闭环 → 明天还有理由           ← L1+L2
一周（周）   周日晚上收到"这周你推进了什么" → 定下周方向               ← L3
一年（年）   年度视图 / 里程碑 / 身份回顾                              ← L3
```

**成就感只产生在闭环上。** heyta 现在有的是"动作"，缺的是三个闭环的收尾动作（收尾 = 产品主动说话）。

## 3. L1 即时反馈：让每一次完成都有回应

### 3.1 完成反馈（补齐 Hook 的第三步）

- 勾选任务 / 完成打卡 / 专注结束时：**200–400ms 的确认动效 + 一次轻微音效**。
- 强度纪律：能被关掉；尊重 `prefers-reduced-motion`（设计系统已有 token 层，走 token 不走裸值）。
- **不做**：全屏撒花、强制弹窗、需要点击"确定"才能继续的庆祝。庆祝打断流程就是负反馈。

### 3.2 今日进度条常驻

- 顶部常驻一条「今日 N/M」，M = 今天该做的（到期任务 + 今天排期的习惯 + 用户自设目标）。
- 默认 **M ≈ 3–5**（宁少不多）。用户可调，但**不要默认把全部待办塞进去** ——
  一个永远填不满的进度条会变成压力源，而不是目标梯度。

### 3.3 今日闭环

完成全部今日项 → 进入"今日完成"态：一句具体的结束语（"今天推进了 4 件事，专注 65 分钟"），
而不是一枚徽章。**信息 > 徽章**（小胜原则）。

### 3.4 禀赋进度：新习惯的"启动期"（与竞品的有意差异）

Nunes & Drèze 证明"预先赠送 2 格"能显著提升完成率。但 heyta 不能在用户数据里**伪造**打卡记录。

**本设计的选择**：新习惯的前 7 天标为**「启动期」**，与长 streak 分开计算，界面明确写"启动期：第 3/7 天"，
期间中断不产生任何"归零"观感。7 天后转入正式 streak。

- 得到禀赋进度的效果（一开始就有进度可看、有明确的短终点）；
- 不撒谎：所有数字都对应真实行为；
- 附带好处：新习惯最容易在第 3–5 天死掉，启动期正好覆盖这段。

> ⚠️ 这是本设计与所有竞品不同的地方，**不要**为了"效果更好"改成伪造打卡。

### 3.5 能力门槛（Fogg 的 A）

一键打卡已具备；需要补的是**撤销的显眼度**（误触成本高会让用户不敢点）与**批量补打卡**入口。

## 4. L2 连续性：streak 不能是一块会碎的玻璃

### 4.1 现状盘点（已经做对的）

[`packages/domain/src/habit-streak.ts`](../../packages/domain/src/habit-streak.ts) 已经处理了三件最容易错的事：
今天没打不断链、非每日习惯按频率判定、补打卡有上限。**这套逻辑是资产，不要重写**，
本设计只在它之上加"韧性"和"多指标"。

### 4.2 核心设计：三个数并存

| 指标 | 会不会减少 | 作用 | 现有能力 |
|---|---|---|---|
| **当前连续** `current` | 会断 | 主动力（损失厌恶） | ✅ 已有 |
| **最长连续** `longest` | **只增** | 断签时的缓冲垫："你没有失去它" | ✅ 已有但被埋没 |
| **累计** （总打卡次数 / 总专注分钟） | **只增** | 最终兜底，永远不会归零 | 🟡 可纯派生 |

**UI 规则（硬性）**：任何一个习惯/总览界面上，**必须同时可见至少一个只增不减的数字**。
断签之后用户看到的第一屏，`current` 不能是唯一的大字；如果只显示一个"0 天"，那就是在赶人走。

### 4.3 韧性四级梯度

| 级别 | 机制 | 规则 | 状态 |
|---|---|---|---|
| 0 | **宽限** | 今天还没打卡不算断（已有 `isStillAlive`） | ✅ 已有 |
| 1 | **冻结（Freeze）** | 提前装备，断签时自动消耗保住链条。每连续 7 天自动 +1，**上限 2 个** | 🆕 |
| 2 | **续接（Repair）** | 断签后 **24 小时内**补打卡即续接，**不需要任何代价** | 🆕 |
| 3 | **重新开始** | 断签 > 7 天：主动提供新的起点，`longest` 与累计**原样保留** | 🆕 |

**与竞品的两处刻意相反**：
- Duolingo 的 freeze 要买、repair 要用宝石（把损失厌恶直接变现）。heyta **不卖** ——
  因为把用户的焦虑当收入来源，与"数据主权 / 自托管 / 不为订阅费买单"的产品定位直接冲突。
- Apple/Habitica 的连续断了就"记录结束"。heyta 的 `longest` 只增不减，断签不销毁任何东西（P2）。

> 冻结上限为什么是 2：Duolingo 官方曾公布"允许同时装备 2 个"后 DAU +0.38%，是同类机制里少数
> 有公开数据的参数（[证据 §6](../research/competitor-incentive-teardown.md)）。上限存在的意义是
> 让冻结是"保险"而不是"免打卡通行证"。

### 4.4 "绝不错过两次"的显式实现

连续错过 **第 2 天**时，触发一次**温和**干预：

> "你上周做到了 5 天。今天只要 1 分钟就够。"

- 触达方式用系统本地通知 / 应用内卡片，**不用红点计数**；
- 一天最多一次，连发 3 天无响应即停止（不纠缠 = 自主，P7）；
- 干预文案必须包含**用户自己的历史事实**（上句里的"5 天"），这不是激励话术，是"看见进步"本身。

### 4.5 文案纪律（禁止清单）

| 禁止 | 原因 |
|---|---|
| "连续归零 / 你已失败 / 中断了" | 直接触发 abstinence violation effect |
| 红点数字堆积 | 制造愧疚性打开（P7） |
| "别人都完成了" | 社会比较（P5） |
| 虚假紧迫（"仅剩 2 小时"） | 与产品调性冲突 |

## 5. L3 叙事：把打卡变成"属于我的东西"

### 5.1 周复盘：一封关于"推进"的信（小胜原则）

每周日晚生成一张**本地生成**的复盘卡，内容按此顺序：

1. **推进了什么**：完成 N 件 / 打卡 N 次 / 专注 N 小时（选一个用户最活跃的维度做主标题）
2. **最专注的一天** + 最常推进的清单
3. **趋势**：与上周对比（"比上周多 2 件事"）
4. **下周一句话**（可选 AI，见 §9 的隐私边界）

**不做**：积分结算、排行榜名次、连续天数考核。复盘的对象是"工作本身"，不是"表现"。

### 5.2 里程碑地图（累计型成就）

Apple 的做法已证明**个性化激励可以完全在设备本地计算**（100/365/500/1000 次 Move 环、个性化月挑战），
这是 heyta 最有力的先例 —— 不需要服务端，不需要用户数据出境。

heyta 的里程碑采用**累计制**（不要求连续）：

| 类别 | 阈值示例 | 数据来源 |
|---|---|---|
| 累计打卡 | 10 / 50 / 200 / 500 / 1000 次 | `HabitLog` |
| 累计专注 | 10 / 50 / 200 / 1000 小时 | `FocusSession` |
| 完成事项 | 50 / 200 / 1000 / 5000 件 | 任务实体 |
| 使用天数 | 7 / 30 / 100 / 365 天 | 本地派生（Apple 先例） |

**必须只增不减**，且**不设惩罚项**（滴答清单的成就值有扣分项，打开即见掉分 → 用户会不敢打开，这是本设计明确否掉的部分）。

### 5.3 身份叙事（自主需求，最抗衰减的一层）

连续/累计达标后给的是**身份标签**，不是奖励：
"连续 60 天早起的人"、"累计专注 100 小时的人"。

- 标签由本地生成，**用户可编辑、可隐藏、可关闭整个功能**；
- 依据："从我在打卡 → 我是这样的人"是内在动机的锚点，也是唯一不依赖外部奖励的长期动力（P3）。

### 5.4 年度视图

现有热力图升级为年度视图（GitHub 贡献图式 / 滴答清单的年视图）。
这是"投入读得回来"的最直接证据，也是 L3 里性价比最高的一项 —— **纯派生，零 schema 改动**。

### 5.5 分享卡：唯一的对外形态

- 用户**自愿导出**一张图片（周/月/年度），可含累计数字与身份标签；
- 带来源标记（由本机生成，可自证来源设备，**不可证真**）→ 定位是**身份表达，不是竞技排名**；
- **不做**：服务端排行榜、联赛、段位晋级、自习室、"别人今天专注了 10 小时"。

> 用户问的"番茄Todo 也做了排行榜，但那只是个番茄钟"—— 是的，番茄Todo 的留存靠**社会比较 + 强制锁机**，
> 这两条 heyta 都不能抄（P5/P7）。可抄的是它的**累计目标**（"一万小时计划"）与**统计可视化**，
> 这两项都是纯本地的。

## 6. 明确不做（反需求 2.0）

| 机制 | 为什么不做 | 依据 |
|---|---|---|
| 排行榜 / 联赛 / 段位晋级 | 需要跨用户可信聚合；会激励一部分人、赶走最需要帮助的另一部分人 | [证据 §4.1](../research/motivation-psychology.md) |
| 自习室（看见他人时长） | 同上，且制造羞耻源 | 番茄Todo 教训 |
| 组队 Boss / 连坐惩罚 | 把"我想做"替换成"我不能害别人"，摧毁自主 | Habitica 教训 |
| 金币 / 积分经济、内购变现损失厌恶 | 过度理由效应，且与"不为订阅费买单"的定位冲突 | Deci 1999 元分析 |
| 掉血 / 死亡 / 枯树式惩罚 | 惩罚对低动机用户是退出按钮 | Habitica 教训 |
| 邀请类徽章 | 需要服务端用户图谱，结构性不可做 | ADR-0005/0006 |
| 无限补打卡 | 削弱连续性的意义（现有 `backfillDays` 上限保留） | 代码注释已说明 |
| 纯 DAU 作为北极星 | 本地工具不以"每天打开"为目标，会诱导愧疚式设计 | P7 |

## 7. 落地映射：**不改 schema**

这是本设计最重要的工程结论。逐项对照后：

| 机制 | 数据来源 | 是否需改 schema |
|---|---|---|
| 完成反馈动效 / 今日进度 | UI 层 + 现有实体 | ❌ 不需要 |
| streak 三指标并存 | `computeStreak` 已有 `current`/`longest`；累计纯派生 | ❌ 不需要 |
| 冻结余额 | 由 `HabitLog` + 本地偏好**派生**（应得 − 已用） | ⚠️ 见下 |
| 续接（24h 补打卡） | `HabitLog`（已有 `backfillDays` 语义） | ❌ 不需要 |
| 里程碑地图 | 纯派生（Apple 先例） | ❌ 不需要 |
| 周复盘 / 年度视图 | 纯派生（本地渲染） | ❌ 不需要 |
| 身份标签 | 纯派生 + 本地偏好存储 | ❌ 不需要 |
| 分享卡 | 本地渲染导出 | ❌ 不需要 |

⚠️ **唯一需要决策的是冻结余额**：它有一个"已消耗"状态需要持久化。
按 [ADR-0014](../adr/0014-memory-switch-and-corrections.md) 的教训（跨设备状态必须进 op-log，且新增实体类型会被
`applyOperation` 静默忽略），这里有两条路，**留给实现前拍板**：

1. **纯派生**（推荐）：冻结余额 = `f(连续记录, 已断签日期, 本地配置)`。
   由于断签日期可由 `HabitLog` 推导，"已用掉几个"也可以被推导出来 → **零 schema 改动、天然跨设备一致**。
2. 新增实体字段 → 需要 bump schema + 迁移 + op-log 处理，成本高得多。

**只要能用派生就不用新字段** —— 这与 `habit-streak.ts` 现有的自研思路一致。

## 8. 分期

| 期 | 内容 | 判据 |
|---|---|---|
| **P1.5 反馈补丁**（1 个迭代） | 完成动效、今日进度条、三指标 UI 规则、文案纪律 | 用户做完一件事后 3 秒内界面有回应 |
| **P2 韧性主线** | 冻结 / 续接 / 重新开始、里程碑地图、周复盘 | 断签后仍有只增不减的数字与看得见的资产 |
| **P3 叙事主线** | 身份标签、年度视图、分享卡 | 三年的数据能读回来 |

顺序理由：先修**回路断裂**（L1），再修**中断悬崖**（L2），最后做**长期叙事**（L3）。
反过来做（先做徽章系统）会得到一堆没人看的图标。

🔴 **实现过程中真的抓到一个设计错误，值得记在这里**：界面本来打算用

### 8.2 渲染这一层不是"最后拼一下"，它自己会暴露问题

领域层全绿、选择器全绿、类型全通过之后，`GrowthView` 仍然**一行都没被渲染过** ——
而那正是本仓库栽过多次的形状（"能力实现了、单测全绿、生产里零调用点"）。
补了一个**挂真 `<App />`、点真标签页、断言真文字**的渲染测试，它当场抓到三个问题：

| # | 问题 | 为什么会漏到这里才被发现 |
|---|---|---|
| 1 | `react-activity-calendar` 的**默认文案是英文**（`Oct`、`1 activities in 2025`、`Less/More`） | 界面文案门禁只扫**我们自己的源码**，看不见库生成的字符串 —— 只能靠真的看一眼。现在已用 `labels` 覆盖为中文，并加了"不许出现 `activities in` / `Less` / `More` / `Jan`"的断言 |
| 2 | 主题色传的是**裸 token 名**（`--ht-color-primary`），而库会用 `CSS.supports('color', c)` 校验 —— 裸名**不是颜色值** | 🔴 在真浏览器里这个库会**抛异常**，而没有错误边界 → **整个应用被打白**（实测 `<body>` 只剩 10 个字符）。必须传 `var(--ht-…)`（实测 `CSS.supports` 为 true，且 SVG `fill` 属性真的会解析它，得到 `rgb(37, 99, 235)`） |
| 3 | 该问题在**习惯页早就存在**（同一段代码），只是**建了第一条习惯之后热力图才渲染**，空态一直把它挡住 | "页面能打开"不等于"页面有数据时也能打开" |

修法上做了一件事：把这套主题色抽成 `apps/web/src/lib/heatmap-theme.ts`（主题色 + 文案），
习惯页与成长页共用 —— 两处逐字相同的配置，加一处共用的踩坑说明。

**测试环境本身也有两个缺口**（`apps/web/tests/setup.ts`）：jsdom 既没有
`CSS.supports`（CSSOM），也没有 `window.matchMedia`。两者都由**同一个库**在渲染时调用，
缺一个就炸在库内部、报错完全指不到我们的代码。补齐时按**真 Chromium 实测的行为**实现
（`var(--x)` 合法 / 裸 token 名非法），而不是一律放行 —— 一律放行会让"真的传了个非法颜色"静默通过。

> 一般规律：**jsdom 缺的东西，要么补齐，要么那个视图就永远没有渲染测试。**
> 补齐的成本是几十行；不补的代价是"这个页面从没被验证过"。

### 8.3 顺手修掉的两个既有缺陷

  现在提到唯一的 `VIEW_TABS`，标题按视图取；四象限页只在筛选真的落在象限上时才用更具体的象限名。

### 8.4 渲染测试反过来抓到了**我自己新写的组件**里的一个真 bug

`TodayProgressCard` 会打出「还有 **-1** 件没做」。

成因不是笔误，是**两个口径的差**：`total` 只数**计划内**的（今天该做的习惯 +
今天到期或逾期的任务），而 `done` **还包含计划外**完成的任务 ——
也就是"今天没有截止日期，但我顺手把它做了"，那是最常见的操作之一。
于是 `done > total`，`total − done` 是负数。实测原文：

    今天 2/1　还有 -1 件没做　今天的都做完了     ← 同一张卡片上自相矛盾

组件自己的文件头其实已经写了这个概念的**一半**（"没有计划、却有完成"那一段，
领域层算成 100%），但只覆盖了 `total === 0` 的情况，没覆盖 `done > total`。

**抓法值得记**：不是靠猜，而是把测试失败信息里的**整段界面文本**打印出来读了一遍
（`waitFor` 的超时消息带现场，见 `motivation-view.spec.tsx`）。
在那段文本里 `还有-1件没做` 就在 `今天的都做完了` 旁边。

修法是两个纯函数（`hintText` / `progressLabel`）用显式分支，**负数在结构上不可能出现** ——
而不是加一个 `Math.max(0, …)`：那会把"计划外也做完了"糊成"还有 0 件"，
把数字修对、把意思弄错。

修完补了断言，并且**先证明它能在旧代码上失败**（临时把旧写法放回去 → 立刻红）：

    expect(flat).not.toMatch(/-\d/u)      // 文案里绝不能出现负数
    expect(flat).toContain('计划内都做完了')

> 与 §8.2 是同一个教训的两面：**渲染层不只是"把已经对的东西画出来"，
> 它会自己产生事实**（这里是"两个口径相减"），而只有真的读一遍界面文本才看得见。
> 另外注意 `beforeEach` 里那个"顺手完成一个没有截止日期的任务"的动作 ——
> 它是**最普通**的用户行为，却正好是这条 bug 的触发条件。
> **测试夹具要尽量用普通的空状态和普通的操作，不要为了"干净"把边界都躲开。**

## 10. 开放问题（需要人拍板）

1. ~~冻结余额走**纯派生**还是新增 schema 字段？~~ → **已拍板：派生，且余额不上界面**，见 [ADR-0022](../adr/0022-resilience-state-stays-derived.md) 与 §11
2. 是否保留 `prefers-reduced-motion` 之外的"极简模式"（关闭所有动效与庆祝）？
   **建议：不加。** `prefers-reduced-motion` 已覆盖唯一有医学依据的场景（前庭功能障碍 / 晕动症），
   而且它是**系统级、零配置、被中央 token 处理**（`tokens.css` 把所有 `--ht-duration-*` 压到 1ms）。
   再加一个应用内开关 = 第二个真相来源，两者一定会漂移。
3. 本地埋点做不做？做的话开关粒度如何（沿用 ADR-0010 的逐功能授权）？
   **建议：只本地、不上报。** 上报要单独 ADR + 逐项授权，且与「本地优先 + E2EE」的定位冲突很大。
   本地埋点（"我这周开了几次成长页"）能回答产品问题，不上报也能自己看。
4. 分享卡是否要加签名 / 来源标记？加了就承认"可自证来源、不可证真"的定位。
   **建议：静态来源标记，不做加密签名。** 本地优先下签名只能证明"某客户端生成"，
   证不了"这个人真的做到了" —— 那是一次**过度承诺**：一旦上线，它会诱使别人把它当证据。
   标一句来源即可，诚实且不欠债。
5. "启动期 7 天"的阈值是否与 `HabitFrequency` 联动（每周一次的习惯 7 天可能只排 1 次）？
   **建议：要耦合，统一到「计划日」口径。** 每周一次的习惯在 7 个日历日里只排 1 次，
   日历日阈值对它是错的。
   ⚠️ 这条现在有**硬证据**支撑：§11 第 4 项那个错误就是"同一个概念两套单位"的现成样本 ——
   领域层已经有稳定的「计划日」口径（`isScheduledOn`），**复用它，不要再引入一套日历日阈值**。
6. 里程碑阈值是否需要用户可改（Apple 允许改 Move 目标）？
   **建议：不改。** 1/10/100 次是**刻度**，不是目标 —— 可改的刻度就不是刻度，
   跨用户也就失去了可比性（而"只与自己比"依赖刻度稳定）。
   真要个性化，走"**自定义里程碑**"（用户可以自己加一个刻度），而不是改我们定的刻度。

### 第 2–6 项的结论：**它们都不在落地路径上**

逐条对着代码核过（2026-09-26），按上面的建议走，**一行代码都不用改**：

| 项 | 建议 | 代码现状（实测） | 要改吗 |
|---|---|---|---|
| 2 极简模式 | 不加 | **没有**应用内动效开关；降级由 `tokens.css:541` 的 `@media (prefers-reduced-motion: reduce)` 统一完成 | ❌ |
| 3 本地埋点 | 只本地、不上报 | 激励与领域代码里 `fetch(` / `sendBeacon` / analytics / telemetry **一处都没有** | ❌ |
| 4 分享卡 | 静态标记、不签名 | `copy.ts` 生成的是**纯文本**（"复制到任何地方"）；无 `subtle` / `hmac` / 签名 | ❌ |
| 5 启动期 | 耦合「计划日」 | 该特性**整体未实现**（`startup` / `gracePeriod` / `newHabit` 全无匹配）——与本文档状态行的"未做"一致 | ❌ |
