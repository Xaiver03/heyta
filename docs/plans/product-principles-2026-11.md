## 0. 一句话总纲

> **80% 以上的用户是普通用户。界面保持简洁，重信息放文档中心；
> 产品决策优先参照滴答清单（被验证过的方式）；我们抄"他做了什么"，不抄"他长什么样"。**

## 1. 界面简洁三原则（写死，写 UI 之前先读）

| # | 原则 | 具体约束 | 判据（建议） |
|---|---|---|---|
| **J1** | **重的信息不进界面** | 长说明、原理性解释、协议细节、隐私机制说明 → **文档中心**。想知道的用户自己去查 | 新增说明文字时，先问"这是不是操作必需"；不是 → 进文档中心 |
| **J2** | **少用 tooltip / 问号图标** | 尽可能减少 `?`、tooltip、hover 说明的使用量。tooltip 是"界面写不下才用"的兜底，不是常规手段 | 现量基线见 §1.1（**2026-11-08 实测，口径逐条写明**）：真靶子是**重复与背景知识**，不是长度 |
| **J3** | **界面默认自解释** | 一个控件需要 tooltip 才能看懂，**优先改控件**（文案/位置/形态），而不是加说明 | 提 PR 加新 tooltip 时，必须同时说明"为什么不能改控件本身" |

> **定位**：这三条与 [`ux-principles.md`](../agents/ux-principles.md) 是**同一族**——
> 那份管"结构怎么摆"，这份管"信息放多少"。**放哪一层的问题归 [`entry-layers.md`](../agents/entry-layers.md)。**

### 1.1 J2 的现量（2026-11-08 实测，口径写在每一行里）

| 测什么 | 口径 | 读数 |
|---|---|---|
| `title=` 属性（原生 tooltip） | `grep -rn 'title="' apps/web/src --include=*.tsx`（排除 spec） | **0** —— 一条都没有 |
| `<Tooltip>` 组件 | 同范围搜组件名 | **0** —— 项目里没有这个东西 |
| 真正在用的说明气泡 | `SettingsInfoTip` 的调用点 | **76 处**，分布在 **21 个文件**（`AiSettings.tsx` 8 处最多） |
| 其中「可直接测量」的（`text` 是字面词条 key） | 36 条（另 40 条经中间变量传，本轮没join） | 长度分布：**>120 字符 0 条**；80–120 **1 条**；≤80 **35 条** |
| 最长那一条 | `web.ai.settings.supply.note`，zh-CN 字符数 | **102** |

**三条结论（它们改变了 J2 的做法）：**

1. **没有 `title=`、没有 Tooltip 组件** —— 说明"少用原生 tooltip"这条在 heyta 已经没有靶子。
   全部说明都走**自定义气泡**（`SettingsInfoTip`），那是 2026-10-24 产品负责人自己要求的形式
   （"不应该是个问号吗？就是应该是一个 tooltip"）。🔴 **所以 J2 与那次决定不冲突**：
   那次反对的是**三行长句常驻在面板上**，J2 反对的是**问号太多**，两件事。
2. **问题不是长度**：35/36 条 ≤80 字符，没有一条 >120。
   而**最长的那一条恰恰不能删** —— `web.ai.settings.supply.note` 讲的是"走托管时内容会在服务器上解开明文"，
   属 [`hard-constraints` §3.7.2](../agents/hard-constraints.md) **要求必须出现**的披露。
   ⇒ **"减少说明文字"不许以删披露为手段。**
3. ⇒ **真正的靶子是两件事**：① **重复**（同一条规则在多个面板各说一遍）；
   ② **背景知识**（请求者能自己查到、或第一次用过就再也不需要的解释）。
   每删一条都要过"这是不是『现在必须知道』"这一问，否则就是把可读性换成整洁。

### 1.2 已做的减法（2026-11-08，三条 + 三类靶子）

现量：说明气泡 JSX 调用点 **49 → 45**（口径 `grep -rho "<SettingsInfoTip"`）。

| 删掉 | 属于哪类 | 为什么它该走 |
|---|---|---|
| `HelpPanel` 的 `tip-about` | **重复** | 气泡的 `text` 与紧邻的**可见那一行是同一条词条** —— 同一句在同一位置渲染两遍 |
| `ProfileOverview` 的 `tip-profile-overview` | **复述界面** | 正文「查看你的身份、近期状态和成长进度。」= 把这一屏已经摆出来的再说一遍 |
| `DataSettingsPanel` 的 `tip-data-backup` | **复述分区功能** | 正文描述"备份/还原"，而同一屏紧接着就是导出/导入按钮，各自写着干什么 |

**三类靶子的判据（下一轮照这个过）**：

1. **重复** —— 同一句话在同一位置出现两遍（通常是 `label`/`text` 与可见文字撞车）。
2. **复述界面** —— 内容是把用户已经看到的控件再说一遍。
3. **复述分区功能** —— 说明的是"这块分区是干什么的"，而分区里的按钮已经自解释。

**第四类靶子（2026-11-08 新识别，与前三类处置不同）**：**在解释一个已经不存在的东西**。
例：`web.ai.assistant.hint` 写「只读档只查询不写入；执行档会自动完成低风险写入…」，
而 ADR-0082 的标题就是「内置助手**不设权限档**：删掉 `assistantTier`（只读 / 执行）」。
它不是"多余"，是**过期的事实陈述** —— 处置是**连同它描述的对象一起删**，
不是改写、也不是保留。判别方法：**这个控件现在还在不在**。

🔴 **不许删的一类**：`hard-constraints` §3.7.2 **要求必须出现**的披露
（例如"走托管时内容会在服务器上解开明文"）。这一条边界在 R15 那次撞过 ——
删它等于把真实取舍藏起来，比多一枚问号严重得多。

⚠️ **判据不在长短**：`迁移` 那枚气泡保留，因为写的是**步骤**（"先查看预览，再合并"），
用户要记住一个顺序。**要不要用户记住顺序**才是分界线，字数是噪音。

## 2. 产品决策参照滴答清单（参照，不是照抄）

| 规则 | 内容 |
|---|---|
| **R-A** | 产品方向的决策，**优先查滴答清单是怎么做的**。它被大量用户验证过，是活的参考实现 |

| **R-D** | **"153 个窗口不必对齐"** —— 那是它的实现粒度，不是用户旅程。粒度裁决维持 [PRD §3](ticktick-parity-prd-2026-11.md)：「按用户能叫出名字的一次操作」 |

### 2.1 活体取证流程（固定，按本节执行）

取证优先级：**已有静态取证（`/tmp/rea-lab` 638 份 XAML、菜单 55 项）→ 活体截图**。
静态读不到、或需要确认"用户真实看到什么"时，按下面流程走：

1. **确认在装**：`ls -d /Applications/TickTick.app`（本机 8.2.03，含 Widget 扩展）
2. **确认在跑**：`pgrep -lf TickTick`；没跑就 `open -a TickTick` 等 3 秒
3. **找窗口**（关键一步，`screencapture -l <窗口id>`，**不要**用 `screencapture -x` 全屏 —— 全屏截到的是最前面那个窗口，本机最前往往是微信）：

   ```bash
   cat > /tmp/winlist.swift <<'EOF'
   import CoreGraphics
   import Foundation
   let opts: CGWindowListOption = [.optionOnScreenOnly, .excludeDesktopElements]
   if let list = CGWindowListCopyWindowInfo(opts, kCGNullWindowID) as? [[String: Any]] {
     for w in list {
       let owner = w["kCGWindowOwnerName"] as? String ?? "?"
       if owner.contains("滴答") || owner.contains("TickTick") {
         print("\(w["kCGWindowNumber"] as? Int ?? -1) | \(owner)")
       }
     }
   }
   EOF
   swift /tmp/winlist.swift
   ```

4. **截图**：`screencapture -l <窗口id> -x /tmp/tick.png`（窗口级，不抢前台）
5. **窗口不在列表里** = 它运行但窗口关着。先 `open -a TickTick`，再不行 `open "ticktick://"` 兜底（URL scheme 能把主窗拉起来，本轮验证有效）
6. **入库**：证据存 `docs/research/evidence/ticktick-live-<日期>/`，命名 `<what>-<view>.png`，**每张图要有 sha256**
7. **纪律**：截图是**读**，不是写——不许用它登录、改设置、点按钮；每次取证记"看了哪几屏、得出什么"

| 13 档 | **第一大档**（macOS 40.9% / Win 28.3%），是它的**正文档** | `--ht-font-size-md` 在手写 CSS 里 **0** 次；**只在 `.ht-type-group-label`（分组标题）这一条语义类里出现，8 处消费** |
| 其余档 | — | `2xs`(11) 29 次 · `base`(16) **22** 次（偏少）· `lg`(18) 19 次 |
| 表达力 | 五档撑起"标题/正文/辅助/元数据/极小"五级 | **五档都在，但 13 只承担一个角色**（分组标题）；"次级正文/元数据行"这一级没有档位，只能借 12（偏小）或 14（偏大） |

**口径（三条，缺一条就会读错）**：
1. 「手写 CSS 次数」= `grep -rn "var(--ht-font-size-X)" --include=*.css apps packages` 排除 `dist/` 与 `generated/`；
2. 「语义类消费次数」= 搜 `.ht-type-*` 在 `*.tsx`/`*.ts` 里的出现次数（3 / 23 / 8 / 10 / 29 / 0 分别对应 screen-title / section-title / group-label / headline / row-title / body-caption）；
3. 两端读数**不可跨端比绝对值**：滴答 macOS 的 13 是 13pt、Windows 的 13 是 13 DIP = 9.75pt，同一数字物理差 25%。

**因此真正的缺口是**：不是"缺档位"（五档齐），也不是"没人用"（8 处在用），
而是 **13px 只有一个语义角色**，撑不起用户说的"信息轻重"。要补的是**角色**，不是新 token。

### 3.2 决策：**暂不做**。它被两条已有的量化规则挡住了（不是不想做）

我按"给 13px 补第二个角色（设置页说明句 14 → 13）"实施过一次，**被三道门禁逐条打回**，
已全部回退。这不是"遇到阻力"，是**仓库里早就写好的预算**在起作用 —— 记清楚，下一个人不用再试一遍：

| 撞上的规则 | 原文（门禁输出） | 说明 |
|---|---|---|
| `check:surface-budget` 单文件档位上限 | `/apps/web/src/styles/app/ai-panels.css 用了 6 档字号（单文件上限 5）` | 那个文件原本恰好 5 档（2xs/xs/sm/base/lg），加 md 就 6 |
| `check:surface-budget` 全局档位上限 | `apps/web 的样式表一共用了 7 档字号（上限 6）：2xs/base/lg/md/sm/xl/xs —— 加一档必须先删一档` | 全局 6 档已满 |
| `check:design` 禁止自拼排版 | `web 壳出现 1 处档位表外的成对自拼排版（字号+字重同写）：ai-panels.css:336 [md+medium] .ht-settings__subtitle` | 我用"合并相邻档"腾预算，结果生成了 11 个语义档之外的组合 |

**⇒ "加一个字号档"在这个仓库里不是一行 CSS，而是一次设计系统变更**，至少要同时做三件：
① 在 `TEXT_STYLES` 里新增语义档并让它**整条消费**（JSX 加 `.ht-type-*`），不能手拼字号+字重；
② 同时**删掉一个现有档**（规则原文："加一档必须先删一档"）—— 候选是 `xl`(20)，它全 web 只有 3 处，
且与 `lg`(18) 只差 2px，正是那条规则嫌的"相邻两档只差 1–2px"；
③ 逐屏看截图（`ui-acceptance` 的硬规定），因为这是视觉回归。

⚠️ **本轮没做的原因就写在这**：②③ 都超出"顺手接线"的范围，而①是 D 包（视觉）的活。
**"五档值得采用"这个方向没有被否掉** —— 被否掉的是"用一行 CSS 实现它"这个做法。

🔴 **并且要记住 13px 现在的真实状态**（§3.1）：它**不是"没用过"**，
它承担 `group-label`（分组标题，8 处）。所以更准确的说法不是"给 13px 一个角色"，
而是"13px 只有一个角色，要不要再加一个" —— 那是一个**设计判断**，不是接线工作。

## 4. 皮肤：最后做，不是不做

> 产品负责人原话："他的 54 个皮肤，我们弄到最后去做，不是不做，是放到最后去做。"

- **排期**：挪到 R13b 全部落地（字号/密度/行着色/图标）**之后**。皮肤依赖"主题系统能生成"这个前提 —— 现在做皮肤等于在手工枚举的 token 上叠 54 层
- **判据已定**（[业界基线](../research/industry-ux-baseline-2026-11.md) Linear 那条）：将来任何新主题/皮肤**只改 ≤3 个变量**（base + accent + contrast）就要能产出一套 —— 这是皮肤能"批量化"的前提，也是"最后做"的技术理由
- **明确不做**它的"61 调色板 / 167 字面色"那个**实现方式**（88% 死重），只做"多皮肤"这个能力

### 4.1 现有三个表面预设（蓝白 / 暖纸 / 雾青）在移动端**不存在** —— 这不是空头承诺，但要说清

2026-11-08 实测（口径：搜 `preset` 在 `packages/ui/src/theme.tsx`、`apps/mobile/src`）：

| 事实 | 读数 |
|---|---|
| 预设的落地形式 | **只有 CSS**：`tokens.css` 的 `[data-theme-preset='warm'\|'mist']` 块，由 web 的 `applyThemePreset()` 写到 `<html>` |
| `@heyta/ui` 的主题轴 | `scheme`（明暗）/ `reducedMotion` / `reducedTransparency` / `packagedFonts` —— **没有 preset 这一轴** |
| 移动端 | `apps/mobile/src/theme.tsx` 只是转发 `@heyta/ui` ⇒ 移动端拿到的是**基准表面色**，看不到暖纸/雾青 |

**为什么它不是"承诺没兑现"**：[ADR-0085](../adr/0085-appearance-is-device-local-and-never-an-op.md) 定的是
**外观是本机偏好、产出零 op**。外观选项**本来就按端各自决定**，web 有而 mobile 没有
不构成跨端承诺 —— 移动端有自己的设置面，它不需要长得和 web 一样。

**但如果要做移动端预设**，工作不是"抄一段 CSS"，而是给 `resolveHeytaUiTheme()` 加一条
**preset 轴**（token 表要能按 preset 取不同表面色，且要进 `check:theme` 的单源判据）。
🔴 这正是本轮**没有做**的那一件：它是一个真实的接线工作，不是顺手改 ——
而"顺手把 CSS 抄进 RN"会造出**第二份表面色表**，`check:theme` 会红，且两份一定漂。
