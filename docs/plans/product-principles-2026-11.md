## 0. 一句话总纲

> **80% 以上的用户是普通用户。界面保持简洁，重信息放文档中心；
> 产品决策优先参照滴答清单（被验证过的方式）；我们抄"他做了什么"，不抄"他长什么样"。**

## 1. 界面简洁三原则（写死，写 UI 之前先读）

| # | 原则 | 具体约束 | 判据（建议） |
|---|---|---|---|
| **J1** | **重的信息不进界面** | 长说明、原理性解释、协议细节、隐私机制说明 → **文档中心**。想知道的用户自己去查 | 新增说明文字时，先问"这是不是操作必需"；不是 → 进文档中心 |
| **J2** | **少用 tooltip / 问号图标** | 尽可能减少 `?`、tooltip、hover 说明的使用量。tooltip 是"界面写不下才用"的兜底，不是常规手段 | 现量基线：`HelpCircle/CircleHelp/Info` 图标 **95 处**、tooltip 相关文件 **17 个**。**只减不增**（同 `r14-entry-table` 的账本纪律） |
| **J3** | **界面默认自解释** | 一个控件需要 tooltip 才能看懂，**优先改控件**（文案/位置/形态），而不是加说明 | 提 PR 加新 tooltip 时，必须同时说明"为什么不能改控件本身" |

> **定位**：这三条与 [`ux-principles.md`](../agents/ux-principles.md) 是**同一族**——
> 那份管"结构怎么摆"，这份管"信息放多少"。**放哪一层的问题归 [`entry-layers.md`](../agents/entry-layers.md)。**

## 2. 产品决策参照滴答清单（参照，不是照抄）

| 规则 | 内容 |
|---|---|
| **R-A** | 产品方向的决策，**优先查滴答清单是怎么做的**。它被大量用户验证过，是活的参考实现 |
| **R-B** | **"不抄"指的是不抄它的表达**（文案、视觉、像素）；**"参考"指的是它实现的功能与用户旅程**。有前人实践 = 被验证的方式 |
| **R-C** | 它的功能，凡是**用户旅程有价值**的，我们都可以做 —— 但按 [逆向→PRD §3](reverse-learning-to-prd-2026-11.md) 的 A–F 六条判据过一遍，别把"它做了"当理由 |
| **R-D** | **"153 个窗口不必对齐"** —— 那是它的实现粒度，不是用户旅程。粒度裁决维持 [PRD §3](ticktick-parity-prd-2026-11.md)：「按用户能叫出名字的一次操作」 |

### 2.1 活体取证流程（固定，按本节执行）

取证优先级：**已有静态取证（`/tmp/rea-lab` 638 份 XAML、菜单 55 项）→ 活体截图**。
静态读不到、或需要确认"用户真实看到什么"时，按下面流程走：

1. **确认在装**：`ls -d /Applications/TickTick.app`（本机 8.2.03，含 Widget 扩展）
2. **确认在跑**：`pgrep -lf TickTick`；没跑就 `open -a TickTick` 等 3 秒
3. **找窗口**（关键一步，`screencapture -l <窗口id>`，**不要**用 `screencapture -x` 全屏 —— 全屏截到的是最前面那个窗口，本机最前往往是微信）：

   ```bash
   cat > /tmp/winlist.swift <<'EOF'
   import CoreGraphics
   import Foundation
   let opts: CGWindowListOption = [.optionOnScreenOnly, .excludeDesktopElements]
   if let list = CGWindowListCopyWindowInfo(opts, kCGNullWindowID) as? [[String: Any]] {
     for w in list {
       let owner = w["kCGWindowOwnerName"] as? String ?? "?"
       if owner.contains("滴答") || owner.contains("TickTick") {
         print("\(w["kCGWindowNumber"] as? Int ?? -1) | \(owner)")
       }
     }
   }
   EOF
   swift /tmp/winlist.swift
   ```

4. **截图**：`screencapture -l <窗口id> -x /tmp/tick.png`（窗口级，不抢前台）
5. **窗口不在列表里** = 它运行但窗口关着。先 `open -a TickTick`，再不行 `open "ticktick://"` 兜底（URL scheme 能把主窗拉起来，本轮验证有效）
6. **入库**：证据存 `docs/research/evidence/ticktick-live-<日期>/`，命名 `<what>-<view>.png`，**每张图要有 sha256**
7. **纪律**：截图是**读**，不是写——不许用它登录、改设置、点按钮；每次取证记"看了哪几屏、得出什么"

## 3. 表达力：字号档位采用滴答的五档

产品负责人原话：**"我们的三个字号太统一了，很难表达信息的轻重级别，需要学习它的档位划分。"**

### 3.1 现量（为什么这条成立）

| | 滴答（两端独立收敛） | heyta 现状 |
|---|---|---|
| 主力档 | **5 档 `11/12/13/14/16`**，占 88.8%（macOS）/ 88.0%（Windows） | 实际消费集中 `11/12/14` 三档（121/137 = 88.3%） |
| 13 档 | **第一大档**（macOS 40.9% / Win 28.3%） | `--ht-font-size-md: 13px` **已登记但 app CSS 消费 0 次**（对照 `xs` 132 次） |
| 表达力 | 五档撑起"标题/正文/辅助/元数据/极小"五级 | 三档承载五级 ⇒ **信息轻重压扁了** |

### 3.2 决策

**采用五档 `11/12/13/14/16` 作为主力档位。** 具体：

1. **不是加 token，是接线**：五档我们**全都有**（`2xs/xs/sm/md/base` = 11/12/14/13/16），缺的是 **`md`(13) 0 消费**。第一步是给 `md` 找到它的角色（滴答的 13 是正文档，我们的 `base` 16 是）——**排印层级表先重排，再谈加档**
2. **不抄它的物理值**：它的 mac 13 = 13pt，Win 13 = 9.75pt，**同一个"13"物理差 25%**。我们抄的是**"五档承载五级"**这个形状
3. **落点**：[`MASTER.md`](../../design-system/heyta/MASTER.md) §13 语义文字样式 + `typography.ts`，由 D 包（视觉）执行
4. **20/24/30/36 四个大档不删**（它们是 display 档，与正文五档不同层）；**但若 0 消费，按 S1 门禁处理**（见 [逆向→PRD §5](reverse-learning-to-prd-2026-11.md)）

## 4. 皮肤：最后做，不是不做

> 产品负责人原话："他的 54 个皮肤，我们弄到最后去做，不是不做，是放到最后去做。"

- **排期**：挪到 R13b 全部落地（字号/密度/行着色/图标）**之后**。皮肤依赖"主题系统能生成"这个前提 —— 现在做皮肤等于在手工枚举的 token 上叠 54 层
- **判据已定**（[业界基线](../research/industry-ux-baseline-2026-11.md) Linear 那条）：将来任何新主题/皮肤**只改 ≤3 个变量**（base + accent + contrast）就要能产出一套 —— 这是皮肤能"批量化"的前提，也是"最后做"的技术理由
- **明确不做**它的"61 调色板 / 167 字面色"那个**实现方式**（88% 死重），只做"多皮肤"这个能力
