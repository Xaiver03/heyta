## 2. R1 · 勾选框"缺了一半"

### 症状

产品负责人两次指同一样东西：任务行最左边那个圈，看着像被切掉一半。
四象限格子里的三行（`B-mac-*`）与时间线里的三行**都有**——所以它是**行骨架**的问题，
不是某一屏的问题。行骨架只有一份：`packages/ui/src/task-list/TaskRow.tsx`。

### 已读到的代码事实

```
TaskRow.tsx:165  checkboxHit: { marginLeft: -(touch-target.min - size.checkbox) / 2 }
TaskRow.tsx:169  box: { width/height: size.checkbox, borderRadius, borderWidth }
tokens.css:303   --ht-touch-target-min: 2.75rem  /* 44px */
tokens.css:413   --ht-size-checkbox:  1.375rem   /* 22px */
```

⇒ 负外边距是 **-(44-22)/2 = -11px**，而勾选框视觉宽度是 **22px**。
也就是说：只要它左边被切掉 11px，就**恰好只剩一半**。这与看到的现象数量级吻合。

### 但这里有两个问题，第二个更要紧

1. **被裁**：负外边距让 22px 的圈探进行左边的留白里。留白够（≥11px）就没事，
   一旦祖先容器有 `overflow: hidden`（卡片圆角几乎必然带）或留白不足，就切在圈中间。
2. 🔴 **那条注释说的"44 的触控区"根本没实现**：`checkboxHit` 只有 `marginLeft`，
   **没有 `width/height: 44`**，所以它的命中区就是那个 22px 的圈。
   注释写着"这一项不随密度变：按容器缩触控区是回归"——而被缩的是**视觉圈**，
   触控区从来就没到过 44。**一条注释在描述一件没发生的事。**

### 待验证的假设（不许跳过这一步）

- **H1 被祖先裁**：需要实测 `task-toggle-*` 的 `getBoundingClientRect()` 与它每个祖先的
  `overflow` + 自身 rect。若圈 rect 的 `left` 小于祖先可视区 `left`，H1 成立。
- **H2 被横向压扁**（RNW 特有）：RNW 的 View 默认 `flex-shrink: 1`，行是 `flexDirection: 'row'`，
  标题长时**可能把 22px 的圈挤成 6px** —— 那看起来正是"缺了一半"。
  判据：实测 rect 的 `width` 是否 < 22。**H1 与 H2 的修法完全不同**（前者改留白/裁剪，
  后者加 `flexShrink: 0`），所以必须先分清再动手。

### 调研入口

- RNW 对 `View` 的默认 `flex-shrink`（react-native-web 源码 `packages/react-native-web/packages/react-native-web/src/exports/View/index.js`）；
- 仓库内既有先例：`check:row-single-source` 门禁（`TaskGroupHead.tsx:10` 提到它挡住过净增的行容器）；
- 同类"命中区与视觉尺寸分离"的既有正确写法：`tokens.css:313` 的注释（图标按钮保持 44 方形命中区）。

### 判据（怎么算修好）

1. 真浏览器（桌面载荷）实测：`task-toggle-*` 的 rect **宽高都等于 `size.checkbox`**，
   且 `left` 不小于其最近裁剪祖先的可视 `left`；
2. 命中区实测 ≥ 44×44（这条现在为假，修完必须为真）；
3. 截图：四象限格内 + 时间线各一张，**人打开看过**（§6.2 规定一），浅色与暗色各一；
4. 一条能失败的判据：把 `flexShrink`/负边距改回旧值 ⇒ 该判据转红（变异验证）。

## 3. R2 · 组件没有铺满高和宽

### 症状

产品负责人原话：**"各个页面内的组件应该是几乎全面铺满高和宽的，为什么这个根本没有铺满？
那这个四象限这个组件就没有铺满。"** 截图上：2×2 只占上部约六成，下面整片是底色。

### 已读到的代码事实

- 共享层 `packages/ui/src/quadrant/QuadrantBoard.tsx:208` 每一格是 `flex: 1` +
  `minHeight: layout.quadrant-min-height`；
- 但 `board`（:192）只有 `gap` 与 `padding`，**没有 `flex: 1`，也没有 `height`**；
- 宿主侧 `apps/web/src/App.tsx:2242` 是 `{contentView === 'quadrant' && <QuadrantBoard />}`
  —— 直接挂在内容列上；
- `HeytaUiProvider`（`packages/ui/src/theme.tsx:230`）**只给 context、不产生 DOM 层**，
  所以"中间多了一层没接上"这个嫌疑**已被排除**（这是一次有用的排除：它把范围收窄到两处）。

⇒ 结论方向：**格子的 `flex: 1` 是空转的**，因为它要长的容器（board）自己高度是内容决定的。
`minHeight` 于是成了唯一有效的高度来源 —— 界面就停在"四张最小高的卡 + 一大片空白"。

### 待验证（两处，实测后才能定改哪一层）

1. 内容列（`.ht-main` 那一层）到底是 `overflow: auto` 的滚动容器，还是 `flex: 1` 的列？
   滚动容器里 `flex: 1` 拿不到确定高度，这是两回事；
2. 如果是滚动容器，"铺满"应当怎么表达（`min-height: 100%` 还是让宿主给 board 一个 `flex: 1` 的插槽）。

⚠️ **不许顺手把 `height: 100vh` 写进共享层**：那一层同时服务移动端（RN，没有 vh）与
窄窗单列（四格竖排时铺满意味着要滚），写死 vh 会在手机上把第四格推到屏幕外。
断点与降级路径必须一起想 —— 这正是 [`goal-layout-audit.md`](goal-layout-audit.md) 页 1 立的规矩。

### 判据

1. 视口高 800 / 1000 / 1200 三档下，四象限 board 的 rect 高度 ≥ 内容列可视高度的 90%
   （留页脚注的空间），**且**四格高度相等；
2. 窄窗（< `layout.two-column-min`）单列时：不裁切、可滚动、每格不低于 `min-height`；
3. 移动端同一份共享层截图（Android 模拟器）：单列不溢出；
4. 一条 e2e 判据能因"把 `flex: 1` 拿掉"而转红。

产品负责人原话：**"各种应用内的文字，能不能都用中文？先默认用中文好不好？
把我们的测试数据全都改成中文的，什么 B-Mac Shot，不要用这个东西。"**

### 已查清的事实（这条不用调研，出处是确定的）

`B-mac-shell-storage-1790761707` / `B-mac-shot-1790762056` / `B-mac-final-1790763473`
**不是仓库里的 fixture**，全仓 grep 只命中四处记录文本：
`PROGRESS.md`、`docs/reference/environment-traps.md`、`BLOCKED.md`、
`apps/desktop-macos/evidence/storage-host/`。
⇒ 它们是**macOS 存储宿主取证时写进真实库的残留数据**，名字是脚本按
`B-mac-<用途>-<epoch>` 拼的 ASCII 串，所以界面上看着刺眼。

### 这一条要分三个问题，别混

1. **默认语言**：界面词条本身已经是中文（截图上除了任务标题全是中文）。要核的是
   **默认值链路**：`?lang=` / `Accept-Language` / 存储的偏好，哪一环会在中文环境下
   落到英文。（服务端凭据页那一条已经定过：默认 `zh-CN`，见 AGENTS §9 的 2026-09-30 那轮。）
2. **残留数据**：取证脚本写进真库的 ASCII 任务，要么**跑完自己清掉**，要么用中文命名。
   🔴 优先"跑完清掉"——留着才是问题本体；改中文名只是让它不那么刺眼。
   这一条与 [`BLOCKED.md`](../../BLOCKED.md) 里"探针会改变被测对象状态"（§7 第 83 条）
   是同一类问题：**探针留下的状态，就是下一次看图的输入**。
3. **界面里的英文残留**：需要一次逐屏扫（截图上有 `English` 切换、任务标题是数据不是 UI）。
   `check:ui-language` 只保证"没有硬编码文案"，**不保证默认语言是中文**。

### 判据

1. 全新 profile（清 IndexedDB/LocalStorage）打开应用：界面**没有一个英文句子**；
2. 取证脚本跑完后库里**残留为 0**（脚本自己收尾），或残留条目名是中文；
3. 现有三条 `B-mac-*` 残留有明确处置（清掉或改名），并留下处置记录。

## 5. R4 · 时间线 UI：全是文字，没有"线"

### 症状

产品负责人原话：**"这个时间线的 UI 很离谱啊，怎么可能都是文字？时间线是线呢？
你搜索一下别人是怎么做这个 UI 的好不好？"**

截图上的实际形状：每条任务是一坨文字（标题 + 说明 + 一行统计 + 一行刻度 `0:00 / 0:30 / 1:00`
+ 一行时间区间 + 一个空框）。**三条任务就是三坨，彼此没有任何时间关系**。
刻度只有一条任务的宽度，所以它不是时间轴，是把 `0:00 0:30 1:00` 当装饰重复了三遍。

### 已读到的代码事实

共享层有 `packages/ui/src/timeline/GanttChart.tsx`（文件里就有 `overflow: 'hidden'`），
⇒ **"线"这一层的件是存在的**，但界面渲染出来的东西没有线。
所以第一个要回答的问题不是"怎么画"，而是 **"GanttChart 有没有被挂上，还是挂着但算出了空数据"**。
这一条必须先查清，否则会在"重画一个"和"接上现有的"之间选错。

### 调研（动手前必须做完，产出写回本节）

1. **别人怎么做**：滴答清单的时间线/日程视图、Todoist 的 agenda、Notion timeline、
   Linear 的 roadmap、以及甘特图的通行要素（时间轴刻度、跨任务的公共时间基线、
   今天线、按天分组的泳道）。要拿到的是**要素清单**，不是截图堆砌；
2. **我们的数据支撑什么**：一条任务在时间轴上有没有"长度"？（`estimate` / 活动日志
   `focusLog` 才是长度来源；只有 `dueDate` 的点，画不出条）；
3. **两种形态怎么共存**：点状时间线（只有截止时间）vs 条状甘特（有估时/活动）——
   缺数据时降级成什么，不许画一条假装有长度的条。

### 判据（调研完再细化）

1. 界面上**存在一条跨任务共用的时间基线**（刻度只画一次，不是每条重复）；
2. 任意两条任务在同一时间轴上的**相对位置**与它们的排期一致（可判定的断言，不是观感）；
3. 没有估时的任务**不出现假长度**；
4. 桌面载荷 + Android 各一张截图，人打开看过；暗色一张。

## 6. R5 · 移动端排序面板被屏幕底边裁掉（我自己取证撞出来的）

### 症状与实测证据

这一条是**给 R 系列做移动端取证时**当场发现的，不是看图猜的。
Android 模拟器（1080×2400）、当前源码重打的 release APK（已按 UTF-16LE 在
`assets/index.android.bundle` 里搜到新词条确认产物是新的）：

```
scrim  content-desc="关闭排序选择"  [0,0][1080,2134]
标题   "选择排序方式"                [42,2176][1038,2237]
档位1  "默认（按截止时间）"          [42,2258][1038,2374]
档位2  "按添加时间"                  [42,2395][1038,2400]   ← 只剩 5px
档位3  "按优先级"                    （根本不在无障碍树里）
```

⇒ 三个档位里**两个点不到**，其中一个完全不存在于树里。
截图：`apps/mobile/evidence/android-sort-2-picker.png`（人已看过）。

### 根因（这一条已经定了，不需要再调研）

`TasksScreen.tsx` 的 `SortPicker` 用的是"遮罩 `flex: 1` + 面板贴底"的形状
（抄的是同一屏 `Composer` 的写法）。`Composer` 内容矮，恰好塞得下；
`SortPicker` 内容更高，于是遮罩吃掉了 2134px，面板只剩 266px，**内容被屏幕底边切掉**。
共享层 `packages/ui/src/search/SearchPanel.tsx` 的注释里已经记过同一件事的第三种面目
（"面板高度是内容决定的，而内容高度是测量出来的"）。

### 修法方向（写在这里，避免下一轮重新想）

遮罩改成**绝对定位铺满**，面板用 `marginTop: 'auto'` 贴底，档位列表放进
`ScrollView` 并给面板一个 `maxHeight` —— 三件事各挡一种坏情况：
遮罩不再和面板抢高度；面板永远贴底；档位再多（或屏幕再矮）也只滚动不裁切。

### 判据

1. 1080×2400 上三个档位**全部在无障碍树里**且 rect 完整在屏幕内；
2. 换一台更矮的（或把面板选项加到 5 个的桩）⇒ 可滚动、不裁切；
3. 点第三个档位真的换档（chip 文字跟着变）—— 这条现在**做不到**，正是它暴露问题的方式。
