## 1.5 调研：六条症状抽象出来的六个普遍错误类

> 产品负责人这一轮的指令不是"把这几处改一下"，是
> **「这些东西的本质原因是什么？抽象出来的普遍错误是什么？在那个抽象层面上，最佳实践是什么？」**
> 所以本节先给抽象，再回头把每条对到类上。**刀要落在哪一层，由类决定，不由症状的位置决定。**

### 取证方法（以及两个探针自身的坑，先记账）

数字来自 `e2e/tests/tmp-layout-measure.spec.ts`（临时探针，收尾即删）+ 私有 vite 4318/4321，
视口 1280×720，三条任务：一条超长标题、一条带自然语言日期的、一条短标题。
产物：`/tmp/heyta-layout-measure.json`、`e2e/test-results/layout-measure/{tasks,quadrant,timeline}.png`（人已看过）。

两个坑都不是产品的，是**探针的**，按 §7 元规则一先怀疑探针，值得留下来：

1. **把函数当字符串传给 `page.evaluate` ⇒ 四个字段静默变成 `undefined`**。
   Playwright 把字符串当**表达式**求值，函数值不可序列化 —— 于是判据不是红，是**缺一块还不报**。
2. **`page.evaluate` 只序列化被调函数自己的源码**，闭包里的模块作用域帮手在页面里不存在
   （实测 `ReferenceError: rectOf is not defined`）。⇒ 浏览器侧函数必须**自包含**。

还有一条归因纪律：第一轮跑失败后 `/tmp` 里留着**上一轮成功的 JSON**，差点拿旧数据下结论。
⇒ **先读日志的 exit code，再信磁盘上的产物。**

### 类 A｜**用一个不存在的属性表达一个契约**（R1）

`checkboxHit` 只有 `marginLeft`，**没有 `width/height`**。负外边距是"让视觉圈往左探出 11px"，
而注释把它说成"44 的触控区"。**契约写在注释里，代码里没有任何一行实现它。**
实测命中区 = **22×22**（不是 44），所以"三端一致的可访问性下限"这一句**今天为假**。

同族的写法还有：用 `margin-top: -1px` 表达"两块要贴住"、用 `z-index` 表达"这是浮层"、
用 `overflow:hidden` 表达"这里可以滚动" —— **都是拿副作用当语义**。

> 该层面的通用规则：**命中区是一个真实的盒子，不是一个借位**。
> Web 用 `padding`/`min-width`+`min-height` 或包装层（MDC 的 `mdc-touch-target-wrapper` 就是这个形状），
> Android 用 `TouchDelegate`"保留 View 原尺寸、扩大可触区域"，iOS 用 44pt 的控件框 + 间距；
> **两个 WCAG 条款测量的都是输入区域，不是那个视觉标记**，Understanding 2.5.8 还明文建议
> "在不增大可见靶标的情况下扩大有效命中区"。细则与出处见本节末尾的引用表。

**推论（决定刀口）**：R1 的修法**必须删掉负边距**，改成"44 的盒子里居中放 22 的圈"。
只把负边距调小 = 保留类 A 本身。

### 类 B｜**裁剪祖先从不显式声明**（R1 的第二半，也是 §7 #82/#83 的同族）

`task-item-*` 与 `quadrant-cell-*` 里那些祖先**全部 `overflow: visible`**，
真正裁的是 RNW 给 `ScrollView` 生成的 **`overflow: hidden auto`**（横向 hidden、纵向 auto）：

| 场景 | 圈的真实 `x` | 裁剪祖先可视左边 | 被切掉 |
|---|---|---|---|
| 任务列表（`task-list-date-2026-10-02`） | 317 | **328** | 11px（正好一半） |
| 四象限格内（cell 里的滚动区） | 114 | **125** | 11px |

⇒ 探出留白的任何东西都会被切，而**没有任何一处代码声明过"这里会裁"**。
仓库里同类事故已记过两次（`app.css:260-266` 的.resizer 命中带、§7 第 83 条原生控件跟系统强调色）。
**通用规则：向外探出的几何与滚动/圆角容器不能共存**；要么探出的东西本来就在盒子里，
要么祖先显式声明 `overflow: visible` 并证明没有别的裁剪层。

### 类 C｜**尺寸由内容决定，而 `flex` 在没有确定母高的祖先里空转**（R2 + R5 同一个根）

这是这一轮**最贵的一条**：R2（铺不满）和 R5（面板被切）看起来一个太小一个太大，
其实是**同一个不变量被破坏** —— 没有把"确定尺寸"从视口一路传到需要它的那一层。

实测链条（视口 720 高）：

```
main.ht-main          display:flex   height 720      ✅ 有确定高度
  div.ht-content      display:block  flex:1  height 664  ← 块容器：只 Stretch 自己，不给子节点弹性基准
    div#quadrant-board flex:0 0 auto height 458     ← 内容决定高度
      div(行)          flex:0 0 auto height 192      ← 内容决定高度
        section.cell   flex:1 1 0%  height 192      ← 这行 `flex:1` 一个字都没生效
```

三处各自独立地断开，**修任何一处都不够**：
`.ht-content` 是块容器（`app.css:550-564`，注释里自己写着"内容区是普通块容器"）；
`board`（`QuadrantBoard.tsx:189`）只有 `gap`+`padding`；
`row`（:193）只有 `flexDirection`+`gap` —— 于是 `cell` 的 `flex:1` 要长的容器本身高度是内容决定的，
192 只来自 `minHeight: layout.quadrant-min-height`。

而 R5 是**同一类的另一面**：`SortPicker` 的面板**没有视口相对的 `max-height`、没有内层滚动**，
内容一高就溢出屏幕底边 —— 与"没有确定母高就不长"是同一条物理定律的两个方向。
🔴 机制在修完后改对了（详见 §6）：**不是**"遮罩 `flex: 1` 抢走高度、面板被压成 266px"，
而是 `View` 默认 `flexShrink: 0` ⇒ 面板**按内容高度**排布并溢出；遮罩只是填满剩余空间的那一个。

> 该层面的通用规则（各家表述不同，内容一致）：
> · **CSS 弹性盒 §9.7**：`flex-grow` 分配的是**剩余**自由空间 —— 父高 `auto` 时没有剩余，就没有分配；
>   `flex-basis: 0` 不等于"有高度可长"；
> · **嵌套滚动的标准解法**是给内层 `min-height: 0`（网格用 `minmax(0, 1fr)`），否则项不肯收缩；
>   通行行解剖学是"固定槽位显式尺寸 + `flex-shrink: 0`，弹性文字 `flex: 1` + `min-width: 0`"。
>   🔴 **后半句我们照抄错了，错得有代表性**：`min-width: 0` 治的是 `flex: 1 1 auto`
>   （`flex-basis` 不确定 ⇒ §4.5 的自动最小取**内容宽**）；而 `flex: 1` 展开后
>   `flex-basis: 0%` 是**确定**的，自动最小取的是 specified size suggestion（= 0），
>   `min-width: auto` 早就咬不到了。实测见 §2.2：删掉那一行，`min-width` 仍是 `0px`、
>   行也不撑宽。**配方抄之前要先看自己那一层的 flex-basis 是什么形状** ——
>   这就是类 E（没被审视过的默认值）的反面教材：**连"最佳实践"里的默认值也要审视**。
> · **RN/RNW 的默认值与 CSS 不同**（`view$raw` 里 `flexShrink: 0`，见下面引用表）——
>   这一条**同时**决定 R1 的"H2 被排除"和 R2 的"board 不 grow"；
> · **底部面板的通行上限是视口的一个比例，不是内容**：Flutter 的 bottom sheet 默认不超过 `9/16` 屏高、
>   Material 的 `PEEK_HEIGHT_AUTO` 是 16:9、Apple 的 sheet 用 `.medium`/`.large` **吸附档位**、
>   vaul/shadcn 的 drawer 用 `calc(100dvh - 6rem)`；共同点是**"顶到内容"要显式设上限 + 内层滚动 + 安全区内边距**。
>
> 反面教训（也是 R2 判据的来源）：**"铺满"不能写成 `100vh`**（共享层同时服务 RN，没有 vh；
> 窄窗单列时"铺满"意味着要滚）。要写的是**"母层给出确定高度，子层按约束长"**。

### 类 D｜**局部坐标系：每个子图自带一把尺子**（R4 本体）

实测：三条任务 → 三张 `gantt-chart`，每张 `width: 1152`（= 100%），每张的刻度都是
`gantt-axis` 里的 `0:00 / 0:30 / 1:00`。⇒ **位置不携带任何信息**，因为每一格都相对自己归一化；
刻度不是坐标轴，是把同一行字重复了三遍。`sharedTimelineSpan` 本意正是治这个，
但它只在**同一次导入的多条目**之间对齐，跨任务仍是各自一张图。

> 该层面叫得出名字的反模式有两个（都是文献里的，不是我编的标签）：
> · **small multiples 不共尺**：「读者不会逐格去核 y 轴，会默认它们共享一把尺，从而得出假结论」（Datawrapper）；
> · **Inappropriate Continuous Encoding / Data-Visual Disproportion**：图形长度不对应数据却画成连续条，
>   会**虚假地暗示连续性或趋势**（图表欺骗分类学，arXiv:2508.09716 §2.1）。
> 反过来，**"位置在同一把尺上"是所有编码里最精确的一种**，所以别人做时间线
> 第一件事都是"一根轴画一次、行与行对齐到它"（dhtmlxGantt 的 `scales`、Jira/Notion/GitHub Roadmap 的顶部时间轴）。

**降级规则（外部产品的一致做法，直接决定 R4 的判据形状）**：真实产品**从不编长度**。三种状态是有名字的：

| 数据 | 画法 | 出处 |
|---|---|---|
| 有起止（范围） | **条** | dhtmlx / Notion Timeline / Jira |
| 只有时刻（点） | **点 / 里程碑菱形**，不是条 | dhtmlx milestone、Mermaid、vis-timeline 的 `point`/`box`/`range` |
| 什么时间数据都没有 | **移出图区，放进一条有名字的泳道** | GitHub Roadmap 的 backlog、MS Planner 的 "Unscheduled tasks" |

唯一的"编时长"先例是日历引擎的**显式兜底项**：FullCalendar 的 `defaultTimedEventDuration`
—— 可配置、看得见、且**标注自己是兜底**，不是当成数据。
对照我们现在这句界面原文：**「其中 1 条未估时，按 1 小时排」**（`gantt-unestimated-summary`）——
它诚实，但**诚实的兜底仍然造出了一条 1152×24 的真条**，这就是"全是文字却没有线"里最坏的那一半：
线画了，可它说的是谎。

### 类 E｜**没被审视过的默认值**（R3 + R4 的编时长 + §7 #83 的原生控件，同一个根）

三件事长得不同，机制一样：**一个默认值在替用户/产品说话，而没人决定过它**。
- 界面某处默认落到英文（R3 的第一半，已修）；
- 没估时的任务默认 60 分钟（R4）；
- 裸 `<input type=checkbox>` 的选中色默认跟系统强调色（§7 第 83 条，主蓝命中 0 就是这么来的）；
- 取证脚本写进真库的 `B-mac-shot-1790762056`（R3 的第二半）——**测试数据的出处泄漏到了用户界面**，
  因为"跑完不清"是默认行为，不是决定。

> 通用规则：**默认值必须被显式定义，并且有一条判据钉住它。**
> 语言这一条是标准化的：RFC 4647 §3.4 明确要求实现**"必须定义 defaulting 行为"**，
> 通行次序是 显式请求 > 用户持久选择 > 设备语言列表与受支持集合匹配 > 在受支持集合内放宽 > 产品默认
> （Apple 的 `CFBundleDevelopmentRegion`、Android 的 `res/values` 都是"最后一道兜底"的具名实现）。
> 我们核对过自己的链路（`apps/web/src/lib/locale.ts` 的 `resolveInitialLocale`）**已经符合** —— 所以这一半不是修，是**记账 + 补判据**。

### 类 F｜**抽取 ≠ 去重**（#10，且 AGENTS §3.5 已经为它写过一篇）

共享 `TaskBadges` 只有移动端在用，web 的行元信息仍走自己手写的 `renderTaskMeta`
（`apps/web/src/App.tsx:979`），web 唯一的共享层消费者是 dev 切片。
这和 `ids.ts` / `SyncClientOptions` 那两次一模一样：**"抽出了一个共享实现"，但旧的那份没删，也没有门禁。**
⇒ 现在给共享层加"清单归属"不会收敛，只会造出**第三种状态**。
顺序因此是硬的：**① 先把 web 迁进共享 `TaskBadges`（删掉旧那份，`task-meta` 锚点跟着搬）→ ② 再加归属 → ③ 加门禁钉住"只有一份"**。

### 引用的标准（外部调研已回，逐条可查）

类 A/B/C 涉及的那些数字**不是我们自己的偏好**，是各家明文写的：

| 来源 | 明文规定 | 对我们这一刀的约束 |
|---|---|---|
| WCAG **2.5.8** Target Size (Minimum)，AA | "the size of the target for pointer inputs is at least **24 by 24 CSS pixels**"；**间距例外**：不足尺寸的靶心画 24px 圆、圆与圆不相交即通过 | 24 是**地板**，且地板之下还有例外 —— 所以"看着像 22 但能点"在这条下**可能合法**，不能拿它当修好了 |
| WCAG **2.5.5** Target Size (Enhanced)，AAA | "at least **44 by 44 CSS pixels**"，**没有间距例外** | 我们注释里那句"44 触控下限"是**取 AAA**，比 AA 严 —— 既然是**自己选的**，就必须**真的兑现**（这正是类 E） |
| Understanding 2.5.8 正文 | 明确建议作者"**在不增大可见靶标的情况下扩大有效命中区**" | 🔴 判据的**测量对象**由此确定：量的是**输入区域**，不是那个圈。"圈是 22"从来不是问题，"命中区是 22"才是 |
| Material / Android | "width and height of at least **48dp**"；MDC Web 48×48px；包装层"只在需要避免相邻靶标重叠时才需要" | 三端里最严的是 Android（48）。我们共享层写 44 是**已知妥协**，得在注释里写明 |
| Apple HIG（Mobility 一节） | iOS/iPadOS **默认 44×44 pt**，最小 28×28（macOS 28/20、tvOS 66/56、visionOS 60/28、watchOS 44/28）；"**控件之间的间距与尺寸同等重要**"（有边框的控件周围约 12pt、无边框约 24pt） | 44 这一档的**出处**；也说明"行与行之间贴多近"是可访问性问题，不是审美问题 |
| NN/g | 指尖 1.6–2cm、拇指约 2.5cm；"最小 **1cm × 1cm**"，"常推荐的 **约 2mm 间距**"实测常常不够 | 桌面指针与触屏不是同一道题 —— 我们的移动端那一腿要按触屏判 |
| MDC Checkbox 的实现 | 把 token 落到**交互元素自己的几何**上：`width/height: var(--mdc-checkbox-touch-target-size)` + `calc((40px - var(…))/2)` 偏移，另给 `mdc-touch-target-wrapper` 处理邻居碰撞 | 🔴 **这就是类 A 的正解形状**：命中区是**真实的盒子**，视觉圈在里面偏移居中，而不是拿负边距借位 |

**"用负边距表达命中区"为什么在规范层面就错了**（CSS 2.1 §11.1 的原文把这种情况**列为溢出**：
"a descendant box has negative margins, causing it to be positioned partly outside the box"）：
负边距**只移动盒子，从不增大盒子** —— 它是唯一一条"看起来在做、其实做不到"的选项，
所以它坏的时候是**静默**的（界面上只是"缺了一半"，没有任何一层报错）。
常见的"绝对定位伪元素外扩（breakout）"这条路在 RNW 上也**走不通**：
RNW 给**每一个** `View` 都加了 `position: relative`，而逃逸只对"它与它的包含块之间"的祖先免疫
⇒ 结构上等于被裁。（后半句是标注过的推断，不是引文。）

**RNW 的默认值**（这条决定了 R1/R2 的修法，也**推翻了我自己写下的 H2**）：
`View` 的基础样式在作者样式**之前**合并（`supportedProps.style = [styles.view$raw, …, props.style]`），
而 `view$raw` = `flexShrink: 0, minWidth: 0, minHeight: 0, boxSizing: border-box, display: flex,
flexDirection: column, position: relative, zIndex: 0`
（`react-native-web/src/exports/View/index.js:147-170`，0.21.3）。
⇒ **"RNW 的 View 默认 `flex-shrink: 1`"是假的**，它默认 **0**（RN 文档同样写 0，CSS 才默认 1）。
真正会漂的是另外两处：**`Text` 没有 `flexShrink`/`minWidth`**（`exports/Text/index.js:189`），
于是它是普通 CSS flex 项，受**自动最小尺寸**（`min-width: auto` = 内容宽，CSS Flexbox §4.5）支配 ——
长标题**不肯收缩**；以及任何走裸 CSS（不是 `StyleSheet`）的东西拿的是 web 默认值。
⇒ 通行的行解剖学因此是：**固定槽位 = 显式尺寸 + `flex-shrink: 0`；弹性文字 = `flex: 1` + `min-width: 0` + 省略号。**
（RNW 的 `numberOfLines=1` 已经会发出 `overflow:hidden; text-overflow:ellipsis`。）

⚠️ 一条**尚未证实**、也不该写进判据的事：`hitSlop` 在 RNW 上到底生效与否我没查到引文。
它对本刀**不影响** —— 我们要的是真实盒子，不是平台命中扩展 API
（Android 那一侧的对应物 `TouchDelegate` 的原文表述是
"retain the original size of a View while expanding its touchable region"）。

### 症状

产品负责人两次指同一样东西：任务行最左边那个圈，看着像被切掉一半。
四象限格子里的三行（`B-mac-*`）与时间线里的三行**都有**——所以它是**行骨架**的问题，

### 已读到的代码事实

```
TaskRow.tsx:165  checkboxHit: { marginLeft: -(touch-target.min - size.checkbox) / 2 }
TaskRow.tsx:169  box: { width/height: size.checkbox, borderRadius, borderWidth }
```

也就是说：只要它左边被切掉 11px，就**恰好只剩一半**。这与看到的现象数量级吻合。

### 2.1 实测结果（2026-10-01，探针 + 桌面载荷）

**H1 成立，H2 被排除 —— 而且 H2 的前提本身是假的。**

| `task-toggle-*` 自身 rect | `x=317, w=22, h=22` | `x=114, w=22, h=22` |

1. **不是压扁**：两处实测 `w` 都**恰好 22**，且 `flex-shrink: 0`。

   RNW 把 `view$raw`（内含 `flexShrink: 0`）在**作者样式之前**合并

   🔴 这条要留在文档里：照着 H2 去修，我会加上一行 `flexShrink: 0` ——
   **它一行问题都解决不了，还会让我以为解决了**（"不能失败的判据"的同族：不起作用的修法）。
2. **是被裁，而且切在正中**：负边距把圈推到 `317`/`114`，裁剪祖先（RNW `ScrollView`
   ⇒ `overflow-x: hidden`）的可视左边是 `328`/`125`。
   **类 A 与类 B 同时成立**：探出靠借位（A），而借出去的东西落在裁剪区里（B）。
3. **命中区是 22，从来不是 44**：`checkboxHit` 没有任何 `width/height`（类 A 的本体）。
   按 WCAG，量的是**输入区域**而不是那个视觉标记，所以"圈是 22"不是问题，
   **"命中区也是 22"才是**。
4. **`TaskRow.tsx:165` 那一条负边距是承重的**：删掉它界面就"看起来正常了"，
   但命中区仍然是 22 ⇒ 判据必须**同时**测几何与尺寸，只测一个都会假绿。

### 2.2 上面那段关于 `minWidth: 0` 的推断**被实测证伪**（2026-10-01，撤回写在这里）

我原来写："RNW 的 `Text` 基础样式里没有 `minWidth` ⇒ `body` 受自动最小尺寸支配 ⇒
长标题不肯收缩 ⇒ 补 `minWidth: 0`。"**这句的结论行是错的**，而且是"不起作用的修法"那一类。
取证方式是把这一行删掉再量（同一份共享层、同一个桌面载荷）：

| 量 | 带 `minWidth: 0` | 删掉 `minWidth: 0` |
|---|---|---|
| `body` 列的计算 `min-width` | `0px` | **`0px`**（一模一样） |
| 行的 `scrollWidth` / `clientWidth` | `359 / 359` | **`359 / 359`** |
| 不可断行的长 URL 那一行 | 换行、不撑宽 | **换行、不撑宽** |

机制：RNW 的 `flex: 1` 展开成 `flex-grow:1; flex-shrink:1; flex-basis:0%`，
而**`flex-basis: 0%` 本身就把自动最小尺寸的起点压成 0**，所以 §4.5 那个洞在这一列上咬不到。
配套变异（m3，见 §2.3）也证实了：删掉这一行，桌面载荷那条**一个字都不红**
—— 也就是那条为它写的"撑宽"断言是一条**永远通过的判据**。

⇒ **这一行连着它的注释、连着只看撑宽的断言，一起删掉**。判据面收窄为
"命中区够大 + 不借位 + 不越出行边"三条，每条都有变异能打红。
（类 C 在 R2/R5 上仍然成立 —— 那里坏的是**高度**方向上没有确定母高，与这条无关。）

## 3. R2 · 组件没有铺满高和宽

### 症状

产品负责人原话：**"各个页面内的组件应该是几乎全面铺满高和宽的，为什么这个根本没有铺满？
那这个四象限这个组件就没有铺满。"** 截图上：2×2 只占上部约六成，下面整片是底色。

### 已读到的代码事实

- 共享层 `packages/ui/src/quadrant/QuadrantBoard.tsx:208` 每一格是 `flex: 1` +
  `minHeight: layout.quadrant-min-height`；
- 但 `board`（:192）只有 `gap` 与 `padding`，**没有 `flex: 1`，也没有 `height`**；
- 宿主侧 `apps/web/src/App.tsx:2242` 是 `{contentView === 'quadrant' && <QuadrantBoard />}`
  —— 直接挂在内容列上；
- `HeytaUiProvider`（`packages/ui/src/theme.tsx:230`）**只给 context、不产生 DOM 层**，
  所以"中间多了一层没接上"这个嫌疑**已被排除**（这是一次有用的排除：它把范围收窄到两处）。

⇒ 结论方向：**格子的 `flex: 1` 是空转的**，因为它要长的容器（board）自己高度是内容决定的。
`minHeight` 于是成了唯一有效的高度来源 —— 界面就停在"四张最小高的卡 + 一大片空白"。

### 已读到的代码事实（行号 2026-10-01 对着文件核过）

- 共享层 `packages/ui/src/quadrant/QuadrantBoard.tsx:207-210` 每一格是 `flex: 1` +
  `minHeight: layout.quadrant-min-height`；
- `board`（:191）只有 `gap` 与 `padding`，`row`（:195）只有 `flexDirection` 与 `gap`，
  `stack`（:204）只有 `gap` —— **三处都没有 `flex`**；
- 宿主侧 `apps/web/src/App.tsx:2282` 是 `{contentView === 'quadrant' && <QuadrantBoard />}`
  —— 直接挂在内容列上；
- `HeytaUiProvider`（`packages/ui/src/theme.tsx:230`）**只给 context、不产生 DOM 层**，
  所以"中间多了一层没接上"这个嫌疑**已被排除**（这是一次有用的排除：它把范围收窄到三处）。

### 3.1 实测链条（视口 1280×720，原来那两处待验证都验了）

```
main.ht-main           display:flex   height 720   overflow visible   ← 有确定高度
  div.ht-content       display:block  flex:1  height 664  minHeight auto
                                          ↑ 块容器：自己 Stretch 到 664，但不给子节点任何弹性基准
    div#quadrant-board flex:0 0 auto   height 458   flexShrink 0   ← 内容决定高度
      div(行)           flex:0 0 auto   height 192   flexShrink 0   ← 内容决定高度
        section.cell    flex:1 1 0%     height 192   ← 这行 flex:1 一个字都没生效
```

四格实测：`quadrant-cell-1..4` 全部 `w=554, h=192`，`flex: "1 1 0%"`；
横向**确实铺满了**（两格 + gap 正好等于行宽），**纵向没有**（board 458 < 内容列 664，差 **206px**）。

⇒ 回答本节原来那两处待验证：

1. 内容列**不是**滚动容器（`overflow: visible`），是 `flex: 1` 的**块**子项 ——
   它拿到了 664px 的确定高度，但因为自己是 `display: block`，**"确定高度"没有向下传播**；
2. 所以"铺满"的表达方式**不是** `min-height: 100%`，也不是 `100vh`，而是
   **"把内容列变成 flex 列，并让 board 声明 grow"** —— 两个动作，缺一律无效。

🔴 三处独立断点，**修任何一处都不够**（这正是类 C 的定义）：
宿主不给弹性上下文（`.ht-content`）、board 不 grow、行不 grow。
`cell` 的 `flex: 1` 是**唯一写了契约的那一层，而它是最后一个才有用的那一层**。

⚠️ **不许顺手把 `height: 100vh` 写进共享层**：那一层同时服务移动端（RN，没有 vh）与
窄窗单列（四格竖排时铺满意味着要滚），写死 vh 会在手机上把第四格推到屏幕外。
共享层要写的是**"按母层给的约束长"**（`flex: 1` + `minHeight` 兜底），
宿主写的是**"把约束传下来"**。

⚠️ **改 `.ht-content` 有一条必须一起想的代价**（现在就记，别等实现时撞）：
它现在被**明文写成"普通块容器"**（`app.css:559-563` 的注释：面与面贴死要由上面那块显式声明间距），
变成 `display: flex; flex-direction: column` 之后 **块之间的外间距不再塌陷合并** ——
所有挂在内容列上的面都会**变矮或变挤**。⇒ 这一刀必须**同时**扫一遍内容列上的全部面
（任务列表 / 日历 / 习惯 / 便签 / 成长 / 搜索 / 设置），不能只对着四象限改。

### 判据

1. **传播判据（新的，也是本体）**：从 `main` 到 `cell` 逐层读计算样式，断言
   "每一层的父层要么是 `display: flex` 的列、要么有确定高度"；
   **任何一层是 `display: block` 或 `flex: 0 0 auto` 就红**。
   只测"board 高度够不够"会**假绿**：那可以在宿主写一个 `100vh` 糊过去；
2. 视口高 800 / 1000 / 1200 三档下，`#quadrant-board` 的 rect 高度 ≥ 内容列可视高度的 90%，
   **且**四格高度相等；
3. 窄窗（< `layout.two-column-min`）单列时：不裁切、可滚动、每格不低于 `minHeight`
   —— **"铺满"在单列下必须换成"可滚动"，这是同一条契约的两个分支，不是例外**；
4. 移动端同一份共享层（Android 模拟器）截图：单列不溢出；
5. 变异验证**两种都要**：① 拿掉 board 的 `flex: 1` ⇒ 判据 2 红；
   ② 拿掉宿主 `.ht-content` 的 `flex-direction: column` ⇒ **判据 1 红、判据 2 可能仍绿**。
   这一对专门用来证明**两层都承重** —— 只写一条判据会漏掉其中一层，
   而漏掉的那层正是"下次有人把它改回去时没人报警"的那层。

#### 判据为什么长成这样（类 C 在移动端换了分支）

剩余 = 0。所以移动端这条判据问的不是"板子长到多高"，而是同一条"只长不缩"应当产生的
**结果**：**每一格都靠滚动够得着**，而不是被压扁或被裁。

| 实测值（1080×2400 / 密度 420，1dp = 2.625px） | 数字 |
|---|---|

| 四格总高 vs 视口高（前提断言） | 2016 > 1888 ⇒ 必须靠滚 |

#### 🔴 无障碍树的两条实测事实，它们直接决定了判据的形状

1. RN 交给 a11y 树的矩形是**裁到父层可视区**的 —— 折叠线以下那格报成**负高**
   （修前实测 `[84,2199][996,2166]`，高 = −33px，而它的兄弟格高 504px）。
2. **超出得多的那一格整节点不在树里** —— 不滚的时候 dump 只有 `quadrant-cell-1/2/3`，
   4 号**根本不存在**（第一轮就把"数节点数"那条判据判成 `total=3` 红）。

⇒ "节点在树里"不等于"用户看得见"，而**静态一帧里数节点**也不等于"节点不在树里"。
两种假信号都来自"拿一帧当全部"（§7 元规则一）。所以 ①（在树里）与 ③（看得见）
**都取滚动扫描的跨帧并集**，并且 ③ 额外要求"那一帧它高够"。

⚠️ 高度判据**必须带容差**：同一份基线里最大高是 504 与 **503** 并存（修前旧包见过 502），
那 1~2px 是 1dp 边框与 dp→px 取整，**不是**"没长到 minHeight"。严格 `≥ 504` 会假红。
判据线因此写成 `192dp − 2dp`（504 − 5 = 499px），容差本身从 token 推导。

### 4.2 残留数据：根因是"这个壳删不掉"，不是"谁忘了删"（2026-10-02）

产品负责人看到的是三行英文任务名，最容易得出的结论是"探针作者偷懒没清理"。
读了一遍代码之后的结论不一样：

**这三条任务在 `apps/node-host` 上根本没有任何删除通道。** 那个壳的接口一直只有
`add / rename / setCompleted / reopen`，而删除与彻底删除的动作早就存在于
`@heyta/app-host`（`actions.ts:132-140` 的 `remove` 发 `DEL` op、
`:172-189` 的 `purge` 写 `purgedAt` 且**拒绝活着的条目**）。零件都在、产品里没这个功能 ——
就是 §1.5 那个 **class F 的镜像形态**：共享实现已经有了，宿主那半边从来没接上 ——
"抽出来"从来不等于"每个宿主都用上了"。没有删除通道的宿主，探针作者唯一能选的就是
"让残留在用户看得见的界面上"。

🔴 **为什么判据必须落在视图上，不能落在"库里 grep 不到"**：每个宿主启动时都做一次
**全量回放**（`recover()` → `getAllOps()` → `replayOperations(emptyState())`），
物化状态只在内存里；`state` 表在生产路径上根本没有写者。所以任何裸 SQL `DELETE`
要么删的是没人读的东西，要么让 op-log 与状态永久分叉 —— 数据会在下次启动**复活**。
处置只能走 op-log，而"彻底删除"关掉的只是**恢复这条路 + 回收站里继续看得到**，
它**不**抹历史（只追加的日志）。

补上的三条命令（commit `b0fca047`）：`remove`、`purge`，以及**为判据本身**补的 `trash` ——
`remove` 与 `purge` 都会让 `list` 变空，所以"purge 之后列表为空"这种判据
在**只做了 `remove` 时照样绿**。必须两个视图都读得到，处置才是三个可区分的状态。

实测（`.backup` 取副本先跑一遍，本体一个字节不动；真库再同样跑一遍）：

| 阶段 | `list` / `trash` | 说明 |
|---|---|---|
| 处置前 | **3 / 0** | 阳性对照：探针确实看得见那三条 |
| 对活着的任务直接 `purge` | **3 / 0** | 反证：守卫拒绝（`exit=1`）且什么都没改 |
| 三条 `remove` 之后 | **0 / 3** | 中间态 —— 这一步的存在证明 `remove ≠ purge` |
| 三条 `purge` 之后 | **0 / 0** | 终态：用户任何视图都读不到 |
| 导出对账 | 3 条实体 `deletedAt`+`purgedAt` 齐全，op 数 **3 → 9** | 历史保留 = 上面那条诚实条款 |

## 5. R4 · 时间线 UI：全是文字，没有"线"

### 症状

产品负责人原话：**"这个时间线的 UI 很离谱啊，怎么可能都是文字？时间线是线呢？
你搜索一下别人是怎么做这个 UI 的好不好？"**

截图上的实际形状：每条任务是一坨文字（标题 + 说明 + 一行统计 + 一行刻度 `0:00 / 0:30 / 1:00`
+ 一行时间区间 + 一个空框）。**三条任务就是三坨，彼此没有任何时间关系**。
刻度只有一条任务的宽度，所以它不是时间轴，是把 `0:00 0:30 1:00` 当装饰重复了三遍。

### 原来要回答的三个问题（产品负责人要求"先搜别人怎么做"，逐条作答）

1. 别人怎么做 → 见 5.2 的形态表与要素清单；
2. 我们的数据支撑什么 → **不支撑**：入参里根本没有"什么时候"（见 5.1），
   长度只有 AI 估时一个来源，且它落在**子条目**上而不是任务上；
3. 两种形态怎么共存 → 见 5.2 的三态降级表（条 / 点 / 有名字的泳道），
   且**缺数据时不许画一条假装有长度的条** —— 这一条今天正在违反。

### 5.1 实测：件都在，坏在**数据契约里没有时间**

本节原来第一个要回答的问题是"GanttChart 有没有被挂上，还是挂着但算出了空数据"。
实测答案：**挂上了，而且画了** —— 每一个几何元素都有真实 rect：

```
gantt-bar-0        1152 × 24   ← 条：有，而且是**整行宽**
gantt-axis         1152 × 16   ← 轴：有，文字是 "0:00 0:30 1:00"
gantt-tick-0/30/60   64 × 16   ← 刻度：三格，每**张图**都来一遍
gantt-today-line     2 × 24    ← 今天线：有
```

三条任务 → 三张 `gantt-chart`，每张 `w=1152`（= 它自己那一行的 100%），
每张的块高都 `163`（一模一样）。⇒ 用户看到的"全是文字没有线"，
真实情况是**线画了，但它不携带信息**：每一张都把自己归一化成 100%，
所以"位置"这个编码被彻底浪费了（类 D）。

🔴 而往下读一层，问题比"观感"严重：`gantt-dates-0` 实测文字是
**「10-01 0:00 → 1:00」** —— 而这条任务的截止时间是 **15:00**。
这不是"没有线"，是**界面把相对偏移印成了日历时间**，说得像一句真话。

根在数据契约，不在画法（这是本节最重要的结论）：

```ts
// packages/app-host/src/timeline-plan.ts:32
export interface TimelineTaskLike { readonly id: string; readonly title: string; readonly note?: string; }
                                              ↑ 没有 dueDate，没有任何"什么时候"
```

- `buildTimeline` 的 `startOffsetMinutes` 定义是"从**该计划**第 0 分钟算起"
  （`packages/domain/src/timeline.ts:127-132`）—— **每条任务自己一条 0 起点的时间轴**；
- `TimelineView` 把 `startDate` 传给图，图就把 `0` 偏移渲染成"起始日的 0:00"，
  于是相对偏移**顺理成章地**变成了假的日历时间；
- `sharedTimelineSpan`（`timeline.ts:201`）只对齐**跨度**（尺子刻度），
  **不对齐原点** —— 所以"每条都占满整行"这件事它一点都没管住。
  🔴 这是一个**名字比实现大**的函数：注释写"所有块共用一把尺子"，实际只共用了**长度单位**，
  没共用**坐标原点**。共尺不共原点 = 等于没共（这正是 small multiples 的经典错法）。

### 5.2 别人的做法：要素清单 + 三态降级（外部调研结论，可逐条查）

**先说形态与数据要求的关系**（这决定了我们该选哪一种）：

| 形态 | 有没有连续时间轴 | 需要的数据 | "线"是什么 | 数据不足时 |
|---|---|---|---|---|
| 滴答清单 时间线视图 | **有，横向共用一根** | 任务的时间/区间 | 轴本身 + 块 | 无时间的**不落图** |
| Notion Timeline | 有，共用 | **日期 + 结束日期（区间强制）** | 条 | 单日期项**不画**，窗口外的用**小箭头**标出 |
| Jira / GitHub Roadmap / MS Planner | 有，顶部一根 | 起止 | 条 + 今天线 + 里程碑菱形 | 无日期的进**有名字的泳道**（backlog / Unscheduled） |
| Agenda / Todoist 列表 / OmniFocus Forecast | **没有轴**（按天分组的序数列表） | 一个日期 | 没有线，日期是文字 | 天然降级，不装 |
| Ant Design Timeline | 没有比例尺（脊柱 + 点） | 只要可排序 | 脊柱 | 天然降级 |
| vis-timeline | 有真轴 | 按类型 | `range` 条 / `point` 点 / `box` 框 | **`point` 类型就是为"没有时长"准备的** |

⇒ **可迁移的裁决**：一个"时间线"要么**共一根轴**并承认它需要时间坐标，
要么就**别用连续编码**（按天分组的列表完全合法，且不需要任何假数据）。
我们此前两头都没选：用了连续编码（条 + 刻度），却没有坐标系统。**这是最坏的组合。**

**甘特要素清单**（通行、且我们该有 / 不该有的分界）：
一根共用时间刻度（只画一次）· 行与刻度对齐 · 条按起止定位 · 
**里程碑/点**表示零时长 · 今天线 · 依赖连线 · 缩放档位 · 非工作日底纹 · 
窗口外用**指示符**而不是截断 · 无数据项进**有名字的泳道** · 冻结行头 + 横向滚动。

**三态降级规则（真实产品从不编长度）**：

| 有什么 | 画什么 | 出处 |
|---|---|---|
| 起止（区间） | **条** | dhtmlx / Notion / Jira |
| 只有时刻 | **点 / 菱形**，不是条 | dhtmlx milestone、Mermaid、vis-timeline `point` |
| 什么时间数据都没有 | **移出图区**，进一条**有名字的泳道** | GitHub Roadmap backlog、Planner "Unscheduled tasks" |

唯一的"兜底时长"先例是日历引擎的**显式可配置项**（FullCalendar `defaultTimedEventDuration`，
文档自己称它是 "fallback duration … without a specified end value"）—— 
可配置、看得见、**标注自己是兜底**，且**只用于内部串行排程**，不用于冒充用户给过的日历长度。

**两条有名字的欺骗形态**（我们同时踩了）：
· **small multiples 不共尺**：「读者不会逐格去核轴，会默认它们共享一把尺，从而得出假结论」（Datawrapper）；
· **Inappropriate Continuous Encoding / Data-Visual Disproportion**：把没有的数据画成连续条，
  等于**虚假地暗示连续性**（图表欺骗分类学 arXiv:2508.09716 §2.1）。

⚠️ **可达性边界（不是本轮的活，但必须先记）**：图区不是无障碍界面。
WCAG 1.1.1 要求复杂图形有**短替代文本 + 长描述**（WAI 明确建议结构化数据用**数据表**）；
1.4.1 要求颜色不是唯一线索；**1.4.11 要求非文本对比 ≥ 3:1，轴线与网格线在适用范围内**。
微软自己的 Project 读屏指南直接把用户**支到网格窗格**（"Move between columns and rows in the
spreadsheet"）—— 说明"共用的那条轴"从来不是无障碍表面。⇒ 我们的判据要包含
"**列表读法仍然存在**"（现有 `TimelineView` 的每一块都有文字标题，这一条不许在重画时丢掉）。

### 5.3 因此这一刀改哪一层（按 §1.5 类 D 的推论，刀不在皮肤上）

1. **领域层**（`packages/domain/src/timeline.ts`）：给"一条任务在时间上的位置"一个类型 ——
   三种状态（`range` / `point` / `unscheduled`）在**类型**上可区分，
   而不是靠"有没有 `durationMinutes`"这种弱信号（那是类 A 在数据层的复现）。
2. **业务语义层**（`packages/app-host/src/timeline-plan.ts`）：入参从 `{id,title,note}`
   扩到**带 `dueDate`**（可选字段，§3.3 的纪律），产出上面那三种之一；
   🔴 **不许在这里编长度**：只有估时没有日期 ⇒ 进未排期；只有日期没有估时 ⇒ `point`。
3. **共享 UI 层**（`packages/ui/src/timeline/*`）：**整个视图只有一根轴**，行 = 任务；
   `point` 画点/菱形、`range` 画条、`unscheduled` 画进**有名字的泳道**且**不落图**；
   任务内部的清单排程**降级成"点开看"**（那是另一个坐标系，必须标明）。
4. `sharedTimelineSpan` **要么改成同时共原点、要么改名** ——
   留着一个"名字承诺了它没做的事"的函数，就是下一个类 A。

### 判据（可失败，逐条对着上面的结论）

1. **一根轴**：视图里 `gantt-axis` 的**数量 == 1**（现在 == 任务数）。

## 6. R5 · 移动端排序面板被屏幕底边裁掉（我自己取证撞出来的）

### 症状与实测证据

这一条是**给 R 系列做移动端取证时**当场发现的，不是看图猜的。
Android 模拟器（1080×2400）、当前源码重打的 release APK（已按 UTF-16LE 在
`assets/index.android.bundle` 里搜到新词条确认产物是新的）：

```
scrim  content-desc="关闭排序选择"  [0,0][1080,2134]
标题   "选择排序方式"                [42,2176][1038,2237]
档位1  "默认（按截止时间）"          [42,2258][1038,2374]
档位2  "按添加时间"                  [42,2395][1038,2400]   ← 只剩 5px
档位3  "按优先级"                    （根本不在无障碍树里）
```

⇒ 三个档位里**两个点不到**，其中一个完全不存在于树里。
截图：`apps/mobile/evidence/android-sort-2-picker.png`（人已看过）。

### 根因（2026-10-01 修完后**回过头把机制改对**）

先前写在这里的那句「遮罩吃掉了 2134px，面板只剩 266px」**方向对、机制错**，
而错的那一半恰好决定了修法对不对。

RN 的 `View` 默认 `flexShrink: 0`（与 CSS 相反 —— §2.1 为 RNW 的 `view$raw`
已经取过一次证，原生侧同规则）。所以面板**不会被压矮**：它按内容高度排布，
遮罩的 `flex: 1` 只是"长到填满剩余空间"，于是面板从 `y=2176` 起、
**内容需要到 `y≈2650`，超出屏幕底边被切**。不是"空间不够被压缩"，是"根本没人给它设上限"。

⇒ 类 C 的一句话版本：**面板高度由内容决定，而它落在一个由遮罩决定的坐标系里，
两者都不引用视口。**

### 已交付的修法，以及它和本文原方案的三处偏离

`apps/mobile/src/screens/TasksScreen.tsx` 的 `SortPicker` 与 `Composer` 各改：
遮罩 `position: 'absolute'` 铺满（离开 flex 流）→ 面板 `marginTop: 'auto'` /
`KeyboardAvoidingView{flex:1, justifyContent:'flex-end'}` 贴底 →
档位/内容进 `ScrollView` → 面板 `maxHeight: '90%'` → `paddingBottom` 接 `insets.bottom`。

| 原方案 | 实际做法 | 为什么改 |
|---|---|---|
| 取 `Dimensions.get('window').height` 的比例算上限 | 直接写 `maxHeight: '90%'` | 百分比是**相对父容器**的，只有当父容器=视口时它才是"视口的九成" —— 而"遮罩离开 flex 流"这一步已经把父容器变成了视口。`Dimensions` 是模块级快照，转屏/分屏不跟随；声明式那一版没有这个洞。**两条都在宿主壳里，没有渗进共享层（§3.5 的界守住了）** |
| 给 `ScrollView` 加 `flexShrink` + 面板 `minHeight: 0` | 只加了 `ScrollView` | `minHeight: 0` 是 CSS flex 的洞，RN/RNW 的 `View` 默认 `flexShrink: 0` 但 `minHeight` 不是 `auto` —— 这一行在 RN 上是**不起作用的修法**（§2.1 结论 1 的同族），加了只会让人以为防住了 |
| 「必须减安全区」 | 已做（`insets.bottom + space.8`） | 无偏离 |

### 变异验证：这四行**各自**挡不挡得住？（同一台 1080×2400 / 密度 420，真模拟器）

判据脚本 `scripts/verify-mobile-sort-sheet.sh`，每行改完**重打 APK 再跑**：

### 本轮 G9 取证新增的两条探针纪律（都是我自己犯的，不是别人的）

1. **变异夹具的"能还原"必须逐字节比，不能只查字符串存在。**
   第三轮诱饵的 Python 里 `i = a.rindex('style={{')` 是在 `a.replace(TAIL_WRAP,'',1)`
   **之前**算的，切片因此晚了 30 个字符，把共享文件 `apps/web/src/App.tsx:1905` 的
   `style={{ marginBlockEnd: cssVar('space.2') }}` 搅成了 `cssVastyle={{.2')` ——
   而夹具的 `verify()` 只断言"诱饵串不在、原串在"，**没断言"文件 == 变异前"**，
   所以它带着坏文件报了成功。是随后的 `pnpm --filter @heyta/web typecheck` 用
   15 条 JSX 语法错把它照出来的。修法靠 `diff /tmp/bk-App.tsx apps/web/src/App.tsx`
   （恰好一行不同）还原，再 `diff -q` 确认逐字节相同、typecheck 回 EXIT=0。
   🔴 **在共享工作树里这类事故的代价不是"我的红"，是别人捡到一份坏文件** ——
   所以变异夹具的收尾必须是一次 `cmp`，不是几次 `in`。
2. **证据图必须核出处（md5 对上探针的哪一张），文件名说的必须与像素相干。**
   我把 `/tmp/heyta-g9/00-full.png` 存成 `02-1440-八个控件常驻.png`，而它是探针流程
   **最后一张**：此时注入的"行尾收起"规则还活着，图里行尾**一个控件都看不见** ——
   文件名与像素正好相反。发现方式很朴素：**人真的打开那张图**（§6.2 规定一）。
   已换成同一轮里未注入状态下的 `01-current-nomouse.png`（md5 `8b5f1cb3…`，
   1440 无鼠标、八个控件全常驻），并给八张图逐张做了 md5 对账。
   📌 一般规律：**探针留下的最后几张图继承了探针改过的状态** —— 与 §7 第 83 条
   「探针会改变被测对象的状态」同族，区别是这次污染的是**证据**而不是判据，
   而坏证据比坏判据更难发现：它长得像已经验过了。

## 7. 顺序与"一条一条解决"

### 7.0 调研阶段已完结（2026-10-01），而且它推翻了台账自己先前的两个判断

这一节写在实施之前，是为了让后面每一刀都能对照"**改之前我们相信什么 / 实测之后剩下什么**"：

1. **R1 原来是猜错的**：先前记的是"负边距 + 可能被压扁"两种假设。实测结论是
   **H2（压扁）排除、H1（被裁）成立**，而且 H2 的前提本身是假的 ——
   RNW 的 `view$raw` 把 `flexShrink: 0` 合在作者样式**之前**，
   "RNW View 默认 flex-shrink:1"这条常识在 RNW 上不成立（§2.1）。
2. **R3 有一半根本不用修**：默认语言链路对着 RFC 4647 §3.4 逐环核过，
   **已经符合**（显式 > 持久偏好 > 设备列表匹配 > 集合内放宽 > 产品默认），
   而且那一半已由另一条会话落地（`0aa6cb0e`）。所以它只剩"残留数据处置 + 逐屏英文扫"。
3. **R4 的病不在 UI**：原先的问题是"`GanttChart` 有没有挂上，还是挂着但算出空数据"。
   实测：**件全挂上了、全有真实 rect**（条 1152×24、三格轴、今天线 2×24）。
   真根在**数据契约里没有时间**（`TimelineTaskLike` 只有 `id/title/note`），
   外加两个各自独立的坏味道：**每个任务一把自己的尺子**与**没估时编成 1 小时**（§5.1）。
4. **抽象出来的六个类（§1.5）里有三类是多条症状共享的**：
   类 C（确定尺寸不向下传播）同时是 R5 和 R2 的根；类 A（用一个不存在的属性表达契约）
   同时是 R1 和 R4 的"名字比实现大"；类 F（抽取 ≠ 去重）是 #10 的全部理由，
   而 AGENTS §3.5 早就为它写过两篇（`ids.ts`、`SyncClientOptions`）。
   ⇒ 这就是产品负责人问的"表面上只是一个地方的问题，实际上是不是设计系统的问题"的答案：
   **R1/R2/R5 是三处症状、两个错误类，刀口在共享层与宿主层，不在任何单页。**

按 **R5 → R1 → R2 → R3 → R4 → #10** 做，理由不是编号顺序：

- **R6 已经动刀**（2026-10-01）：删卡那一半当场做完并验完（见 §6.6），
  **"数字放回三个位置"那一半并进 #10 收集箱重做** —— 它不是独立的一条，
  而是那一屏信息架构的一部分；三格的现状与剩下的缺口记在 §6.6
  （per-tag 计数已补、回收站计数判定为不做、剩下的真缺口是**清单归属只在 web 的行上**）。

- **R5 最先**：根因已定、判据已写、只欠一次改动，而且它挡着移动端所有后续取证
  （面板打不开，排序相关的截图都拍不成）；
- **R1 第二**：它是**行骨架**的缺陷，全应用每一行都受影响。
  ⚠️ 调研后这条的理由**换掉了**：原先写"它可能是 R2 那个 RNW 默认值疑问的同一个根"，
  实测**否掉了这个联想** —— R1 是类 A+B（不存在的属性 + 隐式裁剪祖先），
  R2 是类 C（确定尺寸不向下传播），两者**不是同一个根**（§2.1 / §3.1）。
  它排第二的真实理由是**半径**：`TaskRow` 是唯一行骨架，R2/#10/R4 都要在它上面取证；
- **R2 第三**：需要一次真测量（rect），范围比 R1 大；而且它现在已知要**两层各一刀**
  （宿主 `.ht-content` + 共享 board/row），单层改动会有"看起来绿了"的假修（§3.1 判据 5 那对变异专门挡它）；
- **R3 第四**：三件事里两件是收尾/清扫，不阻塞看界面；默认语言那一半已被核过**不用修**；
- **R4 第五**：外部调研**已做完并回写本节**（§5.2 要素清单 + 三态降级）。
  动手仍在 R1/R2 之后 —— 时间线重画会撞上同一批行骨架与容器问题。
  🔴 **判据 4（"区间里的时间必须来自 `dueDate`"）在改之前必须是红的**：
  它是本轮调研唯一一条"界面在说谎"级别的判据，如果实施时它绿了，
  说明探针没跑到有 `dueDate` 而无估时的那条任务上，**先修探针再改代码**（§7 元规则一）；

  🔴 **四步已全部落地（2026-10-02）**，逐步对到证据：①/② = 提交 `1d485786`（锚点跟着搬、旧的一份当场删）；
  ③ = `listNameFor` 进共享判断层 + 两端各喂一次 `props`；④ 见下面这段，**说明清楚它为什么不是新脚本**。

#### 第 ④ 步：门禁为什么**没有**加新规则，以及它到底靠什么承重

AGENTS §3.5 说收尾是"删旧的那份 + 加门禁"。这里加门禁的动作**没有**变成
`check-row-single-source.mjs` 里的第四条断言 —— 这不是漏做，是一个有理由的选择不，
理由要用实测说，不能只讲道理：

- **断言 A 已经在管这件事的上游**。它的判据是"任务行（复选框 + 标题 + 截止）的实现只有一份"，
  而 #10 那一刀改变的东西**全在这一棵子树里**：`TaskBadges` 是 `TaskRow` 渲染的，
  web 那份被删掉后行骨架只剩共享的一处。现存两道断言都过（`ht-*` 族 28 = 基线 28，未新增）。
- **但它对"第二份归属"结构上是瞎的**，这一点我实测过而不是推断的：
  断言 A 要求 ①勾选框 ②标题槽 ③截止槽 **三种信号同现**才算任务行。
  去 `apps/web/src/features/tasks/row-meta.tsx` 逐条 grep，命中的只有 ③
  （`DueBadge` / `renderMeta` / `dueAt` / `overdue`），**① 一个都没有** ——
  归属徽章天然不含复选框，所以任何"再写一份归属"的形态都凑不齐三信号，
  新规则要么写不成（没有稳定标记可认），要么写成"看到 `projectId` 就报错"那种
  会把设置页一起淹掉的噪音判据（该脚本文件头明确禁这种窄化失败）。
- **真正抓住重复的是那条按整行计数的判据**：本轮 F1 变异（把 `{list}` 渲染两遍）
  让断言 A 毫无反应，而 `apps/web/tests/row-meta-shared.spec.tsx` 里
  「归属只出现一次」为红（连同「空的徽章不占位」、E1/E2/E4 共 6 红）。
  加上移动端那两头的 E6/E7 源码级判据，**"只有一份"这件事是这三处一起钉住的**。

⇒ 所以第 ④ 步的交付是：**保留断言 A 对行骨架的钉，用 E6/E7 + 整行计数判据补它对归属的盲区**，
而不是给一个已知够不着的地方再加一条会永远变绿的规则（§7 元规则二：
一条永远通过的判据比没有判据更糟）。


每完成一条：本篇对应小节里落**证据**（实测数字、截图路径、变异验证结果），
台账那一行的"根因状态"和"状态"两列跟着改。不许只改状态不留证据。
