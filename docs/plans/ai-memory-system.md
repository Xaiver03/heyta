## 1. 先回答「该记住什么」：**从 AI 的行为倒推，不要从偏好本身想**

"该记住什么偏好"这个问题**没法直接回答** —— 偏好的种类是无穷的。
换一个问法，它立刻变得可解：

> **AI 现在会做哪些决定？其中哪些决定，如果我知道你的习惯会做得更好？**

一个东西值得被记住，当且仅当**它能改变一个具体的 AI 行为**。

### 1.1 四条判据（全部满足才进系统）

| # | 判据 | 为什么 |
|---|---|---|
| 1 | **改变行为** | 记住一个不改变任何行为的偏好，等于没记 |
| 2 | **今天就能推断**（或明确知道要装什么埋点） | 推断不出来的偏好是许愿 |
| 3 | **错了能纠正** | 偏好是**推断**，一定会错。用户必须能看见并改 |
| 4 | 🔴 **能被证伪** | 见 §5：不能预测任何东西的"偏好"必须删掉 |

### 1.2 偏好 → 行为对照表（这是判据 1 的具体化）

| 偏好 | 它改变哪个具体行为 |
|---|---|
| 你平均**低估**任务耗时 1.8× | AI 给出的时间估计自动校准 |
| 你的深度工作集中在 **8:00–11:00** | 建议把难任务排到上午，而不是平铺 |
| 你习惯**提前 3 天**开始有截止日期的事 | 提醒时机（而不是到期才提醒） |
| 你的拆解**偏好 3–5 个子任务** | 拆解不给你吐 20 条 |
| 你的命名习惯是「给 X 打电话」 | 捕获补全的说法更贴合你 |

**读法**：右边一栏写不出具体行为 → 这个偏好**不要记**。

### 1.3 🔴 明确不记的

| 不记 | 理由 |
|---|---|
| 情绪 / 心理状态推断 | 「你最近压力大」是**医疗化**的越界，产品没有资格说 |
| 健康 / 财务 / 人际关系的推断 | 即使能从数据推出来，**也不该推** |
| 任何**无法展示给用户**的偏好 | 判据 3 的直接推论：看不见就不能纠正 |
| 「用户是个拖延的人」这类**人格标签** | 偏好必须是**可操作的**，不是评判 |

## 2. 分水岭：**事实** vs **偏好**

这是整个架构里最容易搞错、也最重要的一刀。

`memory.ts` 已经落地的是**事实**。「记住偏好」要建的是**推断**。
两者性质**完全不同**，不能用同一套机制：

| | 事实（`memory.ts` 已有） | 偏好（本计划要建） |
|---|---|---|
| 例子 | 「这条任务被推过 6 次」 | 「你倾向把难任务推到下午」 |
| 来源 | op-log **直接算出** | 从事实**统计归纳** |
| 确定性 | 确定 | **概率性** —— 会错 |
| 可重建 | ✅ 可从 op-log 完整重建 | ⚠️ 取决于推断是否确定性 |
| 是否需要展示 | 不必（它只是事实） | 🔴 **必须**（错了要能改） |
| 错了的后果 | 小（只是数字） | **大**：一个错偏好会污染**每一次** AI 交互 |

> **结论**：偏好层不是事实层的延伸，是**另一层**，而且需要**完全不同的纪律**——
> 要带置信度、要有证据、要可见、要可纠正、要可证伪。

## 3. 架构：四层（**四层都已落地**）

```
op-log（全量事件，唯一真相）
   │
   ├─① 事实层   memory.ts（✅ 已有）      推迟/逾期/专注/落差
   │
   ├─② 推断层   preferences.ts（✅ M1–M4）统计聚合 → 带证据与置信度的偏好
   │
   ├─③ 应用层   preference-hints.ts（✅ M3）把偏好注入 prompt / 排序 / 默认值
   │
   └─④ 反馈层   ai-feedback.ts（✅ M4）    记录用户对 AI 建议的接受/修改/拒绝
                                            → 回灌 ②
```

### 🔴 3.1 第四层曾缺失 —— 现已补齐（M4）

**当时的核实结论**：`apps/web/src/features/ai/AiBreakdown.tsx` 不记录任何接受/拒绝信号，
`onApplyNote` 把 checklist 写进 note 就结束了。
**现在**：建议的接受 / 修改 / 拒绝经 `packages/domain/src/ai-feedback.ts` 落成
`AI_FEEDBACK` op（只记计数与枚举、不记内容），由
`packages/app-host/src/ai-feedback-actions.ts` 产生，回流推断 P6/P7。

后果曾很具体：**最有价值的两类偏好（拆解粒度、交互偏好）当时无法推断** ——
这正是 §4 要分批的理由：**先用今天就有数据的偏好证明这件事值得做，
再为更贵的偏好装埋点。** 反过来做，就是为一个还没被证明的价值建基础设施。

### 3.2 与既有分层的关系

推断层**必须落在 `packages/`**，不是 `apps/*`。
判据是 [ADR-0003](../adr/0003-multi-platform-strategy.md) 那条：
「这行代码在决定**业务上**要做什么吗？」—— 偏好推断决定 AI 该怎么做，**是业务**。
而且三端都要用（浏览器 / Hermes / Node），放 `apps/` 立刻三份实现。

⚠️ 但要注意：**浏览器端是 IndexedDB，没有 SQL**（`apps/web/src/lib/oplog.ts:61`）。
所以推断层必须是**纯函数**（像 `memory.ts` 那样），不能依赖 SQL 聚合。

## 5. 🔴 每条偏好必须能被证伪（沿用上次实验的纪律）

上一轮「要不要向量库」是用实验回答的（`docs/research/ai-memory-necessity.md`）。
**这里用同一套纪律**，否则我们会往系统里塞一堆听起来合理、实际无用的偏好。

### 5.1 每条偏好的输出必须自带三件东西

```ts
interface Preference<T> {
  value: T;              // 推断出来的偏好值
  /** 有多少条样本支撑它。样本太少 → 不许对外说话 */
  sampleSize: number;
  /** 0–1。低于阈值时，这条偏好**不参与**任何 AI 行为 */
  confidence: number;
  /** 证据：给用户看的原话（"基于 34 次专注，78% 在 8:00–11:00"） */
  evidence: string;
}
```

### 5.2 留出法验证（这是「可证伪」的具体做法）

对每条偏好：

1. 用**前 80%** 的 op-log 推断偏好
2. 用它**预测后 20%** 的真实行为
3. 与**基线**（不用偏好）比较

**验收判据**：预测准确率必须**显著高于基线**，否则这条偏好**删掉**。

> 这条规则会砍掉一些看起来很聪明的偏好 —— **那正是它的作用**。
> 一个不能预测未来的"偏好"，记住它只会让 AI 更自信地犯错。

### 5.3 ✅ 已实测（M2 完成）

实现见 `packages/domain/src/preferences.ts`，实验见
`packages/domain/tests/preferences-experiment.spec.ts`。

**协议**：train 80% / test 20%；每组各跑一次**有信号**数据与一次**纯噪声**数据。

| 偏好 | 植入 | 推断出 | 置信度 | 偏好 MAE | 基线 MAE |
|---|---|---|---|---|---|
| P1 估算偏差 | 1.80× | 1.83× | 0.77 | **3.43 分钟** | 24.46 分钟 |
| P2 深度工作时段 | 09:00 | 08:00–11:00 | 0.95 | **0.83 小时** | 3.08 小时 |
| P3 提前量 | 提前 3.0 天 | 提前 3.0 天 | 0.95 | **0.49 天** | 3.05 天 |
| P4 粒度 | 6 项 | 6 项 | 1.00 | **0.50 项** | 3.00 项 |
| P5 表达习惯 | 12 字 | 12 字 | 0.90 | **1.92 字** | 2.75 字 |

**五条全部优于基线，且五条在纯噪声数据上全部正确扣下（零误报）。**
P1 的改善最大（误差降到基线的 1/7）；**P5 最弱**（只降 30%），
但确实优于基线，故保留 —— 若将来线上数据显示它无用，应优先删它。

### 5.4 关于合成数据的诚实声明

⚠️ **上面这组实验只证明「方法有效」，不证明「真实用户身上有这些偏好」** ——
用的是合成数据（本仓库现在没有真实用户数据）。

### 5.5 冷启动必须诚实

新用户没有数据。此时：

- **不许编偏好**（不许用"平均用户"填充）
- AI 必须**明确表现出"我还不了解你"**，而不是假装懂
- 这也是产品机会：**"AI 正在了解你（还需要 N 次专注）"** 是诚实且可展示的

## 6. 隐私：偏好是**小样本、高语义密度**的东西

这是本计划**最需要警惕的技术风险**。

偏好的体积很小，但**语义密度极高**：「工作到凌晨 2 点」「总是推迟财务类任务」
「周五不安排深度工作」—— 这些话比一条任务标题更能刻画一个人。

所以：

| 约束 | 做法 |
|---|---|
| **在本机推断** | 推断层跑在客户端（op-log 本来就在本机），**不把原始事件发出去** |
| **出境的是摘要，不是原文** | 偏好就是压缩后的特征。原则：**发特征，不要发原文**。见 `ai-strategy.md` §2 |
| **最小化** | 一次只发**当前这个决定需要的那一条**偏好，不是全部偏好 |
| **可见可删** | 用户能看见全部偏好，并能**单条删除** |
| **不算明文派生物** | ✅ 偏好可从 op-log **确定性重算**（若推断层是纯函数）→ 不构成"多存一份派生物" |

🔴 **最后一条是设计约束，不是描述**：推断层**必须是纯函数**，
否则偏好会变成一份**不可重建、会漂移**的语义摘要 —— 与
[ADR-0005](../adr/0005-ai-data-path.md) 警告的「端侧明文派生物」是同一类风险。

## 7. 存储决策：推断**不持久化**，只有纠正需要落盘

| 方案 | 做法 | 评价 |
|---|---|---|
| A | 全部持久化 | ❌ 引入会漂移的第二事实源，且需 schema 改动 |
| B | **全部不持久化，每次从 op-log 重算** | ✅ 零 schema 改动、零漂移、天然可重建。**推断是纯函数，重算是毫秒级** |
| C | B + **只持久化用户的纠正** | ✅✅ **推荐** —— 纠正信息**无法**从 op-log 推出（它没有这个信息），因此必须落盘 |
| D | 新增实体类型进 op-log | ⚠️ 语义上最"正确"（纠正可同步），但要动 schema + 同步语义 |

**已实施的是 C。** 原建议是"先 B，第二步升到 C"，实际直接落到了 C：

- **B 的基线**：零 schema 改动（`CURRENT_SCHEMA_VERSION` 不动），
  推断是纯函数 → 放进 `packages/domain` → 三端免费复用。
- **C 的纠正信息**：走 op-log（`PREFERENCE_CORRECTION` / `AI_FEEDBACK`，可跨设备同步），
  且**不需要 bump schema** —— `applyOperation` 对未建模 `entityType` 静态忽略，纯可加性。
  决策见 [ADR-0014](../adr/0014-memory-switch-and-corrections.md) 与 §10。

## 8. 明确不做

| 不做 | 理由 |
|---|---|
| 让 AI **自动改**用户的设置/排序 | 偏好是推断，**推断不能直接改事实**。只能影响 AI 自己的建议 |
| 把偏好做成**黑盒** | 判据 3：看不见就不能纠正 |
| 用「平均用户」冷启动 | 见 §5.5，装懂比不懂更伤信任 |
| 一次性建全套偏好 | 见 §3.1，先证明价值再装埋点 |
| 为偏好引入**任何第三方依赖** | 纯统计 + 纯函数，标准库就够（也避开三端兼容问题） |

## 9.1 落地后记（2026-09-26）

**M3–M6 全部完成。** 实现过程中有三件值得记下来的事：

**① 加实体类型不是局部改动 —— 仓库有四处门禁会同时红，它们全都抓到了我的遗漏。**

| 门禁 | 漏了会怎样 |
|---|---|
| `packages/domain` 的编译期断言（`MODELED_ENTITY_TYPES`） | `typecheck` 直接红 |
| `packages/op-log/tests/entity-coverage.spec.ts` | 实体被**静默丢弃**：同步得到处都是，哪儿也不显示，也不报错 |
| `server` 的 `ALLOWED_ENTITY_TYPES.size` | 服务端**拒收**这两种实体 |
| `apps/mobile` 的实体中文名清单 | 冲突面板上出现 `AI_FEEDBACK` 这种英文代号，用户没法做选择 |

**② 逐条取舍不是 UI 装饰，而是 P7 能成立的前提。**
原来的结果是全有或全无，`appliedCount` 永远等于 `proposedCount`，
P7「保留率」恒为 1 —— 那条偏好会变成一句废话。

**③ 两处我自己写错、被测试当场抓住的地方**（都值得记，因为都是"注释说得对、代码没做到"）：

- `apply()` 里把 outcome **硬编码成 `'accepted'`**，而 `report()` 的注释却写着
  "三态由事实决定"。→ 去掉两条再写入会被记成"全部采用"。
- 「你已忘记」那一区最初用**纠正之后**的集合算，而被抑制的偏好已经不在里面 ——
  于是这一区**永远为空**，恢复按钮根本不出现：**用户删了就再也回不来。**

**④ P7 刻意不含「拒绝」**（如实留白，不是遗漏）。
拒绝的含义是歧义的：可能是"粒度不对"，也可能是"我根本不需要拆解"。
算成"保留率 0"会混淆两种信号、让这条偏好失去可解释性 ——
而不可解释的偏好没法给用户看，也就没法纠正。高拒绝率是一个**独立的**信号
（该不该用 AI），本轮不建模。

## 10. ✅ 已拍板（原「待拍板」）

两项都由产品负责人明确答复，落成 [ADR-0014](../adr/0014-memory-switch-and-corrections.md)。

**① 用户的「纠正」走 op-log。** 产品负责人原话：
「愿意动这个 Schema 的没关系。」

🔴 但实现时发现一个省事的点，已写进 ADR-0014 §3.2：
`applyOperation` 对**未建模的 entityType 静默忽略**，
所以新增 `PREFERENCE_CORRECTION` 是**纯可加性的** ——
旧客户端显示未纠正的推断值，不崩、不栅栏、不污染游标。
对照 `schema-version.ts` 的政策，这属于"旧客户端能未迁移地应用"
→ **不需要 bump `CURRENT_SCHEMA_VERSION`**。

**② 要总开关，默认关闭。** 产品负责人原话：
「需要有个总开关，**不然的话用户可能担心自己的隐私的问题**。」

| 项 | 值 |
|---|---|
| 默认 | **关闭** |
| 关闭时 | **零推断、零偏好、零出境内容**（返回空集，连 `withheld` 都为空） |
| 闸门位置 | `inferPreferences()` 入口 |
| 参数性质 | `memoryEnabled` **必填**，不是可选 |

🔴 **必填是刻意的**：本项目踩过一次 fail open 的坑 ——
`isReadable` 曾是可选参数、默认 `() => true`，于是"忘了传"等于"全部可读"。
隐私开关**绝不允许 fail open**，所以没有默认值，传错就编译不过。

> ⚠️ 主开关关闭的是**偏好推断**，不是"所有记忆"。
> 事实层（`memory.ts`）不受影响 —— 它只是本机数字，不出境、也不刻画人。

## 11. 风险

| 风险 | 缓解 |
|---|---|
| 偏好被当成事实（"AI 说我就是这样的人"） | 每处展示都带 `evidence` 与「这是推断」的措辞 |
| 样本少 → 自信地错 | `confidence` 低于阈值时偏好**不参与任何行为**（不是"低权重参与"） |
| 偏好互相矛盾（P2 说上午高效，P3 说总是拖到晚上） | 矛盾本身就是信号；**不许悄悄取一个**，要在界面上如实呈现 |
| 推断层变成不可重建的第二事实源 | §6 的纯函数约束 —— 违反它就必须写新 ADR |
| 做完没人用（本仓库已踩五次） | §9 M3 的验收判据锁定在「用户能感知」 |
