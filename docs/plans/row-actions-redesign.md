# 行操作（row actions）UX 重设计 —— 12 项 → 新结构

> 2026-11。产品负责人的原话（这是本单的全部理由）：
>
> > 「不需要有更多的三个点。你需要重新设计 UX，包括移动端、Web 端和桌面端，都需要重新设计。
> >  先看一下它是怎么排版的。」
>
> 第二轮口径（同日）：
>
> > 「这个在电脑端，也就是 Web 端，右键就好了。……移动端我记得还可以在这个任务上右滑，
> >  也就是从右边向左边滑，然后就可以删除，或者类似这种操作。」
>
> 本文件是**判决与对账**，不是下一步的愿望清单。实现落点在 §6，判据在 §7，
> 没做的与需要拍板的在 §9（**不藏**）。

---

## 1. 先摸清真身：那个「12 项竖排菜单」在本仓**不存在**

这是本单第一件必须说清的事，因为它决定了后面每一格怎么落。

产品负责人给的参照物（勾选 + 标题 + 一行淡元信息 + 一枚很小的「··· 更多」，
点开项数很少）是**对标产品**的形态；他描述的那 12 项
（`添加子任务 / 关联主任务 / 置顶 / 放弃 / 移动到 › / 标签 › / 开始专注 › /
创建副本 / 复制链接 / 打开便签 / 转换为笔记 / 删除`）是**这一类产品的一条任务行
应有的能力清单**。本仓的实际形状是：

| 端 | 行尾实际有什么 | 真身 | 现量 |
|---|---|---|---|
| Web | 一枚「⋯ **更多**」`<details>`，展开后是**九个同级控件**摊成一行：备注 / 子任务 / 清单+标签 / 重复 / 截止 / 提醒 / AI 拆解 / AI 估时 / 删除 | `apps/web/src/App.tsx` 的 `renderTaskTrailing`（改前 1468–1726 行），样式族 `.ht-compose-actions` | **9 项，无分组**，删除与"重复"同一视觉重量 |
| 移动 | 行尾只有**一枚删除图标**，其余字段全在 `TaskDetailSheet`（`BottomSheet`） | `apps/mobile/src/screens/TasksScreen.tsx` 的 `renderTaskTrailing` + `screens/TaskDetailSheet.tsx` | **1 项**（已经接近目标形态，但入口是"删除"而不是"编辑"） |
| 桌面 | 复用 Web 那一份渲染（Electron 壳） | `apps/desktop*/` 只注入壳 | 同 Web |

也就是说：**病在 Web 端那一格，形状是"九个同级命令 + 没有主次"**，与产品负责人的
描述（12 项、竖排、无分组、删除与置顶同重量）在**症候上完全一致**，在**项数上不一致**。
两者都不改结论 —— 判据是"重操作进一级菜单了没有"，不是"数到 12 没有"。

### 那 12 项逐项对账（依据是 `grep`，不是印象）

| # | 那一项 | 本仓有吗 | 真身 / 依据 |
|---|---|---|---|
| 1 | 添加子任务 | ✅ 有（同一枚 `setParent`） | `packages/app-host/src/actions.ts:337`；UI 是 `SubtaskPicker`（`<select>` 选父） |

| 3 | 置顶 | ❌ **不存在** | 全仓 `pin` 只命中纪念日（`web.countdown.pin` 等）；`Task` 实体无置顶字段，`actions.ts` 无此 op |
| 4 | 放弃 | ❌ **不存在** | `放弃` 只出现在专注中止（`web.focus.detail.aborted`）与浮层脏表单（`web.overlay.discard.*`）；任务无 abandoned 态 |
| 5 | 移动到 › | ✅ 有 | `actions.ts:321 moveToProject` |
| 6 | 标签 › | ✅ 有 | `actions.ts:357 setTags`（此前全仓零读写，是后来补的） |
| 7 | 开始专注 › | ✅ 有（但**不在行上**） | `packages/app-host/src/focus-actions.ts:115`；入口在专注屏，任务行上没有调用点 |

| 9 | 复制链接 | ❌ **不存在**（无任务深链） | 深链只有 `heyta://auth#…`（登录回跳），没有任务级 deeplink |

付过代价，方案 §5.5）。所以本单只处理**存在的那 6 项**，另外 6 项在 §9 登记为产品待办。

## 2. 诊断：那九项各自落在哪个"用户意图"里

依据是本仓自己的解剖结论（`docs/agents/ux-principles.md` §4「配置项默认收起」）
与"这件事一天要做几次"这两件事，不是审美。

| 改前 Web 行上那一项 | 用户意图 | 频率 | 性质 | 判定 |
|---|---|---|---|---|
| 备注 | 写内容 | 中 | **字段编辑** | 进详情面 |
| 子任务（选父） | 建立层级 | 低 | **字段编辑**（还要读候选列表） | 进详情面 |
| 清单 + 标签 | 归类 | **高** | **字段编辑**（下拉 + 复选框组） | 进详情面（**但可见性要留在行上**，见 §5） |
| 重复 | 设规则 | 低 | 配置 | 进详情面 |
| 截止 | 定日期 | **高** | 字段编辑（月历） | 进详情面（显示留在 `task-meta`） |
| 提醒 | 设提醒 | 低 | 配置 | 进详情面 |
| AI 拆解 | 一次动作 | 极低 | 动作（要披露/同意/结果卡） | 进详情面「自动化」组 |
| AI 估时 | 一次动作 | 极低 | 动作（写进备注） | 进详情面「自动化」组 |
| 删除 | 移除 | 低 | **危险** | 右键菜单的**危险区**（不与上面并列） |

一句话：**九项里八项是"字段编辑 / 配置"，只有一项是"动作"，一项是"危险"。**
把八项字段编辑器摊在一行上，等于让用户每次想改一个字段都要先看另外七个 ——
这正是产品负责人说的"一屏全是文字命令、没有分组、没有主次"。

## 3. 新结构（三端）

### 3.1 一级行上留几个 affordance

**零个新增。** 行本身就是入口（点行 = 打开详情），行尾**不再有任何按钮**
（既没有「⋯」也没有常驻三个点）。行上只留**只读**的痕迹：
备注徽标 / 子任务徽标 / 标签 chip / 重复 chip / 提醒徽标 + 共享元信息条（清单 · 截止）。

> 为什么徽标不一起删：`docs/plans/detail-pane-alignment.md` 的 §8.138 不变量是
> **"扫一眼要能看出哪些任务写过东西"**。徽标是只读的，不构成第二个编辑器所有者，
> 也不增加任何一项命令。删掉它们才是功能倒退。

### 3.2 那 12 项各自去哪里

见 §8 的完整表。一句话版本：

- **进详情面**（`TaskDetailCard`，两个落点）：备注、子任务/关联主任务、移动到、标签、
  截止、重复、提醒、优先级、AI 拆解、AI 估时、专注（见 §9 待办）；
- **进右键菜单的危险区**：删除；
- **删掉（不实现）**：置顶、放弃、创建副本、复制链接、打开便签、转换为笔记
  —— 前两项缺数据模型，后四项缺"有这个功能"这件事本身。

### 3.3 危险项走哪一档

**不手填，问 `resolveDangerTier()`**（`@heyta/domain`，`overlay-feedback.md` §2）：

```ts
const tier = resolveDangerTier({
  affectedCount: 1,
  undoAvailable: isUndoableDeletion('task'),   // 任务进回收站 ⇒ true，不手填
  collateralImpact: childCount,               // 直接子任务数（来自 buildTaskTree）
});
```

| 情形 | 档位 | 落成什么 |
|---|---|---|
| 没有子任务 | `undo` | **直接删** + 撤销回执（`UndoReceipt`，`check:undo-receipt` R2 要求）。不弹确认 —— "点两下删一条"是把成本转嫁给每一次正常操作 |
| 有子任务 | `popconfirm` | **就地二次确认**：第一下只把那一条换成「仍要删除」+ 一句后果（"它下面还有 N 条子任务，删除后它们会被提到顶层"），第二下才真删 |
| 批量删除（既有，不在本单） | 既有实现 | 不动 |

那句后果文案是**事实**，不是修辞：删除只给父任务写墓碑（`actions.ts:585`），
而 `@heyta/domain` 的 `buildTaskTree` 会把"父已删除"的子任务**提到顶层**显示
（`subtasks.ts` 文件头的 `promotedFromDeletedParent`）。

### 3.4 三端为什么不一样（每条一个理由）

| 端 | 主入口 | 键盘/无手势等价 | 必须保留的可发现入口 | 为什么是它 |
|---|---|---|---|---|
| **Web** | **右键**行（`contextmenu`，委托在 `.ht-content`） | `Shift+F10` / 菜单键 ⇒ **同一个**处理函数 | **点行 → 详情**（详情列，或窄档对话框） | 桌面列表的既有第一惯例就是右键；但它对触屏笔记本、纯键盘用户**不可达**，所以可发现入口必须是"点行"这条**人人可见**的路，而右键只是熟练用户的加速器 —— 删掉右键，功能一个都不少 |
| **桌面（Electron）** | 同 Web | 同 Web | 同 Web | 壳**复用同一份 Web 渲染**（`apps/desktop*/` 只注入 SQLite 驱动与窗口），所以它不是"顺手一样"，而是**同一份实现必然一样**；另加一条平台事实：macOS 的 control-click 与 Windows 的右键都由浏览器原生映射到 `contextmenu`，无需分叉 |
| **移动** | **长按**行 | VoiceOver / TalkBack 的"操作"转子（同一组动作） | 点行 → `TaskDetailSheet` | 长按是移动端"上下文菜单"的既有手势（iOS/Android 一致）；键盘与右键在这一端都不存在，所以不复制 Web 的形状 |
| **移动（第二入口）** | **左滑露出动作**（从右向左） | — | — | 滑动是列表删除的第一惯例，而它可以被**误触**：一次横向抖动不该毁掉一条任务。所以滑动**只露出**动作，点那一枚才执行；执行之后仍有撤销回执（`undo` 档），因为删除是进回收站的 |

🔴 **三端"不一样"的边界**：结构可以不同，**判断不许分叉**。危险档位三端都问
`resolveDangerTier`；关闭策略都问 `closePolicyOf`。差异只允许在
"用哪个手势/哪一层壳"上（`ux-principles.md` §9 的分工）。

## 4. 可发现性：右键不可达时不能掉队

这是本单最容易被做漏的一格，单独列出来：

| 用户 | 能不能用右键 | 他走哪条路 |
|---|---|---|
| 鼠标用户（大多数） | ✅ | 右键 → 菜单 |
| 纯键盘用户 | ❌（右键不可达） | 聚焦行 → `Shift+F10` / 菜单键；或直接回车进详情 |
| 触屏笔记本 / 平板 | ❌（长按会变成文字选择） | 点行 → 详情对话框 |
| 不知道有右键这回事的人 | ❌ | 点行 → 详情（**这是默认路径**，不是补丁） |

技术事实（写下来免得下次再争）：浏览器对 `Shift+F10` 与菜单键会在**当前聚焦元素**
上派发一个 `contextmenu` 事件，所以"键盘等价"不是第二套代码，而是同一个处理函数。
个别引擎不派发合成事件，所以宿主另外显式接了 `keydown`（`event.key === 'ContextMenu'`
或 `Shift+F10`）—— 那一条落空时用户看到的是"按了没反应"，属于最贵的一类失效。

## 5. 能力守恒：撤掉行尾编辑器之后，窄档怎么办

行尾那排编辑器不只是"太挤"，它同时是**窄窗口 / 详情列被收起**时**唯一**的编辑落点
（`App.tsx` 里 `taskPaneInColumn ? 徽标 : 编辑器` 那六组三目）。直接删掉 = 窄档下
"改截止 / 加提醒 / 挂标签 / 设重复 / 写备注"**整个消失**，而且不会报错。

所以本单同时做了第二半：**同一只 `TaskDetailCard` 的第二个落点**。

- 宽档：详情列（原样，`automationSlot` 注入 AI 那两格）；
- 窄档 / 栏被收起 / 日历这类没有栏的视图：`WebModalShell`（`modal-readonly` 策略）
  里的同一只卡片 —— 背景 / Esc / × 都是出口，因为这一层**没有"关掉就丢"的草稿**
  （每个字段改一次写一条 op）。

判据：`apps/web/tests/task-row-menu.spec.tsx` 的 **P5** 断言
`<TaskDetailCard automationSlot={automationSlotNode} />` 恰好出现**两处** ——
只有一处就意味着"另一个落点没了"，而那正是能力黑洞。

## 8. 12 项的**逐项去向表**（本单交付物之一）

| 项目 | 去哪 | 依据 |

| 开始专注 › | **不在一级菜单**；现状入口在专注屏（§9 待办：加进详情面「自动化」组） | 有 op，但它是"接下来要做什么"的入口，不是"这一条怎么改" |

| 打开便签 | **删掉** | 便签与任务无绑定关系；"打开"没有对象 |
| 转换为笔记 | **删掉** | 无转换 op，且两实体字段语义不同（便签无清单/截止/重复） |
| 删除 | **右键菜单的危险区**（移动端：长按菜单 + 左滑露出） | 危险项，按 `resolveDangerTier` 走 `undo` / `popconfirm` |

## 9. 没做的、以及需要产品拍板的

**没做（按重要性）**

1. **移动端**：长按菜单 + 左滑露出动作 + 删除入口归位。设计已定（§3.4），代码未改 ——
   本单按"先做一个端、跑绿再同步"的纪律，只落了 Web。
2. **桌面壳**：不需要单独做（复用 Web 渲染），但需要在 Windows/macOS 壳里各验一次
   `contextmenu` 的原生映射（control-click / 右键）。e2e 一跑就知道。
3. **e2e 改钉**：见 §7 的清单。这不是"测试要改绿"，而是被判对象合法消失。
4. **专注入口搬进详情面**：现在它只在专注屏。产品负责人把它列进了"重操作"，
   所以它不该在一级菜单 —— 但也得有一个"从任务开始专注"的路径，那需要
   `focus-actions` 的接线，不在本单范围。

**需要产品拍板**

1. **菜单只有两项，够不够**？本单的选择是**只留**「打开详情 + 删除」。
   如果嫌薄，唯一符合"重操作不在一级菜单"的候选是「**今天**」这类**零成本状态切换**
   （一次点击、无子面板、可撤销）。**不建议**把「移动到」提上来：它需要子面板，
   一提上来就把"一级菜单"变成"第二个行尾"。
2. **6 项不存在的能力要不要做**：置顶（要加字段 + op，属于 schema 变更）、
   放弃（要定义语义：与完成/删除的区别）、创建副本（要定义子任务的复制语义）、
   复制链接（要设计任务级深链与其权限）。这四项**都超出 UI 重设计**，需要单独的产品裁决。
3. **移动端左滑的方向与幅度**：本单采用"露出动作、点击执行"（不做全滑直删）。
   若要支持"滑到底即删"，那是另一档 —— 必须配撤销回执与"误触后能反悔"的证据。
