# 会员订阅：免费与付费的边界

> 状态：**产品决定（PM 定稿，待实施）**。价格与周期已按
> [ADR-0020](../adr/0020-ai-subscription-two-tiers.md) 更新为**月付两档**
> （旧的 `¥99 / 年`、`$49 / 年` **已作废**）。
> 本文件管的是**收费边界**：自建 / 托管 / 托管 + 我们的云端 AI，各自的用户拿到什么。
> 🔴 云端 AI 的**收费**归本文件；它的**计量与保留**归 ADR-0020 §3.5，
> 服务本体归 [ADR-0013](../adr/0013-cloud-ai-and-maas.md)（**仍未上线**）。

## 0. 先解决一个矛盾（这个矛盾不解决，后面全是错的）

[`README.md`](../../README.md) 第 3 行写着这个项目的立身之本：

> 一款**功能对标滴答清单（TickTick）**的任务 / 习惯 / 专注管理应用 ——
> 目标是不再为**高昂的订阅费**买单，并且**可以自建自托管**。

[`docs/plans/ai-strategy.md`](ai-strategy.md) §7.2.1 记下了对标产品的会员价：
**约 ¥139 / 年**。

🔴 **这两句话放在一起是自相矛盾的**：如果 heyta 也收 ¥139/年（对标的价），
那它就成了自己声称要取代的那个东西。

这个矛盾**不能靠改 README 解决**（那句承诺是这个项目存在的理由），
只能靠**把收费的对象选对**来解决。

> ✅ **新定价（ADR-0020）给了它一个可验算的答案**：
> 托管只要 **¥5 / 月（= ¥60 / 年）**，远低于对标的 ¥139 / 年；
> 含我们云端 AI 的 **¥12 / 月（= ¥144 / 年）** 比对标略高，
> 但 heyta 的**非 AI 部分永久免费、自建即全功能**，所以站得住（ADR-0020 §3.7）。

## 1. 决定：收费的是"服务器"，不是"功能"

| | 自建（免费） | `hosted-monthly` **¥5 / 月**（$5） | `hosted-ai-monthly` **¥12 / 月**（$12） |
|---|---|---|---|
| **应用本体**（全部功能：任务 / 四象限 / 习惯 / 专注 / 时间线） | ✅ 免费，MIT | ✅ 一样 | ✅ 一样 |
| **自带端点的 AI**（你自己的密钥） | ✅ 全功能 | ✅ 一样 | ✅ 一样 |
| **自托管同步**（你自己的服务器） | ✅ **免费，不校验** | 不需要买 | 不需要买 |
| **官方托管的同步服务**（我们的服务器） | ❌ **需订阅** | ✅ 可用 | ✅ 可用 |
| **我们的云端 AI**（`heyta-cloud`，300 次/月） | ❌ 不可用（用你自己的端点） | ❌ 不含 —— 得买 ¥12 档 | ✅ 可用 |

🔴 **「免费版」= 自托管，不是「官方托管的阉割版」。**
免费这条路是**完整的**，不是试用装 —— 它给你全部功能、不限设备、不校验。

**一句话：你付的是"我们替你运维服务器"（`hosting`）和"用我们的云端 AI"（`ai`），
不是"解锁功能"。** 收费清单上**只允许**出现这两件事，
**本地功能名出现在价格表里就是错的**（ADR-0020 §3.2、§3.4 第 1 条）。

⚠️ **`ai` 与 `hosting` 不是同一类东西，必须分开讲**：`hosted-ai-monthly` 买到的是
**我们的云端 AI** —— 请求要离开你的设备、在 heyta 的服务器上解开明文才能送模型
（ADR-0006 铁律 + ADR-0020 §3.4 第 6 条），所以文案里**不许**把它与同步那句
「我们看不到你的任务内容」讲在一起。**自带端点的 AI 完全不经过我们** ——
永久免费、永不计量、功能不减（ADR-0020 §3.4 第 2 条）。

⚠️ **两个付费项现在都还不能卖**：支付通道未接线（[ADR-0017](../adr/0017-single-paid-tier-and-payment-channel.md) §5）、
我们的云端 AI 服务本体还不存在（[ADR-0013](../adr/0013-cloud-ai-and-maas.md) §4 第 1 条）。
所以落地页上两档都必须是"**即将开放**"，**不许出现点了没反应的购买按钮**（ADR-0020 §4.3）。

### 为什么必须是这个切法

1. **技术上唯一诚实的切法。** 服务端只中转密文（E2EE by design），
   **我们看不见你的任务内容** —— 所以任何"按功能收费"的档位设计，
   我们**根本没有能力去执行**。能执行的只有"你连了几台设备、用了多少存储"。
   一个我们执行不了的定价表，迟早会变成一句空话。
   🔴 **但这条理由只对同步成立，对 AI 不成立** —— 我们的云端 AI 走
   `heyta-cloud`（请求要离开你的设备），我们**天然卡得住**。
   ADR-0020 的结构正是这句话：**不按功能分档（做不到，也不该做），
   把闸门放在唯一卡得住的地方（我们的 AI）**（ADR-0020 §1.3）。
2. **它和 MIT 不冲突。** MIT 允许任何人自托管 —— 你**不可能**靠许可证阻止
   自托管收费。与其写一个执行不了的条款，不如承认：自托管免费是**结构性的**，
   收费只能收在"我们提供的服务"上。
3. **它让免费版是真的。** 免费用户的出路不是"忍受阉割版"，而是
   **"自己跑一台服务器，拿回全部功能"** —— 这条路 README 已经承诺了，
   而且它永远开着。

### 🔴 修正：原先写的「免费 2 台设备」是错的

本文档早先版本写「官方托管免费给 2 台设备」。**这个额度是错的，已废弃。**

**错误在于：需要同步的人，恰恰就是有 ≥2 台设备的人。**

单设备用户**根本不需要同步** —— 同步的全部价值就是"把 A 设备的改动带到 B 设备"。
所以"免费给 2 台"实际等于**把产品白送给它最典型的用户**（手机 + 电脑，
这大概是绝大多数人的配置）。真正会付钱的是 3 台以上的人，而那是少数。

换句话说：那个额度的**筛选方向是反的** —— 它免费的是核心需求，收费的是边缘需求。

| 项 | 自建（免费） | `hosted-monthly`（¥5 / 月） | `hosted-ai-monthly`（¥12 / 月） |
|---|---|---|---|
| 同步设备数 | ✅ 不限（你自己的机器，你自己说了算） | ✅ 不限 | ✅ 不限 |
| 官方托管同步 | ❌ 不可用 | ✅ 可用 | ✅ 可用 |
| 服务端 op 保留 | ✅ 完整（不删，`subscription-boundary.md` 的硬约束） | ✅ 完整（不删） | ✅ 完整（不删） |
| AI（自带密钥） | ✅ 全功能 | ✅ 全功能 | ✅ 全功能 |
| 我们的云端 AI | ❌ 不可用（用你自己的端点） | ❌ 不含 | ✅ 300 次/月（**服务本体未上线，现在还不能卖**）|

**没有一个本地功能是被"阉割"的** —— 三列的差别只有两件事：
**那台服务器是谁在运维**（`hosting`）、**AI 请求走谁的网络**（`ai`，只有 ¥12 档有）。

## 2. 到期后的降级语义

**原则：到期不许变成"数据 hostage"。**

我们卖的是**两件服务**（`hosting` 与 `ai`），所以到期后**正确**的行为是：

| | 到期后 |
|---|---|
| **本地数据** | 🔴 **一个字都不动。** 本地优先是这个产品的底层承诺，付费状态**永远不许**影响本地可用性 |
| **已有数据（服务端）** | 🔴 **不删。** 降级 ≠ 删数据。删除用户数据当催收手段是勒索 |
| **继续同步** | 🔴 **停止（所有设备，不只是新设备）。** 我们不再替你中继 —— 这是你付钱买的那件事，停掉它是**唯一**合理的到期后果 |
| **我们的云端 AI** | 🔴 **停止**（`hosted-ai-monthly` 到期后不再受理新请求）。额度本来就是硬上限、**不自动扣费**（ADR-0020 §3.4 第 4 条）|
| **已接入的设备** | 同上下。但**不许静默**：界面必须明确说明"托管同步已停止 / 云端 AI 已停止"，并给出出路 |
| **出路** | ① 续费；② 🔴 **配置你自己的服务器 —— 立刻恢复同步，数据无损**；③ 云端 AI 的另一条路是**换成自带端点的 AI**（免费、不限次、功能不减，ADR-0020 §3.4 第 2 条）|

🔴 **到期唯一被停掉的就是"我们替你运维的那台中继"和"我们的云端 AI"。**
不是你的数据、不是你的功能、不是你的设备。特别是：**从托管切到自托管之后，
同步是立刻恢复的**，不需要"迁移"、不需要我们配合、不需要导出导入。

> ⚠️ 这条是硬约束，不是偏好。任何"到期就锁住你的任务"的实现都是**不可接受的**，
> 哪怕它转化率更高。

## 6. 一次性支付的授予语义（微信支付逼出来的决定）

### 6.1 问题

微信支付**没有"订阅对象"**。它的回调只说"一笔订单付成功了 + 金额"，
**没有订阅 id**。而阶段一恰恰是**一次性月付**（`hosted-monthly` ¥5 / 月、
`hosted-ai-monthly` ¥12 / 月，ADR-0020 §3.1）—— 周期只有 **30 天**，
续费频率比年付时代高一个数量级，"付了钱却没有权益"这个缺口只会更常被踩到。

已有的支付抽象层里留着这个缺口（`server/src/billing/apply-event.ts` 的
`NO_SUBSCRIPTION_REFERENCE` 分支有一个明确注释）。**按原实现，用户付了钱
却不会得到权益** —— 而这不是一个边界情况，在阶段一它是**主路径**。

这个缺口不是技术问题，是**语义缺失**：没有任何人规定过"一笔一次性付款
应该如何变成一段时长"。下面是这个规定。

### 6.2 决定

| 规则 | 内容 |
|---|---|
| **一行一用户** | `(userId, provider='wechat')` 对应**一行** `Subscription`，长期复用。`externalSubscriptionId` 为 `null`（微信没有订阅对象）。**不要每笔支付插一行** |
| **一次支付 = +30 天** | `currentPeriodEnd = max(now, 已有的 currentPeriodEnd ?? now) + 30 天`（`SUBSCRIPTION_PERIOD_DAYS = 30`，与 `wechat.adapter.ts` 的 `WECHAT_ONE_TIME_PERIOD_DAYS` 同值） |
| 🔴 **必须叠加** | 用户**提前续费不能丢失剩余时间** |
| **`status` = `active`** | 到期后**不做任何删除**（§2 硬约束） |
| **幂等键 = `out_trade_no`** | 商户订单号。同一笔订单重复回调**只能授予一次** |

🔴 **`max(now, 已有到期日)` 里的 `max` 是这套语义的核心。**

如果写成 `now + 30 天`：一个在到期前 **10 天**续费的用户，
本该拿到 `now + 40 天`，却只拿到 `now + 30 天` ——
**白白损失已经付过钱的那 10 天**。这种错误在开发期**完全看不出来** ——
只有真实用户提前续费时才暴露，而那时已经收了一批人的钱。

🔴 **周期从 365 天（年付，已作废）缩到 30 天，把 `max` 的另一个分支从边角情况变成了高频路径。**
年付时代"断档之后才续费"是少数；月付时代它**经常发生**（忘了续、支付通道抽风、
人在假期）。所以两条分支都必须有真实用例，缺一条就是收钱路径上的静默错误：

| 情形 | `max` 取谁 | 新到期日 | 为什么 |
|---|---|---|---|
| **未过期**（提前续费） | 已有的 `currentPeriodEnd` | `已有到期日 + 30 天` | 不吞掉用户已经付过钱的剩余天数 |
| **已过期**（断档后续费） | `now` | `now + 30 天` | 🔴 拿一个**过去**的到期日去叠加，会把新买的 30 天**部分埋进过去**，用户付了钱却立刻少一截 |

⚠️ 30 天周期下"提前续费"的窗口本身就窄（取决于到期前提醒发得多早），
所以**不能只测"未过期 + 续费"这一条** —— 断档续费在月付下才是常态。

反向也必须成立：**不同 `out_trade_no` 的两笔真实购买 = 两次授予**。
如果幂等键取错（比如取"用户 + 金额"），正常复购会被吃成重复。
**这两个方向的测试缺一不可。**

### 6.3 微信支付的技术事实（已核实）

- **Native 扫码支付**：`POST /v3/pay/transactions/native`，返回 `code_url`
  （是二维码内容，**不是跳转 URL** —— 抽象层的 `CheckoutResult` 用 `qrCode` 这一支）。
- **请求签名**：`WECHATPAY2-SHA256-RSA2048`，签名串 `method\nurl\ntimestamp\nnonce\nbody\n`。
- **回调验签**：验签串 `timestamp\nnonce\nbody\n`，**必须同时校验时间戳时效**（防重放）。
- **回调报文**：`resource` 是 **AES-256-GCM** 加密的，密钥为 APIv3 密钥。
- 🔴 **验签失败必须 fail-closed**：拒绝且**不落 `PaymentEvent`**。

### 6.4 🔴 不引入依赖

微信官方**没有 Node 服务端 SDK**（只有 Java / PHP / Go）。社区方案
（`wechatpay-axios-plugin` 等）是**第三方**的，要过 `AGENTS.md` §3.1 可维护性
与 §3.2 许可证两道门并登记进 `THIRD_PARTY_LICENSES.md`。

**本阶段不引入。** RSA-SHA256 签名/验签、AES-256-GCM 解密、随机 nonce
**全部用 `node:crypto` 手写**，HTTP 用内置 `fetch`。这是标准库能覆盖的范围，
为省几十行而引入一个第三方依赖不划算。

### 6.5 凭证（变量名，🔴 值绝不入库）

`WX_APP_ID` / `WX_MCH_ID` / `WX_SERIAL_NO` / `WX_API_V3_KEY` /
`WX_PRIVATE_KEY` / `WX_PUBLIC_KEY`

- 真实值只进**本地 `.env`**（已确认 `.env` 与 `server/.env` 都在 `.gitignore` 里）。
- `server/env.example` **只写变量名 + 占位符**。
- 🔴 提交前必须确认没有 `.env`、没有 `*.pem`、没有任何 base64 私钥被跟踪。

### 6.6 阶段一为什么用微信直连、不用聚合支付

用户有**公司营业执照**，微信支付可走**普通商户**。聚合支付（虎皮椒 / XorPay /
蓝兔 / 面包多 / 爱发电）虽然接入更快，但**有二清风险**，且对账多一层黑箱。
既然主体齐全，**直连更干净**。

支付宝排在微信之后（用户指定顺序）。
