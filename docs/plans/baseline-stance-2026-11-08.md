# 「不许抬基线」这句约束到底指什么：逐处核实

> 起因：我在前一轮里写过"行着色会改像素、会与'不许抬基线'冲突"。
> 那句话**没有核实过**，而它影响了一个"要不要做"的判断 —— 所以这一份把它查清。
> 结论：**这句话在这里被我误用了**。

---

## 1. 仓库里叫"基线"的门禁，量的都不是像素

| 门禁 | 基线指什么 | 有没有"像素/截图"基线 |
|---|---|---|
| `check:l4` | 内联 `style={{` 的**处数上限**（现在 74） | ❌ |
| `check:form-anatomy` | 每种形态的**处数**（`--reseed` 时重设） | ❌ |
| `check:breakpoints` | **落点数下限**（少于它说明扫描面坏了） | ❌ |
| `check:design` / `text-color` / `tokens` | **规则**，没有计数基线 | ❌ |
| `check:state-tiers` / `tag-resolution` / `persistence-keys` / `entry-table` | **账本/清单**，条目要与源码逐条对应 | ❌ |
| 四端重装 | 每端**当前产物判据**（内容占比、主蓝命中数） | ⚠️ 那是"这屏有没有真内容"的门槛，不是"像素一个都别动" |

`node -e "…filter(/visual|snapshot|baseline/)"` ⇒ 只有 `check:script-snapshot`
（那是 bash 脚本快照，与界面无关）。**本仓没有像素基线**。

## 2. 所以"不许抬基线"在那份目标里指的是什么

它连着后面两句一起读才成立：**"不许抬基线 / 不许改判据 / 不许改测试来变绿"**。
三句是同一件事的三个面孔 —— **不许为了让读数变绿去调松那把尺**。
它约束的是**判据**，不是**界面**。

⇒ 给界面加一条色条**不是抬基线**；把 `check:l4` 的 74 改成 78 才是。

## 3. 那我前一轮的判断错在哪

我写"行着色会与'不许抬基线'冲突、所以要等点头"——**第一半是错的**。
行着色真正需要的确认是**外观方向**（色条 / 淡底 / 圆点），不是"能不能动界面"。

**但结论（先不擅自动手）仍然成立**，只是理由要换：
`docs/plans/r11-states-audit-2026-11.md:448` 那句原话是"用**视觉回归**换一个……"
—— 本仓对"改界面"的既有纪律是**改动要能被看见并复验**（四端重装要重跑、
`check:l4` 的处数上限会动、每一行多一个节点），而不是"不许动"。

## 4. 修正后，行着色三态的真实门槛

| 门槛 | 是真的门槛吗 |
|---|---|
| 像素基线 | ❌ 不存在 |
| `check:l4` 处数上限 | ⚠️ **可能**：新加渲染代码若写内联样式会撞 74。但共享层本来就走 `StyleSheet` + token，**不写 `style={{`** ⇒ 大概率不动它 |
| 四端重装要重跑 | ✅ 是（改了界面就得验当前产物） |
| 外观方向（色条/淡底/圆点） | ✅ 是，且**只有产品能定** |

⇒ **做这件事的真实成本比我上一轮说的低**：没有像素基线要维护，
`check:l4` 大概率不动。真正需要点头的只有一件事：**外观长什么样**。
