# AI 能力分支与开发分支策略

- **状态**：**已落地**（AI-0 基座 / AI-1 捕获 / AI-2 拆解·优先级·估时 / AI-5 本机接口
  与记忆层都已实现且端到端可达；AI-3 规划、AI-4 复盘**有意推迟**。见 §9 的实施记录）
- **上游决策**：[ADR-0005 AI 能力的数据路径](../adr/0005-ai-data-path.md)（**已接受**，2026-09-26）
- **前置证据**：[AI 竞品与架构调研](../research/ai-competitive-and-architecture.md)
- **前置阶段**：P2 多端补齐（进行中）—— 本计划**不阻塞** P2，但 AI-0 需要 P2 的宿主抽象已就位
- **范围**：本文件只回答"做哪几条 AI 能力线、按什么顺序、用什么分支策略"。**不含排期数字。**

## 1. 先回答一个容易搞错的问题：这份计划里有几条其实不是 AI

产品负责人给了 5 条功能设想（§5 逐条裁决）。核对之后，**其中 3 条不是 AI 功能**：

| 设想 | 是不是 AI | 实际是什么 |
|---|---|---|
| 甘特图 | ❌ 不是 | 确定性视图：`(start, due, 层级)` 的投影，纯领域函数 |
| Time Left 式倒计时 | ❌ 不是 | 确定性视图：`(createdAt, dueDate, now)` 的投影 |
| API 调用 / 数据出口 | ❌ 不是 | 数据主权接口：不做推理 |

把它们塞进 AI 分支的代价是具体的：**AI 的隐私争议会拖累两个本来零争议的功能，而 AI 的排期会被两个本来今天就能做的视图拖住。**
所以本计划把它们放在**非 AI 分支**，并明确标注 —— 这不是降级，是让它们走更短的路。

## 2. 排序原则（从 ADR-0005 的约束推导，不是偏好）

| # | 原则 | 为什么 |
|---|---|---|
| 1 | **先做不碰数据模型的** | AI 输出必须能落进**已有**字段（`title` / `note` / `priority` / `important` / `dueDate` / `projectId` / `tagIds`）。要新字段的分支，同时叠加了"不可逆层改动"的风险，必须单独走 ADR |
| 2 | **先做数据面最小的** | 发送的明文越少，"AI 看得到你多少数据"越容易一句话说清（ADR-0005 §3.4） |
| 3 | **写入风险与数据面风险是两个轴，分开看** | 只读分支**不产生 op**（工程风险低），但可能**要读一批数据**（隐私风险高）。把它们混成一个"风险分"会同时误判 A3 与 A1 |
| 4 | **基座先于所有调用方** | 否则每个能力分支各写一份 provider 调用 —— 这正是 AGENTS.md §3.5 记录过**两次**的漂移形状（`SyncClient` 12 回调、任务 op 构造） |
| 5 | **无 AI 时功能仍须可用** | 自托管形态下"用户没配 Key"是**默认状态**，不是异常状态（ADR-0005 §4） |

## 3. 能力分支

命名用 `AI-<n>`；每个分支对应一个 git 分支前缀（§4）。

### AI-0 基座（Substrate）—— 所有调用方的前置

| 项 | 内容 |
|---|---|
| **做什么** | `packages/ai`：`AiProvider` 端口 + BYOK / 自托管两个后端（OpenAI 兼容 `fetch`，**不引厂商 SDK**）+ 输出 `zod` 校验 + 数据最小化载荷构造 + 发送前的隐私提示 UI + **分层门禁新规则** |
| **数据面** | 无（基座自己不发送任何东西） |
| **写入风险** | 无 |
| **依赖** | 无。但**两个 spike 必须先做**（见下） |
| **验收判据** | ① 注入一个违规文件（`apps/web` 里出现 `chat/completions`）后 `pnpm check:layering` **必须红**；② 无配置时所有 AI 入口呈"未配置"而非报错；③ provider 单测覆盖：超时、非 200、非 JSON、JSON 不符 schema、额度耗尽 —— 五种失败都要有**可区分的用户可见原因**；④ **出境披露**：发送前显示"发给哪个端点 + 发哪几个字段" |

#### 出境披露 UI —— 照抄 Apple 的范式（**子任务核实**）

**Apple 的「Apple Intelligence & PCC Report」是目前最完整的公开范式**：
设置 → 隐私与安全性 → 选时间范围 → **导出一个文件，列出所有离开设备并由 PCC 处理的请求**。
事前范式是 **Nextcloud Ethical AI Rating**（软件是否 FOSS / 模型可否自托管 / 训练数据是否公开）。

**heyta 应当两者都做，而且这是它的差异化位**（调研文档 §3.6）：
**没有任何产品把"只给当前这一条"命名为数据最小化策略并系统宣传** —— 未找到公开信息。
只有散落的具体做法（Google Magic Compose 只发 1 条草稿 / 前 20 条消息、
Home Assistant 让用户选暴露哪些实体并建议 <25 个、滴答清单搜索关键字仅本地）。

> 🔴 所以 AI-0 交付的不只是"一个 provider 端口"，而是
> **事前"发什么给谁" + 事后"可导出的出境日志"** 这一对能力。
> 前者是 AGENTS.md §5 的 UI 工作（必须走 token + 对比度测试），
> 后者是一个**本地可导出的记录**，与 E2EE 完全兼容。

🔴 **AI-0 的两个 spike —— 本次调研已把它们从"待做"变成"已答"，并产出两条硬约束**

| spike | 状态 | 结论 |
|---|---|---|
| S1 | ✅ **已回答，且改变了设计** | **原生端可直连（不受 CORS 约束）；Web 端架构上站不住** —— LLM Key 是 bearer 凭据，WebCrypto 防不住 XSS；Anthropic 需要 `anthropic-dangerous-direct-browser-access: true` 这个"名字就是警告"的头；OpenAI 的 CORS 支持不稳定（Responses API 已停止发送 ACAO）。**→ Web 端只允许"指向用户自己的 OpenAI 兼容端点"，不做粘 Key**（已落成 ADR-0005 §3.2.1） |
| S2 | ✅ **已回答，且是坏消息** | 🔴 **Hermes 缺 `WebAssembly`**（AGENTS.md §7 #26，真机实测，且无 polyfill）→ **`transformers.js` / `web-llm` 等 WASM 基座在 RN 移动壳上全部出局**；Apple `@Generable` 是捷径但 **Swift-only**。**移动端要做端侧推理 = 原生绑定工程量，不是装 npm 包** |

**因此 spike 分支的用途变了**：不再是"回答未知"，而是**验证落地方案**。
`spike/ai-s1-browser-cors` 与 `spike/ai-s2-rn-ondevice` 这两个分支**不再需要开** ——
结论已经在 `docs/research/ai-competitive-and-architecture.md` §3 里，且已写进 ADR-0005。

⚠️ **但 S2 留下一个仍未答的问题，值得单独开一个 spike**：
**原生绑定（llama.cpp / LiteRT-LM 的 JSI 模块）在 RN 0.84 + 鸿蒙上能不能拼起来？**
这是 ADR-0004 §5 同形状的风险，**且它是 P2 鸿蒙壳未完成的下游** ——
所以它不该在 AI 分支里解决，应挂到 P2。

spike 的产出是**调研文档的勘误/补充**，不是代码。

### AI-1 捕获（Capture）—— 第一条真正的 AI 能力

| 项 | 内容 |
|---|---|
| **做什么** | 一句话 → 结构化任务字段。三级降级：`chrono-node`（已登记、MIT、含中文）→ 规则未命中/低置信度 → LLM 出结构化 JSON（`dueDate` + `tz` + `rrule`）→ **允许用户纠正** |
| **落哪些字段** | `title` / `dueDate` / `priority` / `projectId` / `tagIds` —— **全部是已有字段** |
| **数据面** | 🟢 最小：**只有用户刚敲的那一句话** |
| **写入风险** | 🟢 低：一条任务 = 一个 op，走 `createTaskActions`（`packages/app-host/src/actions.ts`） |
| **依赖** | AI-0 |
| **验收判据** | ① **拔掉 AI 后功能不退化**（`chrono-node` 覆盖的高频表达仍全部可解析）—— 这是本分支最重要的判据；② AI 只被调用在规则未命中时（用计数断言，防止"每条都调模型"）；③ 解析结果与用户手动填写产生**同一种 op**（无 AI 痕迹进入数据） |

### AI-2 结构化（Structure）—— 拆解 / 建议

| 项 | 内容 |
|---|---|
| **做什么** | ① **拆解任务**：一个标题 → 若干可执行条目；② **象限/优先级建议**：逐条建议 `important` + `priority` |
| **🔴 降级实现（重要）** | **拆解结果先写进 `note` 的 Markdown checklist**，而不是真子任务。原因：`packages/domain/src/entities.ts` 的 `Task` **没有 `parentId`** —— 子任务模型不存在（见 §6 的仓库内不一致）。写 `note` 是**零模型改动**，今天就能做；等子任务模型落地后再升级为真树 |
| **数据面** | 🟡 一个任务的标题（+ 用户可选勾上的备注） |
| **写入风险** | 🟡 中：批量产生多条 op，**部分失败会留下半套** |
| **依赖** | AI-0；真子任务形态另需 `Task.parentId`（可选字段，AGENTS.md §3.3 允许）+ 单独 ADR |
| **验收判据** | ① **建议 → 确认 → 才落 op**（未确认时**不得**产生任何 op，用 op 计数断言）；② 批量分组用**可选 payload marker**（如 `batchId`），老客户端忽略它仍能正常同步；③ 中途失败可回滚或可重试且**不产生重复任务**（幂等）；④ 建议被拒绝后不留任何痕迹 |

> ⚠️ **不要做"自动重排优先级"。** 理由在 §5 第 2 条：重排会批量改 `order`，覆盖用户的手动排序，
> 而 AI 排程是用户最不信任的一类能力。**逐条建议**与**批量重排**的差别不是程度，是性质：
> 前者可解释、可撤销、一个 op；后者是把用户对自己清单的控制权交出去。

### AI-3 规划（Planning）—— 推迟

| 项 | 内容 |
|---|---|
| **做什么** | 今日计划、时间块建议、周计划 |
| **数据面** | 🔴 高：必须看一批任务与日程 |
| **写入风险** | 🔴 高：批量改期/排序 |
| **状态** | ⏸ **仍然推迟**，但**理由变了**：不再是"没有证据"，而是**证据说条件极苛刻**（见下）。前置条件仍是 AI-1/AI-2 有真实使用数据 |
| 🔴 **证据已补齐** | 竞品横向调研**已产出**：`research/ai-competitors/horizontal-validated-autosched.md`（16 个产品）。**结论见调研文档 §5.1** |
| 🔴 **证据给出的裁决** | ① **没有任何一个自动排程产品是"因用户嫌弃而下线该功能"的** —— 三个结局是 *acquihire（Clockwise）* / *被收购后预期崩（Reclaim→Dropbox）* / **主动拒绝做全自动（Sunsama）**；<br>② **最强负面证据来自竞品创始人**：Sunsama 联创称 Motion 用户"**spent more time correcting automated scheduling decisions**"；<br>③ **但反证同样真实**：ADHD / 时间盲人群与管理者获益，个人贡献者的深度工作受损 → **人群定位比算法精度更重要** |
| 🔴 **因此不许这样做** | **"全自动排程"不许当卖点**（调研推论 1）。若要做，**先做"锁"和"预览"，而不是"自动"** —— "锁"是**已被证实、未被满足**的需求（Sunsama roadmap 53+ 票、合并 4 条重复请求），实现成本远低于排程算法 |
| ⚠️ **但"锁"有一个具体陷阱** | 🔴 **不要用布尔锁 + 超时**：实测 **Motion 的 fixed 锁有 60 分钟超时** —— 用户以为钉住了，系统仍可能挪走它。<br>**heyta 若做 Lock，语义必须是"永久且明确"，不能是可过期状态。** 这与仓库既有纪律同形：**不要用会被静默改写的东西表达用户的明确意图**（对照 AGENTS.md §7 #19 墙上时钟裁决因果） |
| 🚫 **不要做的事（都有反面样本）** | 不要把"AI 搜索你自己的任务"当卖点（**零用户证词**）；不要让 AI 产物灌进日历主视图（Reclaim 差评 "I have 300 tasks that reclaim.ai created and now I cannot delete them"）；不要静默拆分长任务；不要写"AI 不用于训练"却在别的页面自相矛盾；不要把 AI 捆绑进涨价（Superlist："**AI features that no one asked for**"） |
| 🔴 **可复用的 12 个设计模式** | 调研 §5.1.4 逐条列了先例（预览/逐条确认、Lock/Pin、用户改动优先、可排程窗口、超额时提问、优先级由用户设定只决定"谁让位"、可解释性、不碰不是它创建的东西……）。**做 AI-3 时逐条对照，不要重新发明** |
| 🟢 **三处没有先例的空白** | ① **Undo 撤销自动重排**；② **排程解释 UI**；③ 🔴 **"任务留在 App 内，只有时间块进日历"** —— 用户诉求明确但无产品实现，且**对本地优先的 heyta 天然契合**。<br>**这三条是机会，不是待办** —— 但第③条若要排期，属于**视图工作而非 AI 分支** |
| ⚠️ **证据强度限制** | 该调研**全程无留存数据**（Reddit / Trustpilot / G2 全反爬），结论来自关停公告、融资公告、评分聚合与用户自述。**引用时必须带这个限制** |

### AI-4 复盘（Review）—— 受限分支

| 项 | 内容 |
|---|---|
| **做什么** | 周报、习惯趋势叙述、专注统计解读 |
| **🔴 与 ADR-0005 §3.4 冲突** | 它**必须读一批数据**才能总结，一旦发送就突破了"数据最小化" |
| **因此** | 它是**受限分支**：只能在端侧做，或由用户**逐次勾选范围**并明示"这 N 条将被发送"。**不得**默认开启 |
| **依赖** | AI-0 + 端侧推理（ADR 选项 B）可用 |
| **验收判据** | ① 默认关闭；② 发送前显示**具体条数与范围**；③ 不发送 `note` 正文（只发标题与元数据）——除非用户逐条勾选 |

### AI-5 接口 / 数据主权（Interface）—— **不是 AI 分支**

| 项 | 内容 |
|---|---|
| **做什么** | ① 全量导出（JSON/CSV/ICS，已有 P0 计划）；② **本地 API / MCP server**，让用户拿**自己的** AI 客户端接进来 |
| **为什么不算 AI** | 不做推理、无模型、无 prompt、无幻觉、隐私面为零，且**在没有 AI 的今天也有独立价值**（备份、自建看板、迁移） |
| **数据面** | 用户自己的机器/网络，不经过我们 |
| **依赖** | **无**（与 AI-0 解耦）→ **可以第一天就并行开工** |
| **验收判据** | ① **所有写入都走 `dispatch()`**，不得直接写库（否则 op-log 纪律破掉、改动不同步）；② 默认关闭 + 显式 token；③ 权限范围可限制（只读 / 可写）；④ 明文出口有明确告知（客户端已解密的数据流向用户自己的工具） |

**已验证的依赖**（本机实测，2026-09-25）：

| 组件 | 版本 | 许可 | 最后发版 | 结论 |
|---|---|---|---|---|
| `modelcontextprotocol/typescript-sdk` | 1.30.1 | **Apache-2.0**（原文含 MIT→Apache 过渡声明，两者都在白名单） | 2026-09-23 | ✅ 两道门通过 |

> 该包的 GitHub 许可证字段是 `NOASSERTION (Other)`，**照字段判断会误判为"无授权"**。
> 已读 `LICENSE` 原文确认：MIT → Apache-2.0 过渡，新贡献 Apache-2.0，旧贡献仍 MIT。**两者都允许。**

🔴 **按 2026-07-28 的无状态规范设计，否则会返工**（**子任务核实**）：
该版本是 MCP 最大一次破坏性修订 —— **移除 `initialize` 握手与 `Mcp-Session-Id`**、
新增 `server/discover`、**强制 `Mcp-Method` / `Mcp-Name` 头**、Tasks 降级为扩展、
Roots / Sampling / Logging 弃用。MCP 已于 2025-12-09 捐给 Linux Foundation 的 **AAIF**。

🔴 **安全必须设计进去，不能事后补**（**子任务核实**）：
**Tool Poisoning**（Invariant Labs 2025-04）、
**MCP Inspector 未认证 RCE（CVE-2025-49596，CVSS 9.4）**、**rug pull**；
**NSA 建议签名并校验 MCP 消息**。

**三条同行先例可直接照抄**（**子任务核实**）：

| 先例 | 内容 |
|---|---|
| **Todoist MCP** | 官方 CLI 把 token 存**操作系统凭据管理器**；提供 **`--read-only`** 标志 |
| **ClickUp MCP** | **仅 OAuth，明确不支持 API key** —— 对鉴权选型是直接先例 |
| **Anytype Local API** | 完全 localhost / 完全离线；4 位挑战码换 bearer key；可生成与吊销多个 key；且**官方在页面顶部明确警告**"提供 API key 即授予 vault 访问权，请只用可信扩展" |

> 第 3 条尤其值得学：**把"你在授权什么"写在用户读到 API key 的那一屏**，
> 而不是写在文档里。heyta 的验收判据④应当照此强化。

🔴 **同行验证了这个顺序**：滴答清单的 AI 是 **2026-04 先上 MCP + CLI（把 AI 放在产品外面），
2026-09 才上内置 AI 助手（放进产品里面）** —— 见调研文档 §1.4。
所以 AI-5 **不是"AI 的边角料"，而是这个行业里被验证过的第一步**；
而且它是本项目里**唯一与 E2EE 零冲突**的那条路。

## 4. 开发分支策略

### 4.1 分支模型

```
main（保护；全部门禁必须绿）
 ├─ spike/ai-s1-browser-cors          ← 只产出调研结论，不合并代码
 ├─ spike/ai-s2-rn-ondevice           ← 同上
 ├─ feat/ai-0-substrate               ← 冻结 provider.ts 之后才允许下面开工
 │    ├─ feat/ai-1-capture
 │    ├─ feat/ai-2-structure
 │    └─ feat/ai-4-review（受限，需端侧）
 └─ feat/ai-5-interface               ← 与 AI-0 解耦，可并行
```

| 规则 | 内容 | 为什么 |
|---|---|---|
| **命名** | `feat/ai-<n>-<slug>`；一次性验证用 `spike/ai-<slug>` | 与分支编号一一对应，评审时不必猜这条线属于哪个分支 |
| **spike 不合并** | spike 分支的产出是**文档**（调研勘误），代码全部丢弃 | 否则"验证用的临时实现"会变成事实标准 —— 这正是要避免的 |
| **串行点只有一处** | AI-1 / AI-2 / AI-4 **都必须在 AI-0 合入后**才能开工 | 否则每个分支各写一份 provider 调用。AGENTS.md §3.5 记录过两次同形状漂移，代价是**移动端点"新建任务"就抛异常** |
| **并行面** | AI-5 与 AI-0 **无依赖**，第一天就能并行 | 它的价值独立于 AI，串行排队是纯浪费 |
| **不要长命 umbrella 分支** | 禁止 `feat/ai` 这种把全部 AI 工作放一起的长期分支 | 长期分支必然漂移；每个 AI 分支都应能**独立合入、独立可用** |
| **`packages/ai` 的冲突面** | `provider.ts` 在 AI-0 合入后**冻结**；每个能力分支只碰自己的子目录（`tasks/<capability>/`） | 让 N 个分支改同一个文件的唯一结果是 N 份 merge 冲突 |
| **模型改动不在本计划内** | 任何分支**不得**新增实体类型或必填字段。需要就另写 ADR | AGENTS.md §3.3：给持久化模型加必填字段会**静默炸掉每一个已有安装** |

### 4.2 为什么不需要 feature flag 基础设施

AI 功能**天然是暗的**：没配置推理端点时，provider 就是"未配置"，入口显示引导而不是功能。

> 这比引入一套 flag 系统更好 —— 少一个依赖、少一处状态、少一种"flag 组合"的测试矩阵。
> 但前提是 AI-0 的验收判据②真的做到（无配置时**不报错**）。若做不到，就会退化成"用户看到一堆坏掉的按钮"。

## 5. 对 5 条功能设想的逐条裁决

| # | 设想 | 裁决 | 理由（一句话） | 落在哪 |
|---|---|---|---|---|
| 1 | AI 拆解任务 | ✅ **采纳，但先降级** | 子任务模型不存在（`Task` 无 `parentId`）→ 先写 `note` 的 Markdown checklist（零模型改动），子任务模型落地后再升级 | AI-2 |
| 2 | 优先级排序 | ⚠️ **改判为"逐条建议"** | 不做自动重排：批量改 `order` 会覆盖用户手动排序，且 AI 排程是用户最不信任的一类；改为建议 `important` + `priority`（已有字段，可解释、可撤销） | AI-2 |
| 3 | 自动生成甘特图 | ❌ **否掉"AI"，改判为"时间线视图 + AI 估时"** | 🔴 **滴答清单自己就没有甘特图** —— 官网原文：Timeline View 是 "a lighter project management tool **compared to Gantt charts**"。甘特图**不需要 AI**（是确定性投影，"自动"是渲染问题）；但时间线**需要 `duration` 字段**，而 `Task` 没有。→ **AI 的正当位置只有一处：从标题估工期**（写一个可选字段）；图表本身是确定性渲染 | 视图（非 AI）+ AI-2（只估时） |
| 4 | Time Left 式倒计时 | ⚠️ **采纳为视图，但降级——不是已被验证的机制** | **不是 AI，是视图**：隐私面为零、无模型、无依赖，`createdAt → dueDate` **两字段今天就有**，**成本低、可回退、可 A/B** → 仍该做。<br>🔴 **但原判"不是追平，是差异化"已更正**：滴答清单**有任务列表 countdown mode**（`Task time` ↔ `Countdown Time`，把 "Due Wednesday" 变成 "还剩 2 天"，Google Play **4.6★/164,748 条**），**任务级倒计时不是空白**。<br>🔴 **且反面证据很硬**：**32 个实验的元分析**发现前期投入感高时进度条**反向降低完成率**，而"线性递减"正是这个形状；**无任何 RCT** 检验过本场景。→ **不得宣称能治拖延；必须先定 A/B 指标** | 非 AI（视图） |
| 5 | API 调用（回传云数据） | ⚠️ **改判** | 作为**数据可携带性**功能（导出/本地 API/MCP/用户自有端点）结论不变 —— 那条"回传"是让用户把自己的数据拿走。🔴 但 ~~"不做官方云中转"~~ 已作废：**托管 AI**（内容送 heyta 云做推理）是另一件事，已由 ADR-0013 确认要做，作为显式例外 | AI-5 |

### 5.1 第 3 条为什么"不是 AI"——同行给了最硬的证据

滴答清单官网对 **Timeline View** 的原文描述：

> "The timeline view is **a lighter project management tool compared to Gantt charts**.
> Tasks are displayed according to their **set durations**, allowing you to see how long each task
> will take at a glance. You can also easily **adjust task durations or start times by dragging**."

三件事同时被这句话证实（来源：`docs/research/ai-competitive-and-architecture.md` §5）：

1. **滴答清单主动选择了"比甘特图更轻"** —— 它不做甘特图，也不做依赖关系。
   这与 `docs/research/feature-matrix.md` §11"甘特图是另一条赛道"的判断一致。
2. **时间线的输入是 `duration` + 起点**，而 heyta 的 `Task` **两者都没有**
   （`packages/domain/src/entities.ts:64-82`：无 `startDate`、无 duration）。
   → 所以这条的瓶颈是**数据模型**，不是 AI。
3. **`Task Duration` 与 `Timeline View` 在滴答清单都是 Premium 功能** ——
   说明这是一个"愿意付费"的能力，值得做。

**因此裁决是**：做**时间线视图**（确定性、无依赖图、无 AI），
AI 只用在唯一正当的位置 —— **从标题估算工期**，写进一个**可选**字段（AGENTS.md §3.3 允许的形状）。

> ⚠️ 但 `duration` / `startDate` 属于**不可逆层**（持久化字段 + 可能的 schema 语义），
> **必须先确认产品是否真的要做时间线视图**，再动模型。**不要为了"顺手让 AI 能估时"而加字段。**

### 5.2 第 4 条的具体设计约束（它今天就能做，所以值得写细）

「Time Left 式倒计时」的**模型侧已经够用**：

| 需要 | 现状 |
|---|---|
| 终点（截止） | ✅ `Task.dueDate` |
| 起点 | ⚠️ **`Task.startDate` 不存在** → 用 `Task.createdAt` 兜底（`EntityBase` 提供，一定有值） |
| 当前时间 | 运行期 `now()` |

🔴 **更正：与滴答清单的关系比我原先写的更近。** 我在初稿里写它的是"倒数纪念日"、
"不是任务级进度条"——**这个说法不完整**。滴答清单**有两种**：① 倒数纪念日（独立实体，
Free 5 个 / Premium 299 个）；② 🔴 **任务列表的 countdown mode** —— 视图可在
`Task time` ↔ `Countdown Time` 之间切换，把 "Due Wednesday" 变成 "还剩 2 天"。
**这就是任务级倒计时**，且 Google Play **4.6★ / 164,748 条评论**、ZDNET 专文推荐。

→ **所以"任务级倒计时"不是空白，它是这个品类里唯一有规模证据的成功案例。**
heyta 的差异只在**形态**：我们想做的是 `createdAt → dueDate` 的**递减进度条**，
它只显示**剩余时间**、不显示**进度**。**而这个差异恰好是有反面证据的那个形态。**

🔴 **而独立产品重注这个形态的全部没做起来**（**子任务核实**）：
`Time Left`（2014 年钟面式任务管理器）**已死，2 条评分**；
Deadliner（明确写着 circular progress bar）存活 6 年但**只有 2 条评分**；
Deadline App 63 条 / Griply 197 条 / Deadline Bar **0 条**。

#### 5.2.1 🔴 反面证据（这一节必须先读，再决定要不要做）

| 证据 | 内容 | 后果 |
|---|---|---|
| 🔴 **32 个实验的元分析** | 当"前期投入感高"时，进度条**反而降低完成率** | **"从 `createdAt` 线性匀速递减"正是这个形状** |
| 🔴 **Bisin & Hyndman（NBER w19874）** | 人们**强烈想要** self-imposed deadline，**但 deadline 并没有提高完成率** | "加个倒计时就能治拖延"**站不住** |
| 🔴 **Bonezzi et al. (2011)** | 动机随进度呈 **U 型**，**中点（50%）最低** | 倒计时条恰好把注意力压在中段 |
| ⚠️ 框架效应 | "剩余"vs"已完成"会改变动机方向 | 文案/朝向不是中性的 |
| ✅ **最大缺口** | **找不到任何 RCT / A-B 检验"任务加倒计时条 → 完成率提升"** | **它是假设，不是机制** |

支持性机制证据确实存在（时间折扣预测拖延、目标梯度效应、禀赋进度、Zeigarnik 效应、
ADHD 视觉计时器，以及用户原话 "seeing 3 weeks left motivates me more than a date out on a grid"），
**但要么停留在机制层，要么场景完全不同**（洗车集点卡、问卷进度条）。
反面用户原话也真实存在：*"I don't have any use for it other than the widget looking nice on my lock screen"*。

🔴 **因此附加三条强制约束**（在下面那条设计约束之上）：

1. **不得对外宣称它能治拖延。** 它是"可测量的 UI 假设"，不是"拖延症友好"的承诺。
2. **必须先定 A/B 指标再上线** —— 否则无法知道它**是否有害**（元分析说的是可能反向）。
3. **不做成核心机制**，也不要因为"用户提了"就跳过验证。
   > 这一条正好是 CONTRIBUTING.md 的评审顺序：**先问"该不该做"，再问"做得对不对"。**
   > **用户提的需求 ≠ 已验证的需求**，而"用户提了 + 成本低"正是最容易跳过验证的组合。

设计约束（全部来自 AGENTS.md §5，不是审美偏好）：

- **`tabular-nums` 必加** —— 倒计时数字宽度不跳
- **紧急度不能只用颜色表达** —— 色盲用户与暗色主题都要能读；颜色是冗余通道，不是唯一通道
- **必须尊重 reduced-motion** —— 持续动画的紧迫感对部分用户是焦虑源，不是动力
- **必须可关闭** —— 拖延症友好 ≠ 强迫所有人接受焦虑
- **移动端要控制刷新频率** —— 每条任务每秒重绘在移动端是电量问题；按分钟粒度 + 临界点加速

### 5.3 一句话总结这 5 条

> **意图都成立，但顺序必须由数据模型决定，而不是由"哪条听起来更 AI"决定。**
> 最便宜的两条（倒计时、逐条优先级建议）今天就能做；最贵的一条（甘特图）其实不是 AI 问题而是数据模型问题；
> 而"回传云数据"这一条**必须改判**，否则与产品的核心承诺自相矛盾。

| 支持 | 相对日（今天/明天/后天/大后天/昨天/前天/N天后）、周几（周/星期/礼拜 × 下周/本周/裸）、绝对日（`M月D日`/`M月D号`/`YYYY-M-D`/`M/D`）、优先级（`!1..!4` / `p1..p4`） |

**三条被测试钉住的不变量**（都是"下一个人会顺手改掉"的那类）：

1. 🔴 **不存在"没被采纳却被移除"的片段。** 每个被移除的片段都对应一条 `applied: true` 的匹配。
   理由是中文没有词边界 —— 误报是结构性的（"明天启程"里的"明天"），
   **静默删字与 AGENTS.md §7 #20 是同一种失败形状**。
2. 🔴 **未被采纳的匹配必须显式标出**（UI 上写"未采用，仍在标题中"），
   否则用户会以为它生效了，而不知道那几个字其实原样留着。
3. 🔴 **"忽略"不等于"删除"。** 用户点忽略时，那段文字**回到标题里**
   （`options.exclude` 让规则不再认领它），而**不是从输入框里消失**。
   > ⚠️ 第一版实现写错成"从输入框删掉" —— 那会真的丢掉用户写的字。
   > **是界面测试把它抓出来的**（`capture-composer.spec.tsx`），纯函数层的绿灯完全没暴露它。

**踩到并修掉的一个运行时陷阱**：`M/D` 规则原本用 lookbehind（`(?<![\d/])`）做边界。
**已改为手写字符检查**（`isDigit` + 前后字符比对），理由与 AGENTS.md §7 #26 同源：
Hermes 的正则能力**落后且有版本差异**，而 lookbehind 正是其中一项。
本项目已经因为"假定某个运行时能力存在"付出过一次代价，**不再假定第二次**。

### 9.5 ✅ 已落地：`packages/ai` —— 两种供给模式 + 出境闸门

> 📌 **上面那句"尚未落地"已过期：本包在同一天随后就建好了。**

新增包 `packages/ai`（**零运行时依赖**，47 条测试）。它把
[ADR-0006](../adr/0006-supply-modes.md) 的产品决策变成了可执行、可测试的东西。

| 文件 | 内容 |
|---|---|
| `src/supply.ts` | 供给模式（`off` / `own` / `managed`）+ **目的地由端点推导**（不由模式声明）+ 诚实隐私文案 |
| `src/egress.ts` | 出境闸门：授权**绑定在 `(功能, 目的地)` 上**；切模式时删除失配授权 |
| `src/provider.ts` | 唯一端口。OpenAI 兼容 HTTP，**只产出建议，类型上无法产出 op** |

**四条被测试钉住的关键设计**：

1. 🔴 **目的地由端点推导，不由模式声明。** 用户自备 + `localhost` 端点
   → 目的地是 `none`，**明文没出设备、不需要授权**。
   把"自备"当成一个整体会丢掉这个最重要的区别。
2. 🔴 **授权绑定在 `(功能, 目的地)` 上**，目的地一变就失效；
   且切换模式时 `retainValidConsents` 会**删除**失配的旧授权 ——
   这是"用户同意了 A、系统做了 B"那类事故的止血点。
3. 🔴 **文案不许宣称托管模式是 E2EE**，且**必须主动否认**。
   测试断言：托管文案**必须**含"不受端到端加密"这个确切否定，
   把该句挖掉后**不许残留**任何"端到端加密"字样。
   **已注入违规验证能失败**（改成肯定语气后 2 条测试变红）。
   > 这条测试第一版写反了 —— 它把整个短语都禁掉，于是连**诚实的否定**也一起禁了。
   > 约束是"不许**宣称**"，不是"不许**提及**"。**含糊其辞才是问题。**
4. 🔴 **托管模式当前无法启用，是刻意的。** 它的数据保留策略尚未定案，
   `describeRetention('heyta-cloud')` 返回 `undefined`，`assertEnableable` 因而抛错。
   **产品没想清楚"托管 AI 的数据留多久"之前，谁也没法把它打开。**
   > 这比写一句"待定"强：错误会在**配置那一刻**发生，而不是在用户已经上传了任务之后。

**同时照抄了 Joplin 的 `.local` 判断**（见 ADR-0006 §2.4）：
`isLoopbackEndpoint` 只信字面回环，**局域网主机名一律按远程处理** ——
理由是 **mDNS 名字可以指向当前网络里的任意主机**，它并不能证明"这是你这台机器"。

### 9.10 把 `invokeRouted()` 接上第一个真实调用点：暴露了什么

在 `ai-breakdown.ts` 之前，`packages/ai` 有 95 条测试但**零个生产调用点**。
那种状态下每层单独都对，接起来不对却没人知道。接上之后立刻暴露三个问题：

| # | 问题 | 性质 |
|---|---|---|
| 1 | 设置面板**无法声明能力** → `breakdown` 永远没有路 | 🔴 功能不可达（ADR-0010 §3.4.1） |
| 2 | `TaskActions` **没有 `setNote`** → AI 输出无处可落 | 🔴 缺一个动作，不是缺一个字段 |
| 3 | `parseBreakdownItems` 不认 `2、乙`（顿号后无空格） | 解析漏项（中文写法） |

第 1、2 条都不是"某层写错了"，而是**层与层之间缺一段**。
这就是"没有消费者就没有集成测试"的代价 —— 95 条单测一条都抓不到它们。

⚠️ 注入验证里有一条**没能被干净抓住**，值得记下：
把 `requestBreakdown` 的 `consents` 注入成 `[]` 时，"没有授权就不发请求"
那几条测试**依然是绿的** —— 因为丢掉授权会让远端端点**更加**进不去，属于 fail-closed。
只有"正确授权 → 应当跑通"的测试能抓住它。
这不是测试缺陷，而是这个设计的性质：**闸门失效的方向是"更严"而不是"更松"**。

### 9.11 ⚠️ 事故：注入验证写坏了开发者的登录钥匙串

做"关闭控制字符检查"这个注入时，含换行的密钥走进了 `security -i`。
`-i` **逐行**读命令，那一行在换行处断了，**尾部的临时钥匙串参数被切到下一行**
—— 命令落到默认（登录）钥匙串，留下一条垃圾记录。**已删除，钥匙串现已复查为空。**

根因不是"代码写错了"（那次是故意注入的），而是：

> **测试的安全性依赖被测代码正确。** 那是错的 ——
> 测试必须在代码坏掉时也伤不到开发者的机器。

修法是在测试里加护栏：任何一次 `security` 调用，若**将被执行的那一行**里
没有临时钥匙串路径，就当场抛错、不执行。

⚠️ 护栏第一版**自己也有 bug**：它检查整个 stdin 字符串，而路径确实在字符串里
—— 只是不在**第一行**，所以没拦住。改成只看首行后重放同一注入：
**测试照样红，钥匙串干净。**

> 这类错误在本仓库已经出现**三次**（假注入、注入错位置、护栏自身有洞）。
> 共同形状：**验证手段本身没有被验证。**

### 9.12 披露为什么必须是独立的一步

本轮实现 AI 拆解入口时，把流程拆成了：

```
点击 → [披露：发给谁 + 发哪些字段] → 用户按发送 → 提议 → 用户按确认 → 写入备注
```

**披露不能合并进"发送中"或"发送后"的提示** —— 那样用户已经没有机会反悔了。
所以界面上它是一块**独立的面板**，并且有测试断言：
点「AI 拆解」之后**一个请求都不能发出去**（`calls` 长度为 0）。

同样地，AI 的输出不在拿到时自动落库，必须用户再按一次。
这与 `AiSuggestion` "类型上不能变成 op" 是同一条纪律的两端：
**类型上做不到，界面上也不做。**

### 9.13 假 fetch 证明不了的事

集成测试用假 fetch，能证明"我们发出的请求形状对"，
**证明不了真模型会不会按我们要求的格式回话**。
提示词里写了"每行用「- 」开头、不要前言"—— 这件事只有真跑才知道。

所以加了 `pnpm verify:ai-breakdown-live`（没配端点时跳过并退出 0）。
实测结果：真实模型回得**很干净**，7 项全部可直接用，
没有前言、没有残留标记。14 项断言全过。

⚠️ 同时它**再次复现了那个日期幻觉**：`verify:ai-live` 里
模型对「明天下午三点」返回 `2026-05-08T15:00:00`（正确是 2026-09-27）。
这是"LLM 做得最少"原则的实测依据，不是猜测。

### 9.14 真实子进程补上了"没有真实 MCP 客户端"的缺口

之前所有 JSON-RPC 都是**自己发给自己**的。本轮加了 `mcp-stdio-e2e.spec.ts`：
真的 `spawn` 一个子进程，用管道跟 `dist/cli-mcp.js` 说 JSON-RPC。

它证明了内存流测不到的东西：`tsup` 有没有把入口打出来、环境变量有没有读到、
`process.exit` 的时机对不对、**Node 自己会不会往 stdout 混警告**。

⚠️ 两个诚实的弱点：
1. **CLI 的总开关检查与 `startMcpStdioServer` 里的重复了。** 注入掉 CLI 那处，
   测试**不会红** —— 因为服务器层还会拒绝，且两处文案都含"总开关是关着的"。
   行为是对的（纵深防御），但那条测试分不清是哪一层拒的。
2. **"绑定地址不从配置读"那条 e2e 断言不是承重的。** stdio 根本不监听，
   所以那个字段对 stdio 无意义。它只保证"写歪了不会崩"。

这仍然不是"真实 MCP 客户端"—— 没有握手协商、没有真实客户端的容错行为。
但它是没有客户端时能补上的最接近的一层。

### 9.15 Web 接线时暴露的类型形状 bug

给 `AiBreakdown` 接 `onHealth` 时，`tsc` 报 `Property 'health' does not exist
on type 'BreakdownOutcome'`。

我先后清了三轮构建缓存（`dist`、`tsbuildinfo`）都没用，
还跑了 `--traceResolution` 确认解析到的就是那份正确的 d.ts。

最后一行的诊断定位了真因：

```ts
type Success = Extract<BreakdownOutcome, { ok: true }>;
export const s: Success['health'] = ...;  // ← 这里报错
```

**成功分支上根本没有顶层 `health`** —— 它在 `proposal` 里。
失败分支上才有。两个分支形状不对称，所以 `outcome.health` 不合法。

修法是把 `health` 提到两个分支的顶层。

> 教训：**怀疑构建缓存之前，先怀疑自己的类型。**
> 我在缓存上花了三轮，而真因是我自己上一轮写下的不对称 API。

### 9.16 密钥命令：又一次差点写坏真实钥匙串

写 `cli-ai` 的时候，`runAiKeyCommand` 默认会建一个**指向登录钥匙串**的
`SecretStore` —— 而我的测试直接调它。如果照原样跑，**每个用例都会往
真实登录钥匙串写一条**。

这次在**跑之前**就发现了（上一轮是跑完才发现），做法是把存储做成可注入的，
`AiKeyCommandDeps` 从第一天就留出 `store` 与 `available`。

⚠️ 但手工验证时还是中了一次：我用 `HEYTA_KEYCHAIN_PATH` 指定临时钥匙串，
**而那时 CLI 还不读这个环境变量** —— 于是密钥落进了登录钥匙串。
已删除，并顺手把 `HEYTA_KEYCHAIN_PATH` 做成正式功能
（让用户能把 heyta 的密钥放进**专门的钥匙串**，而不只是测试用）。

> 两次事故的共同形状：**"我以为它去了 A，其实它去了 B"**。
> 第一次是 `-i` 的换行截断，这次是环境变量根本没被读。
> 两次都是"通过**独立事实源**复查"才发现的 ——
> 第一次用 `security dump-keychain`，这次用 `security find`。
> **不要相信被测代码自己的 `get`。**

### 9.17 "没有真实客户端"没能成为借口

我一直把"未用真实 MCP 客户端跑过"列为缺口。这一轮改了做法：
**照着 MCP 规范逐条自查握手序列**，而不是等客户端。

第一个查的就是 `initialize` 之后客户端会立刻发什么 ——
答案是 `notifications/initialized`，而 JSON-RPC 规定**通知不得有响应**。
我的实现回了一条 `-32601`。**真实客户端会认为服务端违约。**

为什么会漏？因为**我自己写的 100 多条 JSON-RPC 用例全都带 `id`**。
"自己发给自己"的测试结构性地测不出这一类问题 —— 不是覆盖不够，
是**测试的形状**就照不到那里。

修完之后，注入回旧行为：核心 3 条、真实子进程 3 条、HTTP 2 条全红。

> ⚠️ 顺带暴露了一个**测试工具**的坑：我写了个 `expectResponse()` helper
> 去消化新的 `| undefined` 返回类型，正则批量包装时**把通知那组也包了** ——
> 而那些用例断言的恰恰是 `undefined`。于是 3 条正确的测试被改红。
> 教训：**批量改测试的断言方向，比批量改实现更危险。**

### 9.18 又一次"照着规范自查"抓到东西：日志说谎 + 连接失同步

沿上一条思路继续查传输层，撞到 stdio 的单行上限处理：

```ts
log('单行超过上限，连接将关闭。');
buffer = '';   // ← 说关，但没关
```

**两个问题，第二个更严重：**

1. 日志**说的是假的**（说关，实际没关）。一个说谎的日志比没有日志更坏 ——
   排查的人会顺着它去找错的方向。
2. 只丢缓冲会让连接**失去同步**：那一行的剩余部分继续到达，
   被当成新消息解析，后面全是 JSON 解析错误。调用方看到的是
   "服务端在乱回错误"，而真实原因是"我发的东西太长了"。

修成真的 `finish()`。注入回旧行为 → 2 条测试红（各等 5 秒超时，
因为 `done` 永远不 resolve —— 这本身就证明了"没关"）。

> 规律：**这一轮和上一轮抓到的是同一类东西** —— 边界路径上"说了但没做"。
> 上一轮是"通知不该回，却回了"；这一轮是"说要关，却只是清了缓冲"。
> 两处都在**正常路径之外**，两处我自己写的测试都照不到。

### 9.19 上一轮修的"界面不说为什么"，任务行里还在犯

上一轮我在**设置面板**加了能力缺口提示，理由是"配了却跑不起来，界面一个字都不说"。

这一轮发现：**任务行里同样的问题还在，而且更糟 —— 它说的是错的。**

`packages/ai` 明明能具体说明原因（`explainNoCandidate()`，
连"缺能力必须显式声明、heyta 不按模型名猜"都写了），
但 `ai-breakdown.ts` 把它**丢掉**，换成一句概括：

> 没有可用端点能处理这个功能。检查端点是否启用、地址是否合法。

而用户遇到的最常见原因恰恰是**忘了声明能力** —— 那句话会把人引去查
两个**根本没问题**的地方。

> 规律：**"好文案已经写好了但被丢掉"比"没写好文案"更难发现。**
> 前者在代码里看着是对的（`describeRoutedFailure` 确实是句人话），
> 只有把两处并排看，才知道信息在哪一层蒸发了。

修法是把 `describeRoutedFailure()` 降级成**兜底**，并给它写上
"不要在这里重新概括"的约束 —— 这是**结构性**规则（两个文案来源必然漂移），
不是一次修 bug。

### 9.20 🔴 连续三轮"查边界"之后，撞到一个真的隐私 bug

前三轮抓的都是"边界路径上说了但没做"。这一轮换了目标：
**去查用户可见的隐私文案，它的触发条件对不对。**

撞到的是 `apps/web` 里判断"端点算不算本机"的一个**手写正则**。
注释写着"与 `classifyDestination` 同一条判据" —— **它不是**。

最要命的一条：

```
http://127.0.0.1:80@evil.com/v1
  正则 → 本机（`127.0.0.1` 后面紧跟着 `:`）
  真判据 → 远端（`new URL().hostname` 是 `evil.com`，前面那段是 userinfo）
  ⇒ 不显示 E2EE 警告，而数据发给了 evil.com
```

**披露给了一个错误的保证**，用户以为数据没出设备。

> 值得记的是：这条注释**当时是对的意图、错的判断**。
> 写的人（我）知道应该用同一条判据，但选择了"再写一个一样的"
> 而不是"调用那一个" —— 而"一样的"从来不会真的一样。

#### 只修这一处是治标的

按 ADR-0003 的判据，「端点算不算本机」决定要不要给用户看隐私警告
—— 是**产品语义**，本来就不该在 `apps/`。
所以给 `check:layering` 加了第 8 条规则，把"这件事只有一个实现"
变成**可执行的**约束。三个方向都实测：真实 bug 红、比较写法红、合法监听绿。

### 9.21 ⚠️ 我上一轮把一个 bug 的严重程度写错了

上一轮我在 ADR-0010 §3.11 写了"数据发给了 evil.com"。

**这一轮实测推翻了它。** `validateEndpointUrl()` 本来就拒绝带 userinfo 的地址，
所以 `http://127.0.0.1:80@evil.com/v1` 在 `resolveRoute` 阶段就被排除，
**一个字节都不会发出去**。

真实性质是**披露不准**，不是**数据泄漏**。

我为什么会写错：我看到"正则说本机、真判据说远端"，就**直接推断**数据会发出去，
**没有去跑一遍发送路径**。这和前几轮犯的错是同一个根：

| 轮次 | 我断言的 | 实际 |
|---|---|---|
| 11–12 | "测试全绿 = 没问题" | 边界路径照不到 |
| 13 | "判据不一致 = 会泄漏" | 还有第二道防线没查 |

> **两次都是把"看起来必然"当成了"实测过"。**
> 所以这一轮改法：先用真实函数跑一遍发送路径，再下结论。

#### 同一轮里找到的**第二个**同形状实例（这次是真的）

修完回环判据后，同一文件里还有一处平行实现：`resolvePreferredTarget()`
自己遍历路由链，只跳过 `disabled`，而 `resolveRoute()` 还按能力/熔断/URL 过滤。

实测：**披露说 A，请求打到 B，结果 `ok = true`** —— 用户同意了 A，
数据发给了 B（另一家公司），**因为成功所以界面上没有任何提示**。

这一次是实测确认真的发出去了。修法是改用 `resolveRoute()`，
并把**整条回退链**写进披露（回退是真实行为，只披露首选必然不够）。

### 9.22 "落盘了但没人读" —— 我自己的诚实清单里早就写了

第 7 轮我做熔断状态落盘，35 条测试全绿，Web 侧也接了 `onHealth` 往里写。
当时我在诚实清单里记了一行：

> `AiBreakdown` does not seed `healthSeed` from persisted health ——
> persist path exists, seed path not yet wired.

**之后整整七轮，我每轮都在报告里说"四个交付物已全部落地验证"。**
而那一行意味着：熔断状态**活不过一次刷新**，落盘逻辑是死代码。

> ⚠️ 教训不在于"漏了功能"，而在于**我怎么描述状态**。
> "落地并验证"对落盘那一半是真的（有 35 条测试），
> 但整体是**假的** —— 因为没人读它。
>
> **"测试全绿"和"用户受益"是两件事。**
> 落盘测试问的是"存进去能取出来吗"，从来没问"取出来的东西被用上了吗"。

这一轮把它接上了，并且用的是**承重断言**：跳闸的端点这次不许再发请求。

#### 顺带确认了一个设计性质

加了 `healthSeed` 之后，披露（不含熔断状态）可能指向一个**已经跳闸**的端点，
而实际请求会打到回退链上的下一个。

这在有回退链披露的前提下是安全的 —— 用户按发送前已经看到过那个备选。
**但反过来也说明：如果没有回退链披露，熔断回退就是一个未披露的目的地变更。**
所以 §3.11.0b 那条披露不是锦上添花，是必需的。已用测试钉住。

### 9.23 判据：**去数一数这个函数被谁调用**

上一轮修的是"熔断状态只写不读"。这一轮用同一个思路系统扫了一遍：
把 `packages/ai` 里**文档写着"给界面用"**的导出逐个去 `apps/` 里找调用点。

结果 `describeEndpointHealth()` —— 文档写着「给界面用」——
**调用点 0 个**，设置面板里连 `health` 这个词都没出现过。

后果：跳闸中的端点在设置里和正常端点**长得一模一样**。
用户只看到"AI 暂时不可用"，不知道是哪个端点、多久恢复。

> **「给界面用」这句注释不是证据，调用点才是。**
>
> 这已经是同一个形状的第二例了（上一个是"落盘没人读"）。
> 两次我的自查方式都是"读代码、看测试" —— 两次都漏了。
> 这次换了方法：**数调用点**。这是一个可以机械执行的动作，
> 不依赖我"想起来去检查"。

### 9.24 "数调用点"的第二次收获，以及一个新信号

沿第 16 轮的方法（把文档写着「给界面用」的导出逐个去 `apps/` 数调用点），
这次是 `buildDisclosure()`。它的文档写着：

> 纯函数，**测试与 UI 共用同一条路径**。

**UI 没走这条路径。** 它手写了一套披露 JSX，于是漏掉了
`buildDisclosure` 三个字段里的一整个：`retentionText`（留多久）。

所以披露在界面上一直是**二维**的（发给谁 / 发什么），
而计划 §5 的验收判据 ④ 也只写了那两维 —— **判据和实现犯了同一个错**，
所以没人发现。

> ⚠️ 这一轮的信号和前面几轮不同：
> 前面几次是"底层写好了、界面没接"。这次是**"连验收判据都漏了同一维"**。
> 当判据本身不完整时，"按判据验收"是查不出来的。
>
> 唯一查出来的方式是回到**源头**（`buildDisclosure` 到底产出什么），
> 而不是回到判据。

补上之后，测试改成**逐字比对**界面文案与 `buildDisclosure()` 的输出 ——
界面再也不可能自己漂移一份。

### 9.25 🔴 数调用点的最大收获：一个**配了完全不生效**的功能

沿第 16-17 轮的方法继续数。这次数的是"这个功能的**写入端**在哪"。

- 设置面板写本机 API 配置 → **浏览器 localStorage**
- MCP 服务读本机 API 配置 → **`~/.heyta/local-api.json`**
- 中间写那个文件的代码 → **0 处**

> **在界面上把本机 API 配好，是一件没有效果的事。**
> 开关、token、逐个工具授权，界面全都有、全都对、全都有测试 ——
> 而服务永远看不到它们。**且不会有任何报错。**

这比前两轮更严重：前两轮是"某个辅助函数没人调"，
这次是**一个完整功能的两个半边各说各的存储**。

#### 修法：`heyta-ai local-api init`

一条命令生成 token、写 0600 的配置文件、打印 MCP 客户端片段。

**关键是这次做的是端到端验证**：真的 `spawn` `cli-mcp.js`，
断言服务能读、能起、能列出恰好授权的工具、换 token 会被拒。

> 只测"文件写对了"是不够的 —— 这个 bug 的本质就是**两端不一致**，
> 所以验证必须**同时跨过两端**。

### 9.26 修完"没人写文件"之后，界面还在骗人

第 18 轮补上了 `local-api init`。但设置面板里的本机 API 区块
**读起来仍然像"我在这里打开，它就生效了"**。

> **一个不会生效、也不会报错的开关，比"没有这个开关"更糟** ——
> 它消耗用户的信任，还让用户以为自己已经配置好了。

补上诚实说明时**刻意没做**"一键把浏览器配置写成文件"：
浏览器写不了 `~/.heyta/`，而且那会变成第三份配置真相。
**指路比伪造能力诚实。**

一个副产品：这段文案第一次写被 `check:ui-language` 挡住了
（`<code>` 里只有 ASCII）。**门禁逼我把「文件」「命令」两个中文前缀写出来**，
而这恰好让说明对不懂技术的用户也可读 —— 门禁在这里不只是合规检查。

### 9.27 最后一次验收又抓到两个 —— 都是"机制在、接线不在"

这次不是找新功能，是**逐条对着目标验收**。两条都没通过：

| 要求原文 | 实际状态 |
|---|---|
| 「写入必须经 dispatch()（有测试钉住）」 | 单元层证明"端口长得像 dispatch"；**真实二进制上从未跑过一次写** |
| 「加密条目可列举但不可读（Bear 范式）」 | 机制全在，但 `isReadable` 缺省 `() => true` 且**没有任何壳传过它** → 产品里 `readable` 恒为 true，**永不触发** |

> 这已经是同一个形状的第 N 次了（"给界面用"没人调、落盘没人读、
> 配置文件没人写、现在是**隐私开关没人传**）。
>
> 共同点：**能力写好了、测试写好了，而"有没有人用"从来没被检查过。**
> 而这四次里，**两次的默认值是 fail-open** —— 静默地退到"不设防"那一侧。

补上之后：
- 跨进程证明写入真的落库（A 进程写、B 进程读）
- `isReadable` 改为**必填**，壳必须显式回答 → 编译期挡住下一次 fail-open

#### ⚠️ 一次**无效的注入验证**（方法论教训）

注入"写工具不 submit"之后测试**全绿**，我一度以为是自己的测试不行。
真相是注入没生效：`@heyta/local-api` 是 **external** 依赖，
运行时从 `packages/local-api/dist` 读 —— **只重建 node-host 不够**。

> **端到端测试的注入面可能横跨多个构建产物。**
> 注入前要问："我要改的这个包，测试运行时加载的是源码还是 dist？"
> 否则注入空转，而结果**伪装成"测试没抓住 bug"** —— 这会让我错误地
> 去加强一个本来就有效的测试，或者更糟：得出"这段代码没问题"的结论。

### 9.8 🔴 真实端点实测（2026-09-26）—— 两条被真数据推翻的假设

新增 `scripts/verify-ai-live.mjs` / `pnpm verify:ai-live`：
**用真实 API key 打真实端点**，验的是"闸门 + 端口 + 数据面 + 失败分类"在真链路上成不成立。
配置放仓库外（`/tmp/heyta-ai-live/provider.json`，权限 600），
没配置时**明确打印"跳过"并退出 0**。

实测环境：本机 CC Switch 的 `qijiopus` 供应商（`openai-proxy.miracleplus.com/v1`，
58 个模型可选）。**全部 17 条断言通过** —— 含"未授权时网络请求数 = 0"（**数出来的**，
不是看返回值）、"请求体只有 `model` + `messages`"、"不存在的模型 → `http-error` + 状态码"。

🔴 但它顺带**推翻了两个我原本写在代码里的假设**：

**发现一：模型会把相对日期算错，而且错得离谱。**

同一个输入「明天下午三点开周会 高优先级」，**同一天**跑：

| 来源 | 结果 |
|---|---|
| **规则内核** `parseCapture` | `dueDate = 2026-09-27` ✅ |
| **真实模型**（`deepseek-v4.1-flash`） | `"datetime":"2026-05-08T15:00:00"` ❌ |

今天是 **2026-09-26**，"明天"是 **09-27**。模型给了 **5 月 8 日** —— **错了约 4 个半月**。

> 这条把 ADR-0005「**LLM 做得最少**」从一条原则变成了**实测结论**：
> **相对日期绝不许交给模型算。** 模型没有"今天"这个概念，
> 它只有一个训练截止日 —— 让它算"明天"等于让它猜。
> 规则内核有注入的 `now`，它算得对，而且**永远**算得对。
> → AI 只能做规则做不了的事（把乱文本里的意图抽出来、提议拆解），
> **凡是能用规则算准的，一律不交给模型。**

**发现二：规则内核本身还有洞，而且是被真输入照出来的。**

同一个输入，规则内核的结果是：

```
title    : 下午三点开周会 高优先级
dueDate  : 2026-09-27T00:00:00.000Z
priority : undefined          ← ❌ 「高优先级」没被识别，留在了标题里
```

- ✅ **「高优先级」已修**（2026-09-26 之后）：`packages/domain/src/capture.ts:155-158`
  的 `PRIORITY_BY_WORD` 现在覆盖「高优先级 / 最高优先级 / 紧急 / 加急」等说法，
  `priority` 不再留在标题里。~~这是真缺陷~~ —— **已修复**。
- ❌ **「下午三点」仍没被解析成时间**（`dueDate` 只有日期，`Task` 也没有时间字段）。

> ⚠️ 第二条暴露的是**产品缺口而不是解析缺口**：`Task.dueDate` 是**日期**，
> 没有"时刻"。所以「下午三点」**目前无处可放** —— 要么加字段（schema 变更，
> 按 AGENTS.md §3.3 要谨慎），要么明确"heyta 的截止是日期级"。
> 这需要一次产品决策，**不是顺手改解析器能解决的**。

**这两条都比"调研结论"值钱**：它们是从**真端点 + 真输入**上撞出来的，
而 47 条打桩测试一条都没碰到 —— 因为桩是按我的理解写的，
**我的理解里就没有"模型会算错日期"这一条**。
