## 1. 打包方式：我替换掉的命令里，写着它为什么必须那样写

**当时怎么想的**：`deploy.sh` 的文档流程用 `git archive HEAD`，但它**只打已跟踪文件** ——
我这一轮有大量未提交改动要带上服务器，于是很自然地换成了「对这几个目录打 `tar`」。

**错在哪**：那条命令下面**紧跟着一行注释**：

```
ssh ubuntu-jcli 'cd ~/heyta && tar xzf /tmp/heyta-server-src.tar.gz'   # .env 不在归档里，会被保留
```

我读到了它，但把它读成了"一句说明"，而它其实是**这条命令设计的理由** ——
`git archive` 的"只打已跟踪文件"不是限制，是**特性**：它正好排掉了 `.env`、`node_modules`、`dist`。
换成 `tar` 之后，那条注释描述的性质就**不成立了**，而注释还在那里，于是它从"设计理由"变成了"一句假话"。

**代价**：生产 `.env` 被本机开发配置覆盖，连 `JWT_SECRET` 都换了。
真正危险的**不是** postgres 起不来（那很吵，会被立刻发现），而是
**所有已签发令牌与在途验证链接会失效，且在容器重启之前一声不响**。

**已经建立起来的防护**：
`docs/reference/environment-traps.md` 新增条目（含正确写法与解包前自检命令）、
`deployment.md` §3.8 就地加了警告框。

## 2. 脚本位置：我把它当成了"资源"，忘了它有"加载时机"这一维

**当时怎么想的**：我在重写 `renderPage` 时，把 `scripts` 和 `<style>` 一起当成"页面头部的东西"，
顺手放进了 `<head>`。服务端渲染出来的 HTML **看起来完全正确** —— 脚本标签在、`data-*` 属性在、
结构干净，单测（当时）也全绿。

**错在哪**：`<script src>` 没有 `defer`/`async` 时是**同步执行**的。
它在 `<head>` 里执行的那一刻，`<body>` 还没被解析 ⇒ `document.body === null`。
也就是说：**这不是"样式问题"，是时序问题** —— 而时序在服务端渲染的产物里**根本看不出来**。

**代价**：用户点邮件里的登录链接，页面出来了、按钮**点了完全没反应**。

**已经建立起来的防护**：
① 脚本移回 `</body>` 之前；② 脚本里加 `DOMContentLoaded` guard（让位置不再承重）；
③ 服务端单测断言脚本位置（挪回 head ⇒ 2 条转红）；
④ **线上真浏览器**断言无 `pageerror` 且按钮真的有反应。

📌 这条与 §1 是**同一个形状**：**我验证的是"我产出的那个东西"，而不是"用户实际经历的那条路径"。**
§1 里我验的是"包解开了"，§2 里我验的是"HTML 是对的"。

## 3. 脱敏正则：我写了一个"看起来对"的正则，然后**没有验证它**

**当时怎么想的**：列生产 `.env` 核对配置，需要遮住密钥，于是写了
`sed -E "s/(PASS|SECRET)=.*/\1=***/"`。

**错在哪**：`.env` 里的键是 **`POSTGRES_PASSWORD=`** —— 它不含 `PASS=` 这个子串，
所以正则**一个都没匹配上**，但命令**照样成功退出**，输出看起来也像正常脱敏后的清单。
我没有做那件一秒钟就能做的事：**数一遍**（`.env` 里有几个敏感键，输出里有几个 `***`）。

**代价**：生产数据库密码被打印在会话记录里。

**已经建立起来的防护**：无代码防护（这是操作纪律）。
可复用的一句话：**脱敏是"必须验证的转换"，不是"顺手加的 sed"** ——
它失败时**没有声音**，只能靠"进去几个、出来几个"来对账。

## 4. 阈值：我在一个"没有阈值可言的判断"上发明了数字

**当时怎么想的**：写线上验收时要断言"应用真的打开了"。文档里提到过 `#root` 渲染出"14629 字符"，
于是我照着写了个 `#root.textContent.length > 1000`。

**错在哪**：那个 14629 量的是 **`innerHTML`**，而我量的是 **`textContent`**（实测 145）。
更重要的一层：**"应用打开了"本来就不该用字符数表达** —— 它是个**元素可见性**问题。
我先把失败阈值从 1000 调到 200，**又红了一次**，才意识到该换判据而不是调数字。

**代价**：两轮无意义的红；而且它反过来**掩盖**了真正该验的东西。

**已经建立起来的防护**：改成断言**真实元素可见**（任务输入框 + 收件箱标题）；
并在测试注释里写明"不要再发明数字"。同一条教训也写进了
`e2e/live-site/live-domain.spec.ts` 里那段 `#root` 注释。

📌 附带一条自我提醒：**当我在调一个判据的阈值时，通常说明这个判据选错了。**
正确的判据不需要调参。

## 这几条的共同点（如果只记一句）

**四次里有三次，问题都不在我写的那段代码，而在我"以为已经验过了"的那一步。**

| 我以为验了 | 实际没验 |
|---|---|
| 包解开了、文件都在 | 包里**多带了什么** |
| 服务端渲染的 HTML 是对的 | 浏览器**真的跑起来**是什么样 |
| 我加了脱敏 | 脱敏**真的匹配上了** |
| 断言变红了又变绿了 | 这个判据**该不该存在** |

对应的动作只有两条，都很便宜：
**① 验证"用户实际走的那条路径"，而不是"我产出的那个中间物"；
② 对自己写的每一道"防护"，问一句"它失败时会不会有声音"。**
