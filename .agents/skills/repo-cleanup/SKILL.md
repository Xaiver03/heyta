# 仓库整理（Repo Cleanup）

本技能的每条纪律都来自真实事故或权威工程实践（Fowler《Refactoring》的
Extract/小步手法、Google Eng Practices 的"重构单独成 CL、~100 行粒度"）。
2026-10-02 在本仓库完整跑过一轮（App.tsx 2603→2198、app.css 3163→14 模块），
下列"实测"均出自那一轮。

## 铁律

```
没有基线不动手；没有测试不拆分；没有门禁绿不提交；
结构重构与行为变更绝不同提交；一次只做一个重构。
```

## 何时使用

**用**：用户明确提出"整理/清理/重构仓库"；某文件大到阻碍改动；两处实现开始漂移。
**不用**：功能/修复任务里的局部顺手清理（留在原任务，测试保持绿即可）；
vendored 代码（`packages/sync-core`、`server/` 上游底座 —— 改了要动 PROVENANCE）；
"看着不顺眼"但没有量化信号、也没有后续改动计划的文件。

## 阶段一：审计（只读，先拿数字）

```bash
# 文件行数 Top（排除生成物/证据目录）
git ls-files '*.ts' '*.tsx' '*.css' | grep -vE '(dist|generated|/evidence/)' | xargs wc -l | sort -rn | head -25
# 超长行（>120 列）逐文件计数 —— 用脚本数，不要用 awk（END 里 FILENAME 是最后一个文件）
# 死代码 / 未用依赖：corepack pnpm dlx knip   ⚠️ 见下方陷阱
# 重复块：corepack pnpm dlx jscpd <dirs> --min-tokens 70
```

**先剔除"天然就大"的文件再下结论**：i18n 词条表、法务文档、schema 清单、
server 大 spec —— 它们是合法聚合，拆了反而伤 zh/en 同步与可读性。
本仓库实测：>120 列的行 85% 是词条/法条的单行字符串 ⇒ **长行不动**；
jscpd 重复率 0.97% ⇒ **重复项不动**。审计的目的就是证明"哪些不用做"。

**knip 陷阱（实测）**：没配 entry 点时输出全是桶导出（barrel re-export）误报。
导出级发现一律"先标 @deprecated 不删"，文件级/依赖级也要过复核清单
（无字符串/动态引用、无包外入口 —— 原生壳加载的 js、e2e、scripts、
被测试按**源码文本**解析的文件，knip 都看不见）。没配好 entry 就别信它。

## 阶段二：计划

1. 按 **seam**（责任边界）分组，不按文件分组；每组打 影响力 × 风险 分，
   "高影响 × 低风险"优先 —— 纯移动 > 抽共享逻辑 > 删死代码 > 拆 UI/样式。
2. 每组写清：动作 / 涉及文件 / 验证命令 / 回滚方式（独立提交即可 revert）。
3. 冻结范围：schema 版本、线协议、已应用迁移、token 事实源（tokens.css）、
   生成物。要越界，先停下问用户。

## 阶段三：执行

1. **一次一个重构**：做完 → 跑门禁 → 提交 → 再开始下一个。
2. 提交纪律：纯移动单独成提交（逻辑逐字未动，只挪位置 + export + import）；
   文件内重构、跨文件移动、行为变更三者分开；提交信息写"为什么"。
3. **纯移动前必须盘点"谁在按路径/按文本读这块"**（2026-10-02 实测撞到两道）：
   ```bash
   grep -rn "<被搬文件名>" --include='*.ts' --include='*.tsx' --include='*.mjs' \
     apps packages scripts e2e | grep -v "import\|from '"
   ```
   - 按文本解析源码的门禁（如 landing 外壳对账读 `const ALWAYS_ON_VIEW_TABS`
     声明块）→ 读取路径跟着搬；**新文件的注释里不许出现锚点串的字面形式**
     （实测：注释里写了 `const ALWAYS_ON_VIEW_TABS`，indexOf 先命中注释、
     切片截进别的数组 ⇒ 对账静默拿错数据）。
   - 按文件路径锚定的豁免表/棘轮（如 check-hardcoded 的排版豁免、
     check-row-single-source 的 ht-* 族基线）→ 要么把路径归一化到聚合器
     （组合数一个不多一个不少），要么让它扫全部模块；**响亮报错的语义保留**。
4. CSS 拆分：聚合器只放 `@import`，**顺序 = 原文件顺序 = 级联顺序**；
   媒体块（≤768px 之类）必须压最后 —— 同特异性、源序后者胜。
5. **发现行为差异立即停**：两份"重复"实现语义不同时，差异可能是 bug，
   但修它属于行为变更 —— 记录、另开任务，不顺手修。

## 阶段四：收尾

1. 重跑阶段一的同口径命令，逐项对账"基线 → 结果"，数字写进报告。
2. 跑完整门禁；宣称完成前**本轮新跑、读完整输出、确认退出码** ——
   引用上一次的绿色输出不算验证。
3. UI/样式拆分必须真浏览器截图（浅色 + 深色双主题、零 pageerror），
   **人打开看** —— "结构完整/深色不是反色/无样式缺失"这种结论只有图能给。
4. 报告回答三问：行为变了什么（正确答案通常是"无"，附测试数前后一致
   的证据）；什么没做、为什么（如 knip 需先配 entry，登记为下轮候选）；
   下一轮候选清单。

## 红线（触发即停）

- 需要改 schema 版本 / 线协议 / 已应用迁移才能继续；
- 要动 vendored 代码或 token 事实源；
- 触碰区域没有测试覆盖（先补测试造出 seam 再回来）；
- 开始"顺手"改行为/文案/取值；
- 为了让检查变绿而改检查的**判据**（迁移检查的**路径**是配套，判据语义不许动）。

## 常见借口对照

| 借口 | 现实 |
|---|---|
| "文件太大，先拆一半下周继续" | 每个已提交的重构都处在门禁绿状态；"拆一半"不可提交 |
| "这两处差不多，直接合并" | "差不多"里藏的就是行为差异；先 diff 行为再谈合并 |
| "knip 说没人用，删了" | 工具看不见动态引用与包外入口；过复核清单才能删 |
| "顺手把这个 bug 修了" | 那是行为变更，另开任务 |
| "测试改一下就能过" | 不为绿灯改测试；是模型问题改模型 |

## 完成核对清单

- [ ] 基线与结果都是同口径命令产出的数字
- [ ] 每个提交单一目的：纯移动 / 单个重构 / 行为变更，无混杂
- [ ] 纯移动提交零语义 diff，且"按路径/按文本读它的人"全部跟着搬了
- [ ] 完整门禁本轮跑过、退出码读过
- [ ] UI 改动有双主题截图，且人看过
- [ ] 冻结范围未被触碰
- [ ] 收尾报告含：量化对账、遗留清单、下轮候选
