# 镜像输入清单 —— 唯一事实源。路径**相对于 server/**。
#
# 谁在读它：
#   · `server/scripts/deploy.sh`      —— 经 `scripts/image-inputs.sh`（四段判断都吃这一份）
#   · `.github/workflows/heyta-server-image.yml` —— 同一个读者，用它算 OCI revision 标签
#
# 为什么只有一份：这四个判断（算 revision / `git diff` / `git diff --cached` /
# `git ls-files --others`）原来在 deploy.sh 里**各自抄了一遍**路径列表，而"哪几个
# 路径算镜像输入"是一个判断被写了四遍 —— 这正是 AGENTS §3.2 那条教训的形状
# （"失败判据被抄了三遍，三遍都漏了同一项"）。发布流水线落地后就有了第五个消费者，
# 而它和 deploy.sh 之间**必须逐字节同集合**：两边算出的 revision 差一个提交，
# 自托管用户每次 `deploy.sh` 都会被 `verify_supersync_image_revision` 以
# "image revision does not match" 硬拒（实测那条是 `exit 1`，不是警告）。
#
# ⚠️ 每一项都必须和 `Dockerfile` 真正 COPY 的东西对齐。**漏一项的后果不是报错，
# 是"跑旧镜像配新迁移"那类事故换个入口重来**：revision 标签会算出一个"看起来最新"的
# commit，而镜像里其实是旧的前端。所以 web 阶段一旦把 `apps/web` 变成镜像输入，
# 这里必须一起加上 —— 两边都在同一个提交里改。
#
# ⚠️ 这里**不许**出现不存在的文件。不存在的 pathspec 不会报错，它是被**静默忽略**的：
# `git log -1 -- <存在> <不存在>` 与只给 `<存在>` 回的是同一个提交（rc 都是 0），
# 而 `git diff --quiet -- <不存在>` 恒真。也就是说写错一个名字的两个方向都不报，
# 只有一方向是对的（不存在），那份输入从此不参与算 revision。
